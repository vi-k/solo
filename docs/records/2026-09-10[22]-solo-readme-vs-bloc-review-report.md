## 1. P2 — повторный load скрывает продолжающуюся загрузку

Место: `packages/solo/README.md:110`;
перевод: `packages/solo/README.ru.md:115`.

В быстром старте onFinish сбрасывает loading для любого Job с ключом
load. Повторный load во время первого запроса применяет droppable:
возвращает прежний Job, а новый завершает с Cancelled до старта.
Этот новый Job тоже вызывает onFinish. В результате loading становится
false, хотя первый запрос ещё выполняется. Экран из раздела Flutter
показывает кнопку вместо индикатора загрузки раньше завершения запроса.

Воспроизведено на Profile и ProfileController, извлечённых из README:
первый load запущен, API ждёт Completer; после второго вызова
same job: true, running: true, loading: false. Защиты от завершения
дубликата в примере нет. Реализация droppable в solo_base.dart:234
явно завершает новый Job; существующий policy_test проверяет этот хук.
Тест README вызывает оба load до старта первого, когда loading ещё
false, поэтому не обнаруживает ошибку.

Минимальное направление исправления: сбрасывать флаг только для load,
который запускался; пропускать Cancelled с started: false. Проверить
повторный вызов после начала запроса и сброс при ошибке и отмене.

**Вердикт:** исправлено. onFinish пропускает Cancelled с started: false.
Повторный load сохраняет loading; успех, ошибка и отмена снимают флаг.

## 2. P2 — ошибка первого emit оставляет заказ в _inFlight навсегда

Место: `packages/solo/doc/vs-bloc.md:1005`;
перевод: `docs/ru/solo/vs-bloc.md:1028`.

В CheckoutCubit метод _pay вызывает emit(Paying()) перед try/finally.
Если onChange наблюдателя один раз бросает ошибку, _pay завершается
до входа в try, а _inFlight.remove не выполняется. Повторный pay для
того же заказа возвращает сохранённую ошибочную Future и больше
не обращается к API, даже когда наблюдатель уже исправно работает.
Сбой наблюдателя — один из явно рассматриваемых сценариев документа,
но представленное как рабочее решение в пункте 7 его не выдерживает.

Воспроизведено на CheckoutCubit из извлечённого пункта 7 с наблюдателем,
который бросает только на первом onChange. После первого отказа
повторный вызов дал same future: true, same error: true, API calls: 0.
Дублирование удерживается завершённой Future, а не работающим платежом.

Вызов наблюдателя и повторное выбрасывание ошибки подтверждены
в [исходнике BlocBase.emit](https://github.com/felangel/bloc/blob/master/packages/bloc/lib/src/bloc_base.dart).
Минимальное исправление — перенести первый emit внутрь try, чтобы
finally снимал регистрацию при любом выходе из _pay. Проверить
повторный платёж после однократного сбоя до обращения к API.

**Вердикт:** исправлено. Первый emit перенесён внутрь try/finally.
После однократного сбоя наблюдателя повторная оплата обращается к API
и завершается успешно; ошибочная Future больше не удерживает заказ.

## 3. P3 — краткое описание uncancellable обещает остановку на выходе

Место: `packages/solo/README.md:228`;
перевод: `packages/solo/README.ru.md:235`.

В Concepts сказано, что uncancellable придерживает отмену на время
вызова и сдаётся после него. На самом деле успешное действие возвращает
значение даже при отложенной отмене; обычный код после await выполняется.
Cancelled бросает следующая контрольная точка. Читатель, положившийся
на краткое описание, может оставить побочный эффект после await,
ожидая, что при отмене управление туда не дойдёт.

Выполненный пример: cancel во время секции, затем завершение Completer.
Флаг после await изменился, ctx.check после него бросил Cancelled,
итог Job — Cancelled(manual). Реализация async_job возвращает результат
из try и применяет отмену в finally без проверки после секции.
Раздел Rules that are not visible in signatures уже описывает это
правильно; два объяснения в одном README расходятся.

Минимальное исправление — в Concepts тоже назвать следующую контрольную
точку, а не обещать остановку на выходе из uncancellable.

**Вердикт:** исправлено. В Concepts обоих README названа следующая
контрольная точка отмены; обычный код после секции может выполниться.
