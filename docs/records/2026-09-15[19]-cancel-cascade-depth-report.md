# Глубина каскада отмены: два потолка и заклинившее дерево

> **Состояние на 2026-09-15:** замерено, вариант C с E выбран владельцем
> и внесён; раздел «Что вышло» в конце записи. Кругов ревью было два,
> и числа этого раздела они переписали — итог в конце записи, разбор
> в `2026-09-15[20]-cancel-cascade-fix-review.md`
> и `2026-09-15[21]-cancel-cascade-fix-review-2.md`.
> **Что это:** отчёт о замере порога рекурсии в каскаде отмены и о том,
> в каком состоянии остаётся дерево после переполнения стека.
> **Связанные записи:** `2026-09-15[17]-async-job-project-review.md`
> (находка в связке L1), `2026-09-15[18]-async-job-review-fixes-report.md`
> (волна, в которой этот пункт оставлен сознательно).

## Зачем мерили

Ревью назвало переполнение стека в каскаде отмены пунктом связки мелочей и дало
порог «6000–12000 уровней». Волна правок его не трогала: итеративная раскрутка
требует разрезать `cancelWith` на фазы, а это точка расширения, которую
переопределяет `solo`. Перед тем как писать спеку, нужны были свои числа:
на чём рвётся, что именно остаётся после разрыва и сколько стоит не чинить.

## Зонд

Цепочка вложенных задач: каждая регистрирует `ctx.onCancel`, самая глубокая
ждёт на `Completer`, который завершает её же колбэк. Это обычный приём «передай
отмену работе», поэтому счётчик `fired` считает не события, а тела, которым
реально сказали остановиться.

```dart
Future<void> down(JobContext ctx, int left) async {
  // What a real body does with a cancellation: hand it to the work.
  ctx.onCancel(() {
    fired++;
    if (left == 0 && !stop.isCompleted) {
      stop.complete();
    }
  });
  if (left == 0) {
    bottom.complete();
    await stop.future;
    return;
  }
  if (!tight) {
    // What any real body does before it spawns the next child: suspend.
    await null;
  }
  final child = Job.deferred<void>((c) => down(c, left - 1));
  jobs.add(child);
  await ctx.run(child);
}

final root = Job<void>((ctx) => down(ctx, depth));
jobs.add(root);
await bottom.future;

Object? thrown;
try {
  root.cancel().ignore();
} on Object catch (error) {
  thrown = error;
}
final marked = jobs.where((job) => job.isCancelled).length;
```

Зонд запускался изнутри пакета, по одному прогону на процесс:
`dart run cascade_probe.dart <глубина> [-v] [--tight]`. В дереве он
не оставлен.

## Порог каскада

```text
depth 3126  built 3127  threw -                   marked 3127  fired 3127
depth 3127  built 3128  threw StackOverflowError  marked 3128  fired 0
```

Граница резкая до одной задачи: **3127 задач отменяются, 3128 обваливаются**.
Пять прогонов с каждой стороны дали одинаковые числа, разброса нет.

Это вдвое ниже нижней границы, названной ревью. Противоречия тут нет: порог
определяется размером кадра, а он зависит от тела задачи. Число машинное
и относится к этой форме зонда, а не к пакету вообще.

## Что остаётся после обвала

Глубина 4000, тот же зонд с ключом `-v`:

```text
depth 4000  built 4001  threw StackOverflowError  marked 3128  fired 0
second cancel: threw -                            marked 3128  fired 0
root outcome after 2s: still running
```

Построчно:

- `cancel()` бросает синхронно: вызывающий получает `StackOverflowError` вместо
  `Future`;
- помечены 3128 задач из 4001 — верхняя часть дерева отменена «на бумаге», и её
  контрольные точки бросят `Cancelled`;
- `onCancel` не сработал **ни у одной из 4001**. Колбэки живут
  за `_markCancelled`, который стоит после каскада, и размотка съела его
  на всех уровнях разом. Ни одно тело не узнало, что надо остановиться;
- повторный `cancel()` не бросает и не меняет ничего: он разворачивается
  на `if (_pendingCancel != null) return`. Снаружи чинить нечем;
- корень работает и через две секунды, и будет работать всегда: самой глубокой
  задаче не сказали остановиться, а её ждёт вся цепочка предков.

Это не «упало», а «упало и заперлось».

## Второй потолок, втрое ниже: постройка

Первая версия зонда не дожила до отмены — обвалилась на постройке дерева.
Трасса называет причину:

```text
JobContextBase.startChild -> _DeferredJob.start -> JobBase.start
  -> JobBase._execute -> тело -> ctx.run -> JobContextBase.startChild
```

`ctx.run` запускает ребёнка синхронно, и тело ребёнка бежит до своего первого
`await`. Если этот первый `await` — следующий `ctx.run`, вся цепочка строится
на одном стеке.

Потолок: **1033 задачи проходят, 1034 обваливаются**, причём необработанным
`Stack Overflow` ещё до всякой отмены. Достаточно одного `await` в теле перед
порождением ребёнка, и потолок поднимается до каскадного — ровно это делает
ветка `!tight` в зонде.

Про эту вторую рекурсию ревью не говорило. Рекурсий в ядре две: отмена рвётся
на 3128, постройка — на 1034.

## Варианты и рекомендация

Разбор вариантов целиком — в переписке с владельцем; здесь итог.

| Вариант | Что делает | Чего стоит |
| --- | --- | --- |
| A | Явный стек, порядок сохранён байт в байт | Разрез `cancelWith` на фазы, новый протокол для домена |
| B | Две фазы: пометить всё, уведомить снизу вверх | То же плюс смена наблюдаемого порядка |
| C | Каскад в `try`, `_markCancelled` в `finally` | Десяток строк, контракт не трогает |
| D | Потолок глубины на `ctx.run` | Новый публичный режим отказа |
| E | Записать предел в документы | Ничего |

**Рекомендация: C и E, без A и B.** Довод дал сам замер: потолок постройки
(1034) ниже каскадного (3128) и ни A, ни B его не поднимают — он лечится только
отложенным стартом ребёнка, то есть сменой контракта `ctx.run`. Значит предел
ядра остаётся величиной порядка тысячи уровней при любом выборе, и работа стоит
не в том, чтобы поднять один из двух потолков, а в том, чтобы отказ на пределе
был честным и записанным.

Что даёт C: «ни одно тело не остановлено» превращается в «остановлены все
помеченные, а вызывающий получил громкую ошибку». Полным лечением это
не становится — хвост ниже обрыва остаётся работать, и корень всё равно
не дождётся, — но заклинивание уходит. Две оговорки к реализации: самый
глубокий кадр побежит по колбэкам на почти исчерпанном стеке, и мест вызова
каскада два (`cancelWith` и `_execute`), с разным продолжением.

D отклонён: число было бы произвольным, а отказ — новым публичным поведением,
которое само просит спеку.

Прецедент для формы C в ядре уже есть: `_RunAllGroup` ловит бросивший
`cancelWith` ветки, чтобы остальные не стояли у барьеров (`job_context.dart`).
Каскад «родитель — дети» такой защиты не получил.

## Что вышло

Владелец выбрал C и E и попросил сделать сразу, без спеки.

**C.** Каскад в `cancelWith` обёрнут в `try`, а `_markCancelled` уехал
в `finally`: что бы ни случилось в спуске, помеченные задачи узнают об отмене
на размотке, а ошибка по-прежнему доходит до того, кто звал `cancel`. Второе
место вызова — `_execute`, где тело отменило себя, — там `_markCancelled`
не зовут нарочно, и защита другая: спуск обёрнут в `catch`, ошибка уходит через
`notifyError`, единственную дверь для ошибки, которой некуда деться. Без него
задача не доходила ни до ожидания детей, ни до своей уборки: ошибка вылетала
из `_execute`, и задача не кончалась никогда.

**E.** Оба потолка записаны: абзацем в `packages/async_job/doc/children.md`
и переводе, пунктом в разделе «Границы» `docs/architecture.md` и записью
в `CHANGELOG`.

Замер после правки, тот же зонд:

```text
depth 4000  built 4001  threw StackOverflowError  marked 2894  fired 2889
```

Было `fired 0` — стало 2889 из 2894. Пять прогонов дали одно и то же число.
Пять оставшихся — самые глубокие: их колбэки бегут на стеке, который только что
кончился, и теряются на втором переполнении. Это предсказанная оговорка,
а не сюрприз.

Цена: порог каскада сдвинулся с 3128 задач на 2893 — кадр `try` стоит примерно
семь с половиной процентов глубины. Мелкое дерево не изменилось вовсе:
на глубине 100 отмена по-прежнему доходит до `Cancelled(manual)`.

**Сторожа** — `packages/async_job/test/cascade_depth_test.dart`, два теста
на цепочке в пятьдесят тысяч уровней: отмена снаружи и тело, отменившее себя.
Первый проверяет, что помеченные задачи — префикс цепочки и что всем им, кроме
горстки на дне, сказали остановиться; второй — что ошибка спуска дошла
до наблюдателя. Мутации: снятый `finally` краснит оба, снятый `catch` во втором
месте — ровно второй.

**Чего не делали.** `cascadeToChildren` по-прежнему бросает весь спуск, если
`cancelWith` одного ребёнка бросил: остальные дети такого родителя отмену
не получат. Для переполнения стека продолжать обход бессмысленно — соседнее
поддерево переполнится сразу же, — а для движка домена, чей `cancelWith`
бросил, это отдельный вопрос со своим решением; в группе он решён иначе
(`job_context.dart`, цикл по веткам ловит каждую). Ревью его не поднимало,
и в эту правку он не входил.

## Что переписали круги ревью

Кругов вышло два, и числа предыдущего раздела они переписали. Каскад теперь
ловит на каждом ребёнке, поэтому брат глубокой ветки получает отмену; кадр
`try` за это платится на каждом уровне спуска, но вызов ребёнка на том же пути
написан прямо в цикле вместо вызова, и порог вернулся туда, где был до всей
работы, — 3128 задач. Переполнение, попавшее в колбэк на дне, не объявляется
провалом колбэка — но только там, под собственной разматывающейся отменой ядра;
в любом другом месте колбэк, кончивший стек, объявляется как раньше, иначе
задача, отменившая себя, заклинивала навсегда. Потери на дне не исчезли: их
от нуля до пяти, и число гуляет между прогонами одной программы, потому что
компилятор оптимизирует спуск на ходу. Разбор и вердикты —
`2026-09-15[20]-cancel-cascade-fix-review.md`
и `2026-09-15[21]-cancel-cascade-fix-review-2.md`.
