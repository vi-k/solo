## Находки Astra

### A1. Minor — `stale_emit` теряет происхождение состояния при условном переприсваивании локальной переменной

**Файл и члены:** `packages/solo_lints/lib/src/rules/stale_emit.dart`,
`_Reads.behind`, `_Writes`.

README обещает отслеживать происхождение значения через локальные переменные
и ветви `?:`, `??`, switch expression. Обычное переприсваивание через `?:`
нарушает это обещание:

```dart
Job<void> work(bool flag) => a.enqueue<Feed, void>((ctx) async {
  var feed = ctx.state;
  await ctx.pause(Duration.zero);
  feed = flag ? feed.confirm('x') : feed;
  ctx.emit(feed);
});
```

В обеих ветвях используется снимок до ожидания. Диагностики на `ctx.emit(feed)`
нет. Контрольная замена на `feed = feed.confirm('x')` возвращает диагностику.

**Механика.** `_Reads.behind` выбирает последнее присваиваемое выражение
по условию `value.offset < root.offset`. При разборе `feed` внутри ветви
условного выражения начало этого выражения уже находится раньше читаемого
идентификатора. Поэтому алгоритм выбирает правую часть того же, ещё
не завершённого присваивания. Защита `seen` обрывает цикл и возвращает пустое
происхождение вместо исходного `ctx.state`.

Исполняемый зонд подтверждает практический сценарий: пока первая линия ждёт,
вторая публикует новые посты; после ожидания первая условно меняет отметку
в старом снимке и возвращает старые посты:

```text
After reload: posts=new
After like: posts=old, liked=true
```

Это дефект эвристики `stale_emit`: механизм `SoloLanes` выполняет явно
запрошенную запись, а предупреждение, заявленное для такой формы кода,
отсутствует.

В том же выборе присваивания подтверждён дополнительный пропуск:

```dart
var feed = ctx.state;
await ctx.pause(Duration.zero);
void refresh() {
  feed = ctx.state;
}
ctx.emit(feed.confirm('x'));
```

`refresh` не вызывается. Однако `_Writes` заходит в тело вложенной функции,
а `_Reads.behind` принимает расположенное там присваивание за обновление снимка
после ожидания. Диагностика снова отсутствует.

**Что предлагаю.** При восстановлении происхождения исключать присваивание,
внутри правой части которого находится текущий читаемый идентификатор,
и учитывать границы отложенных функций. Добавить отдельные регрессии для
условного самоприсваивания и невызванной функции, меняющей захваченную
переменную. Аналогичные формы `??` и switch expression следует проверить
отдельно; в этом ревью они не запускались.

Вердикт Claude: подтверждено своим зондом в копии ревьюера:
`feed = flag ? feed.confirm('x') : feed`, `feed = other ?? feed` и невызванная
локальная функция `void refresh() { feed = ctx.state; }` сообщения не дают,
контроль `feed = feed.confirm('x')` даёт. README обещает происхождение через
ветви `?:`, `??` и локальные переменные, так что это расхождение с документом.
Предложение — чинить в части C (`solo_lints` 0.3.0 не выпущен): при поиске
последнего присваивания пропускать то, в правой части которого стоит само
читаемое имя, и присваивания внутри вложенных функций; тесты на `?:`, `??`,
switch expression и невызванную функцию. Итог: исправлено в части C, коммит
`e5675739`, как предложено. `_Reads.behind` пропускает присваивание, правая
часть которого держит читаемое имя; `_Writes` не входит ни в функциональное
выражение, ни в локальную функцию. Тесты на `?:`, `??`, switch expression,
невызванную локальную функцию и функциональное выражение падали на прежнем
коде; `test_variable_read_again` молчит, как молчал. README `solo_lints`
и перевод говорят, что присваивание во вложенной функции копию не обновляет.

### Minor 4. `stale_emit` срабатывает на ветке с ранним выходом

`packages/solo_lints/lib/src/rules/stale_emit.dart`. Код обычного вида:

```dart
final feed = ctx.state;
if (feed.posts.isEmpty) {
  await api.load();
  return;
}
ctx.emit(feed.mark(id, const Mark(true)));
```

Правило сообщает о `ctx.emit`, хотя между чтением и записью на этом пути
ожидания нет: ветка с `await` кончается `return`. README правила честно пишет,
что ожидание в одной ветке считается для записи в другой, так что это описанная
эвристика, а не расхождение с документом. Но форма «ранний выход с ожиданием»
встречается в обычных контроллерах, и ложное срабатывание в правиле уровня
предупреждения учит ставить `ignore`. Предложение: не считать ожидания внутри
блока, который заведомо кончается `return` или `throw` и не содержит записи;
либо назвать именно этот случай в README. Не срочно, годится в следующий минор
`solo_lints`.

Вердикт Claude: подтверждено своим зондом — `final feed = ctx.state; if (...) {
await ctx.join(load); return; } ctx.emit(feed.confirm('x'));` даёт сообщение.
README называет эвристику («a wait in one branch counts for a write in
another»), и правило — линт, а не предупреждение, так что это не расхождение
с документом. Но `solo_lints` 0.3.0 не выпущен, ранний выход с ожиданием —
обычная форма, а сузить дёшево: ожидание внутри блока, который кончается
`return` или `throw` и не содержит записи, для записи после блока не считается.
Предложение — чинить в части C, с тестом и фразой README и перевода. Итог:
исправлено в части C, коммит `e5675739`. Ожидание внутри блока, последний
оператор которого `return` или `throw expr;`, не считается для записи вне этого
блока. Тесты: ранний выход с `return` и с `throw` молчат и падали на прежнем
коде; та же форма без `return` и запись внутри блока после его ожидания
по-прежнему сообщаются. README `solo_lints` и перевод называют исключение.
Другие выходы — `break`, `continue`, `rethrow` — не опознаются, и ожидание
перед ними по-прежнему считается.
