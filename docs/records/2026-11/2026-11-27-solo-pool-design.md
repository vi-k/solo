# Пул: N корней одной линии сразу

Запись бэклога «Пул в линии — подумать после выпуска `solo` 2.0». `solo` 2.0.1
вышел 2026-11-19, условие записи выполнено.

## Решения владельца

- 2026-11-27: «начни дизайн пула, сначала вопросы смысла» — дизайн начинается
  со смысла политик, состояния, накопителя, `pending` и `drain` при N
  одновременных корнях, а не с API.
- 2026-11-27, третья форма: до N корней сразу, и две задачи одного ключа
  никогда не идут вместе. Владелец спросил, не теряется ли в ней
  параллельность, ради которой всё затевалось; разбор ниже, в «Два примера».
- 2026-11-27: «да, ключ в пуле держит порядок и без политики» — в пуле ключ
  значит больше, чем в линии: с `Policy.sequential` он тоже держит порядок
  своих задач.
- 2026-11-27: «бери pool()» — пул объявляется своим вызовом и имеет свой тип,
  а не параметр `lane`.
- 2026-11-27: «согласен, пиши дизайн» — устройство вторым способом: места
  пула — ядра, как у линии, с общей очередью. Довод за него оказался неверен,
  выбор вынесен владельцу заново (раздел «Подходы»).
- 2026-11-27: «бери первый способ, одно ядро с N местами» — пул — одно ядро,
  в котором до N идущих задач.

## Зачем

Корни линии идут по одному. Работа, которой нужна параллельность корней,
сегодня собирается рецептом, и спор 2026-11-12 показал, что оба рецепта
ломаются на краях:

- **партии через `collect`.** Лайк и снятие одного поста попадают в одну
  партию, дети партии идут рядом, и сервер может получить их в обратном
  порядке. Сердце загорается при старте партии, а не при нажатии. Медленный
  лайк держит следующую партию: в зонде лайк `p2`, нажатый в 150 мс, ушёл
  в 2000 мс.
- **рабочая линия с вечной задачей.** Задача, отменённая до того, как рабочий
  её взял, роняет рабочего синхронно (`ctx.run` над законченной задачей
  бросает), и все следующие загрузки виснут без исхода.
  `close(mode: SoloCloseMode.drain)` не кончается никогда: рабочий сам
  не завершится. Предела одновременности в схеме нет вовсе.

У bloc пул — одна строка трансформера. У `solo` сильнее другое: личная `Job`
каждого вызова с исходом, отменой, правилами и `ifCancelled`. Пул должен дать
параллельность, не отняв этого.

Примеров два, оба из спора: лайки по ключу поста и параллельные загрузки.

## Два примера

```dart
final class FeedController extends SoloLanes<Feed> {
  final FeedApi api;
  int _confirmations = 0;

  late final SoloLane<Feed> _reload;
  late final SoloPool<Feed> _likes;
  late final SoloPool<Feed> _uploads;

  FeedController(this.api) : super(const Feed()) {
    _reload = lane('reload');
    _likes = pool('likes', concurrency: 4);
    _uploads = pool('uploads', concurrency: 2);
  }

  // Likes of different posts run side by side, up to four at once;
  // a like and an unlike of one post run in the order of the taps.
  Job<void> setLiked(String postId, {required bool liked}) =>
      _likes.enqueue<Feed, void>(
        key: postId,
        (ctx) async {
          ctx.emit(ctx.state.mark(postId, Mark(liked)));
          await ctx.join(() => api.setLiked(postId, liked: liked));
          ctx.emit(ctx.state.mark(postId, Mark(liked, ++_confirmations)));
        },
      );

  // No key: any two uploads may run together, two at a time.
  Job<Photo> upload(File file) =>
      _uploads.enqueue<Feed, Photo>((ctx) => ctx.join(() => api.upload(file)));

  int get uploading => _uploads.running.length;
  int get waiting => _uploads.queue.length;
}
```

Лайки. Случай зонда спора: лайк `p1` нажат в 10 мс и длится 2000 мс, снятие
`p1` нажато в 20 мс, лайк `p2` — в 150 мс. В пуле лайк `p1` стартует в 10 мс;
снятие `p1` ждёт его конца, потому что ключ `p1` занят, и уходит в 2010 мс,
после лайка; лайк `p2` берёт свободное место и уходит в 150 мс. Сердце
загорается при нажатии: тело стартует сразу, если есть место.

Загрузки. Ключа нет, и загрузки идут по две сразу; третья стартует, когда одна
из двух кончится. Отменённая до старта загрузка из очереди уходит, как в линии,
и никого не роняет: это путь движка, а не рецепта.

Третья форма отнимает только одновременность задач одного ключа. Лайкам она
и нужна, загрузкам без ключа ничего не стоит. Предел N остаётся защитой сети
и сервера, о которой владелец говорил в споре.

## Цели

- Объявленный в конструкторе пул с пределом `concurrency`: до N корней идут
  сразу.
- Две задачи пула с равными ключами (`==`, `hashCode`, как ключи `Map`) никогда
  не идут вместе, с любой политикой, `sequential` тоже. Задачи без ключа этим
  не ограничены.
- Каждый вызов, как в линии, получает свою `SoloJob`: политики, `canStart`,
  `keepWhile`, `W`, `cancellable`, `timeout`, `ifFailed`, `ifCancelled`,
  `isExpectedError`, `first:`.
- `close`, `cancelAll`, `drain` и `pending` видят все идущие задачи пула.
- Накопитель пула (`collect`, `accumulate`) ставит группы в пул.
- `Solo` и обычные линии не меняются ни в чём, что видно снаружи: порядок
  событий, число микрозадач, отладочные строки, пути виртуальных вызовов
  (раздел «Критерии приёмки»).
- Минорный выпуск `solo` 2.1.0 без ломающих правок.

## Не цели

- Линия или пул по ключу без предела, заведённые на лету. Это по-прежнему
  «Не цели» дизайна линий: число идущих корней перестало бы быть ограниченным
  объявленным.
- Пул в `Solo`. `Solo` остаётся одной очередью.
- Изменение `concurrency` после объявления.
- Приоритеты и справедливость между ключами: пул берёт первую по очереди задачу
  со свободным ключом, и только.
- Взаимное исключение между пулом и линией или между двумя пулами: задачи,
  которые не должны пересекаться, ставятся в одну линию или в один пул с общим
  ключом.
- Правки `async_job`: пул живёт в `solo`, ядро о нём не знает.

## Антицели

- Параллельность по умолчанию: без явного `pool` корни идут по одному, как
  сегодня.
- Тихая перемена поведения `Solo` или линий.
- Ломающие правки: новый член интерфейса, который реализуют пользователи, или
  новый вариант sealed-класса `SoloPending`.

## Подходы

Сейчас у каждой линии своё ядро `_SoloLaneCore` (`lane.dart:297`). С ядром
связано больше, чем одно поле `current`:

- очередь: её создаёт ядро (`lane.dart:310`), и окно стартовых правил очередь
  берёт у своего ядра (`_SoloQueue._held`, `queue.dart:202-205`);
- `SoloLaneId`: каждое ядро заводит свой (`lane.dart:333-334`);
- задача: `_destination` — ядро, которое её сделало, `final`; по нему
  `isQueued`, `adoptedBy` и `cancelWith` читают очередь и окно правил
  (`job.dart:125`, `:152`, `:178`, `:185`). `_execution` у корня — ядро,
  которое её поставило, ставится при постановке (`solo.dart:1040`), и по нему
  отвечает `job.lane` (`job.dart:128`);
- накопитель держит одно ядро и читает его `current` (`accumulator.dart:233`,
  `:280`);
- `cancelAll` снимает очередь каждого ядра (`solo.dart:565-567`), `close`
  обходит окна правил каждого ядра (`:452-466`), а ждёт идущие задачи,
  а не ядра (`:502`); `pending` строит `_pendingOf` ядра (`:339`).

`current` движок читает в насосе (`_step`, `:1259`), в поиске дубликата
и отмене для `restart` (`_enqueueIn`, `:1010-1016`, `:1135-1144`), в поиске
по очереди (`_lastJobWhereIn`, `:1155`), в конце задачи (`_onJobFinished`,
`:1193`), в `close` и `cancelAll` (`:480`, `:573`) — 21 место в файле.

1. **Пул — одно ядро с N местами.** Ядро пула держит набор идущих задач и набор
   занятых ключей вместо одного `current`; насос стартует, пока есть место.
   Очередь, окно правил, `SoloLaneId`, `_destination` и `_execution`,
   накопитель остаются привязаны к одному ядру, как сейчас, и работают для пула
   без новой развилки. Правятся места, которые читают `current`: каждое
   получает ветку для ядра пула.
2. **N мест пула — N ядер с общей очередью.** Каждое место держит одну задачу
   в `current`. Зато всё, что сегодня привязано к ядру, расходится по N ядрам
   и должно снова сойтись в пуле: очередь, которой владеет пул, а не ядро;
   `_held`, который смотрит окна всех мест; один `SoloLaneId` на N ядер;
   `_execution`, переназначенный при старте с пула на место; снимок `cancelAll`
   и записи `pending` без дублей одной очереди; накопитель над N ядрами; поиск
   дубликата и `restart` по всем местам.
3. **Пул поверх движка**, рецептом или вспомогательным классом. Отброшен: это
   и есть рецепты спора с их ловушками в контрактах движка.

Оба первых способа правят общие функции движка, через которые идут `Solo`
и линии: `_step`, `_enqueueIn`, `_lastJobWhereIn`, `_onJobFinished`,
`_pendingOf`. Неизменность `Solo` и линий доказывают критерии приёмки, как
доказывали её при введении линий: прежний набор тестов без правок, порядок
событий, число микрозадач, отладочные строки.

Первая версия этой записи выбрала второй способ словом владельца «согласен,
пиши дизайн», с доводом, что он не трогает выпущенный путь `Solo` и линий.
Проверка строителем показала, что довод неверен (раздел «Проверка строителем»):
второй способ правит те же общие функции и сверх того разводит по N ядрам то,
что первый оставляет одним. Выбор вынесен владельцу заново, и владелец выбрал
первый: «бери первый способ, одно ядро с N местами».

## Устройство

Пул — одно ядро `_SoloLaneCore` или его подкласс, как решит строитель. У ядра
пула вместо одного `current` — идущие задачи, до `concurrency`, и набор занятых
ключей. Очередь, окно стартовых правил `inTransition`, `SoloLaneId`,
`_destination` и `_execution` задачи, ядро накопителя — по одному на пул, как
у линии. Насос спрашивает стартовые правила по одной задаче за раз, синхронно,
поэтому окно правил у ядра пула одно, как сейчас: шаг пула стартует задачи
подряд, пока есть место и в очереди есть задача со свободным ключом.

Места, которые читают `current`, получают ветку для ядра пула: насос (место
есть, ключ свободен), поиск дубликата и отмена для `restart` (идущая задача
ключа), `_lastJobWhereIn` (идущие задачи), конец задачи (освободить место
и ключ), `close` и `cancelAll` (все идущие), `_pendingOf`, накопитель. Ядро
`Solo` и ядра линий идут прежней веткой.

### Объявление

```dart
@protected
SoloPool<S> pool(String name, {required int concurrency});

@protected
List<SoloPool<S>> get pools;
```

- `pool` — член `SoloLanes` рядом с `lane`, с теми же правилами: только в теле
  конструктора, `StateError` после печати набора, после `close` и на имя,
  которое уже занято линией или пулом. Имена у линий и пулов общие: имя — для
  логов и `toString`, два одинаковых читались бы как одно.
- `concurrency` не меньше 1, иначе `ArgumentError`. Пул с одним местом
  допустим: предел бывает настройкой, и 1 — законное её значение; такой пул
  ведёт себя как линия.
- Порядок обхода насосом — порядок объявления линий и пулов вместе; шаг пула
  заполняет свободные места подряд, прежде чем насос перейдёт к следующему
  ядру.
- `lanes` по-прежнему отдаёт только линии, `pools` — только пулы.

### Тип

```dart
abstract interface class SoloPool<S extends Object> {
  String get name;
  SoloLaneId get id;
  int get concurrency;

  SoloJob<T> job<W extends S, T>(...);          // as SoloLane.job
  SoloJob<T> enqueueJob<T>(Job<T> job, {bool first, Policy policy});
  SoloJob<T> enqueue<W extends S, T>(...);      // as SoloLane.enqueue
  SoloAccumulator<E, T> collect<W extends S, E, T>(...);
  SoloAccumulator<E, T> accumulate<W extends S, E, T>(...);

  SoloQueue get queue;
  List<SoloJob<Object?>> get running;
  SoloJob<Object?>? lastJobWhere(bool Function(SoloJob<Object?> job) test);
  SoloPending? get pending;
}
```

- Вместо `current` — `running`: неизменяемый снимок идущих задач в порядке
  старта, не длиннее `concurrency`. Код, написанный под `SoloLane`, с пулом
  не собирается, и тихой ошибки «прочитал одну задачу из N» нет — ради этого
  владелец выбрал `pool()`.
- Общая база `SoloLane` и `SoloPool` — интерфейс со всем, кроме `current`
  и `running`, чтобы код, которому они не нужны, принимал оба. Имя — моё
  решение, проверить: `SoloQueueOwner<S>`. `SoloLane` и `SoloPool` реализуют
  его; у `SoloLane` от этого не прибавляется членов, и фейк `SoloLane`
  не ломается.
- `job.lane` у задачи пула — `id` пула: ядро одно, и `id` у него один. Места
  своего `SoloLaneId` не имеют: место — устройство, а не понятие.
- Задача, сделанная пулом, ставится только этим пулом: чужая — `ArgumentError`,
  как у линии.

### Порядок и ключ

- Ключ занят, пока задача с ним идёт в пуле или её стартовые правила
  спрашиваются в окне пула. Отменённая задача, которая ещё сворачивается, ключ
  держит: она по-прежнему `current` своего места.
- Насос в шаге места берёт первую задачу очереди, чей ключ свободен; задача без
  ключа свободна всегда. Задача занятого ключа ждёт, а задачи за ней с другими
  ключами её обгоняют. Внутри одного ключа порядок очереди строгий.
- `first: true` ставит задачу в голову очереди пула; если её ключ занят, она
  ждёт, как любая.
- `canStart` и `W` спрашиваются при старте, как в линии, по состоянию в момент
  старта. Задача, которую обогнали, спрашивается позже, когда её ключ и место
  свободны.
- Когда задача кончается, насос планируется, как сегодня: освободились место и,
  может быть, ключ.

**Цена выбора следующей задачи.** Перебор очереди в поиске свободного ключа
вернул бы квадратичность, которую убрал индекс по ключу 2026-11-12
(`2026-11-12-queue-key-index-report.md`): тысяча лайков одного поста в очереди
превратила бы каждый старт в обход тысячи. Требование к строителю: выбор
следующей задачи не дороже амортизированного O(1) на старт при любом числе
задач занятых ключей. Задачи занятого ключа откладываются в сторону
и возвращаются в своё место очереди, когда ключ освободился; как именно — дело
строителя, порядок очереди должен сохраниться.

### Политики

Политика смотрит только в свой пул, как в линии — только в свою линию.

- `droppable`: если задача с тем же ключом стоит в очереди пула, в окне правил
  пула или идёт в пуле, вызов получает её. Идущих задач одного ключа не больше
  одной, поэтому ответ однозначен. Исключение осушения остаётся: вызов во время
  `drain` получает принятую задачу ключа.
- `keepLatest`: из очереди пула снимаются задачи ключа, кроме новой; идущая
  остаётся.
- `restart`: как `keepLatest`, и идущая задача ключа получает отмену. Новая
  ждёт её конца, потому что ключ занят. Поэтому `ifCancelled` старой, как
  и сегодня, пишет своё до старта новой.
- `sequential` с ключом: задача встаёт в очередь и ждёт, пока ключ освободится.
  Это и есть новое значение ключа в пуле; `Policy.sequential` в `policy.dart`
  говорит «keys are ignored», и dartdoc придётся сказать, что в пуле это
  не так.

### Правила и состояние

Ничего нового. Запись задачи пула для соседней по пулу — то же, что сегодня
запись другой линии: правила всех идущих задач, кроме пишущей, спрашиваются
после записи (`_running` в `_setState`). Рецепты страницы линий — чтение
в момент записи, склейка, эпоха с `keepWhile` — работают в пуле как есть,
и нужны в нём так же.

Отладочная строка о записи поверх чужой ведётся по ядру: `lastWrite` ядра
(`solo.dart:716`), и `_wroteSinceSeen` (`:1361`) пропускает ядро самой задачи.
В пуле ядро одно на все места, и запись соседки по пулу строка не увидела бы,
хотя для задачи это такая же чужая запись, как запись другой линии. Требование:
строка выходит и о записи другой задачи своего пула, своими словами о пуле,
а не о чужой линии. Как помнить, какая задача пула писала последней, — дело
строителя.

### Накопитель

Накопитель пула ставит группы в очередь пула, и к ним применяется то же правило
ключа. У групп одного накопителя ключ общий — тот, что дан `collect`. Отсюда:

- накопитель с ключом — группы идут по одной, как сегодня в линии;
- накопитель без ключа — группы идут рядом, до N сразу: следующая партия
  не ждёт, пока кончится предыдущая. Это то, чего не было у партий в споре.

Места, где накопитель читает очередь и текущую задачу своей линии (перечислены
в «Очередь и политики» дизайна линий), читают очередь пула и его идущие задачи.
`_isIdle` — «ни одной своей группы в очереди и ни одной своей среди идущих».
Пробуждение throttle планирует насос, когда в пуле есть свободное место
и в очереди есть своя группа: сегодня оно ждёт, пока простаивает ядро
(`accumulator.dart:278-280`), а в пуле это значило бы ждать конца чужой задачи
при свободном месте (моё решение).

Моё решение, проверить: группы накопителя без ключа идут рядом. Иначе
накопитель в пуле был бы неотличим от накопителя в линии.

### Дети

Дети корня пула мест не занимают: они не проходят через очередь. Предел
`concurrency` ограничивает корни, не детей.

### Закрытие и отмена

- `close()`, `cancelAll()` и `drain` обходят все ядра, и ядро пула — одно
  из них, со своей одной очередью и одним окном правил. Правила раздела
  «Закрытие и отмена» дизайна линий держатся: общий снимок очередей и окон
  до первой отмены, потом снимок идущих задач, теперь всех идущих задач пула,
  потом ожидание. `close` ждёт идущие задачи, а не ядра (`solo.dart:502`),
  поэтому его счётчик считает и задачи пула.
- `cancelAll` при одной идущей задаче во всём контроллере отдаёт
  `current.cancel(...)` как есть, как сегодня; при нескольких, в том числе
  в одном пуле, — общий future, который кончается с последней.
- `drain` пула кончается, когда пуста его очередь и кончились все места. Задачи
  занятого ключа — в очереди: они стоят в ней, `isQueued` у них `true`, их
  видят `queue.length`, `remove` и `clear`. Как движок откладывает их внутри
  очереди, снаружи не видно (моё решение).

### `pending`

Нового варианта у sealed-класса `SoloPending` нет. `SoloPendingLanes` — список
записей `SoloPendingLane(lane, pending)`, и `_pendingOf` ядра пула даёт
по записи:

- на каждую идущую задачу — `SoloPendingJob` с `id` пула. Её `queued` — задачи
  её ключа в очереди: только про них верно, что «none of them starts before
  this one is over»;
- если в очереди пула есть задачи, которых не держит ни одна идущая по ключу, —
  одна запись `SoloPendingQueue` с ними: во время `drain` и тогда, когда заняты
  все места. Без этого `pending` не показал бы задачу, которая ждёт места, —
  ровно то зависание из таблицы «Ожидание своего пула», ради которого `pending`
  и существует. Сегодня `SoloPendingQueue` бывает только при `drain`; dartdoc
  говорит о пуле отдельно (моё решение).

Несколько записей с одним `id` в списке — новое: сегодня линия даёт одну.
Dartdoc `SoloPendingLanes.lanes` и `SoloPendingLane.pending` говорит это
словами. У `SoloPool.pending` тот же вид, что у контроллера: `null`, одна
запись как есть или `SoloPendingLanes` с записями этого пула — форму выбирает
строитель так, чтобы она не зависела от числа идущих задач.

### Ожидание своего пула

| Что происходит | Что выходит |
| --- | --- |
| Задача пула ждёт задачу своего пула с тем же ключом | Ждёт навсегда: ключ держит она сама. |
| Задача пула ждёт задачу своего пула с другим ключом или без ключа | Дождётся, если есть свободное место; когда заняты все N и каждая так ждёт, ждут навсегда. |
| Задача пула ждёт задачу другой линии или пула | Ждёт, пока та идёт своим насосом. |
| Задача ждёт `close()` или `cancelAll()` своего контроллера | Ждёт саму себя, как сегодня. |

Вторая строка опаснее сегодняшней: в тесте с пустым пулом ожидание проходит,
под нагрузкой виснет. Поэтому линт `await_own_queue` сообщает ожидание своего
пула всегда, своим текстом, и страница говорит это прямо.

### Отладочные строки

Строки `Solo` и линий — прежние, слово в слово. Строки пула не повторяют
неправды линии: «enqueue X while Y is running: it starts after Y ends» в пуле
верна только для задачи того же ключа. Пул говорит, чего ждёт задача: занятого
ключа (и какой задачей) или свободного места. Слова — строителю.

## Критерии приёмки

- Прежний набор тестов `solo` зелёный без правок.
- `Solo` и обычные линии не меняют порядка событий, числа микрозадач,
  отладочных строк и путей виртуальных вызовов.
- Лайки: трасса случая спора — снятие `p1` после лайка `p1`, лайк `p2` в 150
  мс, сердце в момент нажатия.
- Загрузки: не больше `concurrency` сразу; отменённая до старта загрузка
  не стартует и не роняет других; `drain` кончается.
- Задачи одного ключа никогда не идут вместе ни с одной политикой; задачи без
  ключа ограничены только местом.
- `restart`: новая задача стартует после конца отменённой, `ifCancelled` старой
  записан до её старта.
- `droppable` в пуле находит идущую задачу ключа в любом месте; исключение
  осушения в пуле держится.
- Обгон: задача занятого ключа ждёт, следующие со свободными ключами стартуют;
  порядок внутри ключа строгий.
- Стенд цены: 40 000 задач одного занятого ключа в очереди и поток задач без
  ключа — время старта не растёт с длиной очереди. Замер в отчёте.
- `pending` пула: запись на идущую задачу, `queued` — задачи её ключа; во время
  `drain` — `SoloPendingQueue` с остальными.
- Накопитель без ключа в пуле: две группы идут рядом; с ключом — по одной.
- Ожидание своего пула: случаи таблицы, по тесту на каждый; линт сообщает их.
- `close`, `cancelAll` и `drain` во время работы N мест.
