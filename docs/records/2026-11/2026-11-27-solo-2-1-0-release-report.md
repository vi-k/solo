# Выпуск solo 2.1.0

По слову владельца 2026-11-27 «готовь выпуск async_job_lints, solo 2.1.0
и solo_lints». Слово понято как подготовка: разрешение на связку каждого пакета
приходит отдельным запросом, состоящим только из просьбы опубликовать.

## Что в выпуске

Пул, влитый в `main` 2026-11-27, — раздел «2.1.0» `CHANGELOG.md`:

- `SoloLanes.pool(name, concurrency: n)` и `pools`: до `n` корневых задач
  сразу, ключ держит порядок своих задач при любой политике;
- `SoloPool<S>` с `running` вместо `current`;
- `SoloQueueOwner<S>` — общее у линии и пула;
- `pending` пула и строка `Solo.debug` о том, чего ждёт задача пула: ключа или
  места;
- документация: раздел «A pool of places» страницы линий, справка, диагностика,
  правила накопления, `vs-bloc.md`, README и описание пакета.

## Почему минор

У `SoloLanes` новый защищённый член `pool` и геттер `pools`: подкласс со своим
членом этого имени перестаёт собираться, об этом заметка в «2.1.0». Новый член
класса, от которого наследуются, — минор, решение 134 `docs/settled.md`.
Остальное — добавления.

## Зависимости и порядок

`solo` держит ядро в `>=1.0.0 <1.1.0`, на pub.dev `async_job` 1.0.6, и нового
ядра выпуск не требует. Оверрайдов у `solo` и его примера нет.

Выпуск первый из трёх. `async_job_lints` 0.2.4 и `solo_lints` 0.4.0 узнают пул
по именам `solo` 2.1.0, и их тесты идут против `solo`: до выхода 2.1.0 их
оверрайды ведут на `solo` из дерева. Поэтому порядок — `solo` 2.1.0, затем
`async_job_lints` 0.2.4, затем `solo_lints` 0.4.0: линты выходят после выпуска
`solo`, под имена которого подогнаны правила.

Опубликованные `async_job_lints` 0.2.3 и `solo_lints` 0.3.1 пула не знают
и о нём молчат: распознаватель 0.2.3 спрашивает тип `SoloLane`, а `SoloPool`
его подтипом не является, и `lane_outside_constructor` 0.3.1 смотрит только
на `lane(...)`.

`flutter_solo` просит `solo: ^2.0.0` и выпуска не требует. После выхода 2.1.0
снимаются оверрайды `flutter_solo`, его примера и `camera_example`, и пакет
идёт против опубликованного `solo`.

README `solo` просит `solo_lints: ^0.3.0`. До `^0.4.0` его поднимает отдельная
правка после выхода `solo_lints` 0.4.0, и до pub.dev она дойдёт со следующим
выпуском `solo` — как после `solo_lints` 0.3.0
(`2026-11-18-solo-lints-0-3-0-release-report.md`).

Сайт собирается из `main` по пушу, и связка `solo` покажет раздел о пуле
тогда же, когда 2.1.0 выйдет на pub.dev, — по слову владельца «сайт подождёт
выпуска». Подготовка линтов до своей очереди живёт вне `main`, в ветке
`pool-lints-release`: в `main` их README и примеры просили бы на сайте
`async_job_lints: ^0.2.4` и `solo_lints: ^0.4.0` до публикации.

## Подготовка

Коммит `2c87508` «chore: prepare solo 2.1.0»:

- `version: 2.1.0` в `packages/solo/pubspec.yaml`;
- «Unreleased» в `CHANGELOG.md` стал разделом «2.1.0», «Не выпущено» в переводе
  `docs/ru/solo/CHANGELOG.md` тоже; `check_translations.py` — «no differences».

README версию не называет: установка — `dart pub add solo`. Описание пакета для
pub.dev поправлено в ветке пула.

Коммит `7ea75f8` «test(solo): join the load in flight on the fake clock».
Полный гейт на `2c87508` уронил один тест, который ветка пула не трогала: «a
second call joins the load already in flight» в `testing_rakes_test.dart`. Тест
пускал первую загрузку через `pumpEventQueue`, а фейковый API ждал 20 мс
по настоящим часам; под нагрузкой гейта 20 мс прошли раньше, первая загрузка
кончилась, и второй вызов начал загрузку заново. В одиночку тест прошёл 15 раз
из 15. Теперь он идёт на фейковых часах: первая загрузка стартует прокруткой
микрозадач, второй вызов приходит до конца её 20 мс. Мутант фикстуры
с `Policy.sequential` вместо `droppable` тест роняет.
