# Сравнение

В RxDart `debounceTime(Duration)` оставляет последнее событие серии.
`debounce(window)` принимает фабрику Stream окна; входящее событие
пересоздаёт окно. Это позволяет задавать окно по данным события.
В реализации используется `WindowStrategy.everyEvent`, конец окна
берёт последний элемент; буфер ограничен одним элементом.
Параметров leading/trailing/maxWait у этих двух методов нет.

В stream_transform `debounce(Duration, leading: false, trailing: true)`
позволяет отдельно выдать первое событие сразу и последнее после паузы.
При обоих флагах одиночное событие выдаётся только один раз. Leading
не означает периодическую выдачу при непрерывном потоке: после первого
события следующая серия начнётся только после паузы.

`debounceBuffer(Duration)` использует то же перезапускаемое окно,
но собирает весь список. Флагов leading/trailing у него нет.
Внутренний `_debounceAggregate` отделяет правило времени от способа
хранения: `_dropPrevious` сохраняет последнее, `_collect` добавляет
в список. Это полезный образец для наших двух способов хранения.

В обоих trailing-вариантах непрерывный поток может бесконечно
отодвигать выдачу. Фиксированный срок от первого события реализует
другую идею: `audit` у stream_transform выдаёт последнее значение
в конце такого срока. Для наших накопителей аналогичный срок должен
выдавать весь список или результат merge, а не терять остальные данные.
`maxWait` отсутствует в рассмотренных debounce API; это возможное
дополнение solo, а не возможность, позаимствованная у этих пакетов.

При нормальном завершении источника RxDart сразу выдаёт сохранённое
последнее значение. stream_transform оставляет pending-значение
до конца периода, затем завершает результат. Завершение источника
не равно отмене подписки и не равно `Solo.close()`.

# Исполняемая проверка

Одноразовый стенд: `/private/tmp/solo-debounce-comparison/check.dart`.
Использованы реальные реализации пакетов и `FakeAsync`, без реального
ожидания. Команда из каталога стенда:
`dart --packages=package_config.json check.dart`.

Вход 1, 2, 3 в моменты 0, 60, 120 мс; период 200 мс:

| Оператор | Выданные значения и время, мс |
| --- | --- |
| rxdart debounceTime | 3 в 320 |
| stream_transform debounce | 3 в 320 |
| stream_transform leading | 1 в 0 |
| stream_transform leading + trailing | 1 в 0, 3 в 320 |
| stream_transform debounceBuffer | [1, 2, 3] в 320 |
| stream_transform audit | 3 в 200 |

Дополнительно: одиночное событие в leading + trailing выдаётся один
раз; при закрытии источника в 150 мс RxDart выдаёт 3 в 150,
stream_transform — 3 в 320. Все девять проверок значений прошли.

Первый запуск с публичным фасадом RxDart не скомпилировался на текущем
SDK: ConnectableStreamSubscription наследует StreamSubscription,
который в этом SDK является interface class. Для изолированного
сравнения взят прямой импорт исходника debounce. Это проверка оператора,
а не подтверждение совместимости всего RxDart с текущим SDK.

В промежуточном стенде ожидалось также синхронное с финальным значением
уведомление done. У RxDart в этом FakeAsync-прогоне оно не наблюдалось,
хотя значение вышло в 150 мс. Финальный стенд проверяет именно значения
и их время; время уведомления done отдельным экспериментом не доказано.
Семантика завершения выше сверена с документацией и исходным кодом.

# Предложения для solo

Хранение и время задаются независимо. `collect` сохраняет события,
`accumulate` сразу вызывает merge, правило окна определяет момент
готовности. Поиск последнего значения можно получить чистой merge,
которая возвращает входящее событие; не нужно терять правки настроек
или записи логов ради сходства с обычным debounce.

Три варианта временного правила:

1. Обычный trailing debounce: готовность через Duration после
   последнего принятого события. Самый маленький API, но ожидание
   может быть неограниченным при непрерывном потоке.
2. Debounce с необязательным maxWait: готовность после паузы либо
   при достижении предела от первого события, что наступит раньше.
   Это рекомендация агента для поддержки обоих случаев одним режимом.
3. Фиксированное окно: срок от первого события без перезапуска.
   Подходит для пакетов логов; имя должно отличать его от debounce.

Эскиз единого параметра, ещё не утверждённый и не реализованный:

```dart
window: AccumulationWindow.debounce(
  const Duration(milliseconds: 200),
  maxWait: const Duration(seconds: 1),
),
```

Для фиксированного режима возможна фабрика
`AccumulationWindow.fixed(Duration)`. Без window сохраняется нынешнее
поведение. Имена и включение fixed в первую реализацию не согласованы.
Leading/trailing-переключатели не предлагаются для первой реализации
накопителей: leading-only теряет последующие данные. Если нужен такой
оператор для отдельных событий, его контракт надо определить отдельно.

# Интеграция с очередью: явная цена вариантов

Рекомендация для общего накопителя: ожидающая окно группа видна
в очереди и даёт хэндл, но прокачка выбирает первую готовую задачу.
Тогда `[A ждёт, B готова]` позволяет выполнить B. Это явное расширение
правил запуска; прежнюю гарантию порядка всех задач нельзя заявлять
неизменной. Правила adjacent/replace/join продолжают выбирать группу
по текущему расположению, а не определяют её готовность.

Альтернатива ближе к stream-операторам: отдельный debouncer хранит
события до помещения работы в очередь. Планировщик остаётся прежним,
но появляется отдельное владение ожиданием, хэндлами и закрытием.
Нельзя автоматически обещать прежнюю семантику adjacent: между
отложенными событиями уже могли пройти другие задачи.

При явном окне предлагается фиксировать состав группы в момент
закрытия окна, даже если слот занят. Дальнейшие события создают новую
группу. Это изменение прежней границы приёма только для нового режима;
без окна граница остаётся при извлечении. maxWait ограничивает
ожидание новых событий, а не задержку занятой очереди. Замена группы
через replace должна переносить начало окна maxWait вместе с данными,
иначе новый хэндл каждый раз обнулял бы предел ожидания.

`close` предлагается сохранить с отменой ожидающих групп и таймеров.
Автоматическая отправка остатка из stream-операторов не переносится
в close без отдельного решения о досылке. Работающий Job не отменяется
при новом событии только из-за debounce.

Предложения не утверждены владельцем. Следующий шаг — выбрать правило
времени и способ интеграции, затем подготовить спеку. Код solo не менялся;
пакетные тесты повторно не запускались. Проверяются отчёт, handoff,
ширина Markdown, ссылки на записи и diff.
