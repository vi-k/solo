# Объявленная операция

## Задача

Сегодня операция контроллера собирается заново на каждом вызове:

```dart
SoloJob<String> load() => run<Profile, String>(
      key: 'load',
      policy: Policy.droppable,
      (ctx) async { ... },
    );
```

Идентичность операции — строка `'load'`, и она живёт в том же выражении,
что и тело. Что из этого следует:

- **Ключ ничем не связан с типом результата.** `Object?` и `T`
  независимы. Пока это чинили с двух сторон: `droppable` теперь бросает
  понятный `ArgumentError` вместо `TypeError`
  (`2026-09-11[9]-review-fixes-report.md`), но сам контракт «один ключ —
  один тип результата» так и остался соглашением, которого компилятор не
  проверяет.
- **Политика задаётся на вызове.** Два метода с одним ключом и разными
  политиками компилируются молча.
- **Аргумент операции нигде не объявлен.** `load(String id)` передаёт
  `id` замыканием, и ни очередь, ни политика о нём не знают.

Стороннее ревью пришло к этому с двух сторон: второе предлагало
`SoloKey<T>`, третье — объявлять операцию полем контроллера. Второе
лечение слабее: типизированный ключ всё равно нужно передавать на каждый
вызов и следить за политикой руками.

## Прецедент внутри пакета

Накопители уже устроены ровно так. `collect` и `accumulate` возвращают
`SoloAccumulator<E, T>`, который держат в поле, а работа начинается с
`add(event)`. Дартдок говорит прямо:

> Keep one instance to combine events. Different instances never combine,
> even with the same job key.

и в коде рядом комментарий: «A stable object identifies compatible groups
across additions».

То есть в пакете уже есть форма «объявил один раз — вызывай», и она
применена там, где идентичность важнее всего. Предложение не приносит
чужую идею, а распространяет свою на обычные задачи.

## Форма

```dart
final class ProfileController extends Solo<ProfileState> {
  late final _load = operation<Loaded, String, Profile>(
    name: 'load',
    policy: Policy.droppable,
    (ctx, id) async {
      final profile = await ctx.wait(() => api.load(id));
      ctx.emit(Loaded(profile));

      return profile;
    },
  );

  SoloJob<Profile> load(String id) => _load(id);
}
```

Три параметра типа: рабочее состояние `W`, аргумент `A`, результат `T`.
`name` — только для диагностики, идентичность несёт сам объект.
Публичный метод остаётся обычным Dart-методом с обычной сигнатурой.

`SoloOperation<A, T>` вызывается как функция — `call(A arg)` — и отдаёт
`SoloJob<T>`.

### Механизм

Поле объявляется `late final`, и это не украшение: обычный инициализатор
поля не видит `this`, а `late` видит, потому что считается при первом
обращении. Проверено прогоном на 3.13.0:

```
declared over seed 7
identical(holder.declared, holder.declared) -> true
```

Второе важно не меньше первого: объект создаётся один раз, а значит
годится как идентичность.

### Что переезжает в объявление

`key` (становится самим объектом), `policy`, `canStart`, `keepWhile`,
`cancellable`, `describe`, `onError`, `onCancel`. Всё, что сегодня
повторяется на каждом вызове и не имеет права разойтись между вызовами.

### Что остаётся на вызове

Аргумент. Больше ничего.

## Что это чинит

- Тип результата связан с операцией на объявлении, и `droppable` не может
  вернуть несовместимую задачу **по построению**. `ArgumentError`,
  добавленный в `add`, остаётся для прямых вызовов с сырым ключом.
- Политику нельзя случайно задать разную для одной операции.
- Строковых ключей на вызовах нет, значит нет и совпадения строк из
  разных частей приложения.
- Аргумент операции виден движку: он попадает в `describe` и в журнал
  наблюдателя без ручной сборки строки.

## Открытые вопросы

Это то, ради чего спека идёт на ревью.

**1. Идентичность операции против идентичности запроса.** `_load('a')` и
`_load('b')` — одна операция. При `droppable` второй вызов вернёт первую
задачу, хотя запрашивали другой профиль. Сегодня это решается разными
ключами. Варианты: оставить как есть и сказать об этом в дартдоке;
добавить `keyOf: (arg) => arg` и подключать аргумент к идентичности;
сделать `keyOf` обязательным при политиках, отличных от `sequential`.

**2. Обработчики итогового состояния.** `onError` и `onCancel` сейчас
параметры `run`. В объявлении они естественны, но бывает ли нужда
переопределить их на одном вызове?

**3. Сосуществование с `run` и `job`.** Если операция не заменяет их, в
пакете два способа сделать одно. Если заменяет — ломает всё. Спека
исходит из того, что `run` и `job` остаются нижним уровнем, а операция
надстройкой. Нужно решить, что говорит об этом документация: «берите
операцию по умолчанию» или «берите `run`, операция для повторяющихся».

**4. Отложенные задачи.** `job()` создаёт задачу, не ставя её в очередь —
для фабрик вроде `_closeCameraJob()`. Нужен ли операции такой же
`_load.job(arg)`, или объявление всегда про очередь?

**5. Дети.** `ctx.run(child)` и `ctx.each` берут задачу, а не операцию.
Должна ли операция уметь запускаться дочерней, и что тогда с её
политикой, которая про очередь контроллера?

**6. Накопители.** `collect` и `accumulate` уже объявляются. Стоит ли
свести их и операцию к одной форме, или это разные вещи, которые просто
похоже выглядят?

**7. Имя.** `operation` на контроллере и `SoloOperation<A, T>` — рабочие.
Третье ревью называло это `action`. `action` короче, но в пакете уже есть
`action` как параметр `wait`/`join` — тот самый вызов, который операция
оборачивает. Одно слово на два разных понятия в одном API — плохо.

**8. Операция без контроллера.** Нужна ли возможность объявить операцию
отдельно от `SoloBase` — например, чтобы переиспользовать между
контроллерами или собрать в тесте?

## Чего в спеке нет намеренно

Генерации кода, классов-событий на каждое действие, обязательного DI.
Ревью их и не просило: третья беседа прямо говорит, что не стала бы
делать событие из каждого нажатия кнопки.

## Совместимость

Аддитивно. `run`, `job`, `add`, `collect`, `accumulate` не меняются, и
ничей код не ломается — кроме правила «новый член базового класса ломает
подкласс»: `operation` как имя члена `SoloBase` столкнётся с подклассом,
у которого такой член уже есть. Это отмечается в `CHANGELOG.md`, как
отмечено для `pending` и `isDraining`.
