# Ревью спеки 2026-09-14[10]-eager-parallel-run-design.md, второй круг

## Вердикт

**Не годится для плана.** Вторая редакция сделала принципиальный шаг, сменив
механизм с внешнего расширения над `ctx.run` на ядровый член с реакцией
на исход тела ветки. Однако перенос точки уведомления внутрь ядра создал новые
критические дефекты, блокирующие написание плана:

1. **Разрыв идентификации упавшего ребёнка:** при раннем выходе по отмене тела
   ветки `parent._outcomeChild` ещё не содержит упавшего ребёнка (регистрация
   происходит только в `finish()`). В итоге родительский `_handlerCancel`
   не может восстановить имя ребёнка, и описание исхода теряет ключ ветки
   вопреки Критерию 5.
2. **Двойное освобождение ресурсов:** при отмене ветки комбинатором её итоговый
   исход перетирается на `Cancelled`. Стек очистки самой ветки видит исход
   `Cancelled` и автоматически выполняет зарегистрированный `discard`, после
   чего комбинатор `runAll` вызывает собственный колбэк `cleanUp` над тем же
   объектом. Для неидемпотентных ресурсов это ведёт к падению или сбою
   рантайма.
3. **Утечка ресурсов в цикле `cleanUp`:** контракт `cleanUp` не изолирует шаги
   очистки нескольких значений, из-за чего ошибка уборщика первого значения
   навсегда оставляет невычищенными последующие значения; не определено
   поведение при отмене родителя во время асинхронного `cleanUp`.
4. **Противоречие в правиле исходов:** отказ, случившийся в ветке после её
   отмены комбинатором (в блоке `finally`), поглощается ядром в пользу отмены
   (`_pendingCancel ?? outcome`) и без наблюдателя не попадает даже в зону, что
   спорит с безусловным обещанием «отказ побеждает отмену».

## Находки

### 1. Нарушение идентификации ребёнка при раннем исходе (`_outcomeChild` не видит отмену тела)

**Важность:** блокирует план

**Что не так:** Спека утверждает (строки 179–182, 471–473): отмена тела выходит
наружу тем же объектом, родительский `_execute` ловит её в `on Cancelled`,
вызывает `_handlerCancel`, который находит ребёнка
в `parent._outcomeChild[thrown]` по тождеству и формирует описание
`child b: ...` (Критерий приёмки 5).

В архитектуре ядра (`job_base.dart:742`) регистрация
`parent._outcomeChild[outcome] = this` выполняется строго внутри метода
`finish(decided)`, то есть ПОСЛЕ завершения всех потомков (`_awaitChildren()`)
и стека очистки (`_cleanups`).

При раннем сигнале тела упавший ребёнок ещё не завершил ни потомков,
ни очистку, и метод `finish` не вызывал. В этот момент таблица
`parent._outcomeChild` пуста.

Более того: когда тело ребёнка делает `throw Cancelled`, в `_execute` ветки
срабатывает `outcome = selfCancelled = _handlerCancel(cancelled, stackTrace)`,
который конструирует НОВЫЙ экземпляр `Cancelled.by` (`job_base.dart:1043`).
Поэтому даже когда ребёнок позже дойдёт до `finish`, в `_outcomeChild` попадёт
этот новый объект `outcome`, а не исходный объект отмены, выброшенный телом.

В результате `parent._handlerCancel` получает `null` по брошенному объекту
отмены, описание ребёнка теряется (`description: 'manual-reason'` вместо
`'child b: manual-reason'`), и Критерий приёмки 5 («описание называет ребёнка»)
не выполним на уровне механики ядра.

**Доказательство:** Зонд `probe/probe_outcome_child_timing.dart`:
```bash
cd /private/tmp/r2a-5f8032/packages/async_job && dart run probe/probe_outcome_child_timing.dart
```
Вывод:
```text
Child isFinished right now: false
Parent outcome: Cancelled(handler: cancel-from-child-body)
Parent reason: handler
Parent description: cancel-from-child-body
```
Имя дочерней задачи `child-b` отсутствует в описании исхода родителя, так как
`_outcomeChild` не заполнен на момент раннего выхода тела.

Контрольный зонд `probe/probe_seam_investigation.dart` подтверждает: при
штатном полном завершении через `ctx.run` родитель получает
`child worker-b: ...` только потому, что ждёт `finish()` и получает созданный
внутри `_handlerCancel` объект, отличный от исходного броска тела
(`Is identical to manualCancel? false`).

**Что предлагаю:** Специфицировать новый шов ядра не просто как точку выхода,
а как расширение контракта регистрации:
1. Ранний шов в `_execute` ребёнка при возникновении `Cancelled` обязан
   регистрировать брошенный объект в `parent._outcomeChild` до возврата сигнала
   комбинатору; либо
2. `JobContextBase.runAll` должен явно связывать пойманную отмену с хэндлом
   ребёнка из своего списка и сам передавать тождество в родительский контекст.

**Вердикт: принято, блокирует.** Проверил в коде: `parent._outcomeChild[outcome]
= this` стоит в `finish` (`job_base.dart:741`), и ключом там лежит итоговый
объект, а не брошенный телом. Чинится тем же решением, что находки 2 и 4:
ранний шов остаётся **спусковым крючком** — он говорит «пора останавливать
остальных», — а выбор и бросок идут по итоговым исходам веток, тем самым
объектам, которые уже лежат в `_outcomeChild`.

### 2. Двойное освобождение ресурса (конфликт `cleanUp` комбинатора и `discard` ядра)

**Важность:** блокирует план

**Что не так:** В `children.md:60` и `job_context.dart:62` зафиксировано
правило: ресурс, передаваемый наружу, открывается через
`ctx.wait(open, discard: (r) => r.close())`.

В `_execute` (`job_base.dart:963`) регистрация `discard` срабатывает, если
итоговый исход задачи `(_pendingCancel ?? outcome)` не является `Done`.

В сценарии `runAll`: ветка `a` успешно вернула ресурс наружу, но сосед `b`
упал. Комбинатор останавливает группу и отменяет ветку `a` через
`a.cancelWith(SiblingCancelReason)`.

Ветка `a` выставляет `_pendingCancel = Cancelled(sibling)`. При сворачивании
`_execute` ветки `a` проверяет `(_pendingCancel ?? outcome) is Done<T>`, видит
исход `Cancelled` (не `Done`) и ВЫПОЛНЯЕТ зарегистрированный `discard`,
закрывая ресурс (счётчик закрытий = 1).

Затем комбинатор `runAll`, обнаружив неуспех группы, берёт полученное значение
ветки `a` и вызывает переданный пользователем колбэк `cleanUp`. Ресурс
закрывается ВТОРОЙ РАЗ (счётчик закрытий = 2).

Для неидемпотентных ресурсов (сокеты, соединения БД, системные дескрипторы)
повторный вызов закрытия приводит к падению `cleanUp` (`StateError`) или сбою
рантайма.

**Доказательство:** Зонд `probe/probe_double_disposal.dart`:
```bash
cd /private/tmp/r2a-5f8032/packages/async_job && dart run probe/probe_double_disposal.dart
```
Вывод:
```text
=== PROBE DISCARD ON POST-BODY CANCELLATION ===
Body of childA has finished. closeCount = 0
childA isFinished = false
Cancelling childA while in _awaitChildren...
childA isFinished after cancel = true
childA outcome: Cancelled(manual)
resource closeCount after childA cancelled: 1
runAll calling cleanUp...
resource closeCount after cleanUp: 2
Parent finished. Final resource closeCount: 2
=== END PROBE DISCARD ON POST-BODY CANCELLATION ===
```

**Что предлагаю:** Устранить конфликт владения ресурсами:
1. Зафиксировать в контракте `runAll`: значения, полученные комбинатором,
   снимаются с очистки в самой ветке (комбинатор перехватывает владение); либо
2. Явно описать в `children.md`, что ветки внутри `runAll` не должны
   использовать `discard`, если группе передан `cleanUp`, либо сделать
   `cleanUp` проверяющим состояние закрытия ресурса.

**Вердикт: принято, блокирует.** Свой зонд подтверждает: ветка кончила тело
успехом, её отменили до конца, `closes после отмены: [discard соединение]`,
а значение до родителя не дошло (`ветка кончилась ошибкой: Cancelled(manual)`).
Правило станет однозначным: группа берёт значение только у ветки, кончившейся
`Done`; ресурс ветки, накрытой отменой, освобождает сама ветка.

### 3. Утечка ресурсов при исключении в `cleanUp` и неопределённость при отмене родителя

**Важность:** блокирует план

**Что не так:** Спека заявляет (строки 277–280): «`cleanUp` зовётся для каждого
значения, которое `runAll` успел получить, на любом пути, кроме полного успеха;
ровно один раз на значение; его собственная ошибка не подменяет ошибку,
выходящую наружу, а уходит тем же маршрутом, что и опоздавшие».

Спека умалчивает об изоляции шагов уборки: если у группы завершились 2 ветки,
и при сворачивании вызов `cleanUp(value1)` завершается синхронным или
асинхронным броском исключения, наивный цикл обрывается, и `cleanUp(value2)`
никогда не вызывается — ресурс `value2` тихо утекает.

Кроме того, `cleanUp` сигнатурно асинхронен (`FutureOr<void>`). Спека
не определяет, что происходит, если во время ожидания асинхронного `cleanUp`
родитель получает внешнюю отмену: прерывается ли цикл очистки (вызывая утечку
ресурсов) или очистка гарантированно доигрывает до конца подобно блоку
`_cleanups` в `_execute`.

**Доказательство:** Зонд `probe/probe_cleanup_scenarios.dart`:
```bash
cd /private/tmp/r2a-5f8032/packages/async_job && dart run probe/probe_cleanup_scenarios.dart
```
Вывод:
```text
=== PROBE CLEANUP SCENARIOS ===
Naive loop: cleaned=[], errors=[Bad state: cleanUp failed on 1]
Did item 2 leak in naive loop? true
=== END PROBE CLEANUP SCENARIOS ===
```

**Что предлагаю:** Специфицировать в контракте `cleanUp`:
1. Цикл вызова `cleanUp` для накопленных значений изолирует каждую итерацию
   через `try/catch` (аналогично `_runCleanup` в `job_base.dart:1023`), ошибки
   всех упавших вызовов направляются в зону, ни один ресурс не пропускается.
2. Асинхронная очистка `cleanUp` защищена от прерывания отменой родителя
   (выполняется в режиме, аналогичном `uncancellable`).

**Вердикт: принято.** Ошибка уборщика, отмена родителя во время уборки
и асинхронный уборщик уходят в критерий 14 отдельными входами.

### 4. Противоречие в правиле «отказ побеждает отмену» при падении ветки после пометки отмены

**Важность:** править до плана

**Что не так:** Спека формулирует безусловное правило: «есть среди веток
настоящий отказ — наружу выходит он» (строки 160–161).

Однако в ядре (`job_base.dart:893–897`, `921`, `987–996`) и в смежной спеке
`2026-09-14[4]` (строки 187–201) действует базовый инвариант: отказ, брошенный
задачей после того, как задача уже была помечена к отмене
(`_pendingCancel != null`), считается «способом тела сдаться». Итоговым исходом
остаётся `_pendingCancel ?? outcome` (отмена), а `_reportCovered` не вызывается
(`failedFirst == false`).

Зонд `probe_post_cancel_failure.dart` доказал: если ветка `a` была отменена
комбинатором (`SiblingCancelReason`), а затем в блоке `finally` бросила
`StateError`, её исход остаётся `Cancelled(sibling)`, а `StateError` без
наблюдателя не доходит даже до зоны.

Если `runAll` ориентируется на ранний исход тела (`Failed`), он выдаст наружу
`StateError`, разойдясь с окончательным исходом ветки и инвариантом `[4]`.
Если же он дожидается сворачивания ветки, `_pendingCancel` поглотит отказ,
и наружу выйдет отмена вопреки правилу спеки.

**Доказательство:** Зонд `probe/probe_post_cancel_failure.dart`:
```bash
cd /private/tmp/r2a-5f8032/packages/async_job && dart run probe/probe_post_cancel_failure.dart
```
Вывод:
```text
=== PROBE POST-CANCEL FAILURE ===
Cancelling childA...
childA in finally throwing StateError...
Parent caught from childA: Cancelled(manual)
Parent caught type: Cancelled
childA outcome: Cancelled(manual)
Parent outcome: Done(null)
Zone errors: []
=== END PROBE POST-CANCEL FAILURE ===
```

**Что предлагаю:** Уточнить формулировку правила «отказ побеждает отмену»:
отказ побеждает отмену, если он произошёл ДО запроса отмены ветки
(`failedFirst == true`). Отказ, возникший в ветке после того, как комбинатор
уже запросил её остановку, трактовать в соответствии с правилом накрытого
отказа ядра `[4]`.

**Вердикт: принято.** Мой зонд: ветка отменена, потом бросает в `finally` —
исход `Cancelled(manual)`, зона пуста. Формулировка «есть среди веток настоящий
отказ» была шире, чем правило соседней спеки. После перехода на итоговые исходы
накрытый отказ в выборе не участвует, потому что `Failed` у такой ветки просто
не появляется.

### 5. Внутреннее противоречие Критерия 9 с правилом маршрутизации опоздавших ошибок

**Важность:** править до плана

**Что не так:** В разделе «Куда уходят опоздавшие ошибки» (строки 293–296)
и вердикте 5 автор прямо утверждает: «Пересказ нужен там, где не слышал никто:
без наблюдателя `notifyObserver` ребёнка молчит, а ветка наблюдена самим
комбинатором, и ядро её в зону не отправит». То есть пересказ в зону
предназначается исключительно для случая отсутствия наблюдателя.

Однако Критерий 9 (строки 489–492) требует: «в зоне ровно один раз тот же
объект; от родителя наблюдателю — ни разу; от самой ветки — один раз».

Критерий требует в одном сценарии С НАБЛЮДАТЕЛЕМ («от самой ветки — один раз»),
чтобы та же ошибка появилась и в зоне («в зоне ровно один раз тот же объект»).
Это порождает сброс необработанной ошибки в зону процесса даже при полностью
настроенном наблюдателе, что противоречит цели «не дублировать отчёт».

**Доказательство:** Текст критерия 9 (строка 489) против текста правил (строка
293).

**Что предлагаю:** Разделить Критерий 9 на два независимых сценария по аналогии
с Критерием 8:
1. С наблюдателем: наблюдатель слышит отказ от самой ветки ровно один раз, зона
   пуста.
2. Без наблюдателя: зона получает опоздавший отказ ровно один раз.

**Вердикт: принято.** Критерий 9 разводится на два прогона, как критерий 8:
с наблюдателем — он слышит от ветки один раз, зона пуста; без наблюдателя —
зона получает ровно один раз.

### 6. Критерий 10 сохраняет мутацию прототипа вопреки принятому вердикту первого круга

**Важность:** править до плана

**Что не так:** В первом круге (`2026-09-14[11]`, находка 11) ревьюер указал,
что завершитель первой ошибки — артефакт внешнего прототипа, а не инвариант
ядра. Автор в вердикте зафиксировал: «Принято. Ловушка с завершителем —
свойство прототипа, а не ядра. Критерий 9 будет про инвариант...».

Несмотря на этот вердикт, во второй редакции в Критерии 10 (строки 496–497)
сохранена буквальная формулировка: «Мутация: гасить завершитель без учёта
настоящего отказа — краснеет вторым входом».

В ядровом `JobContextBase` никакого завершителя нет; критерий приёмки ядра
не должен формулироваться через мутацию чужого внешнего прототипа.

**Доказательство:** Текст вердикта 11 в `[11]` (строки 484–486) против текста
Критерия 10 в `[10]` (строки 496–497).

**Что предлагаю:** Заменить мутацию на проверку инварианта ядра: при отказе
приёма одной из веток запущенные ранее задачи останавливаются, а настоящий
отказ уже запущенного ребёнка доставляется в зону.

**Вердикт: принято, и это моя недоработка.** Вердикт первого круга я записал,
а в текст спеки не внёс: критерий 10 по-прежнему описывал мутацию прототипа.
Проверять чужой прототип в приёмке ядра незачем.

### 7. Выход из `runAll` до завершения упавшей ветки оставляет активного ребёнка в вызывающем контексте

**Важность:** мнение

**Что не так:** Критерий 3 фиксирует: ошибка выходит из группы до того, как
отпущен барьер собственного потомка упавшей ветки. Так как обычный отказ
не каскадирует отмену на потомков (`children.md:19`), упавшая ветка остаётся
в статусе выполнения (`_awaitChildren()`) в момент, когда вызывающий код
в родителе уже получает управление из `runAll`.

Если родитель перехватывает ошибку через `try/catch` и продолжает работу,
упавший ребёнок всё ещё числится в списке активных детей родителя
(`_children`), а его ресурсы (`_cleanups`) ещё не освобождены. В `solo` это
продлевает жизненный цикл операции.

**Доказательство:** Зонд `probe/probe_outcome_child_timing.dart`
(`Child isFinished right now: false` в момент перехвата ошибки).

**Что предлагаю:** Явно зафиксировать в разделе «Контракт владения и границы»:
ранний выход при отказе тела с живыми потомками означает, что упавшая ветка

## Ответы на четыре вопроса владельца

1. **Имя: `runAll`** Рекомендация: **Оставить `runAll`**. Довод: Имя прямо
   парно с `ctx.run(child)`. В парадигме structured concurrency (Kotlin
   `coroutineScope`, Python `TaskGroup`) одновременный запуск набора ветвей
   по контракту останавливает соседей при первой ошибке. Имя `race` неверно
   семантически, так как означает соревнование на первый успех. Слово `All`
   отражает запуск всех переданных детей.

2. **`cleanUp`** Рекомендация: **Оставить, но доработать контракт.** Довод:
   Параметр необходим для предотвращения тихих утечек значений успешных веток
   при падении группы. Однако его контракт обязан быть согласован с `discard`
   ядра (находка 2) и защищён от сбоев внутри цикла (находка 3).

3. **Кортежная форма `(a, b).runAll`** Рекомендация: **Отложить.** Довод:
   Рекорды в Dart не имеют единого супертипа; добавление кортежей требует
   генерации 8 шаблонных методов расширения. Откладывание не нарушает обратной
   совместимости и может быть выполнено аддитивно в любой момент.

4. **Выпуск** Рекомендация: **Выпускать отдельной работой после `0.3.0` (в
   версии `0.4.0`).** Довод: Версия `0.3.0` уже готова и полностью
   стабилизирована работой по конвертам `[...].wait` (`[4]`, `[9]`). Включение
   в неё сырого `runAll` с несогласованным швом в ядре и конфликтом ресурсов
   задержит релиз ядра.
