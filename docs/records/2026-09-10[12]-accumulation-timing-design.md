# Согласованные требования

Владелец выбрал обычный debounce и throttle. maxWait не нужен.
collect сохраняет все принятые события; в accumulate пользователь
решает через merge, какие данные сохранить или отбросить. Временной
режим сам данные не отбрасывает.

Ни debounce, ни throttle не задерживают очередь других событий.
Ожидающая группа A пропускает готовую задачу B. Обработчики сохраняют
последовательное выполнение: готовая A ждёт завершения текущего Job,
включая его детей и уборку. Последнее объяснение принято ответом «ок».

Ниже зафиксирована предложенная конкретизация: API, отсчёт throttle,
границы групп и механизм очереди. После отдельной работы над ctx.run
владелец поручил продолжить debounce и throttle; реализация возобновлена
по этой спецификации. Детали реализации сверяются с кодом на `9493c31`.

# Область и API

Добавить необязательный параметр timing к существующим collect
и accumulate. Без него полностью сохранить нынешнее поведение.
Обычные job/add/run в этой работе новых временных параметров не получают.

Публичный неизменяемый тип AccumulationTiming имеет две фабрики:

```dart
AccumulationTiming.debounce(Duration duration);
AccumulationTiming.throttle(Duration duration);
```

Параметр обеих фабрик накопителей: AccumulationTiming? timing.
Один объект настройки можно передать нескольким накопителям; таймеры
и интервалы у них независимы. Ключ задачи не объединяет их время.
Фабрики настройки проверяют аргумент через throw ArgumentError при
отрицательной длительности. Конструкторы не const: проверка действует
в release. Duration.zero отключает задержку и сохраняет прежнюю границу
накопления при извлечении; таймер для нулевой длительности не создаётся.

Накопитель поискового запроса, оставляющий последнее событие:

```dart
late final _search = accumulate<AppState, String, void>(
  (ctx, query) => ctx.join(() => api.search(query)),
  merge: (previous, incoming) => incoming,
  timing: AccumulationTiming.debounce(
    const Duration(milliseconds: 200),
  ),
);
```

Накопитель логов, сохраняющий каждый элемент:

```dart
late final _logs = collect<AppState, LogEntry, void>(
  (ctx, entries) => ctx.join(() => api.sendLogs(entries)),
  timing: AccumulationTiming.throttle(
    const Duration(seconds: 1),
  ),
);
```

Это фрагменты методов существующего контроллера с соответствующим API.
Проверка компиляции выполняется после появления нового публичного API.
Ни библиотека, ни эти примеры не гарантируют доставку после ошибки
или отмены. Обычные правила исходов и закрытия сохраняются.

# Debounce

Каждая открытая группа получает однократный таймер от первого события.
Успешное присоединение следующего события перезапускает таймер на полную
длительность. Это происходит и тогда, когда merge возвращает прежнее
значение: событие принято, даже если его данные пользователь отбросил.
Ошибка merge не принимает событие и не меняет таймер.

При срабатывании таймера группа закрывается для добавлений и становится
готовой. collect получает неизменяемый снимок один раз. Если слот занят,
группа ждёт его, оставаясь закрытой: поздние события создают новую группу
или попадают в другую открытую группу согласно AccumulationPolicy.

Для событий в 0, 60 и 120 мс и окна 200 мс одна группа готова в 320 мс.
У collect это список всех трёх событий, у accumulate — результат merge.
При непрерывном потоке готовность может отодвигаться бесконечно.
Ни готовые задачи других накопителей, ни обычные задачи этого не ждут.

Окно принадлежит группе, а не ключу и не всему накопителю. Поэтому
разделённые политикой adjacent группы имеют независимые окна.

# Throttle

Предлагается ограничивать частоту фактических стартов групп одного
накопителя. Первая группа готова без временной задержки. После её старта
следующая группа этого накопителя может стартовать не раньше чем через
duration; занятый слот способен дополнительно отложить этот старт.
Отсчёт от начала, а не от завершения обработчика.

Во время интервала новые события принимаются обычным collect/accumulate.
Добавление не продлевает интервал. Когда он истёк, накопленное становится
готовым и запускается при свободном слоте без необходимости нового add.
Пустая группа и запуск без данных не создаются.

Отсчёт общий для всех групп экземпляра накопителя, включая разделённые
посторонними задачами. Если одновременно ждут три группы, старт одной
снова закрывает временную готовность двух остальных на duration.
Это предотвращает запуск накопившихся групп подряд после долгой B.

Throttle не закрывает состав группы по таймеру: приём закрывается
при извлечении, до стартовых правил и хуков, как сейчас без timing.
Поэтому задержка занятого слота позволяет собрать больше событий.
Группа, уже извлечённая или работающая, новых данных не получает.

Пример для duration 200 мс, свободного слота и коротких обработчиков:

| Действие | Результат для collect |
| --- | --- |
| A1 в 0 мс, затем прокачка | Старт группы [A1] в 0 мс |
| A2 в 60 мс, A3 в 120 мс | Ожидающая группа [A2, A3] |
| Обычная B в 150 мс | B может стартовать в 150 мс |
| Интервал истёк в 200 мс | Старт [A2, A3], если B завершилась |

Если B занимает слот с 150 до 500 мс, вторая группа стартует в 500 мс.
Следующая группа того же накопителя сможет стартовать с 700 мс.
Синхронные A1, A2, A3 до первой прокачки по-прежнему могут составить
одну группу: готовность без задержки не означает запуск внутри add.

Началом интервала считается переход Job в running до onStart.
Отмена из onStart интервал уже не отменяет. Отклонённые стартовыми
правилами или отменённые до старта группы интервал не расходуют.
Если обработчик работает дольше duration, после его завершения
следующая группа уже не имеет дополнительной временной задержки.

# Очередь и правила накопления

Выбранное для этой спецификации предложение — группы остаются обычными
элементами очереди. Прокачка идёт от начала к концу и извлекает первую
готовую задачу. Готовность проверяет только внутренние временные флаги;
пользовательские canStart и keepWhile при поиске не вызываются.

Если все группы ждут, прокачка прекращается без повторяющихся микротасок.
Очередь при этом не пуста, current отсутствует. Следующее добавление,
освобождение слота или срабатывание таймера вновь планирует прокачку.
При свободном слоте обработчик запускается через обычную микротаску.

queue.jobs показывает расположение в очереди, включая ожидающие группы.
Фраза «first to run first» в dartdoc больше не точна: ожидающую группу
можно обойти. length, isQueued, lastWhere, remove и clear учитывают
как готовые, так и ожидающие группы. Публичный флаг готовности не нужен.

Правила выбора данных сохраняются:

- adjacent проверяет только текущий хвост и присоединяет к открытой
  группе того же накопителя. Исполнившаяся B больше не является
  разделителем. Если A1 осталась хвостом, после B событие A2 может
  присоединиться к A1. Это следствие разрешённого обхода.
- join ищет последнюю открытую группу того же накопителя и оставляет
  её Job и место в очереди.
- replace ищет такую же группу, переносит данные в новый Job в хвосте
  и отменяет прежний. Debounce нового Job ждёт полную паузу от нового
  события. Общий интервал throttle замена не сбрасывает.

Готовые закрытые debounce-группы не являются кандидатами для слияния
и replace. Работающие группы не являются кандидатами во всех режимах.
Удаление разделителя не объединяет существующие группы задним числом.
Старый хэндл replace остаётся отменённым, перенаправления не появляется.

Без timing результат A1, B, A2 остаётся прежним во всех трёх политиках.
С timing гарантируется порядок готовых задач по текущему расположению;
полный FIFO через ожидающие группы намеренно не гарантируется.

# Таймеры, границы и повторный вход

Использовать обычные однократные Timer без внешней runtime-зависимости.
У debounce таймер принадлежит группе, у throttle — накопителю.
У контроллера есть приватный реестр только действующих таймеров,
чтобы close мог отменить и интервал throttle без ожидающих групп.
Не хранить постоянный список всех когда-либо созданных накопителей.

Таймер throttle живёт до конца интервала, даже если очередь этого
накопителя опустела или была очищена. Иначе новое add обошло бы
ограничение частоты. По истечении он снимается с регистрации;
автоматического следующего таймера без нового старта нет.

Готовность меняется по обработке callback таймера. На совпавших сроках
действует порядок выполнения Dart: если add выполнен до callback
debounce, он ещё может продлить открытую группу; после callback
присоединиться к ней уже нельзя. Заблокированный event loop может
задержать callback. Точность реального времени не гарантируется.
Duration.zero обрабатывается отдельно, без зависимости от этого порядка.

Таймеры debounce создаются или перезапускаются только после успешного
приёма данных. Замена сначала устанавливает новую группу и её время,
затем вызывает уведомления отмены прежней. Повторный вход из уведомлений
видит согласованную очередь. Колбэк отменённого или заменённого таймера
не может закрыть новую группу или разбудить её раньше срока.

Снимок debounce создаётся при закрытии окна; извлечение закрытой группы
не копирует его повторно. Для throttle снимок создаётся при извлечении.
Освобождение данных, закрытие приёма и остановка таймера идемпотентны.

# Отмена, ошибки и close

Отмена ожидающего Job удаляет именно его группу и таймер debounce.
Политики с тем же key по-прежнему видят эти группы как обычные задачи.
queue.clear/remove соблюдают cancellable и force. Принудительная замена
AccumulationPolicy.replace работает и при cancellable: false.

Отмена ожидающей throttle-группы не отменяет интервал, начатый прежней
работающей группой. Отмена самой работающей группы тоже его не сбрасывает.
Провал merge не меняет данные, хэндл, положение или сроки. Остальные
ошибки правил и обработчика следуют существующему контракту исходов.

close сначала запрещает новые добавления и отменяет все временные
ожидания, затем завершает ожидающие группы Cancelled(closed) и работает
с текущей задачей как раньше. Интервал throttle не задерживает close.
После close не остаётся активных таймеров этого механизма и повторных
запусков. Досылки и автоматических повторов нет.

Создание пустого накопителя после close допустимо. Его add возвращает
новый отменённый Job, не удерживает событие и не создаёт таймер.

# Изменяемые части реализации

- Новый accumulation_timing.dart: публичная неизменяемая настройка,
  две фабрики и валидация длительности. Экспорт из solo.dart.
- solo_base.dart: параметры фабрик, реестр действующих таймеров,
  выбор готовой задачи и очистка времени при close.
- accumulator.dart: таймер debounce у группы, интервал throttle
  у накопителя, переходы при приёме, замене и завершении.
- queue.dart: выбор первой готовой задачи и идемпотентная фиксация
  состава при извлечении; исправление документации queue.jobs.
- job.dart: учёт старта throttle в started до пользовательских хуков.
  Общий жизненный цикл async_job не меняется.

Поиск готовой задачи имеет O(q) в худшем случае, где q — длина очереди.
При первой готовой задаче обход заканчивается сразу; удаление из списка
уже сейчас требует сдвига элементов. Новых сортировок и постоянного
опроса по таймеру нет. collect не копирует список на каждом событии.

# Проверки

Все временные сценарии проверяются FakeAsync; тесты не ждут реального
времени. Журналы должны показывать данные, порядок и моменты стартов,
исходы и идентичность хэндлов. Нужны отдельные сценарии:

1. Debounce в 0/60/120 мс с готовностью в 320 мс; непрерывный вход;
   ошибка merge и merge, возвращающая прежнее значение.
2. Готовая B обходит ожидающую A для обоих временных режимов;
   несколько ожидающих накопителей; все группы ждут без busy loop.
3. Debounce закрывает данные при занятом слоте; позднее событие идёт
   в другую группу; снимок не меняется при дальнейших добавлениях.
4. Throttle запускает первый пакет без задержки, копит последующие,
   запускает остаток по сроку без нового add; пустых запусков нет.
5. Долгая B сдвигает фактический старт throttle и следующий интервал;
   несколько разделённых групп одного накопителя не стартуют подряд.
6. Долгий обработчик throttle, дети и уборка удерживают слот; истёкший
   интервал не добавляет задержки после их завершения.
7. adjacent/join/replace для обоих способов хранения, обход B,
   одинаковые key у разных накопителей, общий объект timing.
8. Замена не сбрасывает throttle, перезапускает debounce и публикует
   новое состояние до onFinish/whenCancelled прежнего Job.
9. Отмена, clear/remove с force и без него, повторный вход из хуков,
   close во время ожидания, в стартовых правилах и из onStart.
10. Отклонённый старт не расходует throttle; отмена из onStart расходует.
11. События до и после callback на одной границе времени, отменённые
    таймеры, нулевая и отрицательная длительность.
12. После close нет таймеров; после окончания интервала без данных
    нет нового таймера; после clear ограничение throttle сохраняется.
13. Весь прежний набор накопителей и обычной очереди проходит без timing.
