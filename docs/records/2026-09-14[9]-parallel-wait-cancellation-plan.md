# План: конверт параллельного ожидания разбирается ядром

Всё, что ниже, — по спеке; расхождение с ней означает ошибку плана,
а не свободу исполнителя. Работа идёт в неотпущенном наборе, оверрайды в дереве
стоят, публиковать между шагами ничего не нужно. Выпуск — потом, `0.3.0` вместе
с накопленным, решением владельца.

## Радиус проверен пробой: краснеть нечему

Замер 2026-09-14 на `48f828a`. В `_execute` поставлена черновая классификация —
чистый конверт из одних отмен отдаёт свою первую отмену тем же путём, что
и голый `throw`, — и прогнаны все наборы:

```text
packages/async_job        303  All tests passed!
packages/solo             526  All tests passed!
packages/solo/example       9  All tests passed!
packages/flutter_solo      87  All tests passed!
```

Ни одного красного. Из этого следуют две вещи, и обе важны для плана.

**Старое поведение не сторожит ни один тест.** Всё, что защищает правку,
придётся написать: набор не поймает ни потерю разбора, ни съеденный отказ.
Поэтому мутации в конце плана — не формальность, а единственная проверка того,
что новые тесты кусаются.

**Резать коммиты можно свободно.** Красного дерева между шагами не будет:
правка в `async_job` не роняет ни `solo`, ни `flutter_solo`, хотя оверрайды
показывают её им сразу.

## Коммитов два

1. **Ядро и тесты.** Разбор конверта, классификация ошибки тела, `_toZone`,
   весь новый набор тестов.
2. **Документы.** `doc/children.md`, его перевод, `CHANGELOG` пакета.

Порядок обязателен: документ описывает поведение, которого до первого коммита

## Шаг 1. Разбор в ядре

### Новый `part`: `lib/src/envelope.dart`

Библиотека `lib/src/job_base.dart` уже собрана из частей (`job_context`,
`job_stream`, `job_then`, `outcome`). Разбор — пятая часть, своим файлом: он
самостоятелен, и в `job_base.dart` ему тесно.

```dart
part of 'job_base.dart';

final class _EnvelopeAnalysis {
  const _EnvelopeAnalysis({
    this.firstCancelled,
    this.firstStackTrace,
    this.cancellationCount = 0,
    this.hasRealFailure = false,
    this.hasUnparsed = false,
  });

  final Cancelled? firstCancelled;
  final StackTrace? firstStackTrace;
  final int cancellationCount;
  final bool hasRealFailure;
  final bool hasUnparsed;

  bool get isCleanCancellation =>
      cancellationCount > 0 && !hasRealFailure && !hasUnparsed;
}

/// `null`, если это вообще не конверт: голый объект идёт прежним путём.
_EnvelopeAnalysis? _analyzeEnvelope(Object error) { … }
```

Устройство обхода — по спеке, раздел «Разбор конверта», восемь правил:

- итеративно, стеком, в глубину, слева направо;
- состояние узлов — `Map<Object, _NodeState>.identity()`, `visiting` против
  `visited`: замкнутая ссылка на активный путь ставит `hasUnparsed`,
  законченный подграф проходится снова;
- формы `errors`: `List<AsyncError?>` и кортежи арностей 2..9 рекордными
  паттернами; всё прочее — `hasUnparsed`;
- `null` в позиции — успех ветки; лист, не являющийся `Cancelled`, —
  `hasRealFailure`;
- чтение каждой позиции обёрнуто в `try`: `TypeError` из `cast`-списка ловится
  и даёт `hasUnparsed`. Наружу из разбора не выходит ничего: бросок отсюда
  стоял бы в `catch` у `_execute` и оставил бы задание незаконченным;
- обход полный: счёт отмен и признак отказа нужны обоим вызывающим;
- первая отмена и её след запоминаются по первому вхождению; `defaultError`,
  `errorCount` и `toString` не используются.

### `_execute` (`job_base.dart:894`)

В ветку `on Object catch` добавляется разбор — **перед** чтением `failedFirst`
и перед `notifyObserver`:

```dart
} on Object catch (error, stackTrace) {
  final envelope = _analyzeEnvelope(error);
  if (envelope != null && envelope.isCleanCancellation) {
    final cancelled = envelope.firstCancelled!;
    if (_pendingCancel case final pending?) {
      outcome = pending;
    } else {
      outcome = selfCancelled =
          _handlerCancel(cancelled, envelope.firstStackTrace!);
    }
  } else {
    failedFirst = _pendingCancel == null;
    notifyObserver(error, stackTrace);
    outcome = Failed(error, stackTrace);
  }
}
```

Развилка внутри повторяет `on Cancelled catch` дословно — это она и есть,
только объект добыт из конверта. `_handlerCancel` получает **тот самый**
объект: на его тождестве держится `_outcomeChild` и описание «child victim: …».

### `_toZone` (`job_base.dart:827`)

```dart
void _toZone(Object error, StackTrace stackTrace) {
  if (error is Cancelled) { … }          // как было
  final envelope = _analyzeEnvelope(error);
  if (envelope != null && envelope.isCleanCancellation) {
    return;                               // молчим, как на голой отмене
  }
  _zone.handleUncaughtError(error, stackTrace);
}
```

Конверт с настоящим отказом или с неразобранной частью уходит в зону целиком,
как есть.

### Тесты

Новый файл `test/parallel_wait_test.dart`, `@Timeout(Duration(seconds: 5))`,
группами по разделам спеки. Формы конверта гоняются телом, которое бросает
собранный руками конверт: спека объявила такой конверт прозрачным, так что это
законный вход, а не обход.

| Группа | Пункты приёмки спеки | Тестов |
|---|---|---|
| Чистый конверт | 1–5 | 6 |
| Формы и обход | 6, 7 | 8 |
| Выбор отмены | 8–10 | 3 |
| Внешняя отмена | 11 | 1 |
| Диагностика | 12, 13 | 6 |
| Продолжение `then` | 14 | 1 |
| Сторожа неизменности | 15–22 | 9 |

Арности кортежей 2..9 — 44 позиции — гоняются циклом внутри одного теста группы
«Формы и обход», с отдельным `reason` на каждую позицию.

Два теста требуют внимания при написании:

- **`cast`-список.** Ожидание — задание **закончилось** (а не зависло), исход
  `Failed`, объект тот же. Тест обязан падать по таймауту, если защиту чтения
  снять, — поэтому `@Timeout` в файле обязателен.
- **`ctx.each`.** Кроме исхода и закрытой подписки проверяется тождество
  `StateError` внутри конверта, дошедшего до наблюдателя: без этого мутация
  строки 88 проходит мимо (проверено вторым кругом ревью).

## Мутации

Снимаются по одной, и падать обязан именно названный тест. Набор до правки
зелёный целиком, поэтому мутации здесь — единственное доказательство, что новые
тесты кусаются.

- убрать разбор из `_execute` — падает «чистый конверт даёт отмену»;
- поддержать только список, без кортежей — падают кортежные позиции;
- взять след конверта вместо следа ветки — падает тест следа;
- остановить обход на первой отмене — падает сторож смешанного конверта;
- считать любую найденную отмену достаточной — падает он же;
- заменить активный путь глобальным `visited` — падает тест общей ссылки без
  цикла;
- заменить итерацию рекурсией — падает тест цепочки на 20 000;
- снять `try` вокруг чтения позиции — падает тест `cast`-списка, по таймауту;
- пропустить неизвестный узел — падает тест «неизвестное рядом с отменой»;
- предпочесть отмену своего ребёнка — падает тест «чужая первой, свой ребёнок
  вторым»;
- отфильтровать в `_toZone` конверт с любой отменой — падает сторож зоны;
- поставить `Failed` выше `_pendingCancel` — падает сторож принятой отмены;
- распаковать намеренный `Failed` — падает сторож 20;
- убрать регистрацию уборки у `ctx.wait` — падает сторож 22.

## Чего план не делает

- не трогает `Future.wait`, `Future.any`, `timeout`, `whenComplete`: конверта
  там нет, разбирать нечего;
- не трогает `job_stream.dart:88`, `_isOwnCancellation`
  и `job_context.dart:813` — по спеке, с причинами;
- не заводит публичных типов и не меняет публичный API;
- не даёт ранней отмены веток: решением владельца этой возможности не будет
  вовсе;
- не чинит молчание зоны при накрытом отказе под принятой отменой: это
  действующее правило ядра, и спека его сохраняет.
