## 2. [P2] Отключение источника первым небезопасно и при cancel

Места: `packages/solo/doc/state.md:219` и `docs/ru/solo/state.md:219`. Цитаты:
«with `SoloCloseMode.cancel` it costs nothing»; «и при `SoloCloseMode.cancel`
он ничего не стоит».

`cancel` может ждать работающую задачу с `cancellable: false`. Отказ от обычной
отмены не защищает её от нарушения рабочего типа. Если задача работает
в `Ready` и через `ctx.wait` ждёт ответа устройства, внешний `Disconnected`
отменяет её по правилам и освобождает очередь. Удалённая перед `super.close()`
подписка лишает задачу этого сигнала.

Зонд берёт рецепт `Camera` и запускает такую задачу. Единственное отличие
старого варианта — переставленные две строки в `close`: сначала
`await _link.cancel()`, затем `await super.close(mode: mode)`. После начала
`cancel` источник сообщает отключение. До принудительного освобождения ожидания
в уборке зонда получены точные результаты:

```text
# legacy_cancel.dart — источник погашен первым
CANCEL source=false state=Ready jobFinished=false closeDone=false
# guarded_cancel.dart — порядок нынешнего рецепта
CANCEL source=false state=Disconnected jobFinished=true closeDone=true
```

Оба процесса завершились с кодом 0: зависшее ожидание старого варианта
освобождается самим стендом только после снятия результата. Без этого
освобождения задача продолжала бы ждать недоступный ответ, а `close` — задачу.
Причина видна и в `packages/solo/lib/src/solo_base.dart:643`: отмену можно
отклонить, завершения задачи движок всё равно дожидается.

Цена: читатель, использующий только `cancel`, получает неверное основание
оставить прежний порядок и может зависнуть при закрытии. Нужно ограничить
утверждение условиями, при которых работа больше не зависит от внешних фактов.
Менять сам новый рецепт не требуется: он прошёл оба режима.

Вердикт: подтверждено зондами на старом и новом порядке отключения источника.

**Вердикт:** принято. Фраза «при `SoloCloseMode.cancel` он ничего не стоит»
сужена в обоих языках: порядок безопасен, только пока от факта не зависит ни
одна работающая задача, и `cancel` от этого не спасает — задачу `cancellable:
false`, ждущую ответа устройства, освобождает именно отключение, а `close` ждёт
эту задачу. Рецепт не менялся: он и так проходил оба режима.

## 3. [P2] Миграция не предупреждает о совместимой коллизии isFinished

Место: `packages/solo/CHANGELOG.md:18`. Абзац говорит: «Adding a member to a
class meant to be extended is breaking on its own», затем приводит `Job`
и вероятное совпадение имени у загрузки или синхронизации. Он не говорит, что
собственный булевый признак тоже нужно переименовать, даже если компиляция
после обновления успешна.

Проверены три внешних наследника. Метод `bool isFinished()` не компилируется:

```text
bin/collision_method.dart:4:8: Error: Can't declare a member that conflicts with an inherited one.
```

Геттер `int get isFinished` тоже не компилируется:

```text
The return type of the method 'Download.isFinished' is 'int', which does not match the return type, 'bool', of the overridden method, 'SoloBase.isFinished'.
```

В обоих случаях `dart compile kernel` возвращает 254. Но естественный для
загрузки булевый геттер компилируется с кодом 0:

```dart
class Download extends Solo<int> {
  bool transferComplete = false;
  Download() : super(0);
  bool get isFinished => transferComplete;
  void feed(int value) {
    if (!isFinished) externalSetState(value);
  }
}
```

После `await c.close()` вызов `c.feed(1)` выдаёт:

```text
COMPATIBLE_OVERRIDE closed=true isFinished=false error=Bad state: Download has finished closing, cannot set state
```

Это выполнение скомпилированного `collision_bool.dill`. Рекомендованная
проверка смотрит на доменный признак, а движок правильно проверяет приватный
`_finished`. Поэтому ошибки компиляции не помогают обнаружить такую коллизию.
Обратное значение доменного признака может преждевременно заглушить источник
ещё живого контроллера.

Цена: наследник добавляет защиту из CHANGELOG, получает успешную компиляцию,
но оставляет поздние `StateError`. Нужна явная инструкция переименовать
существующий доменный `isFinished` вместе с его обращениями, включая
совместимые булевы поля и геттеры. Выбранное имя API и приватную проверку
движка менять не предлагается.

Вердикт: подтверждённый пропуск существенного случая миграции.

**Вердикт:** принято, и это самая полезная находка по миграции. Несовместимую
коллизию ловит компилятор, а совместимую — булев `isFinished` наследника — не
ловит никто: код собирается, защита наследника начинает отвечать доменным
флагом, а движок, спрашивающий приватный `_finished`, продолжает отказывать в
записи. В `CHANGELOG` добавлено прямое требование переименовать доменный
признак.

«раньше следующей строки того кода, который изменил состояние».

в журнал `after set(2)`; B только журналирует состояние. Точный вывод:

```text
REENTRANT [A:1, after set(2), B:2, A:2, B:2, after set(1)]
```

Связанное обещание «before the rules ... are re-evaluated» тоже нуждается
в оговорке. Уже существующий зелёный тест

раньше её доставки.

Цена: читатель может поставить после вложенной записи действие, которое
рассчитывает на завершённую обработку слушателями, и выполнить его слишком
рано. Нужно описать отдельный порядок вложенной записи. Это несоответствие уже
было в секции до двух проверяемых коммитов; оно выявлено при требуемой сверке
всей секции с движком. Менять согласованный алгоритм не требуется.
