# `jobs`: исполнительное ядро

## Откуда это

Ядро уже написано дважды. В `solo` оно живёт внутри `SoloBase`; в `scopo`
0.14.0 (в дереве, не выпущен) стоит своя копия: `ScopeInitCancelled` —
это `Cancelled`, `ScopeInitContext` с `check`, `wait`, `onCancel`,
`progress` — это `JobContext`, `ScopeInitHandle` с `cancel()` и фабрикой
`childOf(parent)` — это `Job` с детьми. Дартдоки совпадают дословно, вплоть
до «It ends the waiting, not the work».

Вторая копия беднее: нет `join`, нет `uncancellable`, нет исходов с
причинами, нет отправки необслуженного отказа в зону, дети собраны вручную
через `onCancel`. И в тот же день, когда писалась эта спека, в `scopo`
открытым вопросом стояло «брать ли `join`» — то есть копия продолжала
догонять оригинал руками.

Границу нащупали независимо дважды. Это и есть довод за вынос: не «так
чище», а «одно и то же пишется в двух местах, и одно из них отстаёт».

## Что такое `Job`

`Future`, которую можно отменить. Тело — обычная `async`-функция,
получающая контекст; отмена кооперативная; исход у задачи один из трёх.

```dart
final job = Job<Database>(
  cancellable: true,
  (ctx) async {
    final database = await ctx.join(
      Database.open,
      ifCancelled: (database) => database.close(),
    );
    await ctx.wait(() => database.migrate());
    await ctx.uncancellable(() => database.markReady());

    return database;
  },
);

job.cancel();

final database = await job.value;
```

Всё, что здесь есть, уже написано и покрыто тестами в `solo`. Вынос — это
разрез по существующей границе, а не новая функциональность.

## Что в ядре и чего в нём нет

В ядре: жизненный цикл задачи (создание, старт, отмена, завершение),
исходы, дети, семья ожидания, отправка необслуженного отказа в зону
создания, наблюдатель.

Не в ядре: состояние и `emit`, очередь и политики, правила (`canStart`,
`keepWhile`, рабочий тип `W`), прогресс.

Правил нет вообще — решение владельца 2026-09-05: «кому надо, отменяет».
`keepWhile` без состояния мог бы проверяться только в момент, когда тело
трогает контекст, и не остановил бы задачу, стоящую в долгом `await`. Такой
предикат обещает больше, чем делает, поэтому его нет; а `job.cancel()` —
полноценный канал для того, кто умеет следить сам. Ровно так и работает
solo: переоценивает правила у себя и зовёт отмену.

Прогресса нет по той же причине: единственным его потребителем был бы
`stream_future`, который по плану архивируется, а у `scopo` прогресс свой —
типизированный и завязанный на виджетный слой. Ядро дало бы ему
нетипизированный канал, поверх которого пришлось бы городить свой.

## Публичное API

### `Job<T>`

Хэндл и он же точка создания. Два конструктора:

- `Job(body, {key, describe, cancellable})` — старт назначается на
  ближайшую микротаску, как у `Future(() => ...)`. Тело не начинает
  выполняться внутри конструктора: вызывающий успевает положить хэндл в
  переменную, подписаться на `done` и, если передумал, отменить — тогда
  задача кончится `Cancelled(started: false)`, а тело не запустится вовсе.
- `Job.deferred(body, {key, describe, cancellable})` — не стартует сама.
  Её запускает тот, кто ею распоряжается: `job.start()` вручную, очередь
  solo или родитель через `ctx.run(child)`.

Отложенная форма — не украшение: ребёнок обязан быть отложенным, иначе он
начнёт работу раньше, чем его усыновят, и родитель его не дождётся.
`start()` для уже стартовавшей или законченной задачи — `StateError`.

Члены хэндла переезжают из `solo` как есть: `done`, `value`, `outcome`,
`whenCancelled`, `cancel()`, `ignore()`, `isRunning`, `isFinished`,
`isCancelled`, `key`, `describe()`, `level`, `isChild`.

`isQueued` не переезжает: очередь — это solo, и там он вычисляется по
членству в ней.

### `JobContext`

`check`, `wait`, `join`, `uncancellable`, `onCancel`, `run`, `log`, `job` —
дословно как в `solo`, включая `ifCancelled` у `wait` и `join`. Extension
`each` приезжает вместе с ними: он собран из `wait` и `onCancel` и ничего
больше не знает.

Читать в ядре нечего, поэтому `state`, `stateAs` и `emit` остаются в solo.
Спросить «меня уже отменили?», не бросая, можно через `ctx.job.isCancelled`
— отдельного члена у контекста для этого нет.

### `Outcome` и `CancelReason`

`Outcome<T>` с `Done`, `Failed`, `Cancelled` переезжает целиком; `switch`
по трём случаям остаётся исчерпывающим.

`CancelReason` перестаёт быть `enum` — из чужого пакета enum не расширить,
а причины нужны и solo (`rules`, `closed`), и, вероятно, `scopo`. Вместо
него открытый value-класс:

```dart
final class CancelReason {
  final String name;

  const CancelReason(this.name);

  static const manual = CancelReason('manual');
  static const parent = CancelReason('parent');
  static const handler = CancelReason('handler');

  @override
  bool operator ==(Object other) =>
      other is CancelReason && name == other.name;

  @override
  int get hashCode => name.hashCode;

  @override
  String toString() => name;
}
```

`toString()` тот же, что у enum, поэтому журналы тестов (`Cancelled(rules:
is not NotDisposed)` и сотня подобных утверждений) не меняются. Цена —
исчерпывающий `switch` по причинам компилятором больше не проверяется.

Вместе с этим из причины уходит управление. Сегодня в `_cancel` стоит
`if (!job.cancellable && cancelled.reason != CancelReason.rules) return;` —
то есть «отмену по правилам отклонить нельзя» закодировано в ярлыке. Ядро
не должно толковать причины, которых не знает, поэтому отклоняемость
становится явным аргументом отмены, а причина остаётся надписью для исхода,
наблюдателя и журнала.

### `JobObserver`

`onStart`, `onFinish`, `onError`, `onLog` — без `onChange` и `onClose`,
которых в ядре нет. Глобальной статической точки установки у ядра нет:
наблюдателя получает задача. У `SoloBase.observer` она остаётся своя, и
solo сводит одно к другому в своём наследнике.

## Шов: `JobBase`

Наследуемая основа с защищёнными членами — то, чем сегодня служат
`_private` внутри одного файла. Через границу пакета приватность так не
работает, а `@protected` работает.

Наследнику достаются: `start()`, `finish(outcome)`, `markCancelled(...)`,
статус, список детей, `pendingCancel`, и главное — фабрика контекста.

Фабрика контекста и есть точка расширения:

- solo подставляет свой контекст, добавляя `state`, `stateAs`, `emit`;
- `scopo` — свой, добавляя `progress`;
- обоим достаётся семья ожидания из ядра.

Сегодня это уже делается руками в обоих пакетах — только вместе с
жизненным циклом, который в обоих написан заново.

Статусы в ядре: `created`, `running`, `finished`. `queued` — понятие
очереди, оно у solo.

## Что остаётся в `solo`

`SoloBase`, `Solo`, `SoloQueue`, `Policy`, `SoloObserver`,
`externalSetState`, стрим и `SoloListenable`; `JobContext<S, W>` поверх
контекста ядра со
`state`, `stateAs`, `emit`; правила `W`/`canStart`/`keepWhile` и их
переоценка при каждом изменении состояния; причины `rules` и `closed`;
`isQueued`.

Публичное API solo от выноса не меняется — кроме того, что часть типов
начинает приезжать из `jobs`. Пользовательский код, написанный по нынешнему
README, продолжает компилироваться.

## Порядок работ

1. **Шов внутри solo, без пакета.** Разделить нынешний `_Job` на
   ядро-подобную основу и наследника solo; вынести `_rejectStart` и
   `_rejectKeep` из задачи в движок; свести доступ движка к задаче к
   явному набору членов; сделать `CancelReason` открытым классом и убрать
   толкование причин из `_cancel`. Публичное API не меняется, все тесты
   остаются зелёными.
2. **Пакет `packages/jobs`.** Перенести ядро, посадить `solo` на него
   зависимостью по пути. Пока `jobs` не опубликован, `solo` публиковать
   нельзя — поэтому 0.1.0 solo выходит до этого шага, а вынос приезжает в
   его следующем релизе.
3. **`scopo` на `jobs`.** Отдельная работа в своём репозитории: заменить
   `ScopeInitCancelled`, `ScopeInitContext` и `ScopeInitHandle` на типы
   ядра, оставив себе контекст с `progress`. `scopo` 0.14.0 не выпущен,
   поэтому смена типов наружу ничего не ломает.
4. **`stream_future` архивировать**, а не чинить.

## Открытые вопросы

- Имя пакета. `jobs` свободно и взято рабочим; владелец написал держателю
  `job`. Если имя освободится — переезд до первой публикации бесплатен.
- Нужен ли контексту `isCancelled` отдельным членом. Сейчас предлагается
  обходиться `ctx.job.isCancelled`; у `scopo` в его копии такой член есть,
  и если при переносе окажется, что он там нужен постоянно, это
  неломающее добавление.
