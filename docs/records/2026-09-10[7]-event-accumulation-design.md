# Задача и границы согласования

Владелец положительно оценил сбор событий в список ожидающей задачи,
затем предложил немедленно объединять данные в один `SettingsPatch`.
После сравнения настроек и логов поручил подготовить спеку двух вариантов
с общими правилами очереди.

Предлагаются два способа хранения входных данных до запуска:

- `collect` собирает все события в список в порядке добавления;
- `accumulate` хранит одно значение и обновляет его функцией `merge`.

Имена, сигнатуры, объект накопителя и детали ниже — конкретизация агента,
которую ещё предстоит утвердить. Новый код сейчас не написан.

Данные принадлежат ожидающему `SoloJob`. Состояние контроллера меняет
обработчик через `ctx.emit` при выполнении. `externalSetState` для
аккумуляции не используется. Прежний рецепт с внешней записью состояния
из `2026-09-10[6]-state-accumulation-design.md` остаётся отклонённым.

# Публичный API

Добавить в `SoloBase<S>` две фабрики:

```dart
SoloAccumulator<E, T> collect<W extends S, E, T>(
  Future<T> Function(SoloContext<S, W> ctx, List<E> events) handler, {
  Object? key,
  bool Function(W state)? canStart,
  bool Function(W state)? keepWhile,
  bool cancellable = true,
  String Function()? describe,
});

SoloAccumulator<E, T> accumulate<W extends S, E, T>(
  Future<T> Function(SoloContext<S, W> ctx, E value) handler, {
  required E Function(E accumulated, E incoming) merge,
  Object? key,
  bool Function(W state)? canStart,
  bool Function(W state)? keepWhile,
  bool cancellable = true,
  String Function()? describe,
});

abstract interface class SoloAccumulator<E, T> {
  SoloJob<T> add(E event);
}
```

Фабрика привязывает накопитель к контроллеру, рабочему типу `W`,
обработчику и правилам. Она не создаёт задачу и не запускает работу.
`add` синхронно принимает событие и возвращает хэндл содержащей его
задачи. Контекст обработчика — обычный `SoloContext<S, W>`.

Обработчик и `merge` задаются один раз. В ранних примерах чата они
передавались при каждом событии: это оставляло неоднозначность, какой
колбэк сохранить при объединении. Объект накопителя устраняет её
и связывает типы без сравнения анонимных функций.

`key` задаёт обычный ключ создаваемых задач для поиска, политик и
диагностики; он может быть `null`. Для объединения используется
идентичность накопителя. Два разных накопителя с одинаковым `key`
не объединяются, даже если их типы и обработчики совпадают.

`cancellable`, `canStart`, `keepWhile`, `describe` имеют смысл параметров
обычного `job`. Фабрики и `add` не принимают `policy` или `first`.
Добавление новой группы всегда идёт в хвост очереди.

Накопитель хранится в поле контроллера, обычно `late final`.
Создавать его заново для каждого события означает создавать отдельные
группы. Отдельного `close` у накопителя нет: его жизненным циклом
управляет контроллер. После закрытия контроллера создание пустого
накопителя разрешено, но его `add` возвращает отменённую задачу.

# Пример: настройки

Один `SettingsPatch` описывает одну или несколько правок. Для примера
настройки имеют ненулевые поля, поэтому `null` в правке означает
«не менять поле», а `false` — обычное заданное значение.

```dart
class SettingsPatch {
  final bool? notifications;
  final String? theme;
  final String? language;

  const SettingsPatch({
    this.notifications,
    this.theme,
    this.language,
  });

  SettingsPatch merge(SettingsPatch incoming) => SettingsPatch(
        notifications: incoming.notifications ?? notifications,
        theme: incoming.theme ?? theme,
        language: incoming.language ?? language,
      );

  Settings apply(Settings current) => current.copyWith(
        notifications: notifications ?? current.notifications,
        theme: theme ?? current.theme,
        language: language ?? current.language,
      );
}
```

В контроллере с состоянием `Settings` и полем `SettingsApi _api`:

```dart
late final _updates = accumulate<Settings, SettingsPatch, void>(
  (ctx, patch) async {
    final next = patch.apply(ctx.state);
    await ctx.join(() => _api.save(next));
    ctx.emit(next);
  },
  merge: (accumulated, incoming) => accumulated.merge(incoming),
  key: 'settings',
);

SoloJob<void> update(SettingsPatch patch) => _updates.add(patch);
```

Три вызова до прокачки очереди:

```dart
final a = update(const SettingsPatch(notifications: true));
final b = update(const SettingsPatch(theme: 'dark'));
final c = update(const SettingsPatch(language: 'ru'));

assert(identical(a, b));
assert(identical(b, c));
final outcome = await c.done;
```

Первое событие становится накопленным значением. Второе немедленно
создаёт правку с уведомлениями и темой. Третье добавляет язык. На старте
обработчик получает один готовый `SettingsPatch`; списка событий нет.
Одно поле берётся из последней задавшей его правки, остальные сохраняются.

Настройки меняются при успешном выполнении обработчика, а не при вызове
`update`. Ошибка не меняет состояние и даёт `Failed` всей группе.
Новая отдельная группа не восстанавливает правки неудачной предыдущей.
Повтор этих правок — явное решение вызывающего кода.

В этом примере нет других писателей настроек. Future от `_api.save`
должна означать завершение самой операции; `join` удерживает слот до неё.
Отмена ожидания или клиентский таймаут не доказывают остановку серверной
записи. Эти условия относятся к примеру сетевого сохранения, а не
к механизму аккумуляции. Для nullable-полей с возможностью очистки
потребуется отдельный признак присутствия значения в правке.

# Пример: логи

В контроллере с состоянием `AppState` и полем API:

```dart
late final _logs = collect<AppState, LogEntry, void>(
  (ctx, entries) => ctx.join(() => _api.sendLogs(entries)),
  key: 'logs',
);

SoloJob<void> logEvent(LogEntry entry) => _logs.add(entry);
```

`logEvent(a)`, `logEvent(b)`, `logEvent(c)` до старта создают одну задачу.
Обработчик получает список `[a, b, c]`, включая повторяющиеся записи.
Функция слияния и копирование списка при каждом событии пользователю
не нужны. Список, переданный обработчику, нельзя структурно изменить.

Один пакет сохраняет все принятые в него события. Это не гарантия
доставки логов: ошибка, отмена или закрытие могут завершить пакет без
успешной отправки. Автоматическое сохранение на диск и досылка при
закрытии в эту работу не входят.

# Приём события и граница группы

При вызове `add(event)`:

1. Если этот накопитель уже выполняет `merge`, синхронно бросить
   `StateError`. Эта проверка предшествует проверке закрытия.
2. Если контроллер закрывается или закрыт, вернуть новый `SoloJob<T>`
   с `Cancelled(closed)` и `started: false`. Событие не удерживается;
   `merge` и обработчик не вызываются. Поведение соответствует `run`.
3. Посмотреть только на последний элемент очереди. Если это открытая
   группа того же экземпляра накопителя, принять событие в неё
   и вернуть тот же объект `SoloJob<T>`.
4. Иначе создать новую группу с первым событием и обычный `SoloJob<T>`,
   поставить его в хвост и запланировать обычную прокачку очереди.

Работающая задача никогда не подходит для добавления. Группа закрывается
для новых событий при извлечении из очереди, до проверки стартовых правил
и вызова `onStart`. Событие из этих колбэков относится к следующей группе.
До этой границы список или результат `merge` могут изменяться.

Соседство проверяется в текущей очереди. Между группами не проводится
поиск одинакового ключа; уже созданные группы задним числом не сливаются.
Пример при занятой текущей задаче, где `B` — посторонняя работа:

```text
add A1, add A2           -> [A(A1, A2)]
add B, add A3, add A4    -> [A(A1, A2), B, A(A3, A4)]
```

Это сохраняет порядок относительно `B`. Если промежуточную задачу потом
удалили, оставшиеся группы не объединяются. Следующее событие снова
проверяет только фактический хвост.

Пустые группы не создаются. Пока очередь свободна, накопить несколько
событий можно до её ближайшей прокачки. Во время другой работы события
собираются до старта своей группы. Дополнительной задержки нет.

# Два способа хранения

`collect` держит приватный расширяемый список и добавляет каждое событие
в конец. Амортизированная стоимость добавления данных — O(1), память
для n событий — O(n). При закрытии группы создаётся неизменяемый снимок
списка за O(n), один раз на группу. Последующие группы имеют свои списки.
Копирование элементов неглубокое: объекты событий не клонируются.

`accumulate` хранит одно значение типа `E`. Для первого события
`merge` не вызывается. Для каждого следующего вызов строго левосторонний:
`merge(merge(e1, e2), e3)`. Порядок не меняется; ассоциативность
и коммутативность от пользователя не требуются.

Результат `merge` заменяет прежнее значение только после успешного
возврата. Предыдущие версии не сохраняются. Стоимость определяется
пользовательской функцией и размером результата. Для фиксированного
`SettingsPatch` память на накопленные данные не зависит от числа событий;
для строки или коллекции это уже не так.

`E` может быть nullable: первый `null` является событием, а не признаком
пустой группы. У движка должен быть отдельный признак наличия данных.

События и накопленные значения предполагаются неизменяемыми со стороны
вызывающего. `merge` синхронна и чиста: не меняет аргументы, контроллер,
очередь и внешние объекты. Очередь не делает глубоких копий, не может
откатить мутацию чужого объекта и не освобождает ресурсы внутри событий.
Для передачи владеющих ресурсами объектов нужен отдельный контракт.

# Ошибка слияния и повторный вход

Если чистая `merge` бросает, `add` синхронно пробрасывает ту же ошибку
с её стеком. Входящее событие не принято, новый `Job` не создаётся,
накопленное значение и исход существующей задачи не меняются.
Это ошибка вызова `add`, а не провал тела задачи; уведомление `onError`
для старого `Job` не добавляется. Брошенный `Cancelled` здесь тоже
остаётся исключением вызова и не отменяет существующую группу.

На время `merge` повторный `add` в тот же накопитель отвергается
синхронным `StateError`. Защита снимается в `finally`. Если `merge`
перехватила эту ошибку и вернула значение, внешний вызов может завершиться
успешно; вложенное событие не было принято.

Пользовательский колбэк технически может нарушить требование чистоты:
добавить постороннюю задачу, отменить текущую группу или закрыть контроллер.
Перед записью результата движок повторно проверяет, что контроллер открыт,
группа ещё принимает данные и остаётся хвостом очереди. Если это не так,
внешний `add` бросает `StateError` и не записывает результат слияния.
Он не возвращает хэндл, в который новое событие не попало. Побочные
действия пользовательского колбэка не откатываются, `merge` не повторяется.

Вне выполнения `merge` обычный повторный вход из `onStart`, `onFinish`,
`whenCancelled` и диагностики допускается по текущим правилам движка.
В этих точках
внутренние переходы группы уже должны быть завершены. В частности,
завершённый пакет не должен принять событие из своего `onFinish`.

# Выполнение, результаты и отмена

Группа имеет один `SoloJob<T>`, один запуск обработчика и один исход.
Все вызовы `add`, вошедшие в неё, возвращают идентичный хэндл.
У каждого вызывающего нет отдельной отмены, отдельного результата или
квитанции о доставке своего события. Результат `T` относится ко всей группе.

Правила `W`, `canStart`, `keepWhile` применяются к группе как к обычной
задаче. Добавление событий не проверяет правила и не меняет состояние.
Отказ стартовых правил отменяет всю группу до вызова обработчика.
Исключение стартового правила даёт обычный `Failed`.

Перед передачей данных обработчику выполняется `ctx.check()`. Если
`onStart` уже отменил задачу, обработчик не вызывается; у отмены
`started: true`, поскольку запуск задачи состоялся.

Дальше действуют обычные правила тела: `ctx.run`, `each`, контрольные
точки, дети и уборка. До завершения всей группы слот очереди занят.
Следующая группа может накапливаться в очереди во время её выполнения.
Ожидать добавленную корневую группу из текущей задачи того же контроллера
нельзя: как у обычного `run`, очередь будет ждать собственный текущий слот.

Самостоятельный провал обработчика даёт `Failed`; все события группы
считаются частью этой попытки. Брошенный из тела `Cancelled` означает
самоотмену. Уже принятая отмена сохраняет приоритет над последующим
результатом или ошибкой. Все маршруты ошибок, включая ошибку после
отмены, остаются обычными маршрутами `Job`.

Частичный внешний эффект не откатывается. Очередь продолжает работу,
следующие группы не получают данные провалившейся. Наблюдение исхода
и ненаблюдённые ошибки следуют обычному контракту `Job`.

Отмена через любой общий хэндл касается всей группы. До старта обработчик
не вызывается; после старта отмена кооперативная. Настройка
`cancellable: false`, `uncancellable` внутри тела и обязательная отмена
по правилам имеют обычную семантику `solo`.

Обычные операции очереди видят группу как одну задачу. `clear` и
`remove` отменяют группу целиком. `replace` или `restart` из другого
вызова могут воздействовать на неё по обычному `Job.key`; исключений
для накопителей нет. `droppable` с тем же ключом может вернуть хэндл
группы по действующему контракту типов. Он не добавляет в неё событие.

`close` отменяет ожидающие группы и запрашивает отмену текущей, затем
дожидается её по обычным правилам. Новая финальная отправка не создаётся.
Отдельной автоматической доставки, повторов и передачи данных между
отменёнными группами нет.

# Наблюдение и освобождение данных

Наблюдатель видит одну задачу на группу: обычные начало, завершение,
ошибки и журналирование. Успешное присоединение события не создаёт
промежуточный отменённый `Job` и не вызывает стартовые или финальные хуки.
Новые публичные события наблюдателя в эту работу не входят.

После завершения, в том числе отмены до старта, внутренние ссылки
на список или накопленное значение освобождаются. Удержание завершённого
хэндла не должно само по себе удерживать входные данные через служебное
хранилище группы. Если их сохраняет пользовательский обработчик,
результат `T` или исключение, это уже обычное владение вызывающего кода.
Из самого долгоживущего накопителя не должно быть ссылок на старые группы.

# Внутреннее устройство

Вся новая функциональность живёт в `solo`. Изменений в `async_job`
и новых вариантов `Policy` не требуется. Накопитель — фабрика очередных
корневых задач своего контроллера, а не новая разновидность контекста.

Предлагаемая раскладка:

- `packages/solo/lib/src/accumulator.dart` — новая часть библиотеки
  `solo_base.dart`: публичный интерфейс `SoloAccumulator`, приватная
  конфигурация накопителя, группа и два способа хранения данных.
- `solo_base.dart` — фабрики `collect` и `accumulate`, общий путь приёма
  события. Хвост берётся напрямую из приватной очереди без поиска по ключу.
- `job.dart` — необязательная приватная связь `_SoloJob` с группой
  для обработки извлечения и освобождения данных при завершении.
- `queue.dart` — закрытие группы для добавлений при извлечении,
  включая путь стартовых правил; обычные группы остаются `_SoloJob`.

Два способа хранения используют один алгоритм выбора хвоста, постановки,
фиксации входа и освобождения данных. Конфигурация накопителя неизменяема;
у каждой очередной группы своё изменяемое хранилище. Один накопитель
может иметь несколько групп, разделённых другими задачами, поэтому
единственного глобального буфера или указателя на «ожидающую группу»
недостаточно для владения данными.

Служебная группа и её данные связываются с задачей до вызова любых хуков,
способных вернуть управление в пользовательский код. Завершение очищает
ссылки независимо от того, запускалось ли тело. Новые защищённые методы
ядра, ослабление владения дочерними задачами и новый публичный `Job`
для аккумуляции не требуются.

# Что не входит в эту работу

- Debounce, окно времени, максимальный размер пакета и backpressure.
- Досылка при закрытии, автоматические повторы и хранение на диске.
- Гарантия доставки каждого события или однократного внешнего эффекта.
- Объединение через посторонние задачи, отдельная отмена события.
- Изменение уже работающей группы или состояния при приёме события.
- Универсальное преобразование типа события `E` в другой тип аккумулятора.

Вопросы окна задержки и буфера с досылкой остаются в `docs/backlog.md`.
Сбор в список решает упаковку событий для одного запуска, но не весь
контракт надёжного буфера. Записи бэклога этой работой не удаляются.

# Проверки будущей реализации

Тестировать в `packages/solo/test/accumulator_test.dart` через `FakeAsync`
и управляемые `Completer`, без реального времени. Проверять журнал вызовов,
идентичность хэндлов, данные и моменты завершения.

1. Создание накопителя не добавляет задач. Первое событие создаёт группу.
   Три синхронных события дают один хэндл и один вызов обработчика.
2. `collect` сохраняет порядок, повторы и nullable-события. Снимок
   неизменяем и не меняется от добавлений в следующую группу.
3. `accumulate` не зовёт `merge` на первом событии, затем зовёт строго
   слева направо при каждом `add`, ещё до прокачки. Возврат `null`
   допустим для nullable-типа; фиксированная правка не хранит историю.
4. Ошибка чистой `merge`, в том числе брошенный `Cancelled`, оставляет
   прежнее значение, не создаёт задачу и синхронно достигает вызывающего.
   Следующее корректное событие по-прежнему может присоединиться.
5. Повторный вход в `merge` отвергается; после исключения защита снята.
   Изменение хвоста, отмена группы и закрытие из `merge` не приводят
   к записи в неподходящую группу, повторному вызову или ложному хэндлу.
6. Посторонняя задача разделяет группы. Разные экземпляры накопителя
   не объединяются при одинаковых ключах, типах и обработчиках.
   Удаление разделителя задним числом не сливает уже созданные группы.
7. Добавление во время работы, из стартового правила или `onStart`
   не меняет извлечённую группу. Следующая группа ждёт тело, детей
   и уборку предыдущей, прежде чем начать обработку.
8. `W`, `canStart`, `keepWhile` работают на всю группу. Отмена из
   `onStart` не вызывает обработчик и имеет `started: true`.
9. Все участники группы получают общий `T`, `Failed` или `Cancelled`.
   Отмена одним участником касается всех. Ненаблюдённый провал группы
   сообщается по обычным правилам, один раз для одного `Job`.
10. Ошибка или отмена группы не переносит данные в следующую. Частично
    выполненный обработчик не перезапускается автоматически.
11. `clear`, `remove`, политики с тем же ключом и `cancellable: false`
    сохраняют обычную семантику. Повторный вход из завершения не оживляет
    старую группу. После завершения внутреннее хранилище освобождено.
12. `close` снимает ожидающие группы и ждёт текущую, включая отказ отмене;
    досылки нет. `add` после закрытия не вызывает `merge` или обработчик,
    даёт `Cancelled(closed)` и не удерживает событие.
13. Настройки: разные поля объединяются, последнее присваивание одного
    поля побеждает, `false` не теряется, состояние до тела не меняется.
14. Логи: один список на запуск, все записи в порядке добавления,
    один снимок при старте вместо копирования при каждом событии.

Проверки памяти должны проверять освобождение служебного хранилища,
а не зависеть от недетерминированного времени сборки мусора. Требование
сложности `collect` сверяется с алгоритмом и содержательным тестом
большого пакета, без порога времени на конкретной машине.

# Документация и условия готовности

При реализации добавить `packages/solo/doc/accumulation.md` и перевод
`docs/ru/solo/accumulation.md`, ссылки из обоих README `solo`, запись
CHANGELOG и dartdoc API. Примеры должны показывать оба способа,
наблюдение исходов и границы отмены. Обновить `docs/architecture.md`
по фактической реализации и включить новую пару в проверку переводов.

Перед коммитом кода выполнить анализ и тесты `solo` и затронутых примеров;
проверки зависимых пакетов по необходимости для нового API. Обязательны
сверка переводов, dartdoc, форматирование, ширина Markdown и дифф.
Сценарии интеграции должны подтвердить отсутствие изменений в поведении
обычных задач и политик. После утверждения спеки составить план реализации.

Для подготовки этой записи прочитаны текущие `SoloBase`, `_SoloJob`,
`SoloQueue` и переходы запуска и завершения `JobBase`. API выше является
предложением; примеры с ним ещё не компилировались и не запускались.
Проверки нынешней работы охватывают документ, его ссылки и ширину строк.
