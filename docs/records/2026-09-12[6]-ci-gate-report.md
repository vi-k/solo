# Гейт машиной

Владелец спросил, есть ли CI. Был один workflow, и не про код:
`site.yml` собирает документацию и публикует её на Pages, триггер — push
в `main` по путям документации. Ни анализа, ни тестов, ни формата, ни
проверок документов; гит-хуков в репозитории тоже нет. Весь гейт держался
на том, что его прогоняет агент в сессии.

## Находка по дороге

Пример `flutter_solo` разрешался против **опубликованного** `solo`
0.2.0, а не против дерева. Зонд: файл в `lib/` примера с обращением к
`currentState` и `flutter analyze` — `undefined_getter`, хотя геттер в
дереве есть с утра.

Причина: у `packages/flutter_solo/example` не было своего
`pubspec_overrides.yaml`, а оверрайды `packages/flutter_solo` до него не
доходят — pub применяет оверрайды только того пакета, который разрешает,
и путевая зависимость приносит один свой `pubspec.yaml`.

Почему молчал `flutter analyze` примера: ошибки живут в файлах
зависимости, а анализ примера их не показывает. То есть проверка была
зелёной и не значила ничего — ровно тот случай, против которого в
`AGENTS.md` написано правило про оверрайды. Добавлен четвёртый файл,
`package_config.json` примера теперь показывает `../../../solo`, список
в `AGENTS.md` дополнен вместе с причиной.

## Что в workflow

`name: gate`, триггеры — push в `main`, pull request, ручной запуск;
группа конкурентности по ref с отменой прежнего прогона. Три задания:

| Задание | Что делает |
| --- | --- |
| `dart` | `async_job`, `solo`, `packages/solo/example`: `pub get`, формат, анализ, `dart doc --dry-run`, тесты |
| `flutter` | `flutter_solo` и его пример: то же плюс `flutter test` |
| `docs` | `check_line_width`, `check_doc_shape`, `check_translations`, `build_site.py` |

Разделение на `dart` и `flutter` — не для скорости. В задании `dart`
Flutter не ставится вовсе, и это и есть проверка обещания «никакого
Flutter в ядре»: случайный `package:flutter` в `solo` или `async_job`
перестанет разрешаться там и больше нигде.

Версии прибиты к полу пакетов: Dart 3.6.0 и Flutter 3.27.0, который его
несёт. Локально это даёт `fvm`, здесь — сами actions, так что `fvm`
в командах не нужен.

Каждое задание кончается шагом «ничего не уползло»: `git status
--porcelain` пуст. `--porcelain`, а не `git diff --exit-code`: второй
сравнивает отслеживаемое и молчит о файле, который шаг создал из ничего.

Чего в гейте нарочно нет:

- `dart pub publish --dry-run`. Между выпусками в дереве лежат оверрайды,
  и прогон по ним описывает не тот архив, который уйдёт. Готовность к
  выпуску — шаг выпуска, порядок в
  `2026-09-11[1]-solo-release-readiness-report.md`;
- проверки `AGENTS.md` и записей `docs/records/`: скрипт ширины берёт
  `packages/` и `docs/` и пропускает записи по замыслу, так что это
  по-прежнему работа глазами;
- задания «потолок» (прогон на текущем stable) — не заказывали; если
  нужно, добавлю отдельно, как в `scopo`.

## Проверено локально

Весь YAML разобран парсером (`js-yaml` из `site/node_modules`): три
задания, шаги на месте. Тела шагов прогнаны из корня репозитория теми же
командами и в том же порядке: анализ чист в четырёх пакетах, тесты 303 +
492 + 9 + 37, формат 30 + 66 + 12 файлов без изменений, `dart doc
--dry-run` 0/0 в трёх пакетах, три проверки документов чисты, сайт
собирается — 42 страницы.

Чего проверить нельзя не запуская: сами actions и их версии
(`actions/checkout@v7` взят из `site.yml` этого же репозитория,
`dart-lang/setup-dart@v1`, `subosito/flutter-action@v2` и
`actions/cache@v4` — из CI соседних проектов владельца). Первый прогон
на GitHub покажет.
