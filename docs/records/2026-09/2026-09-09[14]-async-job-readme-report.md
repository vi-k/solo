# README async_job

По просьбе владельца README переписан более естественным техническим
языком. Вместо метафор и риторических противопоставлений текст прямо
описывает действия задачи, вызывающего кода и обработчиков. Длинные
абзацы разделены по смыслу; перечисления правил оформлены списками.

Сохранены правила отмены и наблюдения ошибок, порядок уведомлений,
связи причин отмены, поведение дочерних задач и освобождение ресурсов.
`join` объяснён самостоятельно; отмена после `return` показана на примере
ожидания дочерней задачи. `wait` предложен для прекращения ожидания.

Английский оригинал и русский перевод изменены вместе. Все 17 блоков
кода в каждом файле и адреса ссылок сохранены. Реализация не менялась.

По следующему замечанию владельца во введении русского README возможности
API описаны через имя `Job`: «`Job` также предоставляет» и «`Job` объединяет
эти действия». Слово «задача» сохранено в описаниях выполнения работы.

Рекомендация по ожиданию восстановлена явно: внешние асинхронные операции
в теле следует вызывать через контекст. Прямой `await` допустим технически,
но сам не проверяет отмену. Внутри действия, переданного методу контекста,
он уместен; контрольные точки не добавляются между внутренними шагами
автоматически. Пример уборки после прямого `await` помечен как объяснение
поведения, с рекомендацией использовать `join` при получении ресурса.

Перед рекомендацией `solo` восстановлено объяснение границ `async_job`:
в ядре нет управления состоянием, очереди и правил планирования. Затем
текст поясняет, что `solo` добавляет эти возможности. Оба языка обновлены.

## Повторная вычитка на связность

По просьбе владельца оба README целиком сопоставлены с версией до
редактуры (`72915bc`). Проверялись последовательность введения понятий,
причины выбора API, условия поведения и переходы между абзацами.

- Во введении проблема обычной Future предшествует объяснению `Job`.
  Кооперативная отмена объясняет, зачем телу методы контекста.
- Перед Quick start поставлена задача примера. Вернулась связь между
  остановкой миграции по токену, ожиданием `join` и защитой `markReady`.
- Получение исхода и наблюдение ошибок описаны до собственных причин
  отмены. Уведомление `whenCancelled` отделено от итогового исхода.
- `join`, `wait` и `uncancellable` собраны как три варианта ожидания.
  Условия отмены названы явно. `onCancel` связан с механизмом остановки
  операции, `unattended` с асинхронной остановкой, `each` с подпиской.
- Ожидание дочерних задач объясняет момент уборки. Пример буфера поясняет
  прямую регистрацию колбэка, а возврат ресурса из `join` объясняет,
  зачем для снятия регистрации нужен `disown`.
- Второй проход `discard` объясняется после отмены во время уборки.
  Ожидание собственной задачи из уборки связано с взаимной блокировкой.
- Наблюдатель сначала введён как канал событий и ошибок, затем показан
  его пример и подробности журналирования. Отложенный запуск связан
  с автоматическим запуском обычного `Job`, расширение ядра с его границами.

Спорные утверждения сверены с реализацией: ожидание в `join`, обработка
поздних значений, доступность контекста при уборке, уведомления и порядок
завершения. Код и примеры не менялись. Все блоки кода и адреса ссылок
сопоставлены как с `72915bc`, так и с HEAD перед этой правкой.

По следующему замечанию владельца исправлено пояснение двух примеров

выбор этого типа не определяет способ проброса. Код примеров не менялся.

## Проверка перехваченной отмены

Утверждение об исходе `Cancelled` после перехвата проверено по реализации
и отдельным Dart-зондом с `FakeAsync`. Все четыре сценария прошли:

- После принятого `job.cancel()` тело перехватывает `Cancelled` из
  `ctx.wait`, выполняет код после `catch` и возвращает 42. Итог:
  `Cancelled(manual)`.
- Тот же сценарий с `ctx.join` даёт `Cancelled(manual)`. В обоих случаях
  следующий `ctx.check()` бросает ту же отмену, а `cancel()` ждёт тело.
- Перехваченный `Cancelled`, брошенный операцией внутри `ctx.join`,
  не отменяет сам `Job`: итог `Done(42)`, `isCancelled == false`.
- Перехваченный `Cancelled` от `child.value` не отменяет родителя:
  у дочерней задачи `Cancelled`, у родителя `Done(42)`.

Причина видна в завершении `JobBase`: принятая отмена в `_pendingCancel`
имеет приоритет над результатом тела. Перехват исключения не очищает её.
Если отметки не было и исключение не вышло из тела, завершение получает
обычный результат тела. Пока тело ещё ждёт, итогового исхода нет.

В обоих README уточнены условие принятой отмены, возможность выполнения
кода после `catch`, повторный бросок на контрольной точке и отличие
от перехваченной отмены отдельной операции или дочерней задачи.
