# Ревью спеки `ctx.runAll`, второй круг

## Вердикт

**Вторая редакция пока не годится, чтобы писать по ней план.** Ранний сигнал
из ядра реализуем, но документ совместил новую точку наблюдения со старыми
правилами, выведенными из завершения `ctx.run`. От этого меняются доступные
ошибки, тождество отмены, владение значением и смысл трёх критериев приёмки.

Предмет ревью — `docs/records/2026-09-14[10]-eager-parallel-run-design.md`,
вторая редакция. Проверены оба отчёта первого круга с вердиктами владельца,
соседняя спека
`docs/records/2026-09-14[4]-parallel-wait-cancellation-design.md`, указанные
файлы ядра, доменный приём `solo` и соответствующие существующие тесты.

Написаны четыре запускаемых зонда и общий вспомогательный файл. Все четыре
прогона завершились кодом 0 и строкой `CHECKS OK`. Реализации `runAll` нет
ни в ядре, ни в зондах. Там вызывается действующее ядро, сохраняется результат
пользовательского тела и отдельно воспроизводятся запросы отмены либо вызовы
уборщика. Это доказательства свойств механизма, а не прогоны будущего API.

`TapJob.execute` добавляет один `await`, чтобы записать возврат или бросок тела
до классификации ядром. Поэтому `rawBody` в выводе — измерительный снимок,
а не готовый исход `_execute`. Порядок точного числа микрозадач по нему
не утверждается. Барьеры проверяются после исчерпания микрозадач.

## Находки

### 1. Два принятых вердикта стали несовместимы после перехода к исходам тел

**Важность:** блокирует план

**Что не так:** Строки 160–164 требуют выбрать настоящий отказ среди веток.
Строки 302–318 одновременно утверждают, что отказ внутри уже отменённого `join`
комбинатор не увидит и его маршрут не изменится. Второе было верно для первого
прототипа, который слушал `ctx.run`. Новый сигнал тела этот отказ видит: `join`
пропускает ошибку операции наружу независимо от отмены, а `_execute` создаёт
`Failed` до окончательного `_pendingCancel ?? outcome`.

Получается выбор, которого документ не сделал. Если всякий `Failed` тела
участвует в выборе, ошибка остановленной операции может превратить чистую
отмену группы в отказ. Если отказ после пометки исключается, нужно назвать это
исключение и передать признак времени пометки вместе с ранним событием. Одного
объекта `Outcome` для такого различения недостаточно.

В соседней работе правило уже ограничено явно: отказ после принятой отмены
является диагностикой тела, исход остаётся отменой, в зону такой отказ
не отправляется. Код сохраняет это через `failedFirst`, считанный **перед**
`notifyObserver`. Наблюдатель сам может отменить задачу.

Поэтому принятие находки 3
в `docs/records/2026-09-14[11]-eager-parallel-run-review.md` требует поправки
в обосновании: соседняя спека не вводит безусловное правило «любой настоящий
отказ во всей работе побеждает отмену». Она классифицирует доступный конверт
и сохраняет приоритет принятой отмены. Принятие находки 3
в `docs/records/2026-09-14[12]-eager-parallel-run-review-2.md` было верным для
старого механизма; его утверждение о невидимости отказа больше неверно.

**Доказательство:** Из `/private/tmp/c9e4b1-r2c/packages/async_job`:

```sh
rtk proxy dart run probe/body_signals.dart
```

Точные строки:

```text
CASE cancel-before-body-error/join/observer=false
bodyFailed=true branch=Cancelled(probe-stop) observerErrors=0 zoneErrors=0
zone=[]
CASE cancel-before-body-error/join/observer=true
bodyFailed=true branch=Cancelled(probe-stop) observerErrors=1 zoneErrors=0
zone=[]
CASE envelope-sees-final-branches
bodyFailed=true a=Cancelled(probe-stop) parent=Cancelled(handler: child a: Cancelled(probe-stop))
zone=[]
```

Отмена здесь подана вручную, собственной причиной зонда. Это та же публичная
операция `cancel`, которой будет пользоваться комбинатор. В последнем входе
настоящее `[ctx.run(a), ctx.run(b)].wait` получает окончательные отмены обеих
веток и закономерно не видит записанный отказ тела `a`.

Для `wait` граница действительно другая: тело уже закончено отменой, а ошибка
оставленной операции идёт через `notifyError`; зонд это различает. Код:
`job_context.dart:594`, `job_base.dart:906–924,987–996`.

**Что предлагаю:** Определить множество ошибок, участвующих в выборе, с учётом
отказа до и после принятой отмены ребёнком. Для сохранения смысла соседнего
решения передавать раннему потребителю также `failedFirst`, считанный
до пользовательских уведомлений. Если намеренно выбираются и отказы после
пометки, прямо принять отличие `runAll` от ожидания окончательных исходов
и переписать «Границу обещания». Сам разбор конверта менять не нужно.

**Вердикт: принято, блокирует.** И поправка к моему обоснованию верна:
`2026-09-14[4]-parallel-wait-cancellation-design.md` не вводит безусловного
«любой настоящий отказ побеждает отмену», он классифицирует доступный конверт
и сохраняет приоритет принятой отмены. Мой вердикт по находке 3 первого круга
был прав по сути и неточен в доводе. Выбор пойдёт по итоговым исходам веток —
там накрытого отказа нет по построению.

### 2. Не определено, какой исход сообщает шов и как учитывается поздняя отмена

**Важность:** блокирует план

**Что не так:** Существуют три разных объекта: брошенная телом ошибка,
классифицированный исход тела и окончательный исход ветки. Строки 177–205
переходят между ними без определения границы.

Обычный `throw Cancelled(...)` ядро превращает в новый `Cancelled` через
`_handlerCancel`. Если переслать сырой объект тела, родитель не найдёт его
в `_outcomeChild`, даже дождавшись ребёнка. Следовательно, одного обещания «не
копировать объект в runAll» недостаточно для критерия 5.

Поставить уведомление до разбора ошибок тоже нельзя: чистый `ParallelWaitError`
выглядит там обычной ошибкой, хотя классифицированный исход тела — отмена. Член
сам конвертов не создаёт, но ребёнок вправе их бросить.

Обратный переход не менее существенен: тело может вернуть `Done(7)` после
внешней отмены, а ветка закончится `Cancelled`. Это законно для обычного
`await` чужого будущего. Только исходов тел недостаточно, чтобы исполнить
обещание о чужой отмене из строк 183–189 и критерий 13. Названная в цене пара
«отказ тела / отмена ветки» этого случая успеха не покрывает.

**Доказательство:** Из каталога пакета выполнены:

```sh
rtk proxy dart run probe/body_signals.dart
rtk proxy dart run probe/ownership_and_routes.dart
rtk proxy dart run probe/acceptance_edges.dart
```

Точные строки:

```text
CASE cancel-object/forwardRaw=true
rawIsBranch=false causeIsBranch=false parent=Cancelled(handler: body-cancel)
CASE cancel-object/forwardRaw=false
rawIsBranch=false causeIsBranch=true parent=Cancelled(handler: child child: Cancelled(handler: body-cancel))
CASE body-value-final-cancellation
body=Done(7) branch=Cancelled(probe-stop) runThrewBranch=true
CASE raw-clean-envelope-is-not-a-body-failure
rawTap=Failed branch=Cancelled(handler: nested) observerErrors=0 stack=LEAF_STACK
```

Первый и второй входы различаются только тем, какой объект родитель бросает
после ожидания ребёнка. Это проверка тождества, а не модель `runAll`. Привязка
отмены к ребёнку записывается только в `finish`, `job_base.dart:737–743`; её
читает `_handlerCancel`, строка 1033.

**Что предлагаю:** Назвать раннее событие результатом **после классификации**
тела. Сохранять также окончательный канал завершения ветки: он нужен для
поздней отмены, значений, уборки и привязки причины к ребёнку. Уточнить, какой
объект отмены выигрывает, если исход тела позднее накрыт другой отменой. Если
наружу должен идти ранний объект отмены, отдельно определить его связь
с ребёнком: существующая карта окончательных исходов этого не гарантирует.

**Вердикт: принято, блокирует.** Три объекта разведены явно: брошенное телом,
классифицированный исход тела и итог ветки. Комбинатор берёт итог. Замечание
про место шва принято отдельно: раньше разбора конверта его ставить нельзя,
иначе чистый `ParallelWaitError` ребёнка прочитается отказом.

### 3. Главный критерий не разделяет раннее уведомление и конец группы

**Важность:** блокирует план

**Что не так:** Критерий 3, строки 462–466, требует, чтобы ошибка уже вышла
из группы до отпускания барьеров. Основное правило и раздел цены требуют
дождаться сворачивания. Для барьера, который отмена не освобождает, эти
требования несовместимы. Прежняя проблема раннего сигнала получила новое
ожидание, которое может запрещать правильное ожидание детей.

Есть и невыбранный участник отмены. «Остальные ветки» в строке 133 исключают
источник отказа; «каждая ветка, которая ещё не кончилась» в строке 209 включает
его. Если отменены только соседи, потомок упавшей ветки продолжает держать
группу. Если отменять также источник, его исход может стать отменой, а причина
`SiblingCancelReason` с описанием «другая ветка» становится причиной остановки
из-за собственного отказа.

**Доказательство:** Из каталога пакета:

```sh
rtk proxy dart run probe/body_signals.dart
```

Точные строки:

```text
CASE failed-source-descendant/cancelSource=false
beforeRelease sourceBodyFailed=true sourceFinished=false descendantCancelled=false siblingFinished=true parentFinished=false
afterRelease parentFinished=true
CASE failed-source-descendant/cancelSource=true
beforeRelease sourceBodyFailed=true sourceFinished=true descendantCancelled=true siblingFinished=true parentFinished=true
afterRelease parentFinished=true
CASE failed-source-with-uninterruptible-descendant
beforeRelease sourceCancelled=true descendantFinished=false parentFinished=false
afterRelease parentFinished=true
```

Первые два входа используют отменяемое ожидание потомка. Последний — обычное
будущее за барьером и `cancellable: false`. Никакой таймаут не выдаётся
за доказательство зависания: перед отпусканием барьера нет события, которое
могло бы завершить это ожидание.

**Что предлагаю:** До отпускания барьера проверять запрос отмены соседа, его
причину и сохранение незавершённого `runAll`. После отпускания — исход, ошибку
и след. Отдельным входом доказать быстрое завершение, когда вся уборка
и потомки кооперативно заканчиваются. Прямо выбрать, останавливаются ли потомки
источника отказа и какой причиной; это часть поведения, а не место для догадки
исполнителя плана.

**Вердикт: принято, блокирует.** Критерий 3 переписывается: до отпускания
барьера проверяется, что **соседи остановлены**, а не что ошибка вышла наружу.
Вторая половина решена так: **источник отказа не отменяется**. Иначе его исход
станет `Cancelled(sibling)` и съест тот самый отказ, ради которого всё
затевалось; цена — его потомки доигрывают, и группа их ждёт.

### 4. Уведомление только из `_execute` пропускает завершение без тела

**Важность:** блокирует план

**Что не так:** Доменный отказ `beforeChildStart` вызывает `finish` и вообще
не заходит в `_execute`. Критерий 11 требует получить такую отмену, а шов,
описанный только как уведомление об исходе тела, не производит события.
Ожидание количества сигналов по числу принятых элементов повиснет.

Синхронный бросок правила либо `createContext` тоже завершает ребёнка `Failed`
без тела. В общем ядре этот ребёнок **не вызывает `onError`**: `startChild`
делает `ignore`, `finish(Failed(...))` и `rethrow`. `finish` уведомляет
о завершении, но не об ошибке. Поэтому основание маршрута «ветка уже сказала
наблюдателю» из строк 288–295 не универсально.

В `solo` бросающее правило отдельно вызывает `_notifyObserver` именно потому,
что ядро этого не делает. Нельзя переносить эту доменную страховку на любой
допустимый наследник `JobBase`. Для выбранного и пойманного отказа приёма
отсутствие наблюдателя не является потерей ошибки: её получил вызывающий.
Находка — в неверной предпосылке и неописанной ответственности за эти входы,
а не требование поменять сегодняшнее поведение `finish`.

**Доказательство:** Из каталога пакета:

```sh
rtk proxy dart run probe/ownership_and_routes.dart
rtk proxy dart run probe/solo_admission.dart
```

Точные строки:

```text

executions=0 bodySignal=null branch=Failed(Bad state: context-throws) syncThrow=true caughtSame=true observerErrors=0
CASE no-body/rule-throws
executions=0 bodySignal=null branch=Failed(Bad state: rule-throws) syncThrow=true caughtSame=true observerErrors=0
CASE no-body/rule-rejects
executions=0 bodySignal=null branch=Cancelled(probe-stop) syncThrow=false caughtSame=false observerErrors=0
CASE solo-rule/throws=false
executions=0 child=Cancelled(rules: canStart) syncThrow=false thirdStarted=true reportedBy=[] parent=Done(null)
CASE solo-rule/throws=true
executions=0 child=Failed(Bad state: start-rule) syncThrow=true thirdStarted=true reportedBy=[child] parent=Done(null)
```

Контрольный `direct-finish-failed` также дал `observerErrors=0`. Код:
`job_context.dart:960–995`, `packages/solo/lib/src/job_context.dart:142–164`.

**Что предлагаю:** Описать завершение без исполнения как отдельный вход группы
и учитывать каждый элемент ровно один раз, даже если у него нет события тела.
Отдельно определить приоритет синхронного отказа приёма над уже полученными
отказами тел и путь невыбранных ошибок. Не добавлять второе уведомление ребёнку
`solo`, который уже сообщил о бросившем правиле.

**Вердикт: принято, блокирует.** Ветка может кончиться, не заходя
в `_execute` вовсе, и наблюдателю о себе не сказать. Счёт веток пойдёт
по итогам, а не по сигналам тела — тогда отсутствие сигнала ничего не ломает.
Обоснование маршрута опоздавших ошибок («ветка уже сказала наблюдателю»)
поправлено: оно верно для ветки с телом и неверно для завершения без тела.

### 5. `cleanUp` не имеет определённой границы передачи владения

**Важность:** править до плана

**Что не так:** Строки 276–280 обещают один вызов для каждого полученного
значения, но после появления сигнала тела «полученное значение» неоднозначно.
Тело может вернуть ресурс, пока ветка ещё ждёт потомков или свой асинхронный
уборщик. Если группу в это время остановить, `discard` ветки закроет ресурс
из-за окончательной отмены. Один вызов группового `cleanUp` для сохранённого
значения тела закроет его второй раз.

Это не повтор находки первого круга о `dispose` на полном успехе. Новый
контрпример использует правильный `discard`, а пересечение владельцев
появляется из-за наблюдения значения **до** окончательного исхода ветки.

**Доказательство:** Из каталога пакета:

```sh
rtk proxy dart run probe/ownership_and_routes.dart
```

Точные строки:

```text
CASE body-value-discard-then-group-cleanup
beforeCancel bodyHasSame=true branchFinished=false closes=0
afterDrain branch=Cancelled(probe-stop) closes=1
afterOneCallbackOnBodyValue closes=2
```

Последний вызов сделан зондом вручную: это применение предложенного правила
к сохранённому значению тела, **не** результат отсутствующего `runAll`.
Идентичность ресурса проверена; групповой колбэк моделируется одним `close`.
Повторное закрытие веткой следует из существующей обработки `_skipped`
в `job_base.dart:966–985`.

**Что предлагаю:** Передавать группе владение значением только при
окончательном `Done` ребёнка. Ранний сигнал нужен для остановки, а не для
преждевременной передачи ресурса. Явно назвать, что ресурс тела, накрытого
отменой ветки, освобождает сама ветка через `discard`; группе он не передан.
К критерию 14 добавить этот вход и поздний успешный результат неотменяемого
ребёнка после начала сворачивания.

**Вердикт: принято**, и решение совпадает с тем, к которому пришёл второй
ревьюер этого круга: владение передаётся группе только на окончательном `Done`
ребёнка.

### 6. Асинхронность уборщика и отмена внутри уборки не закреплены приёмкой

**Важность:** править до плана

**Что не так:** Подпись принимает `FutureOr<void>`, но текст не говорит прямо,
дожидается ли группа возвращённого будущего, продолжает ли остальные уборки
после его ошибки и что именно считается концом группы при отмене родителя
во время уборки. Критерий 14 содержит только флаг, счётчик и ошибку; его можно
выполнить одними синхронными уборщиками, не проверив ни одного из этих свойств.

Обычный `try { cleanUp(value); } catch` ловит синхронный бросок, но пропускает
ошибку после `await`. Она даже может оказаться в ожидаемой зоне, и тест «ошибка
ушла в зону» останется зелёным при неверном порядке завершения. Следовательно,
проверять нужно барьер и состояние группы до его отпускания.

Принятая отмена родителя по существующему правилу побеждает ошибку тела
и во время такой уборки. Формулировку «ошибка уборщика не подменяет ошибку
наружу» нельзя читать как обещание, что наружу всегда выйдет прежний отказ
после внешней отмены.

**Доказательство:** Из каталога пакета:

```sh
rtk proxy dart run probe/ownership_and_routes.dart
```

Точные строки из изолированной проверки вызова колбэка:

```text
CASE async-cleanup/await=false
beforeRelease entered=1 cleanupEnded=false jobFinished=true
afterRelease caughtCleanup=false zoneCleanup=1 outcome=Failed(Bad state: selected)
CASE async-cleanup/await=true
beforeRelease entered=1 cleanupEnded=false jobFinished=false
afterRelease caughtCleanup=true zoneCleanup=0 outcome=Failed(Bad state: selected)
CASE parent-cancel-during-async-cleanup
beforeRelease entered=1 finished=0 parentFinished=false
afterRelease closes=1 originalInObserver=1 originalInZone=0 cleanupInZone=1 parent=Cancelled(manual)
```

В последнем входе зонд сам маршрутизирует ошибку уборщика через существующий
`reportToZone` и затем бросает выбранный ранее отказ. Так проверяется приоритет
`_pendingCancel`, а не готовый групповой уборщик.

**Что предлагаю:** Зафиксировать ожидание всех начатых уборок, однократность
по принятому результату, продолжение после синхронного и асинхронного броска,
приоритет внешней отмены. Проверять два ресурса: первый уборщик бросает, второй
всё равно вызывается; один из них держит барьер. Отдельно проверить отмену
родителя в этом окне и возврат успеха после контрольной точки `solo`. Уточнить
позиции с `null` при nullable `T` и одинаковые объекты в результатах разных
детей: «один раз на значение» не должен неявно означать дедупликацию.

**Вердикт: принято.** Асинхронный уборщик, ошибка уборщика и отмена внутри
уборки закрепляются критерием, а не остаются подразумеваемыми.

### 7. Критерий 9 требует пересказа ошибки, которая теперь выбрана основной

**Важность:** блокирует план

**Что не так:** В критерии 9 первая ветка даёт отмену, а неотменяемый сосед
позже бросает единственный настоящий отказ. По новому правилу этот отказ
становится результатом `runAll`, как уже требует критерий 4. Он больше
не является невыбранной ошибкой, для которой нужен пересказ в зону.

Требования «в зоне ровно один раз» и «от родителя наблюдателю ни разу»
описывают старую политику первой ошибки. Если тело родителя пропустит новый
выбранный отказ наружу, `_execute` обязан сообщить о нём наблюдателю родителя.
Если тело его поймает, дополнительный пересказ в зону всё равно не следует
из правила о невыбранных ошибках.

**Доказательство:** Само противоречие — между строками 467–470 и 489–492 спеки.
Поведение ядра при выходе выбранного отказа проверено из каталога пакета:

```sh
rtk proxy dart run probe/acceptance_edges.dart
```

Точные строки:

```text
CASE promoted-failure-is-the-selected-error
parent=Failed(Bad state: only-real-failure) reportedBy=[child, parent] zoneErrors=0
```

Зонд не притворяется реализацией повышения приоритета: он изолирует следующий
шаг после выбора единственного отказа — передачу той же ошибки через тело
родителя. При наблюдённом исходе этот шаг не создаёт сообщения в зону.

**Что предлагаю:** Для критерия 9 использовать **два настоящих отказа**: первый
выбирается, второй становится невыбранным. Проверять тождество второго объекта
и отдельно его сообщения в зоне, у ребёнка и у родителя. Вход «сначала отмена,
потом единственный отказ» оставить в критерии 4 и явно проверить отсутствие
лишнего пересказа выбранного отказа.

**Вердикт: принято.** Пересказывать выбранную наружу ошибку не нужно —
её получил вызывающий.

### 8. Исправление мутации фильтра отмены снова устарело после смены маршрута

**Важность:** править до плана

**Что не так:** Критерий 8 теперь обещает убить снятие фильтра хотя бы при
наблюдателе. Это верно для прежнего `unattended`, но вторая редакция отказалась
от этого маршрута: пересказ идёт только в зону. `reportToZone` вызывает
`_toZone` независимо от наличия наблюдателя, а тот отбрасывает `Cancelled`.
Поэтому снятие **группового** фильтра не меняет ни один из двух журналов
в обоих прогонах.

Принятие находки 6 в `docs/records/2026-09-14[11]-eager-parallel-run-review.md`
и соответствующей части находки 7
в `docs/records/2026-09-14[12]-eager-parallel-run-review-2.md` было верным для
старого пересказа наблюдателю. После принятия нового маршрута переформулировка
чинит прежнюю мутацию только на прежнем коде.

**Доказательство:** Из каталога пакета:

```sh
rtk proxy dart run probe/ownership_and_routes.dart
```

Точные строки:

```text
CASE new-zone-route/observer=false/filter=false
observerErrors=0 zoneErrors=0
CASE new-zone-route/observer=false/filter=true
observerErrors=0 zoneErrors=0
CASE new-zone-route/observer=true/filter=false
observerErrors=0 zoneErrors=0
CASE new-zone-route/observer=true/filter=true
observerErrors=0 zoneErrors=0
```

Зонд при снятом фильтре напрямую вызывает существующий `reportToZone`, а при
включённом не вызывает. Никакая копия `_toZone` не использовалась.

**Что предлагаю:** Сохранить поведенческий сторож тишины, но убрать обещание
про эту мутацию. Если пересказ всегда проходит `_toZone`, отдельный фильтр
только ради диагностики отмен избыточен. Проверять нарушение реального
маршрута: пересказ через `notifyError` либо обход `_toZone` прямым вызовом
обработчика зоны. Мутацию фильтра выбора исхода с этим не смешивать.

**Вердикт: принято.** Маршрут сменился, и вслед за ним переписываются фильтр
своих отмен и его мутация.

### Где может находиться шов в `_execute`

Рабочая область — после существующего разбора `catch` и установки
`_bodyEnded = true`, до первого `await _awaitChildren()`, то есть возле строк
928–932. Нужно сохранить уже существующий каскад `selfCancelled`. Доставка
может стоять после него, если контракт порядка уведомлений этого требует. Здесь
доступны классифицированный `outcome` и `failedFirst`, а контекст уже запрещает
начинать новых детей из обратного вызова отмены.

Это пока область, а не предложение готовой вставки. Для плана требуется
зафиксировать следующие условия:

- Не вызывать внешние уборщики и не ожидать группу из этого обратного вызова:
  группа ждёт ту же ветку. Ранний обработчик должен записать событие
  и запросить остановку, после чего дать `_execute` продолжить сворачивание.
- Не переносить `notifyObserver` ради удобства нового потребителя. Сейчас
  наблюдатель вызывается до `_bodyEnded`; он способен синхронно запустить
  дополнительного ребёнка. Зонд дал
  `insideObserver bodyEnded=false extraChildStarted=true`. Изменение этого
  порядка изменит существующее поведение `ctx.run` без всякого `runAll`.
- Зарегистрировать потребителя до `startChild`. Синхронно бросающее тело
  проходит классификацию раньше возврата из старта. Зонд дал
  `log=[before-a, a:onError, after-a, b:start, after-b]`.
- Определить обработку событий во время цикла приёма. Немедленная отмена ещё
  не стартовавших элементов завершит их до тела, а последующий `startChild`
  отвергнет уже завершённый хэндл. Это расходится с обещанием запустить весь
  список. Нужны отдельные состояния «снимок принят», «элемент
  стартовал/отвергнут», «ранняя ошибка записана».
- Не давать сбою обработчика уведомления прервать путь к `finish`.
  Предусмотреть снятие регистрации и учёт терминальных исходов без тела, чтобы
  не хранить группу на хэндле после её завершения.
- Зафиксировать, какая зона получает невыбранную ошибку: зона создания
  родителя, ребёнка или вызова `runAll`. Сегодня `reportToZone` использует зону
  создания того задания, на котором его вызвали. Равенство этих зон
  спецификацией не гарантировано.

### Разбор всех 22 критериев приёмки

Реализации члена нет. Поэтому тесты 1–17 буквально «краснеют до правки» уже
от отсутствующего метода; это не доказывает качество их утверждений. Ниже
указаны **проектируемые** поведенческие контрпримеры и мутации после появления
компилируемого члена. Мутации `lib` не выполнялись. Выполненные зонды отделены
от предлагаемых проверок.

| № | Каким входом и кодом проверять; что поймает мутация |
|---|---|
| 1 | Два разных значения `1` и `2`, два `Completer`, второй отпустить первым. `expect(result, [1, 2])` убивает `values.add(value)` в порядке получения. Сравнение `[1, 1]` не годится. |
| 2 | На живом контексте проверить `[]` и неизменный счётчик детей у наследника. Отдельно пустой вызов из `unattended`, после конца тела при ещё живом потомке, после полного конца и после отмены. Предварительный `return []` ломает фиксированные ожидания `StateError`/того же `Cancelled`. Нынешние входы `run` воспроизведены; будущий пустой `runAll` не запускался. |
| 3 | В нынешней формулировке нет однозначного правильного теста: см. находку 3. После исправления мутация слушать только `child.value` должна оставить соседа неотменённым до барьера. Утверждение раннего `catch` заменить проверкой раннего запроса отмены и позднего завершения. |
| 4 | `b` даёт отмену, `a` отказывается от внешней отмены и позже бросает заранее созданный `error` со `stack`. Проверить объект в прямом `catch`, затем пробросить и проверить `Failed.error`. Выбор `firstError` без разделения видов выдаст отмену. Дополнить входом отменённого `a`, когда отказ тела пришёл после пометки: он требует решения находки 1. |
| 5 | Прямой `catch (error, stack)` вокруг `await ctx.runAll` обязан проверить `identical(error, expectedCancellation)` и след, затем `rethrow`. Одного размещения `catch` мало. Конверт и копия должны различаться именно здесь; итоговый классификатор иначе может скрыть мутацию. Проверить нормализованный объект ребёнка, `cause`, описание и один вызов слушателя. |
| 6 | Четыре сочетания списка и порядка завершения двух барьеров тел; оба тела гарантированно доходят до настоящего отказа. Выбор минимального индекса падает в двух сочетаниях. Дополнительно задержать уборку первого упавшего ребёнка: выбор из полных исходов иначе может пройти всю матрицу одинаковых уборок. |
| 7 | Фейковая операция с явным действием записи и отдельным подтверждением остановки. Вариант `onCancel` плюс `join`: после отпускания всех барьеров записи нет. Вариант `wait`: операция ещё совершает запись. Снятие отмены соседей ломает первый вариант; флаг после `await` тела не заменяет флаг внутри операции. |
| 8 | Начать с отмены, а не с настоящего отказа источника, чтобы журнал `onError` действительно мог быть пустым. Поведение проверяемо, названная мутация неразличима в обоих режимах: находка 8. Контрольные мутации — пересказ через наблюдателя и обход фильтра зоны. |
| 9 | Вход надо заменить двумя настоящими отказами: находка 7. Для второго объекта проверить одно сообщение ребёнка, ноль пересказов родителя и одно сообщение зоны. Удалённая доставка в зону и доставка через `notifyError` тогда различимы. С единственным отказом после отмены критерий конфликтует с 4. |
| 10 | На третьем элементе использовать конкретный наследник, бросающий заранее созданный объект из `adoptedBy` или создания контекста; обычный `ArgumentError` из ядра заранее получить по тождеству нельзя. Проверить синхронный отказ, дренаж первых детей и отсутствие лишнего сообщения. Вторым входом добавить сохранённый отказ неотменяемого первого ребёнка и явно проверить его маршрут. Мутация — потерять этот сохранённый отказ при переходе к отказу приёма; наличие конкретного `Completer` не обязательно. |
| 11 | Реальный `solo.job(canStart: (_) => false)`, следом ветка со счётчиком запуска. Отказавшая ветка не исполняет тело, третья стартует, полученная отмена сохраняется. Ожидание только броска либо только событий тела даст неверный исход/незавершимость. Обычный доменный приём подтверждён зондом. |
| 12 | Отмена родителя во время барьера: сохранить объект из `whenCancelled`, проверить итог по тождеству и `ParentCancelReason.cause` у детей. ## Ответы на четыре вопроса владельца

1. **Имя:** оставить `runAll`. Оно связано с `run` и описывает запуск всех
   элементов; ожидание сворачивания не противоречит слову `All`.
2. **`cleanUp`:** оставить в подписи. Он нужен для переданных группе ресурсов,
   которые не достанутся вызывающему при неуспехе. Принять параметр
   недостаточно: до плана нужны граница владения и ожидание его будущего.
3. **Кортежи:** отложить. Добавление формы не решает текущих вопросов исхода,
   отмены и уборки. Запрет навсегда ничем из этого ревью не обоснован.
4. **Выпуск:** готовый разбор конверта не задерживать ради этой спеки; `runAll`
   вести отдельной работой после `0.3.0`. Номер следующего выпуска этим ревью
   не определяется. Действий по выпуску не было.
