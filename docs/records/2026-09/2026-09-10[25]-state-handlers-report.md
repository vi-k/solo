# Обработчики состояния Job

## Реализация

В run и job добавлены необязательные синхронные преобразования:

```dart
S Function(S state, Object error, StackTrace stackTrace)? onError
S Function(S state, Cancelled cancelled)? onCancel
```

_SoloJob.finished выбирает обработчик по уже зафиксированному исходу
после тела, детей и уборки, до освобождения очереди и onFinish.
Исход не меняется и не наблюдается обработчиком за вызывающий код.
Ошибки обработчиков сообщаются отдельно, очередь освобождается в finally.
Для Done, отброшенной Job и тела, которое не запускалось, вызова нет.
Опубликованное ядро async_job не менялось.

Внешний переход, нарушающий W/keepWhile, окончательно отзывает право
коррекции. Проверка работает и после отмены, окончания тела, во время
ожидания детей и уборки. Свой emit исключён, canStart не повторяется.
Ошибка проверки тоже запрещает коррекцию и диагностируется.
После синхронного callback право проверяется ещё раз перед записью.

Ранний отзыв выполняется перед уведомлениями: вложенный переход обратно
в совместимое состояние не скрывает первоначальный запрет. Обычные
правила отмены повторно проверяются после уведомлений: наблюдатель может
изменить данные замыкания, не меняя состояние. Повторная диагностика
ошибки той же Job в рамках одного перехода подавляется.

## Граница родителей

Дополнительные проверки выполняются только у Job с собственными
обработчиками состояния. Отозванное право родителя запрещает коррекцию
потомков. Однако родитель без обработчиков после конца тела больше
не проверяет свои правила, как и прежде; продолжающий работу ребёнок
ограничен собственными правилами. Потенциальные будущие обработчики
внуков не продлевают действие правил обычного родителя.

Это уточнение убрало расширение, добавленное при проектировании агентом,
а не требование владельца. Объяснение передано владельцу в ходе работы.
Без него обычный родитель без новых параметров получал дополнительные
вызовы keepWhile после конца тела и мог отмениться из побочного эффекта
предиката или хука диагностики. Итоговая граница закреплена тестами
и описана в README и dartdoc.

## Документы

Быстрый старт использует sealed ProfileState: Initial, Loading, Loaded,
Failure. Тело устанавливает Loading/Loaded, параметры onError/onCancel
возвращают Failure/Initial. Общий onFinish и externalSetState удалены
из этого примера. Отдельный разбор Disconnected показывает работу правил
и границу отмены во время уборки. Объяснено отличие run.onCancel
при завершении от немедленного сигнала ctx.onCancel.

Связанные примеры проверки состояния, журнал и Flutter-экран обновлены.
Тест дубликата теперь вызывает второй load после старта первого.
Английский README и русский перевод содержат по 28 блоков кода.
Обновлены CHANGELOG, dartdoc и архитектура. README vs-bloc не менялся.

## Ревью реализации

Ревью выполнял независимый агент state_handlers_review по code-critic.
Каждая находка воспроизводилась до правки; итоговое ревью подтвердило
отсутствие существенных замечаний в пределах уточнённого контракта.

### 1. P2 — ранний результат keepWhile скрывает изменение замыкания

Кеш раннего keepWhile пропускал отмену после изменения замкнутых данных
в onChange. Родитель без handlers с keepWhile: (_) => allowed ждал
ребёнка с onCancel; onChange менял allowed на false без замены S.
Родитель оставался running, хотя на базе HEAD отменялся.

**Вердикт:** исправлено. После уведомлений keepWhile вызывается заново;
ревизия перехода используется только для дедупликации диагностики.

### 2. P2 — поздний обработчик внука теряет историю предка

В первоначальном расширенном контракте tracking предка включался лишь
при появлении потомка с обработчиком. Внешний disconnected во время
ожидания ребёнка мог случиться раньше; последующий обработчик внука
перезаписывал состояние вопреки обещанию постоянного отзыва у предков.

**Вердикт:** контракт уточнён. Правила родителя без обработчиков не
продлеваются после тела ради потенциальных потомков. Поздний потомок
пользуется собственными правилами; это поведение явно проверено тестом.

### 3. P2 — разные экземпляры ошибки дают двойную диагностику

Проверка identical для ранней и поздней ошибок не подавляла повторное
сообщение, когда keepWhile каждый раз создавал новый StateError.
Один external переход давал два одинаковых сообщения наблюдателю.

**Вердикт:** исправлено. Дедупликация относится к Job и переходу,
а не к идентичности экземпляра ошибки. Оба варианта проверены.

### 4. P2 — tracking обычного родителя меняет прежний жизненный цикл

Tracking каждого parent вызывал keepWhile после bodyEnded даже без
обработчиков у любой Job. Новый вызов мог бросить и через onError
отменить родителя с ребёнком; сам предикат тоже мог вызвать cancel.
На HEAD тот же родитель продолжал ждать ребёнка без проверки и ошибки.

**Вердикт:** исправлено ограничением проверок собственными обработчиками.
Регрессионный тест проверяет отсутствие вызова предиката после тела
обычного родителя. Исход Done и ожидание ребёнка сохраняются.
