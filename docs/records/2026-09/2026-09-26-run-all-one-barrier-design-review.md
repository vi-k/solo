## А. Находки

### А1. Довод о цене не держится для `discard`-компенсации

**Важность:** Medium.

**Где:** дизайн, строки 142–152 («Строгий обратный порядок теряется только…»,
«ресурс, который ветка отдаёт, не может рассчитывать…»), и предлагаемое правило
для `children.md` (строки 212–215).

**Что не так.** Довод говорит об отдаваемом ресурсе, а не о самом колбэке
`discard`. Частый случай — компенсация: значение ветки — данные (id строки),
а `discard` — откат побочного эффекта через сессию, которую ветка держит через
`dispose` ниже по стеку. На успехе `discard` не выполняется вовсе,
и вызывающему нужен только id. Поэтому фраза «`discard`, которому нужен живой
`dispose`-ресурс, сломан на успешном пути и без этой правки» здесь неверна.
На неуспехе компенсация теперь идёт после закрытия сессии. У любой задачи то же
бывает только в гонке (отмена во время уборки), а у ветки группы это обычный
путь отказа соседа.

**Доказательство:** зонд `P1`
в `packages/async_job/test/zz_review_probe_test.dart`. Ветка `a` берёт сессию
через `ctx.wait(…, dispose: close)`, затем
`ctx.wait(() => s.insert(7), discard: (id) => s.delete(id))`; сосед падает
через 10 мс.

Старое ядро:
```
P1 a=Cancelled(sibling) rows left={} log=[insert 7, b throws, delete 7, session closed, parent caught Bad state: b] zone errors=[]
```
Эксперимент:
```
P1 a=Cancelled(sibling) rows left={7} log=[insert 7, session closed, b throws, parent caught Bad state: b] zone errors=[Bad state: session closed, cannot delete 7]
```

**Что предложить.** Переписать первый пункт «Почему цена приемлема»: честно
назвать, что теряется. Колбэк `discard` не может опираться на то, что ветка
держит через `dispose`. Всё, что нужно компенсации, должно принадлежать
родителю (жить выше группы) или открываться в самом `discard`. То же правило —
в `children.md`, в формулировке про колбэк, а не только про отдаваемый ресурс.
Сторож 3 порядок уже держит; можно дать ему форму компенсации, чтобы правило
читалось из теста.

**Вердикт: принято, и эта находка сменила вариант.** Зонд P1 перепроверил своим
прогоном на трёх ядрах: на старом `rows left={}`, на эксперименте (а)
`rows left={7}` и ошибка в зоне, на прототипе (б) вывод совпадает со старым
ядром строка в строку. Довод дизайна опирался на успешный путь, где `discard`
не выполняется вовсе, и для компенсации не держится. Владелец 2026-09-27 выбрал
(б): до решения группы ветка выполняет только то, что строгий обратный порядок
выполнил бы раньше первого `discard`, поэтому компенсация по-прежнему идёт
раньше того, что ветка взяла до неё. В редакции 2 — сторож 3.

### А2. H1 остаётся для регистраций, которые приходят, когда ветка уже стоит на барьере

**Важность:** Medium.

**Где:**
- дизайн, строки 121–123 («Ловушка H1 уходит для всего, что ветка держит для
  себя»);
- предлагаемый dartdoc, строки 193–203 («has run by then»);
- `job_context.dart:811–825`: `_keepLate` кладёт позднее значение
  в `addCleanup(… always: true)`;
- `job_base.dart:1327–1345`: стек перечитывается только после барьера.

**Что не так.** Значение от вызова, от которого тело ушло (типичный случай —
`ctx.wait(acquire, dispose: release).timeout(…)` с запасным значением),
попадает в стек, пока ветка стоит на барьере, и освобождается только после
вердикта. Так же ведут себя `ctx.onDispose` из таймера и работа `unattended`.
Если слот ждёт третья ветка, группа не решит никогда. Под `.wait` то же тело
освобождает слот сразу: задача уже кончилась, и `_keepLate` выполняет `dispose`
на месте. Страница `cleanup.md` обещает для позднего значения «runs even after
the job has ended — late and alone», а у ветки на барьере оно ждёт группу.

**Доказательство:** зонд `P2` в `zz_review_probe_test.dart`. Пул на один слот.
`b` держит слот 20 мс. `a` ждёт слот 5 мс через `.timeout` и возвращает `-1`.
`c` ждёт слот через `join`.

Эксперимент:
```
P2 runAll: parent=null values=null log=[b holds, a waits, c waits, a gives up, b releases, a holds]
P2 runAll after cancel: parent=null cancel returned=false
P2 .wait: parent=Done(null) values=[1, -1, 2] log=[b holds, a waits, c waits, a gives up, b releases, a holds, a releases, c holds, c releases]
```
Старое ядро (там это сам H1):
```
P2 runAll: parent=null values=null log=[b holds, a waits, c waits, a gives up]
P2 runAll after cancel: parent=null cancel returned=false
```

**Что предложить.** Одно из двух.
- (а) Держаться принципа варианта (а) до конца: безусловная регистрация,
  пришедшая на барьер, выполняется сразу, не дожидаясь вердикта. При этом ветка
  не должна кончиться, пока такая регистрация не отработала, а условные
  по-прежнему ждут вердикта. Для критерия 22 это меняет только момент
  выполнения безусловной записи.
- (б) Записать ограничение: в дизайне вместо «для всего, что ветка держит для
  себя» — «для всего, что зарегистрировано до барьера»; в dartdoc
  и в `children.md` сказать, что позднее значение ветки на барьере
  освобождается после решения группы.

Отдельным сторожем зафиксировать выбранное поведение.

**Вердикт: принято, вариант (а) ревьюера в узкой форме.** P2 воспроизвёл:
на старом ядре и на эксперименте группа не решает. В редакции 2 поздний ответ
ветке, которая стоит на барьере, освобождается сразу, а на стек встаёт
безусловная запись, которая ждёт этого освобождения, так что ветка не кончится
раньше него. Только на барьере: пока ветка разматывает стек, поздний ответ
встаёт на стек, как у любой задачи. Этот порядок держат три теста —
`late_value_test` и два в `cancellation_rakes_test`, — и освобождение на месте
для всех задач их краснит. `onDispose` из таймера и работа `unattended`,
зарегистрированные на барьере, по-прежнему ждут, пока группа отпустит ветку:
это держит тест «what a branch registers while it waits follows the verdict»,
и страница это назовёт. На прототипе P2 даёт
`parent=Done(null) values=[1, -1, 2]`, как `.wait`. Сторож 5.

### А3. У первого барьера была вторая роль: фаза «не убирается» у удержанной ветки

**Важность:** Low.

**Где:** дизайн, строки 27–31 («На деле он даёт одно»);
`packages/solo/lib/src/job_context.dart:81–104` (`_checkedState`:
`throwIfDisposing`, затем правило и `cancelOwnJob`), `emit` там же на 128–142.

**Что не так.** На первом барьере `isDisposing == false`. Поэтому чтение
`ctx.state`, вызов `check()` или `emit` на контексте ветки (из таймера,
из `unattended`) были законны, и чтение с нарушенным `keepWhile` отменяло
правилами ветку, уже вернувшую значение, а с ней и всю группу. Теперь
на единственном барьере это `StateError`, как требует критерий 22. Сдвиг
в сторону согласованности, но изменение поведения `solo` в дизайне не названо.
Сама переоценка правил в `solo` ветку после тела не трогает (`solo.dart:1021`:
`canCancel = !job.isCancelled && !job._bodyEnded`), так что другой дороги
у правил нет.

**Доказательство:** `packages/solo/test/zz_review_probe_test.dart`.

Эксперимент:
```
SOLO read=Bad state: Job(a) is disposing, cannot state a=Done(1) values=[1, 2] thrown=null discarded=0
```
Старое ядро:
```
SOLO read=Cancelled(rules: keepWhile) a=Cancelled(rules: keepWhile) values=null thrown=Cancelled(rules: keepWhile) discarded=1
```

**Что предложить.** Назвать это в разделе «Зачем был первый барьер» или «Что
это даёт». По желанию — сторож в `solo`: чтение на удержанной ветке бросает
`StateError` и не отменяет её.

**Вердикт: принято.** В редакции 2 ветка входит в фазу уборки перед верхом
стека всегда, есть ей что убирать или нет: иначе фаза на первом барьере
зависела бы от стека, а это критерий 22 запретил для второго. Поэтому смена для
`solo` та же, что на эксперименте: зонд SOLO на прототипе дал
`read=Bad state: Job(a) is disposing, cannot state a=Done(1) values=[1, 2]`.
Смена названа в разделе «Цена», сторож в `solo` — сторож 8.

### А4. Цена не только в порядке на пути отказа

**Важность:** Low.

**Где:** дизайн, раздел «Цена: порядок на пути отказа» (132–158).

**Что не так.** Первый барьер давал ещё две наблюдаемые вещи, которых раздел
не называет.
1. На успешном пути ни одна безусловная уборка не начиналась, пока не кончились
   тела всех соседей. Ресурс одной ветки через `dispose`, отданный соседу через
   замыкание или `Completer`, раньше жил до конца тел, теперь закрывается под
   соседом. Так же, как под `.wait`, но это изменение.
2. На пути отказа уборка видит другое: `onDispose` читает
   `isCancelled == false`, а колбэки `ctx.onCancel` тела идут после `dispose`.
   Документированный приём `ctx.onCancel(() => ctx.unattended(device.stop))`
   (dartdoc `onCancel`) попадает на уже закрытое устройство.

**Доказательство:** `zz_review_probe_test.dart`, зонды P3, P4, P6. Сначала
старое ядро, потом эксперимент:
```
P3 values=[1, 2] caught=null log=[insert 2, session closed]
P3 values=null caught=Bad state: session closed log=[session closed]
P4 onDispose saw isCancelled=true, a ends Cancelled(sibling)
P4 onDispose saw isCancelled=false, a ends Cancelled(sibling)
P6 log=[b throws, a: onCancel aborts the conn, a: conn closed (dispose)]
P6 log=[a: conn closed (dispose), b throws, a: onCancel aborts the conn]
```

**Что предложить.** Перечислить все три в «Цене». Решить, нужна ли строка
в `children.md` («ресурс, который делят ветки, принадлежит родителю»).
`children.md:247` про `isCancelled` уже говорит «not the last word», так что
второе, вероятно, достаточно назвать в дизайне.

**Вердикт: принято.** На (б) все три остаются, но только для того, что ветка
выполняет до решения группы, — для верха стека над первым `discard`: P3, P4
и P6 на прототипе дают то же, что на эксперименте. В редакции 2 они названы
в «Цене», а правила — в документах: общий ресурс принадлежит родителю, то, что
зависит от исхода, идёт в `discard`, а `onCancel` тела после его конца может
прийти уже после уборки.

### А9. Уже существующее: ветка, законченная движком `Done` в первом проходе, после фиксации висит на барьере

**Важность:** Low. Есть на обоих ядрах, правка его не вносит.

**Где:** `job_context.dart:1614` (`_parkBeforeOutcome`), `job_base.dart:1327`.

## Б. Находки

### Б1. Первый проход ветки идёт при временном исходе, и дизайн эту цену не называет

**Важность:** Medium.

**Где:**
- дизайн, раздел «Цена: порядок на пути отказа» и абзац «Правила уборки ветки
  становятся правилами любой задачи с одним исключением»;
- `lib/src/job_context.dart:659-664`, dartdoc `throwIfDisposing`: «The body is
  gone and the outcome is decided … a disposer … asks `job.isCancelled` about
  the outcome»;
- `lib/src/job_base.dart:817-821`, dartdoc `isDisposing`: «The body is gone and
  the outcome is decided».

**Что не так.** Раньше первый барьер держал ветку до приговора. Если сосед
падал, пока тела ещё шли, ветку отменяли до уборки: уборщик видел
`isCancelled == true`, а колбэки `onCancel` шли раньше `dispose`. Теперь первый
проход идёт, пока соседи ещё в теле. Уборщик читает временный `false`, хотя
ветка кончится `Cancelled(sibling)`. `onCancel` срабатывает уже после того, как
`dispose` закрыл ресурс. У обычной задачи такое бывает только в окне поздней
отмены. У ветки это обычный путь отказа, а dartdoc ядра прямо советует уборщику
спрашивать `isCancelled`.

**Доказательство.**
`packages/async_job/test/review/one_barrier_probes_test.dart`, тесты P1 и P1b.

```text
старое ядро: P1 log=[a dispose: isCancelled=true] a=Cancelled(sibling)
правка:      P1 log=[a dispose: isCancelled=false] a=Cancelled(sibling)
старое ядро: P1b log=[a: onCancel, a: connection closed (dispose)] a=Cancelled(sibling)
правка:      P1b log=[a: connection closed (dispose), a: onCancel] a=Cancelled(sibling)
```

**Что предложить.**
- Назвать это в «Цене» рядом с порядком `discard`/`dispose`: у ветки первый
  проход идёт под временным исходом, всё, что зависит от исхода, должно идти
  в `discard`, а `onCancel` после тела может прийти уже после `dispose`.
- Внести в список документов dartdoc `isDisposing` и `throwIfDisposing`.
- В `children.md` к пункту «The outcome of a branch is not final until the
  group decides» добавить: уборщик ветки, который спрашивает `isCancelled`,
  получает временный ответ.

**Вердикт: принято, совпадает с находкой А4.** Под (б) касается только верха
стека над первым `discard`. Dartdoc `isDisposing` и `throwIfDisposing` —
в списке документов редакции 2, правило для `children.md` то же, что предлагает
ревьюер.

### Б2. Довод о цене не покрывает компенсацию, которой нужен удерживаемый ресурс

**Важность:** Medium.

**Где:** дизайн, «Почему цена приемлема», первый пункт; предложенная фраза для
`children.md` (строки 213–215 дизайна).

**Что не так.** Довод говорит об отдаваемом ресурсе: «на успехе вызывающий
получает его, когда тот уже закрыт». Но живой `dispose`-ресурс бывает нужен
не самому отдаваемому значению, а действию `discard`, то есть компенсации.
Пример: ветка держит замок реестра (`dispose: release`), бронирует место
(`discard: ledger.cancel(seat)`, отмена брони требует замка) и возвращает
бронь. На успехе бронь у вызывающего ничего от замка не требует, и этот путь
не сломан. На отказе старое ядро отменяло бронь под замком. Правка сначала
отпускает замок, а бронь отменяет позже, когда замок уже может держать кто-то
другой. Это хуже не только по форме: компенсация идёт вне критической секции.

**Доказательство.** `one_barrier_probes_test.dart`, тест P2. Посторонний
(не ветка) `x` просит тот же замок на 5-й мс, сосед `b` падает на 10-й.

```text
старое ядро: P2 log=[a holds, x waits, a: seat cancelled, lock held by a, a releases, x holds, x releases]
правка:      P2 log=[a holds, a releases, x holds, a: seat cancelled, lock held by x, x releases]
```

**Что предложить.**
- В «Цене» признать этот случай, а не выводить его из успешного пути.
- В `children.md` и dartdoc `runAll` вместо «отдаваемый ресурс не должен
  нуждаться в удерживаемом» написать: на пути отказа `discard` ветки идёт после
  её `dispose`, поэтому компенсация, которой нужен замок, берёт его сама.

**Вердикт: принято, совпадает с находкой А1.** P2 на прототипе (б) совпадает
со старым ядром: `a: seat cancelled, lock held by a`.

### Б3. Не названо изменение для `solo`: чтение состояния удерживаемой ветки больше не отменяет её правилом

### Б4. Граница, где теряется строгий LIFO, проведена не там

**Важность:** Low.

**Где:** дизайн, строки 142–144: «сосед упал после того, как тело ветки вернуло
значение. Упал раньше — ветку отменяют в теле».

**Что не так.** Порядок теряется, только если сосед упал после начала первого
прохода ветки, то есть когда она уже дождалась своих потомков. Если сосед упал,
пока тело уже вернуло значение, а ветка ещё ждёт ребёнка, её отменяют
до уборки, и LIFO сохраняется на обоих ядрах.

**Доказательство.** `one_barrier_probes_test.dart`, тест P4, одинаково на обоих
