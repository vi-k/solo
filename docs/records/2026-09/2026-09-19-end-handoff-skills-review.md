## Команды, которые обещают не то, что делают

**1. `git diff -- <файл>` не видит заиндексированную чужую правку.** Нашли двое
независимо. Сосед по шагу 9 делает `git add` перед `git commit -- …`, и в это
окно файл состояния для `git diff` чист. Шаг 1 объявляет отправную точку
чистой, блок переписывается поверх чужого текста, а `git commit -- <путь>`
берёт версию из дерева: чужая строка исчезает без следа в истории. Проба: после
соседского `git add` `git diff -- h.md` пуст, `git diff HEAD -- h.md`
показывает `+neighbour`, а после моего коммита `git status` чист и чужой блоб
остаётся висячим объектом.

**Вердикт (2026-09-19):** принята. В обоих скиллах команда заменена
на `/usr/bin/git diff HEAD -- <файл состояния>`, и сказано, почему именно
`HEAD`.

**2. `git apply` из подкаталога молча пропускает файлы вне него.** Проба:
`cwd=pkg`, патч на `docs/h.md` — `git apply --check` и `git apply -R` выходят
нулём и не делают ничего; из корня тот же патч откатывается. Патч на файл
внутри текущего каталога при этом применяется, поэтому ошибка и не бросается
в глаза. Цена: «проверка ложится обратно» проходит вхолостую, а на ветке stash
за ней идёт `git stash drop` — и запись уходит в reflog.

**Вердикт (2026-09-19):** принята. В оба блока шага 3 первой строкой добавлен
`cd "$(git rev-parse --show-toplevel)"`, рядом сказано почему; у stash условие
дополнено: `--check` прошёл из корня **и** файл в дереве изменился.

**3. `git merge-base --is-ancestor <ветка> HEAD` с `-C <копия>` всегда говорит
«слита».** Внутри копии `HEAD` — вершина проверяемой ветки. Две соседние строки
блока идут с `-C <копия>`, третья — без, и дописать `-C` к ней естественно.
Цена тяжёлая: этой же проверкой шаг 2 разрешает `git branch -D` в обход отказа
`-d`. Проба: из основной копии «не слита», с `-C <копия>` — «слита».

**Вердикт (2026-09-19):** принята. В обоих местах сказано, что ancestry
считается от `HEAD` основной копии, и почему строка с `-C` соврёт.

**4. `git worktree list` не печатает причину замка.** Скилл решает по причине
(«называет pid, и по нему видно, чья»), а команда даёт только слово `locked`.
Проба подтвердила: причину показывает `-v` или `--porcelain`.

**Вердикт (2026-09-19):** принята. В блоке шага 1 теперь `worktree list -v`.

падают с «Entry 'new.dart' not uptodate. Cannot merge», жалуется

**Вердикт (2026-09-19):** принята. `git reset -q -- <свои новые файлы>` вписан

## Что ревьюеры проверили и признали верным

- Патч в `.git/wip` вместо stash: каталог не виден `git status`, переживает
  `git clean -xdff`, общий для копий дерева; stash действительно один стек
  на репозиторий, а индекс у каждой копии свой.
- `git worktree remove` молча уносит игнорируемое, а на неигнорируемое
  неотслеживаемое отказывает.
- Разбор `-d` против `-D` с цитатой сообщения git.
- `git commit -- <пути>` оставляет чужой заиндексированный файл вне коммита;
  без `git add` новый файл даёт обещанную ошибку pathspec.
- Пределы формы `AskUserQuestion`: от двух до четырёх вариантов, до четырёх
  вопросов за вызов, `multiSelect` — штатное поле.
- `awk length` на macOS считает байты, `pgrep -fl` печатает полную строку
  запуска, `gh run list --commit` существует.
- Проверка переноса работает и стоит копейки: на настоящей уборке (`f7f6752` →
  `fe275eb`) — ноль проблем, и после правки скрипта тоже.

Утверждение «`/clear` не убивает фоновые Bash и субагентов (Claude Code
