# Решение владельца

После примера кода владелец отклонил решение: `externalSetState`
предназначен не для такой записи правок, сама предложенная аккумуляция
не нужна и слишком сложна. Рецепт снят с дальнейшей работы.

Ошибка предложения — использование внешней установки состояния для
обхода очереди обычными методами контроллера. Учёт редакций и повторов
усложнил решение, но не исправил выбор механизма. Техническая возможность
вызвать `externalSetState` не делает это подходящим применением API.

Ниже сохранено отклонённое предложение. Оно не является руководством
к реализации. Отказ относится к этому решению; новый способ аккумуляции
не согласован. Вопросы debounce и буфера с досылкой в бэклоге не закрыты.

# Задача и предлагаемое решение

Владелец выбрал аккумуляцию после предложения дописать рецепт для `solo`
и поручил предложить решение и подготовить спеку. Эта запись описывает
рецепт на существующем API. Новая политика очереди не требуется.
Все решения ниже — предложение агента, а не уже согласованный контракт.

Сценарий: пользователь меняет уведомления, тему и язык в настройках
одного профиля. Приложение сразу показывает желаемые значения, а серверу
последовательно отправляет полные снимки настроек. Если несколько правок
накопились до старта отправки, достаточно одного снимка со всеми правками.

Предлагаю разделить две обязанности: состояние хранит желаемые значения,
а очередь хранит намерение их отправить. Публичный метод синхронно
записывает правку через `externalSetState`, затем ставит отправку
с постоянным ключом и `Policy.replace`. Тело отправки читает состояние
на старте. Удаление ожидающей задачи не удаляет уже записанную правку.

# Рассмотренные варианты

1. **Желаемое состояние и `replace` — выбранный вариант.** Один источник
   локальных значений, существующие API и последовательные отправки.
   Подходит, когда сервер принимает полный снимок настроек одной сущности.
2. **Накопитель частичных правок вне состояния.** Полезен для сервера,
   принимающего только patch. Потребует собственного слияния, отделения
   отправленного набора от новых правок и возврата изменений после ошибки.
   Для данного примера это лишний механизм и второй источник данных.
3. **Новая политика слияния задач.** Потребует определить функцию слияния,
   владение данными и судьбу хэндлов. Очередь сама не знает, можно ли
   заменить событие новым значением. Оснований расширять API здесь нет.

# Область применимости

Один экземпляр контроллера владеет настройками одного профиля.
Снимок содержит только редактируемые настройки: `notifications`, `theme`,
`language`. Служебные поля профиля в запрос не входят.

Значения имеют семантику присваивания: последняя правка одного поля
побеждает, правки разных полей сохраняются вместе. Промежуточные значения
не требуется доставлять. Счётчики событий, логи, платежи и команды
с самостоятельным эффектом требуют другого решения.

Сервер принимает идемпотентную установку полного снимка настроек.
Успешное завершение future означает применение снимка. После завершения
future от запроса этот запрос уже не сможет записать данные позднее.
Других писателей той же сущности в примере нет. Серверное преобразование
значений, конфликт версий и несколько клиентов требуют отдельного
протокола; локальный номер редакции их не решает.

# Состояние и методы примера

`Settings` — неизменяемое значение с тремя полями настроек.
`SettingsState` — неизменяемое состояние контроллера:

- `desired: Settings` — последние локальные значения;
- `revision: int` — номер последней локальной правки;
- `savedRevision: int` — последняя подтверждённая редакция;
- `hasUnsavedChanges` — вычисляется как `revision != savedRevision`.

Начальные настройки уже прочитаны с сервера; оба номера равны нулю.
Каждая принятая правка увеличивает `revision`, даже повторное присваивание
того же значения. Сравнение значений и устранение таких повторов
не входят в рецепт. Всегда `0 <= savedRevision <= revision`.

Контроллер `SettingsController extends Solo<SettingsState>` предоставляет:

- `setNotifications(bool value)`;
- `setTheme(String value)`;
- `setLanguage(String value)`;
- `retry()`.

Все четыре метода возвращают `SoloJob<void>`. Это методы примера,
а не дополнение публичного API пакета. Строки темы и языка в примере
считаются проверенными вызывающим кодом.

# Запись правки

Каждый setter выполняет синхронно, без промежуточного `await`:

1. Проверяет `isClosed`. После начала закрытия бросает
   `StateError('Settings controller is closed')`, не меняя состояние.
2. Читает текущее состояние и создаёт новое: заменяет только своё поле
   в `desired`, увеличивает `revision`, сохраняет `savedRevision`.
3. Публикует новое состояние через `externalSetState`.
4. Создаёт отправку и добавляет её с `Policy.replace`.

Отправка имеет приватный стабильный ключ одного экземпляра контроллера,
например `_saveKey = Object()`, и обычное `cancellable: true`.
Рабочий тип — `SettingsState`, дополнительных правил старта и удержания
нет. Изменение настроек поэтому не отменяет уже работающую отправку.

Тела задач не захватывают отдельную правку или заранее собранный снимок.
Они вызывают один и тот же алгоритм отправки актуального состояния.

`externalSetState` может синхронно вызвать пользовательский хук.
Вложенная правка должна сохраняться: после публикации setter больше
не записывает старое состояние. Если хук начал закрытие, последующий
`run` вернёт `Cancelled(closed)`, а уже принятая локальная правка останется.
Это отличается от вызова setter на уже закрытом контроллере.

# Отправка и подтверждение

Приватная фабрика `_saveJob()` создаёт задачу следующего содержания:

1. На старте читает `snapshot = ctx.state`.
2. Если `snapshot.hasUnsavedChanges` ложно, успешно завершается без сети.
3. Вызывает и ожидает `ctx.join(() => api.save(snapshot.desired))`.
4. После успешного возврата читает новое текущее состояние и через
   `ctx.emit` обновляет только `savedRevision` на `snapshot.revision`.
   Текущие `desired` и `revision` сохраняются.

`join` удерживает слот до завершения внешней операции, в том числе
при отмене задачи. `wait` здесь не подходит: прекращение ожидания могло
бы освободить слот, пока старый запрос ещё способен записать снимок.
Контракт API выше нужен и при сетевой ошибке: клиентский таймаут сам
по себе не гарантирует прекращения серверной записи.

Номер подтверждается только после успешного возврата из `join`.
Если за время запроса появились новые правки, `savedRevision` отстаёт
от `revision`: интерфейс продолжает показывать несохранённые изменения.
Следующая отправка возьмёт все новые значения. Ответ сервера никогда
не заменяет `desired` старым снимком.

Задачи выполняются последовательно, поэтому подтверждения не обгоняют
друг друга. Номер редакции — локальная отметка подтверждения, в запрос
он не передаётся и версией сущности на сервере не является.

# Примеры последовательности

Три setter вызываются до первой прокачки очереди:

```text
setNotifications(true) -> revision 1
setTheme('dark')        -> revision 2
setLanguage('ru')       -> revision 3
save                   -> {notifications: true, theme: dark, language: ru}
ack                    -> savedRevision 3, hasUnsavedChanges false
```

Первые две ожидающие задачи заменены, но все три правки остались
в состоянии. Сеть получает один запрос.

Если первый запрос уже отправляет редакцию 1, правки редакций 2 и 3
обновляют локальное состояние и заменяют ожидающую отправку. Подтверждение
редакции 1 оставляет `revision = 3`, `savedRevision = 1`. Затем второй
запрос отправляет полный снимок редакции 3. Одновременно запрос только
один; промежуточная редакция 2 отдельно не отправляется.

Если каждая отправка успевает завершиться до следующей правки, будут
три запроса. `replace` объединяет накопленное в очереди и не создаёт
временного окна ожидания. Debounce остаётся отдельной темой бэклога.

# Ошибка, повтор, отмена и закрытие

Ошибка `api.save` выходит из тела обычным `Failed`. Состояние не
откатывается, `savedRevision` не продвигается. Хэндл и наблюдатель
используются по обычным правилам `solo`; пример должен явно показывать
наблюдение исхода через `.done` и разбор всех трёх исходов.

`retry()` проверяет закрытие так же, как setter, затем ставит обычную
отправку с тем же ключом и `replace`, не меняя `revision`. При старте она
читает актуальное состояние. Если всё уже подтверждено, сети нет.
Если после неудачной отправки в очереди есть более новая, она продолжит
работу и отправит все желаемые значения. Автоматического цикла повторов,
backoff и сохранения на диск в примере нет.

Отмена хэндла отменяет попытку отправки, но не откатывает локальную
правку. `Cancelled` заменённого хэндла не означает потерю этой правки:
её значение могло войти в следующий снимок. Хэндлы заменённых задач
не перенаправляются на новую задачу.

`Done` хэндла означает успешное завершение конкретной попытки, включая
случай уже сохранённого состояния. Это не обещание сохранить правки,
пришедшие позднее снимка. Актуальность подтверждения показывает состояние.

При отмене работающего запроса `join` дожидается его завершения и бросает
принятую отмену. Сервер мог сохранить снимок, но `savedRevision` в этом
случае не продвигается. Отметка остаётся консервативной; повторная
идемпотентная отправка разрешает эту неопределённость.

`close()` сохраняет обычную семантику: отменяет очередь, отменяет текущую
задачу и ждёт её фактического завершения. Финальная отправка не добавляется.
Несохранённые локальные значения остаются в памяти состояния, но их
доставка и сохранность после уничтожения контроллера не гарантируются.
Буфер с досылкой при закрытии остаётся отдельной темой бэклога.

# Критерии приёмки будущей реализации

Проверять через `FakeAsync` и управляемые `Completer`, без реального сна.
Fake API хранит журнал снимков, применяет их при явном завершении
и считает число одновременно работающих запросов.

1. Три правки до запуска дают один запрос со всеми тремя значениями;
   два заменённых хэндла имеют `Cancelled`, последний — `Done`.
2. Повторная правка одного поля сохраняет последнее значение, не теряя
   правок остальных полей.
3. Правки во время запроса дают следующий полный снимок; максимум
   одновременно работающих запросов равен одному.
4. Старое подтверждение сохраняет новые значения и не сбрасывает
   `hasUnsavedChanges`. Последнее подтверждение сбрасывает его.
5. Ошибка не откатывает значения. Явный `retry` отправляет актуальный
   снимок; более новая ожидающая отправка также выполняется после ошибки.
6. `retry` уже сохранённого состояния заканчивается без запроса.
7. Отмена ожидающей отправки не откатывает правки; `retry` их отправляет.
8. Отмена работающей отправки не освобождает слот до завершения запроса;
   подтверждение не записывается после принятой отмены.
9. `close` снимает ожидающую отправку и ждёт текущую операцию без досылки.
   Setter и `retry` после начала закрытия не меняют состояние и бросают.
10. Вложенная правка из `onChange` сохраняется в последнем снимке;
    закрытие из хука оставляет принятую правку без обещания доставки.
11. Разнесённые правки, между которыми сеть завершилась, дают отдельные
    запросы: пример не обещает debounce.

Перед коммитом реализации: анализатор и тесты затронутых пакетов
и отдельного пакета примера, сверка переводов, ширины и диффа.
Нынешняя спека проверена чтением `SoloBase.add`, `externalSetState`,
