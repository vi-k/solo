# Изменение

`CancelReason` — открытый абстрактный класс. Встроенные причины:
`ManualCancelReason`, `ParentCancelReason`, `HandlerCancelReason`,
`RulesCancelReason`, `ClosedCancelReason`. Последние две наследуют открытую
основу `SoloCancelReason`. `name` остаётся меткой для журнала, равенство по
имени удалено. Для распознавания используются типы; свои причины могут
хранить ошибку, стек и другие данные.

`job.cancel(reason: reason)` передаёт объект причины без копирования.
Явная причина из `throw Cancelled.by(...)` сохраняется; обычный
`throw Cancelled(...)` использует `HandlerCancelReason`. Поле `cause` у
родительской причины и причины ребёнка, вышедшей через тело, сохраняет
исходный `Cancelled` со всеми данными. Всё входит в неподготовленный
к публикации выпуск 0.2.0; нового выпуска и push не было.

# Независимое ревью

## P2: ошибка в метке причины останавливает завершение родителя

Если ребёнок отменяется с пользовательской причиной, чей `name` бросает,
а родитель ожидает `child.value`, `_handlerCancel` вызывает этот getter
через `$thrown`. Интерполяция находится вне обработки ошибок тела.
`_execute` обрывается до `_bodyEnded`, уборка не запускается, `done`,
`cancel` и закрытие контроллера зависают.

**Вердикт:** подтверждено собственным падающим тестом. Построение описания
защищено, ошибка идёт через `notifyError`, резервное описание —
`child cancellation`. `HandlerCancelReason.cause` сохраняет исходную
отмену. Тест и повторный зонд ревьюера подтверждают завершение и уборку.

## P2: публичный тип родительской причины не доказывает каскад

Ребёнок выполняет
`throw Cancelled.by(reason: const ParentCancelReason(), started: true)`,
родитель ожидает `child.value` внутри `ctx.unattended`. Теперь
`_handlerCancel` сохраняет переданный тип, а `_isOwnCancellation` считает
его доказательством каскада и подавляет уведомление. Родитель успешно
заканчивается `Done`: собственной отмены и каскада не было. Это нарушает
контракт доставки самостоятельной отмены ребёнка наблюдателю.

**Вердикт:** подтверждено собственным падающим тестом. Фактический каскад
регистрирует связь конкретной причины с приватным токеном ребёнка;
публичного типа недостаточно. Значение `Expando` — токен, а не хэндл, чтобы
хранение причины не удерживало ребёнка. Повторный зонд ревьюера подтвердил
доставку уведомления, удержанный каскад, каскад самоотмены и повторное
использование причины одного ребёнка другим.
