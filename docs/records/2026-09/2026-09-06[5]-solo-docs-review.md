# Ревью документации `solo` глазами пользователя

Ревьюер — агент с чистым контекстом. Роль: Dart-разработчик, который про
пакет ничего не знает, у которого есть своя задача (последовательные
операции над состоянием, которые надо уметь отменять), минута на решение
«моё / не моё» и двадцать минут на первый рабочий контроллер.

## Вердикт ревьюера

Пакет брать стоит, и по лицу это видно. Проза README точная, ритмичная и
без маркетинга; я прогнал **все** двадцать Dart-фрагментов README, все
девятнадцать фрагментов `vs-bloc.md` и пример целиком — компилируется всё,
и каждое утверждение о поведении, которое я проверял прогоном, оказалось
верным. Публикационная гигиена чистая: `dry-run` 0 warnings, `dart doc` 0
warnings, `dart analyze` и 238 тестов зелёные, `repository` у pana проходит
на 10/10 (в отличие от `jobs`).

Мешают выйти к людям три вещи разного веса.

Первая и единственная блокирующая — техническая. В архив едет
`example/pubspec.yaml` с `dependency_overrides` на `../../jobs`, пути,
которого в архиве нет. README и `example/README.md` в один голос велят
`cd example && dart pub get`, вкладка Example на pub.dev показывает ровно
эти инструкции, и они не работают ни у кого, кто скачает пакет. Проверено
прогоном на копии архива. По «Следующим шагам» handoff эта чистка стоит
*после* публикации; её место — до неё, вместе с удалением
`pubspec_overrides.yaml`. Это находка 1.

Вторая — про мой сценарий. README ни разу не отменяет задачу. «Кооперативная
отмена» стоит в первой строке титула и в `description` пакета, весь раздел
Concepts про то, что делает отмена внутри тела, — а вызова `job.cancel()`
в документе нет ни одного, `cancelAll()` упомянут один раз и только в
оговорке. Человек, пришедший за отменой, узнаёт из README, как её пережить,
и не узнаёт, как её объявить.

Третья — обещание, которое пакет продаёт заголовком. «Монополия владения
состоянием» сформулирована в README трижды как абсолют («Only jobs write…
never overlapping», «no other job of this controller touches the state»,
«jobs of one controller never overlap»), и все три раза она сильнее, чем
правда: ребёнок, запущенный `ctx.run`, пишет состояние одновременно с
родителем — прогон ниже даёт чередование
`[child 0, parent 0, child 1, parent 1, …]`. `vs-bloc.md` формулирует это
же место аккуратно и с обоими исключениями; README — нет.

Ничто из перечисленного не требует правок кода: все четырнадцать находок
закрываются документами и одной строкой в `example/pubspec.yaml`.

### 1. [critical] Опубликованный `example/` не соберётся: оверрайд `jobs` ведёт в пустоту

`example/pubspec.yaml:14-18`:

```yaml
# A root package applies no override of its dependency, so the path to the
# unpublished `jobs` has to be repeated here.
dependency_overrides:
  jobs:
    path: ../../jobs
```

В дереве `../../jobs` — это `packages/jobs`, и всё работает. В архиве
`example/` лежит внутри пакета, `../../jobs` указывает наружу, и там ничего
нет. Проверено на копии в раскладке архива
(`<scratchpad>/archive-sim/solo-0.2.0`, `pubspec_overrides.yaml` удалён,
как перед публикацией):

```
$ cd solo-0.2.0/example && dart pub get
Resolving dependencies...
Because solo_example depends on jobs from path which doesn't exist
(could not find package jobs at "../../jobs"), version solving failed.
```

Чего это стоит. `README.md:927-932` и `example/README.md:8-13` велят
выполнить именно `dart pub get` в этой папке, и `example/README.md` — это
то, что pub.dev покажет на вкладке Example. Единственный запускаемый
артефакт пакета не запускается ни у кого, кроме владельца, и первая
команда, которую пакет предлагает человеку, отвечает ошибкой про
несуществующий путь. Починить это без нового номера версии нельзя.

Оверрайд к моменту публикации `solo` уже не нужен: по порядку связки
`jobs` 0.1.0 выходит первым, и `jobs: ^0.1.0` резолвится с pub.dev.
`docs/handoff.md:62-63` эту чистку знает, но относит её к «после
публикации» — вместе с шаблоном `SOLO_PUBSPEC` в `tool/doc_snippets.py`,
которому там самое место.

Направление правки: убрать `dependency_overrides` из
`example/pubspec.yaml` тем же шагом, что и
`packages/solo/pubspec_overrides.yaml`, то есть в пункте 1.2 «Следующих
шагов», до `dart pub get` и dry-run; после
удаления прогнать `dart pub get`, `dart analyze` и `dart test` из папки
примера. В handoff перенести эту строку из «после публикации» в шаг 2
связки.

### 2. [important] README ни разу не отменяет задачу

`README.md:3-4` и `pubspec.yaml:2-4` обещают кооперативную отмену первой же
фразой. В самом README вызова отмены нет.

`grep` по всему документу даёт десять вхождений `cancel`, и ни одно из них
не отменяет задачу снаружи: `:102` — `subscription.cancel()` у подписки на
стрим, `:184`, `:528-529`, `:533`, `:561`, `:577` — чужие токены и таймеры,
`:853` — `current?.cancel()` внутри `dispose()` контроллера. Единственное
упоминание самого метода — `:279`, одна фраза посреди плотного абзаца
«Outcomes»: «`job.cancel()` cancels and waits for the job to actually
finish». Ни одного фрагмента, где кто-то вызывает `cancel()` и смотрит на
исход.

Рядом та же дыра шире: `cancelAll()` встречается в README **один раз**
(`:359`) и сразу в оговорке — «`close()` awaited from inside the current
job's body never completes… The same holds for `cancelAll()`». Читатель
узнаёт о методе из предупреждения, как его нельзя звать, раньше, чем из
объяснения, что он делает.

Чего это стоит. Человек с моей задачей — «последовательные операции над
состоянием, которые надо уметь отменять» — прочитал README целиком и не
увидел, как отменить операцию. Быстрый старт (`:46-120`) показывает
состояние, задачу, чтение `state`, подписку, `await job.value` и `close()`
— и ничего не отменяет. Всё, что README рассказывает про отмену, написано
с точки зрения тела задачи: как её пережить, чем обернуть вызов, что
бросится. Точка зрения вызывающего — «я нажал «Отмена», что мне делать и
что я получу» — не показана нигде. Для сравнения, «Quick start» ядра
(`packages/jobs/README.md:44-66`) отменяет задачу в шести строках и на
этом держится.

Направление правки: три-четыре строки к быстрому старту или сразу под ним —
`final job = profile.load(); … await job.cancel(); print(job.outcome); //
Cancelled(manual)` — и полстроки про `cancelAll()` там, где описана
очередь (`:282-289`), до оговорки на `:359`.

**Вердикт (2026-09-06):** Принято. Сразу за «Быстрым стартом» — фрагмент
из трёх строк: `final job = profile.load();`, `await job.cancel();`,
`print(job.outcome);`. Прогон в стенде даёт `Cancelled(manual)`. Рядом
строка про `cancelAll()` и `close()`, до всякой оговорки о них.

### 3. [important] «Никакая другая задача не трогает состояние» — дети трогают

README формулирует главное обещание пакета трижды, и каждый раз сильнее,
чем оно есть:

- `:115-116` — «Only jobs write, one at a time, in queue order, never
  overlapping.»
- `:141-142` — «At most one root job runs at a time, and while it runs no
  other job of this controller touches the state.»
- `:755` — «There is no `concurrent` transformer: jobs of one controller
  never overlap».

При этом `:258-259` учит читателя ровно тому, что эти фразы запрещают:
«`ctx.run(child)` starts a job right now, bypassing the queue, as a child
of the current one». Ребёнок — задача того же контроллера, он не в
очереди, и он пишет состояние одновременно с родителем. Прогон
(`bin/p7_overlap.dart`: родитель запускает ребёнка и не ждёт его, оба
пишут в цикле):

```
writes in order: [S(child 0), S(parent 0), S(child 1), S(parent 1),
                  S(child 2), S(parent 2)]
```

Чередование чистое: две задачи одного контроллера писали состояние по
очереди, между `await` и `emit` друг у друга. Ни «never overlapping», ни
«no other job… touches the state» этого не допускают.

Чего это стоит. Обещание монопольного владения — то, ради чего пакет
берут, и то, чем «Coming from bloc» объясняет отсутствие `concurrent`.
Читатель, поверивший `:755` буквально, напишет родителя, который пускает
детей и пишет состояние сам, и получит ту самую гонку из пункта 3
`vs-bloc.md` — внутри одного контроллера, с полным правом. Хуже того, в
`vs-bloc.md` то же место сформулировано верно и с обоими исключениями:
«while a root job runs no other **root** job of this controller writes the
state. The two ways in are its own children, started by `ctx.run` inside
the same body, and `externalSetState` from outside — both deliberate, both
visible». То есть точная формулировка у проекта есть, она просто не в том
документе, который читают.

Заодно: `:115-116` и `:126-127` дважды говорят «only jobs write», а
`:264-265` вводит `externalSetState`, который пишет состояние вне всякой
задачи. Для `@protected`-метода это верно по духу («никто снаружи»), но
читатель встречает абсолют за полтораста строк до исключения.

Направление правки: перенести формулировку из `vs-bloc.md` в `:141-142`
(«no other **root** job… writes the state»), поправить `:755` тем же
словом и `:115-116` — оговоркой про детей и `externalSetState`. В абзац
«Children» (`:258-262`) — одну фразу: ребёнок пишет состояние параллельно
с родителем, и это единственный способ получить два писателя внутри
контроллера намеренно.

**Вердикт (2026-09-06):** Принято, все три места. «Пишут только задачи: по
одной корневой за раз» — и тут же оба исключения, ребёнок и
`externalSetState`; «никакая другая **корневая** задача… состояние не
пишет»; «корневые задачи одного контроллера никогда не накладываются». В
«Детях» дописана фраза о том, что записи родителя и ребёнка чередуются и
что это единственный намеренный способ получить двух писателей.

### 4. [important] `whenCancelled` описан сильнее, чем он есть: `solo` разошёлся с исправленным `jobs`

`README.md:277-278`:

> `job.whenCancelled` completes the moment the job is marked cancelled,
> before the body finishes;

Это та же формулировка, которую ревью ядра назвало неверной (находка 12
`2026-09-06[4]-jobs-docs-review.md`, принята) и в README `jobs` уже
исправило. Сегодня `packages/jobs/README.md:94-97` говорит иначе:

> `job.whenCancelled` completes on every `Cancelled` outcome — for a

### 14. [minor] Термины ядра приходят в автодополнение без введения

`package:solo/solo.dart` реэкспортирует `package:jobs/jobs.dart` целиком
(`lib/solo.dart:5`). В автодополнении пользователя оказываются
`DeferredJob`, `JobBase`, `JobContext`, `JobContextBase`, `JobObserver` и
`JobStatus`. Из них README не называет ни одного, кроме `JobContext` —
и того ровно один раз, `:254`:

> `each` is an extension on `JobContext`, not a member of it

до этого и после этого весь документ говорит `SoloContext`. Читатель
встречает второе имя контекста в придаточном предложении, без объяснения,
что это интерфейс ядра, который `SoloContext` реализует.

Чего это стоит. Немного и по-разному: `JobStatus` и `DeferredJob`
безобидны, а вот `JobBase`/`JobContextBase` — половина API ядра, и
человек, который на них наткнётся, не поймёт, зачем они ему в пакете про
контроллеры. Обратная симметрия у ядра уже сделана (находка 8 ревью
`jobs`): его «Why» говорит, что `solo` реэкспортирует его целиком и брать
оба не нужно. У `solo` та же фраза есть (`:29-32`), но она не говорит
следствия: в автодополнении будут типы ядра, они для тех, кто строит свой
движок, и трогать их не надо.

Направление правки: полстроки к `:29-32` — что типы ядра видны в
автодополнении и нужны только для собственного движка, со ссылкой на
README `jobs`; и в `:254` расшифровать `JobContext` одним словом («the
core interface `SoloContext` implements»).

**Вердикт (2026-09-06):** Принято. В абзаце про реэкспорт перечислено,
что придёт в автодополнение, и сказано, что из этого нужно только
`JobObserver`, а остальное — для собственного движка и объясняется в README
ядра. У `each` расшифрован `JobContext`.

## Что дописать

README отвечает на вопросы первого дня лучше, чем большинство пакетов.
Чего в нём нет и что человек спросит на второй:

- **Повтор с отступом (retry/backoff).** Ближайший сосед рецепта Timeout,
  и на `Policy.droppable` плюс `job.done` он пишется в пять строк.
  Отложен ещё ревью 2026-09-03 (находка A9, «Открытые вопросы» handoff) —
  напоминаю, что вопрос жив.
- **Два контроллера, которые слушают друг друга.** У bloc это
  `BlocListener` и подписка в конструкторе, и в таблице «Coming from bloc»
  (`:743`) `BlocListener` переведён как «`await job.done` at the call
  site» — это ответ для экрана, а не для контроллера. С появлением
  `ctx.each` ответ у пакета есть: `ctx.each(other.stream, …)` внутри
  долгоживущей задачи, с подпиской, живущей ровно столько, сколько задача.
  Три строки закрывают вопрос, который сегодня приходится решать самому.
- **Как тестировать отмену.** Раздел Testing показывает исход и журнал, но
  не показывает `cancel()` — то есть ровно то, чего в README нет и в
  остальных местах (находка 2). Плюс правило, которое ядро в своём разделе
  Testing уже написало (`packages/jobs/README.md:274-276`): `Future(...)`
  и `Future.delayed(...)` — таймеры, а не микротаски, и под `fakeAsync`
  им нужен `flushTimers()`. Пользователь `solo` пишет ровно такие фейки
  API, и без этой строки его первый `fakeAsync`-тест зависнет.
- **Кто может звать `run`, `job` и `add`.** Они публичные, а `queue`,
  `current`, `externalSetState` и `lastJobWhere` — `@protected`. README
  описывает первые три как способ контроллера собрать себе задачу
  (`:134-138`) и не говорит, что снаружи их тоже видно. Одна фраза о том,
  что предполагается — методы контроллера, а не вызовы снаружи, — снимет
  вопрос и у читателя, и у ревьюера чужого кода.
- **`stateAs` и `check`** названы по одному разу в перечислениях
  (`:164`, `:354`) и не показаны. `check()` при этом — прямой перевод
  `emit.isDone` в таблице миграции (`:738`), то есть первое, что будет
  искать пришедший с bloc.
- **`flutter_solo` не найти поиском.** К `solo` это относится косвенно, но
  бьёт по тому же читателю: `packages/flutter_solo/pubspec.yaml` — без
  `topics` и без `issue_tracker`, в отличие от `solo` и `jobs`. Человек,
  который ищет `state-management` и которому нужен Flutter, найдёт
  пакет без виджетного слоя, а строчка `flutter pub add flutter_solo`
  стоит в README `solo` на `:40-44`.

**Вердикт (2026-09-06):** Написано три пункта из шести. Слежение за другим
контроллером — новый рецепт с `ctx.each` над чужим стримом (прогон:
состояние экрана подхватывает сессию). Тестирование отмены и правило
«`Future(...)` — таймер, а не микротаска» — в разделе Testing. Кто зовёт
`run`, `job` и `add` — в «Очереди и политиках». Не написаны: повтор с
отступом (владелец отложил его 2026-09-03, решение в силе), `stateAs` и
`check` фрагментом, и топики `flutter_solo` — последнее закрывается ревью
`2026-09-06[6]-flutter-solo-docs-review.md`.

## Что хорошо

Не трогать:

- **Точность утверждений.** Я проверил прогоном всё, что README обещает
  про очередь, политики, правила, исходы, детей, поздние значения, два
  пути ошибки, уход необслуженного `Failed` в зону, микротаску стрима и
  поведение после `close`. Сошлось всё, кроме находок 3, 4 и 7. Особенно
  хороши тонкие места: «`wait` calls it late… and nothing waits for that»
  против «`join` awaits the disposal before it throws» (`:203-208`) —
  прогон подтверждает порядок дословно; «a job that emits itself out of
  `W` must not touch `ctx` again» (`:322-325`); «reads after a cancelled
  job still throw its `Cancelled`» (`:354-356`).
- **Раздел Errors** (`:365-435`). Он делает то, чего не делает почти
  никакая документация: называет цену собственного механизма. «Being an
  `Exception` cuts both ways: a wide `catch` in a body catches the job's
  own `Cancelled` too» с фрагментом `on Cancelled { rethrow; }` — это
  критическая находка ревью ядра, закрытая здесь заранее и лучше, чем
  там.
- **`doc/vs-bloc.md`.** Восемь пунктов, в каждом сначала рабочее решение
  на bloc с его ценой. Я прогнал обе стороны всех восьми: все трассы,
  которые документ цитирует, воспроизводятся дословно, ни одного соломенного
  чучела, цитаты из трекера точны, и там, где у bloc есть ответ, он показан
  кодом. Это лучший сравнительный документ, который я видел в
  Dart-пакете, и `tool/doc_snippets.py` рядом с ним — правильная гарантия:
  фрагменты не могут разойтись с прогонами молча.
- **Раздел Testing и раздел Flutter.** Оба отвечают на настоящие вопросы
  (кто создаёт контроллер, кто его закрывает, что делать с исходом в
  виджете, `mounted` после `await`) и оба компилируются как есть. Журнал
  через наблюдателя со сверкой всего порядка одним `expect` — приём,
  которому стоило бы поучиться половине пакетов.
- **Пример.** Отдельный пакет, свой README, семь тестов, `bin/main.dart` с
  живым журналом, `dart analyze` чист. README честно говорит «this
  controller extended», и это правда: пример — надмножество, с `Broken`,
  `reopen`, `pause`, `resume` и фокусом. Единственная беда — находка 1,
  и она не про содержимое.
- **Публикационная гигиена.** `dry-run` без предупреждений, архив 72 КБ,
  ничего лишнего: `README.ru.md`, `pubspec_overrides.yaml`, `doc/api/` и
  `pubspec.lock` отсечены правильно. `repository` проверяется pana на
  10/10, переводы в синхроне (`check_translations.py` зелёный),
  `issue_tracker` и `topics` на месте.
