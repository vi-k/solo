# `jobs`: план выноса ядра

> **Для агентов:** выполнять задачу за задачей по
> `superpowers:subagent-driven-development` (рекомендуется) или
> `superpowers:executing-plans`. Шаги отмечены чекбоксами.

**Цель:** вынести из `solo` исполнительное ядро задачи — `Job` как
отменяемую `Future` без состояния, очереди и правил — в отдельный пакет
`packages/jobs`, оставив `solo` его потребителем и не сломав ни одного из
223 его тестов.

**Архитектура:** ядро — две наследуемые основы (`JobBase<T>` и
`JobContextBase`) плюс публичные интерфейсы `Job<T>` и `JobContext`. Всё,
что знает про состояние, очередь и правила, живёт в наследниках solo:
`_SoloJob` и `_SoloContext` за интерфейсами `SoloJob<T>` и
`SoloContext<S, W>`. Движок solo трогает задачу только через приватные
обёртки своего наследника: `@protected` действует внутри наследника, а
`SoloBase` обращается к задаче со стороны.

**Стек:** Dart 3.13.0 (stable) локально, пол `^3.6.0`; `package:meta`,
тесты на `package:test` и `package:fake_async`; Flutter 3.47.0 для
`flutter_solo`.

**Спецификация:** `docs/records/2026-09-05[4]-jobs-design.md`, четвёртая
редакция. План аргументирует от неё; исполнитель читает обе записи. Ссылки
вида «спека, раздел X» — на неё.

## Когда это делать

После публикации `solo` 0.1.0 на pub.dev. Причина в спеке (раздел «Порядок
работ», шаг 2): следующий релиз `solo` невозможен, пока `jobs` не
опубликован, поэтому 0.1.0 выходит раньше, а вынос приезжает в 0.2.0.

Публикация `jobs` и `solo` 0.2.0 в план не входит: это отдельная связка по
правилам `AGENTS.md`, только по отдельному запросу владельца.

## Глобальные ограничения

- Пол SDK во всех пакетах — `environment: sdk: ^3.6.0`. Ничего из языка
  новее 3.6: без `_` как wildcard дважды в одном списке параметров.
- Зависимости в согласии с Flutter, соответствующим полу SDK (Flutter
  3.27): рантайм `meta: ^1.15.0`; dev `fake_async: ^1.3.1`, `test: ^1.26.3`,
  `lints: ^5.1.1`. `lints` 6.x требует SDK 3.8 и не берётся.
- Ядро без Flutter и без зависимостей, кроме `meta`.
- Публичные типы, которые пользователь получает от движка (`Job`,
  `JobContext`, `SoloJob`, `SoloContext`, `SoloQueue`), — `abstract
  interface class`; `Outcome` — `sealed`, `Done`/`Failed`/`Cancelled` —
  `final`; наследуемые основы (`JobBase`, `JobContextBase`, `SoloBase`,
  `Solo`, `SoloObserver`, `JobObserver`) — без `base` и `final`.
- `StateError` на нарушение жизненного цикла, `ArgumentError` на неверный
  аргумент, через `throw`, не `assert`.
- Dartdoc, `README.md`, `CHANGELOG.md`, тексты ошибок, коммиты — по-
  английски. Документы в `docs/` — по-русски. Правка английского оригинала
  и правка русского перевода идут одним коммитом; сверка —
  `python3 tool/check_translations.py` из корня.
- `dart analyze` без предупреждений и info, `dart format
  --set-exit-if-changed .` и `dart test` зелёный — в каждом затронутом
  пакете перед каждым коммитом.
  Строки до 80 символов, одинарные кавычки, завершающие запятые.
- Тесты: `FakeAsync`, сдвиги времени явные, проверка упорядоченного журнала
  целиком. Один сценарий — один `test`, имя описывает ситуацию.
- Код в блоках этого плана пишется под линты проекта, включая
  `require_trailing_commas` и `cascade_invocations`: `dart format` запятые
  не расставит, а `dart analyze` перед коммитом обязан быть чист. Строки
  журнала в тестах — по формату `JournalObserver`
  (`test/support/journal.dart`): `finished` и `dropped` без двоеточия.
- Коммиты по Conventional Commits, в `main`, без PR. Каждая задача
  заканчивается коммитом. `docs/handoff.md` обновляется в том же коммите:
  раздел «В работе прямо сейчас» называет номер выполненной задачи и
  следующую.
- Числа тестов в шагах — ориентир, считанный от 223 на входе фазы A; если
  сторожевой тест уже есть в дереве, число на единицу меньше. Красным
  дерево не оставляется никогда.
- 223 теста `solo` остаются зелёными на каждом коммите фазы A. Ни один из
  них не переписывается «под новую архитектуру»: они и есть проверка того,
  что шов не сдвинул поведение. Правятся только имена типов и те три
  места, где спека меняет поведение осознанно (задачи 2, 5, 8).

## Решения, принятые в плане

Спека оставляет эти места реализации; владелец может отменить любое.

1. **Порядок задач фазы A — по возрастанию связности с движком:** сначала
   типы, которые движок только упоминает (`CancelReason`, `JobStatus`),
   потом контекст, потом задача, потом три поведенческие правки
   (усыновление, `ifCancelled`, дети). Каждая задача — коммит с зелёными
   тестами; ни одна не оставляет дерево в промежуточном состоянии.
2. **`SoloCancelReason` в фазе A живёт в части `outcome.dart`**, рядом с
   `CancelReason`, и уезжает в собственную библиотеку
   `lib/src/solo_cancel_reason.dart` в задаче 10, когда ядро покидает
   пакет. Не потому, что цикл библиотек запрещён — он законен и в дереве
   уже есть (`observer.dart` и `solo_base.dart` импортируют друг друга), —
   а потому, что до задачи 9 `CancelReason` лежит в части библиотеки
   `solo_base.dart`, и отдельная библиотека ради двух констант ничего не
   даёт.
3. **Приватные обёртки `_SoloJob` для движка** называются по действию, с
   подчёркиванием: `_launch()`, `_drop(outcome)`, `_cancelWith(cancelled,
   rejectable: …)`, `_jobStatus`, `_whenDone`, `_isCancellable`. Имена
   отличаются от имён защищённых членов основы: в фазе A наследник и
   основа лежат в одной библиотеке, и `_status` столкнулся бы с полем.
   `SoloBase` и `_SoloQueue` пользуются только обёртками. В задаче 4
   заводятся ещё две — `_pending` и `_childJobs`, — а в задаче 5, когда
   отмена уезжает на задачу, они теряют потребителей и снимаются.
4. **Тестовые дубли ядра** живут в `test/support/foreign_job.dart`:
   минимальный `ForeignJob extends JobBase<T>` и `ForeignContext extends
   JobContextBase`. Они нужны в фазе A, где инстанцируемой задачи ядра ещё
   нет, для проверок «чужой контекст не усыновляет задачу solo» и «solo не
   принимает голую задачу ядра».
5. **`ifCancelled` у задачи** объявляется как `FutureOr<void> Function(T
   value)?` — так же, как у `ctx.wait` и `ctx.join`
   (`2026-09-05[2]-resource-ownership-design.md`), и движок его дожидается.
   В `SoloBase.job` и `SoloBase.run` параметр встаёт после `cancellable`.
6. **Имя пакета — `jobs`**, версия `0.1.0`, `repository` —
   `github.com/vi-k/solo/tree/main/packages/jobs`. Если владелец получит
   имя `job`, переезд делается до первой публикации и стоит переименования
   папки, `name:` и импортов.
7. **`solo` 0.2.0 и `flutter_solo` 0.2.0** — версии после выноса; пол
   `solo: ^0.2.0` у `flutter_solo`. Ломающих правок нет, но публичное API
   solo растёт и меняется в шести местах, а на нулевой мажорной ломающая
   граница — минорная версия.
8. **Отладочных канала два:** `JobBase.debug` у ядра и `SoloBase.debug` у
   solo. Каждая строка идёт в канал того пакета, чей код её печатает;
   `hooks_test.dart` ставит оба.

/// Why a job was cancelled.
///
/// Not an enum: an engine built on the core declares reasons of its own,
/// and an enum cannot be extended from another package. Reasons are equal
/// by [name], so a reason declared elsewhere with the same name is the
/// same reason here — a label for the journal and the observer, never a
/// value the engine branches on.
@immutable
final class CancelReason {
  /// [Job.cancel] or a duplicate dropped by a policy.
  static const manual = CancelReason('manual');

  /// Cascade from a cancelled parent job.
  static const parent = CancelReason('parent');

  /// The job body threw `Cancelled` itself.
  static const handler = CancelReason('handler');

  /// The label of this reason.
  final String name;

  /// Creates a reason called [name].
  const CancelReason(this.name);

  @override
  bool operator ==(Object other) => other is CancelReason && name == other.name;

  @override
  int get hashCode => name.hashCode;

  @override
  String toString() => name;
}

/// The reasons `solo` adds to the core ones.
final class SoloCancelReason {

  static const rules = CancelReason('rules');

  /// [SoloBase.close], or [SoloBase.add] after close.
  static const closed = CancelReason('closed');

}

  /// Creates a job and starts it on the next microtask.
  ///
  /// Not inside the constructor: the caller gets the handle first, and may
  /// listen to [done] or cancel before the body ever runs.
  factory Job(
    Future<T> Function(JobContext ctx) body, {
    Object? key,
    String Function()? describe,
    bool cancellable,
    FutureOr<void> Function(T value)? ifCancelled,
    JobObserver? observer,
  }) = _AutoJob<T>;

  /// Creates a job that waits for [DeferredJob.start].
  static DeferredJob<T> deferred<T>(
    Future<T> Function(JobContext ctx) body, {
    Object? key,
    String Function()? describe,
    bool cancellable = true,
    FutureOr<void> Function(T value)? ifCancelled,
    JobObserver? observer,

      _DeferredJob<T>(
        body,
        key: key,
        describe: describe,
        cancellable: cancellable,
        ifCancelled: ifCancelled,
        observer: observer,

  _Job(
    this._body, {
    super.key,
    super.describe,
    super.cancellable,
    super.ifCancelled,
    super.observer,
  });

  JobContextBase createContext() => _CoreContext(this);

  @override
  Future<T> execute(covariant _CoreContext ctx) => _body(ctx);

  _AutoJob(super.body, {super.key, super.describe, super.cancellable,
      super.ifCancelled, super.observer}) {

    // in the same stripe, and then this microtask does nothing.
    scheduleMicrotask(() {
      if (status == JobStatus.created) {
        start();

    });
  }

  @override
  void start() => super.start();
}
