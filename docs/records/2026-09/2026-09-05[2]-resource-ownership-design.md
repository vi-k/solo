# Кто закроет ресурс, если задачу отменили

## Откуда вопрос

Владелец сравнил две записи одного и того же:

```dart
final database = await ctx.join(Database.open);
```

```dart
final database = await Database.open();
ctx.check();
```

и заметил: в первой при отмене ресурс теряется, даже если дождались
завершения вызова; во второй его можно закрыть.

## Что подтвердилось в коде

`join` до правки (`lib/src/job_context.dart`):

```dart
final result = await action();
_checkedState();   // бросает Cancelled
return result;
```

Бросок происходит **внутри** вызова, когда значение уже есть, но лежит в
кадре `join`. Телу оно не достаётся никогда, закрыть его некому.

У `wait` то же самое и тише: значение приходит после того, как ожидание
кончилось, и в `_race` молча выбрасывается — так и было записано в
контракте.

`uncancellable` проверяет отмену только на входе и потому значение
отдаёт всегда. Это его сознательное свойство, разобранное в
`2026-09-04[4]-join-design.md`: «шаг, чей результат обязан доехать».

Отсюда же — неправда в дартдоке `join`: «It is `await action();
ctx.check();` under one name». Для вызова со значением это не так, и не
так ровно в том месте, о котором вопрос: двухстрочная форма связывает
переменную до броска, `join` — нет.

Граница поэтому такая. `join` цел для вызова, который ничего не отдаёт во
владение: `hw.open()`, `device.write(chunk)`, `player.seek(...)` —
владение остаётся у железа. Ломается он там, где вызов отдаёт владение:
`Database.open`, `socket.connect`, `File.open`.

## Решение

У обоих членов появился необязательный параметр:

```dart
Future<T> wait<T>(
  FutureOr<T> Function() action, {
  FutureOr<void> Function(T value)? ifCancelled,
});

Future<T> join<T>(
  FutureOr<T> Function() action, {
  FutureOr<void> Function(T value)? ifCancelled,
});
```

| | когда зовётся | кто ждёт |
|---|---|---|
| `join` | пост-проверка бросает, значение есть | тело, а с ним `close()` |
| `wait` | значение пришло после ожидания | никто: задача кончилась |

Общее для обоих:

- действие бросило — значения нет, `ifCancelled` не зовётся, ошибка идёт
  как раньше;
- отмены не было — не зовётся;
- бросок из самого `ifCancelled` уходит в `onError` и там кончается, а
  `Cancelled` бросается как ни в чём не бывало: задача отменена, и прятать
  это за ошибкой уборки нельзя. Так же ведут себя колбэки `onCancel`.

`uncancellable` не тронут: он и так всегда отдаёт значение.

## Почему не другие варианты

**Захватывать через `uncancellable`.** Значение он отдаёт, но на время
открытия отказывает в отмене вообще, а долгое открытие с токеном как раз
хочется уметь прерывать. И обвязка в теле выходит громоздкой.

**Ослабить правило «каждый вызов идёт через контекст»** и писать захват
двумя строками. Правило держит весь стиль тела; дыра в нём стоит дороже
одного необязательного параметра.

## Чего `ifCancelled` не закрывает

Окно у него ровное и короткое: между возвратом вызова и получением
значения телом. Дальше работает обычный `try/finally` — но уборка в
`finally` идёт **голым** `await`, потому что задача к этому моменту уже
может быть отменена, а тогда откажет любой член контекста, включая
`uncancellable` (он бросает на входе). Тело при этом всё ещё внутри
`_body`, поэтому `close()` контроллера уборку дожидается. Это записано в
README, в новом абзаце «Taking ownership».

Открытый вопрос про подписку на стрим на время задачи
(`2026-09-05[1]-generators-migration-review.md`, находка F2) этим не
закрывается: `stream.listen` синхронный, окна отмены внутри вызова нет, и
вопрос там о другом — держать подписку всё время тела.
