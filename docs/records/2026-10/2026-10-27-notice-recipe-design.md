# Рецепт «сигнал как состояние с приёмкой»

## Откуда

Сессия tez переводит приложение tez-taxi с bloc на solo и прислала заявку
на канал разовых эффектов: `ctx.signal(e)`, `onEffect` у наблюдателя,
виджет-слушатель. Владелец 2026-10-27 решил, что нового API не нужно: сигнал —
обычное состояние с приёмкой, а закрытие экрана и есть приёмка. В tez так уже
устроено уведомление о целях города: оно ждёт приёмки, принимается и уходит.
Правила записаны в ADR-0014 tez:

1. сигнал — поле состояния, а не ветка sealed;
2. приёмка адресная, по id или идентичности, иначе опоздавшая приёмка сотрёт
   следующий сигнал;
3. приёмка не ждёт за длинной задачей: сигналы живут в своём маленьком
   контроллере, иначе перестроенный экран покажет сигнал второй раз, пока
   приёмка стоит в очереди.

Владелец на предложение сессии tez ответил «давай рецепт» — только
документация, без API.

## Куда

Новый раздел `## A notice the screen accepts` в `packages/solo/doc/state.md`,
после «External state» (по ревью), и его перевод в `docs/ru/solo/state.md`. Это
страница о состоянии и правилах `W`, а рецепт стоит на них: ветка состояния

## Пример

Камера страницы (`CameraState`: `Ready`, `Disconnected`, `Off`). Требование:
когда снимок сохранён, экран показывает уведомление «Photo 7 saved», пока
пользователь его не закроет. Экран, построенный заново (поворот, возврат
на экран), показывает его снова, пока оно не закрыто; закрытое не возвращается.
Камера тем временем работает: запись, начатая после снимка, идёт. Отменённый
снимок уведомления не даёт.

### Первая попытка — уведомление как ветка состояния

Словарь bloc ведёт сюда: `emit(PhotoSaved(7))`, а `BlocListener` показывает
тост.

```dart
// The first attempt: the notice is a state of the camera.
final class Saved extends CameraState {
  final int photo;

  const Saved(this.photo);
}

Job<void> shoot() => enqueue<Ready, void>((ctx) async {
      final photo = await ctx.join(device.shoot);
      ctx.emit(Saved(photo));
    });

Job<void> accept() =>
    enqueue<Saved, void>((ctx) async => ctx.emit(const Ready()));
```

Что происходит: пока уведомление на экране, камера не в `Ready`, и всё, что
стартует в `Ready`, отклоняется правилами: `record()`, поставленная после
снимка, кончается `Cancelled(rules: is not Ready)` с `started: false`, как
и следующий `shoot()`. Камера стоит, пока пользователь не закроет уведомление.
Вариант «`emit(Saved)`, тут же `emit(Ready)`» камеру не держит, но экран,
который в этот момент не слушал, уведомления не увидит вовсе. (Зонд: да,
`Cancelled(rules: is not Ready1)` у `record` и у второго `shoot`.)

### Вторая попытка — поле состояния, приёмка в очереди камеры

```dart
// The second attempt: the notice is a field, accepted by a job of the queue.
Job<void> shoot() => enqueue<Ready, void>((ctx) async {
      final photo = await ctx.join(device.shoot);
      ctx.emit(ctx.state.copyWith(notice: photo));
    });

Job<void> accept() => enqueue<Ready, void>(
      (ctx) async => ctx.emit(ctx.state.copyWith(notice: null)),
    );
```

(Как очистить поле через `copyWith` — решу в коде: `clearNotice: true` или
отдельный конструктор; на странице `Ready.copyWith` уже есть.)

Что происходит: камера работает, запись стартует. Пользователь закрывает
уведомление через секунду, `accept()` встаёт в очередь — за записью, которая
идёт десять секунд. Всё это время поле держит уведомление, и экран, построенный
заново, показывает его второй раз. `first: true` не помогает: он ставит впереди
ждущих, а не впереди работающей. (Зонд: на 2 с поле ещё 7, на 11,2 с — пусто.)

### Ответ — свой контроллер для уведомлений

```dart
final class Notice {
  final int photo;

  Notice(this.photo);
}

final class NoticeBoard {
  final Notice? notice;

  const NoticeBoard([this.notice]);
}

final class Notices extends Solo<NoticeBoard> {
  Notices() : super(const NoticeBoard());

  Job<void> post(Notice notice) =>
      enqueue<NoticeBoard, void>((ctx) async => ctx.emit(NoticeBoard(notice)));

  Job<void> accept(Notice notice) => enqueue<NoticeBoard, void>((ctx) async {
        // Only the notice the screen showed: a newer one stays.
        if (identical(ctx.state.notice, notice)) ctx.emit(const NoticeBoard());
      });
}
```

И у камеры:

```dart
Job<void> shoot() => enqueue<Ready, void>((ctx) async {
      final photo = await ctx.join(device.shoot);
      notices.post(Notice(photo));
    });
```

Проза:

- очередь `Notices` держит только короткие задачи, поэтому приёмка не ждёт
  записи камеры; состояние камеры уведомления не знает, правила её задач оно
  не трогает;
- уведомление — поле состояния (`Solo<S extends Object>`, `null` состоянием
  не бывает, и поле `notice` — это и есть «пусто»);
- приёмка адресная: экран передаёт то уведомление, которое показал. Если пока
  закрывался баннер, пришло новое, `accept` старого его не стирает. Безадресная
  приёмка стёрла бы новое, которого никто не видел;
- `post` стоит после работы: отменённый снимок не публикует ничего;
- экран слушает `notices` (`addListener` / `SoloListenable`), показывает
  `currentState.notice`, по закрытию зовёт `accept(notice)`;
- `post` и `accept` — задачи, а не `externalSetState`: это работа, о которой
  просят контроллер, а не факт внешнего мира (правило раздела
  «externalSetState» той же страницы).

Таблица случаев:

| Что делаешь | Что происходит |
| --- | --- |
| Снимок, затем запись | Запись идёт, уведомление на экране |
| Закрыть уведомление во время записи | Пропадает сразу; перестроенный экран его не показывает |
| Новый снимок, пока закрывается старое уведомление | Новое остаётся |
| Снимок отменён | Уведомления нет |
| `close()` контроллера уведомлений | `post` после него кончается `Cancelled(closed)` |

(Зонд подтвердил все строки.)

Кто закрывает `Notices` — тот, кто его создал, вместе с камерой; на странице
одной фразой.
