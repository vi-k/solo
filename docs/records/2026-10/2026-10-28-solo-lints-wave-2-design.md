# `solo_lints`, вторая волна: дизайн

## Зачем

Первая волна дала пять правил по `packages/solo/doc/mistakes.md`. Три вещи она
отложила на вторую: правило `key_per_request` (решение владельца 2026-10-28),
быстрые исправления и сторож страницы ошибок. С тех пор у задачи появился
`isExpectedError` (`2026-10-28-if-failed-answer-design.md`), и с ним новая
ошибка: `ignoreFailure()` на задаче, которая уже называет свои ожидаемые
ошибки. Предикат пропускает баги дальше, а `ignoreFailure()` глушит и их. В эту
ошибку попала бы кнопка README `flutter_solo`: до `isExpectedError` она была
`onPressed: () => controller.load().ignoreFailure()`, и когда `load` назвал
свои ожидаемые ошибки, её пришлось переписать в `onPressed: controller.load`
(`a3e03472`). Владелец 2026-10-28 велел добавить правило во вторую волну.

Цели:

- два новых правила: `key_per_request` и `ignore_failure_hides_bugs`;
- быстрые исправления там, где правка механическая: `release_on_the_call`,
  `catch_without_check`, `key_per_request`;
- сторож: каждый блок «Don't do this» страницы ошибок даёт диагноз своего
  правила, каждый «Do this» молчит.

Не цели:

- плагин в самих пакетах репозитория и упоминания в README ядра и `solo` —
  позже, решением владельца (`2026-10-28-solo-lints-design.md`, «Решения
  владельца»);
- выпуск: пакет выходит после 0.6.0 ядра и `solo`, порядок — в `AGENTS.md`;
- новый раздел страницы ошибок под `ignore_failure_hides_bugs`: страница
  говорит о семи ошибках, а эта уже показана в README `flutter_solo`.

Анти-цели:

- предупреждение, которое срабатывает на законном коде у всех, кто подключил
  пакет: оно приучит не читать остальные. Эвристики — линтами;
- исправление, которое меняет смысл кода. Где правка не механическая,
  исправления нет.

## Правила

Общие положения первой волны остаются: тело задачи, контекст, точки отмены,
опознание типов по имени и библиотеке
(`packages/solo_lints/lib/src/ context.dart`).

### `key_per_request` — линт, `solo`

Сказано в `2026-10-28-solo-lints-design.md`, раздел о правиле; повторено здесь
с тем, что нужно реализации.

Диагноз ставится, когда задача с `Policy.droppable` взяла ключ, который
не ссылается ни на один параметр объемлющего метода или функции, а литерал тела
ссылается хотя бы на один. Две формы:

- `enqueue(..., key: K, policy: Policy.droppable, body)` на `Solo`;
- `enqueueJob(job(..., key: K, body), policy: Policy.droppable)`: у `job`
  своего `policy:` нет, ключ и политика стоят в разных вызовах, `job` — прямо
  в аргументе.

Объемлющий — ближайший `MethodDeclaration` или `FunctionDeclaration`
(не литерал функции). Параметр считается, если на него ссылается
`SimpleIdentifier` с тем же элементом. Ключ, построенный из поля или
константы, — тоже общий ключ. Другие политики правило не проверяет: `droppable`
единственная отдаёт второму вызывающему результат первого.

Диагноз — на выражении ключа. Сообщение: «`'{0}' is one key for every call:
Policy.droppable hands a later caller the result of the first.`», где `{0}` —
текст ключа. Исправление: «`Put the arguments the body reads into the key.`»

Линт, а не предупреждение: общий ключ бывает задуман, когда параметр для
результата не важен (решение владельца).

### `ignore_failure_hides_bugs` — линт, `solo`

Имя — мой выбор.

Диагноз ставится на вызов `ignoreFailure()` интерфейса `Job` ядра, если задача,
на которой он вызван, называет свои ожидаемые ошибки, а сама задача дальше
никому не нужна. Обе части обязательны.

**Задача называет ожидаемые ошибки,** если выражение задачи `E` — цель вызова
`E.ignoreFailure()` или цель каскада `E..ignoreFailure()` — сводится к вызову
`job` или `enqueue` на `Solo` с именованным аргументом `isExpectedError`. Или
к `a.add(e)` накопителя, где `a` — поле того же класса, объявленное `final` или
`late final`, чей инициализатор — `collect` или `accumulate`
с `isExpectedError`. У `collect` и `accumulate` своего `ignoreFailure()` нет:
они возвращают `SoloAccumulator`, задачу даёт его `add`, а сам накопитель
документы держат в поле. Поле — объявление со значением, а не переменная,
которой присваивают; поэтому правило «переменные не прослеживаются» ниже оно
не нарушает — мой выбор. Сведение идёт:

- через аргумент `enqueueJob(x)`. С `Policy.droppable` он может вернуть уже
  идущую задачу того же ключа, а не `x`, и её предикат может быть другим.
  Правило судит по `x`: тот же ключ почти всегда даёт тот же метод;
- через вызов метода или функции, объявленных в той же библиотеке, чьё тело —
  одно выражение (`=>`) или один `return`. Объявление берётся
  из `RuleContext.allUnits`. Правило анализатора не видит тел других библиотек,
  поэтому метод из другого файла пакета правило не проверяет и молчит;
- с защитой от рекурсии: метод, уже пройденный на этом сведении, не проходится
  второй раз.

Переменные не прослеживаются: `final job = load(); job.ignoreFailure();`
правило не видит. Анализ потока значения `Job` отвергнут ещё в первой волне.

**Задача никому не нужна,** если значение `E` выброшено:

- `E.ignoreFailure()` — всегда: `ignoreFailure()` возвращает `void`, и после
  него задачи у вызывающего нет;
- `E..ignoreFailure()` — только если значение каскада выброшено: каскад —
  выражение `ExpressionStatement` или тело `=>` функции, чей тип возврата
  `void`. У объявленной функции это объявленный тип, у литерала — тип возврата
  контекстного типа, если он есть: `onPressed: () => load()..ignoreFailure()`
  с `VoidCallback` срабатывает. Литерал без контекстного типа судится по своему
  статическому типу — мой выбор. Каскад, который присвоен или передан
  (`final job = profile.load()..ignoreFailure();` в тесте под `fakeAsync`),
  молчит: исход задачи читают.

Сообщение: «`'ignoreFailure()' also hides the bugs that '{0}' lets through.`»,
где `{0}` — `isExpectedError` с именем первого метода или функции, через
которые прошло сведение, то есть ближайших к `ignoreFailure()`:
`load's isExpectedError`. Цепочка `load` → `_load` → `job` даёт `load`. Без
метода — имя самого вызова: `enqueue's isExpectedError`, а для накопителя — имя
поля. Это мой выбор. Исправление: «`Drop 'ignoreFailure()': isExpectedError
already keeps the expected errors quiet.`»

Линт, а не предупреждение — мой выбор. Законный случай есть, и страница ошибок
его называет («Answering for every failure»): исход никому не нужен, а отчёт
оставлен хукам. Там `ignoreFailure()` на задаче с предикатом делает ровно то,
что задумано.

Исправления нет. Удалить `.ignoreFailure()` механически можно,
но в `onPressed: () => controller.load().ignoreFailure()` останется лямбда,
и `unnecessary_lambdas` потребует тот же отрыв, который README и показывает.
Правка на две строки по месту — не быстрое исправление.

## Быстрые исправления

Регистрируются `registry.registerFixForRule(код, генератор)`; генератор —
`ResolvedCorrectionProducer`
из `package:analysis_server_plugin/edit/dart/correction_producer.dart`. Оба
есть в 0.3.14, нижней границе пакета. Исправление предлагается только там, где
правка однозначна; иначе продюсер ничего не строит, и диагноз остаётся без
исправления.

Продюсеру нужны `ChangeBuilder`
из `package:analyzer_plugin/utilities/change_builder/change_builder_core.dart`
и `FixKind` из `package:analyzer_plugin/utilities/fixes/fixes.dart`.
`analysis_server_plugin` их не реэкспортирует,
а `depend_on_referenced_packages` включён. Поэтому `analyzer_plugin` становится
прямой зависимостью с `'>=0.14.8 <0.15.0'`. Граф разрешения от этого
не меняется: `analysis_server_plugin` и так держит `analyzer_plugin` точной
версией, 0.3.14 — 0.14.8. Нижнюю границу проверяет `floor`, как у остальных
зависимостей. Это мой выбор.

### `release_on_the_call`

Исходный код:

```dart
final socket = await ctx.join(() => connect());
ctx.onDispose(socket.close);
```

После исправления:

```dart
final socket = await ctx.join(
  () => connect(),
  dispose: (socket) => socket.close(),
);
```

Иначе говоря: вызов `onDispose` (или `onDiscard`) удаляется, а в вызов,
принёсший ресурс, добавляется `dispose:` (или `discard:`). Значение — функция
одного параметра с именем объявленной переменной:

- отрыв `x.m` — `(x) => x.m()`;
- литерал без параметров — тот же литерал с параметром `x`, тело как было.

Другие формы аргумента (имя функции, вызов) исправления не получают. Перенос
строк — `dart format`, не продюсер.

### `catch_without_check`

В начало блока `catch` вставляется `ctx.check();`, где `ctx` — имя контекста
из диагноза, с отступом первой инструкции блока. Пустой блок получает
инструкцию с отступом блока плюс два пробела.

### `key_per_request`

Ключ `K` заменяется записью `(K, p1, ..., pn)`, где `p1, ..., pn` — параметры
объемлющего метода, которые читает тело, в порядке объявления. Так делает «Do
this» страницы ошибок: `key: (_Op.load, id)`.

Исправление предлагается, только если тип каждого такого параметра сравнивается
по значению: `String`, `int`, `double`, `num`, `bool`, перечисление или они же
с `?`. Список, колбэк или токен в записи не равны себе от вызова к вызову,
и `droppable` молча перестал бы отбрасывать что-либо. Тогда исправления нет,
диагноз остаётся — мой выбор.

## Сторож страницы ошибок

Тест в `packages/solo_lints/test/`, файл — на выбор строителя. Он читает
`packages/solo/doc/mistakes.md` и для каждой пары «Don't do this» / «Do this»
проверяет два условия:

- блок «Don't do this» даёт диагноз правила своей пары и никаких других правил
  пакета;
- блок «Do this» не даёт ни одного диагноза правил пакета, линты включены.

Пары адресуются разделом и порядком внутри раздела. Адресация по имени
из `tool/doc_blocks.py` здесь не годится: оба блока пары объявляют одно имя —
`syncAndRecord` в «Steps as children», `load` в «A key for each request».
Каждая пара названа в таблице сторожа: правило или «без правила». Первая пара
«Each wait in its place» — обычный `await` в теле — без правила, его первая
волна отвергла как шумное. «Answering for every failure» — тоже без правила.
У пары без правила молчат оба блока: правило, которое однажды на ней сработает,
должно попасть в таблицу. Пара, которой нет в таблице, роняет тест: новый
раздел страницы не проскочит молча.

Таблица по нынешней странице:

| Раздел | Пара | Правило |
|---|---|---|
| Each wait in its place | 1 | без правила |
| Each wait in its place | 2 | `ctx_in_cleanup` |
| Registering a release on the call | 1 | `release_on_the_call` |
| Letting cancellation through a catch | 1 | `catch_without_check` |
| Steps as children | 1 | `await_own_queue` |
| Answering for every failure | 1 | без правила |
| Moving the clock in fakeAsync | 1 | `sync_fake_async` |
| A key for each request | 1 | `key_per_request` |

Блок — фрагмент, а не файл. Сторож вставляет его в обвязку своего раздела:
класс-наследник `Solo`, тело задачи с `ctx`, заглушки `device`, `api`,
`profile` — что нужно разделу, чтобы фрагмент разрешился без ошибок компиляции.
Обвязка живёт в тесте. `AnalysisRuleTest` включает одно правило, поэтому сторож
регистрирует и включает все правила пакета сам. Ошибка компиляции фрагмента
роняет тест отдельно от диагноза: иначе молчание правила на неразрешённом коде
выглядело бы как «Do this».

Обвязка «Answering for every failure» даёт `profile.load()` без
`isExpectedError` — мой выбор. Абзац страницы над «Do this» говорит о задаче,
исход которой никому не нужен, и о предикате там речи нет. С предикатом блок
дал бы диагноз `ignore_failure_hides_bugs`, и сторож покраснел бы на законном
совете.

В архив pub.dev сторож не входит: в архиве `solo_lints` нет
`packages/solo/doc/`, а задание `floor` гоняет тесты архива. Файл сторожа
исключён в `.pubignore` пакета — мой выбор. Его гоняет задание `dart`
из дерева.

## Тесты

Правила — как в первой волне: `analyzer_testing`, `AnalysisRuleTest`, по файлу
на правило, настоящие исходники `async_job` и `solo` через `newPackage`. Для
`ignore_failure_hides_bugs` — каждая строка раздела правила: сведение через
`enqueueJob`, через метод той же библиотеки, через поле накопителя, литерал
с `VoidCallback`, молчание на методе другой библиотеки, на переменной,
на присвоенном каскаде; рекурсия не виснет. Для исправления `key_per_request` —
молчание на параметре-списке.

Исправления — проверка «до/после» на тексте. В `analyzer_testing` до 0.4.4
средств для исправлений нет. Первым шагом плана — зонд: собрать
`DartFixContext` из разрешённой библиотеки теста, запустить продюсер, применить
правки к тексту. Не соберётся — исправления выходят без автоматических тестов
и проверяются вручную в IDE, и это записывается в отчёт; решать тогда
владельцу.

`DartFixContext` собирается через классы из `src/` (`DartChangeWorkspace`,
`TestInstrumentationService`), а между 0.3.14 и свежими версиями они
не обещаны. Поэтому тесты исправлений в архив не входят: их исключает
`.pubignore`, как сторожа, и гоняет задание `dart` на свежих версиях дерева.
Само исправление на нижней границе держит `floor` только через `analyze lib` —
мой выбор.

учитывает.

## Мои решения

- имя `ignore_failure_hides_bugs`;
- `ignore_failure_hides_bugs` — линт, без исправления;
- задача накопителя сводится через поле `final` или `late final`;
- у литерала `void` берётся из контекстного типа;
- `{0}` сообщения — ближайший к `ignoreFailure()` метод;
- исправление `key_per_request` — сверх двух кандидатов первой волны, и только
  на параметрах, которые сравниваются по значению;
- прямая зависимость `analyzer_plugin`;
- обвязка «Answering for every failure» без предиката;
- сторож и тесты исправлений вне архива через `.pubignore`;
- вторая волна в том же `## 0.1.0`.
