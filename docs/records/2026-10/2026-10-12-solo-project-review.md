## Сводка

High нет ни у кого. Движок `solo` все четверо оценили высоко, и его поведение
на обычных путях подтвердили зондами.

**Главное, что нашли трое: пример README `flutter_solo` уводит провал в зону
(M1).** `onPressed: controller.load` выбрасывает возвращённый `Job`,
а `ifFailed` не наблюдение: экран возвращается в `Empty`, ошибка уходит в зону.
Тесты README кнопку не нажимают. Рядом — README `solo`, где о зоне
и `ignoreFailure()` нет ни слова (M2), и вопрос о самом правиле (M3).

**Слабое место кода — Flutter-слой, подписки и выборки.** `SoloSubscriptions`:
чтение `length` во время отмены (M9), бросающий репортёр (M10) и удержание
отменённой подписки (M11) — каждое нашли двое. `SoloSelection`: кеш при
изменяемом источнике (M6), повтор отложенного уведомления (M7), удержание
результата без слушателей (M8). `SoloSelector.changed` сравнивает с ещё
не показанным значением, а dartdoc говорит обратное (M5, двое).

**В `solo` — края реентерабельности:** `lastJobWhere` отдаёт задачу, которую
предикат отменил (M13, двое), `canStart` с синхронной записью состояния (M14),
брошенный `publish` (M16), зона тела корневой задачи (M12).

**Документация в трёх рецептах учит неверному** (M17 — `!=` вместо `identical`,
M19 — слежение за контроллером, L12 — зона в тестах), README `flutter_solo`
обещает отмену сильнее механики (M18), три dartdoc и CHANGELOG отстали от кода
(L3, L7–L10).

**Форма страниц** — первые попытки, вступления о структуре, длина — снижала
оценку у всех четырёх (M20, L4). Это решения владельца, вопросы к нему.

### M1. Пример README `flutter_solo` оставляет ошибку загрузки необработанной

**Нашли:** Opus (D1 и C5 о тестах README), Astra (D1), Sol (D1). **Где:**
`packages/flutter_solo/README.md`, «Usage» и «Selecting one value»:
`onPressed: controller.load` в строках 133, 212 и 250; правило — там же,
«Outcomes», строки 451–453.

Кнопка зовёт метод, Flutter отбрасывает возвращённый `Job`, а `ifFailed` только
меняет состояние и исход не наблюдает. При обычной ошибке API экран
возвращается в `Empty`, а провал уходит в зону — в Flutter это
`PlatformDispatcher.onError` и крэш-репортер. Тесты README везде зовут
`load().ignoreFailure()` и кнопку не нажимают, поэтому пример зелёный. Пример
пакета делает правильно: его `_load` ждёт `done`.

```text
README errors=[Bad state: offline] state=Empty
```

Вердикт: принято, Medium, исправлено; главный дефект документации этого ревью —
трое нашли независимо. Воспроизведено: тест, нажимающий кнопку README
с падающим API, краснеет на `StateError`. Чинить: пример наблюдает исход сам —
или явный `ignoreFailure()` с объяснением, если провал оставлен репортёру, —
и сторож нажимает кнопку. Правка README с переводом. Итог 2026-10-12: сделано
после ответа владельца на M3 — правило остаётся. Кнопка «Usage» стала
`() => controller.load().ignoreFailure()`, а за абзацем об обработчиках встал
новый: они отвечают за экран, а не за вызвавшего; брошенная `Job` с провалом
уходит в зону и после `ifFailed`; `ignoreFailure()` на кнопке говорит, что
экрана хватит; ссылка на «Outcomes». Разошлось с предложенным в одном: кнопки
`save` в «Selecting one value» остались `controller.save`. У `save` нет
`ifFailed`, его провал не обработан ничем, и зона для него — законное место,
а `ignoreFailure()` сделал бы провал сохранения немым. Сторожа
в `readme_rakes_test.dart`: нажатие Load при падающем API (на старой кнопке
краснеет `Bad state: no network`, проверено мутацией копией) и сброшенный

### M3. `ifFailed` не считается наблюдением, и `onUnanswered` такой провал не видит

**Нашёл:** Opus (C1). **Где:** `packages/solo/lib/src/solo.dart`, `Solo.run`
и `Solo.job` (параметр `ifFailed`), `Solo.onUnanswered`,
`Solo.unansweredHandler`.

Задача с `ifFailed`, исход которой никто не прочитал, публикует состояние
из `ifFailed` и отправляет `Failed` в зону. `unansweredHandler`
и переопределённый `onUnanswered` его не видят: у приложения нет одного места,
где сказать «провалы, которые экран обработал состоянием, — не крэш».

```text
probe1 state=Empty
probe1 zone=[Bad state: offline]
probe1 unansweredHandler=[] onUnanswered=[] onError=[load: Bad state: offline]
```

Вердикт: воспроизведено, но это правило ядра — ненаблюдённый `Failed` идёт
в зону, — названное в README `flutter_solo` «Outcomes» и на `errors.md`. Вопрос
владельцу, дизайн: оставить правило и назвать его там, где начинают (M1, M2),
или считать `ifFailed` ответом на провал, или вести такой провал через
`onUnanswered`. Моя рекомендация — сначала M1 и M2: они чинят вред без смены
правила. Итог 2026-10-12: владелец оставил правило. Вред закрыт в README (M1,
M2), поведение `solo` и ядра не менялось.

### M5. `SoloSelector.changed` сравнивает с ещё не показанным значением

**Нашли:** Astra (C1), Sol (D3, Low). **Где:**
`packages/flutter_solo/lib/src/solo_selector.dart:64`, dartdoc `changed`:
«`previous` is the value [builder] was last given».

Две публикации до кадра: `changed` принимает первую, и вторая сравнивается уже
с ней, хотя `builder` её не видел. Для пороговых предикатов это меняет ответ.

```text
SELECTOR seen=[0, 2] comparisons=[0->2, 2->3] state=3
```

Вердикт: воспроизведено, исправлено словом; код расходился с dartdoc. Вопрос
владельцу: чинить код — база сравнения равна показанному значению — или слово —
«последнее принятое значение». Виджет он правил 2026-10-11 по README
(`2026-10-04-flutter-solo-readme-reread-report.md`, M5), и выбор базы
сравнения — его. Итог 2026-10-12: владелец выбрал слово. Сначала я рекомендовал
код и собрал его прототип: поле с показанным значением, все тесты
`flutter_solo` и пример зелёные без правок. Владелец спросил, что это меняет,
раз `setState` и грязный элемент те же. Разница только в значении, которое
получит `builder`, и зонд показал, что прототип делает его зависимым от кадров.
При пороге 2 история 0 → 2 → 3 одним кадром даёт 3, двумя — 2, а при
`changed: current > previous` история 0 → 5 → 3 даёт 3 и 5. Нынешний код даёт 2
и 5 в обоих случаях, и так же сравнивает `SoloSelection`. Рекомендация
пересмотрена, код не тронут. Dartdoc `changed` теперь говорит, что `previous` —
выбор, который виджет принял последним: первый или последний, названный
изменившимся. `builder` обычно его уже получил, но не всегда, и экран
останавливается там, куда ведут изменения, независимо от кадров. То же в абзаце
README «Selecting one value» с переводом, в dartdoc класса и в комментарии
поля. Сторож в `packages/flutter_solo/test/readme_rakes_test.dart` гонит длину
имени 0, 3, 5 при пороге 3. Одним кадром второе изменение сравнивается с 3

провала — зона создания — не задет. Документы `solo` о зоне тела молчат. Вопрос

уже в зоне того, кто ждёт. Зависает другое: тело, которое ждёт будущее своей
зоны создания, когда это будущее падает, а тело бежит под другим
`runZonedGuarded`. Ошибка в зону тела не переходит, уходит обработчику зоны
