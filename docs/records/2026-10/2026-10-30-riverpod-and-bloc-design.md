## Зачем

Пункт 3 списка «Что предлагаю владельцу» записи
`2026-10-30-prospects-review.md` (Opus F2, Fable F2). Большинство тех, кому
нужна отмена с уборкой, уже живут на riverpod или bloc и слой состояния менять

обработчик одной-двумя строками, а `solo` ему для этого не нужен.

## Вступление

Вступление называет версии, на которых стоит код страницы: riverpod 3, bloc 9
с `bloc_concurrency`, http 1.5 и новее, dio 5. Следом — вход для торопливого
по решению 71 `docs/settled.md`: четыре строки, по одной на раздел, со ссылкой
на раздел — `ref.onDispose(job.cancel)`, `_current?.cancel()` в нотифаере,
`emit.forEach(watch(job), …)`, токен клиента через `ctx.onCancel`.

## Разделы

Форма страниц `doc/`: требование, первая попытка, ответ. Первая попытка — та
версия, к которой ведёт словарь API; где ошибаться не на чем, раздел
открывается ответом.

Общий предмет — `Database` из быстрого старта README: `open`, чтение
по страницам, `close`, каждое печатает строку. Чтение по страницам нужно,
потому что `ctx.join` дожидается уже начатого вызова: с одним чтением трассы
первой попытки и ответа совпадают.

### A provider that is gone

Требование: экран ушёл, `FutureProvider.autoDispose` освобождён — чтение
останавливается, база закрывается.

Первая попытка: провайдер возвращает `job.value` и больше ничего. Трасса зонда:
провайдер освобождён, задача дочитывает все четыре страницы и кончается `Done`.

Вторая попытка: `ref.onCancel(job.cancel)` — имя обещает ровно это. В riverpod
3 `onCancel` зовётся и тогда, когда все слушатели на паузе: задача кончается
`Cancelled`, а `Cancelled` — это `Exception`, и повтор по умолчанию строит
провайдер заново; на `onResume` идёт вторая задача. Трасса зонда ревьюера:
`AsyncLoading(error: Cancelled(manual), retrying)`, затем «onCancel#2: start».

Ответ — одна строка `ref.onDispose(job.cancel)`. Трасса зонда:

```text
database opened
screen left
provider disposed
page 1 read
database closed
outcome: Cancelled(manual)
```

Две фразы после ответа. В зону ошибка не уходит, но `ProviderObserver` получает
`providerDidFail` с `Cancelled(manual)` — наблюдатель, который шлёт сбои
в отчёты, отсеивает `error is Cancelled`. И `Cancelled`, которым задача
кончилась сама — по своему сроку или своей отмене, — riverpod повторяет как
сбой.

### A notifier that starts again

Нотифаер ведёт задачу из метода, а `onDispose` между вызовами метода
не зовётся. Раздел открывается ответом, ошибаться в нём не на чем, кроме
забытой строки: поле `_current`, метод отменяет прежнюю задачу перед новой,
`ref.onDispose` отменяет текущую. Короткий, одна трасса.

### A handler that restarts

Требование: поиск на каждый ввод с `restartable()` из `bloc_concurrency` —
новый ввод останавливает прежний поиск, `close()` блока — текущий.

Первая попытка: обработчик ждёт `job.value` и проверяет `emit.isDone`. Зонд:
`restartable()` отписывается от обработчика, но тело прежнего поиска дочитывает
всё и кончается `Done`; поиск, начатый перед `close()`, читает уже после
`bloc closed`.

Ответ — функция `watch`, стрим со значением задачи, отписка от которого
отменяет задачу, и `emit.forEach`:

```dart
Stream<T> watch<T>(Job<T> job) {
  late final StreamController<T> controller;
  controller = StreamController<T>(
    onListen: () {
      job.value
          .then(controller.add, onError: controller.addError)
          .whenComplete(controller.close);
    },
    onCancel: job.cancel,
  );
  return controller.stream;
}

on<Searched>((event, emit) async {
  final job = search(event.query);
  await emit.forEach(watch(job), onData: (rows) => Found(rows));
}, transformer: restartable());
```

Комментарий в коде `watch`: стрим слушают сразу, значение задачи читается
в `onListen`.

Почему так, а не опрос `emit.isDone` таймером, как в зонде Fable F2:
у `Emitter` нет колбэка отмены, но `restartable()` и `close()` отменяют эмиттер
синхронно, и он тут же отменяет подписки своих `onEach` и `forEach` (`bloc`
9.2.1, `lib/src/emitter.dart`, `cancel` и `_close`; `lib/src/bloc.dart`,
`close`). Таймер опаздывает на свой период и крутится, пока жив обработчик.
Трасса зонда: «a» кончается `Cancelled(manual)` на второй странице, как только
пришло «ab»; «abc» кончается `Cancelled(manual)` после `bloc closed`, прочитав
одну страницу, а не три.

`close()` отменяет обработчик при любом трансформере, не только при
`restartable()`: зонд с трансформером по умолчанию — «a» и «ab» идут
параллельно и обе кончаются `Done`, а «abc» на `close()` кончается
`Cancelled(manual)` после одной страницы. Страница говорит это одной фразой:
адаптер нужен любому обработчику, который ждёт задачу, а `restartable()`
добавляет к `close()` отмену на новом событии.

Оговорки, которые страница называет:

- ни новое событие, ни `close()` не ждут уборки прежней задачи: `restartable()`
  запускает новый обработчик раньше, чем отменяет старый, а `close()` эмиттера
  не ждёт `job.cancel()`. «database opened for ab» стоит раньше «database for a
  closed», база «abc» закрывается после `bloc closed`. Для ресурса, которого
  может быть только один, это важно;
- задача, кончившаяся `Cancelled` сама, приходит в `forEach` ошибкой, bloc
  отдаёт её в `onError` и в зону, и `Job.isCancellationError` тут ни при чём.
  Страница показывает `onError:` у `forEach`.

`watch` остаётся кодом страницы, а не API ядра: пункт 6 того же списка — новых
возможностей до первых внешних пользователей не добавлять.

### A request to abort

Требование: задача отменена — HTTP-запрос прерывается, а не дочитывается.

Первая попытка: `ctx.join(() => client.get(url))`, как учит быстрый старт.
Отмена ждёт, пока ответ придёт целиком: в зонде ревьюера `cancel()`
возвращается через 252 мс, когда сервер уже отдал тело. Одна фраза
об `abandonable` со ссылкой на «Stopping the operation» страницы
`cancellation.md`: задача кончается сразу, но ответ всё равно приходит, уже
никому.

Ответ — токен клиента через `ctx.onCancel`, как в разделе «A token through
`onCancel`» страницы `cancellation.md`, на двух клиентах:

- http 1.5 и новее: `AbortableRequest` с `abortTrigger`, `ctx.onCancel`
  завершает `Completer` триггера. Клиент, который `abortTrigger`
  не поддерживает, его не замечает, и токен сводится к `join`; страница это
  называет;
- dio: `CancelToken`, `ctx.onCancel(token.cancel)`.

И одна строка в `main`, чтобы прерванный запрос не шёл в отчёты о сбоях:

```dart
Job.isCancellationError = (error) =>
    error is http.RequestAbortedException ||
    error is DioException && error.type == DioExceptionType.cancel;
```

Без неё в зону уходят `ClientException: Request aborted…`
и `DioException [request cancelled]`; с ней — ничего.

Сервер в трассах — сырой `ServerSocket` на loopback, который печатает «client
hung up», когда клиент закрыл соединение, и «sending body», когда отдаёт тело.
`HttpServer` для этого не годится: он печатает «answered» и после того, как
клиент ушёл. Драйвер печатает строки сервера после `await job.cancel()`
и `await` закрытия соединения, так что порядок держат ожидания, а не запас
времени. Миллисекунды страница не цитирует.

## Стенд

Код страницы живёт только при стенде в CI, как у `vs-bloc.md`
и `accumulation.md`. Новый генератор `tool/adapter_snippets.py`: блоки берёт
`tool/doc_blocks.py` по разделу и имени, пакет `adapters_check` вне дерева
с путевой зависимостью на ядро и с riverpod `^3.0.0`, bloc `^9.0.0`,
bloc_concurrency `^0.3.0`, http `^1.5.0`, dio `^5.9.0`. Каждый блок страницы
взят драйвером, иначе сборка падает.

- Разделы о riverpod и bloc идут на виртуальном времени с раннером `RUNNER`
  из `tool/doc_snippets.py`: часы двигаются снаружи зоны, и между шагами
  проходит оборот настоящего цикла событий. Голый `fakeAsync`, как
  в `accumulation_snippets.py`, не годится: `bloc.close()` под ним
  не завершается, потому что ждёт future корневой зоны (`cancel` подписки
  в `switchLatest`, `_eventController.close()`), а после одного переключения
  `restartable()` не отменяет и текущий обработчик. Задержки разведены так,
  чтобы два события не падали на одну миллисекунду: под виртуальным временем
  «page 1 read» и «screen left» на 30 мс меняются местами.
- Раздел о запросе идёт на настоящем времени с сервером из раздела выше.

Задание `snippets` гейта: генератор, `pub get`, `analyze --fatal-infos`, прогон
драйверов с выводом в файл, `check_traces.py` для новой страницы, ключ кэша
с новым генератором. Правило «стенд вне CI — не стенд» из скилла `doc-bench`;
проверка, что задание умеет краснеть, — мутацией блока и ожидания драйвера.

Стенд гоняется на SDK `stable` и разрешает самые свежие версии: riverpod 3.4
требует Dart 3.12. На полу ядра, Dart 3.10, читатель получит riverpod 3
постарше, и его стенд не проверяет. Поэтому версии во вступлении названы
мажорами, как они есть, без обещания пола.

Что правится заодно: `AGENTS.md` и `docs/conventions.md` называют стенды
задания `snippets` — их становится три.

## Чего нет

- Пакета-адаптера `async_job_riverpod` или `async_job_bloc`: пункт 6 — новых
  пакетов не плодить.
- Сравнения `solo` с riverpod: Opus F2 первой записи просил его, Fable F2 этой
  записи считает страницу адаптеров ценнее, потому что она не просит менять
  слой состояния.
- Flutter: страница на чистом Dart, `ProviderContainer` вместо `ProviderScope`.
  `flutter_riverpod` и `flutter_bloc` дают те же `ref` и `Emitter`.

## Ревью дизайна

Ревьюер на Opus прочёл первую версию дизайна, прогнал зонды и написал свои.
Находки ниже пересказаны коротко; каждую я проверил своим прогоном его зондов
или по своему.

**1. High. Голый `fakeAsync` ломает разделы о bloc.** `bloc.close()` под ним
не завершается, а после переключения `restartable()` не отменяет текущий
обработчик: future корневой зоны. Раннер `RUNNER` из `tool/doc_snippets.py` это
обходит. Задержки — без совпадений по миллисекунде.

Вердикт: подтверждаю своим зондом: под голым `fakeAsync` `close()` после
`restartable()` не вернулся, совпадение на 30 мс меняет порядок строк. Принято,
раздел «Стенд».

**2. High. Первая попытка о запросе показывает не то.** `abandonable`
отменяется так же быстро, как токен; разница видна только на сервере,
а `HttpServer` печатает «answered» и после ухода клиента. Первая попытка —
`ctx.join`, `abandonable` — одной фразой; сервер — `ServerSocket` с печатью
«client hung up»; миллисекунды не цитировать.

Вердикт: подтверждаю его зондом `net.dart`: `join` — 252 мс, `abandonable` — 3
мс и «response arrived to nobody», токены — «client hung up» сразу. Принято,
раздел «A request to abort».

**3. Medium. riverpod гасит отмену не целиком.** После освобождения
`ProviderObserver.providerDidFail` получает `Cancelled(manual)`.

Вердикт: подтверждаю его зондом `rv.dart`: «observer: providerDidFail
Cancelled(manual)». Принято: фраза и фильтр в наблюдателе.

**4. Medium. `ref.onCancel` — ловушка словаря.** В riverpod 3 он зовётся
и на паузе всех слушателей; задача кончается `Cancelled`, повтор строит вторую.
Свой `Cancelled` задачи riverpod повторяет как сбой.

Вердикт: подтверждаю тем же зондом:
`AsyncLoading(error: Cancelled(manual), retrying)` и «onCancel#2: start».
Принято второй попыткой раздела о провайдере.

**5. Medium. Перекрытие есть и на `restartable()`, не только на `close()`.**

Вердикт: подтверждаю своим зондом: «database opened for ab» раньше «database
for a closed». Принято, оговорка общая.

**6. Low–Medium. Свой `Cancelled` задачи уходит через bloc в зону.** И `watch`
надо слушать сразу.

Вердикт: подтверждаю его зондом `edge.dart`: «bloc onError: Cancelled(handler:
self)», «zone: Cancelled(handler: self)». Принято: оговорка, `onError:`
у `forEach` и комментарий в `watch`.

**7. Low. Версии.** riverpod 3.4.3 требует Dart 3.12, стенд на `stable`, пол
читателя не проверен; часть клиентов http `abortTrigger` не поддерживает.

Вердикт: принято: версии мажорами во вступлении, фраза о клиентах без
`abortTrigger`.

**8. Low. Вход для торопливого по решению 71.** И пометка первой попытки,
и предел в десять строк `check_doc_shape.py`, и запись о стенде
в `docs/conventions.md`.

Вердикт: принято, раздел «Вступление» и «Стенд».

Открытые вопросы первой версии ревьюер закрыл так: раздел о нотифаере нужен,
короткий; раздел о запросе остаётся с трассой, на детерминированном сервере.
Принято, разделы «A notifier that starts again» и «A request to abort».

## Что вышло

Страница `packages/async_job/doc/riverpod-and-bloc.md`, перевод
`docs/ru/async_job/riverpod-and-bloc.md`, стенд `tool/adapter_snippets.py`. Что
разошлось с дизайном и что выяснилось по ходу:

- Провайдер на странице — семейство `FutureProvider.autoDispose.family`
  по запросу. Тот же ответ закрывает смену запроса: экран слушает другой
  провайдер семейства, прежний освобождается и отменяет свою задачу. Это держит
  сторож драйвера.
- Вторая попытка: перезапуск приходит повтором riverpod, но идёт только после
  того, как экран снова виден. Зонд без повторов (`retry: (_, _) => null`) —
  экран возвращается к `AsyncError(Cancelled(manual))`; зонд без
  возобновления — вторая задача не начинается. Страница говорит обе вещи.
- Нотифаер: поле `_current`, отмена прежней задачи через `unawaited`, а перед
  записью состояния — проверка `ref.mounted` и `identical(job, _current)`. Без
  проверки `Cancelled` прежнего поиска ложится в состояние, пока новый
  грузится; сторож на варианте блока без проверки это требует.
- Строк `outcome:` в трассах riverpod и bloc нет: задача создаётся внутри блока
  страницы, драйверу её не достать. Исход держат сторожа по числу прочитанных
  страниц.
- Ключ блока включает подраздел `###`: первая попытка и ответ раздела о bloc
  объявляют один `SearchBloc`. Блок `watch` своего имени для
  `tool/doc_blocks.py` не объявляет — `watch<T>(` регулярка не ловит, —
  и берётся по `SearchBloc`.
- Сервер печатает свои строки сам, когда событие случилось. Порядок в трассе
  токенов держит ожидание: драйвер печатает исход после того, как сервер увидел
  уход клиента.
- Стенд краснеет: снятый `ref.onDispose(job.cancel)` — «pages read: 3, not 1»;
  снятый `onCancel: job.cancel` у `watch` — «pages read: 9, not 7»; правленая
  строка трассы — `tool/check_traces.py`.
