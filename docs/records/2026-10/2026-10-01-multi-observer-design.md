# Несколько наблюдателей

## Зачем

Задача получает одного наблюдателя, `Solo.observer` — тоже один. Приложению
обычно нужно несколько: лог, аналитика, отчёт о падениях, а в `solo` ещё
и наблюдатели со страницы `errors.md` (`SlowCancellations`,
`StuckCancellations`). Сейчас их сводят в один класс руками, и он смешивает
разную работу в одном месте. Владелец спросил 2026-10-01, не сделать ли
наблюдателя, которому передают список; решено делать для обоих пакетов.

## Ловушка, ради которой это не рецепт

У `JobObserver` хуки двух видов. `onStart`, `onFinish`, `onError` и `onLog`
только сообщают, и их можно раздать списку. `onUnanswered` отвечает за ошибку,
которую не несёт ни один исход, и тело по умолчанию отдаёт её в зону, где
задача создана.

Класс, который раздаёт списку все пять хуков, отдаёт ошибку в зону столько раз,
сколько в списке наблюдателей без своего `onUnanswered`, и ответ одного
наблюдателя её не останавливает. Зонд 2026-10-01 на дереве после `f36d03d`: два
логгера с телом `onUnanswered` по умолчанию и третий, который отвечает сам;
работа из `ctx.unattended` бросает.

```text
без отвечающего: [a onError, b onError] [zone: late, zone: late]
с отвечающим:    [a onError, b onError, sentry answered] [zone: late, zone: late]
```

Страница `observing.md` обещает обратное: «an observer written to watch changes
nowhere an error goes». С таким составным это перестаёт быть правдой для
каждого наблюдателя, который в него попал. Это и первая попытка нового раздела
страницы: к ней ведёт сам словарь — `onUnanswered` такой же хук, как остальные,
и цикл по списку пишется для всех пяти.

У `SoloObserver` хука ответа нет: отвечают `Solo.onUnanswered`
и `Solo.errorHandler`. Там раздача списку ловушки не несёт.

## `MultiJobObserver` — `async_job`

```dart
final class MultiJobObserver with JobObserver {
  MultiJobObserver(Iterable<JobObserver> observers, {JobObserver? answer});
}
```

```dart
Job<void>(
  observer: MultiJobObserver([Log(), Analytics()], answer: Crashes()),
  body,
);
```

Правила:

1. `onStart`, `onFinish`, `onError` и `onLog` идут каждому наблюдателю
   из списка по порядку, затем `answer`, если он есть. Каждый вызов изолирован
   так же, как ядро изолирует хук одного наблюдателя (`JobBase._notify`):
   ошибка уходит в текущую зону, брошенный `Cancelled` никуда не уходит,
   следующий наблюдатель вызывается. Без своей изоляции ядро обернуло бы только
   весь составной вызов, и первый бросивший выключал бы остальных — страница
   обещает, что бросивший хук «changes nothing else».
2. `onUnanswered` идёт одному `answer`. Без `answer` работает тело
   по умолчанию: зона, где задача создана, один раз, отмены отбрасываются —
   то же, что у одного наблюдателя без переопределения. `onUnanswered`
   наблюдателей из списка не вызывается никогда.
3. `answer` и наблюдает, и отвечает: его сообщающие хуки вызываются после
   списка. Так класс отчёта о падениях, который и пишет хлебные крошки
   в `onError`, и отвечает в `onUnanswered`, ставится одной строкой.
4. Конструктор бросает `ArgumentError` в двух случаях. Первый — наблюдатель,
   который встречается дважды (`identical`) среди списка и `answer`, считая
   и вложенные составные: иначе он слышит каждое событие дважды, и молча.
   Второй — составной с `answer` в списке: правило 2 обошло бы его
   `onUnanswered`, и его ответ пропал бы; совет в сообщении — передать его как
   `answer`. Составной в роли `answer` разрешён: он спрашивает свой.
5. Список обходится один раз, при создании, и копируется: ленивый `Iterable`
   не строит наблюдателей заново на каждое событие, и наблюдатель на `Expando`,
   как `SlowCancellations`, не теряет своих меток. Пустой список без `answer`
   допустим и ведёт себя как наблюдатель без переопределений.
6. Ничего не хранит сверх списка и `answer`, публичных геттеров нет.
   Наследуемость: `final class`, в `async_job.dart`, рядом с `JobObserver`,
   частью библиотеки `job_base.dart` (`part 'observer.dart'`), чтобы звать
   `JobBase._notify`.
7. Ленивое сообщение `onLog` строит каждый наблюдатель списка, который следует
   соглашению `Log` со страницы: столько раз, сколько их. Об этом говорит
   dartdoc.

Что остаётся как было: дети без своего наблюдателя наследуют составного
целиком; продолжение `then` берёт только переданного ему; движок домена,
который ставит своего наблюдателя на каждую задачу, как `solo`, ставит его
и дальше. Составной наблюдатель — обычный `JobObserver`, ядро о нём не знает.

Правило 2 молча обходит наблюдателя списка, который переопределил
`onUnanswered`: его ответ не вызывается. Узнать переопределение во время
выполнения Dart не даёт. Это говорит dartdoc и раздел страницы: в списке
наблюдают, отвечает тот, кто назван `answer`.

## `MultiSoloObserver` — `solo`

```dart
final class MultiSoloObserver extends SoloObserver {
  MultiSoloObserver(Iterable<SoloObserver> observers);
}
```

```dart
Solo.observer = MultiSoloObserver([
  LoggingObserver(),
  SlowCancellations(),
  StuckCancellations(),
]);
```

Все семь хуков (`onCreate`, `onStart`, `onFinish`, `onError`, `onChange`,
`onLog`, `onClose`) идут каждому наблюдателю по порядку, каждый вызов
изолирован `Solo._callHook`: ошибка — в текущую зону, включая `Cancelled`,
следующий вызывается. Класс объявлен в `solo.dart`, рядом с `_SoloJobObserver`,
и зовёт `_callHook` сам, без копии правила: правило одно, и составной идёт
за ним, если оно изменится. Обёртка не меняет, куда идёт ошибка: наблюдатель,
который в одиночку отдаёт брошенный `Cancelled` в зону, отдаёт его туда
и внутри составного. Список обходится один раз и копируется. `answer` нет:
отвечают `Solo.onUnanswered` и `Solo.errorHandler`, наблюдатель не отвечает
ни за что.

`flutter_solo` своего наблюдателя не имеет и получает `MultiSoloObserver`
реэкспортом `solo`.

   первого; второй по образцу.

## Открытый вопрос владельцу: имя

`MultiJobObserver` и `MultiSoloObserver` — отдельные публичные типы. Другой
путь — фабрика на базовом типе, `JobObserver.all([...], answer: ...)`
и `SoloObserver.all([...])`, с приватной реализацией. Зонд 2026-10-01 на Dart
3.6.0 и 3.13.0: `abstract mixin class` принимает фабрику и только тривиальный
генеративный конструктор; фабрика без явного `JobObserver();` отнимает
конструктор по умолчанию у каждого `extends JobObserver`, с явным — собираются
и `extends`, и `with`. Дизайн до решения пишет `MultiJobObserver`; поведение
от имени не зависит.

## Ревью

Независимый ревьюер на Opus, 2026-10-01, по копии дерева на `f36d03d`: скелет
обоих классов по правилам дизайна, зонды тестами внутри пакетов на Dart 3.13
и на полу 3.6.0. Ниже его отчёт, к каждой находке — вердикт.

Что подтвердилось: на 3.6.0 `dart analyze lib` обоих пакетов чист, зонды
`async_job` 19 из 19, `solo` 3 из 3; языка новее 3.6 дизайн не требует.
Порядок: список по порядку, `answer` последним, его `onUnanswered` после всех
`onError`. Без `answer` при двух наблюдателях с телом по умолчанию строка
`zone:` одна; пустой список ведёт себя как задача без наблюдателя. Изоляция:
бросивший `onStart` не выключает следующих, `Cancelled` из `onLog` никуда
не уходит. Бросивший `onUnanswered` у `answer` изолирует обёртка ядра `_notify`
(`job_base.dart:1301`). `ArgumentError` на `answer` в списке срабатывает,
правка исходного списка ничего не меняет, ребёнок наследует составного
(`job_context.dart:1424`). `MultiSoloObserver`: семь хуков по порядку,
бросивший не выключает второго. Блокеров нет.

1. Нужно исправить. Составной с `answer`, положенный в список другого
   составного, молча теряет свой ответ: правило 2 обходит `onUnanswered`
   каждого из списка. Зонд
   `MultiJobObserver([MultiJobObserver([a], answer: inner)])` с ошибкой
   из `ctx.unattended` печатает

   списком. Обратный случай работает: составной в роли `answer` спрашивает
   свой. Решение — `ArgumentError` с советом передать такой составной как
