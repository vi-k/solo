# Project overview

По реализации это исполнительный примитив структурированной асинхронной
работы внутри одного Dart isolate. Сам пакет не ставит корневые задачи в
очередь и не сериализует произвольно созданные `Job`: каждая автостартующая
задача получает свою микротаску. Управление очередью, состоянием и правилами
остаётся у доменного движка. Это важное прочтение границы ядра, а не
предложение добавлять в него пул или параллельность.

| Компонент | Фактическая ответственность |
|---|---|
| `lib/jobs.dart` | Единственная публичная библиотека, реэкспорт типов и extension |
| `Job<T>`, `DeferredJob<T>` | Хэндл наблюдения и отмены; фабрики автоматического и ручного старта |
| `JobBase<T>` | Состояние задачи, запуск, завершение, дети, отмена, уборка и маршруты ошибок |
| `JobContext`, `JobContextBase` | Контрольные точки, четыре способа обращения с работой, регистрации и усыновление |
| `Outcome`, `Done`, `Failed`, `Cancelled`, `CancelReason` | Разделение успеха, ошибки и отмены; сохранение значений, причин и стеков |
| `JobStream.each` | Подписка, последовательная доставка, ранний буфер, связь с отменой и уборкой |
| `JobObserver` | Синхронные события старта, завершения, ошибки и пользовательского журнала |

Основной поток: фабрика создаёт задачу и запоминает зону для диагностики;
старт создаёт контекст и переводит статус в `running`; тело получает
контекст; движок фиксирует конец тела, ждёт детей, раскручивает уборку и
публикует исход. Фаза уборки внутренне отдельная, хотя публичный статус
ещё `running`. `done` отдаёт исход без ошибки, `value` превращает его
в значение либо исключение.

Отмена синхронно ставит пометку, каскадирует на детей и вызывает callbacks.
Ожидание `cancel()` завершается только вместе с задачей. `wait` прекращает
ожидание действия, `join` дожидается действия, `uncancellable` придерживает
отклоняемую отмену до выхода. `unattended` запускает работу в отдельной
error-zone и не присоединяет её к завершению. Ограничения прохождения
ошибочных future через такую границу явно описаны.

У ресурсов два режима: `dispose` выполняется при любом исходе, `discard`
при потере результата; регистрация принятого значения происходит до его
выдачи телу. Дети завершаются раньше родительской уборки. Позднее значение,
которое уже не могло попасть телу, убирается без условия по исходу.

Production-зависимость одна — `meta: ^1.15.0`; `fake_async`, `test`, `lints`
используются для разработки. В `lib` нет Flutter, I/O, сетевых клиентов,
сериализации или платформенных каналов. Заявленный минимум — Dart 3.6.

# Medium and low-severity findings

## 1. Отмена родителя внутри проверки старта пропускает нового ребёнка

**Severity: Medium. Confidence: high.**

**Место:** `packages/jobs/lib/src/job_context.dart:740–771`.
Существующий потребитель: `packages/solo/lib/src/job_context.dart:116–130`.

`run` проверяет `pendingCancel` до вызова `beforeChildStart`, а добавляет
ребёнка в `_children` после него. Если проверка синхронно отменяет родителя
и возвращает разрешение старта, каскад проходит по списку без этого ребёнка.
После возврата проверки ребёнок добавляется и запускается без отмены.

Это достижимо в текущем `solo`: `canStart` дочерней задачи вызывает
`ctx.job.cancel().ignore()` и возвращает `true`. Обязательной чистоты правил
не заявлено; `packages/solo/test/start_rules_test.dart:262–289` прямо
проверяет `close()` внутри `canStart` для корневой задачи.

Ребёнок с `ctx.wait(() => neverCompletes)` остаётся работать под помеченным
родителем. Родитель ждёт его, а повторный `cancel()` уже не каскадирует
из-за установленной пометки. Поэтому `parent.cancel()` может не завершиться;
аналогичный путь через `solo.close()` задерживает закрытие контроллера.
Нарушено обещание отмены детей и отказа в старте под отменённым родителем.

**Направление исправления:** повторно проверить отмену и жизненный цикл
родителя после пользовательской проверки, до старта; закрыть уже
усыновлённого ребёнка без исполнения и передать отмену в тело. Проверить
callback с отменой родителя и callback с закрытием существующего потребителя.
Внешний зонд `beforeChildStart cancellation drops the child` подготовлен,
но не исполнен.

**Вердикт.** Подтверждено прогоном. Зонд F1 (`verify_probes_test.dart` в
`.artifacts/2026-09-08-jobs-review/`): контекст, чьё `beforeChildStart`
вызывает `job.cancel()` и возвращает `null`, ребёнок с `wait(delay(1000))`.
Вывод: ребёнок дошёл до `Done(null)`, а родитель получил `Cancelled(manual)`
только после того, как отработала вся тысяча миллисекунд ребёнка. То есть
каскад его не тронул, и родитель ждал того, кого должен был отменить.
Механика в находке описана верно. Решение о правке за владельцем.

## 2. Перенесённый во второй проход `discard` больше нельзя снять

**Severity: Medium. Confidence: high.**

**Место:** `packages/jobs/lib/src/job_base.dart:779–796`;
`packages/jobs/lib/src/job_context.dart:611–613,625–636`.

При потенциальном `Done` первый проход переносит условные уборщики
из `_cleanups` в локальный `skipped`. Функция снятия регистрации и
`disown(value)` продолжают искать только в `_cleanups`. Регистрация ещё
жива и может исполниться после поздней отмены, но для публичного механизма
снятия она уже исчезла.

Минимальная последовательность, выведенная из кода:

```dart
late void Function() unregister;
final resource = Object();
final job = Job<Object>((ctx) async {
  ctx.onDispose(() {
    unregister();
    ctx.job.cancel().ignore();
  });
  unregister = ctx.onDiscard(() => print('unexpected cleanup'));
  return resource;
});
await job.done;
```

Сначала `onDiscard` откладывается на потенциальном успехе. Нижний уборщик
вызывает `unregister`, который ничего не снимает, затем отменяет задачу.
Второй проход всё равно вызывает `unexpected cleanup`. У параметрической
регистрации тот же дефект: `disown(resource)` возвращает `false`, хотя
уборщик ещё ожидает исполнения.

Работа регистраций и `disown` в фазе уборки разрешена публичным контрактом
и `2026-09-07[1]-dispose-design.md`. Последствия — освобождение переданного
ресурса или повторная уборка вопреки снятию регистрации. Текущие тесты
проверяют снятие и второй проход отдельно, но не их пересечение.

**Направление исправления:** сохранить доступность всех ожидающих
регистраций для удаления, включая отложенные. Флаг активности достаточен
для remover, но `disown` также нужен доступ к этим регистрациям. Два
соответствующих внешних зонда подготовлены, не исполнены.

**Вердикт.** Подтверждено прогоном. Зонд F2 воспроизводит
последовательность из находки дословно. Вывод: `disown: false`, и следом
`discard ran`. Снятие регистрации молча не сработало, а уборщик исполнился —
ровно то, что описано. Решение о правке за владельцем.

## 3. Ошибка диагностического канала разрывает жизненный цикл

**Severity: Medium. Confidence: high.**

**Место:** `packages/jobs/lib/src/job_base.dart:290–294,542–546,596–601`;
вызовы диагностики в `706–713`.

`_debug` без защиты вычисляет сообщение и вызывает `JobBase.debug`.
Вычисление включает пользовательские `describe()` и `toString()`.
Диагностика вызывается между обязательными переходами жизненного цикла.

При `JobBase.debug = (_) => throw StateError('logger')` ручной `start()`
устанавливает `running`, затем бросает из `_notifyStart`, не дойдя до
`_execute`. Тело не запущено, а завершить задачу некому. Если logger бросает
только на сообщении `finished`, статус и исход уже установлены, но
`_done.complete` не вызывается: `isFinished == true`, тогда как `done`,
`value` и ожидание родителя остаются незавершёнными.

Даже исправный logger не защищает от бросающего `describe` или
`Done.value.toString`. Сбой возникает только при включённом канале;
это ограничивает вероятность, но не последствия. Тесты `debug_test.dart`
проверяют содержание сообщений, не устойчивость к их ошибкам.

**Направление исправления:** изолировать и построение, и доставку
диагностического сообщения, чтобы их ошибка не прерывала запуск,
завершение, отмену или основной маршрут ошибки. Проверить оба перехода
и бросок при форматировании. Внешний зонд завершения подготовлен,
не исполнен.

**Вердикт.** Подтверждено прогоном, и последствие тяжелее, чем названо в
находке. Зонд F3, `JobBase.debug` бросает на сообщении `finished`. Вывод:
`isFinished: true, outcome: Done(null)`, при этом `done` **не завершилась
никогда**, а зона получила `Bad state: logger`. Задача выглядит законченной
по всем публичным признакам, но `await job.done` и ожидание родителя висят
вечно. Решение о правке за владельцем.

## 4. Синхронный результат `wait` проходит в тело после отмены внутри действия

**Severity: Medium. Confidence: high.**

**Место:** `packages/jobs/lib/src/job_context.dart:648–657`;
асинхронная защита для сравнения — `710–717`.

После `action()` синхронная ветка не смотрит на отмену и возвращает
значение. Ветка `Future<T>` через `_race` проверяет отмену, произошедшую
во время вызова действия.

```dart
final job = Job<void>((ctx) async {
  final value = await ctx.wait(() {
    ctx.job.cancel().ignore();
    return 7;
  });
  print('continued: $value');
});
```

По трассировке текущей реализации `print` достижим, хотя пометка поставлена
до возврата результата. При возврате `Future<int>` вместо `int` в том же
сценарии ожидание заканчивается отменой. Для API с `FutureOr<T>` поведение
может различаться между попаданием в кэш и асинхронной загрузкой.

Дартдок `wait:41–45` обещает прерывание ожидания, если отмена пришла во
время действия. Здесь тело продолжает побочные действия, а конечный
`Cancelled` скрывает это от вызывающего. Ресурс тоже выдаётся в тело
вместо маршрута значения, которое не должно было туда попасть.

**Направление исправления:** обработать уже установленную отмену и в
синхронной ветке, сохранив уборку потерянного значения. Не расширять
попутно семантику `wait` до дополнительной проверки правил домена без
необходимости. `waiting_test.dart:227–253` проверяет эту реентерабельность
только с future; внешний синхронный зонд подготовлен, не исполнен.

**Вердикт.** Подтверждено прогоном. Зонд F4, код из находки дословно.
Вывод: `[continued: 7, outcome: Cancelled(manual)]` — тело получило значение
и продолжило после того, как само же поставило пометку. Асимметрия с ветвью
`Future` реальна. Решение о правке за владельцем.

## 5. Отмена из `onError` скрывает ошибку, которая случилась раньше неё

**Severity: Medium. Confidence: high.**

**Место:** `packages/jobs/lib/src/job_base.dart:739–742,800–804`.

`failedFirst` вычисляется после `notifyObserver`. Наблюдатель получает
хэндл и может синхронно вызвать `job.cancel()` из `onError`. Тогда ошибка
тела уже произошла, но после возврата callback движок записывает
`failedFirst == false`, как будто отмена была раньше.

Задача заканчивается `Cancelled`, а `_reportCovered` не вызывается.
Если исход никто не наблюдал, первоначальная ошибка не достигает зоны.
Сам факт вызова observer по принятому контракту наблюдением исхода
не считается.

Это дефект исполнения принятого решения о поздней отмене.
`2026-09-07[8]-jobs-fixes-review.md`, находка 1, требует фиксировать
пометку в момент падения; `2026-09-07[10]-jobs-narrow-review-2.md`,
находка 8, отдельно закрепляет одинаковые условия при наличии observer.

**Направление исправления:** сохранить признак порядка до пользовательских
callback-ов. Проверить `onError → job.cancel()` для ненаблюдённого исхода
и сохранить противоположный сценарий ошибки после уже принятой отмены.
Внешний зонд подготовлен, не исполнен.

**Вердикт.** Подтверждено прогоном. Зонд F5: наблюдатель из `onError`
зовёт `job.cancel()`, исход никто не наблюдает. Вывод: `observer errors:
[Bad state: boom]`, `zone caught: []` — ошибка в зону не ушла. Дартдок
`_reportCovered` обещает те же условия, что у обычного провала, и отдельно
оговаривает «whether or not there is an observer»; здесь наличие
наблюдателя, который отменяет, эти условия отменяет. Решение о правке за
владельцем.

## 6. Перекрытая ошибка уходит в зону до обещанного окна наблюдения

**Severity: Medium. Confidence: high.**

**Место:** `packages/jobs/lib/src/job_base.dart:800–825`;
обычный маршрут для сравнения — `596–604,872–883`.

`_reportCovered` вызывается до `finish` и синхронно передаёт ошибку зоне.
Обычный `_reportUnobserved` работает после `finished`, `onFinish` и
завершения `_done`, затем предоставляет микротаску для наблюдения.

Сценарий: тело падает при работающем ребёнке, затем родителя отменяют.
Observer реализует `onFinish(job) { job.ignore(); }` или читает там
`job.done`. Для обычного `Failed` такой обработчик успевает принять исход.
Для перекрытой ошибки зона получает исключение раньше вызова `onFinish`.
Даже синхронное наблюдение при завершении оказывается поздним.

Контракт `_reportCovered:813–819` обещает те же условия, что для обычного
провала; правила наблюдения также допускают подключение при завершении.
Последствия — необработанная ошибка в зоне при существующем обработчике,
ложный crash report или завершение isolate с обычной корневой зоной.
Принятое решение отправлять ненаблюдённую перекрытую ошибку в зону
не требует этой разницы в порядке.

**Направление исправления:** выровнять момент сообщения и отсрочку
с обычным провалом. Тест `zone_test.dart:273–289` с наблюдением после
завершения покрывает лишь обычный `Failed`; внешний зонд перекрытого
случая подготовлен, не исполнен.

**Вердикт.** Подтверждено прогоном. Зонд F6, наблюдатель зовёт
`job.ignore()` из `onFinish`. Вывод: `order: [onFinish, zone, onFinish]` —
зона получила ошибку между `onFinish` ребёнка и `onFinish` самой задачи, то
есть раньше, чем обработчик смог принять исход. Для обычного `Failed` тот же
обработчик успевает. Решение о правке за владельцем.

## 7. Пример Cleanup закрывает БД, пока миграция ещё работает

**Severity: Medium. Confidence: high.**

**Место:** `packages/jobs/README.md:244–254`, особенно строка 251.
Тот же код присутствует в `README.ru.md`.

Фрагмент приобретает lock с `dispose`, открывает БД с `discard`, затем
вызывает `await ctx.wait(database.migrate)`. При отмене во время миграции
`wait` отпускает действие, тело заканчивается и движок закрывает БД и
освобождает lock. Миграция при этом может продолжать писать.

Это нарушает условия безопасного владения самим примером. README:86–89
прямо объясняет, что для миграции нужен `join` именно по этой причине.
Возможны запись в закрытую БД, ошибка операции и доступ следующего
владельца ресурса одновременно с оставшейся миграцией. Ошибка находится
в учебном фрагменте, а не в принятой семантике `wait`.

**Направление исправления:** применить `join` в этом фрагменте обоих
языков. Проверить отмену именно во время миграции, с журналом порядка
`migration end → database close → lock release`. Во внешнем стенде блок
собран с БД, отмечающей закрытие; исполнение не состоялось.

**Вердикт.** Подтверждено чтением, и это самая неприятная находка круга:
README противоречит сам себе. Строка 251 показывает
`await ctx.wait(database.migrate)`, а строки 86–89 того же файла объясняют,
что здесь нужен именно `join`, и почти теми же словами описывают вред от
`wait`. Фрагмент учебный, и новичок скопирует его. Правится в обоих языках
одним словом. Решение о правке за владельцем.

## 8. `onCancel` не объясняет, что ошибка async-callback обходит observer

**Severity: Low. Confidence: high.**

**Место:** `packages/jobs/lib/src/job_context.dart:187–206,578–590`.

Сигнатура `void Function()` допускает передачу функции, возвращающей
`Future<void>`. Естественное `ctx.onCancel(device.stop)` для асинхронного
`stop` поэтому не заставляет пользователя явно выбрать другой механизм.
`guarded` игнорирует возвращённую future и ловит только синхронный бросок.
Асинхронная ошибка становится необработанной ошибкой зоны, из которой
вызван callback, даже при установленном job observer.

Справка без оговорки обещает маршрут ошибки callback в `onError` и
упоминает подписку среди способов применения. Для асинхронного
`StreamSubscription.cancel` риск тот же. Нужный рецепт уже существует:
`ctx.onCancel(() => ctx.unattended(device.stop))`, но находится в длинном
описании другого метода, `unattended`, и не связан ссылкой с `onCancel`.

Severity снижена до Low: синхронная модель callback сама по себе
последовательна, безопасный способ существует; дефект — локально неполный
контракт и молчаливая ловушка на естественном вызове. Последствие ошибки
пользователя, однако, может быть серьёзным.

**Направление исправления:** явно описать синхронность у `onCancel`,
границу обработки ошибок и показать безопасную обёртку рядом. Альтернатива
— принимать `FutureOr<void>` и отдельно наблюдать позднюю ошибку, не
задерживая саму маркировку. Менять выбранную модель отмены не требуется.

**Вердикт.** Подтверждено чтением. `void Function() onCancel(void
Function() callback)`: в Dart `void` в позиции возвращаемого типа принимает
что угодно, поэтому `Future<void> Function()` присваивается туда молча —
это тот же механизм, что в правиле «Async-обработчик в listen» скилла
`dart`. Дартдок обещает маршрут ошибки колбэка в `onError` без оговорки о
синхронности, а пример в нём (`ctx.onCancel(token.cancel)`) — ровно та
форма, которая ломается, если `cancel` окажется асинхронным. Решение о
правке за владельцем.

## 9. Ранний буфер `each` проигрывается за квадратичное время

**Severity: Low. Confidence: high для сложности; время не измерялось.**

**Место:** `packages/jobs/lib/src/job_stream.dart:166–172`.

Каждое `early.removeAt(0)` сдвигает оставшийся growable List. При `n`
ранних событиях суммарно перемещается `n(n−1)/2` элементов. Для 100 тысяч
событий это 4 999 950 000 перемещаемых ссылок, а не измеренная длительность.

Триггер соответствует уже поддержанному и тестируемому источнику:
синхронный broadcast-контроллер выдаёт накопленный batch из `onListen`
(`each_test.dart:369–403`). При большом batch CPU растёт непропорционально,
задерживая другую работу isolate. Обычные короткие потоки такого расхода
не создают, поэтому Low.

**Направление исправления:** сохранить принятый буфер, заменив извлечение
на `ListQueue.removeFirst` либо последовательный индекс с освобождением
обработанных ссылок. Проверить порядок и отмену на прежних сценариях,
отдельно измерить крупный replay. Возвращаться к `asyncMap` не предлагается.

**Вердикт.** Подтверждено замером, которого у ревьюера не было. Зонд F9:
синхронный broadcast-контроллер выдаёт 20 000 событий из `onListen`, все
попадают в ранний буфер. Вывод: `delivered=20000 in 371 ms` — 20 тысяч
событий, четверть секунды процессорного времени на одни сдвиги списка, и
рост квадратичный. Замена `removeAt(0)` на `ListQueue.removeFirst` или
индекс убирает это без смены принятого решения о буфере. Решение о правке за
владельцем.

## 10. Публичные формулировки маршрутов `Cancelled` расходятся с кодом

**Severity: Low. Confidence: high.**

**Место:** `packages/jobs/README.md:131–134`;
`packages/jobs/lib/src/observer.dart:25–33`.

README утверждает, что после пометки отмену бросает каждый член контекста.
На деле `onDispose`, `onDiscard`, `disown`, `unattended`, `log`, `job`
продолжают работать; точный контракт уже есть в `JobContext:5–23`.
Пользователь, рассчитывающий на такую контрольную точку, например в
`unattended` после пойманной отмены, запустит новое действие.

Справка `onError` без ограничения относит отмену ребёнка из `child.value`
к событиям observer. В обычном теле она попадает в `catch Cancelled`
(`job_base.dart:733–738`) и становится `Cancelled(handler)` без `onError`.
Маршрут к observer появляется в другом контексте — например в уборщике
или unattended-работе. Перечисление «three cases» также не исчерпывает
`Cancelled`, который может бросить уборщик или callback отмены.

Последствия — неверный выбор контрольной точки и неправильные ожидания
от журнала ошибок. Это неточность справки; исправлять соответствующую
принятым решениям семантику ради текста не нужно.

**Направление исправления:** назвать группы членов и условия маршрутов
по контексту возникновения; обновить перевод README одновременно.

**Вердикт.** Подтверждено чтением, обе половины. README:131–133 обещает,
что после пометки бросает «every context member», — а `onDispose`,
`onDiscard`, `disown`, `unattended`, `log` и `job` продолжают работать, и у
`unattended` это не случайность, а зафиксированное подменой свойство (см.
`2026-09-08[6]-unattended-plan.md`). Дартдок `JobObserver.onError`
перечисляет три случая `Cancelled`, и отмена ребёнка из `child.value` в
обычном теле среди них лишняя: она уходит в `_handlerCancel` и становится
исходом, не пройдя через `onError`. Перечисление к тому же не закрывает
`Cancelled`, брошенный уборщиком или колбэком `onCancel`. Решение о правке
за владельцем.

# Architecture review

Граница ядра выдержана. В `solo` правила и очередь опираются на `JobBase`,
а не реализуют второй lifecycle. `JobContextBase.check` даёт полезную
точку расширения для доменных правил; protected API в основном описывает
обязанности наследника и способы безопасного доступа. Недостающих
`owner`/`parent` для рассмотренного потребителя не обнаружено.

Связность внутри ядра высокая и оправданная: задача, контекст и исходы
составляют одну Dart library с `part`. Они используют приватное состояние
друг друга. Импорты `job_base.dart` и `observer.dart` образуют небольшой
цикл библиотек, отражающий двусторонний контракт Job/Observer; конкретного
дефекта загрузки или расширения из него не найдено. `each` остаётся
отдельным адаптером поверх публичного `JobContext`.

Слабое место — переходы состояния вокруг пользовательских callback-ов.
Усыновление, уведомление ошибки, диагностическое сообщение и снятие
регистрации выглядят локально короткими действиями, но вызывающий код
может отменить задачу, поменять владение или бросить. Находки 1–6
показывают, что именно эти пересечения требуют более явных гарантий.
Полной замены движка или новых публичных классов это не требует.

Скрытая фаза уборки в текущей модели нужна: она запрещает телу запускать
новую работу, сохраняя регистрацию поздних ресурсов. Локальный список
`skipped`, однако, стал вторым хранилищем живых регистраций вне области
видимости контекста — источник находки 2. Представление ещё ожидающих
уборщиков должно оставаться единым с точки зрения удаления.

Сознательные ограничения владельца не включены в дефекты: удержание отмены
в `uncancellable`, отсутствие каскада при обычном падении тела, приоритет
поздней отмены, непубличный `isDisposing`, отдельный хэндл, выбранный буфер
`each`, имя пакета и временно недоступные ссылки. Зоны unattended
рассмотрены с учётом `2026-09-08[4]-detached-design.md`.

**Отдельная неясность формулировки, не требование смены решения.**
`2026-09-08[10]-zone-cancelled-report.md` описывает отсутствие `Cancelled`
во всех маршрутах движка. `_toZone` действительно фильтрует четыре
бездомных маршрута и `reportToZone`; намеренный `Failed(Cancelled)`
сохраняет исключение. Но `_notify` (`job_base.dart:301–305`) по-прежнему
отправляет любой бросок observer hook, включая `Cancelled`, прямо в текущую
зону. Это соответствует другому явному контракту из `observer.dart:5–7`.
Нужно различать ошибку работы и сбой наблюдателя: абсолютная формулировка
не описывает последний путь. Намерение распространять новый фильтр также
на сломанный observer из записей однозначно не устанавливается; поведения
я не менял и новой общей политики здесь не предлагаю.

# Testing review

Тесты охватывают жизненный цикл, исходы и стеки, отмену до старта и во
время работы, вложенные защищённые секции, детей, поздние значения,
регистрации уборки, ошибки наблюдателя, stream-паузы, ранние события и
границы unattended-зон. Они используют `FakeAsync`, сравнивают журналы,
проверяют порядок, идентичность ошибок, факт старта и закрытие ресурсов.
Это содержательная база, а не набор проверок одних getters.

Не хватает пересечений уже проверяемых свойств:

| Риск | Что есть | Какой сценарий добавить |

| № 1: ребёнок переживает отмену | Отменённый родитель; бросившее правило; close из корневого canStart | Отмена родителя из успешного beforeChildStart, затем незавершающийся ребёнок |

Мутационные результаты прошлых записей не выдаются за результаты этой сессии.

# Performance and reliability

Для небольшого дерева и умеренного числа ресурсов алгоритмы простые:
регистрация — добавление в список, обычная уборка — снятие с конца,
ожидание детей — сбор их futures. `whenDone` отделяет внутреннее ожидание
от наблюдения и не глушит ошибки детей. Нет лишних таймеров для самого
старта задачи.

Подтверждённая асимптотическая проблема большого раннего replay — находка 9.
Дополнительно `parent._children.remove(this)` (`job_base.dart:583`) при
массовом завершении детей и `skipped.removeAt(0)` (`793`) допускают
квадратичную работу. Численных порогов и профиля нагрузки нет, поэтому
эти места отмечены как кандидаты для измерения, без отдельной severity.
Вместо общего benchmark стоит измерить большое число одновременно живых
детей, много условных уборщиков и replay из `onListen` отдельно.

Зафиксированные цены модели описаны достаточно честно: остановить чужую
future нельзя; `each` не ждёт уже исполняющийся обработчик после отмены;
cleanup источника может задержать объявление конца стрима; фоновый таймер
в unattended держит задачу и захваченные объекты. Это не новые утечки.
Бесконечное действие внутри `join`, неотменяемый ребёнок или уборщик,
ожидающий свой `job.done`, закономерно задерживают завершение.

**Неподтверждённые предположения:** не измерены heap/GC и удержание графа
при хранении завершённых дочерних хэндлов; `_parent` не очищается, но
объявлять это утечкой без сценария удержания и измерения нельзя. Не
проверялись нестандартные реализации Future, глубокий стек дерева,
длительная нагрузка и пропускная способность.

Поверхность безопасности мала: библиотека сама не читает секреты, не
парсит недоверенные данные и не открывает сеть. Подтверждённых
уязвимостей не найдено. Это оценка исходников данной версии, не аудит
зависимостей по базе известных уязвимостей. Практические риски здесь —
ошибки жизненного цикла и отказ в завершении, а не доступ к данным.

# Maintainability

Код небольшой по числу модулей, но сложный по состояниям. Имена приватных
методов обычно отражают обязанность; комментарии объясняют, почему нельзя
добавить await в определённое место, поменять порядок пометки или удалить
буфер. Эти объяснения полезнее косметического сокращения строк.

Область технического долга — повторяющиеся маршруты ошибок и неполная
атомарность переходов относительно callback-ов. `_reportCovered` и
`_reportUnobserved` обещают сходные условия, но уже расходятся в моменте
проверки; реестр cleanup разделился на два списка. Стоит формулировать
общие правила рядом с переходами и закрыть их наблюдаемыми тестами.
Разделять файлы ради размера или вводить новый слой абстракций оснований нет.

Публичный API в основном соответствует Dart: `abstract interface`
для получаемых типов, `sealed` исходы, `FutureOr` для синхронных действий,
`@protected`/`@mustCallSuper` для расширения. Правило не бросать из
`started()` явно написано — его сознательная обязанность наследника
не дублируется как находка.

Серьёзного мёртвого кода и ненужных production-зависимостей не выявлено.
Большой шаблон `analysis_options.yaml` содержит Flutter-ориентированные
правила и исключения, не относящиеся к этому пакету; измеримого дефекта

вес сжатого архива в фактическом dry-run — 62 KB; это не проблема размера.

# User's view

## Первое знакомство и README подряд

Первый экран отвечает на вопрос, зачем пакет: отдельный исход, дети,
кооперативная отмена и доставка ненаблюдённой ошибки. Сразу сказано,
что хэндл не Future и ждать следует `done`/`value`. Это хорошие входные
опоры. Словосочетание «waiting family» пока ничего не объясняет;
короткая таблица поведения помогла бы раньше большого примера.

Различие с голой Future понятно. С `CancelableOperation` сравнение менее
точно: фраза «ends the waiting the same way» скрывает важную деталь.
В установленном `async 2.13.0`, `lib/src/cancelable_operation.dart:105–110,
130–144`, `value` после отмены не завершается, а `valueOrCancellation`
позволяет получить значение отмены. `ctx.wait` завершает ожидание
исключением `Cancelled`; `job.done` — отдельным исходом. Это сравнение
прочитано по локальному коду зависимости, без предположений о будущих
версиях пакета.

Quick start полезен для ресурсной отмены, но требует усвоить сразу
`join`, `discard`, `uncancellable`, delayed start и исход. Комментарии
после него объясняют решения. Затем идут исходы, отмена, дети и уборка —
порядок в целом рабочий. Абсолютное «body must never await anything by
itself» приходится мысленно согласовывать с последующим `await child.value`
и прямым `await Database.open()`; лучше прямо назвать разрешённые
исключения, которые README сам использует.

В Cleanup обнаружен небезопасный код № 7. В Testing название теста
обещает закрытие открытой БД, но единственный `expect` проверяет
`Cancelled` (README:366–379). Само ядро имеет тесты закрытия; замечание
здесь к учебному примеру: новичку полезнее показать и счётчик закрытий,
чтобы он не принял правильный исход за доказательство уборки.

## Пакетный пример

`example/example.dart` прочитан целиком и дважды запущен командой
`dart run example/example.dart`. Оба раза выполнение остановилось на
телеметрии, поэтому строки `database closed` и `Cancelled(manual)`
**не наблюдались**. По исходнику открытие занимает 50 ms, отмена
запрошена через 10 ms, `join` должен дождаться открытия и передать БД
в `discard`; это объясняет ожидаемый вывод, но не заменяет его прогон.

Как первое впечатление пример удачен для проверки отмены открывающегося
ресурса. Он не демонстрирует успешное получение БД; миграция и markReady
в этом конкретном сценарии не достигаются. Мне после него нужен ещё один
короткий запуск: успех → получение значения → явное закрытие новым
владельцем. Это улучшение обучения, не отдельная severity-находка.

## Эргономика и ошибки новичка

| Член | Что нужно понять до использования |
|---|---|
| `wait` | Отменяет ожидание, действие продолжает работать |
| `join` | Ждёт окончание действия и отдаёт отмену после него |
| `uncancellable` | Придерживает отмену; хвост, обязанный выполниться, должен быть внутри секции |
| `unattended` | Работа живёт отдельно, имеет error-zone границу и может удерживать задачу |
| `each` | Ждёт поток, сериализует onData; отмена не дожидается уже работающего обработчика |
| `onDispose` / `onDiscard` | Любой исход против потери результата; неправильный discard течёт на успехе |
| `disown` | Передача владения, поиск по идентичности; `false` означает отсутствие найденной регистрации |
| `check` | Явная контрольная точка; в cleanup даёт StateError |
| `onCancel` | Синхронная доставка отмены в реальный механизм остановки; async требует отдельной обёртки |

Имена становятся понятны после объяснения, но по одному `wait`/`join`
семантику угадать трудно. Наиболее вероятные ошибки не дают полезного
`StateError` вообще: `await job` не ждёт завершения, `discard` для
временного ресурса не исполняется на успехе, async-callback `onCancel`
оставляет необработанную future. Первые два свойства описаны и
не оспариваются как решения API; третьему посвящена находка 8.

Все явные `StateError` и `ArgumentError` в `lib` просмотрены. Сообщения
обычно называют задачу, действие и нарушенную фазу: `already running`,
`already finished`, `is disposing`, `has ended its body`, `inside
unattended work`. Ошибка о двух cleanup-параметрах сразу говорит, как
исправить вызов. Чужой child — `ArgumentError.value` с именем аргумента.
Без `key` в сообщении остаётся `Job()`, поэтому рецепт диагностики стоит
показывать с ключами. Оснований требовать отдельный адрес объекта во
всех сообщениях не найдено.

В `ctx.log` строковое представление сообщения вычисляется даже без
observer (`job_context.dart:783–784`), поэтому «no-op» в справке означает
отсутствие доставки, а не отсутствие вычисления. Для объекта с дорогим
или бросающим `toString` лучше передавать заранее выбранную строку;
существеннее для надёжности остаётся разрыв lifecycle из debug, № 3.

# Positive findings

- Единый lifecycle уже обслуживает настоящего потребителя; ядро не знает
  о состоянии и очереди `solo`.
- Исходы исчерпывающи для switch, а `value` сохраняет ошибку и стек.
- Внутреннее ожидание детей и отмены не притворяется наблюдением исхода.
- Родитель помечается до каскада; самоотменившееся тело закрывается для
  новых детей до вызовов их callback-ов.
- Родительские ресурсы живут до завершения детей; поздние значения
  имеют собственный обязательный маршрут уборки.
- Ошибка одного уборщика не подменяет исход и не прекращает следующие.
- `each` учитывает ранние события, паузы и отмену; его непростой буфер
  подкреплён тестами наблюдаемого порядка.
- Unattended-зоны маркируются отдельно для каждой задачи; проверка
  собственной отмены учитывает тип и идентичность.
- Production dependency одна; пакет самодостаточен по метаданным,
  README, лицензии и примеру; русский перевод исключён из архива.
