# Уборка, которую доводит до конца движок

## Откуда вопрос

Владелец, разобрав `ifCancelled` у задачи: до значения при отмене
пользователь не доберётся, при ошибке — тоже, так почему уборка не
автоматическая? И почему уборщик один и висит на задаче, когда тело
открывает не только тот ресурс, который возвращает?

Набросок владельца:

```dart
final job = Job<Database>((ctx) async {
  final database = await ctx.join(Database.open);
  ctx.onDispose = database.close;

  final transaction = await ctx.join(database.startTransaction);
  ctx.onDispose = () {
    database.close();
    transaction.rollback();
  };

  // ...
});
```

Набросок показывает и задачу, и обе её ловушки. Сеттер заменяет
предыдущего уборщика, поэтому второй пришлось собирать руками — и порядок
в нём перевёрнут: база закрывается до отката транзакции. А кто уборщика
ждёт и куда девается его ошибка, форма не говорит вовсе.

## Что уже есть

Три механизма, каждый про своё окно.

- **`ifCancelled` у `wait` и `join`** — значение вернулось из вызова, но до
  тела не доехало: отмена бросилась внутри вызова. `join` дожидается
  уборки перед броском, `wait` зовёт её поздно, и её не ждёт никто.
- **`ifCancelled` у задачи** — тело вернуло значение, а отмена накрыла его
  между `return` и завершением. Движок дожидается уборки до `finish`.
- **`try/finally` в теле** — всё остальное: и отмена, и ошибка. Движок
  дожидается его вместе с телом.

Автоматической уборки нет, но ручная есть, и `finally` покрывает оба
случая из вопроса: отмена приходит в тело броском `Cancelled`, ошибка —
своим броском, и то и другое раскручивает тело. Так это и записано сегодня
в README `solo`: «Once the body does hold the value, an ordinary `finally`
takes over».

## Чего у `try/finally` нет

1. **Он не масштабируется.** Два ресурса — вложенные `try`, три —
   пирамида. Набросок владельца именно про это.
2. **Уборка идёт голым `await`.** Задача уже отменена, поэтому любой член
   контекста откажет — включая `uncancellable`, который бросает на входе.
   Тело обязано это знать; в README про это отдельный абзац.
3. **`finally` работает раньше детей.** Тело раскрутилось — дети ещё живут
   и ещё пользуются ресурсом. Ровно поэтому `ifCancelled` у задачи зовётся
   после `_awaitChildren()`.
4. **`finally` не дотягивается за `return`.** Это окно закрывает
   `ifCancelled` у задачи, и только для возвращённого значения.

## Решение

Стек регистраций у задачи, который раскручивает движок. Два вида записи в
нём, и на них один словарь на весь пакет:

- **`dispose`** — убрать при любом исходе. Лок, временный файл, счётчик:
  на успехе тоже, иначе останется занят навсегда.
- **`discard`** — убрать, если значение никому не досталось. База, которую
  тело возвращает: на успехе она уходит наружу, и закрывать её тогда
  нельзя, а при отмене и при ошибке её не получит никто.

Регистрируют двумя способами, в зависимости от того, откуда взялось
значение.

### Значение пришло из вызова

```dart
Future<T> wait<T>(
  FutureOr<T> Function() action, {
  FutureOr<void> Function(T value)? dispose,
  FutureOr<void> Function(T value)? discard,
});

Future<T> join<T>(
  FutureOr<T> Function() action, {
  FutureOr<void> Function(T value)? dispose,
  FutureOr<void> Function(T value)? discard,
});
```

Правило одно: **не доехало до тела — убрать прямо здесь, доехало — положить
в стек.**

- Действие бросило — значения нет, уборщик не зовётся, ошибка идёт как
  раньше.
- Отмена бросилась внутри вызова, значение уже есть — уборщик зовётся на
  месте: `join` дожидается его перед броском, `wait` зовёт его, когда
  брошенное действие наконец вернулось, и не ждёт его никто. Это дословно
  нынешнее поведение `ifCancelled`.
- Значение доехало до тела — движок кладёт в стек запись со значением и
  уборщиком; `dispose` — «всегда», `discard` — «если исход не `Done`».
- Оба параметра сразу — `ArgumentError`.

Тело при этом пишет уборщика один раз, а закрыты оба окна:

```dart
final job = Job<Database>((ctx) async {
  final lock = await ctx.join(
    Lock.acquire,
    dispose: (lock) => lock.release(),
  );
  final database = await ctx.join(
    Database.open,
    discard: (database) => database.close(),
  );

  await ctx.wait(database.migrate);

  return database;
});
```

Перед `return` тело не делает ничего: намерение сказано один раз, там, где
ресурс захвачен. Раскрутка идёт в обратном порядке захвата, поэтому база
закроется раньше, чем отпустят лок, который её сторожил.

`return await ctx.join(Database.open, discard: (db) => db.close());` тоже
безопасен: переменную заводить не обязательно.

### Значение взялось иначе

```dart
/// Registers [disposer] to run when the job ends, whatever the outcome.
/// Returns a function that unregisters it.
void Function() onDispose(FutureOr<void> Function() disposer);

/// Registers [disposer] to run only if the job ends without handing its
/// value over: cancelled, or failed. Returns a function that unregisters
/// it.
void Function() onDiscard(FutureOr<void> Function() disposer);
```

Для того, что тело построило само, а не получило из вызова. Уборщик здесь
значения не принимает — он его захватывает.

### Снятие регистрации

```dart
/// Drops the cleanup registered for [value] by [wait] or [join].
/// Returns whether anything was dropped.
bool disown(Object value);
```

Снимают тем же, чем регистрировали: запись, сделанную членом, — функцией,
которую член вернул; запись, сделанную параметром, — значением. Записи
членов значения не несут, и `disown` их не видит; незнакомое значение —
не ошибка, просто `false`. Аргумент не нулевой: ресурс, которым тело
владеет, нулём не бывает, а у `join<T?>`, вернувшего `null`, и снимать
нечего — уборщик получит `null` и ничего не сделает.

Снятие нужно там, где тело распорядилось ресурсом само:

```dart
final transaction = await ctx.join(
  database.startTransaction,
  dispose: (transaction) => transaction.rollback(),
);

// ...

await ctx.join(transaction.commit);
ctx.disown(transaction);
```

Транзакция могла бы стоять и на `discard`: на успехе её коммитит тело, и
откатывать нечего. `dispose` со снятием строже — он ловит и забытый
коммит, потому что снятие лежит рядом с коммитом и забывается вместе с
ним: транзакция откатится, а не повиснет открытой. Второй случай снятия —
передача владения в середине тела: сокет уехал в пул, закрывать его больше
нельзя, `ctx.disown(socket)`.

### Одно значение — одна регистрация

Параметр и член создают **независимые** записи, поэтому

```dart
final socket = await ctx.join(Socket.connect, discard: (s) => s.close());
final unregister = ctx.onDiscard(socket.close);   // вторая запись!
```

при отмене отработают обе, а `unregister()` снимет только вторую — в пул
уедет закрытый сокет. Взять член рядом с параметром «ради функции снятия»
нельзя; для этого есть `disown`. В дартдоке это сказано прямо.

### Остальные правила регистрации

- **Один стек, раскрутка LIFO.** Оба вида ложатся в один список в порядке
  регистрации и снимаются с конца. Ошибка порядка из наброска здесь
  недостижима — порядок задаёт не автор, а стек.
- **Регистрация не отказывает отменённой задаче.** `onDispose`,
  `onDiscard` и `disown` работают на помеченной задаче — как `log` и
  `job`, которые и так ничего не начинают: отказывать в регистрации уборки
  значит вернуть ту самую ловушку «уборка идёт голым `await`».
  `StateError` они бросают только на завершённой задаче; идущая уборка их
  не закрывает — на этом стоит вложенная уборка.
- **Уборщик может зарегистрировать уборщика.** Стек раскручивается, пока
  не опустеет, поэтому вложенная уборка работает; это же делает её
  потенциально бесконечной, и в дартдоке это сказано прямо.
- **Условие `discard` проверяет движок, а не уборщик.** По итоговому
  исходу — `_pendingCancel ?? outcome`, — поэтому `Done`, накрытый
  пришедшей отменой, считается несостоявшимся. Это ровно нынешний случай
  `ifCancelled` у задачи.

### Где живёт

Стек — на `JobBase`, рядом с `_onCancel`. Запись — приватный класс с тремя
полями: уборщик, признак «всегда» и значение (у записей от членов его
нет). Функция снятия держит запись и убирает её по идентичности, как
`addCancelCallback` держит колбэк; `disown` ищет по `identical` значение.
`JobContextBase` даёт защищённый доступ, через него же пишут `wait` и
`join`; публичные `onDispose`, `onDiscard` и `disown` реализованы там же,
рядом с `onCancel`.

## Когда стек раскручивается

Место то же, где сегодня стоит `ifCancelled` у задачи (`job_base.dart`,
`_run`): тело кончилось → **дождались детей** → раскрутка стека →
`finish`. Порядок «дети раньше уборки» держится по той же причине, что и
сейчас: дети могут ещё пользоваться ресурсами родителя. Свои стеки они
раскрутили раньше — родитель их дождался.

Раскрутку **ждут**: `finish` зовётся на пустом стеке, поэтому `close()` у
`solo` дожидается освобождения, а `done` приходит уже после него.

`dispose` отрабатывает при любом исходе: `Done`, `Cancelled`, `Failed`.
`discard` — только когда значение никому не досталось.

К моменту раскрутки придержанных отмен не бывает: `uncancellable` закрывает
секцию в своём `finally`, а закрытие внешней секции придержанную отмену
применяет, — значит тело кончилось с уже помеченной задачей или с
непомеченной, третьего нет.

### Отмена, пришедшая внутрь уборки

Уборка — это `await`, поэтому отмена может прийти в неё: тело вернуло
значение, дети дожданы, стек раскручивается — и в этот момент `cancel()`.
Инвариант ядра говорит, что отмена, пришедшая до завершения, побеждает, и
`finish(_pendingCancel ?? outcome)` её применит. Но `discard`-уборщики,
снятые со стека раньше, когда исход был `Done`, окажутся пропущены — и
ресурс утечёт ровно там, где мы его чинили.

Поэтому: **пропущенный `discard` не выбрасывается, а откладывается.**
Условие проверяется в момент снятия со стека по живому
`_pendingCancel ?? outcome`; пропущенные ложатся в отдельный список; когда
стек опустел, движок смотрит ещё раз, и если отмена всё-таки пришла —
раскручивает отложенное вторым проходом. Меняться может только отмена
(`Failed` известен до раскрутки), поэтому проходов не больше двух и цикл
конечен.

Во втором проходе порядок относительно уже отработавших `dispose` не
сохраняется: отложенный `discard` отработает после уборщика, который
регистрировали раньше него. Это цена окна, и она мала — окно длиной в одну
уборку.

Альтернатива «закрыть дверь» — считать исход зафиксированным с началом
уборки, а отмену, пришедшую внутрь, поздней — отброшена: длину этого окна
задаёт пользовательский уборщик, и `await job.cancel()`, вернувшийся при
исходе `Done`, объяснить нечем.

### Чего раскрутка не касается

`finish(outcome)`, вызванный движком домена напрямую, по-прежнему не ждёт
детей и не зовёт уборку — это уже записано в его дартдоке. У задачи,
отменённой до старта, тело не бежало и стек пуст. `onCancel` к уборке
отношения не имеет: он срабатывает в момент пометки, задолго до неё.

## Ошибки и границы уборщика

**Ошибка уборщика идёт в `notifyError`** — наблюдателю, а без него в зону
создания задачи, — и на этом кончается. Исход она не трогает: провалившаяся
уборка не подменяет собой ни отмену, ни ошибку тела. Раскрутка
продолжается: следующий уборщик снимается со стека всё равно, как `finally`
не отменяется тем, что предыдущий бросил. Правило то же, что сегодня у
`ifCancelled`.

**Во время уборки контекст ведёт себя как у завершённой задачи.** Тела уже
нет, дети дожданы, исход по существу решён: `run`, `wait`, `join`,
`uncancellable` и `onCancel` бросают `StateError`, а `check`, `log` и `job`
остаются легальны. Это ровно тот набор, что уже записан в шапке
`JobContext` для пережившего задачу контекста; внутри ядра его держит
`throwIfFinished`, который теперь смотрит не только на завершённость, но и
на идущую уборку. `isFinished` при этом не трогается: он публичный, и врать
наружу до завершения нельзя.

Иначе получается уборщик, который на `Done` работает, а на `Cancelled`
бросает `Cancelled`, — ведёт себя по-разному в зависимости от того, чего
автор уборщика не контролирует. Заодно закрывается сегодняшняя дыра: из
`ifCancelled` сейчас можно позвать `ctx.run` и завести ребёнка **после**
того, как детей дождались, — он переживёт родителя, и никто его не ждёт.

Исключение — `onDispose`, `onDiscard` и `disown`: они остаются открыты, на
них стоит вложенная уборка.

**Зависший уборщик держит задачу, а с ней очередь и `close()`.** Он
работает вне тела: ни отмена, ни `onCancel` до него не дотягиваются,
остановить его нечем. Таймаута не будет; в дартдоке сказано прямо: уборщик
короткий и безусловный.

## Почему не другие формы

**Только `discard`, без «всегда».** Правило проще, и для главного пути
`scopo` («вернул построенное — движок освободит») бесплатно. Но ресурсы
второго вида на успешном выходе тело закрывает само, то есть `try/finally`
из тела никуда не девается и «одного механизма» не получается.

**Один вид записи, снимаемый функцией.** Идиома `onCancel` один в один,
учить нечего. Но снятие встаёт на главный путь `scopo` — перед каждым
`return` возвращаемого ресурса, — и его надо не забыть. Забыл — вызывающий
получает закрытую базу. Два вида стоят одного лишнего имени и снимают это
целиком: намерение сказано один раз, там, где ресурс захвачен.

**Уборщик получает исход и решает сам.** Одно имя, снятия нет, но условие
переезжает внутрь каждого уборщика: `if (outcome is! Done)` повторяется из
тела в тело, а модель исходов протекает в каждое замыкание уборки.

**Разделить окна между параметром и членом.** Параметр закрывает окно «не
доехало», член регистрирует уборку для «доехало» — и тело пишет одного и
того же уборщика дважды, двумя строками подряд. Совмещение дубль убирает,
потому что вызов держит значение в обоих случаях; отдельного имени
`ifCancelled` под этой формой не остаётся — это `discard`, у которого не
дошло до регистрации.

**Флаг в замыкании вместо `disown`.** Уборщик вида `(s) { if (owned)
s.close(); }` и `owned = false` при передаче владения — работает и не стоит
пакету ничего. Но возвращает в тело ту самую ручную бухгалтерию, ради ухода
от которой всё затевалось, и забытый `owned = false` — тихая ошибка.
`disown` стоит одного короткого члена и закрывает оба случая снятия.

**Параметры у `uncancellable`.** Не нужны: он всегда отдаёт значение, окна
«не доехало» у него нет, а значит и совмещать нечего — регистрация членом
следующей строкой читается так же.

`ctx.each` эта работа не трогает: он про время жизни подписки внутри тела,
и отписку ведёт через `onCancel`. Переезд `each` на стек — отдельный
вопрос, не этой записи.

## Что уходит

Ничего не опубликовано, ломать некого, поэтому начисто и без депрекейта:

- `ifCancelled` у `Job(...)`, `Job.deferred(...)` и у защищённого
  конструктора `JobBase`; поле `_ifCancelled` и его ветка в `_run` — на её
  месте раскрутка стека;
- `ifCancelled` у `wait` и `join` — на его месте `dispose` и `discard`;
- в `solo` — проброс `ifCancelled` через `SoloBase.run`, `SoloBase.job` и
  `solo`-шный `Job`;
- у `flutter_solo` своего кода тут нет, он только реэкспортирует.

## Что правится вокруг

## Тесты

Сначала красный, по конвенции проекта. `FakeAsync`, порядок событий — по
журналу наблюдателя.

- `onDispose` при `Done`, `Cancelled`, `Failed`; `onDiscard` молчит на
  `Done` и работает на двух других.
- LIFO на смешанном стеке: запись, сделанная позже, отрабатывает раньше.
- `join(dispose:)` и `join(discard:)`: значение доехало — уборщик лёг в
  стек и отработал в конце; отмена внутри вызова — уборщик отработал на
  месте, и `join` дождался его перед броском.
- `wait(discard:)` на позднем значении: уборщик зовётся, когда брошенное
  действие вернулось, и его не ждёт никто.
- Действие бросило — уборщик не зовётся, в стеке пусто.
- Оба параметра сразу — `ArgumentError`.
- `disown`: снимает запись параметра и возвращает `true`; на незнакомом
  значении и на записи, сделанной членом, — `false` и никаких снятий; на
  завершённой задаче — `StateError`.
- Параметр и член на одно значение: отрабатывают обе записи —
  документированное поведение, тест его фиксирует.
- Уборку ждут: `done` приходит после уборщика, `close()` у `solo` — тоже.
- Дети раньше уборки (нынешний `late_value_test.dart` переезжает на новый
  API).
- Отмена, пришедшая внутрь уборки: пропущенный `discard` отрабатывает
  вторым проходом. Проверяется мутантом: снимаем второй проход — тест
  краснеет.
- Ошибка уборщика: ушла наблюдателю, исход цел, следующий уборщик
  отработал.
- Снятие функцией: снятый не зовётся; двойное снятие и снятие после
  отработки безвредны.
- Регистрация на отменённой задаче работает; на завершённой — `StateError`.
- Во время уборки `run`, `wait`, `join`, `uncancellable`, `onCancel`
  бросают `StateError`; `onDispose` изнутри уборщика работает.
- Задача, отменённая до старта: стек пуст, уборки нет.

## Что делать

Порядок: ядро (реализация и тесты) → `solo` (снять проброс, поправить
тесты) → доки и переводы → записи и `handoff`.

Перед коммитом: `dart analyze` и `dart test` в `packages/jobs` и
`packages/solo`, `flutter test` в `packages/flutter_solo`, тесты примера —
`dart test` из `packages/solo/example/`, сверка переводов
(`python3 tool/check_translations.py`) из корня.
