# Уборка, которую доводит до конца движок

## Откуда вопрос

Владелец, разобрав `ifCancelled` у задачи: до значения при отмене
пользователь не доберётся, при ошибке — тоже, так почему уборка не
автоматическая? И почему уборщик один и висит на задаче, когда тело
открывает не только тот ресурс, который возвращает?

Набросок владельца:

```dart
final job = Job<Database>((ctx) async {
  final database = await ctx.join(Database.open);
  ctx.onDispose = database.close;

  final transaction = await ctx.join(database.startTransaction);
  ctx.onDispose = () {
    database.close();
    transaction.rollback();
  };

  // ...
});
```

Набросок показывает и задачу, и обе её ловушки. Сеттер заменяет
предыдущего уборщика, поэтому второй пришлось собирать руками — и порядок
в нём перевёрнут: база закрывается до отката транзакции. А кто уборщика
ждёт и куда девается его ошибка, форма не говорит вовсе.

## Что уже есть

Три механизма, каждый про своё окно.

- **`ifCancelled` у `wait` и `join`** — значение вернулось из вызова, но до
  тела не доехало: отмена бросилась внутри вызова. `join` дожидается
  уборки перед броском, `wait` зовёт её поздно, и её не ждёт никто.
- **`ifCancelled` у задачи** — тело вернуло значение, а отмена накрыла его
  между `return` и завершением. Движок дожидается уборки до `finish`.
- **`try/finally` в теле** — всё остальное: и отмена, и ошибка. Движок
  дожидается его вместе с телом.

Автоматической уборки нет, но ручная есть, и `finally` покрывает оба
случая из вопроса: отмена приходит в тело броском `Cancelled`, ошибка —
своим броском, и то и другое раскручивает тело. Так это и записано сегодня
в README `solo`: «Once the body does hold the value, an ordinary `finally`
takes over».

## Чего у `try/finally` нет

1. **Он не масштабируется.** Два ресурса — вложенные `try`, три —
   пирамида. Набросок владельца именно про это.
2. **Уборка идёт голым `await`.** Задача уже отменена, поэтому любой член
   контекста откажет — включая `uncancellable`, который бросает на входе.
   Тело обязано это знать; в README про это отдельный абзац.
3. **`finally` работает раньше детей.** Тело раскрутилось — дети ещё живут
   и ещё пользуются ресурсом. Ровно поэтому `ifCancelled` у задачи зовётся
   после `_awaitChildren()`.
4. **`finally` не дотягивается за `return`.** Это окно закрывает
   `ifCancelled` у задачи, и только для возвращённого значения.

## Решение

Стек регистраций у задачи, который раскручивает движок. Два вида записи в
нём, и на них один словарь на весь пакет:

- **`dispose`** — убрать при любом исходе. Лок, временный файл, счётчик:
  на успехе тоже, иначе останется занят навсегда.
- **`discard`** — убрать, если значение никому не досталось. База, которую
  тело возвращает: на успехе она уходит наружу, и закрывать её тогда
  нельзя, а при отмене и при ошибке её не получит никто.

Регистрируют двумя способами, в зависимости от того, откуда взялось
значение.

### Значение пришло из вызова

```dart
Future<T> wait<T>(
  FutureOr<T> Function() action, {
  FutureOr<void> Function(T value)? dispose,
  FutureOr<void> Function(T value)? discard,
});

Future<T> join<T>(
  FutureOr<T> Function() action, {
  FutureOr<void> Function(T value)? dispose,
  FutureOr<void> Function(T value)? discard,
});
```

Правило одно: **не доехало до тела — убрать прямо здесь, доехало — положить
в стек.**

- Действие бросило — значения нет, уборщик не зовётся, ошибка идёт как
  раньше.
- Отмена бросилась внутри вызова, значение уже есть — уборщик зовётся на
  месте: `join` дожидается его перед броском, `wait` зовёт его, когда
  брошенное действие наконец вернулось, и не ждёт его никто. Это дословно
  нынешнее поведение `ifCancelled`.
- Значение доехало до тела — движок кладёт в стек запись со значением и
  уборщиком; `dispose` — «всегда», `discard` — «если исход не `Done`».
- Оба параметра сразу — `ArgumentError`.

Тело при этом пишет уборщика один раз, а закрыты оба окна:

```dart
final job = Job<Database>((ctx) async {
  final lock = await ctx.join(
    Lock.acquire,
    dispose: (lock) => lock.release(),
  );
  final database = await ctx.join(
    Database.open,
    discard: (database) => database.close(),
  );

  await ctx.wait(database.migrate);

  return database;
});
```

Перед `return` тело не делает ничего: намерение сказано один раз, там, где
ресурс захвачен. Раскрутка идёт в обратном порядке захвата, поэтому база
закроется раньше, чем отпустят лок, который её сторожил.

`return await ctx.join(Database.open, discard: (db) => db.close());` тоже
безопасен: переменную заводить не обязательно.

### Значение взялось иначе

```dart
/// Registers [disposer] to run when the job ends, whatever the outcome.
/// Returns a function that unregisters it.
void Function() onDispose(FutureOr<void> Function() disposer);

/// Registers [disposer] to run only if the job ends without handing its
/// value over: cancelled, or failed. Returns a function that unregisters
/// it.
void Function() onDiscard(FutureOr<void> Function() disposer);
```

Для того, что тело построило само, а не получило из вызова. Уборщик здесь
значения не принимает — он его захватывает.

### Снятие регистрации

```dart
/// Drops the cleanup registered for [value] by [wait] or [join].
/// Returns whether anything was dropped.
bool disown(Object value);
```

Снимают тем же, чем регистрировали: запись, сделанную членом, — функцией,
которую член вернул; запись, сделанную параметром, — значением. Записи
членов значения не несут, и `disown` их не видит; незнакомое значение —
не ошибка, просто `false`. Аргумент не нулевой: ресурс, которым тело
владеет, нулём не бывает, а у `join<T?>`, вернувшего `null`, и снимать
нечего — уборщик получит `null` и ничего не сделает.

Снятие нужно там, где тело распорядилось ресурсом само:

```dart
final transaction = await ctx.join(
  database.startTransaction,
  dispose: (transaction) => transaction.rollback(),
);

// ...

await ctx.join(transaction.commit);
ctx.disown(transaction);
```

Транзакция могла бы стоять и на `discard`: на успехе её коммитит тело, и
откатывать нечего. `dispose` со снятием строже — он ловит и забытый
коммит, потому что снятие лежит рядом с коммитом и забывается вместе с
ним: транзакция откатится, а не повиснет открытой. Второй случай снятия —
передача владения в середине тела: сокет уехал в пул, закрывать его больше
нельзя, `ctx.disown(socket)`.

### Одно значение — одна регистрация

Параметр и член создают **независимые** записи, поэтому

```dart
final socket = await ctx.join(Socket.connect, discard: (s) => s.close());
final unregister = ctx.onDiscard(socket.close);   // вторая запись!
```

при отмене отработают обе, а `unregister()` снимет только вторую — в пул
уедет закрытый сокет. Взять член рядом с параметром «ради функции снятия»
нельзя; для этого есть `disown`. В дартдоке это сказано прямо.

### Остальные правила регистрации

- **Один стек, раскрутка LIFO.** Оба вида ложатся в один список в порядке
  регистрации и снимаются с конца. Ошибка порядка из наброска здесь
  недостижима — порядок задаёт не автор, а стек.
- **Регистрация не отказывает отменённой задаче.** `onDispose`,
  `onDiscard` и `disown` работают на помеченной задаче — как `log` и
  `job`, которые и так ничего не начинают: отказывать в регистрации уборки
  значит вернуть ту самую ловушку «уборка идёт голым `await`».
  `StateError` они бросают только на завершённой задаче; идущая уборка их
  не закрывает — на этом стоит вложенная уборка.
- **Уборщик может зарегистрировать уборщика.** Стек раскручивается, пока
  не опустеет, поэтому вложенная уборка работает; это же делает её
  потенциально бесконечной, и в дартдоке это сказано прямо.
- **Условие `discard` проверяет движок, а не уборщик.** По итоговому
  исходу — `_pendingCancel ?? outcome`, — поэтому `Done`, накрытый
  пришедшей отменой, считается несостоявшимся. Это ровно нынешний случай
  `ifCancelled` у задачи.

### Где живёт

Стек — на `JobBase`, рядом с `_onCancel`. Запись — приватный класс с тремя
полями: уборщик, признак «всегда» и значение (у записей от членов его
нет). Функция снятия держит запись и убирает её по идентичности, как
`addCancelCallback` держит колбэк; `disown` ищет по `identical` значение.
`JobContextBase` даёт защищённый доступ, через него же пишут `wait` и
`join`; публичные `onDispose`, `onDiscard` и `disown` реализованы там же,
рядом с `onCancel`.

## Когда стек раскручивается

Место то же, где сегодня стоит `ifCancelled` у задачи (`job_base.dart`,
`_run`): тело кончилось → **дождались детей** → раскрутка стека →
`finish`. Порядок «дети раньше уборки» держится по той же причине, что и
сейчас: дети могут ещё пользоваться ресурсами родителя. Свои стеки они
раскрутили раньше — родитель их дождался.

Раскрутку **ждут**: `finish` зовётся на пустом стеке, поэтому `close()` у
`solo` дожидается освобождения, а `done` приходит уже после него.

`dispose` отрабатывает при любом исходе: `Done`, `Cancelled`, `Failed`.
`discard` — только когда значение никому не досталось.

К моменту раскрутки придержанных отмен не бывает: `uncancellable` закрывает
секцию в своём `finally`, а закрытие внешней секции придержанную отмену
применяет, — значит тело кончилось с уже помеченной задачей или с
непомеченной, третьего нет.

### Отмена, пришедшая внутрь уборки

Уборка — это `await`, поэтому отмена может прийти в неё: тело вернуло
значение, дети дожданы, стек раскручивается — и в этот момент `cancel()`.
Инвариант ядра говорит, что отмена, пришедшая до завершения, побеждает, и
`finish(_pendingCancel ?? outcome)` её применит. Но `discard`-уборщики,
снятые со стека раньше, когда исход был `Done`, окажутся пропущены — и
ресурс утечёт ровно там, где мы его чинили.

Поэтому: **пропущенный `discard` не выбрасывается, а откладывается.**
Условие проверяется в момент снятия со стека по живому
`_pendingCancel ?? outcome`; пропущенные ложатся в отдельный список; когда
стек опустел, движок смотрит ещё раз, и если отмена всё-таки пришла —
раскручивает отложенное вторым проходом. Меняться может только отмена
(`Failed` известен до раскрутки), поэтому проходов не больше двух и цикл
конечен.

Во втором проходе порядок относительно уже отработавших `dispose` не
сохраняется: отложенный `discard` отработает после уборщика, который
регистрировали раньше него. Это цена окна, и она мала — окно длиной в одну
уборку.

Альтернатива «закрыть дверь» — считать исход зафиксированным с началом
уборки, а отмену, пришедшую внутрь, поздней — отброшена: длину этого окна
задаёт пользовательский уборщик, и `await job.cancel()`, вернувшийся при
исходе `Done`, объяснить нечем.

### Чего раскрутка не касается

`finish(outcome)`, вызванный движком домена напрямую, по-прежнему не ждёт
детей и не зовёт уборку — это уже записано в его дартдоке. У задачи,
отменённой до старта, тело не бежало и стек пуст. `onCancel` к уборке
отношения не имеет: он срабатывает в момент пометки, задолго до неё.

## Ошибки и границы уборщика

**Ошибка уборщика идёт в `notifyError`** — наблюдателю, а без него в зону
создания задачи, — и на этом кончается. Исход она не трогает: провалившаяся
уборка не подменяет собой ни отмену, ни ошибку тела. Раскрутка
продолжается: следующий уборщик снимается со стека всё равно, как `finally`
не отменяется тем, что предыдущий бросил. Правило то же, что сегодня у
`ifCancelled`.

**Во время уборки контекст ведёт себя как у завершённой задачи.** Тела уже
нет, дети дожданы, исход по существу решён: `run`, `wait`, `join`,
`uncancellable` и `onCancel` бросают `StateError`, а `check`, `log` и `job`
остаются легальны. Это ровно тот набор, что уже записан в шапке
`JobContext` для пережившего задачу контекста; внутри ядра его держит
`throwIfFinished`, который теперь смотрит не только на завершённость, но и
на идущую уборку. `isFinished` при этом не трогается: он публичный, и врать
наружу до завершения нельзя.

Иначе получается уборщик, который на `Done` работает, а на `Cancelled`
бросает `Cancelled`, — ведёт себя по-разному в зависимости от того, чего
автор уборщика не контролирует. Заодно закрывается сегодняшняя дыра: из
`ifCancelled` сейчас можно позвать `ctx.run` и завести ребёнка **после**
того, как детей дождались, — он переживёт родителя, и никто его не ждёт.

Исключение — `onDispose`, `onDiscard` и `disown`: они остаются открыты, на
них стоит вложенная уборка.

**Зависший уборщик держит задачу, а с ней очередь и `close()`.** Он
работает вне тела: ни отмена, ни `onCancel` до него не дотягиваются,
остановить его нечем. Таймаута не будет; в дартдоке сказано прямо: уборщик
короткий и безусловный.

## Почему не другие формы

**Только `discard`, без «всегда».** Правило проще, и для главного пути
`scopo` («вернул построенное — движок освободит») бесплатно. Но ресурсы
второго вида на успешном выходе тело закрывает само, то есть `try/finally`
из тела никуда не девается и «одного механизма» не получается.

**Один вид записи, снимаемый функцией.** Идиома `onCancel` один в один,
учить нечего. Но снятие встаёт на главный путь `scopo` — перед каждым
`return` возвращаемого ресурса, — и его надо не забыть. Забыл — вызывающий
получает закрытую базу. Два вида стоят одного лишнего имени и снимают это
целиком: намерение сказано один раз, там, где ресурс захвачен.

**Уборщик получает исход и решает сам.** Одно имя, снятия нет, но условие
переезжает внутрь каждого уборщика: `if (outcome is! Done)` повторяется из
тела в тело, а модель исходов протекает в каждое замыкание уборки.

**Разделить окна между параметром и членом.** Параметр закрывает окно «не
доехало», член регистрирует уборку для «доехало» — и тело пишет одного и
того же уборщика дважды, двумя строками подряд. Совмещение дубль убирает,
потому что вызов держит значение в обоих случаях; отдельного имени
`ifCancelled` под этой формой не остаётся — это `discard`, у которого не
дошло до регистрации.

**Флаг в замыкании вместо `disown`.** Уборщик вида `(s) { if (owned)
s.close(); }` и `owned = false` при передаче владения — работает и не стоит
пакету ничего. Но возвращает в тело ту самую ручную бухгалтерию, ради ухода
от которой всё затевалось, и забытый `owned = false` — тихая ошибка.
`disown` стоит одного короткого члена и закрывает оба случая снятия.

**Параметры у `uncancellable`.** Не нужны: он всегда отдаёт значение, окна
«не доехало» у него нет, а значит и совмещать нечего — регистрация членом
следующей строкой читается так же.

`ctx.each` эта работа не трогает: он про время жизни подписки внутри тела,
и отписку ведёт через `onCancel`. Переезд `each` на стек — отдельный
вопрос, не этой записи.

## Что уходит

Ничего не опубликовано, ломать некого, поэтому начисто и без депрекейта:

- `ifCancelled` у `Job(...)`, `Job.deferred(...)` и у защищённого
  конструктора `JobBase`; поле `_ifCancelled` и его ветка в `_run` — на её
  месте раскрутка стека;
- `ifCancelled` у `wait` и `join` — на его месте `dispose` и `discard`;
- в `solo` — проброс `ifCancelled` через `SoloBase.run`, `SoloBase.job` и
  `solo`-шный `Job`;
- у `flutter_solo` своего кода тут нет, он только реэкспортирует.

## Тесты

Сначала красный, по конвенции проекта. `FakeAsync`, порядок событий — по
журналу наблюдателя.

- `onDispose` при `Done`, `Cancelled`, `Failed`; `onDiscard` молчит на
  `Done` и работает на двух других.
- LIFO на смешанном стеке: запись, сделанная позже, отрабатывает раньше.
- `join(dispose:)` и `join(discard:)`: значение доехало — уборщик лёг в
  стек и отработал в конце; отмена внутри вызова — уборщик отработал на
  месте, и `join` дождался его перед броском.
- `wait(discard:)` на позднем значении: уборщик зовётся, когда брошенное
  действие вернулось, и его не ждёт никто.
- Действие бросило — уборщик не зовётся, в стеке пусто.
- Оба параметра сразу — `ArgumentError`.
- `disown`: снимает запись параметра и возвращает `true`; на незнакомом
  значении и на записи, сделанной членом, — `false` и никаких снятий; на
  завершённой задаче — `StateError`.
- Параметр и член на одно значение: отрабатывают обе записи —
  документированное поведение, тест его фиксирует.
- Уборку ждут: `done` приходит после уборщика, `close()` у `solo` — тоже.
- Дети раньше уборки (нынешний `late_value_test.dart` переезжает на новый
  API).
- Отмена, пришедшая внутрь уборки: пропущенный `discard` отрабатывает
  вторым проходом. Проверяется мутантом: снимаем второй проход — тест
  краснеет.
- Ошибка уборщика: ушла наблюдателю, исход цел, следующий уборщик
  отработал.
- Снятие функцией: снятый не зовётся; двойное снятие и снятие после
  отработки безвредны.
- Регистрация на отменённой задаче работает; на завершённой — `StateError`.
- Во время уборки `run`, `wait`, `join`, `uncancellable`, `onCancel`
  бросают `StateError`; `onDispose` изнутри уборщика работает.
- Задача, отменённая до старта: стек пуст, уборки нет.

## Дополнение 2026-09-07: ответы на ревью

Ревью `2026-09-07[2]-dispose-design-review.md`: критических находок нет,
форма API не меняется, но шесть мест основного текста ниже переписаны, а
четыре случая он не описывал вовсе. Где дополнение расходится с основным
текстом, верно дополнение.

### Третий случай правила: значение в завершённую задачу

Правило «не доехало до тела — убрать на месте, доехало — положить в стек»
знало два случая. Третий: тело не дождалось собственного вызова
(`unawaited(ctx.wait(...))`), задача закончилась, значение пришло потом.
По букве основного текста запись легла бы в стек мертвеца — и не убралась
бы никогда.

**Задача завершена — уборщик зовётся на месте, и его никто не ждёт**, как
сегодня зовётся поздний `ifCancelled` у `wait`. Во время **идущей уборки**
запись, наоборот, кладётся в стек: цикл раскрутки работает до опустошения
и снимет её, на этом же стоит вложенная уборка. Синхронный путь `wait`
(значение вернулось без `Future`) регистрирует так же, как асинхронный.

### Передача владения атомарна только под секцией

> Пересмотрено вторым дополнением: для `emit` секция не работает — там
> синхронная тройка `check`/`disown`/`emit`, — а правило «уборщик обязан
> терпеть» снято.

Оба примера со снятием в основном тексте небезопасны: между тем, как тело
распорядилось ресурсом, и `disown` стоит член контекста, а он бросает.
`await ctx.join(transaction.commit); ctx.disown(transaction);` — отмена,
пришедшая во время коммита, бросается из `join` **после** возврата
действия, `disown` не достигнут, и уборка откатывает закоммиченное.
Поменять строки местами нельзя: тогда при отмене транзакция уже снята со
стека, а откатить её некому. В `solo` та же форма ждёт `emit`: он
проверяет отмену и после записи состояния.

Идиома: **передача владения и снятие стоят в одной неотменяемой секции.**

```dart
await ctx.uncancellable(() async {
  await transaction.commit();
  ctx.disown(transaction);
});
```

`disown` внутри секции законен: он не отказывает и помеченной задаче.
Полной атомарности секция не даёт — неотклоняемые отмены (правила `solo`)
проходят сквозь неё, — поэтому рядом стоит второе правило, и оно
обязательное: **уборщик обязан терпеть вызов после того, как ресурс уже
отдан.** Откат закоммиченной транзакции, закрытие отданного сокета,
освобождение отпущенного лока — уборщик обязан отработать их без вреда.
Парный `join(..., disown: value)` отклонён: третье имя ради одного случая.

### Фаза уборки называется

> Пересмотрено вторым дополнением: `state`, `stateAs` и `check` в уборке
> не легальны, а закрыты, как `emit`.

Во время раскрутки задача не завершена (`isFinished` — `false`, статус —
`running`), но тела уже нет и исход решён. Фаза получает имя: защищённый
`isDisposing` на `JobBase` и `JobContextBase`, и своё сообщение
`StateError` — «is disposing, cannot …», а не «has already finished».
Нового значения `JobStatus` не заводим: перечисление публично, и `switch`
в `cancelWith` пришлось бы трогать.

Что делает надстройка домена в этой фазе:

- `emit` у `solo` **запрещён**: писать состояние после решённого исхода
  некуда;
- `state`, `stateAs` и `check` легальны, и то, что `_checkedState()` при
  разошедшихся правилах пометит задачу прямо из уборки, принято — это
  обычная отмена, пришедшая внутрь уборки, и её ловит второй проход;
- `progress` у `scopo` идёт по той же линии, что `emit`, — решать
  `scopo`.

### `isCancelled` в уборке говорит правду

Уборщик, зарегистрированный как `dispose`, может хотеть знать, каким
вышел исход (у `scopo` так устроен `disposeScope`). Спросить он может
только `ctx.job.isCancelled`: `outcome` до `finish` пуст. А `isCancelled`
лгал для тела, бросившего `Cancelled` самостоятельно: `_pendingCancel`
там остаётся пустым, отмену держит локальная переменная `_execute`.

Поэтому **перед раскруткой движок кладёт решённую отмену в
`_pendingCancel`** — включая случай `throw Cancelled` из тела. Тогда
`isCancelled` в уборке правдив и монотонен: `false` → `true` и никогда
обратно, а отмена, пришедшая внутрь уборки, видна тому уборщику, который
спросит. `outcome` до `finish` по-прежнему пуст: он ещё может
перевернуться вторым проходом, и обещать наружу решённый исход нельзя.
Форма «уборщик получает исход параметром» остаётся отклонённой — теперь у
неё есть замена.

### `disown` снимает верхнюю запись

При двух записях с одним значением (`reopen`, вернувший тот же
экземпляр; объект, дважды взятый из пула) `disown` снимает **верхнюю**,
одну за вызов, и возвращает `true`. Правило «одно значение — одна
регистрация» делает это редкостью, но поведение названо.

Вызов, не отдающий значения, `disown` адресовать не может:
`ctx.join(lock.acquire, dispose: (_) => lock.release())` при
`Future<void>` регистрирует уборку, у которой нет адреса. Это сказано в
дартдоке обоих параметров: нужна возможность снять — регистрируй членом,
он вернёт функцию. Фраза основного текста про `join<T?>`, вернувший
`null`, неверна и отменяется: запись там настоящая, просто неадресуемая.

### `discard` — только для того, что уходит наружу

Выбор между двумя видами тих в одну сторону. `dispose` на возвращаемом
ресурсе ошибается громко: вызывающий получает закрытую базу. `discard` на
ресурсе, который тело не отдаёт наружу, — временном файле, буфере,
подписке — не сработает на `Done`, и это утечка на успешном пути, которую
не покажет ни один тест на отмену. Движок выбора не видит и помочь не
может, поэтому правило идёт в дартдок обоих параметров и в README:
**`discard` — только для того, что тело возвращает или передаёт наружу;
всё остальное — `dispose`.**

### Что переписано в основном тексте

- **Запрет `run` в уборке — не «заодно».** Утверждение, будто из
  сегодняшнего `ifCancelled` можно завести ребёнка, который переживёт
  родителя, неверно: `ifCancelled` зовётся только под пометкой, а `run`
  под помеченным родителем завершает ребёнка `Cancelled(parent)` и
  бросает отмену. Дыру открывает `dispose`, бегущий на `Done`: там задача
  не помечена, и `run` прошёл бы. Тест на запрет поэтому пишется на
  задаче с исходом `Done` — написанный на отменённой, он зелен и без
  запрета.
- **Обоснование второго прохода.** Не «`cancel()` при исходе `Done`
  объяснить нечем» — объяснить есть чем, так уже ведёт себя задача с
  `cancellable: false`. Причина в другом: при запечатанном исходе
  значение уедет через `Done` тому, кто задачу отменил и результата не
  ждёт. Это ровно та утечка, ради которой всё делается.
- **Длина окна второго прохода.** Не «одна уборка», а от первого
  пропущенного `discard` до конца раскрутки: отмена может прийти в любой
  уборщик, лежащий ниже.
- **Раскрутка — цикл, а не снимок.** И первый проход, и второй снимают по
  одной записи с конца, пока стек не опустеет: уборщик второго прохода
  тоже может зарегистрировать уборку.
- **`Cancelled` из уборщика.** `check` в уборке легален и на отменённой
  задаче бросает её же отмену. Такой `Cancelled`, тождественный
  `pendingCancel`, движок глотает; всё прочее идёт в `notifyError` —
  иначе наблюдатель получал бы `onError` с отменой на каждой отменённой
  задаче, чей уборщик читает контекст.
- **Придержанных отмен «не бывает».** Верно про движок, но не про тело:
  недождавшаяся `uncancellable`-секция оставляет глубину ненулевой, и
  придержанная отмена упадёт в `leaveUncancellable` уже после `finish`.
  Это ошибка тела, движок её не чинит.
- **`onCancel` в уборке.** «К уборке отношения не имеет» — про
  регистрацию, а не про срабатывание: колбэк может отработать посреди
  уборщика, как сегодня посреди ожидания детей.
- **Голый `await` в уборке** обязателен только на пути отмены; при
  `Failed` задача не помечена и контекст свободен.
- **`finish()` напрямую** теперь теряет весь стек, а не одно значение:
  раскрутить его он не может — он синхронный, — поэтому пишет строку
  наблюдателю.
- **Имя метода** — `_execute`, а не `_run`.
- **Рост интерфейса.** `JobContext` прибавляет три члена и меняет две
  сигнатуры. `each` в своё время сделали extension'ом, чтобы не трогать
  интерфейс; здесь это неизбежно, и до публикации бесплатно:
  `implements JobContext` в дереве нет, только `extends JobContextBase`.

### Имя

`dispose`, `discard`, `disown` — три слова на `dis-`, и это решение, а не
случайность: они об одном предмете, владении, и стоят рядом в списке
дополнения. Различие первых двух несёт всю семантику механизма, поэтому
`discard` выбрано за прямое значение «выбросить, не отдав», а `dispose` —
за нейтральное «распорядиться в любом случае». Риск спутать их на глаз
принят и оплачен правилом из раздела выше и строкой в README.

## Дополнение 2026-09-07, второй круг: чтения, передача, поздние значения

Ревью первого дополнения (`2026-09-07[3]-dispose-addendum-review.md`):
девять находок, приняты все, две критические — с заменой решения. Форма
API снова не меняется. Где этот раздел расходится с первым дополнением
или с основным текстом, верно он.

### Контекст тела в уборке закрыт весь

Первое дополнение оставляло `check`, `state` и `stateAs` легальными в
уборке. Это неверно, и в обе стороны.

На пути отмены уборщик, прочитавший контекст, обрывается на первом
чтении: `check` бросает отмену задачи, а её движок глотает — уборка
останавливается на середине, и не узнаёт об этом никто, ни наблюдатель,
ни журнал. На пути `Done` в `solo` хуже: `_checkedState()` проверяет
правила по текущему состоянию, а текущее — то, которое тело излучило
последним, и собственный `emit` задачу не проверял. Форма из README —
задача с рабочим типом `Idle`, излучившая `Loaded` перед возвратом, —
даёт уборщику, прочитавшему `ctx.state`, отмену по правилам: исход
успешной задачи переворачивается в `Cancelled(rules)`, и второй проход
выбрасывает возвращённое значение. Отмена тут не пришла — её сделало
чтение.

Поэтому **в фазе уборки контекст тела закрыт целиком**: `check`, `state`,
`stateAs`, `emit`, `run`, `wait`, `join`, `uncancellable`, `onCancel` —
все бросают `StateError` «is disposing». Легальны только `log`, `job`,
`onDispose`, `onDiscard` и `disown`. Уборщик берёт нужное из замыкания, а
про исход спрашивает `ctx.job.isCancelled` — единственный член, который
это дополнение делает правдивым. Фраза основного текста «`check`, `log` и
`job` остаются легальны» сужается до `log` и `job`.

Следствие: правило проглатывания `Cancelled` из первого дополнения
снимается вместе с причиной — в уборке ни один член контекста отмену
больше не бросает. Остаётся один чужой источник: `await child.value` на
отменённом ребёнке. Такая отмена не тождественна `pendingCancel` и уходит
в `notifyError` как ошибка уборщика — уборщик сам решил ждать чужого
исхода. Слово «тождественный» везде значит `identical`: `Cancelled` не
переопределяет `==`.

`progress` у `scopo` идёт по той же линии — решать `scopo`.

### Передача владения: тройка для `emit`, секция для асинхронного шага

Идиома «передача и снятие в одной неотменяемой секции» верна не для всех
и не по той причине, которую называло первое дополнение.

**Для `emit` секция не работает вовсе.** `emit` проверяет отмену после
записи состояния, и эта проверка бросает на неотклоняемой отмене, которую
секция не держит: реентерабельный `externalSetState` из хука или
слушателя ставит состояние, ломающее правила задачи, `emit` бросает,
`disown` не достигнут, а состояние уже держит базу, которую `discard`
закроет. Вместо секции — **порядок и синхронность**:

```dart
ctx.check();
ctx.disown(db);
ctx.emit(Ready(db));
```

Три синхронных вызова, между ними вклиниться некому. Не прошёл `check` —
база ещё в стеке, и уборка её закроет: состояние её не получило.
Бросил `emit` после записи — база уже в состоянии и уже снята со стека.
Остаток один: хук, реентерабельно заменивший состояние на такое, где базы
нет, — это ошибка хука, и её не закрывает ни одна форма, сегодняшняя в
том числе.

**Для асинхронного шага секция верна, но с условием: внутри неё шаг идёт
голым `await`.** Пара «шаг + `disown`» атомарна не потому, что секция
держит отмены, а потому, что между ними нет члена контекста, который
бросает: `uncancellable` после действия отмену не проверяет, `disown`
помеченной задаче не отказывает. Поставь внутрь секции `ctx.join` — и он
бросит после шага на неотклоняемой отмене, `disown` не достигнут, откат
пойдёт по закоммиченному. Правило «каждый вызов идёт через контекст»
внутри секции не действует, и это надо говорить прямо — в дартдоке
`uncancellable` и в обоих README.

```dart
await ctx.uncancellable(() async {
  await transaction.commit();   // голым await, не через ctx.join
  ctx.disown(transaction);
});
```

**Правило «уборщик обязан терпеть вызов после того, как ресурс уже отдан»
снято.** Оно перекладывало дыру на того, у кого нет средств её закрыть:
закрыть сокет, отданный в пул, «без вреда» нельзя, а узнать об отдаче
уборщику нечем — для этого и есть `disown`. На его месте — правило
размещения: **`disown` стоит перед передачей, если передача синхронна и
сама может бросить после своей работы (`emit`), и в одной секции с ней,
если передача асинхронна.**

### Позднее значение убирают без условия по исходу

Значение, пришедшее после того, как тело кончилось, **до тела не
доехало** — значит и `dispose`, и `discard` для него работают без условия
по исходу: в завершённой задаче уборщик зовётся на месте, и его никто не
ждёт; в идущей уборке запись ложится в стек как «всегда».

Первое дополнение клало её обычной записью, и на исходе `Done` фильтр
`discard` её пропускал: тело сделало `unawaited(ctx.join(Database.open,
discard: ...))` и вернулось, база приехала посреди уборки — и утекла на
успешном пути, в том самом классе ошибок, ради которого написан раздел
про `discard`.

Два уточнения того же места. Переход «стек пуст → `finish`» синхронный:
`await` в этом зазоре пустил бы запись в стек, который никто больше не
раскрутит. И новая ветка в `join` («задача завершена или убирается —
уборщик на месте») стоит **до** его пост-проверки, иначе значение
вернётся в никуда.

### Как именно заполняется `_pendingCancel`

Решение первого дополнения держится, но два слова текста решали разное
поведение:

- **сырым присваиванием**, не `_markCancelled`: иначе для тела,
  бросившего `Cancelled` само, побегут колбэки `onCancel`, которые тело
  не сняло, и недождавшееся `ctx.wait` получит ошибку там, где сегодня
  тихо получает значение;
- **после `_awaitChildren`**, не в `catch`: иначе внешний `cancel()`,
  пришедший, пока родитель ждёт детей, увидит заполненный
  `_pendingCancel`, вернётся молча и перестанет каскадировать на детей;
- **`_cancelled` закрывается там же**, без колбэков, и дартдок
  `whenCancelled` правится на «когда тело кончилось и дети дожданы»:
  иначе в окне уборки `isCancelled` уже `true`, а `whenCancelled` ещё
  открыт — два публичных члена расходятся.

Цена размещения после детей принята словами: в окне ожидания детей
`isCancelled` для самобросившегося тела по-прежнему `false`, и
`_reevaluate` в этом окне может перекрыть собственную отмену тела отменой
по правилам. Это сегодняшнее поведение, и оно не меняется.

### Запрет `emit`: причина и цена

Причина не «писать некуда» — состояние живёт своей жизнью, и
`externalSetState` пишет его даже после `close()`. Причина в том, что
**исход решён, и состояние, записанное после него, исхода уже не
отразит**.

Цена: «состояние на выходе» остаётся в теле. На успехе — `emit` до
`return`, на ошибке — `try/catch` с `emit` и `rethrow`; кусок пирамиды,
от которой стек уводит, никуда не девается. Это принято, но в README
`solo` стоит рядом со стеком, иначе первый же пользователь напишет
`onDispose(() => ctx.emit(Idle()))` и получит `StateError` в
наблюдателе.

Что запрет не ломает — проверено ревью по коду `solo`: очередь, `close()`,
`Policy.restart`, `externalSetState`, `_reevaluate`, наблюдатель.
`throwIfFinished` остаётся одним защищённым методом с проверкой фазы
внутри: наследник получает запрет даром и не наследует второе имя.

### Ещё четыре уточнения

- **Прямой `finish()` с непустым стеком** пишет строку в статический
  `JobBase.debug`, а не наблюдателю: это ошибка движка домена, а не
  событие задачи. Тест цепляется за `debug`, как `debug_test.dart`.
- **Дыру для `run` в уборке** открывает `dispose`, бегущий и на `Done`, и
  на `Failed`: там задача тоже не помечена. Проверка фазы ставится не в
  одну ветку.
- **Исход переворачивает отмена, пришедшая в уборку**, а второй проход —
  следствие, а не причина.
- **«Голый `await` в уборке обязателен только на пути отмены»** — это про
  сегодняшний `finally`, а не про новую фазу: в ней контекст закрыт и на
  `Failed`.

### Что добавилось в список правок и тестов

К правкам: `docs/architecture.md` — инвариант 2 (новые члены идут в
список тех, кто правил не смотрит), инвариант 8 (фаза уборки и что в ней
легально) и инвариант 9, который устарел ещё с `439c8fb`: «отклонённая
отмена нигде не копится и потом не применяется» — секция придерживает её
с того самого коммита. Раз файл всё равно трогаем, девятый чинится тем же
коммитом. Дартдок `isCancelled` — «в уборке по решённому исходу». В
README `solo`, абзац «Taking ownership», — тройка для `emit`, «состояние
на выходе пишут в теле» и правило голого `await` внутри секции.

К тестам: `join` внутри секции при отмене по правилам; тройка
`check`/`disown`/`emit` с реентерабельным `externalSetState` из
`onChange`; позднее значение в идущую уборку на исходе `Done`, не только
в завершённую задачу; `state` и `check` в уборщике на `Done` при
последнем `emit` вне рабочего типа; `whenCancelled` и недождавшийся
`wait` при `throw Cancelled` из тела; `cancel()` родителя, ждущего детей
после собственного `throw Cancelled`, — каскад на месте; придержанная
отмена от незакрытой секции во время уборки; `Cancelled` из `child.value`
внутри уборщика — что видит наблюдатель.

## Дополнение 2026-09-07, третий круг: границы

Ревью второго дополнения (`2026-09-07[4]-dispose-addendum-2-review.md`):
девять находок, приняты все, критических нет. Ни одно решение не
заменено — проведены границы, без которых реализация разошлась бы с
намерением текста. Где этот раздел расходится с предыдущими, верно он.

### Граница «тело кончилось»

Второе дополнение знало две фазы — «задача завершена» и «идёт уборка», —
а между концом тела и уборкой стоит третья: ожидание детей. Она есть
всегда: `await _awaitChildren()` — это минимум микротаск. Позднее
значение, пришедшее туда, по букве текста считалось доехавшим,
регистрировалось условно и на `Done` утекало.

Границу проводит **флаг «тело кончилось»**, который `_execute`
выставляет сразу после того, как тело вернуло или бросило, **до**
`_awaitChildren`. С этого момента:

- `wait` и `join` кладут записи «всегда» — стек раскрутят после детей;
- после `finish` уборщик зовётся на месте, и его никто не ждёт;
- **новая ветка `join` кончает вызов сама** и в `check` не заходит:
  уборщик позван, затем на отменённой задаче `join` бросает
  `pendingCancel`, дождавшись уборщика, а иначе возвращает значение.
  Иначе брошенный `join` провалился бы в закрытый `check` и на успешном
  пути отправил бы `StateError` в зону — шум о вызове, которого тело не
  делало.

Предел механизма назван честно: самое быстрое позднее значение флагом не
ловится. Если действие завершилось к моменту `return` (готовый future),
продолжение внутри `join` встаёт в очередь микротасков раньше, чем движок
узнаёт о конце тела. Это оговорка в дартдоке `join` и `wait`: движок
ловит позднее значение с момента, когда узнал о конце тела, а не с
`return`; `unawaited` на вызове, отдающем ресурс, — ошибка тела.

### Правила `solo` после конца тела задачу не смотрят

`_reevaluate` помечает по правилам любую работающую задачу, а задача,
чьё тело кончилось, всё ещё `running`. На форме из README — рабочий тип
`Idle`, последний `emit(Loaded(...))`, `return` — любая внешняя установка
состояния в окне после тела отменяет задачу по правилам: исход
переворачивается в `Cancelled(rules)`, `discard` закрывает возвращённое
значение, вызывающий вместо значения получает отмену. Уборка удлиняет
это окно на каждый уборщик.

**Решение: после конца тела правила задачу не смотрят** — `_reevaluate`
её пропускает. Стеречь нечего, тела нет; `cancel()`, `close()` и каскад
родителя дотягиваются по-прежнему, и второй проход остаётся для них.
Побочно уходит и то, что второе дополнение приняло как данность:
`_reevaluate` больше не перекрывает собственную отмену тела своей, и
исход будет тем, о котором тело просило.

Это смена семантики `solo`, и она записывается не только сюда:
инвариант 3 в `docs/architecture.md` и абзац в README `solo`.

### Чтения закрыты только в уборке

Механизм, названный первым дополнением (`throwIfFinished` с проверкой
фазы внутри), закрыл бы `check`, `state` и `stateAs` и **после**
`finish` — а это опубликованный контракт: README `solo` про утёкший
контекст, шапка `JobContext` («`check` и `log` остаются легальны»),
инвариант 8 и зелёный `leaked_context_test.dart`. Намерение было другим.

**Чтения закрыты только в фазе уборки.** У них своя защищённая проверка
фазы; `throwIfFinished` с фазой внутри остаётся для шести пишущих членов
(`emit`, `run`, `wait`, `join`, `uncancellable`, `onCancel`). После
`finish` чтения законны, как и были.

Цена названа в дартдоке `check`: брошенное действие, которое опрашивает
`ctx.check()` в цикле, попав опросом в окно уборки, получит `StateError`
вместо `Cancelled` — его собственный `on Cancelled` не сработает, а
ошибка уйдёт в `notifyError`. Окно немонотонно: законно → `StateError` →
законно.

Строка действия у трёх чтений — имя члена: `'check'`, `'state'`,
`'stateAs'`.

### Видимость нарушения в `solo`

В `solo` у задачи наблюдатель есть всегда, поэтому ошибка уборщика в
зону не уходит; а по умолчанию `SoloBase.observer` — `null` и
`SoloBase.onError` пуст. Значит уборщик, тронувший закрытый контекст,
останавливается на первом чтении, остаток уборки не бежит, и об этом не
узнаёт никто, кроме статического `JobBase.debug`.

Принят минимум: **абзац в README `solo` рядом со стеком** — ошибка
уборщика, включая `StateError` закрытого контекста, доходит только до
`onError` и `SoloBase.observer`; без них уборщик замолкает на полпути. И
тест «`emit` из уборщика» ставит наблюдателя явно, иначе он зелен и на
молчании. Второй канал — отдавать ошибки уборщиков в зону, если
`onError` не переопределён — отклонён: он ломает документированное
«stops there» для поздних ошибок и инвариант 4.

### Ещё четыре уточнения

- **Уборщик не ждёт ни свою задачу, ни задачу своей очереди.** `await
  ctx.job.done`, `ctx.job.value`, `await ctx.job.cancel()` из уборщика
  вешают задачу навсегда: `finish` ждёт уборщика, уборщик ждёт `finish`.
  То же с задачей той же очереди: `_pump` не стартует следующую, пока
  текущая не завершилась. Это класс инварианта 7, и фраза о нём идёт в
  дартдок `onDispose`/`onDiscard` и в README.
- **Тождественность снята вместе с правилом.** Любой `Cancelled`,
  брошенный уборщиком, идёт в `notifyError`; `identical` больше нигде не
  проверяется.
- **Правило секции — по причине, а не по форме.** Между шагом и `disown`
  не должно стоять ничего, что бросает отмену этой задачи: ни член
  контекста, ни `await child.value` (каскад кладёт ребёнка раньше, чем
  помечен родитель), ни `ctx.run`. «Голым `await`» — следствие, а не
  правило.
- **`_cancelled` закрывается под защитой** `!isCompleted`, как в
  `finish`: у задачи, помеченной раньше обычной отменой, он уже закрыт.

### Что добавилось в списки

К правкам: дартдоки `join` и `wait` (с какого момента ловится позднее
значение, и что `unawaited` на вызове с ресурсом — ошибка тела), `check`
(окно уборки и его цена), `onDispose`/`onDiscard` (про ожидания),
`isRunning` и `JobStatus.running` (в уборке оба `true`, а фаза
защищённая), `uncancellable` (правило по причине). В
`docs/architecture.md` — инвариант 2 (пишущим членам правила
безразличны, чтения в уборке бросают `StateError`), инвариант 3 (правила
после конца тела задачу не трогают), инвариант 8 («чтения после
завершения законны» остаётся, рядом встаёт «в уборке — нет») и инвариант
9, устаревший с `439c8fb`. В README `solo` — три абзаца: наблюдатель или
молчание, уборщик не ждёт свою задачу и свою очередь, `onFinish` с
`externalSetState` как единственный путь для состояния на выходе при
отмене.

К тестам: позднее значение в окне детей на исходе `Done`; брошенный
`join` в уборку на `Done` — тишина и в `onError`, и в зоне; чтения после
`finish` остаются законны (регрессионный); внешняя установка состояния
во время уборки на форме README — задача не отменяется; «`emit` из
уборщика в `solo`» с явно поставленным наблюдателем.
