# Ожидание дочернего Job

Владелец спросил, можно ли автоматически проверять отмену родителя после
завершения ребёнка, как в join. Сейчас ctx.run синхронно запускает ребёнка
и возвращает тот же хэндл; Job.value передаёт исход ребёнка всем читателям.
Успешный ребёнок может отказать отмене и вернуть значение, хотя родитель
уже отменён. Подмена этого значения отменой родителя внутри общего value
изменила бы контракт для внешних читателей тоже.

Существующий ctx.join(() => child.value) ждёт ребёнка и проверяет отмену
родителя после получения значения. Эта форма показана в примере README,
вместо рекомендации самостоятельно вызвать ctx.check после ожидания.
Отказ ребёнка от отмены не прекращает ожидание. Если ребёнок успешно
завершится, join бросит принятую отмену родителя, и тело не перейдёт
к следующему действию. Ошибка ребёнка передаётся обычным путём через value.

Реализация не менялась. Вопрос о новом ожидании, привязанном к родителю,
или изменении самого value не считается согласованным изменением API.
Обсуждение timing остаётся на этапе согласования отдельной спецификации.

## Уточнение владельца

Владелец имел в виду проверку внутри run без отдельного ctx.join.
Предыдущий ответ показывал способ ожидания с нынешним API, а не изменение
самого run. Проверка только перед синхронным возвратом хэндла недостаточна:
отмена может прийти позже, пока ребёнок работает.

Предложение агента: сделать результатом run Future<T>. Метод запускает
и регистрирует ребёнка, ждёт child.value, после успешного получения
значения проверяет отмену родителя и только затем отдаёт значение телу.
Пользователь пишет await ctx.run(child); отдельный join не нужен.
Исходный child сохраняет свой хэндл и независимый исход. Ошибка ребёнка
передаётся как в join; отказ ребёнка от отмены не прекращает ожидание.

Это изменение контракта, а не добавление проверки к прежнему return:
нынешний run возвращает Job<T> сразу. Потребуется пересмотреть вызовы,
включая внутренний запуск each, который должен возвращать хэндл сразу.
На этом этапе вопрос обсуждался; смена результата run ещё не была
согласована или реализована. После пояснения, что run возвращает тот же
Job, владелец ответил «тогда да, делай как предложил». Реализация перехода
на Future<T> выполнена по `2026-09-10[14]-context-run-plan.md`;
итог и проверки — в `2026-09-10[15]-context-run-report.md`.
