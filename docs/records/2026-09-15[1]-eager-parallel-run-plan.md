# План: `ctx.runAll` — параллельный запуск с остановкой соседей

Всё, что ниже, — по спеке; расхождение с ней означает ошибку плана,
а не свободу исполнителя. Работа идёт в неотпущенном наборе, оверрайды в дереве

1. **`fix:`** снятие ребёнка по тождеству — два места, один тест. Отдельным

## Шаг 1. Снятие ребёнка по тождеству

### `job_base.dart:740`, внутри `finish`

```dart
parent._children.removeWhere((child) => identical(child, this));
```

### `job_context.dart:980`, аварийная ветвь `startChild`

```dart
_owner._children.removeWhere((each) => identical(each, child));
```

Второе место важнее первого и было упущено восьмой редакцией: снятие идёт
**до** `child.finish(Failed(...))`, поэтому исправление одного `finish`
потерянного ребёнка уже не вернёт.

## Шаг 2. `ctx.runAll`

### Стадия 2.1. Швы в `_execute`

Три внутренние точки, все невидимые снаружи.

**Сигнал об исходе тела ребёнка.** После классификации ошибки тела
и до `_awaitChildren`. После — иначе чистый `ParallelWaitError`, брошенный
ребёнком, прочитается отказом, хотя исход тела — отмена. До — иначе смысл
теряется.

**Первый барьер.** Между блоком `if (outcome is Cancelled)`
(`job_base.dart:945`) и `if (_cleanups.isNotEmpty)` (строка 951).

**Второй барьер.** Внутри уборки, между первым циклом (строки 962–970, снимает
стек и откладывает условные записи) и вторым (строка 973, перечитывает
`(_pendingCancel ?? outcome)` и доигрывает отложенное). Барьер выносится **из**
`if (_cleanups.isNotEmpty)`: ветка без регистраций обязана встать на него тоже,
иначе группе не с кем сверяться. Хвост после второго цикла — `_skipped.clear()`
и `finish` — остаётся без `await`, как требует комментарий ядра на строке 953.

После каждого барьера — `if (isFinished) return;` **со сбросом `_disposing`**:
движок домена вправе закончить ветку по руке прямо в окне ожидания, а голый
`return` обошёл бы сброс на строке 985 и оставил ветку «убирающейся» навсегда.

Фаза ветки на втором барьере выбирается одна для всех: сегодня `_disposing`
включается только внутри `if (_cleanups.isNotEmpty)`, и ветка с уборщиками
стоит на барьере «убирающейся», а ветка без них — нет. Разница наблюдаема через
`ctx.check()` и `isDisposing`; план выбирает **«убирающаяся» для обеих**,
потому что права ветки на барьере не должны зависеть от того,
зарегистрировала ли она уборку.

Отпускание барьера несёт **вердикт** — «успех» или «неуспех», — а не пустой
сигнал.

### Стадия 2.2. Координатор: запуск, остановка, выбор

`SiblingCancelReason` — новый публичный тип причины в `async_job`:

```dart
final class SiblingCancelReason extends CancelReason {
  const SiblingCancelReason({required this.cause});

  final Object cause;

  @override
  String get name => 'sibling';
}
```

`Future<List<T>> runAll<T>(Iterable<Job<T>> children)` — член `JobContext`,
реализован один раз в `JobContextBase`; домены получают его даром.

Порядок: снимок входа копией до первого старта; отказ повторов **строго
по тождеству** (`Set.identity()`, не обычный `Set` — доменный наследник вправе
переопределить `==`); синхронный запуск всех; на первом сигнале «тело кончилось
ошибкой» — `cancel` всем, **кроме источника**, с `SiblingCancelReason`.

Выбор исхода — по итоговым исходам веток, без тех отмен, о которых просил сам
вызов: первый полученный `Failed`, иначе первая полученная `Cancelled`.
Бросается тот самый объект, что несёт исход.

### Стадия 2.3. Барьеры и синхронная фиксация

Пять шагов фиксации, и между ними нет ни одного `await`:

1. все ветки стоят на втором барьере, ни одна не сменила исход;
2. группа проверяет свой контекст — жив ли ещё родитель;
3. группа перечитывает состояния веток после этой проверки;
4. группа снимает с каждой ветки её отложенные записи;
5. группа отпускает барьеры с вердиктом «успех» и возвращает список.

Шаги 2 и 3 порознь, и порядок не переставить: без проверки родителя коммит
пройдёт там, где родитель уже отменён, а обе ветки `cancellable: false`
сохранили успех, и там, где `keepWhile` вернул `false` без пометки; без
перечитывания устареет решение, если доменный `check()` успешно вернулся,
отменив по дороге ветку.

На неуспехе всё иначе: ветки отменяются, отпускаются с вердиктом «неуспех»,
и группа дожидается всех до конца — это и есть гарантия, что к моменту, когда
родитель поймает ошибку, всё закрыто.

Вердикт переопределяет **только в сторону успеха**. Успешная фиксация запрещает
`discard` зафиксированного значения при любом последующем исходе ветки; без
фиксации работает обычное `_pendingCancel ?? outcome`. Иначе неуспешный вердикт
закрыл бы ресурс у ветки, отвергшей отмену и отдающей его через свой `value`.

Отпускание — в `finally`, на всех путях, включая бросок из кода самой группы;
на аварийных путях ветки надо ещё и **отменить**, а не просто отпустить, иначе
те, чьи тела вернули значения, кончатся `Done`, пропустят условные записи
и тихо унесут ресурсы.

### Стадия 2.4. Сток невыбранной ошибки

Новая внутренняя точка «обработать, не рассказывая наблюдателю», которую домен
переопределяет. Выбирать маршрут по наличию наблюдателя нельзя: у каждого
`SoloJob` внутренний наблюдатель есть всегда. `reportToZone` проходит мимо
`SoloBase.errorHandler`, `notifyError` зовёт наблюдателя второй раз —
не годится ни то, ни другое. В `solo` точка ведёт в `errorHandler`.
