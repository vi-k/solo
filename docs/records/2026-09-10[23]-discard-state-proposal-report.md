# Предложение onDiscard для run и job

Владелец указал: сброс loading через общий onFinish и externalSetState
усложняет быстрый старт. externalSetState нужен для уведомлений от
внешнего источника, который уже изменил своё состояние.

## Предлагаемый контракт

Необязательный onDiscard в run и job принимает текущее S и синхронно
возвращает S. Движок применяет результат как часть уборки этой Job.

- Выполняется при ошибке или отмене после запуска тела.
- При Done, отбрасывании дубликата и отмене в очереди не выполняется.
- Регистрируется перед телом в существующем стеке onDiscard; обычная
  уборка тела проходит раньше, дети уже завершены.
- Очередь ждёт завершения Job, дополнительная Job не создаётся.
- Отмена не мешает этому преобразованию; обычный ctx.emit сохраняет
  свои проверки отмены.
- Передаётся текущее S, не прежний снимок и не рабочий подтип W:
  внешний источник мог уже сменить состояние. Неподходящее состояние
  обработчик возвращает без изменения.
- Ошибка обработчика идёт по существующему пути ошибок уборки и
  не заменяет исходную ошибку или отмену Job.

Владелец уточнил: даже первый короткий пример должен показывать
sealed-состояния Initial, Loading, Loaded и Failure и обработку ошибки.
Вместо сброса bool обработчик отмены возвращает Initial только из
Loading. Уже установленное Failure или Loaded сохраняется.

Пример предполагаемого API внутри ProfileController:

```dart
sealed class ProfileState {
  const ProfileState();
}

final class Initial extends ProfileState {
  const Initial();
}

final class Loading extends ProfileState {
  const Loading();
}

final class Loaded extends ProfileState {
  final String name;
  const Loaded(this.name);
}

final class Failure extends ProfileState {
  final Object error;
  const Failure(this.error);
}

Job<String> load() => run<ProfileState, String>(
      key: 'load',
      policy: Policy.droppable,
      onDiscard: (state) => state is Loading ? const Initial() : state,
      (ctx) async {
        ctx.emit(const Loading());
        try {
          final name = await ctx.wait(api.fetchName);
          ctx.emit(Loaded(name));
          return name;
        } on Cancelled {
          rethrow;
        } on Object catch (error) {
          ctx.emit(Failure(error));
          rethrow;
        }
      },
    );
```

Контроллер наследует Solo<ProfileState> и начинает с const Initial().
Рабочий тип run — ProfileState: тело должно иметь доступ к контексту
при переходах между всеми четырьмя состояниями.

Обычная ошибка устанавливает Failure и пробрасывается дальше, чтобы
Job завершился Failed и вызывающий код мог получить ошибку через value.
Cancelled пробрасывается отдельной веткой и не становится Failure.
При отмене в Loading onDiscard устанавливает Initial до следующей Job.
Если внешний источник уже сменил состояние, обработчик его сохраняет.
Пример иллюстрирует предложенный API: параметра onDiscard в run ещё нет.

## Обоснование и альтернативы

JobBase уже ждёт детей, выполняет стек уборки и только потом освобождает
очередь. Регистрация до тела позволяет использовать этот порядок без
изменения ядра async_job. Реализация должна применять состояние внутри
solo с идентичностью завершающейся Job, сохраняя уведомления и переоценку
правил других работающих Job.

Обычный finally с ctx.emit не решает отмену: emit бросает Cancelled.
Разрешить emit после отмены вообще означало бы разрешить и обычному
телу публиковать устаревший результат. Отдельный контекст уборки мог бы
дать более широкие возможности, но для преобразования состояния
достаточно синхронного обработчика без запуска новых операций.

При реализации проверить отмену после начала загрузки, ошибку, успех,
дубликат и отмену до старта, close, порядок относительно детей и уборки,
смену типа состояния внешним источником, ошибку обработчика и отмену,
пришедшую во время асинхронной уборки. Учесть синхронный повторный вход
через наблюдателей. Это предложение API, не готовая реализация.


## Пересмотр: onError и onCancel для коррекции состояния

Владелец предложил отделить обработку ошибки и отмены, чтобы простой
пример не требовал try/catch. Название onDiscard для коррекции состояния
отклонено: оно остаётся у механизма освобождения ресурсов.
Предыдущий вариант выше сохранён как рассмотренная альтернатива.

Предлагаемые параметры run и job:

```dart
S Function(S state, Object error, StackTrace stackTrace)? onError
S Function(S state, Cancelled cancelled)? onCancel
```

Это синхронные преобразования текущего состояния при завершении
начавшейся Job. Для Failed выбирается onError, для Cancelled — onCancel.
При Done, отбрасывании дубликата и отмене до старта тела они не нужны.
Обработчики выполняются после тела, детей и уборки, до освобождения
очереди. Отмена не запрещает движку применить возвращённое состояние.
Состояние передаётся как S, поскольку рабочий подтип W мог смениться.

Обработчики меняют состояние, но не превращают Failed или Cancelled
в Done и не восстанавливают значение T. Ошибка остаётся доступна через
job.value и существующие механизмы диагностики. Ошибка самого обработчика
сообщается отдельно и не подменяет исходную ошибку или отмену.
Это не касается локального восстановления с повтором операции: для
него try/catch в теле остаётся уместным.

run.onCancel — завершение отменённой Job. Существующий ctx.onCancel —
немедленный сигнал отмены для остановки внешней операции. Их порядок
и назначение необходимо явно различать в документации.

```dart
Job<String> load() => run<ProfileState, String>(
      key: 'load',
      policy: Policy.droppable,
      onError: (state, error, stackTrace) =>
          state is Loading ? Failure(error) : state,
      onCancel: (state, cancelled) =>
          state is Loading ? const Initial() : state,
      (ctx) async {
        ctx.emit(const Loading());
        final name = await ctx.wait(api.fetchName);
        ctx.emit(Loaded(name));
        return name;
      },
    );
```

Для реализации нужна точка обработки исхода после уборки. Прежнее
предположение о достаточности одной регистрации ctx.onDiscard к этому
варианту автоматически не переносится. До реализации определить порядок
фиксации исхода и повторного входа из наблюдателя при публикации состояния:
отмена в этот момент не должна вызвать противоречивые обработчики.
Все ранее перечисленные проверки жизненного цикла сохраняются.

Проверено поведение bloc по первичным исходникам:
[Emitter](https://github.com/felangel/bloc/blob/master/packages/bloc/lib/src/emitter.dart)
после cancel игнорирует call; исключение отмены в тело не отправляется.
[Bloc.on](https://github.com/felangel/bloc/blob/master/packages/bloc/lib/src/bloc.dart)
связывает отмену подписки с emitter.cancel, а Future тела продолжает
исполняться. Поэтому отменённый обработчик через свой Emitter не вернёт
Initial; другой активный обработчик может установить это состояние.
