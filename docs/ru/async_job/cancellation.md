# Отмена

`cancel()` запрашивает; тело останавливается в контрольной точке. От того,
какая это точка, зависит, что станет с операцией за ней:

```dart
Job<void>((ctx) async {
  // Собственный сигнал остановки клиента базы, отменяется вместе с задачей.
  final stop = CancelToken();
  ctx.onCancel(stop.cancel);

  // Ожидание кончается сразу; чтение идёт дальше, а значение отбрасывается.
  final rows = await ctx.abandonable(database.readAll);

  // Ждёт, пока миграция не кончится или не остановится по токену,
  // и только потом задача сдаётся.
  await ctx.join(() => database.migrate(stop));

  // Отмена ждёт конца всего шага, и запущенный им ребёнок
  // не отменяется; её бросит следующая точка.
  await ctx.uncancellable(() async {
    await database.writeVersion();
    await ctx.run(database.readyFlag());
  });

  // Между шагами вычисления оборачивать нечего.
  ctx.check();
  use(rows);
});
```

| Метод | Если отмена приходит во время ожидания |
| --- | --- |
| `ctx.abandonable(action)` | Оставляет действие: перестаёт его ждать и сразу бросает `Cancelled`, а действие идёт дальше. Его результат отбрасывается, а если вызову передан `dispose` или `discard`, уходит туда. |
| `ctx.join(action)` | Присоединяется к действию: ждёт его дальше, пока оно не кончится, затем бросает `Cancelled` вместо возврата значения либо собственную ошибку действия, если оно упало. Если вызову передан `dispose` или `discard`, `join` сперва отдаёт туда значение и дожидается конца освобождения, а потом бросает. |
| `ctx.uncancellable(action)` | Придерживает запрос до конца секции: ни `onCancel`, ни передачи отмены детям, пока она идёт. |
| `ctx.pause(duration)` | Сразу бросает `Cancelled` и снимает свой таймер. |
| `ctx.check()` | Бросает, если задача уже приняла отмену. |

Работающая задача принимает запрос прямо внутри `cancel()`, если его
не придерживает секция `uncancellable` и задача не создана
с `cancellable: false`. Приняв его, задача становится отменённой: отмена
передаётся запущенным ею детям, вызываются её колбэки `onCancel`, и задача
кончится `Cancelled`, что бы тело ни делало дальше. С этого момента `check`,
`abandonable`, `join`, `pause`, `uncancellable`, `run`, `runAll` и `each`
бросают `Cancelled` на своих контрольных точках. `onCancel` тоже бросает: его
колбэки уже вызваны, и зарегистрированный сейчас не был бы вызван никогда.
`onDispose`, `onDiscard`, `disown` и `unattended` остаются доступны, чтобы тело
могло организовать уборку после отмены.

Тело, которое отменяет само себя, бросив `Cancelled` или выпустив наружу отмену
ребёнка, принимает отмену в момент броска, и задача отменяется так же: отмена
передаётся её детям, её колбэки `onCancel` вызываются, и она кончается
`Cancelled`.

Внутри действия, переданного контексту, обычный `await` уместен: контекст
не добавляет контрольных точек между шагами этого действия, и шагу, которому
нужна своя проверка, нужно своё обращение к контексту. Раздел
[«Шаг, который должен закончиться»](#шаг-который-должен-закончиться) ставит
каждую из двух записей в свой `join`, а потом обе в один и показывает, что
делает каждая форма, когда отмена приходит во время первой записи.

Строки под кодом показывают, что он печатает при запуске. База говорит, что
пишет, а `printing`, наблюдатель каждой задачи ниже, печатает то, что до него
дошло: `log:` для `ctx.log`, `onError:` для ошибки. `cancel` отмечает момент,
когда пользователь отменяет, а `outcome:` показывает, чем завершается
`job.done`.

## Остановка операции

Задача открывает базу, мигрирует её и отдаёт; `discard` закрывает базу, если
задача кончилась не `Done`. Миграция идёт в три шага по 10 мс, и перед каждым
она читает `CancelToken`, сигнал остановки клиента базы, а не тип этого пакета;
найдя его отменённым, она останавливается, бросая `DatabaseStopped`. Когда
пользователь отменяет, миграция должна остановиться, а база закрыться, когда
в неё уже никто не пишет. Пользователь отменяет на 15-й миллисекунде, во время
второго шага.

### Первая попытка

Тело ждёт миграцию через `abandonable`, чтобы при отмене задача кончалась
сразу:

```dart
// Первая попытка: база закрывается под идущей миграцией.
final job = Job<Database>(observer: printing, (ctx) async {
  final database = await ctx.join(
    Database.open,
    discard: (database) => database.close(),
  );
  final stop = CancelToken();

  await ctx.abandonable(() => database.migrate(stop));

  return database;
});
```

```text
step 1
cancel
database closed
outcome: Cancelled(manual)
step 2 on a closed database
step 3 on a closed database
```

`abandonable` кончает ожидание, а не миграцию. Вот что происходит:

1. Отмена выходит из `abandonable` сразу, и задача кончается.
2. `discard` закрывает базу, когда миграции остаётся записать ещё два шага.
3. Всё, что миграция бросит потом, уйдёт в `onError` и по умолчанию дальше
   в зону.

`abandonable` подходит операции, от которой задача может уйти: например,
чтению, результат которого уже никому не нужен.

Результат, пришедший так поздно, отбрасывается, а если `abandonable` передан
`dispose` или `discard`, уходит туда. Пока тело или дети задачи ещё идут, этот
колбэк выполняется сразу, и задача его дожидается; если задача уже выполняет
стек уборки, колбэк добавляется в стек, а если она уже завершилась, колбэк
выполняется отдельно. Этот порядок разобран в разделе
[«Значение, которое приходит поздно»](cleanup.md#значение-которое-приходит-поздно)
страницы об уборке.

### Вторая попытка

`join` остаётся с миграцией до её конца:

```dart
// Вторая попытка: ненужная миграция идёт до конца.
await ctx.join(() => database.migrate(stop));
```

```text
step 1
cancel
step 2
step 3
database closed
outcome: Cancelled(manual)
```

Теперь в закрытую базу никто не пишет: `join` ждёт миграцию, и задача сдаётся
только после неё. Но и остановиться миграции никто не сказал, поэтому она пишет
шаг, который уже никому не нужен, а исход приходит тогда, когда миграция
кончилась бы и так.

### Токен через `onCancel`

Миграция не знает об отмене задачи: она слушает только свой токен. Отменить
токен вместе с задачей можно через `onCancel`:

```dart
final stop = CancelToken();
ctx.onCancel(stop.cancel);

await ctx.join(() => database.migrate(stop));
```

```text
step 1
cancel
step 2
migration stopped
onError: DatabaseStopped
database closed
outcome: Cancelled(manual)
```

Колбэк, переданный в `ctx.onCancel`, вызывается синхронно, когда задача
принимает отмену, до того как тело дойдёт до контрольной точки. Здесь он
отменяет токен, миграция читает его перед третьим шагом и бросает
`DatabaseStopped`, а `join` дожидается этого, прежде чем задача закроет базу.
Запрос, который нужно прервать, или подписка, которую нужно отменить, проходят
через `onCancel` так же. Остановке, которая занимает время, этого мало, и что
ей нужно, показывает раздел
[«Остановка, которая занимает время»](#остановка-которая-занимает-время)
в конце страницы.

Строка `onError:` и есть тот самый `DatabaseStopped`. `join` бросает ошибку
своего действия как есть, даже после отмены, а тело её не ловит. Задача всё
равно кончается `Cancelled`, поэтому ни один исход эту ошибку не несёт. Она
идёт путём любого такого провала тела: к наблюдателю, затем в зону, если
наблюдатель не перехватит её в `onUnanswered`. Каждая остановка попадала бы
в отчёты приложения о сбоях как сбой. Поэтому приложение один раз, в `main`,
называет остановку своего клиента базы, и каждая задача на этой странице идёт
с этой строкой:

```dart
Job.isCancellationError = (error) => error is DatabaseStopped;
```

Названная им ошибка доходит до наблюдателя и на нём останавливается. Фильтр
разобран в разделе [«Ошибки отмены»](observing.md#ошибки-отмены) страницы
о наблюдении. Что видит `catch` вокруг этого `join`, разобрано ниже, в разделе
[«Перехват ошибок операции»](#перехват-ошибок-операции).

## Шаг, который должен закончиться

Миграция позади, и последний шаг помечает базу готовой: пишет версию схемы,
а затем флаг готовности. База с версией, но без флага не старая и не готовая.
Две записи делаются двумя вызовами базы, `writeVersion` и `writeReadyFlag`.
Пользователь отменяет, пока пишется версия.

### Первая попытка

`join` ждёт своё действие, поэтому каждая запись идёт через него:

```dart
// Первая попытка: после отмены во время первой записи второй не будет.
await ctx.join(database.writeVersion);
await ctx.join(database.writeReadyFlag);
```

```text
cancel
version written
outcome: Cancelled(manual)
```

Шаг не доходит до конца: база остаётся с версией, но без флага готовности.
Каждый `join` служит отдельной контрольной точкой. Первый дожидается версии
и бросает отмену, и до второго тело не доходит.

### Один `join` на шаг

```dart
await ctx.join(() async {
  await database.writeVersion();
  await database.writeReadyFlag();
});
```

```text
cancel
version written
ready flag written
outcome: Cancelled(manual)
```

Внутри действия контрольных точек нет, поэтому обе записи сделаны, а отмена
выходит из `join` уже после них. Этого хватает, пока шаг остаётся обычным
кодом: он не берёт токен, который отменяет `onCancel`, не запускает дочерних
задач и не проходит контрольных точек контекста.

## Шаг, который запускает ребёнка

Шаг тот же, но флаг теперь пишет отдельная задача: её возвращает
`database.readyFlag()`, а шаг запускает её дочерней через `ctx.run`.
Пользователь отменяет, пока пишется версия.

### Первая попытка

У шага остаётся его единственный `join`:

```dart
// Первая попытка: внутри join ctx.run бросает отмену.
await ctx.join(() async {
  await database.writeVersion();
  await ctx.run(database.readyFlag());
});
```

```text
cancel
version written
outcome: Cancelled(manual)
```

Флаг снова потерян. `join` ждёт своё действие, но задача принимает отмену
сразу, и дальше `ctx.run` бросает её вместо того, чтобы запустить ребёнка; уже
запущенный ребёнок был бы отменён.

### Придержать отмену

`uncancellable` придерживает отмену, пока шаг не кончится:

```dart
await ctx.uncancellable(() async {
  await database.writeVersion();
  await ctx.run(database.readyFlag());
});
```

```text
cancel
version written
ready flag written
outcome: Cancelled(manual)
```

Пока идёт секция, задача отмену не принимает: `ctx.run` запускает ребёнка, дети
задачи не отменяются, и `onCancel` не вызывается. Придерживает, а не отклоняет:
задача принимает отмену в тот момент, когда секция закрывается, и следующая
контрольная точка её бросает. Задача всё равно кончается `Cancelled`, даже если
тело вернёт значение, поэтому всему, что должно случиться после шага в любом
случае, место внутри той же секции.

Если шаг падает, а тело пропускает ошибку дальше, задача всё равно кончается
`Cancelled`, а провал идёт туда же, куда любой провал тела отменённой задачи:
его слышит наблюдатель, а затем зона, если наблюдатель не перехватит его
в `onUnanswered`. Таблица есть в разделе
[«Куда уходят ошибки»](observing.md#куда-уходят-ошибки) страницы о наблюдении.

Всегда ожидайте `ctx.uncancellable`. Секция открывается при вызове, даже если
её future не ждут. Без `await` секция может пережить тело; если задача
завершится раньше, придержанная отмена потеряется: `cancel()` вернётся,
а исходом будет `Done`. Если тело пошло дальше, не дождавшись секции, и потом
отменило само себя, бросив `Cancelled` или выпустив наружу отмену ребёнка,
задача принимает эту отмену сразу: секция придерживает запрос на отмену,
а не отмену, которую бросает само тело. `onCancel` вызывается, пока секция ещё
открыта, и `abandonable` внутри неё бросает.

## Задача, которая отклоняет отмену

Задача пишет резервную копию, а оборванная копия хуже никакой: всё тело — шаг,
который должен закончиться. Если нужно защитить всё тело, а не одну секцию,
создайте `Job(body, cancellable: false)`. Она отклоняет обычную отмену после
запуска тела, а до него её ещё можно отменить:

| Когда приходит отмена | Что делает задача |
| --- | --- |
| До запуска тела | Кончается исходом `Cancelled` с `started: false`, и тело не запускается вовсе |
| После запуска тела | Отклоняет обычную отмену: тело идёт дальше, а `cancel()` ждёт, пока задача кончится |

Флаг не даёт оборвать тело, которое уже началось, а до старта обрывать нечего.
Задача, созданная через `Job(body)`, стартует на следующей микротаске, поэтому
не запущенной её застаёт только отмена, которая пришла раньше. Задача,
созданная через `Job.deferred`, ждёт, пока её запустят: через `start()` или
через `ctx.run` родителя. Запустят ли её вообще, ядро не знает. Откажи такая
задача в отмене и не запусти её потом никто, она не кончилась бы никогда: её
`done` не завершился бы, `cancel()`, которому она отказала, ждал бы вечно,
а более сильной формы, чтобы снять задачу, у `cancel()` нет.

Движок, который держит задачи до старта, знает то, чего не знает ядро: он
запускает их сам. `solo`, построенный на этом ядре, сам запускает задачи своей
очереди и отклоняет отмену за задачу с `cancellable: false`, пока она ждёт там.
Такой отказ строит раздел [«Своя очередь»](extending.md#своя-очередь) страницы
о расширении. Ещё `solo` отменяет задачу тогда, когда состояние контроллера
перестаёт ей подходить: задача там сама объявляет, в каких состояниях она
работает. Такую отмену не придерживают ни секция, ни `cancellable: false`.

## Перехват ошибок операции

Неудачная миграция здесь не смертельна: тело пишет её в лог и идёт дальше
помечать базу готовой. Отменённая задача всё равно должна остановиться,
а в логе должны быть сбои, а не отмены. Пользователь отменяет на 15-й
миллисекунде.

### Первая попытка

Отмена бросает `Cancelled`, поэтому ветка для него стоит первой и пробрасывает
его дальше:

```dart
// Первая попытка: ошибка, вызванная токеном, записывается как сбой.
final stop = CancelToken();
ctx.onCancel(stop.cancel);

try {
  await ctx.join(() => database.migrate(stop));
} on Cancelled {
  rethrow;
} on Exception catch (error) {
  ctx.log('migration failed: $error');
}
await ctx.join(() async {
  await database.writeVersion();
  await database.writeReadyFlag();
});
```

```text
step 1
cancel
step 2
migration stopped
log: migration failed: DatabaseStopped
outcome: Cancelled(manual)
```

Лог называет отмену неудачной миграцией. Вот что происходит:

1. Токен останавливает миграцию, и из `join` выходит собственный
   `DatabaseStopped` миграции, а не `Cancelled`: `join` бросает ошибку своего
   действия как есть.
2. Ветка для `Cancelled` его пропускает, и его ловит `on Exception`. Код ветки
   `on Exception` выполняется на уже отменённой задаче.
3. Задача всё равно кончается `Cancelled`: `join` следующего шага бросает,
   не начав своё действие.

Без токена ветка для `Cancelled` работает: миграция доходит до конца, и `join`
бросает `Cancelled`. Без этой ветки `on Exception` ловит и этот `Cancelled`,
потому что `Cancelled` реализует `Exception`, и пишет
`migration failed: Cancelled(manual)`.

### Спросить задачу

Отменена ли задача, спрашивают у задачи, а не у ошибки:

```dart
try {
  await ctx.join(() => database.migrate(stop));
} on Exception catch (error) {
  ctx.check();
  ctx.log('migration failed: $error');
}
```

```text
step 1
cancel
step 2
migration stopped
outcome: Cancelled(manual)
```

`ctx.check()` бросает отмену задачи, если та её приняла, что бы ни поймал
`catch`. Миграция, упавшая сама, пишется в лог, и тело идёт дальше. В отличие
от раздела [«Токен через `onCancel`»](#токен-через-oncancel), строки
`onError: DatabaseStopped` здесь нет: `DatabaseStopped` ловит `on Exception`,
и из тела он не выходит. Тело кончается отменой задачи из `ctx.check()`,
а отмена в `onError` не попадает. Если ветка должна ловить всё, включая
`Error`, как `on Object catch (error)`, первой строкой в ней нужен тот же
`ctx.check()`.

Платит ветка за это провалами, которые приходят после отмены. Когда задача её
приняла, `ctx.check()` бросает отмену, что бы ни поймал `catch`, даже настоящий
провал: миграция, упавшая сама уже после отмены пользователя, в лог
не попадает, а тело кончается отменой, так что о провале не слышат
ни `onError`, ни зона. Если такой провал надо услышать, ветка на отменённой
задаче бросает пойманное дальше: `if (ctx.job.isCancelled) rethrow;` вместо
`ctx.check()`. Тогда провал доходит до `onError` и до зоны, а остановка
миграции не идёт дальше `onError`, потому что её называет фильтр, поставленный
в `main`.

Если задача уже приняла отмену, перехват её `Cancelled` эту отмену не снимает.
Код после `catch` выполняется, но следующая контрольная точка снова бросает,
и исходом всё равно будет `Cancelled`, даже если тело вернёт значение.

### `Cancelled`, который задаче не принадлежит

Страница показывает миниатюру, когда та отрисовалась, а когда нет, уходит без
неё. Упавшая миниатюра попадает в лог, а отменённая — нет. `Cancelled`,
перехваченный в теле, не всегда принадлежит самой задаче. Операция бросает его,
когда ждёт `value` отменённой задачи, а дочерняя задача, запущенная через
`ctx.run` и отменённая напрямую, а не через родителя, бросает свой `Cancelled`
из `run`. `ctx.check()` тогда проходит, потому что сама задача не отменена,
и тело идёт дальше и может кончиться `Done`. Ветка из раздела
[«Спросить задачу»](#спросить-задачу) пишет такой `Cancelled` в лог как сбой.
Раз `ctx.check()` прошёл, пойманный `Cancelled` задаче не принадлежит,
и проверка типа отличает отменённую необязательную дочернюю задачу от упавшей:

```dart
final thumbnail = Job.deferred<String>(renderThumbnail);
try {
  return 'page with ${await ctx.run(thumbnail)}';
} on Exception catch (error) {
  ctx.check();
  if (error is! Cancelled) ctx.log('thumbnail failed: $error');
  return 'page without a thumbnail';
}
```

Ветка, которая пробрасывает любой `Cancelled`, кончает и саму задачу:
с причиной `HandlerCancelReason`, если это `Cancelled` ребёнка, и с собственной
причиной чужой задачи, если это `Cancelled` операции. Эти причины разбирает
раздел [«Почему задачу отменили»](outcomes.md#почему-задачу-отменили) страницы
об исходах.

## Дать времени пройти

Задача читает строки раз в секунду.

### Первая попытка

```dart
// Первая попытка: обычный await досиживает задержку.
final job = Job<void>((ctx) async {
  while (true) {
    use(await ctx.abandonable(database.readAll));
    await Future<void>.delayed(const Duration(seconds: 1));
  }
});
```

Пользователь отменяет через 500 мс после старта, на середине задержки, и задача
кончается на 510 мс позже. Обычный `await` контрольной точкой не служит: тело
досиживает задержку и узнаёт об отмене на `ctx.abandonable` следующего оборота.
До тех пор `cancel()` не возвращается, и всё, что ждёт задачу, ждёт вместе
с ней.

### Вторая попытка

```dart
// Вторая попытка: таймер задержки переживает задачу.
await ctx.abandonable(
  () => Future<void>.delayed(const Duration(seconds: 1)),
);
```

Теперь задержка стоит за контрольной точкой, и задача кончается в момент
отмены. Но `abandonable` прекращает ожидание, а не работу, а работой здесь
служит таймер: `Future.delayed` отменить нельзя, и его таймер идёт оставшиеся
510 мс, хотя его никто не ждёт. Программа, которой больше нечего делать,
не выйдет, пока он не сработает, а тест, который ищет незавершённые таймеры,
найдёт один.

### Пауза самой задачи

```dart
await ctx.pause(const Duration(seconds: 1));
```

`ctx.pause` служит контрольной точкой, которая занимает время. Она сразу
бросает `Cancelled`, когда приходит отмена, как `ctx.abandonable`, и её таймер
снимается вместе с ней:

| Как тело ждёт | Задача кончается | Оставшийся таймер |
| --- | --- | --- |
| `await Future.delayed(...)` | через 510 мс после отмены | нет |
| `ctx.abandonable(() => Future.delayed(...))` | сразу | ещё 510 мс |
| `ctx.pause(...)` | сразу | нет |

Без длительности `ctx.pause()` возвращается на следующем обороте цикла событий:
в этом месте долгое вычисление пропускает другую работу и может услышать
отмену. Внутри `ctx.uncancellable` отмена придержана, как любая другая, и пауза
идёт целиком.

## Срок

Миграции дано 15 мс. Когда они вышли, задача должна остановиться так же, как
при отмене пользователем: токен останавливает миграцию, а `discard` закрывает
базу. Вручную здесь никто не отменяет.

### Первая попытка

Задачу останавливает `cancel`, поэтому таймер вызывает его, когда предел вышел:

```dart
// Первая попытка: таймер лимита переживает задачу.
const limit = Duration(milliseconds: 15);

final job = Job<Database>(observer: printing, (ctx) async {
  final database = await ctx.join(
    Database.open,
    discard: (database) => database.close(),
  );
  final stop = CancelToken();
  ctx.onCancel(stop.cancel);

  await ctx.join(() => database.migrate(stop));

  return database;
});
Timer(limit, job.cancel);
```

```text
step 1
step 2
migration stopped
onError: DatabaseStopped
database closed
outcome: Cancelled(manual)
```

Задача останавливается так же, как у пользователя в разделе
[«Токен через `onCancel`»](#токен-через-oncancel), а задачу, которая уже
кончилась, вызов не трогает: `cancel()` с ней ничего не делает. Но сам таймер
живёт до предела, кончилась задача или нет. Миграция, которая падает на плохой
схеме, сразу кончает задачу `Failed`, а таймер идёт оставшиеся 15 мс, хотя
отменять ему нечего. Программа, которой больше нечего делать, не выйдет, пока
он не сработает, а тест, который ищет незавершённые таймеры, найдёт один.

### Вторая попытка

Таймер снимается, когда задача кончается:

```dart
// Вторая попытка: чтение done не пускает сбой в зону.
final timer = Timer(limit, job.cancel);
job.done.whenComplete(timer.cancel);
```

Оставшегося таймера больше нет, но чтение `job.done` наблюдает исход. Провал
на плохой схеме по-прежнему доходит до наблюдателя как `onError`, а до зоны
больше не доходит: без наблюдателя его никто не слышит, и сообщать о нём
приходится коду, который снимает таймер.

### Срок самой задачи

```dart
final job = Job<Database>(observer: printing, timeout: limit, (ctx) async {
  final database = await ctx.join(
    Database.open,
    discard: (database) => database.close(),
  );
  final stop = CancelToken();
  ctx.onCancel(stop.cancel);

  await ctx.join(() => database.migrate(stop));

  return database;
});
```

```text
step 1
step 2
migration stopped
onError: DatabaseStopped
database closed
outcome: Cancelled(timeout)
```

`timeout` даёт задаче собственный срок. Ядро ставит таймер, когда стартует
тело, поэтому время до старта не считается: например, ожидание `start()`
у `Job.deferred` или `ctx.run` у родителя. Когда срок выходит, задача
отменяется с причиной `TimeoutCancelReason`, у которой `timeout` равен пределу,
и исход говорит об этом: `Cancelled(timeout)`, тогда как таймер первой попытки
оставлял `Cancelled(manual)`, как у пользователя.

Срок действует как отмена через `cancel()`, а не как `TimeoutException`
из `Future.timeout`:

- тело останавливается на следующей контрольной точке;
- секция `uncancellable` придерживает запрос, пока не закроется;
- уже отменённая задача сохраняет свою причину;
- дети получают срок в `cause` своей `ParentCancelReason`.

Если тело и дети, которых задача ждёт, кончились, пока секция ещё придерживает
запрос, запрос уходит вместе с таймером, и задача кончается тем, что вернуло
тело.

Срок ограничивает тело и детей, которых задача ждёт после него, но не стек
уборки. Ядро снимает таймер до того, как стек начнёт разматываться: отмена,
пришедшая туда, превратила бы задачу, которая сделала свою работу, в отменённую
и закрыла бы её значение через `discard`. Таймер снимается и при любом другом
конце задачи, и снятие ничего не наблюдает:

| Как задача получает предел | Оставшийся таймер | Провал задачи |
| --- | --- | --- |
| `Timer(limit, job.cancel)` | ещё 15 мс | доходит до зоны |
| `job.done.whenComplete(timer.cancel)` | нет | до зоны не доходит |
| `timeout: limit` | нет | доходит до зоны |

Задача, которая ещё идёт, когда кончается тест, держит свой таймер, как любой
другой: тест под `fakeAsync` или `testWidgets` кончает такую задачу, отменив её
или дождавшись, раньше, чем кончится сам. Нулевой или отрицательный срок
бросает `ArgumentError`, и так же бросает срок вместе с `cancellable: false`:
отмену по сроку задача вправе отклонить, а такая задача отклоняла бы её всегда.

### Срок для одного шага

Страница уходит без миниатюры, если миниатюра рисуется дольше 15 мс,
а `renderThumbnail` рисует её 20. Отдельный шаг получает срок как собственный
ребёнок:

```dart
final thumbnail = Job.deferred<String>(
  renderThumbnail,
  key: 'thumbnail',
  timeout: const Duration(milliseconds: 15),
);
try {
  return 'page with ${await ctx.run(thumbnail)}';
} on Cancelled catch (cancelled) {
  if (cancelled.reason case TimeoutCancelReason(:final timeout)) {
    return 'page without a thumbnail after ${timeout.inMilliseconds} ms';
  } else {
    rethrow;
  }
}
```

```text
outcome: Done(page without a thumbnail after 15 ms)
```

Ребёнок кончается `Cancelled(timeout)`, и `ctx.run` бросает эту отмену в тело
родителя. Сам родитель не отменён: срок вышел у ребёнка. Ветка `catch` в Dart
отбирает только по типу, без шаблона и без `when`, поэтому она ловит любой
`Cancelled`, а шаблон стоит в `if` внутри неё: он узнаёт причину срока
и достаёт его длительность. `else` бросает дальше всё, что не относится
к сроку: отмену самой задачи и миниатюру, которую отменил кто-то другой. Если
ветки нет, срок ребёнка кончает родителя
`Cancelled(handler: Job(thumbnail): Cancelled(timeout))`. Ключ нужен ради этой
строки: ребёнок без ключа печатается как `Job()`.

## Остановка, которая занимает время

Задача ведёт запись с устройства и освобождает его в `onDispose`. Устройство
останавливается не сразу, а пользователь отменяет задачу во время записи.

Остановка запускается работой, которую задача не ждёт:

```dart
ctx.onDispose(device.release);
ctx.onCancel(() => ctx.unattended(device.stop));
await ctx.abandonable(device.record);
```

```text
cancel
device released
outcome: Cancelled(manual)
device stopped
```

`onCancel` принимает `void Function()`. Dart пропустит туда и `async`-функцию,
но задача не узнает, что с ней стало:

1. Future, которую она вернёт, не ждёт никто.
2. Её ошибка уходит мимо наблюдателя в зону, где вызван колбэк. Для отмены,
   принятой внутри `cancel()`, это зона кода, который вызвал `cancel()`.
3. В `onError` попадает только то, что колбэк бросит синхронно,
   а `async`-функция синхронно не бросает никогда: даже ошибка до её первого
   `await` уходит в её future.

`ctx.unattended` оставляет ошибки остановки при задаче: они доходят
до наблюдателя, а после него по умолчанию и до зоны, где задача создана;
подробно он разобран в разделе
[«Работа, которую задача не ждёт»](observing.md#работа-которую-задача-не-ждёт)
страницы о наблюдении. Больше он ничего не делает: остановку задача не ждёт,
и устройство освобождается, пока оно ещё останавливается.

### Дождаться остановки

Чтобы кончиться только после остановки устройства, задача ждёт через `join`
операцию, которую остановка прерывает. Здесь это запись, и она кончается только
тогда, когда устройство остановилось:

```dart
ctx.onDispose(device.release);
ctx.onCancel(() => ctx.unattended(device.stop));
await ctx.join(device.record);
```

```text
cancel
device stopped
device released
outcome: Cancelled(manual)
```

`join` ждёт, пока остановка не закончит запись, так же, как ждёт миграцию
в разделе [«Токен через `onCancel`»](#токен-через-oncancel). Если операция
кончается, как только остановка началась, `join` ждать нечего, и задача
кончается, пока устройство ещё останавливается.
