# Отмена

`cancel()` запрашивает; тело отвечает в контрольной точке. От того, какая это
точка, зависит, что станет с операцией за ней:

```dart
Job<void>((ctx) async {
  // Собственная остановка базы, отменяется вместе с задачей.
  final stop = CancelToken();
  ctx.onCancel(stop.cancel);

  // Ожидание кончается сразу; чтение идёт дальше, а значение отбрасывается.
  final rows = await ctx.wait(database.readAll);

  // Этого дожидаются, пока миграция не кончится или не остановится
  // по токену, и только потом задача сдаётся.
  await ctx.join(() => database.migrate(stop));

  // Отмена ждёт конца всего шага, и запущенный им ребёнок
  // не отменяется; бросит следующая точка.
  await ctx.uncancellable(() async {
    await database.writeVersion();
    await ctx.run(database.readyFlag());
  });

  // Между шагами вычисления оборачивать нечего.
  ctx.check();
  use(rows);
});
```

| Метод | Если отмена приходит во время ожидания |
| --- | --- |
| `ctx.wait(action)` | Сразу бросает `Cancelled`. Действие продолжается; его результат отбрасывается, а если вызову передан `dispose` или `discard`, уходит туда. |
| `ctx.join(action)` | Ждёт действие, затем бросает `Cancelled` вместо возврата значения — или собственную ошибку действия, если оно упало. Если вызову передан `dispose` или `discard`, `join` сперва отдаёт туда значение и дожидается конца освобождения, а потом бросает. |
| `ctx.uncancellable(action)` | Удерживает запрос до конца секции: ни `onCancel`, ни передачи отмены детям, пока она идёт. |
| `ctx.check()` | Бросает, если `Job` уже принял отмену. |

Работающая задача принимает запрос прямо внутри `cancel()`, если его
не придерживает секция `uncancellable` и задача не создана
с `cancellable: false`. Приняв его, задача становится отменённой: её колбэки
`onCancel` вызываются, отмена передаётся запущенным ею детям, и задача кончится
`Cancelled`, что бы тело ни делало дальше. С этого момента `check`, `wait`,
`join`, `uncancellable`, `run` и `each` бросают `Cancelled` на своих
контрольных точках. `onCancel` тоже бросает: его колбэки уже вызваны,
и зарегистрированный сейчас не был бы вызван никогда. `onDispose`, `onDiscard`,
`disown` и `unattended` остаются доступны, чтобы тело могло организовать уборку
после отмены.

Внутри действия, переданного контексту, обычный `await` уместен: контекст
не добавляет контрольных точек между шагами этого действия, и шагу, которому
нужна своя проверка, нужно своё обращение к контексту.

Строки под кодом — то, что он печатает при запуске. База говорит, что пишет,
а наблюдатель задачи печатает то, что до него дошло: `log:` для `ctx.log`,
`onError:` для ошибки. `cancel` — момент, когда пользователь отменяет,
а `outcome:` — то, чем завершается `job.done`. Каждый раздел ниже открывается
версией, к которой ведут имена, — `wait`, чтобы дождаться операции, `join`,
чтобы довести шаг до конца, ветка для `Cancelled`, чтобы пропустить отмену, —
и показывает, что этот код делает. Где исправляющая её версия всё ещё
не дотягивает, она стоит второй попыткой, а рабочая версия идёт следом под
своим заголовком.

## Остановка операции

Задача открывает базу, мигрирует её и отдаёт; `discard` закрывает базу, если
задача кончилась, не отдав её. Миграция — три шага по 10 мс, и перед каждым она
читает `CancelToken`; найдя его отменённым, она останавливается, бросая
`DatabaseStopped`. Когда пользователь отменяет, миграция должна остановиться,
а база — закрыться, когда в неё уже никто не пишет. Пользователь отменяет
на 15-й миллисекунде, во время второго шага.

### Первая попытка

`wait` ждёт миграцию:

```dart
final job = Job<Database>((ctx) async {
  final database = await ctx.join(
    Database.open,
    discard: (database) => database.close(),
  );
  final stop = CancelToken();

  await ctx.wait(() => database.migrate(stop));

  return database;
});
```

```text
step 1
cancel
database closed
outcome: Cancelled(manual)
step 2 on a closed database
step 3 on a closed database
```

`wait` кончает ожидание, а не миграцию. Отмена выходит из `wait` сразу, задача
кончается, и `discard` закрывает базу, когда миграции остаётся записать ещё два
шага. Всё, что миграция бросит потом, уйдёт в `onError`. `wait` — для операции,
от которой задача может уйти: например, для чтения, результат которого уже
никому не нужен.

Результат, пришедший так поздно, отбрасывается, а если `wait` передан `dispose`
или `discard`, уходит туда: если задача ещё завершается, этот колбэк
добавляется в её стек уборки, и задача его дожидается; если задача уже
завершилась, колбэк выполняется отдельно.

### Вторая попытка

`join` остаётся с миграцией до её конца:

```dart
await ctx.join(() => database.migrate(stop));
```

```text
step 1
cancel
step 2
step 3
database closed
outcome: Cancelled(manual)
```

Теперь в закрытую базу никто не пишет: `join` ждёт миграцию, и задача сдаётся
только после неё. Но и остановиться миграции никто не сказал, поэтому она пишет
шаг, который уже никому не нужен, а исход приходит тогда, когда миграция
кончилась бы и так.

### Токен через `onCancel`

Миграция не знает об отмене задачи: она слушает только свой токен. Отменить
токен вместе с задачей можно через `onCancel`:

```dart
final stop = CancelToken();
ctx.onCancel(stop.cancel);

await ctx.join(() => database.migrate(stop));
```

```text
step 1
cancel
step 2
migration stopped
onError: DatabaseStopped
database closed
outcome: Cancelled(manual)
```

`ctx.onCancel(callback)` вызывается синхронно при принятии отмены,
до контрольной точки в теле. Он отменяет токен, миграция читает его перед
третьим шагом и бросает `DatabaseStopped`, а `join` дожидается этого, прежде
чем задача закроет базу. Запрос, который нужно прервать, или подписка, которую
нужно отменить, передаются так же.

Строка `onError:` — это тот самый `DatabaseStopped`. `join` бросает ошибку
своего действия как есть, даже после отмены, а тело её не ловит. Задача всё
равно кончается `Cancelled`, поэтому ошибка — ничей исход: она доходит
до наблюдателя и на нём останавливается, а без наблюдателя её не слышит никто.
Что видит `catch` вокруг этого `join` — предмет раздела о перехвате ниже.

Остановка, которая занимает время, передаётся иначе. `onCancel` принимает
`void Function()`, и Dart пропускает туда `async`-функцию: future, которую она
вернёт, не ждёт никто, и её ошибка уходит в зону мимо наблюдателя. В `onError`
попадает только то, что колбэк бросит синхронно. Для устройства, которое
останавливается не сразу, передайте остановку задаче:

```dart
ctx.onCancel(() => ctx.unattended(device.stop));
```

`ctx.unattended` оставляет ошибки остановки при задаче, и они доходят
до наблюдателя; подробно он разобран в разделе
[«Работа, которую задача не ждёт»](observing.md#работа-которую-задача-не-ждёт)
страницы о наблюдении.

## Шаг, который должен закончиться

Миграция позади, и последний шаг помечает базу готовой: пишет версию схемы,
а затем флаг готовности, и база с версией, но без флага — ни старая,
ни готовая. Две записи — два вызова базы, `writeVersion` и `writeReadyFlag`.
Пользователь отменяет, пока пишется версия.

### Первая попытка

`join` ждёт своё действие, поэтому каждая запись идёт через него:

```dart
await ctx.join(database.writeVersion);
await ctx.join(database.writeReadyFlag);
```

```text
cancel
version written
outcome: Cancelled(manual)
```

Шаг не доходит до конца: база остаётся с версией, но без флага готовности.
Каждый `join` — отдельная контрольная точка. Первый дожидается версии и бросает
отмену, и до второго тело не доходит.

### Один `join` на шаг

```dart
await ctx.join(() async {
  await database.writeVersion();
  await database.writeReadyFlag();
});
```

```text
cancel
version written
ready flag written
outcome: Cancelled(manual)
```

Внутри действия контрольных точек нет, поэтому обе записи сделаны, а отмена
выходит из `join` уже после них. Этого хватает, пока шаг — обычный код: он
не берёт токен, который отменяет `onCancel`, не запускает дочерних задач
и не проходит контрольных точек контекста.

### Придержать отмену

Шаг, который сам пользуется задачей, — другое дело. Пусть флаг пишет отдельная
задача, `database.readyFlag()`, и шаг запускает её дочерней:

```dart
await ctx.join(() async {
  await database.writeVersion();
  await ctx.run(database.readyFlag());
});
```

```text
cancel
version written
outcome: Cancelled(manual)
```

Флаг снова потерян. `join` ждёт своё действие, но задача принимает отмену
сразу, и дальше `ctx.run` бросает её вместо того, чтобы запустить ребёнка; уже
запущенный ребёнок был бы отменён. `uncancellable` придерживает отмену, пока
шаг не кончится:

```dart
await ctx.uncancellable(() async {
  await database.writeVersion();
  await ctx.run(database.readyFlag());
});
```

```text
cancel
version written
ready flag written
outcome: Cancelled(manual)
```

Пока идёт секция, задача отмену не принимает: `ctx.run` запускает ребёнка, дети
задачи не отменяются, и `onCancel` не вызывается. Удерживает, а не отклоняет:
задача принимает отмену в тот момент, когда секция закрывается, и следующая
контрольная точка её бросает. Задача всё равно кончается `Cancelled`, даже если
тело вернёт значение, поэтому всему, что должно случиться после шага в любом
случае, место внутри той же секции.

Всегда ожидайте `ctx.uncancellable`. Секция открывается при вызове, даже если
её future не ждут. Без `await` секция может пережить тело; если задача
завершится раньше, удержанная отмена потеряется и `cancel()` вернётся с исходом
`Done`.

Если нужно защитить всё тело, а не одну секцию, создайте
`Job(body, cancellable: false)`. Он отклоняет обычную отмену после запуска
тела, но до запуска его всё ещё можно отменить. `solo`, построенный на этом
ядре, отменяет задачу ещё и тогда, когда состояние контроллера перестаёт ей
подходить: задача там сама объявляет, в каких состояниях она работает. Такую
отмену не удерживают ни секция, ни `cancellable: false`.

## Перехват ошибок операции

Неудачная миграция здесь не смертельна: тело пишет её в лог и идёт дальше —
помечать базу готовой. Отменённая задача всё равно должна остановиться,
а в логе должны быть сбои, а не отмены. Токен подключён через `onCancel`, как
выше, и пользователь отменяет на 15-й миллисекунде.

### Первая попытка

Отмена бросает `Cancelled`, поэтому ветка для него стоит первой и пробрасывает
его дальше:

```dart
try {
  await ctx.join(() => database.migrate(stop));
} on Cancelled {
  rethrow;
} on Exception catch (error) {
  ctx.log('migration failed: $error');
}
await ctx.join(() async {
  await database.writeVersion();
  await database.writeReadyFlag();
});
```

```text
step 1
cancel
step 2
migration stopped
log: migration failed: DatabaseStopped
outcome: Cancelled(manual)
```

Лог называет отмену неудачной миграцией. Миграцию остановил токен, и из `join`
вышел собственный `DatabaseStopped` миграции, а не `Cancelled`: `join` бросает
ошибку своего действия как есть. Ветка для `Cancelled` его пропускает, его
ловит `on Exception`, и код этой ветки выполняется на уже отменённой задаче.
Задача всё равно кончается `Cancelled`: `join` следующего шага бросает,
не начав своё действие. Без токена ветка для `Cancelled` работает: миграция
доходит до конца, и `join` бросает `Cancelled`. Без этой ветки `on Exception`
ловит и этот `Cancelled`, потому что `Cancelled` реализует `Exception`, и пишет
`migration failed: Cancelled(manual)`.

### Спросить задачу

Отменена ли задача — вопрос к задаче, а не к ошибке:

```dart
try {
  await ctx.join(() => database.migrate(stop));
} on Exception catch (error) {
  ctx.check();
  ctx.log('migration failed: $error');
}
```

```text
step 1
cancel
step 2
migration stopped
outcome: Cancelled(manual)
```

`ctx.check()` бросает отмену задачи, если та её приняла, что бы ни поймал
`catch`. Миграция, упавшая сама, пишется в лог, и тело идёт дальше. Строки
`onError: DatabaseStopped`, как в разделе о токене, здесь нет:
`DatabaseStopped` ловит `on Exception`, и из тела он не выходит. Тело кончается
отменой задачи из `ctx.check()`, а отмена в `onError` не попадает. Если ветка
должна ловить всё, включая `Error`, как `on Object catch (error)`, первой
строкой в ней нужен тот же `ctx.check()`.

Если задача уже приняла отмену, перехват её `Cancelled` эту отмену не снимает.
Код после `catch` выполняется, но следующая контрольная точка снова бросает,
и исходом всё равно будет `Cancelled`, даже если тело вернёт значение.

`Cancelled`, перехваченный в теле, не всегда принадлежит самой задаче. Дочерняя
задача, запущенная через `ctx.run` и отменённая напрямую, а не через родителя,
бросает свой `Cancelled` из `run`. Если эта дочерняя задача была
необязательной, `ctx.check()` проходит, и тело идёт дальше без неё и кончается
`Done`. Ветка, которая пробрасывает любой `Cancelled`, отменяет и родителя,
с `Cancelled(handler)`; эту причину разбирает раздел
[«Почему задачу отменили»](outcomes.md#почему-задачу-отменили) страницы
об исходах.
