# Отмена

`cancel()` запрашивает; тело отвечает в контрольной точке. От того, какая это
точка, зависит, что станет с операцией за ней:

```dart
Job<void>((ctx) async {
  // Собственная остановка базы, отменяется вместе с задачей.
  final stop = CancelToken();
  ctx.onCancel(stop.cancel);

  // Ожидание кончается сразу; чтение идёт дальше, а его значение
  // отбрасывается или уходит в колбэк освобождения.
  final rows = await ctx.wait(database.readAll);

  // Этого дожидаются, пока миграция не кончится или не встанет
  // по токену, и только потом задача сдаётся.
  await ctx.join(() => database.migrate(stop));

  // Отмена ждёт, пока это не кончится: onCancel не вызывается,
  // поэтому токен остаётся как был, а потом её бросит следующая точка.
  await ctx.uncancellable(() => database.markReady(stop));

  // Между шагами вычисления оборачивать нечего.
  ctx.check();
  use(rows);
});
```

| Метод | Если отмена приходит во время ожидания |
| --- | --- |
| `ctx.wait(action)` | Сразу бросает `Cancelled`. Действие продолжается; его результат отбрасывается или уходит в колбэк освобождения. |
| `ctx.join(action)` | Ждёт действие, затем бросает `Cancelled` вместо возврата значения — или собственную ошибку действия, если оно упало. Колбэк освобождения для значения дожидается первым. |
| `ctx.uncancellable(action)` | Удерживает запрос до конца секции: ни `onCancel`, ни передачи отмены детям, пока она идёт. |
| `ctx.check()` | Бросает, если `Job` уже принял отмену. |

Работающая задача принимает запрос прямо внутри `cancel()`, если его
не придерживает секция `uncancellable` и задача не создана
с `cancellable: false`. Приняв его, задача становится отменённой: её колбэки
`onCancel` вызываются, отмена передаётся запущенным ею детям, и задача кончится
`Cancelled`, что бы тело ни делало дальше. С этого момента `check`, `wait`,
`join`, `uncancellable`, `run` и `each` бросают `Cancelled` на своих
контрольных точках. `onCancel` тоже бросает: его колбэки уже вызваны,
и зарегистрированный сейчас не был бы вызван никогда. `onDispose`, `onDiscard`,
`disown` и `unattended` остаются доступны, чтобы тело могло организовать уборку
после отмены.

Внутри действия, переданного контексту, обычный `await` уместен: контекст
не добавляет контрольных точек между шагами этого действия, и шагу, которому
нужна своя проверка, нужно своё обращение к контексту.

Строки под кодом — то, что он печатает при запуске. База говорит, что пишет,
а наблюдатель задачи печатает то, что до него дошло: `log:` для `ctx.log`,
`onError:` для ошибки. `cancel` — момент, когда пользователь отменяет,
`outcome:` — то, чем завершается `job.done`, а `zone:` — ошибка, дошедшая
до зоны неперехваченной. Каждый раздел ниже открывается версией, к которой
ведут имена, — `wait`, чтобы дождаться операции, `join`, чтобы довести шаг
до конца, ветка для `Cancelled`, чтобы пропустить отмену, `unawaited` из Dart
для работы, которую никто не ждёт, — и показывает, что этот код делает. Где
исправляющая её версия всё ещё не дотягивает, она стоит второй попыткой,
а рабочая версия идёт следом под своим заголовком.

## Остановка операции

Задача открывает базу, мигрирует её и отдаёт; `discard` закрывает базу, если
задача кончилась, не отдав её. Миграция — три шага по 10 мс, и перед каждым она
читает `CancelToken`. Когда пользователь отменяет, миграция должна встать,
а база — закрыться, когда в неё уже никто не пишет. Пользователь отменяет
на 15-й миллисекунде, во время второго шага.

### Первая попытка

`wait` ждёт миграцию:

```dart
final job = Job<Database>((ctx) async {
  final database = await ctx.join(
    Database.open,
    discard: (database) => database.close(),
  );
  final stop = CancelToken();

  await ctx.wait(() => database.migrate(stop));

  return database;
});
```

```text
step 1
cancel
database closed
outcome: Cancelled(manual)
step 2 on a closed database
step 3 on a closed database
```

`wait` кончает ожидание, а не миграцию. Отмена выходит из `wait` сразу, задача
кончается, и `discard` закрывает базу, когда миграции остаётся записать ещё два
шага. Всё, что миграция бросит потом, уйдёт в `onError`. `wait` — для операции,
от которой задача может уйти: например, для чтения, результат которого уже
никому не нужен.

Результат, пришедший так поздно, отбрасывается или передаётся колбэку
освобождения, переданному в `wait`: если задача ещё завершается, колбэк
добавляется в её стек уборки, и задача его дожидается; если задача уже
завершилась, колбэк выполняется отдельно.

### Вторая попытка

`join` остаётся с миграцией до её конца:

```dart
await ctx.join(() => database.migrate(stop));
```

```text
step 1
cancel
step 2
step 3
database closed
outcome: Cancelled(manual)
```

Теперь в закрытую базу никто не пишет: `join` ждёт миграцию, и задача сдаётся
только после неё. Но и остановиться миграции никто не сказал, поэтому она пишет
шаг, который уже никому не нужен, а исход приходит тогда, когда миграция
кончилась бы и так.

### Токен через `onCancel`

Отмена задачи до операции за ней не доходит; чтобы остановить операцию, нужен
её собственный механизм — здесь токен:

```dart
final stop = CancelToken();
ctx.onCancel(stop.cancel);

await ctx.join(() => database.migrate(stop));
```

```text
step 1
cancel
step 2
migration stopped
onError: DatabaseStopped
database closed
outcome: Cancelled(manual)
```

`ctx.onCancel(callback)` вызывается синхронно при принятии отмены,
до контрольной точки в теле. Он отменяет токен, миграция читает его перед
третьим шагом и встаёт, а `join` дожидается этого, прежде чем задача закроет
базу. Запрос, который нужно прервать, или подписка, которую нужно отменить,
передаются так же.

Миграция встаёт, бросая `DatabaseStopped`, а `join` бросает ошибку своего
действия как есть, даже после отмены. Задача всё равно кончается `Cancelled`,
поэтому ошибка — ничей исход: она доходит до наблюдателя и на нём
останавливается, а без наблюдателя её не слышит никто. Что видит `catch` вокруг
этого `join` — предмет раздела о перехвате ниже.

## Шаг, который должен закончиться

Миграция позади, и последний шаг помечает базу готовой: `markReady` пишет
версию схемы, а затем флаг готовности, и база с версией, но без флага —
ни старая, ни готовая. `markReady` берёт токен миграции, и пользователь
отменяет, пока пишется версия.

### Первая попытка

`join` ждёт всё действие:

```dart
final stop = CancelToken();
ctx.onCancel(stop.cancel);

await ctx.join(() => database.markReady(stop));
```

```text
cancel
version written
marking stopped
onError: DatabaseStopped
outcome: Cancelled(manual)
```

`join` ждёт весь `markReady`, а `markReady` всё равно встаёт на полпути. `join`
отмену не придерживает: задача принимает её, как только она пришла, `onCancel`
отменяет токен, и `markReady` читает его между двумя записями. База остаётся
с версией и без флага готовности.

### Придержать отмену

```dart
await ctx.uncancellable(() => database.markReady(stop));
```

```text
cancel
version written
ready flag written
outcome: Cancelled(manual)
```

`uncancellable` удерживает запрос до конца секции. Пока идёт `markReady`,
задача её не принимает: `onCancel` не вызывается, токен остаётся как был,
и дочерняя задача, запущенная телом, не отменяется. Удерживает, а не отклоняет:
задача принимает её в тот момент, когда секция закрывается, и следующая
контрольная точка её бросает. Задача всё равно кончается `Cancelled`, даже если
тело вернёт значение, поэтому всему, что должно случиться после шага в любом
случае, место внутри той же секции.

Всегда ожидайте `ctx.uncancellable`. Секция открывается при вызове, даже если
её future не ждут. Без `await` секция может пережить тело; если задача
завершится раньше, удержанная отмена потеряется и `cancel()` вернётся с исходом
`Done`.

Если нужно защитить всё тело, а не одну секцию, создайте
`Job(body, cancellable: false)`. Он отклоняет обычную отмену после запуска
тела, но до запуска его всё ещё можно отменить. `solo`, построенный на этом
ядре, отменяет задачу и по своим правилам, и их не удерживают ни секция,
ни `cancellable: false`.

## Перехват ошибок операции

Неудачная миграция здесь не смертельна: тело пишет её в лог и идёт дальше —
помечать базу готовой. Отменённая задача всё равно должна встать, а в логе
должны быть сбои, а не отмены. Токен подключён через `onCancel`, как выше,
и пользователь отменяет на 15-й миллисекунде.

### Первая попытка

Отмена бросает `Cancelled`, поэтому ветка для него стоит первой и пробрасывает
его дальше:

```dart
try {
  await ctx.join(() => database.migrate(stop));
} on Cancelled {
  rethrow;
} on Exception catch (error) {
  ctx.log('migration failed: $error');
}
await ctx.uncancellable(() => database.markReady(stop));
```

```text
step 1
cancel
step 2
migration stopped
log: migration failed: DatabaseStopped
outcome: Cancelled(manual)
```

Лог называет отмену неудачной миграцией. Миграцию остановил токен, и из `join`
вышел собственный `DatabaseStopped` миграции, а не `Cancelled`: `join` бросает
ошибку своего действия как есть. Задача всё равно кончается `Cancelled` —
`uncancellable` бросает до начала `markReady`, — но код между `catch` и этой
точкой выполняется на отменённой задаче. Без токена ветка работает: миграция
доходит до конца, и `join` бросает `Cancelled`. Без ветки `on Exception` ловит
и этот `Cancelled`, потому что `Cancelled` реализует `Exception`, и пишет
`migration failed: Cancelled(manual)`.

### Спросить задачу

Отменена ли задача — вопрос к задаче, а не к ошибке:

```dart
try {
  await ctx.join(() => database.migrate(stop));
} on Exception catch (error) {
  ctx.check();
  ctx.log('migration failed: $error');
}
```

```text
step 1
cancel
step 2
migration stopped
outcome: Cancelled(manual)
```

`ctx.check()` бросает отмену задачи, если та её приняла, что бы ни поймал
`catch`. Миграция, упавшая сама, пишется в лог, и тело идёт дальше. Строка
`onError: DatabaseStopped` остановленной миграции выше тоже пропала: тело
сдаётся с отменой задачи, а не с ошибкой миграции. Тот же `ctx.check()`
работает и в ветке `on Object`.

Если задача уже приняла отмену, перехват её `Cancelled` эту отмену не снимает.
Код после `catch` выполняется, но следующая контрольная точка снова бросает,
и исходом всё равно будет `Cancelled`, даже если тело вернёт значение.

`Cancelled`, перехваченный в теле, не всегда принадлежит самой задаче. Дочерняя
задача, запущенная через `ctx.run` и отменённая напрямую, а не через родителя,
бросает свой `Cancelled` из `run`. Если эта дочерняя задача была
необязательной, `ctx.check()` проходит, и тело идёт дальше без неё и кончается
`Done`. Ветка, которая пробрасывает любой `Cancelled`, отменяет и родителя,
с `Cancelled(handler)`; см. [Исходы](outcomes.md).

## Работа, которую задача не ждёт

Когда миграция позади, задача отправляет событие аналитики и не ждёт его.
Наблюдатель задачи — то место, где приложение узнаёт об ошибках задачи,
а отправка падает: аналитика недоступна.

### Первая попытка

`unawaited` из Dart помечает future, который намеренно не ждут:

```dart
unawaited(analytics.send('migrated'));
```

```text
outcome: Done(null)
zone: Bad state: analytics offline
```

Наблюдатель не слышит ничего: ошибка future, которого никто не ждёт, уходит
в зону как неперехваченная; `unawaited` лишь говорит анализатору, что
не ждать — намеренно.

### Работа, переданная задаче

```dart
ctx.unattended(() => analytics.send('migrated'));
```

```text
outcome: Done(null)
onError: Bad state: analytics offline
```

`ctx.unattended(action)` оставляет ошибки работы при задаче, даже после её
завершения: они передаются наблюдателю, а без него — в зону, где задача
создана. Задача работу не ждёт и не отменяет.

Асинхронная остановка, переданная в `onCancel`, — та же работа. `onCancel`
принимает `void Function()`, и Dart пропускает туда `async`-функцию: future,
который она вернёт, не ждёт никто, и его ошибка уходит в зону мимо наблюдателя.
В `onError` попадает только то, что колбэк бросит синхронно. Для устройства,
которое останавливается не сразу, передайте остановку задаче:

```dart
ctx.onCancel(() => ctx.unattended(device.stop));
```

Запускайте работу внутри колбэка и ничего из него не выносите: работа идёт
в собственной зоне ошибок, и граница держит в обе стороны. Если future создан
снаружи, а ждут его внутри, то при ошибке он не возвращается никогда, а его
ошибка уходит в зону, где он создан. Если future создан внутри, а ждут его
снаружи, то при ошибке он вешает того, кто его ждёт, — а если его ждёт тело,
то и задачу.
