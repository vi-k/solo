# Наблюдение и тестирование

Исход говорит, чем задача кончилась. `JobObserver` слышит остальное: когда
задача начинается и кончается, что её тело пишет в лог, и ошибки, которых
не несёт ни один исход. Последний раздел показывает, как тестировать задачу,
не ожидая в реальном времени.

Строки под кодом показывают, что он печатает:

- `cancel`: пользователь отменяет задачу;
- `outcome:` то, чем завершается `job.done`;
- `onError:` ошибка, которую слышит наблюдатель;
- `onUnanswered:` ошибка, за которую наблюдатель ответил;
- `zone:` ошибка, дошедшая до зоны неперехваченной.

## Наблюдатель

Задача загружает число. Её наблюдатель печатает, чем задача кончилась и что
тело записало в лог:

```dart
final class Log extends JobObserver {
  @override
  void onFinish(Job<Object?> job) => print('$job: ${job.outcome}');

  @override
  void onLog(Job<Object?> job, Object? message) {
    final data = message is Object? Function() ? message() : message;
    print('$job: $data');
  }
}

final job = Job<int>(
  key: 'load',
  observer: Log(),
  (ctx) async {
    ctx.log('loading');
    return ctx.abandonable(load);
  },
);
```

```text
Job(load): loading
Job(load): Done(3)
```

У `JobObserver` четыре хука: `onStart`, `onFinish`, `onError` и `onLog`. Первые
три задача вызывает сама. Сообщения для `onLog` тело отправляет через
`ctx.log(message)`. `onFinish` вызывается для каждой задачи, даже для
отменённой до старта. `onStart` вызывается только для задачи, которая
стартовала.

По умолчанию хуки ничего не делают, поэтому наблюдатель переопределяет только
те, что ему нужны. Наблюдатель, который ещё и отвечает за ошибки, подмешивает
`JobAnswerer`, а с ним пятый хук, `onUnanswered`; о нём раздел
[«Ответ за ошибки»](#ответ-за-ошибки) ниже. Класс, который уже наследует другой
класс, подмешивает наблюдателя через `with JobObserver` или
`with JobObserver, JobAnswerer` и так же переопределяет хуки.

Наблюдателя передаёт при создании задачи тот, кто её запускает. Дочерние
задачи, которые она запускает, наследуют его, если у них нет своего.
Продолжение, созданное через `then`, получает только наблюдателя, переданного
в `then`.

Если хук бросит исключение, оно попадёт в текущую зону, и больше ничего
не изменится: задача кончится так же, как кончилась бы, а остальные хуки всё
равно будут вызваны. `Cancelled`, брошенный хуком, в зону не попадает и задачу
не отменяет. Чтобы отменить задачу из хука, вызовите `job.cancel()`: задача
отменится так же, как при вызове из любого другого места.

При создании задаче можно дать ключ `key` и колбэк `describe`. Строковое
представление задачи такое:

- `Job($key)`, если есть ключ;
- `Job($key: $description)`, если есть ключ и `describe` возвращает непустое
  описание;
- `Job($description)`, если такое описание есть, а ключа нет;
- `Job()`, если нет ни того, ни другого.

Используйте `key`, чтобы обозначить задачу в логе или в правилах планирования
библиотеки, например в политиках очереди `solo`. `describe` добавляет
к обозначению подробности.

Если бросает `toString` ключа или сам `describe`, на его месте печатается
метка: `Job(load: <describe threw StateError>)`. Ядро называет задачи
в собственных сообщениях об ошибках, и сломанное имя не занимает место
сообщения. Саму ошибку имени ядро всё равно сообщает, в двух местах. Когда ядро
называет дочернюю задачу в отмене родителя, ошибка идёт, как сказано в строке 4
таблицы ниже. Когда задачу называет строка отладочного канала, ошибка идёт
в зону.

От отменённой задачи ждут, что она скоро кончится. Та, что работает дальше,
занята делом, от которого пользователь уже отказался. Наблюдатель находит такие
задачи, засекая, сколько каждая проработала после отмены:

```dart
final class SlowCancellations extends JobObserver {
  final _since = Expando<Stopwatch>('cancellation');

  @override
  void onStart(Job<Object?> job) =>
      job.whenCancelled((_) => _since[job] = Stopwatch()..start());

  @override
  void onFinish(Job<Object?> job) {
    final watch = _since[job];
    if (watch != null) {
      print('$job ran ${watch.elapsedMilliseconds} ms past its cancellation');
    }
  }
}
```

`Job.whenCancelled`, зарегистрированный в `onStart`, срабатывает, когда задача
принимает отмену. `onFinish` срабатывает, когда приходит исход. Время между
ними показывает, сколько задача проработала после отмены, вместе с дочерними
задачами и уборкой. Счёт определяют три вещи:

- Если тело ждёт что-то долгое голым `await`, остаток этого ожидания попадает
  в счёт. Тот же вызов через `ctx.abandonable` показывает 0 мс.
- Счёт идёт с момента, когда задача приняла отмену, а не с вызова `cancel()`.
  `ctx.uncancellable` придерживает отмену, и задача принимает её, когда секция
  кончится: секция на 100 мс, отменённая на 10-й миллисекунде, показывает 0 мс,
  хотя вызвавший `cancel` ждал 90 мс.
- Тело, которое сдаётся само, бросая `Cancelled` или выпуская наружу отмену
  дочерней задачи, принимает отмену в момент броска, и счёт идёт оттуда.

## Сообщение для лога

Тело мигрирует базу. Когда миграция падает, оно пишет в лог пойманную ошибку
`error`. Тот, кто отлаживает приложение, даёт задаче наблюдателя. В релизной
сборке его нет, и там сообщение не должно стоить ничего.

### Первая попытка

`log` принимает сообщение, и строка годится в сообщение:

```dart
// Первая попытка: строка собирается впустую.
ctx.log('migration failed: $error');
```

Без наблюдателя `ctx.log` ничего не делает, но строка к этому моменту уже
построена: Dart вычисляет аргумент до вызова, поэтому `error.toString()`
выполняется впустую.

### Форматирование остаётся наблюдателю

```dart
ctx.log(() => 'migration failed: $error');
```

Колбэк откладывает построение сообщения. `ctx.log` передаёт колбэк дальше без
изменений, как любой другой объект, поэтому без наблюдателя ничего не строится.
Если наблюдатель есть, то вызовет ли он колбэк, зависит от его соглашения:
`Log` выше вызывает колбэк и печатает то, что тот вернул, а наблюдатель,
который печатает каждое сообщение как пришло, напечатал бы сам колбэк. Если
передать один `error`, форматирование тоже останется наблюдателю, и никакого
соглашения не нужно.

## Куда уходят ошибки

Приложение сообщает о каждой ошибке, которая дошла до его зоны неперехваченной.
Задача мигрирует базу, а отмена останавливает миграцию по её токену, как
в разделе [«Токен через `onCancel`»](cancellation.md#токен-через-oncancel)
страницы об отмене. Пользователь отменяет, пока миграция идёт.

### Первая попытка

Dart отправляет в зону ошибку, которую никто не поймал, поэтому приложение
полагается на зону, наблюдателя задаче не даёт и связывает токен так же, как
страница об отмене:

```dart
// Первая попытка: каждая отмена доходит до зоны как сбой.
final job = Job<void>((ctx) async {
  final stop = CancelToken();
  ctx.onCancel(stop.cancel);

  await ctx.join(() => database.migrate(stop));
});
```

```text
cancel
zone: DatabaseStopped
outcome: Cancelled(manual)
```

Ничего не сломалось, а зона сообщает о сбое при каждой отмене. Вот что
происходит:

1. Задача принимает отмену, и `onCancel` отменяет токен. С этого момента она
   кончится `Cancelled`, что бы ни сделала миграция.
2. Миграция останавливается по токену и бросает свой `DatabaseStopped`,
   а `join` бросает его как есть. Тело падает с этой ошибкой на уже отменённой
   задаче.
3. Исходом эта ошибка не становится: исход несёт отмену. Задача отвечает
   за неё, как за любой провал своего тела, который исход не несёт: её
   услышал бы `onError` наблюдателя, а дальше она идёт к ответу, и без
   наблюдателя ответ — зона.

Задача не может знать, что это за ошибка. Здесь операция остановилась по токену
задачи. Но настоящий сбой после отмены идёт тем же путём, и его услышать нужно:
если база после отмены оказалась заблокирована, приложение должно об этом
узнать.

### Ошибки отмены

Ошибкой отмены называется ошибка, которую операция бросает потому, что её
остановила отмена задачи: `DatabaseStopped` от токена, который отменил
`ctx.onCancel`, или `DioException` из `dio`, для которой выполняется
`CancelToken.isCancel`. Приложение называет такие ошибки один раз, в `main`:

```dart
Job.isCancellationError = (error) => error is DatabaseStopped;
```

```text
cancel
outcome: Cancelled(manual)
```

Задача осталась прежней. `Job.isCancellationError` спрашивают о каждом провале
задачи, которая приняла отмену. Спрашивают, когда задача собирается отправить
провал к ответу, и только тогда. Названная им ошибка по-прежнему доходит
до `onError` и дальше не идёт: её не слышат ни `onUnanswered`, ни зона. Исходов
фильтр тоже не меняет. О провале задачи, которую никто не отменял, его
не спрашивают: тело, которое бросает `DatabaseStopped`, пока его задача идёт
дальше, кончается с ним `Failed`, и если этот исход никто не наблюдает, он
доходит до зоны. Токен тогда отменил кто-то другой, и задача должна об этом
сказать.

Фильтр вызывается синхронно, с одним провалом за раз и никогда с `Cancelled`,
поэтому пусть он только проверяет тип. Задача обходит `ParallelWaitError`
и спрашивает о каждом провале внутри него отдельно. Если фильтр бросил, это
ошибка приложения: она уходит в зону, где создана задача, а провал, о котором
его спрашивали, идёт дальше к ответу.

Поле принадлежит приложению, как `Job.debug`, и библиотека его не ставит. Если
свои ошибки называют две части приложения, вторая продолжает цепочку первой:

```dart
final previous = Job.isCancellationError;
Job.isCancellationError =
    (error) => error is DatabaseStopped || (previous?.call(error) ?? false);
```

Тест, который ставит поле, возвращает его в `tearDown`, как вернул бы
`Job.debug`.

Фильтр не видит ошибку, которую Dart отдаёт зоне сам, мимо задачи: ошибку
вызова контекста, которого тело не дождалось, например
`unawaited(ctx.join(() => database.migrate(stop)))`, и ошибку `async`-колбэка
`ctx.onCancel`. Их разбирают строка 7 таблицы ниже и раздел
[«Токен через `onCancel`»](cancellation.md#токен-через-oncancel).

Ошибка, которую тело делает из собственной отмены, до фильтра тоже доходит,
но проверка типа выше её не узнаёт. Тело, которое ловит всё вокруг
`ctx.abandonable` и бросает вместо пойманного свою ошибку, например
`throw AppException(error)`, заворачивает каждый `Cancelled` в `AppException`,
и зона слышит его при каждой отмене. Фильтр называет обёртку по причине:
`(error) => error is AppException && error.cause is Cancelled`.

Вместо этого `catch` может первым делом вызвать `ctx.check()`, как в разделе
[«Спросить задачу»](cancellation.md#спросить-задачу) страницы об отмене: тогда
наружу уходит сама отмена, а отмена не провал. Это обходится дороже фильтра.
Когда задача приняла отмену, `ctx.check()` бросает её, что бы ни поймал
`catch`. Тело, которое ждёт через `ctx.join`, так теряет настоящий провал,
дошедший до `catch` после отмены: например, открытие, которое нашло базу
заблокированной. Его не слышат ни `onError`, ни зона. Фильтр не пускает только
те ошибки, которые называет.

Фильтр только не пускает ошибки к ответу, и `ctx.runAll` это показывает. Ветка,
которую отменили снаружи и чьё тело бросило ошибку отмены, для группы упала,
поэтому группа отменяет остальные ветки с `SiblingCancelReason`, у которой
причиной стоит эта ошибка. Ветка, которую никто не отменял и которая кончилась
`Failed` с такой ошибкой, считается обычным провалом: группа бросает её ошибку
вместо отмены другой ветки, и тело родителя получает эту ошибку,
а не `Cancelled`.

### С наблюдателем

Ещё приложение хочет видеть ошибки своих задач по мере того, как они случаются.
Задача открывает базу, пользователь отменяет, пока она открывается, а затем
открытие падает: база заблокирована.

```dart
final class Reporter extends JobObserver {
  @override
  void onError(Job<Object?> job, Object error, StackTrace stackTrace) =>
      print('onError: $error');
}

final job = Job<Database>(
  observer: Reporter(),
  (ctx) => ctx.join(
    Database.open,
    discard: (database) => database.close(),
  ),
);
```

```text
cancel
onError: Bad state: database locked
zone: Bad state: database locked
outcome: Cancelled(manual)
```

Наблюдатель слышит через `onError` ошибки, которые ловит его задача, кроме её
собственной отмены. Но только слышит: переопределение `onError` никуда ошибку
не переносит. Упавшее открытие всё равно доходит до зоны, как дошло бы без
наблюдателя: задача кончается `Cancelled`, а фильтр выше `StateError`
не называет.

Исход считается наблюдаемым, когда кто-то читает `done` или `value`, вызывает
`ignoreFailure()` или передаёт провал дальше через `then`: продолжение, которое
отменили раньше, чем упал его источник, ничего не передаёт, и провал остаётся
ненаблюдаемым. Об этом раздел
[«Ошибка, которую никто не ждёт»](outcomes.md#ошибка-которую-никто-не-ждёт)
страницы об исходах. Хуки наблюдателя исход не наблюдают, даже хук, который
читает `job.outcome`, как `onFinish` у `Log` выше.

Таблица показывает, куда уходит каждая ошибка, с наблюдателем и без него.
«Зона» здесь та, где задача создана. «Ответ» означает `onUnanswered`, если
наблюдатель отвечает за ошибки, и зону, если не отвечает.

| Ошибка | С наблюдателем | Без него |
| --- | --- | --- |
| 1. Ошибка тела, и задача кончается с ней `Failed` | `onError`, а если исход никто не наблюдал, то и зона | Зона, если исход никто не наблюдал |
| 2. Ошибка тела, и задача кончается `Cancelled` | `onError`, затем ответ | Зона |
| 3. Ошибка тела в ветке `ctx.runAll`, чья группа бросает другой провал | `onError`, затем ответ | Зона |
| 4. Ошибка вне тела, в местах из списка ниже | `onError`, затем ответ | Зона |
| 5. `Cancelled`, брошенный вне тела | `onError` | Никто |
| 6. Собственная отмена задачи из действия, ожидание которого прервал `ctx.abandonable`, или из работы `ctx.unattended` | Никто | Никто |
| 7. Ошибка вызова контекста, сделанного телом без `await` (см. ниже) | Зона, где идёт тело | Зона, где идёт тело |

Строки 4 и 7 охватывают только эти случаи:

- Строка 4: поздняя ошибка действия, ожидание которого прервал
  `ctx.abandonable`; уборка; колбэк `ctx.onCancel`, `job.whenCancelled` или
  `job.whenFinished`; работа `ctx.unattended`; `toString` ключа дочерней
  задачи, её `describe` или её `Cancelled`, когда ядро называет её в отмене
  родителя.
- Строка 7: ошибка уходит в зону, где идёт тело, как у любой future, которую
  никто не ждёт. Это касается и собственной отмены задачи. У `ctx.abandonable`
  так бывает, только пока тело не кончилось.

Ошибка, которую называет `Job.isCancellationError`, в строках 2 и 4 дальше
`onError` не идёт, если задача приняла отмену, откуда бы ошибка ни пришла:
из тела, из шага `ctx.uncancellable`, из дочерней задачи, которую задача ждала,
из уборки.

Вызов контекста, сделанный телом без `await`, бросает в future, которую никто
не ждёт. Dart отдаёт эту ошибку зоне, где идёт тело; у задачи, созданной через
`Job.deferred`, это зона, откуда её запустили. Туда же уходит и собственная
отмена задачи: когда задачу отменяют, `ctx.abandonable`, вызванный без `await`,
бросает `Cancelled` в свою future, и Dart отдаёт его зоне, как любую другую
ошибку. Эту отмену в зону отправляет не задача, а Dart.

У `ctx.abandonable`, вызванного без `await`, так бывает, только пока тело идёт.
Если его действие упадёт, когда тело уже кончилось, ошибка идёт по строке 4
таблицы, как у действия, которое `ctx.abandonable` перестал ждать из-за отмены:
её слышит `onError`, а дальше она идёт туда же, куда другие ошибки вне тела.

Ошибка может дойти и до `onError`, и до зоны, и приложение, которое сообщает
об ошибках в обоих местах, услышит её дважды. Таблица показывает два пути
в зону. Первый: исход никто не наблюдал. Второй: за ошибку никто не отвечает
или `onUnanswered` отправляет её дальше. Первый путь закрывается наблюдением
исхода. Второй — наблюдателем, который отвечает (`with JobAnswerer`).

Исход не несёт двух видов провалов тела, и они уходят в `onUnanswered` или
в зону, даже если исход наблюдали: задача кончается `Cancelled`, и исход несёт
отмену (строка 2); или упала ветка `ctx.runAll`, а группа бросила другую ошибку
(строка 3). Такой провал отпускается вызовом `ignoreFailure()` у задачи, чьё
тело упало: `onError` его по-прежнему услышит, но ни до `onUnanswered`,
ни до зоны он не дойдёт. `ignoreFailure()` отпускает провалы только этой
задачи: дочерняя задача, чьё тело упало, отвечает за свой провал сама, что бы
ни вызвал её родитель.

При отладке ошибки, которые задача отдаёт своему наблюдателю, видны и без
наблюдателя: их показывает отладочный канал. `Job.debug = print;` печатает
запуск, отмену и конец каждой задачи. Ещё он печатает каждую такую ошибку, есть
у задачи наблюдатель или нет, а если ошибка ушла дальше в зону, говорит
и об этом. `ParallelWaitError` занимает одну строку, целиком, тогда как
`onError` слышит каждый провал внутри него по отдельности. Для первой попытки
выше канал печатает `Job() error: DatabaseStopped` после отмены и до конца
задачи, а после конца сообщает, что ошибка ушла в зону. С фильтром он печатает
`Job() kept a cancellation error out of the answer: DatabaseStopped` вместо
зоны: фильтр один на всё приложение, и по каналу видно, почему ошибка так
и не дошла до зоны. Канал один на все задачи приложения и говорит с тем, кто
читает консоль. Через наблюдателя приложение слышит то, на что ему надо
отреагировать.

## Работа, которую задача не ждёт

Задача отправляет событие аналитики и не ждёт его. Отправка падает: аналитика
недоступна. У задачи `Reporter` из раздела выше.

### Первая попытка

`unawaited` из Dart помечает future, которую намеренно не ждут:

```dart
// Первая попытка: ошибка уходит в зону, а не в задачу.
unawaited(analytics.send('loaded'));
```

```text
outcome: Done(null)
zone: Bad state: analytics offline
```

Наблюдатель не слышит ничего, и ничто не связывает ошибку с задачей. Ошибка
future, которую никто не ждёт, уходит в зону как неперехваченная. `unawaited`
лишь говорит анализатору, что future не ждут намеренно.

### Работа, переданная задаче

```dart
ctx.unattended(() => analytics.send('loaded'));
```

```text
outcome: Done(null)
onError: Bad state: analytics offline
zone: Bad state: analytics offline
```

`ctx.unattended(action)` оставляет ошибки работы при задаче, даже те, что
приходят, когда задача уже кончилась. Их слышит наблюдатель, а дальше они
уходят в зону, где задача создана, если наблюдатель за них не отвечает. Без
наблюдателя они уходят туда сразу. Задача работу не ждёт и не отменяет.

Запускайте работу внутри колбэка и ничего из него не выносите. Работа идёт
в собственной зоне ошибок, и граница действует в обе стороны:

- Future, созданная снаружи и ожидаемая внутри, при ошибке не возвращается
  никогда, а её ошибка уходит в зону, где создана сама future.
- Future, созданная внутри и ожидаемая снаружи, при ошибке вешает того, кто её
  ждёт. Если её ждёт тело, зависает задача.

Задача, запущенная внутри колбэка, границе не подчиняется: её тело идёт в зоне,
откуда начата работа.

## Ответ за ошибки

Ошибки, которых не несёт ни один исход, идут от `onError` дальше, к ответу.
Наблюдатель, который только смотрит, например `Reporter`, ответа не даёт,
поэтому эти ошибки уходят туда же, куда ушли бы без наблюдателя: в зону. То,
что наблюдатель слышит ошибку, само по себе не меняет, куда она уходит.
Наблюдатель, который отвечает за эти ошибки сам, подмешивает `JobAnswerer`
и переопределяет `onUnanswered`:

```dart
final class Answering extends JobObserver with JobAnswerer {
  @override
  void onUnanswered(Job<Object?> job, Object error, StackTrace stackTrace) =>
      print('onUnanswered: $error');
}
```

Там ошибки и останавливаются, до зоны они не доходят. `onUnanswered`
по умолчанию отправляет их в зону, где задача создана, как и без ответа.
Поэтому вызов `super.onUnanswered(job, error, stackTrace)` тоже отправляет
ошибку дальше в зону. Наблюдатель, который отвечает только за знакомые ему
ошибки базы данных, отдаёт остальное `super`:

```dart
final class DatabaseErrors extends JobObserver with JobAnswerer {
  @override
  void onUnanswered(Job<Object?> job, Object error, StackTrace stackTrace) {
    if (error is DatabaseException) {
      print('onUnanswered: $error');
    } else {
      super.onUnanswered(job, error, stackTrace);
    }
  }
}
```

Задача отдаёт `ctx.unattended` две операции, которых ждут вместе. `saveDraft`
падает с `DatabaseException`, а `sendAnalytics` падает со `StateError`.
`[saveDraft(), sendAnalytics()].wait` бросает `ParallelWaitError`, в котором
лежат оба провала:

```dart
final job = Job<void>(
  observer: DatabaseErrors(),
  (ctx) async {
    ctx.unattended(() => [saveDraft(), sendAnalytics()].wait);
  },
);
```

```text
outcome: Done(null)
onUnanswered: DatabaseException
zone: Bad state: analytics offline
```

`onUnanswered` спрашивают об одном провале за раз. Задача обходит
`ParallelWaitError` и спрашивает о каждом провале внутри него, со стектрейсом
этого провала. Поэтому за ошибку базы данных отвечает наблюдатель, а ошибку
аналитики зона слышит отдельно. Неперехваченный `Cancelled` не провал, и о нём
не спрашивают никого, пришёл ли он один или внутри `ParallelWaitError`.
Не спрашивают никого и об ошибке, которую приложение назвало в разделе
[«Ошибки отмены»](#ошибки-отмены), если задача приняла отмену.

`onError` тоже слышит их по одной, а `Cancelled` внутри `ParallelWaitError`
слышит отдельным вызовом. Исход хранит ошибку такой, какой её бросили: тело,
упавшее с `ParallelWaitError`, кончается `Failed` с этой ошибкой.
`Job.visitErrors` делает тот же обход для того, кто читает исход:

```dart
final outcome = await job.done;
if (outcome case Failed(:final error, :final stackTrace)) {
  Job.visitErrors(
    error,
    stackTrace,
    onFailure: (failure, failureStackTrace) => print('failed: $failure'),
  );
}
```

Переопределение отвечает за задачу, которой передали наблюдателя, и за дочерние
задачи, которые его наследуют, на любой глубине. Чтобы ответить за все задачи
сразу, приложение пользуется своей зоной, где и так сообщает о неперехваченном:
туда эти ошибки приносит `onUnanswered`, если его не переопределять. Зона
получает ошибку и её стектрейс, но не задачу, так что отчёту, который называет
задачу, нужно переопределение.

## Несколько наблюдателей

Приложение отправляет всё, за что никто не ответил, в отчёт о падениях.
У задачи из раздела
[«Работа, которую задача не ждёт»](#работа-которую-задача-не-ждёт) остаётся
и её `Reporter`. Отвечает наблюдатель `Crashes`:

```dart
final class Crashes extends JobObserver with JobAnswerer {
  @override
  void onUnanswered(Job<Object?> job, Object error, StackTrace stackTrace) =>
      print('onUnanswered: $error');
}
```

### Первая попытка

`observer:` принимает одного `JobObserver`, поэтому класс передаёт свои хуки
обоим, а ответ — `Crashes`:

```dart
// Первая попытка: каждый хук передаётся вручную и без try/catch.
final class Both extends JobObserver with JobAnswerer {
  final _reporter = Reporter();
  final _crashes = Crashes();

  @override
  void onError(Job<Object?> job, Object error, StackTrace stackTrace) {
    _reporter.onError(job, error, stackTrace);
    _crashes.onError(job, error, stackTrace);
  }

  @override
  void onUnanswered(Job<Object?> job, Object error, StackTrace stackTrace) =>
      _crashes.onUnanswered(job, error, stackTrace);

  // onStart, onFinish и onLog так же, как onError.
}
```

```text
outcome: Done(null)
onError: Bad state: analytics offline
onUnanswered: Bad state: analytics offline
```

Это работает: `Reporter` слышит ошибку, `Crashes` за неё отвечает. Но каждый
хук передаётся руками: пять методов на два наблюдателя, а третий наблюдатель
добавит по строке в каждый. Для полноты каждый вызов надо ещё обернуть
в `try`/`catch`, иначе наблюдатель, который бросил исключение, выключает тех,
кто идёт после него.

### Наблюдатели одним списком

```dart
final job = Job<void>(
  observer: JobObserver.all([Reporter(), Crashes()]),
  (ctx) async {
    ctx.unattended(() => analytics.send('loaded'));
  },
);
```

```text
outcome: Done(null)
onError: Bad state: analytics offline
onUnanswered: Bad state: analytics offline
```

`JobObserver.all` передаёт каждый хук каждому наблюдателю в порядке списка,
и каждый вызов идёт сам по себе: наблюдатель, который бросил исключение,
не выключает следующего. Наблюдатель с `JobAnswerer` тоже смотрит на своём
месте в списке и отвечает за весь список, когда `onError` услышали все. Если
`JobAnswerer` в списке нет, ошибки уходят в зону, как у наблюдателя, который
не отвечает. Если отвечающих двое или один и тот же наблюдатель стоит дважды,
`JobObserver.all` бросает `ArgumentError`. Наблюдатель, собранный
`JobObserver.all`, может стоять в списке другого и отвечает там, если отвечает
кто-то внутри него.

## Тестирование

Тест проверяет, что при отмене во время открытия база всё равно закрывается,
когда открытие завершится. `package:fake_async` выполняет таймеры и микротаски
во времени под управлением теста, и тест ничего не ждёт в реальном времени.

### Первая попытка

`cancel()` возвращает future, которая завершается, когда задача кончилась,
поэтому тест её ждёт:

```dart
// Первая попытка: ни один expect не выполняется.
test('a cancelled open still closes what it opened', () {
  fakeAsync((async) async {
    var closed = 0;
    final job = Job<Database>(
      (ctx) => ctx.join(
        Database.open,
        discard: (db) {
          closed++;
          return db.close();
        },
      ),
    );

    async.elapse(const Duration(milliseconds: 10));
    await job.cancel();

    expect(job.outcome, isA<Cancelled>());
    expect(closed, 1);
  });
});
```

Тест проходит, и с `expect(closed, 0)` прошёл бы точно так же: ни один `expect`
не выполняется. Под `fakeAsync` время движется, только когда его двигает тест.
Колбэк возвращается на первом `await`, и `fakeAsync` возвращается вместе с ним.
Время больше никто не двигает, так что future из `cancel()` не завершается
никогда. Если написать `() => fakeAsync(...)`, тест будет ждать эту future
и упадёт по таймауту.

### Тест двигает время

```dart
test('a cancelled open still closes what it opened', () {
  fakeAsync((async) {
    var closed = 0;
    final job = Job<Database>(
      (ctx) => ctx.join(
        Database.open,
        discard: (db) {
          closed++;
          return db.close();
        },
      ),
    );

    async.elapse(const Duration(milliseconds: 10));
    job.cancel().ignore(); // внутри `fakeAsync` никто ничего не ждёт
    async.flushTimers();

    expect(job.outcome, isA<Cancelled>());
    expect(closed, 1); // ради чего тест и назван
  });
});
```

Внутри `fakeAsync` никто ничего не ждёт. Future из `cancel()` проигнорирована,
`flushTimers()` доводит открытие до конца, и проверки видят то, что произошло.
Для запуска задачи достаточно `flushMicrotasks()`: её тело начинается
в микротаске. Операции, запланированные через `Future(...)` или
`Future.delayed(...)`, используют таймеры, поэтому для них нужны
`flushTimers()` или `elapse(...)`.
