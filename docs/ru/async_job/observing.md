# Наблюдение и тестирование

Исход говорит, чем задача кончилась. `JobObserver` слышит остальное: когда
задача начинается и кончается, что её тело пишет в журнал и ошибки, которых
не несёт ни один исход. Последний раздел тестирует задачу, не ожидая в реальном
времени.

Строки под кодом — то, что он печатает при запуске. `cancel` — момент, когда
пользователь отменяет, `outcome:` — то, чем завершается `job.done`,
`onError:` — то, что дошло до наблюдателя, а `zone:` — ошибка, дошедшая до зоны
неперехваченной. Первый раздел, о самом наблюдателе, открывается ответом.
Остальные открываются версией, к которой ведут имена, — строка для `ctx.log`,
зона для ошибки, которую никто не поймал, `unawaited` для future, которую
намеренно не ждут, `await` для future, которую возвращает `cancel()`, —
и показывают, что этот код делает. Работающая версия идёт следом под своим
заголовком.

## Наблюдатель

Задача загружает число. Её наблюдатель печатает, чем задача кончилась и что
тело записало в журнал:

```dart
final class Log extends JobObserver {
  @override
  void onFinish(Job<Object?> job) => print('$job: ${job.outcome}');

  @override
  void onLog(Job<Object?> job, Object? message) {
    final data = message is Object? Function() ? message() : message;
    print('$job: $data');
  }
}

final job = Job<int>(
  key: 'load',
  observer: Log(),
  (ctx) => ctx.wait(load),
);
```

```text
Job(load): Done(3)
```

У `JobObserver` пять хуков: `onStart`, `onFinish`, `onError`, `onUnanswered`
и `onLog`. Первые четыре `Job` вызывает сама, а сообщения для `onLog` тело
отправляет через `ctx.log(message)`. `onFinish` вызывается для каждой задачи,
в том числе отменённой до старта; `onStart` — только для задачи, чьё тело
запустилось.

Все, кроме `onUnanswered`, по умолчанию ничего не делают, поэтому можно
переопределить только нужные; что делает `onUnanswered`, — предмет раздела
[«Куда уходят ошибки»](#куда-уходят-ошибки) ниже. Класс, который уже наследует
другой класс, подмешивает наблюдателя через `with JobObserver` и сохраняет эти
тела по умолчанию. Наблюдателя передаёт при создании задачи тот, кто её
запускает; дочерние задачи, которые она запускает, наследуют его, если у них
нет своего, а продолжение, созданное через `then`, получает только наблюдателя,
переданного в `then`. Если хук наблюдателя бросит исключение, оно попадёт
в текущую зону, и больше ничего не изменится: задача кончится так же, как
кончилась бы, а остальные хуки наблюдателя всё равно будут вызваны.

Строковое представление задачи имеет вид `Job($key)`, или
`Job($key: $description)`, когда `describe` что-то возвращает, или
`Job($description)`, когда ключа нет, или `Job()`, когда нет ни того,
ни другого. Используйте `key` для обозначения задачи в журнале или в правилах
планирования библиотеки, например в политиках очереди `solo`; `describe`
добавляет к этому представлению подробности.

Наблюдатель может и засечь отмену. `Job.whenCancelled`, зарегистрированный
в `onStart`, срабатывает, когда задача принимает отмену, а `onFinish` — когда
приходит исход; время между ними — то, сколько задача проработала после отмены,
вместе с дочерними задачами и уборкой. Тело, ждущее что-то долгое голым
`await`, показывает остаток этого ожидания, тогда как тот же вызов через
`ctx.wait` показывает 0 мс. Счёт идёт от принятия, а не от `cancel()`: отмену,
придержанную `ctx.uncancellable`, задача принимает, когда секция кончается,
поэтому секция на 100 мс, отменённая на 10-й миллисекунде, показывает 0 мс,
а вызвавший `cancel` ждал 90 мс.

## Сообщение для журнала

Тело мигрирует базу и, когда миграция падает, пишет в журнал пойманную ошибку
`error`. Тот, кто отлаживает приложение, даёт задаче наблюдателя; в релизной
сборке его нет, и там сообщение не должно стоить ничего.

### Первая попытка

`log` принимает сообщение, а строка — сообщение:

```dart
ctx.log('migration failed: $error');
```

Без наблюдателя `ctx.log` ничего не делает, но строка к этому моменту уже
построена: Dart вычисляет аргумент до вызова, и `error.toString()` выполняется
ни для кого.

### Форматирование остаётся наблюдателю

```dart
ctx.log(() => 'migration failed: $error');
```

Колбэк откладывает само построение сообщения. `ctx.log` передаёт его без
изменений, как любой другой объект, поэтому без наблюдателя ничего не строится.
С наблюдателем строить сообщение — его соглашение: `Log` выше вызывает колбэк
и печатает то, что тот вернул, а наблюдатель, который печатает сообщение как
пришло, напечатает сам колбэк. Если передать один `error`, форматирование тоже
останется наблюдателю, и никакого соглашения не нужно.

## Куда уходят ошибки

Приложение сообщает о каждой ошибке, которая дошла до его зоны неперехваченной.
Задача открывает базу, пользователь отменяет, пока она открывается, а затем
открытие падает: база заблокирована.

### Первая попытка

Dart отправляет в зону ошибку, которую никто не поймал, поэтому приложение
полагается на зону и наблюдателя задаче не даёт:

```dart
final job = Job<Database>(
  (ctx) => ctx.join(
    Database.open,
    discard: (database) => database.close(),
  ),
);
```

```text
cancel
outcome: Cancelled(manual)
```

До зоны не доходит ничего, и приложение так и не узнаёт, что открытие
не удалось: ошибку поймала сама задача. Задача приняла отмену, пока база
открывалась, поэтому она кончается `Cancelled`, что бы ни сделало открытие.
Затем `join` бросает собственную ошибку открытия, и тело сдаётся с ней на уже
отменённой задаче. Эта ошибка — не исход, и задача отдаёт её только своему
наблюдателю. Чаще всего такая ошибка — операция, остановившаяся по токену
задачи, как миграция, которая бросает `DatabaseStopped` в разделе
[«Токен через `onCancel`»](cancellation.md#токен-через-oncancel) страницы
об отмене, и в зоне каждая такая отмена выглядела бы сбоем. Отличить такую
остановку от сбоя, как этот, задача не может, поэтому без наблюдателя не слышно
ни того, ни другого.

### С наблюдателем

```dart
final class Reporter extends JobObserver {
  @override
  void onError(Job<Object?> job, Object error, StackTrace stackTrace) =>
      print('onError: $error');
}

final job = Job<Database>(
  observer: Reporter(),
  (ctx) => ctx.join(
    Database.open,
    discard: (database) => database.close(),
  ),
);
```

```text
cancel
onError: Bad state: database locked
outcome: Cancelled(manual)
```

Наблюдатель слышит все ошибки своей задачи через `onError` — и только слышит:
переопределение `onError` никуда ошибку не переносит. Куда уходит каждая,
с наблюдателем и без него; зона здесь — та, где задача создана:

| Ошибка | С наблюдателем | Без него |
| --- | --- | --- |
| Ошибка тела, и задача кончается с ней `Failed` | `onError`, а если исход никто не наблюдал, то и зона | Зона, если исход никто не наблюдал |
| Ошибка тела, а отмена приходит, пока задача ждёт дочерние или идёт её уборка | `onError`, затем `onUnanswered`: по умолчанию зона | Зона |
| Ошибка тела после того, как задача приняла отмену | `onError` | Никто |
| Ошибка тела в ветке `ctx.runAll`, чья группа бросает другой провал | `onError`, затем `onUnanswered`: по умолчанию зона | Зона |
| Вне тела: поздняя ошибка действия, ожидание которого прервал `wait`, ошибка уборки, колбэка `ctx.onCancel` или `job.whenCancelled`, работы `ctx.unattended`, построения описания отмены дочерней задачи | `onError`, затем `onUnanswered`: по умолчанию зона | Зона |
| `Cancelled`, брошенный вне тела | `onError`, затем `onUnanswered`: по умолчанию никто | Никто |

Ошибки, которых не несёт ни один исход, идут от `onError` дальше, в хук
`onUnanswered`, который за них отвечает. Его тело по умолчанию отправляет их
туда же, куда они ушли бы без наблюдателя, — в зону, а отмену отбрасывает:
`Cancelled` или `ParallelWaitError`, в котором одни отмены. Поэтому
наблюдатель, написанный, чтобы смотреть, как `Reporter`, не меняет, куда уходит
ошибка. Наблюдатель, который отвечает за эти ошибки сам, переопределяет
`onUnanswered`:

```dart
@override
void onUnanswered(Job<Object?> job, Object error, StackTrace stackTrace) =>
    print('onUnanswered: $error');
```

Там ошибки и останавливаются, до зоны они не доходят. Вызов
`super.onUnanswered(job, error, stackTrace)` отправляет ошибку ещё и в зону.
Отдавайте `super` всё, что переопределение не может различить: тело
по умолчанию знает, какие ошибки — отмены.

Ошибка может дойти и до `onError`, и до зоны, и приложение, которое сообщает
об ошибках в обоих местах, услышит её дважды. Путь каждой ошибки в зону
показывает таблица: если исход никто не наблюдал или если `onUnanswered`
отправил ошибку дальше. Первый путь закрывает наблюдение исхода; как это
сделать, показывает раздел
[«Ошибка, которую никто не ждёт»](outcomes.md#ошибка-которую-никто-не-ждёт)
страницы об исходах. Второй закрывает переопределение `onUnanswered`. Для двух
провалов тела, которых исход не несёт, — покрытого отменой и провала ветки, чья
группа бросает другой, — второй путь закрывает и `job.ignore()`: `onError`
провал слышит, а отвечать за него некому.

## Работа, которую задача не ждёт

Задача отправляет событие аналитики и не ждёт его, а отправка падает: аналитика
недоступна. У задачи `Reporter` из раздела выше.

### Первая попытка

`unawaited` из Dart помечает future, которую намеренно не ждут:

```dart
unawaited(analytics.send('loaded'));
```

```text
outcome: Done(null)
zone: Bad state: analytics offline
```

Наблюдатель не слышит ничего, и ничто не связывает ошибку с задачей: ошибка
future, которую никто не ждёт, уходит в зону как неперехваченная; `unawaited`
лишь говорит анализатору, что не ждать — намеренно.

### Работа, переданная задаче

```dart
ctx.unattended(() => analytics.send('loaded'));
```

```text
outcome: Done(null)
onError: Bad state: analytics offline
zone: Bad state: analytics offline
```

`ctx.unattended(action)` оставляет ошибки работы при задаче, даже после её
завершения: их слышит наблюдатель задачи, а его `onUnanswered` отправляет их
дальше, в зону, где задача создана. Без наблюдателя они уходят туда сразу.
Задача работу не ждёт и не отменяет.

Запускайте работу внутри колбэка и ничего из него не выносите: работа идёт
в собственной зоне ошибок, и граница держит в обе стороны. Если future создана
снаружи, а ждут её внутри, то при ошибке она не возвращается никогда, а её
ошибка уходит в зону, где она создана. Если future создана внутри, а ждут её
снаружи, то при ошибке она вешает того, кто её ждёт, — а если её ждёт тело,
то и задачу.

## Тестирование

Тест проверяет, что отмена во время открытия базы всё равно приводит к её
закрытию, когда открытие завершится. `package:fake_async` выполняет таймеры
и микротаски в фейковом времени, так что тест ничего не ждёт в реальном
времени; этот пакет использует его в собственных тестах.

### Первая попытка

`cancel()` возвращает future, которая завершается, когда задача кончилась,
поэтому тест её ждёт:

```dart
test('a cancelled open still closes what it opened', () {
  fakeAsync((async) async {
    var closed = 0;
    final job = Job<Database>(
      (ctx) => ctx.join(
        Database.open,
        discard: (db) {
          closed++;
          return db.close();
        },
      ),
    );

    async.elapse(const Duration(milliseconds: 10));
    await job.cancel();

    expect(job.outcome, isA<Cancelled>());
    expect(closed, 1);
  });
});
```

Тест проходит, и с `expect(closed, 0)` прошёл бы точно так же: ни один `expect`
не выполняется. Под `fakeAsync` время движется, только когда его двигает тест.
Колбэк возвращается на первом `await`, `fakeAsync` возвращается вместе с ним,
и время больше никто не двигает, так что future из `cancel()` не завершается
никогда. Если написать `() => fakeAsync(...)`, тест будет ждать эту future
и упадёт по таймауту.

### Время двигает тест

```dart
test('a cancelled open still closes what it opened', () {
  fakeAsync((async) {
    var closed = 0;
    final job = Job<Database>(
      (ctx) => ctx.join(
        Database.open,
        discard: (db) {
          closed++;
          return db.close();
        },
      ),
    );

    async.elapse(const Duration(milliseconds: 10));
    job.cancel().ignore(); // внутри `fakeAsync` никто ничего не ждёт
    async.flushTimers();

    expect(job.outcome, isA<Cancelled>());
    expect(closed, 1); // ради чего тест и назван
  });
});
```

Внутри `fakeAsync` никто ничего не ждёт: future из `cancel()` проигнорирована,
`flushTimers()` доводит открытие до конца, и проверки видят то, что произошло.
Для запуска задачи достаточно `flushMicrotasks()`: её тело начинается
в микротаске. Операции, запланированные через `Future(...)` или
`Future.delayed(...)`, используют таймеры: для них нужны `flushTimers()` или
`elapse(...)`.
