# Наблюдение и тестирование

Исход говорит, чем задача кончилась. `JobObserver` слышит остальное: когда
задача начинается и кончается, что её тело пишет в лог и ошибки, которых
не несёт ни один исход. Последний раздел тестирует задачу, не ожидая в реальном
времени.

Строки под кодом показывают, что он печатает при запуске: `cancel` в момент,
когда пользователь отменяет, `outcome:` с тем, чем завершается `job.done`,
`onError:` с тем, что дошло до наблюдателя, `onUnanswered:` с ошибкой,
за которую наблюдатель ответил, и `zone:` с ошибкой, дошедшей до зоны
неперехваченной. Первый раздел, о самом наблюдателе, открывается ответом.
Остальные открываются версией, к которой ведёт привычка, и показывают, что этот
код делает. Следом под своим заголовком идёт версия, которая работает, а там,
где первая уже работает, версия проще.

## Наблюдатель

Задача загружает число. Её наблюдатель печатает, чем задача кончилась и что
тело записало в лог:

```dart
final class Log extends JobObserver {
  @override
  void onFinish(Job<Object?> job) => print('$job: ${job.outcome}');

  @override
  void onLog(Job<Object?> job, Object? message) {
    final data = message is Object? Function() ? message() : message;
    print('$job: $data');
  }
}

final job = Job<int>(
  key: 'load',
  observer: Log(),
  (ctx) async {
    ctx.log('loading');
    return ctx.wait(load);
  },
);
```

```text
Job(load): loading
Job(load): Done(3)
```

У `JobObserver` четыре хука: `onStart`, `onFinish`, `onError` и `onLog`. Первые
три `Job` вызывает сама, а сообщения для `onLog` тело отправляет через
`ctx.log(message)`. `onFinish` вызывается для каждой задачи, в том числе
отменённой до старта, а `onStart` вызывается только для задачи, чьё тело
запустилось.

По умолчанию они ничего не делают, поэтому можно переопределить только нужные.
Наблюдатель, который ещё и отвечает за ошибки, подмешивает `JobAnswerer`,
а с ним пятый хук, `onUnanswered`; о нём раздел
[«Куда уходят ошибки»](#куда-уходят-ошибки) ниже. Класс, который уже наследует
другой класс, подмешивает наблюдателя через `with JobObserver` или
`with JobObserver, JobAnswerer` и так же переопределяет нужные ему хуки.
Наблюдателя передаёт при создании задачи тот, кто её запускает; дочерние
задачи, которые она запускает, наследуют его, если у них нет своего,
а продолжение, созданное через `then`, получает только наблюдателя, переданного
в `then`. Если хук наблюдателя бросит исключение, оно попадёт в текущую зону,
и больше ничего не изменится: задача кончится так же, как кончилась бы,
а остальные хуки наблюдателя всё равно будут вызваны. Исключение `Cancelled`,
брошенное хуком, в зону не попадает: брошенную отмену ядро нигде не считает
ошибкой. Задачу оно тоже не отменяет. Хук, которому нужно отменить задачу,
вызывает `job.cancel()`, и задача отменяется так же, как при вызове из любого
другого места.

Задаче при создании можно дать ключ `key` и колбэк `describe`. Её строковое
представление имеет вид `Job($key)`, или `Job($key: $description)`, когда
`describe` возвращает непустое описание, или `Job($description)`, когда ключа
нет, или `Job()`, когда нет ни того, ни другого. Используйте `key`, чтобы
обозначить задачу в логе или в правилах планирования библиотеки, например
в политиках очереди `solo`; `describe` добавляет к этому представлению
подробности.

От отменённой задачи ждут, что она скоро кончится; та, что работает дальше,
занята делом, от которого пользователь уже отказался. Наблюдатель находит такие
задачи, засекая, сколько каждая проработала после отмены:

```dart
final class SlowCancellations extends JobObserver {
  final _since = Expando<Stopwatch>('cancellation');

  @override
  void onStart(Job<Object?> job) =>
      job.whenCancelled((_) => _since[job] = Stopwatch()..start());

  @override
  void onFinish(Job<Object?> job) {
    final watch = _since[job];
    if (watch != null) {
      print('$job ran ${watch.elapsedMilliseconds} ms past its cancellation');
    }
  }
}
```

`Job.whenCancelled`, зарегистрированный в `onStart`, срабатывает, когда задача
принимает отмену, а `onFinish` срабатывает, когда приходит исход. Время между
ними показывает, сколько задача проработала после отмены, вместе с дочерними
задачами и уборкой. Если тело ждёт что-то долгое голым `await`, остаток этого
ожидания попадает в счёт, а тот же вызов через `ctx.wait` показывает 0 мс. Счёт
идёт от принятия, а не от `cancel()`: отмену, придержанную `ctx.uncancellable`,
задача принимает, когда секция кончается, поэтому секция на 100 мс, отменённая
на 10-й миллисекунде, показывает 0 мс, хотя вызвавший `cancel` ждал 90 мс.
Тело, которое сдаётся само, бросая `Cancelled` или выпуская наружу отмену
дочерней задачи, принимает отмену в момент броска, и счёт идёт оттуда.

## Сообщение для лога

Тело мигрирует базу и, когда миграция падает, пишет в лог пойманную ошибку
`error`. Тот, кто отлаживает приложение, даёт задаче наблюдателя; в релизной
сборке его нет, и там сообщение не должно стоить ничего.

### Первая попытка

`log` принимает сообщение, и строка годится в сообщение:

```dart
ctx.log('migration failed: $error');
```

Без наблюдателя `ctx.log` ничего не делает, но строка к этому моменту уже
построена: Dart вычисляет аргумент до вызова, и `error.toString()` выполняется
ни для кого.

### Форматирование остаётся наблюдателю

```dart
ctx.log(() => 'migration failed: $error');
```

Колбэк откладывает само построение сообщения. `ctx.log` передаёт его без
изменений, как любой другой объект, поэтому без наблюдателя ничего не строится.
С наблюдателем сообщение строится по его соглашению: `Log` выше вызывает колбэк
и печатает то, что тот вернул, а наблюдатель, который печатает сообщение как
пришло, напечатает сам колбэк. Если передать один `error`, форматирование тоже
останется наблюдателю, и никакого соглашения не нужно.

## Куда уходят ошибки

Приложение сообщает о каждой ошибке, которая дошла до его зоны неперехваченной.
Задача открывает базу, пользователь отменяет, пока она открывается, а затем
открытие падает: база заблокирована.

### Первая попытка

Dart отправляет в зону ошибку, которую никто не поймал, поэтому приложение
полагается на зону и наблюдателя задаче не даёт:

```dart
final job = Job<Database>(
  (ctx) => ctx.join(
    Database.open,
    discard: (database) => database.close(),
  ),
);
```

```text
cancel
outcome: Cancelled(manual)
```

До зоны не доходит ничего, и приложение так и не узнает, что открытие
не удалось: ошибку поймала сама задача. Задача приняла отмену, пока база
открывалась, поэтому она кончается `Cancelled`, что бы ни сделало открытие.
Затем `join` бросает собственную ошибку открытия, и тело падает с ней на уже
отменённой задаче. Исходом эта ошибка не становится, и задача отдаёт её только
своему наблюдателю. Чаще всего такую ошибку бросает операция, остановившаяся
по токену задачи, как миграция, которая бросает `DatabaseStopped` в разделе
[«Токен через `onCancel`»](cancellation.md#токен-через-oncancel) страницы
об отмене, и в зоне каждая такая отмена выглядела бы сбоем. Отличить такую
остановку от сбоя, как этот, задача не может, поэтому без наблюдателя не слышно
ни того, ни другого.

### С наблюдателем

```dart
final class Reporter extends JobObserver {
  @override
  void onError(Job<Object?> job, Object error, StackTrace stackTrace) =>
      print('onError: $error');
}

final job = Job<Database>(
  observer: Reporter(),
  (ctx) => ctx.join(
    Database.open,
    discard: (database) => database.close(),
  ),
);
```

```text
cancel
onError: Bad state: database locked
outcome: Cancelled(manual)
```

Наблюдатель слышит через `onError` ошибки, которые ловит его задача, кроме её
собственной отмены. Но только слышит: переопределение `onError` никуда ошибку
не переносит. Куда уходит каждая, с наблюдателем и без него; зоной здесь
считается та, где задача создана:

| Ошибка | С наблюдателем | Без него |
| --- | --- | --- |
| Ошибка тела, и задача кончается с ней `Failed` | `onError`, а если исход никто не наблюдал, то и зона | Зона, если исход никто не наблюдал |
| Ошибка тела, а задача принимает отмену после неё: отмену, пришедшую до того, как ошибка вышла из тела, пока задача ждёт дочерние задачи или идёт её уборка, или отмену, которую `ctx.uncancellable` придерживал, пока падал его шаг | `onError`, затем `onUnanswered`, если наблюдатель отвечает, иначе зона | Зона |
| Ошибка тела, случившаяся после того, как задача приняла отмену | `onError` | Никто |
| Ошибка тела в ветке `ctx.runAll`, чья группа бросает другой провал | `onError`, затем `onUnanswered`, если наблюдатель отвечает, иначе зона | Зона |
| Вне тела: поздняя ошибка действия, ожидание которого прервал `ctx.wait`, ошибка уборки, колбэка `ctx.onCancel` или `job.whenCancelled`, работы `ctx.unattended`, построения описания отмены дочерней задачи | `onError`, затем `onUnanswered`, если наблюдатель отвечает, иначе зона | Зона |
| `Cancelled`, брошенный вне тела | `onError`, затем `onUnanswered`, если наблюдатель отвечает, иначе никто | Никто |
| Собственная отмена задачи из действия, ожидание которого прервал `ctx.wait`, или из работы `ctx.unattended` | Никто | Никто |
| То, что бросает вызов контекста, сделанный телом без `await`, в том числе собственная отмена задачи, а у `ctx.wait` только пока тело не кончилось | Зона, где идёт тело, как у любой future, которую никто не ждёт | Зона, где идёт тело |

Что было раньше, провал или отмена, решает момент, когда провал случился,
а не когда тело его бросило. Провал операции в `ctx.wait` или `ctx.join`,
колбэка `ctx.each`, дочерней задачи или шага `ctx.uncancellable` выходит
из тела не сразу: на это уходит несколько микрозадач или вся уборка дочерней
задачи. Если задача приняла отмену в этом промежутке, порядок такой: провал
случился, задача приняла отмену, тело бросило провал. Задача кончится
`Cancelled`, но провал был раньше отмены, и он попадает во вторую строку
таблицы, а не в третью. Тело сохраняет провал первым, если пропускает его
дальше или ловит и позже бросает снова; новая ошибка, брошенная вместо него,
обёртка тоже, приходит после отмены. Когда случился провал, задача узнаёт
от этих членов и от своих дочерних задач: ошибка future, которую тело ждёт
само, будет первой, только если тело бросит её до отмены.

Тело ловит провал открытия и показывает его пользователю, прежде чем бросить
снова:

```dart
final job = Job<Database>(
  observer: Reporter(),
  (ctx) async {
    try {
      return await ctx.join(Database.open);
    } catch (error) {
      await showError(error);
      rethrow;
    }
  },
);
```

Открытие падает на 20-й миллисекунде, пользователь отменяет на 30-й, пока
ошибка на экране, а тело бросает провал на 50-й:

```text
cancel
onError: Bad state: database locked
zone: Bad state: database locked
outcome: Cancelled(manual)
```

Провал был раньше отмены, это вторая строка таблицы: его слышит зона, хотя
задача кончилась `Cancelled`. Если отменить на 10-й миллисекунде, до того как
открытие упало, тот же провал попадает в третью строку, и слышит его только
наблюдатель:

```text
cancel
onError: Bad state: database locked
outcome: Cancelled(manual)
```

Шаг `ctx.uncancellable` и тот же шаг в `ctx.join` попадают в разные строки.
Секция придерживает отмену, пришедшую, пока шаг идёт, и задача принимает её,
когда секция закрывается на выходе из провала: провал случился первым и доходит
до зоны даже без наблюдателя. `join` даёт задаче принять отмену, как только та
пришла, поэтому провал шага приходит после неё, и без наблюдателя его не слышит
никто.

Вызов контекста, сделанный телом без `await`, бросает в future, которую никто
не ждёт, и Dart отдаёт её ошибку зоне, где идёт тело: у `Job.deferred` это
зона, которая её запустила, а если её запустили внутри `ctx.unattended`,
то зона, откуда начата эта работа. Туда же уходит и собственная отмена задачи:
когда задачу отменяют, `ctx.wait`, вызванный без `await`, бросает `Cancelled`
в свою future, и Dart отдаёт его зоне, как любую другую ошибку. Сама задача
отмену в зону не отправляет никогда, это делает Dart. У `ctx.wait` всё это так,
только пока тело идёт. Когда тело кончилось, `ctx.wait` перестаёт ждать своё
действие, как при отмене. Если действие упадёт после этого, его ошибка идёт
по пятой строке таблицы, как у действия, которое `ctx.wait` перестал ждать
из-за отмены: её слышит `onError`, а дальше она идёт к ответу, как другие
ошибки вне тела.

Ошибки, которых не несёт ни один исход, идут от `onError` дальше, к ответу.
Наблюдатель, написанный, чтобы смотреть, как `Reporter`, ответа не даёт, и они
уходят туда же, куда ушли бы без наблюдателя: в зону, а отмена отбрасывается,
будь то `Cancelled` или `ParallelWaitError`, в котором одни отмены. Поэтому
наблюдение не меняет, куда уходит ошибка. Наблюдатель, который отвечает за эти
ошибки сам, подмешивает `JobAnswerer` и переопределяет его `onUnanswered`:

```dart
final class Answering extends JobObserver with JobAnswerer {
  @override
  void onUnanswered(Job<Object?> job, Object error, StackTrace stackTrace) =>
      print('onUnanswered: $error');
}
```

Там ошибки и останавливаются, до зоны они не доходят. Реализация `onUnanswered`
по умолчанию отправляет их в зону, где задача создана, а отмену отбрасывает,
как и без ответа. Поэтому вызов `super.onUnanswered(job, error, stackTrace)`
отправляет ошибку ещё и в зону. Наблюдатель, который отвечает только
за знакомые ему ошибки базы данных, отдаёт остальное `super`:

```dart
final class DatabaseErrors extends JobObserver with JobAnswerer {
  @override
  void onUnanswered(Job<Object?> job, Object error, StackTrace stackTrace) {
    if (error is DatabaseException) {
      print('onUnanswered: $error');
    } else {
      super.onUnanswered(job, error, stackTrace);
    }
  }
}
```

Ошибку базы данных, пришедшую вместе с другой, он пропускает. Задача отдаёт
`ctx.unattended` две операции, которых ждут вместе: `saveDraft` падает
с `DatabaseException` на 20 мс, а `sendAnalytics` со `StateError` на 10 мс.
`[a, b].wait` бросает `ParallelWaitError`, в котором лежат оба провала,
и наблюдатель получает эту одну ошибку:

```dart
final job = Job<void>(
  observer: DatabaseErrors(),
  (ctx) async {
    ctx.unattended(() => [saveDraft(), sendAnalytics()].wait);
  },
);
```

```text
outcome: Done(null)
zone: ParallelWaitError(2 errors): DatabaseException
```

Ошибка базы данных ушла в зону без ответа, а ошибка аналитики не названа вовсе.
`Job.visitErrors` отдаёт наблюдателю ошибки изнутри по одной:

```dart
final class DatabaseErrors extends JobObserver with JobAnswerer {
  @override
  void onUnanswered(Job<Object?> job, Object error, StackTrace stackTrace) =>
      Job.visitErrors(
        error,
        stackTrace,
        onFailure: (failure, failureStackTrace) {
          if (failure is DatabaseException) {
            print('onUnanswered: $failure');
          } else {
            super.onUnanswered(job, failure, failureStackTrace);
          }
        },
      );
}
```

```text
outcome: Done(null)
onUnanswered: DatabaseException
zone: Bad state: analytics offline
```

Теперь `super` получает провалы по одному, и зона слышит ошибку аналитики
отдельно, а не весь `ParallelWaitError`. Неперехваченные `Cancelled` внутри
`ParallelWaitError` уходят в `onCancelled`, которого этот наблюдатель
не передаёт, и отбрасываются, как их отбрасывает реализация по умолчанию.
Проверка `error is Cancelled` отбросила бы не все: `ParallelWaitError`,
в котором одни `Cancelled`, сам не является `Cancelled`, а `[a, b].wait`
бросает именно его, когда future, которые он ждёт, завершаются с `Cancelled`.

Переопределение отвечает за задачу, которой передали наблюдателя, и за дочерние
задачи, которые его наследуют, на любой глубине. За все задачи сразу приложение
отвечает в своей зоне, где и так сообщает о неперехваченном: туда эти ошибки
приносит реализация по умолчанию. Зона получает ошибку и её стектрейс,
но не задачу, так что отчёту, который называет задачу, нужно переопределение.

Ошибка может дойти и до `onError`, и до зоны, и приложение, которое сообщает
об ошибках в обоих местах, услышит её дважды. Путь каждой ошибки в зону
показывает таблица: если исход никто не наблюдал или если ответа нет либо
`onUnanswered` отправил ошибку дальше. Первый путь закрывает наблюдение исхода;
как это сделать, показывает раздел
[«Ошибка, которую никто не ждёт»](outcomes.md#ошибка-которую-никто-не-ждёт)
страницы об исходах. Второй закрывает наблюдатель, который отвечает
(`with JobAnswerer`).

Ошибка тела, которой нет в исходе, уходит в `onUnanswered` или в зону, даже
если исход наблюдали. Таких в таблице две: задача упала, а потом приняла
отмену, и исход несёт отмену; или упала ветка `ctx.runAll`, а группа бросила
другую ошибку. Такую ошибку отпускает `ignore()`, вызванный у задачи, чьё тело
упало: `onError` её по-прежнему услышит, но ни до `onUnanswered`, ни до зоны
она не дойдёт.

## Работа, которую задача не ждёт

Задача отправляет событие аналитики и не ждёт его, а отправка падает: аналитика
недоступна. У задачи `Reporter` из раздела выше.

### Первая попытка

`unawaited` из Dart помечает future, которую намеренно не ждут:

```dart
unawaited(analytics.send('loaded'));
```

```text
outcome: Done(null)
zone: Bad state: analytics offline
```

Наблюдатель не слышит ничего, и ничто не связывает ошибку с задачей: ошибка
future, которую никто не ждёт, уходит в зону как неперехваченная; `unawaited`
лишь говорит анализатору, что future не ждут намеренно.

### Работа, переданная задаче

```dart
ctx.unattended(() => analytics.send('loaded'));
```

```text
outcome: Done(null)
onError: Bad state: analytics offline
zone: Bad state: analytics offline
```

`ctx.unattended(action)` оставляет ошибки работы при задаче, даже после её
завершения: их слышит наблюдатель задачи, а дальше они уходят в зону, где
задача создана, если наблюдатель за них не отвечает. Без наблюдателя они уходят
туда сразу. Задача работу не ждёт и не отменяет.

Запускайте работу внутри колбэка и ничего из него не выносите: работа идёт
в собственной зоне ошибок, и граница держит в обе стороны. Если future создана
снаружи, а ждут её внутри, то при ошибке она не возвращается никогда, а её
ошибка уходит в зону, где она создана. Если future создана внутри, а ждут её
снаружи, то при ошибке она вешает того, кто её ждёт, а если её ждёт тело,
то и задачу.

## Несколько наблюдателей

Приложение отдаёт то, за что никто не ответил, в отчёт о падениях, а у задачи
из раздела выше остаётся её `Reporter`. Отвечает `Crashes`:

```dart
final class Crashes extends JobObserver with JobAnswerer {
  @override
  void onUnanswered(Job<Object?> job, Object error, StackTrace stackTrace) =>
      print('onUnanswered: $error');
}
```

### Первая попытка

`observer:` принимает одного `JobObserver`, поэтому класс передаёт свои хуки
обоим, а ответ `Crashes`:

```dart
final class Both extends JobObserver with JobAnswerer {
  final _reporter = Reporter();
  final _crashes = Crashes();

  @override
  void onError(Job<Object?> job, Object error, StackTrace stackTrace) {
    _reporter.onError(job, error, stackTrace);
    _crashes.onError(job, error, stackTrace);
  }

  @override
  void onUnanswered(Job<Object?> job, Object error, StackTrace stackTrace) =>
      _crashes.onUnanswered(job, error, stackTrace);

  // onStart, onFinish и onLog так же, как onError.
}
```

```text
outcome: Done(null)
onError: Bad state: analytics offline
onUnanswered: Bad state: analytics offline
```

Это работает: `Reporter` слышит ошибку, `Crashes` за неё отвечает. Но каждый
хук передаётся руками: пять методов на два наблюдателя, а третий добавит
по строке в каждый.

### Наблюдатели одним списком

```dart
final job = Job<void>(
  observer: JobObserver.all([Reporter(), Crashes()]),
  (ctx) async {
    ctx.unattended(() => analytics.send('loaded'));
  },
);
```

```text
outcome: Done(null)
onError: Bad state: analytics offline
onUnanswered: Bad state: analytics offline
```

Строки те же, что у `Both`. `JobObserver.all` передаёт каждый хук каждому
наблюдателю в порядке списка, и каждый вызов идёт сам по себе: тот, кто бросил
исключение, не выключает следующего. Тот, кто `JobAnswerer`, наблюдает на своём
месте и отвечает за весь список, когда `onError` услышали все; если такого нет,
ошибки уходят в зону, как у наблюдателя, который не отвечает. Двое отвечающих
или один и тот же наблюдатель дважды, и `JobObserver.all` бросает
`ArgumentError`. Наблюдатель, собранный `JobObserver.all`, может стоять
в списке другого и отвечает там, если отвечает кто-то внутри него.

## Тестирование

Тест проверяет, что при отмене во время открытия база всё равно закрывается,
когда открытие завершится. `package:fake_async` выполняет таймеры и микротаски
во времени под управлением теста, так что тест ничего не ждёт в реальном
времени.

### Первая попытка

`cancel()` возвращает future, которая завершается, когда задача кончилась,
поэтому тест её ждёт:

```dart
test('a cancelled open still closes what it opened', () {
  fakeAsync((async) async {
    var closed = 0;
    final job = Job<Database>(
      (ctx) => ctx.join(
        Database.open,
        discard: (db) {
          closed++;
          return db.close();
        },
      ),
    );

    async.elapse(const Duration(milliseconds: 10));
    await job.cancel();

    expect(job.outcome, isA<Cancelled>());
    expect(closed, 1);
  });
});
```

Тест проходит, и с `expect(closed, 0)` прошёл бы точно так же: ни один `expect`
не выполняется. Под `fakeAsync` время движется, только когда его двигает тест.
Колбэк возвращается на первом `await`, `fakeAsync` возвращается вместе с ним,
и время больше никто не двигает, так что future из `cancel()` не завершается
никогда. Если написать `() => fakeAsync(...)`, тест будет ждать эту future
и упадёт по таймауту.

### Тест двигает время

```dart
test('a cancelled open still closes what it opened', () {
  fakeAsync((async) {
    var closed = 0;
    final job = Job<Database>(
      (ctx) => ctx.join(
        Database.open,
        discard: (db) {
          closed++;
          return db.close();
        },
      ),
    );

    async.elapse(const Duration(milliseconds: 10));
    job.cancel().ignore(); // внутри `fakeAsync` никто ничего не ждёт
    async.flushTimers();

    expect(job.outcome, isA<Cancelled>());
    expect(closed, 1); // ради чего тест и назван
  });
});
```

Внутри `fakeAsync` никто ничего не ждёт: future из `cancel()` проигнорирована,
`flushTimers()` доводит открытие до конца, и проверки видят то, что произошло.
Для запуска задачи достаточно `flushMicrotasks()`: её тело начинается
в микротаске. Операции, запланированные через `Future(...)` или
`Future.delayed(...)`, используют таймеры: для них нужны `flushTimers()` или
`elapse(...)`.
