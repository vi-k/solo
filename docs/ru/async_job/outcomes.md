# Исходы

Когда тело, дочерние задачи и уборка завершились, у задачи есть исход
`Outcome<T>`: `Done` со значением, которое вернуло тело, `Failed` с ошибкой,
которую оно бросило, или `Cancelled`. `job.done` завершается этим исходом
и никогда не бросает, `job.value` отдаёт одно значение, а `job.outcome` хранит
исход после конца задачи и `null` до него. `Outcome<T>` объявлен как `sealed`,
поэтому `switch` по этим трём вариантам исчерпывающий.

Строки под кодом — то, что он печатает при запуске. Три раздела ниже
открываются версией, к которой ведёт словарь API, — членом, названным
по вопросу, который вы задаёте: `value` для значения, `outcome` для того, чем
кончилась задача, `reason` для того, почему её отменили, — и показывают, что
этот код делает. Работающая версия идёт под своим заголовком. Последний раздел,
о реакции до исхода, открывается ответом.

## Чтение результата

`report` — задача `Job<Report>`, которую пользователь может отменить. Когда она
кончилась, код, который её запустил, печатает одно из трёх: отчёт, ошибку,
с которой задача упала, или то, что её отменили.

### Первая попытка

`value` — это отчёт, а `try` принимает то, что пошло не так:

```dart
try {
  print('report: ${await report.value}');
} on Object catch (error) {
  print('failed: $error');
}
```

Пользователь отменяет, и отмена печатается как ошибка:

```text
failed: Cancelled(manual)
```

`value` при успехе завершается значением, а при ошибке или отмене бросает,
и для отмены бросает сам `Cancelled`. `Cancelled` реализует `Exception`,
поэтому `catch` принимает его вместе с ошибками — и `on Exception`,
и `on Object`.

### `switch` по `done`

```dart
final message = switch (await report.done) {
  Done(:final value) => 'report: $value',
  Failed(:final error) => 'failed: $error',
  Cancelled(:final reason) => 'cancelled: $reason',
};
print(message);
```

```text
cancelled: manual
```

`done` отдаёт исход, а не бросает его, и у каждого варианта своя строка.
`value` подходит коду, для которого отмена — такая же ошибка, как любая другая,
например тесту, который ждёт значение. Если результат совсем не нужен,
подтвердите это вызовом `report.ignore()`.

## Ошибка, которую никто не ждёт

`sync` загружает данные в фоне, и никто её не ждёт. Строка статуса при каждой
отрисовке читает, чем кончилась задача.

### Первая попытка

`outcome` — то, чем кончилась задача, и `null`, пока она идёт:

```dart
final sync = Job<void>(upload);

// Там, где рисуется строка статуса:
final status = switch (sync.outcome) {
  null => 'syncing',
  Done() => 'synced',
  Failed(:final error) => 'sync failed: $error',
  Cancelled() => 'sync cancelled',
};
print('status: $status');
```

Загрузка падает. Зона, в которой создана задача, получает ошибку как
необработанную, а строка статуса, нарисованная после этого, говорит то же:

```text
zone: Bad state: disk full
status: sync failed: Bad state: disk full
```

Ошибка, которую никто не наблюдал, передаётся в зону создания задачи
на микротаске после её завершения: так она остаётся видна, даже когда
вызывающий код не ждёт результата. В тесте это зона теста, и тест падает.
Чтение `outcome` наблюдением не считается, как и ожидание `job.cancel()`,
регистрация через `whenCancelled` и любой колбэк наблюдателя: `onError`
и `onFinish` ошибку слышат, а в зону она всё равно приходит.

### Сказать ядру, что она обработана

```dart
final sync = Job<void>(upload)..ignore();
```

```text
status: sync failed: Bad state: disk full
```

`ignore()` говорит ядру, что ошибку обрабатывают в другом месте (здесь это
строка статуса), и в зону ничего не приходит. Обращение к `done` или `value`
тоже наблюдает ошибку, поэтому коду, который ждёт задачу, например чтобы
перерисовать строку статуса по её концу, `ignore()` не нужен. `done` не бросает
никогда, а с `value` ожидающий код получает саму ошибку и должен обработать её,
как у любой `Future`. Передача ошибки через `then` тоже наблюдает её:
ответственность переходит к продолжению.

Одну ошибку ожидание не наблюдает: тело `sync` падает, а после этого приходит
отмена, например пока задача ещё ждёт своих дочерних задач или идёт её уборка.
Задача кончается `Cancelled`, и код, который её ждёт, получает отмену,
а не ошибку. Ошибка идёт путём ошибки, которой не несёт ни один исход; этот
путь показывает раздел [«Куда уходят ошибки»](observing.md#куда-уходят-ошибки)
страницы о наблюдении. В зону её не пускает `ignore()`.

## Почему задачу отменили

При отмене исход также объясняет, почему работа остановилась: `Cancelled`
хранит причину `reason`. В собственной причине можно хранить дополнительные
данные, например ошибку и её исходный стектрейс:

```dart
final class RequestCancelReason extends CancelReason {
  final Object error;
  final StackTrace stackTrace;

  const RequestCancelReason(this.error, this.stackTrace);

  @override
  String get name => 'request';
}
```

`report` запускает дочернюю задачу `fetch` за данными и ничего из того, что
из неё выходит, не ловит:

```dart
final fetch = Job.deferred<Data>(download);
final report = Job<Report>((ctx) async {
  final data = await ctx.run(fetch);
  return Report(data);
});
```

`fetch` нужен токен, который обновляет запрос в другом месте. Когда этот запрос
падает, код, который его отправил, отменяет `fetch` и передаёт ошибку
в причине. Тот же экземпляр получают исход `fetch` и слушатель,
зарегистрированный через `fetch.whenCancelled` (его разбирает раздел
[«Реакция до исхода»](#реакция-до-исхода)):

```dart
try {
  await refreshToken();
} on Object catch (error, stackTrace) {
  await fetch.cancel(reason: RequestCancelReason(error, stackTrace));
}
```

Код, который запустил `report`, должен отличить упавший запрос от отмены
пользователем.

### Первая попытка

`switch` по `done` получает вариант для причины:

```dart
final message = switch (await report.done) {
  Done(:final value) => 'report: $value',
  Failed(:final error) => 'failed: $error',
  Cancelled(reason: RequestCancelReason(:final error)) =>
    'request failed: $error',
  Cancelled(:final reason) => 'cancelled: $reason',
};
print(message);
```

```text
cancelled: handler
```

Запрос отменил `fetch`, а не `report`. Отмена `fetch` вышла через тело
`report`, и `report` кончилась собственным `Cancelled` с причиной
`HandlerCancelReason`: её тело сдалось. `RequestCancelReason` лежит на шаг
глубже, в `cause` этой причины.

### По цепочке `cause`

```dart
CancelReason origin(Cancelled cancelled) => switch (cancelled.reason) {
      HandlerCancelReason(:final cause?) ||
      ParentCancelReason(:final cause?) ||
      ChainCancelReason(:final cause) =>
        origin(cause),
      final reason => reason,
    };

final message = switch (await report.done) {
  Done(:final value) => 'report: $value',
  Failed(:final error) => 'failed: $error',
  final Cancelled cancelled => switch (origin(cancelled)) {
      RequestCancelReason(:final error) => 'request failed: $error',
      final reason => 'cancelled: $reason',
    },
};
print(message);
```

```text
request failed: Bad state: token expired
```

Три причины хранят в `cause` отмену, которая их вызвала. Когда родитель
отменяет дочернюю задачу, её `ParentCancelReason.cause` хранит `Cancelled`
родителя. Когда отмена дочерней задачи выходит через тело родителя, его
`HandlerCancelReason.cause` хранит `Cancelled` дочерней задачи. В цепочке
`then` задача, отменённая соседом, хранит `Cancelled` соседа
в `ChainCancelReason.cause`. Эти ссылки сохраняют исходную причину и её данные,
и `origin` проходит по ним до конца: `cause` равен `null` там, где за причиной
ничего нет, как у тела, которое само бросило `Cancelled('why')`.
У `SiblingCancelReason` тоже есть `cause`, но это то, из-за чего остановилась
группа: ошибка или отмена, которой кончилась другая ветка, или ошибка самой
группы, например `ArgumentError` о задаче, которую она не приняла веткой.
На `SiblingCancelReason` `origin` и останавливается.

Задача, которая не дочерняя, такой связи не получает. Тело, которое ждёт
`value` чужой задачи, пропускает её отмену с причиной как есть: исход читается
как `Cancelled(manual)` у задачи, у которой `cancel` никто не вызывал.

Кроме причины `reason`, `Cancelled` содержит флаг `started`, необязательное
описание `description` и стектрейс отмены. Флаг `started` показывает, успело ли
тело запуститься или отмена произошла до запуска. Встроенные классы причин:
`ManualCancelReason`, `ParentCancelReason`, `HandlerCancelReason`,
`ChainCancelReason` и `SiblingCancelReason`; последнюю группа `ctx.runAll`
выдаёт своим веткам, когда проваливается. Все они наследуют `CancelReason`.

Проверяйте причину по типу, например `reason is ParentCancelReason`. Свойство
`name` служит меткой для лога и не определяет равенство. По умолчанию причины
сравниваются по идентичности, но класс может определить равенство по данным.

Тело может бросить `Cancelled.by(reason: reason, started: true)` с явной
причиной или `Cancelled('why')` с причиной `HandlerCancelReason`. Стектрейс
ошибки, сохранённый в причине, отделён от стектрейса отмены:
`RequestCancelReason.stackTrace` указывает, где упал запрос,
а `Cancelled.stackTrace` — откуда пришла отмена.

## Реакция до исхода

Чтобы отреагировать на принятую отмену до получения итогового исхода,
зарегистрируйте слушателя через `job.whenCancelled(callback)`. Он вызывается
синхронно и получает `Cancelled` с причиной и подробностями. Сам метод
регистрации возвращает функцию снятия слушателя:

```dart
// Вызывается, когда отмена принята; задача ещё может завершать работу.
final unregister = report.whenCancelled((cancelled) {
  print('cancelling: ${cancelled.reason}');
});

await report.done;
// Безопасно после завершения; можно снять раньше, если больше не слушаем.
unregister();
```

Когда слушатель вызывается, зависит от того, как задачу отменили:

- При внешней отмене работающей задачи он вызывается после передачи отмены
  дочерним задачам и вызова колбэков `ctx.onCancel`, не дожидаясь окончания
  тела.
- При отмене до запуска он вызывается в момент отмены задачи.
- Если тело бросило `Cancelled`, он вызывается после окончания тела и дочерних
  задач, перед уборкой.

Когда проход по слушателям уже начался, новый слушатель при регистрации
вызывается сразу, даже если задача уже завершилась. Так бывает и со слушателем,
который регистрирует другого, пока выполняется сам: новый выполнится сразу,
раньше слушателей, которые ещё ждут своей очереди. Регистрация раньше, пока
отмена расходится по детям или пока задача, тело которой отменило себя, ждёт
их, встаёт в очередь прохода после зарегистрированных прежде. Отклонённая
отмена прохода не начинает. Секция `uncancellable` откладывает его до принятия
отмены. Задача, завершившаяся с `Done` или `Failed` без отмены, освобождает
слушателей без вызова.

Каждая регистрация срабатывает один раз. Слушатели, которые ждут своей очереди,
вызываются в порядке регистрации, по снимку списка: снятие слушателя во время
прохода не исключает его из этого прохода. Повторное снятие регистрации
безопасно.

Синхронная ошибка слушателя передаётся в `onError` и по умолчанию дальше в зону
создания задачи, а без наблюдателя прямо в эту зону. Брошенный `Cancelled`
в зону не передаётся. Ошибки слушателей не меняют отмену и не мешают вызову
остальных. `async`-колбэк принимается, но задача не ждёт его future, и ни одна
его ошибка не доходит до `onError`: `async`-функция синхронно не бросает
никогда, и даже ошибка до её первого `await` уходит в future, которую она
возвращает. Эта ошибка становится необработанной ошибкой той зоны, где вызван
слушатель. Для отмены, принятой внутри `cancel()`, это зона кода, который его
вызвал. Для отмены, которую придержала секция `uncancellable`, и для тела,
которое сдалось само, это зона, где идёт тело, а у задачи, которая запускается
сама, это зона, где её создали.
