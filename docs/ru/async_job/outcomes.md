# Исходы

Когда тело, дочерние задачи и уборка завершились, у задачи есть исход
`Outcome<T>`: `Done` со значением, которое вернуло тело, `Failed` с ошибкой,
которую оно бросило, или `Cancelled`. `job.done` завершается этим исходом
и никогда не бросает, `job.value` отдаёт только значение, а `job.outcome`
хранит исход после конца задачи и `null` до него. `Outcome<T>` объявлен как
`sealed`, поэтому `switch` по этим трём вариантам исчерпывающий.

Строки под кодом показывают, что он печатает при запуске, а строка `zone:`
означает ошибку, которая дошла до зоны необработанной. Каждый раздел ниже
открывается версией, к которой ведёт API, и показывает, что из неё выходит.
В первых трёх это член, названный по вопросу, который вы задаёте: `value` для
значения, `outcome` для того, чем кончилась задача, и `reason` для того, почему
её отменили. В последнем это исход, прочитанный через `done`, как его читает
первый раздел. Работающая версия идёт под своим заголовком.

## Чтение результата

Задачу `report` типа `Job<Report>` пользователь может отменить. Когда она
кончилась, код, который её запустил, печатает одно из трёх: отчёт, ошибку,
с которой задача упала, или то, что её отменили.

### Первая попытка

`value` отдаёт отчёт, а `try` принимает то, что пошло не так:

```dart
try {
  print('report: ${await report.value}');
} on Object catch (error) {
  print('failed: $error');
}
```

Пользователь отменяет, и отмена печатается как ошибка:

```text
failed: Cancelled(manual)
```

`value` при успехе завершается значением, а при ошибке или отмене бросает,
и для отмены бросает сам `Cancelled`. `Cancelled` реализует `Exception`,
поэтому `catch` принимает его вместе с ошибками: и `on Exception`,
и `on Object`.

### `switch` по `done`

```dart
final message = switch (await report.done) {
  Done(:final value) => 'report: $value',
  Failed(:final error) => 'failed: $error',
  Cancelled(:final reason) => 'cancelled: $reason',
};
print(message);
```

```text
cancelled: manual
```

`done` отдаёт исход, а не бросает его, и у каждого варианта своя строка.
`value` подходит коду, для которого отмена ничем не отличается от любой другой
ошибки, например тесту, который ждёт значение. Если результат совсем не нужен,
подтвердите это вызовом `report.ignore()`.

## Ошибка, которую никто не ждёт

`backup` загружает данные в фоне, и никто её не ждёт. Строка статуса при каждой
отрисовке читает, чем кончилась задача.

### Первая попытка

`outcome` хранит то, чем кончилась задача, и равен `null`, пока она идёт:

```dart
final backup = Job<void>(upload);

// Там, где рисуется строка статуса:
final status = switch (backup.outcome) {
  null => 'backing up',
  Done() => 'backed up',
  Failed(:final error) => 'backup failed: $error',
  Cancelled() => 'backup cancelled',
};
print('status: $status');
```

Загрузка падает. Зона, в которой создана задача, получает ошибку как
необработанную, а строка статуса, нарисованная после этого, говорит то же:

```text
zone: Bad state: disk full
status: backup failed: Bad state: disk full
```

Ошибка, которую никто не наблюдал, передаётся в зону создания задачи
на микротаске после её завершения: так она остаётся видна, даже когда
вызывающий код не ждёт результата. В тесте это зона теста, и тест падает.
Чтение `outcome` наблюдением не считается, как и ожидание `job.cancel()`,
регистрация через `whenCancelled` и любой колбэк наблюдателя: `onError`
и `onFinish` ошибку слышат, а в зону она всё равно приходит.

### Сказать ядру, что она обработана

```dart
final backup = Job<void>(upload)..ignore();
```

```text
status: backup failed: Bad state: disk full
```

`ignore()` говорит ядру, что ошибку обрабатывают в другом месте (здесь это
строка статуса), и в зону ничего не приходит. Обращение к `done` или `value`
тоже наблюдает ошибку, поэтому коду, который ждёт задачу, например чтобы
перерисовать строку статуса по её концу, `ignore()` не нужен. `done` не бросает
никогда, а с `value` ожидающий код получает саму ошибку и должен обработать её,
как у любой `Future`. Передача ошибки через `then` тоже наблюдает её:
ответственность переходит к продолжению.

Ожидание не наблюдает ошибку, которую накрыла отмена: тело `backup` падает,
а после этого приходит отмена, например пока задача ещё ждёт своих дочерних
задач или идёт её уборка. Задача кончается `Cancelled`: код, который её ждёт,
получает отмену, а не ошибку, и строка статуса пишет `backup cancelled`. Ошибка
идёт путём ошибки, которой не несёт ни один исход; этот путь показывает раздел
[«Куда уходят ошибки»](observing.md#куда-уходят-ошибки) страницы о наблюдении.
`ignore()` не пускает её в зону, и тогда её слышит только `onError`
наблюдателя.

## Почему задачу отменили

При отмене исход также объясняет, почему задача остановилась: `Cancelled`
хранит причину `reason`. В собственной причине можно хранить дополнительные
данные, например ошибку и её исходный стектрейс:

```dart
final class RequestCancelReason extends CancelReason {
  final Object error;
  final StackTrace stackTrace;

  const RequestCancelReason(this.error, this.stackTrace);

  @override
  String get name => 'request';
}
```

`report` запускает дочернюю задачу `fetch` за данными и ничего из того, что
из неё выходит, не ловит:

```dart
final fetch = Job.deferred<Data>(download);
final report = Job<Report>((ctx) async {
  final data = await ctx.run(fetch);
  return Report(data);
});
```

`fetch` нужен токен, который обновляет запрос в другом месте. Когда этот запрос
падает, код, который его отправил, отменяет `fetch` и передаёт ошибку
в причине, а исход `fetch` хранит этот же экземпляр причины:

```dart
try {
  await refreshToken();
} on Object catch (error, stackTrace) {
  await fetch.cancel(reason: RequestCancelReason(error, stackTrace));
}
```

Код, который запустил `report`, должен отличить упавший запрос от отмены
пользователем.

### Первая попытка

`switch` по `done` получает вариант для причины:

```dart
final message = switch (await report.done) {
  Done(:final value) => 'report: $value',
  Failed(:final error) => 'failed: $error',
  Cancelled(reason: RequestCancelReason(:final error)) =>
    'request failed: $error',
  Cancelled(:final reason) => 'cancelled: $reason',
};
print(message);
```

```text
cancelled: handler
```

Запрос отменил `fetch`, а не `report`. Отмена `fetch` вышла через тело
`report`, и `report` кончилась собственным `Cancelled` с причиной
`HandlerCancelReason`: её тело сдалось. `RequestCancelReason` лежит на шаг
глубже, в `cause` этой причины.

### По цепочке `cause`

```dart
CancelReason origin(Cancelled cancelled) => switch (cancelled.reason) {
      HandlerCancelReason(:final cause?) ||
      ParentCancelReason(:final cause?) ||
      ChainCancelReason(:final cause) =>
        origin(cause),
      final reason => reason,
    };

final message = switch (await report.done) {
  Done(:final value) => 'report: $value',
  Failed(:final error) => 'failed: $error',
  final Cancelled cancelled => switch (origin(cancelled)) {
      RequestCancelReason(:final error) => 'request failed: $error',
      final reason => 'cancelled: $reason',
    },
};
print(message);
```

```text
request failed: Bad state: token expired
```

Три причины хранят в `cause` отмену, которая их вызвала. Когда родитель
отменяет дочернюю задачу, её `ParentCancelReason.cause` хранит `Cancelled`
родителя. Когда отмена дочерней задачи выходит через тело родителя, его
`HandlerCancelReason.cause` хранит `Cancelled` дочерней задачи. В цепочке
`then` задача, отменённая соседом, хранит `Cancelled` соседа
в `ChainCancelReason.cause`. Эти ссылки сохраняют исходную причину и её данные,
и `origin` проходит по ним до конца: `cause` равен `null` там, где за причиной
ничего нет, как у тела, которое само бросило `Cancelled('why')`.
У `SiblingCancelReason` тоже есть `cause`, но это то, из-за чего остановилась
группа `ctx.runAll`: ошибка или отмена, которой кончилась другая ветка, или
ошибка самой группы. Поэтому `origin` по этому `cause` не идёт: он возвращает
сам `SiblingCancelReason`.

Тело, которое ждёт `value` чужой задачи, `HandlerCancelReason` для неё
не получает: её отмена проходит с причиной как есть, и исход читается как
`Cancelled(manual)` у задачи, у которой `cancel` никто не вызывал.

Кроме причины `reason`, `Cancelled` содержит флаг `started`, необязательное
описание `description` и стектрейс отмены. Флаг `started` показывает, успело ли
тело запуститься или отмена произошла до запуска. Встроенные классы причин:
`ManualCancelReason`, `ParentCancelReason`, `HandlerCancelReason`,
`ChainCancelReason` и `SiblingCancelReason`; все они наследуют `CancelReason`.
`SiblingCancelReason` выдаёт своим веткам группа `ctx.runAll`, когда
проваливается.

Проверяйте причину по типу, например `reason is ParentCancelReason`. Свойство
`name` служит меткой для лога и не определяет равенство. По умолчанию причины
сравниваются по идентичности, но класс может определить равенство по данным.

Тело может бросить `Cancelled.by(reason: reason, started: true)` с явной
причиной или `Cancelled('why')` с причиной `HandlerCancelReason`. Стектрейс
ошибки, сохранённый в причине, отделён от стектрейса отмены:
`RequestCancelReason.stackTrace` указывает, где упал запрос,
а `Cancelled.stackTrace` указывает, откуда пришла отмена.

## Реакция до исхода

`report` выполняет шаг, который отмена прервать не может, и после него убирает
за собой:

```dart
final report = Job<void>((ctx) async {
  ctx.onDispose(() => print('cleanup'));
  await ctx.run(
    Job.deferred<void>(cancellable: false, (ctx) async {
      await ctx.pause(const Duration(milliseconds: 50));
      print('step finished');
    }),
  );
});
```

Экран, который показывает отчёт, должен сказать об отмене сразу, как только
кто-то отменил задачу, пока шаг ещё идёт.

### Первая попытка

Исход говорит, отменили ли задачу:

```dart
if (await report.done case Cancelled(:final reason)) {
  print('cancelling: $reason');
}
```

```text
step finished
cleanup
cancelling: manual
```

Экран говорит об этом, только когда шаг и уборка уже позади. `done` завершается
исходом, а исход у задачи появляется, только когда закончились её тело, её дети
и уборка. Ожидание `report.cancel()` быстрее не будет: оно кончается в тот же
момент. `report.isCancelled` становится `true` в момент, когда отмена принята,
но экран узнает об этом, только когда снова прочитает геттер.

### Слушатель отмены

Чтобы отреагировать на принятую отмену до получения итогового исхода,
зарегистрируйте слушателя через `job.whenCancelled(callback)`. Он вызывается
синхронно и получает `Cancelled` с причиной и подробностями:

```dart
// Вызывается, когда отмена принята; задача ещё может завершать работу.
final unregister = report.whenCancelled((cancelled) {
  print('cancelling: ${cancelled.reason}');
});
```

```text
cancelling: manual
step finished
cleanup
```

Регистрация возвращает функцию, которая снимает слушателя. Её вызывает экран,
который закрылся, пока отчёт ещё идёт, и отмена, пришедшая после этого, экрану
ничего не сообщает:

```dart
// Экран закрылся; отчёт идёт дальше.
unregister();
```

```text
step finished
cleanup
```

Когда задача завершилась, снимать уже нечего: каждый слушатель либо вызван,
либо отпущен, и вызов этой функции ничего не делает.

Когда слушатель вызывается, зависит от того, как задачу отменили:

- При внешней отмене работающей задачи он вызывается после передачи отмены
  дочерним задачам и вызова колбэков `ctx.onCancel`, не дожидаясь окончания
  тела.
- При отмене до запуска он вызывается в момент отмены задачи.
- Если тело сдаётся само (бросает `Cancelled` или выпускает отмену другой
  задачи, когда задачу никто не отменял), он вызывается, когда тело кончается:
  после передачи отмены дочерним задачам и вызова колбэков `ctx.onCancel`,
  не дожидаясь окончания дочерних задач.

Когда проход по слушателям уже начался, новый слушатель при регистрации
вызывается сразу, даже если задача уже завершилась. Так бывает и тогда, когда
слушатель регистрирует другого, пока выполняется сам: новый выполнится сразу,
раньше слушателей, которые ещё ждут своей очереди. Пока проход не начался,
новый слушатель встаёт в очередь прохода после зарегистрированных раньше, даже
если отмена уже расходится по дочерним задачам или идут колбэки `ctx.onCancel`
самой задачи. Отклонённая отмена прохода не начинает. Секция `uncancellable`
откладывает его до принятия отмены. Задача, завершившаяся с `Done` или `Failed`
без отмены, освобождает слушателей без вызова.

Каждая регистрация срабатывает один раз. Слушатели, которые ждут своей очереди,
вызываются в порядке регистрации, по снимку списка: снятие слушателя во время
прохода не исключает его из этого прохода. Повторное снятие регистрации
безопасно.

Синхронная ошибка слушателя передаётся в `onError`, а затем в зону создания
задачи, если наблюдатель не отвечает за неё сам, как показывает раздел
[«Куда уходят ошибки»](observing.md#куда-уходят-ошибки) страницы о наблюдении.
Без наблюдателя она уходит прямо в эту зону. Брошенный `Cancelled` в зону
не передаётся. Ошибки слушателей не меняют отмену и не мешают вызову остальных.
Future `async`-колбэка задача не ждёт, и ни одна его ошибка не доходит
до `onError`: `async`-функция синхронно не бросает никогда, и даже ошибка до её
первого `await` уходит в future, которую она возвращает. Эта ошибка становится
необработанной ошибкой той зоны, где вызван слушатель. Для отмены, принятой
внутри `cancel()`, это зона кода, который его вызвал. Для отмены, которую
придержала секция `uncancellable`, и для тела, которое сдалось само, это зона,
где идёт тело. Тело задачи из `Job(...)` идёт в зоне, где её создали, а тело
задачи из `Job.deferred` идёт в зоне, откуда её запустили. Если задачу
из `Job(...)` создали или задачу из `Job.deferred` запустили внутри работы,
отданной `ctx.unattended`, её тело идёт в зоне, откуда эту работу начали.
