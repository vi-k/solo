# Ошибки

`JobObserver` слышит ошибки, которых не несёт ни один исход, как показывает
страница [«Наблюдение»](observing.md). Такая ошибка, если это не отмена, идёт
дальше, к ответу, и туда же идёт провал, чей исход никто не наблюдает. Куда они
уходят, называют два слова:

- зона — это зона, где задача создана, и ошибка, которая до неё дошла, там
  неперехваченная;
- ответ — это `onUnanswered` наблюдателя, который подмешивает `JobAnswerer`,
  как показывает раздел [«Ответ за ошибки»](#ответ-за-ошибки), и зона, если
  такого наблюдателя у задачи нет.

Приложение, которому нужно лишь сообщать о каждой ошибке один раз, начинает
с раздела в конце страницы:
[«Сообщать о каждой ошибке один раз»](#сообщать-о-каждой-ошибке-один-раз).

Строки под кодом — то, что код печатает:

| Строка | Что это |
| --- | --- |
| `cancel` | пользователь отменяет задачу |
| `outcome:` | то, чем завершается `job.done` |
| `onError:` | ошибка, которую слышит наблюдатель |
| `onUnanswered:` | ошибка, за которую наблюдатель ответил |
| `zone:` | ошибка, дошедшая до зоны неперехваченной |

## Куда уходят ошибки

Приложение сообщает о каждой ошибке, которая дошла до его зоны неперехваченной.
Задача мигрирует базу, а отмена останавливает миграцию по её токену, как
в разделе [«Токен через `onCancel`»](cancellation.md#токен-через-oncancel)
страницы об отмене. Пользователь отменяет, пока миграция идёт.

### Первая попытка

Dart отправляет в зону ошибку, которую никто не поймал, поэтому приложение
полагается на зону, наблюдателя задаче не даёт и связывает токен так же, как
страница об отмене:

```dart
// Первая попытка: каждая отмена доходит до зоны как сбой.
final job = Job<void>((ctx) async {
  final stop = CancelToken();
  ctx.onCancel(stop.cancel);

  await ctx.join(() => database.migrate(stop));
});
```

```text
cancel
zone: DatabaseStopped
outcome: Cancelled(manual)
```

Ничего не сломалось, а зона сообщает о сбое при каждой отмене. Вот что
происходит:

1. Задача принимает отмену, и `onCancel` отменяет токен. С этого момента она
   кончится `Cancelled`, что бы ни сделала миграция.
2. Миграция останавливается по токену и бросает свой `DatabaseStopped`,
   а `join` бросает его как есть. Тело падает с этой ошибкой на уже отменённой
   задаче.
3. Исходом эта ошибка не становится: исход несёт отмену. Задача отвечает
   за неё, как за любой провал своего тела, который исход не несёт: её
   услышал бы `onError` наблюдателя, а дальше она идёт к ответу, и без
   наблюдателя ответ — зона.

Задача не может знать, что это за ошибка. Здесь операция остановилась по токену
задачи. Но настоящий сбой после отмены идёт тем же путём, и его услышать нужно:
если база после отмены оказалась заблокирована, приложение должно об этом
узнать.

### Ошибки отмены

Ошибкой отмены называется ошибка, которую операция бросает потому, что её
остановила отмена задачи: `DatabaseStopped` от токена, который отменил
`ctx.onCancel`, или `DioException` из `dio`, для которой выполняется
`CancelToken.isCancel`. Приложение называет такие ошибки один раз, в `main`:

```dart
Job.isCancellationError = (error) => error is DatabaseStopped;
```

```text
cancel
outcome: Cancelled(manual)
```

Задача осталась прежней. `Job.isCancellationError` спрашивают о каждом провале
задачи, которая приняла отмену. Спрашивают, когда задача собирается отправить
провал к ответу, и только тогда. Названная им ошибка по-прежнему доходит
до `onError` и дальше не идёт: её не слышат ни `onUnanswered`, ни зона. Исходов
фильтр тоже не меняет. О провале задачи, которую никто не отменял, его
не спрашивают: тело, которое бросает `DatabaseStopped`, пока его задача идёт
дальше, кончается с ним `Failed`, и если этот исход никто не наблюдает, он идёт
к ответу. Токен тогда отменил кто-то другой, и задача должна об этом сказать.

Фильтр вызывается синхронно, с одним провалом за раз и никогда с `Cancelled`,
поэтому пусть он только проверяет тип. Задача обходит `ParallelWaitError`
и спрашивает о каждом провале внутри него отдельно. Если фильтр бросил, это
ошибка приложения: она уходит в зону, где создана задача, а провал, о котором
его спрашивали, идёт дальше к ответу.

Поле принадлежит приложению, как `Job.debug`, и библиотека его не ставит. Если
свои ошибки называют две части приложения, вторая продолжает цепочку первой:

```dart
final previous = Job.isCancellationError;
Job.isCancellationError =
    (error) => error is DatabaseStopped || (previous?.call(error) ?? false);
```

Тест, который ставит поле, возвращает его в `tearDown`, как вернул бы
`Job.debug`.

### С наблюдателем

Ещё приложение хочет видеть ошибки своих задач по мере того, как они случаются.
Задача открывает базу, пользователь отменяет, пока она открывается, а затем
открытие падает: база заблокирована.

```dart
final class Reporter extends JobObserver {
  @override
  void onError(Job<Object?> job, Object error, StackTrace stackTrace) =>
      print('onError: $error');
}

final job = Job<Database>(
  observer: Reporter(),
  (ctx) => ctx.join(
    Database.open,
    discard: (database) => database.close(),
  ),
);
```

```text
cancel
onError: Bad state: database locked
zone: Bad state: database locked
outcome: Cancelled(manual)
```

Наблюдатель слышит через `onError` ошибки, которые ловит его задача, кроме её
собственной отмены. Но только слышит: переопределение `onError` никуда ошибку
не переносит. Упавшее открытие всё равно доходит до зоны, как дошло бы без
наблюдателя: задача кончается `Cancelled`, а фильтр выше `StateError`
не называет.

Провал, который несёт исход, идёт к ответу, только если исход никто
не наблюдает, через микрозадачу после конца задачи, и наблюдатель, который
отвечает, получает его в `onUnanswered`. Исход считается наблюдаемым, когда
кто-то читает `done` или `value`, вызывает `ignoreFailure()` или передаёт
провал дальше через `then`: продолжение, которое отменили раньше, чем упал его
источник, ничего не передаёт, и провал остаётся ненаблюдаемым. Об этом раздел
[«Ошибка, которую никто не ждёт»](outcomes.md#ошибка-которую-никто-не-ждёт)
страницы об исходах. Хуки наблюдателя исход не наблюдают, даже хук, который
читает `job.outcome`, как `onFinish` у `Log` из раздела
[«Наблюдатель»](observing.md#наблюдатель).

### Куда идёт каждая ошибка

Таблица показывает, куда уходит каждая ошибка, с наблюдателем и без него. Зона
и ответ — те, что определены во вступлении. Более редкие пути, например пути
`ctx.runAll` и движков, собраны в разделе [«Редкие маршруты»](#редкие-маршруты)
ниже.

| Ошибка | С наблюдателем | Без него |
| --- | --- | --- |
| Ошибка тела, и задача кончается с ней `Failed` | `onError`, затем ответ, если исход никто не наблюдал | Зона, если исход никто не наблюдал |
| Ошибка тела, и задача кончается `Cancelled` | `onError`, затем ответ | Зона |
| Поздняя ошибка действия, ожидание которого прервал `ctx.abandonable` | `onError`, затем ответ | Зона |
| Ошибка уборки | `onError`, затем ответ | Зона |
| Ошибка колбэка `ctx.onCancel`, `job.whenCancelled` или `job.whenFinished` | `onError`, затем ответ | Зона |
| Ошибка работы `ctx.unattended` | `onError`, затем ответ | Зона |

Чего таблица не показывает:

- Если тело вызывает контекст без `await`, вызов бросает в future, которую
  никто не ждёт. Dart отдаёт эту ошибку зоне, где идёт тело, с наблюдателем
  и без него; у задачи, созданной через `Job.deferred`, это зона, откуда её
  запустили.
- Если задачу отменяют, пока идёт тело, `ctx.abandonable`, вызванный без
  `await`, бросает `Cancelled` в свою future, и Dart отдаёт его зоне, где идёт
  тело, как любую другую ошибку: туда же уходит и собственная отмена задачи.
  Эту отмену в зону отправляет не задача, а Dart.
- Если действие `ctx.abandonable`, вызванного без `await`, упадёт, когда тело
  уже кончилось, ошибка идёт путём поздней ошибки действия, которое
  `ctx.abandonable` перестал ждать. Её слышит `onError`, а дальше она идёт
  к ответу. Вызов `ctx.abandonable` без `await` доходит до зоны, где идёт тело,
  со своей ошибкой или с отменой задачи, только пока тело идёт.
- Если задача приняла отмену, ошибка, которую называет
  `Job.isCancellationError`, не идёт дальше `onError`. Это касается строк обеих
  таблиц, которые кончаются ответом: строк тела отменённой задачи и строк
  ошибок вне тела. Откуда бы ошибка ни пришла, так и будет: из тела, из шага
  `ctx.uncancellable`, из дочерней задачи, которую задача ждала, из уборки.
- Если задача кончается `Cancelled`, исход несёт отмену, а не провал тела. Этот
  провал уходит в `onUnanswered` или в зону, даже если исход наблюдали,
  и так же уходит провал ветки `ctx.runAll`, чья группа бросила другую ошибку.
- Если у задачи, чьё тело упало, кто-то вызвал `ignoreFailure()`, провал её
  тела дальше не идёт: `onError` его по-прежнему услышит,
  но ни до `onUnanswered`, ни до зоны он не дойдёт.
- Если упало тело дочерней задачи, она отвечает за свой провал сама, что бы
  ни вызвал её родитель: `ignoreFailure()` у родителя отпускает провалы только
  самого родителя.
- Если приложение сообщает об ошибках и в `onError`, и в зоне, ошибку, которая
  дошла до обоих, оно услышит дважды. Таблица выше показывает один путь
  от задачи в зону — ответ, когда за ошибку никто не отвечает или
  `onUnanswered` отправляет её дальше или бросает. Движок, который нарочно
  кончает задачу `Failed`, добавляет второй, мимо ответа: последняя строка
  [«Редких маршрутов»](#редкие-маршруты).
- Если исход кто-то наблюдал, провал, который несёт исход, с пути через ответ
  снят: он идёт этим путём, только если исход никто не наблюдал. Наблюдатель,
  который отвечает (`with JobAnswerer`), закрывает сам путь.
- Если один провал стал исходом нескольких задач, он доходит до `onError`
  по разу на каждой из них. Ребёнок `ctx.run` падает, родитель выпускает провал
  из тела, и наблюдатель, которого ребёнок унаследовал, слышит тот же объект
  на ребёнке, а потом на родителе. Так же ведут себя ветка `ctx.runAll` и её
  родитель, источник и его продолжение `then` с одним наблюдателем.
- Если наблюдатель считает провалы, он отличает второй вызов от новой ошибки
  по `identical`, а `Expando` помнит услышанные ошибки и не держит их в памяти.
  Ошибка, брошенная константой, например `throw const SignedOut()`, — один
  и тот же объект при каждом броске, и два таких провала считаются за один.

### Отладочный канал

При отладке ошибки, которые задача отдаёт своему наблюдателю, видны, даже если
наблюдателя не писать. Приложение включает отладочный канал в `main`:

```dart
Job.debug = print;
```

Канал печатает запуск, отмену и конец каждой задачи. Ещё он печатает каждую
ошибку, которую задача отдаёт наблюдателю, есть у задачи наблюдатель или нет,
а если ошибка ушла дальше в зону, говорит и об этом. Первая попытка выше под
каналом:

```text
Job() started
cancel
cancel Job(): Cancelled(manual)
Job() error: DatabaseStopped
Job() finished: Cancelled(manual)
Job() error nobody answered for: DatabaseStopped
Job() error went to the zone: DatabaseStopped
zone: DatabaseStopped
outcome: Cancelled(manual)
```

Строки, которые начинаются с `Job()`, и строка `cancel Job()` — строки канала.
С фильтром вместо трёх строк после `Job() finished` канал печатает одну:
`Job() kept a cancellation error out of the answer: DatabaseStopped`. Фильтр
один на всё приложение, и по каналу видно, почему ошибка так и не дошла
до зоны.

`ParallelWaitError` занимает в канале одну строку, целиком, тогда как `onError`
слышит каждый провал внутри него по отдельности. Канал один на все задачи
приложения и говорит с тем, кто читает консоль. Через наблюдателя приложение
слышит то, на что ему надо отреагировать.

### Пределы фильтра

- Ошибка, которую тело делает из собственной отмены, до фильтра тоже доходит,
  но проверка типа из раздела [«Ошибки отмены»](#ошибки-отмены) её не узнаёт.
  Тело, которое ловит всё вокруг `ctx.abandonable` и бросает вместо пойманного
  свою ошибку, например `throw AppException(error)`, заворачивает каждый
  `Cancelled` в `AppException`, и зона слышит его при каждой отмене. Фильтр
  называет обёртку по причине:

```dart
Job.isCancellationError =
    (error) => error is AppException && error.cause is Cancelled;
```

- Вместо этого `catch` может первым делом вызвать `ctx.check()`, как в разделе
  [«Спросить задачу»](cancellation.md#спросить-задачу) страницы об отмене:
  тогда наружу уходит сама отмена, а отмена не провал. Это обходится дороже
  фильтра: когда задача приняла отмену, `ctx.check()` бросает её, что бы
  ни поймал `catch`. Тело, которое ждёт через `ctx.join`, так теряет настоящий
  провал, дошедший до `catch` после отмены: например, открытие, которое нашло
  базу заблокированной. Его не слышат ни `onError`, ни зона. Фильтр не пускает
  только те ошибки, которые называет.
- Фильтр только не пускает ошибки к ответу, и `ctx.runAll` это показывает.
  Ветка, которую отменили снаружи и чьё тело бросило ошибку отмены, для группы
  упала. Поэтому группа отменяет остальные ветки с `SiblingCancelReason`,
  у которой причиной стоит эта ошибка. Ветка, которую никто не отменял
  и которая кончилась `Failed` с такой ошибкой, считается обычным провалом.
  Группа бросает её ошибку вместо отмены другой ветки, и тело родителя получает
  эту ошибку, а не `Cancelled`.
- Фильтр не видит ошибку, которую Dart отдаёт зоне сам, мимо задачи. Это ошибка
  вызова контекста, которого тело не дождалось, например
  `unawaited(ctx.join(() => database.migrate(stop)))`, и ошибка `async`-колбэка
  `ctx.onCancel`. Их разбирают разделы
  [«Куда идёт каждая ошибка»](#куда-идёт-каждая-ошибка)
  и [«Остановка, которая занимает время»](cancellation.md#остановка-которая-занимает-время).

### Редкие маршруты

Здесь пути ветки `ctx.runAll`, имени дочерней задачи, `Cancelled` и движка.
Столбцы — те же, что в разделе
[«Куда идёт каждая ошибка»](#куда-идёт-каждая-ошибка).

| Ошибка | С наблюдателем | Без него |
| --- | --- | --- |
| Ошибка тела в ветке `ctx.runAll`, чья группа бросает другой провал | `onError`, затем ответ | Зона |
| Ошибка `toString` ключа дочерней задачи, её `describe` или её `Cancelled`, когда ядро называет её в отмене родителя | `onError`, затем ответ | Зона |
| `Cancelled`, брошенный вне тела | `onError` | Никто |
| Собственная отмена задачи из действия, ожидание которого прервал `ctx.abandonable`, или из работы `ctx.unattended` | Никто | Никто |
| Провал задачи, которую движок заканчивает `Failed` с `Cancelled` или с `ParallelWaitError` из одних отмен, чтобы провалить её нарочно | `onError`, затем зона мимо ответа, если исход никто не наблюдал | Зона, если исход никто не наблюдал |

## Работа, которую задача не ждёт

Задача отправляет событие аналитики и не ждёт его. Отправка падает: аналитика
недоступна. У задачи `Reporter` из раздела [«С наблюдателем»](#с-наблюдателем).

### Первая попытка

`unawaited` из Dart помечает future, которую намеренно не ждут:

```dart
// Первая попытка: ошибка уходит в зону, а не в задачу.
unawaited(analytics.send('loaded'));
```

```text
outcome: Done(null)
zone: Bad state: analytics offline
```

Наблюдатель не слышит ничего, и ничто не связывает ошибку с задачей. Ошибка
future, которую никто не ждёт, уходит в зону как неперехваченная. `unawaited`
лишь говорит анализатору, что future не ждут намеренно.

### Работа, переданная задаче

```dart
ctx.unattended(() => analytics.send('loaded'));
```

```text
outcome: Done(null)
onError: Bad state: analytics offline
zone: Bad state: analytics offline
```

`ctx.unattended(action)` оставляет ошибки работы при задаче, даже те, что
приходят, когда задача уже кончилась. Их слышит наблюдатель, а дальше они
уходят в зону, где задача создана, если наблюдатель за них не отвечает. Без
наблюдателя они уходят туда сразу. Задача работу не ждёт и не отменяет.

Запускайте работу внутри колбэка и ничего из него не выносите. Работа идёт
в собственной зоне ошибок, и граница действует в обе стороны:

- Future, созданная снаружи и ожидаемая внутри, при ошибке не возвращается
  никогда, а её ошибка уходит в зону, где создана сама future.
- Future, созданная внутри и ожидаемая снаружи, при ошибке вешает того, кто её
  ждёт. Если её ждёт тело, зависает задача.

Задача, запущенная внутри колбэка, границе не подчиняется: её тело идёт в зоне,
откуда начата работа.

## Ответ за ошибки

Ошибки, которых не несёт ни один исход, идут от `onError` дальше, к ответу,
и туда же идут провалы, чей исход никто не наблюдает. Наблюдатель, который
только смотрит, например `Reporter`, ответа не даёт, поэтому эти ошибки уходят
туда же, куда ушли бы без наблюдателя: в зону. То, что наблюдатель слышит
ошибку, само по себе не меняет, куда она уходит. Наблюдатель, который отвечает
за эти ошибки сам, подмешивает `JobAnswerer` и переопределяет `onUnanswered`:

```dart
final class Answering extends JobObserver with JobAnswerer {
  @override
  void onUnanswered(Job<Object?> job, Object error, StackTrace stackTrace) =>
      print('onUnanswered: $error');
}
```

Там ошибки и останавливаются, до зоны они не доходят. `onUnanswered`
по умолчанию отправляет их в зону, где задача создана, как и без ответа.
Поэтому вызов `super.onUnanswered(job, error, stackTrace)` тоже отправляет
ошибку дальше в зону. Наблюдатель, который отвечает только за знакомые ему
ошибки базы данных, отдаёт остальное `super`:

```dart
final class DatabaseErrors extends JobObserver with JobAnswerer {
  @override
  void onUnanswered(Job<Object?> job, Object error, StackTrace stackTrace) {
    if (error is DatabaseException) {
      print('onUnanswered: $error');
    } else {
      super.onUnanswered(job, error, stackTrace);
    }
  }
}
```

Переопределение отвечает за задачу, которой передали наблюдателя, и за дочерние
задачи, которые его наследуют, на любой глубине. Чтобы ответить за все задачи
сразу, приложение пользуется своей зоной, где и так сообщает о неперехваченном:
туда эти ошибки приносит `onUnanswered`, если его не переопределять. Зона
получает ошибку и её стектрейс, но не задачу, так что отчёту, который называет
задачу, нужно переопределение.

Переопределение, которое бросило, не уносит ошибку с собой. Ошибка уходит
в зону, где создана задача, а следом в текущую зону уходит то, что бросило
переопределение, как и у любого хука; брошенный им `Cancelled` в зону
не попадает, как и сама ошибка, брошенная обратно, так что ошибка уходит туда
один раз. Переопределение, которое успело сообщить об ошибке и только потом
бросило, сообщит о ней дважды: в свою систему и в зону.

### Несколько провалов в одной ошибке

Задача отдаёт `ctx.unattended` две операции, которых ждут вместе. `saveDraft`
падает с `DatabaseException`, а `sendAnalytics` падает со `StateError`.
`[saveDraft(), sendAnalytics()].wait` бросает `ParallelWaitError`, в котором
лежат оба провала:

```dart
final job = Job<void>(
  observer: DatabaseErrors(),
  (ctx) async {
    ctx.unattended(() => [saveDraft(), sendAnalytics()].wait);
  },
);
```

```text
outcome: Done(null)
onUnanswered: DatabaseException
zone: Bad state: analytics offline
```

`onUnanswered` спрашивают об одном провале за раз. Задача обходит
`ParallelWaitError` и спрашивает о каждом провале внутри него, со стектрейсом
этого провала. Поэтому за ошибку базы данных отвечает наблюдатель, а ошибку
аналитики зона слышит отдельно. За `Failed` с такой ошибкой, который никто
не наблюдает, отвечают так же, провал за провалом. Неперехваченный `Cancelled`
не провал, и о нём не спрашивают никого, пришёл ли он один или внутри
`ParallelWaitError`. Не спрашивают никого и об ошибке, которую приложение
назвало в разделе [«Ошибки отмены»](#ошибки-отмены), если задача приняла
отмену.

`onError` тоже слышит их по одной, а `Cancelled` внутри `ParallelWaitError`
слышит отдельным вызовом. Исход хранит ошибку такой, какой её бросили: тело,
упавшее с `ParallelWaitError`, кончается `Failed` с этой ошибкой.
`Job.visitErrors` делает тот же обход для того, кто читает исход:

```dart
final outcome = await job.done;
if (outcome case Failed(:final error, :final stackTrace)) {
  Job.visitErrors(
    error,
    stackTrace,
    onFailure: (failure, failureStackTrace) => print('failed: $failure'),
  );
}
```

## Несколько наблюдателей

Приложение отправляет всё, за что никто не ответил, в отчёт о падениях.
У задачи из раздела
[«Работа, которую задача не ждёт»](#работа-которую-задача-не-ждёт) остаётся
и её `Reporter`. Отвечает наблюдатель `Crashes`:

```dart
final class Crashes extends JobObserver with JobAnswerer {
  @override
  void onUnanswered(Job<Object?> job, Object error, StackTrace stackTrace) =>
      print('onUnanswered: $error');
}
```

### Первая попытка

`observer:` принимает одного `JobObserver`, поэтому класс передаёт свои хуки
обоим, а ответ — `Crashes`:

```dart
// Первая попытка: каждый хук передаётся вручную и без try/catch.
final class Both extends JobObserver with JobAnswerer {
  final _reporter = Reporter();
  final _crashes = Crashes();

  @override
  void onError(Job<Object?> job, Object error, StackTrace stackTrace) {
    _reporter.onError(job, error, stackTrace);
    _crashes.onError(job, error, stackTrace);
  }

  @override
  void onUnanswered(Job<Object?> job, Object error, StackTrace stackTrace) =>
      _crashes.onUnanswered(job, error, stackTrace);

  // onStart, onFinish и onLog так же, как onError.
}
```

```text
outcome: Done(null)
onError: Bad state: analytics offline
onUnanswered: Bad state: analytics offline
```

Это работает: `Reporter` слышит ошибку, `Crashes` за неё отвечает. Но каждый
хук передаётся руками: пять методов на два наблюдателя, а третий наблюдатель
добавит по строке в каждый. Для полноты каждый вызов надо ещё обернуть
в `try`/`catch`, иначе наблюдатель, который бросил исключение, выключает тех,
кто идёт после него.

### Наблюдатели одним списком

```dart
final job = Job<void>(
  observer: JobObserver.all([Reporter(), Crashes()]),
  (ctx) async {
    ctx.unattended(() => analytics.send('loaded'));
  },
);
```

```text
outcome: Done(null)
onError: Bad state: analytics offline
onUnanswered: Bad state: analytics offline
```

`JobObserver.all` передаёт каждый хук каждому наблюдателю в порядке списка,
и каждый вызов идёт сам по себе: наблюдатель, который бросил исключение,
не выключает следующего. Наблюдатель с `JobAnswerer` тоже смотрит на своём
месте в списке и отвечает за весь список, когда `onError` услышали все. Если
`JobAnswerer` в списке нет, ошибки уходят в зону, как у наблюдателя, который
не отвечает. Если отвечающих двое или один и тот же наблюдатель стоит дважды,
`JobObserver.all` бросает `ArgumentError`. Наблюдатель, собранный
`JobObserver.all`, может стоять в списке другого и отвечает там, если отвечает
кто-то внутри него.

## Сообщать о каждой ошибке один раз

Приложение, которое сообщает об ошибках, хочет услышать каждую один раз. Все их
забирают два места, которые не пересекаются: наблюдатель, который отвечает
за ошибки, и зона, в которой идёт приложение.

```dart
final class Reports extends JobObserver with JobAnswerer {
  @override
  void onUnanswered(Job<Object?> job, Object error, StackTrace stackTrace) =>
      print('report: $job: $error');
}
```

```dart
runZonedGuarded(
  startApp,
  (error, stackTrace) => print('report: $error'),
);
```

`startApp` — функция, которая запускает приложение, во Flutter, например,
`() => runApp(const App())`. Каждая корневая задача получает
`observer: Reports()`, и её дети его наследуют. Кто о чём сообщает:

| Ошибка | Кто сообщает |
| --- | --- |
| Провал, исход которого никто не наблюдал | `Reports`, и он называет задачу |
| Провал, исход которого кто-то наблюдал | никто: он у кода, который его наблюдал |
| Провал ребёнка, который родитель выпустил из тела | `Reports`, один раз, как провал родителя, если родителя никто не наблюдал |
| Ошибка, которой не несёт ни один исход, например ошибка тела отменённой задачи, уборки, колбэка, действия, которое задача перестала ждать | `Reports`, и он называет задачу |
| Ошибка, которую приложение бросает вне своих задач | зона |

`Reports` отвечает за все ошибки задач, которых больше ни у кого нет, поэтому
они останавливаются на нём и до зоны не доходят; в зону уходит то, что
приложение бросает вне своих задач. Зона задачи не знает, поэтому её отчёт
задачу не называет. `onError` в отчёте не участвует: провал, который он слышит,
может попасть и в отчёт, а один провал он слышит по разу на каждой задаче,
исходом которой этот провал стал. Все пути ошибки показывают разделы
[«Куда идёт каждая ошибка»](#куда-идёт-каждая-ошибка)
и [«Редкие маршруты»](#редкие-маршруты).
