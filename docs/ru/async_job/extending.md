# Своё поверх ядра

Если вашей библиотеке нужны своё состояние, очередь или правила планирования,
стройте их поверх ядра: наследуйте `JobBase<T>` для задачи и `JobContextBase`
для контекста, который получает её тело. Базовые классы держат жизненный цикл,
описанный на других страницах: старт, [детей](children.md),
[отмену](cancellation.md), [уборку](cleanup.md) и [исход](outcomes.md).
Наследники добавляют поведение библиотеки через свой защищённый API. Третий
тип, `JobStatus`, говорит, где задача в своей жизни: `created`, `running` или
`finished`.

Все три живут в `package:async_job/engine.dart`, а не в основном импорте:
приложению, которое только запускает задачи, они не нужны. Движок импортирует
эту библиотеку вместо `async_job.dart`, который она тоже экспортирует.

Строки под кодом показывают, что он печатает при запуске. Наблюдатель задачи
печатает то, что до него дошло: `onError:` для ошибки. `cancel` и `sign out`
отмечают моменты, когда пользователь отменяет задачу или выходит из аккаунта,
а `outcome:` показывает, чем завершается `job.done`. Две части страницы ниже
открываются версией, к которой ведёт защищённый API: очередь, которая запускает
свои задачи через `start`, и правило, добавленное в `check()`. Каждая
показывает, что этот код делает. Где исправляющая версия всё ещё не дотягивает,
она стоит второй попыткой, а рабочая версия идёт следом под своим заголовком.

## Своя задача

Своя задача создаёт контекст, который получает её тело, а движок, который её
запускает, открывает себе свою дверь к защищённому:

```dart
import 'package:async_job/engine.dart';

final class MyJob<T> extends JobBase<T> {
  MyJob(this._body, {super.key, super.observer});

  final Future<T> Function(MyContext ctx) _body;

  @override
  JobContextBase createContext() => MyContext(this);

  @override
  Future<T> execute(covariant MyContext ctx) => _body(ctx);

  // `start` и `whenDone` защищены: движок открывает к ним свои двери,
  // закрытые для всех вне его библиотеки.
  void _launch() => start();

  Future<void> get _whenDone => whenDone;
}

final class MyContext extends JobContextBase {
  MyContext(super.owner);
}
```

`@protected` действует внутри наследника, а движок обращается к задаче сбоку:
из своей очереди, из своего контроллера. Обёртки приватные, поэтому движок
живёт в библиотеке `MyJob`, и никто другой, у кого есть задача, не запустит её
в обход движка. `whenDone` ждёт задачу, не наблюдая её исход, поэтому провал,
на который никто не посмотрел, всё равно доходит до зоны. Ожидание `done`
считалось бы наблюдением.

Переопределите `started()` и `finished()`, чтобы следить за жизненным циклом.
`started()` вызывается перед стартом тела, когда задача уже работает.
`finished()` вызывается, когда у задачи появился исход, в том числе у задачи,
снятой до того, как её тело начало работу. Перед таким `finished()` вызова
`started()` не было. Ошибка, брошенная любым из них, уходит в `onError`
и `onUnanswered`, а задача идёт дальше как шла; недоделанным остаётся ваш
собственный учёт, поэтому держите оба короткими и безусловными.

Чтобы дать свой ответ ошибке, на которую никто не ответил, повесьте своего
наблюдателя на каждую задачу и переопределите его
[`onUnanswered`](observing.md#с-наблюдателем), как это делает `solo`. Ребёнок,
принятый без наблюдателя, берёт наблюдателя родителя, поэтому ответ доходит
и до детей. Исключение составляет ребёнок, который пришёл со своим
наблюдателем: он отвечает через своего. Продолжение, которое создаёт `then`,
не задача вашего движка: оно принадлежит тому, кто вызвал `then`, и у него
только тот наблюдатель, которого передали в `then`. Провал вашей задачи,
который оно принимает, этот наблюдатель слышит как провал самого продолжения.
За ошибки в коде продолжения отвечает тот, кто вызвал `then`, в своей зоне,
поэтому своего наблюдателя продолжению не передавайте.

Когда ответ вашего движка никому не достаётся, `reportToZone` передаёт ошибку
в зону создания задачи и не пускает туда отмену, как это делает ядро. Если
метод контекста нельзя вызывать
из [работы, запущенной через `unattended`](observing.md#работа-которую-задача-не-ждёт),
проверяйте это с помощью `throwIfUnattended`. Весь защищённый API описан
в справке
[JobBase](https://pub.dev/documentation/async_job/latest/engine/JobBase-class.html)
и [JobContextBase](https://pub.dev/documentation/async_job/latest/engine/JobContextBase-class.html).

## Своя очередь

Движок выполняет свои задачи по одной, в том порядке, в каком они пришли.
Задачу могут отменить, пока она ждёт своей очереди, и те, что стоят за ней, всё
равно должны выполниться.

### Первая попытка

Очередь хранит задачи и запускает каждую через дверь `MyJob`:

```dart
final class MyQueue {
  final _waiting = <MyJob<Object?>>[];

  void add(MyJob<Object?> job) => _waiting.add(job);

  Future<void> run() async {
    while (_waiting.isNotEmpty) {
      final job = _waiting.removeAt(0).._launch();
      await job._whenDone;
    }
  }
}
```

Пользователь отменяет вторую задачу, пока работает первая:

```dart
final second = MyJob<void>(key: 'second', (ctx) => ctx.wait(upload));
final queue = MyQueue()
  ..add(MyJob<void>(key: 'first', (ctx) => ctx.wait(upload)))
  ..add(second);
final running = queue.run();
await second.cancel();
print('second: ${await second.done}');
try {
  await running;
  print('the queue is empty');
} on StateError catch (error) {
  print('the queue stopped: $error');
}
```

```text
second: Cancelled(manual)
the queue stopped: Bad state: Job(second) has already finished
```

Задачу, которая ещё не стартовала, отмена заканчивает сразу: останавливать
в ней нечего, тела нет. Очередь всё ещё держала её, и когда подошла её очередь,
`start` бросил ошибку. На этом очередь остановилась, и все задачи за второй
ждут вечно.

### Уйти из очереди при отмене

Любая отмена задачи приходит в `cancelWith`: `cancel()`, каскад от родителя,
правило движка, которое отменяет через `cancelOwnJob`. Это единственный член
жизненного цикла, который наследник дополняет, а не заменяет, и анализатор
требует, чтобы переопределение вызывало `super`. `MyJob` помнит очередь,
которая её держит, и там же из неё уходит:

```dart
  MyQueue? _queue;

  @override
  void cancelWith(Cancelled cancelled, {bool rejectable = true}) {
    _queue?._waiting.remove(this);
    super.cancelWith(cancelled, rejectable: rejectable);
  }
```

Очередь сообщает каждой задаче, чья она:

```dart
  void add(MyJob<Object?> job) => _waiting.add(job.._queue = this);
```

```text
second: Cancelled(manual)
the queue is empty
```

Задачу, которая не стартовала, ядро заканчивает, что бы ни говорил
`cancellable`: задача, созданная с `cancellable: false`, отказывается от отмены
только тогда, когда уже работает. Если задача вашей очереди может отказаться
от отмены, пока ждёт, откажите в `cancelWith`, до вызова `super`, как это
делает `solo`.

## Своё правило

Задачам движка можно работать, только пока пользователь вошёл в аккаунт, и это
показывает `account.signedIn`. Задача, которая ещё работает, когда пользователь
выходит, останавливается так же, как отменённая: её колбэки `onCancel`
закрывают то, что она открыла, её дети останавливаются, а сама она кончается
`Cancelled`.

`check()` служит контрольной точкой контекста. Пока тело работает, `wait`,
`join` и `uncancellable` спрашивают её перед действием, `join` ещё раз после
него, `run` когда пришло значение ребёнка, а `runAll` перед тем, как отдать
значения. Правило движка ставится туда. Задача скачивает строки через
соединение и сохраняет их:

```dart
final job = MyJob<void>(observer: printer, (ctx) async {
  ctx.onCancel(() => print('close the connection'));
  final rows = await ctx.join(download);
  print('downloaded $rows rows');
  await ctx.join(() => save(rows));
  print('saved');
})
  .._launch();
```

### Первая попытка

`MyContext` переопределяет `check()` правилом:

```dart
  @override
  void check() {
    if (!account.signedIn) throw const SignedOut();
  }
```

Пользователь отменяет задачу, пока идёт скачивание:

```text
cancel
close the connection
downloaded 42 rows
saved
outcome: Cancelled(manual)
```

Пользователь выходит из аккаунта, пока идёт скачивание:

```text
sign out
onError: SignedOut
outcome: Failed(SignedOut)
```

Анализатор указывает на это переопределение, и оба запуска показывают почему.
Оно заменило контрольную точку ядра, а не дополнило её: после `cancel`
`check()` больше не спрашивает об отмене, поэтому `join` отдал строки
отменённой задаче, тело их сохранило, а `ctx.uncancellable` начал бы свой шаг
на отменённой задаче. `wait` и `run` отмену всё равно бросают: они читают её
сами. А правило, которое перестало выполняться, не провал. Задача кончается
`Failed` с ошибкой самого движка, соединение никто не закрывает, а ребёнок
задачи доработал бы до конца.

### Вторая попытка

Переопределение сперва спрашивает `super.check()`, а правило бросает
`Cancelled` с причиной самого движка:

```dart
final class SignedOutReason extends CancelReason {
  const SignedOutReason();

  @override
  String get name => 'signed out';
}
```

```dart
  @override
  void check() {
    super.check();
    if (!account.signedIn) {
      throw Cancelled.by(
        reason: const SignedOutReason(),
        started: true,
        stackTrace: StackTrace.current,
      );
    }
  }
```

```text
sign out
outcome: Cancelled(signed out)
```

Отмена снова останавливает задачу на `join`, а выход из аккаунта теперь кончает
задачу `Cancelled`. Соединение по-прежнему никто не закрывает. Задачу никто
не отменял: её тело сдалось само, бросив свой `Cancelled`. Такое тело передаёт
отмену детям, но его собственные колбэки `onCancel` не вызываются.

### Отменить задачу из правила

Правило отменяет задачу, а потом бросает отмену, которую задача приняла:

```dart
  @override
  void check() {
    super.check();
    if (!account.signedIn) {
      final cancelled = Cancelled.by(
        reason: const SignedOutReason(),
        started: true,
        stackTrace: StackTrace.current,
      );
      cancelOwnJob(cancelled);
      throw pendingCancel ?? cancelled;
    }
  }
```

```text
sign out
close the connection
outcome: Cancelled(signed out)
```

```text
cancel
close the connection
outcome: Cancelled(manual)
```

`cancelOwnJob` делает `cancelWith(cancelled, rejectable: false)`: это отмена,
от которой задача отказаться не может, и её не придерживают
ни `cancellable: false`, ни `ctx.uncancellable`. Отмена, которую такая секция
придерживала до этого, пропадает: она уже не сработает, и `heldCancel` её
больше не называет. Дальше задача отменена так же, как её отменяет `cancel()`:
её колбэки `onCancel` вызываются, дети останавливаются, а `pendingCancel`
хранит отмену, которую она приняла. `check()` могут спросить и после того, как
задача кончилась `Done` или `Failed`, из работы, которую бросило её тело. Там
`cancelOwnJob` ничего не меняет, `pendingCancel` равен `null`, и правило
бросает свою отмену. `super.check()` стоит первым: пока ядро убирает за телом,
он бросает `StateError`, а правило, спрошенное раньше него, превратило бы
задачу, вернувшую значение, в отменённую. Правило спрашивают там же, где
спрашивают `check()`, и больше нигде: выход из аккаунта во время скачивания
замечают, когда `join` возвращается.

Идущую задачу движок тоже заканчивает отменой. `finish` заканчивает задачу
поданным исходом, но не ждёт детей и не разматывает стек уборки: не выполняются
ни `onDispose`, ни `discard`, и открытое телом остаётся открытым. Сколько
уборок брошено, говорит только отладочный канал. Задача, которая приняла
отмену, кончается этой отменой, что бы ни подали в `finish`, и поданное
значение не достаётся никому. Движок, который всё же заканчивает идущую задачу
руками, сначала освобождает то, что она держит.

## Отложенный старт

Обычная `Job` планирует свой запуск на следующую микротаску. Если момент
запуска должен выбрать вызывающий код, используйте `Job.deferred(body)`. Он
возвращает `DeferredJob<T>` с публичным методом `start()`. Его можно вызвать
самостоятельно, поручить запуск очереди или передать задачу родителю через
`ctx.run(child)`, как в разделе [«Дети»](children.md#дети).

```dart
final job = Job.deferred<void>((ctx) => ctx.wait(work));
// ... позже, или из своей очереди
job.start();
```
