# Своё поверх ядра

Движком эта страница называет библиотеку со своим состоянием, очередью или
правилами планирования. Свой движок стройте поверх ядра: наследуйте
`JobBase<T>` для задачи и `JobContextBase` для контекста, который получает её
тело. Базовые классы держат жизненный цикл, описанный на других страницах:
старт, [детей](children.md), [отмену](cancellation.md), [уборку](cleanup.md)
и [исход](outcomes.md). Наследники добавляют поведение движка через свой
защищённый API. Третий тип, `JobStatus`, показывает, на каком этапе жизни
задача: `created`, `running` или `finished`.

Все три живут в `package:async_job/engine.dart`, а не в основном импорте:
приложению, которое только запускает задачи, они не нужны. Движок импортирует
этот файл вместо `async_job.dart`: `engine.dart` экспортирует всё, что
экспортирует `async_job.dart`.

Строки под кодом показывают, что он печатает при запуске. Наблюдатель задачи
печатает то, что до него дошло: `onError:` для ошибки. `cancel` и `sign out`
отмечают моменты, когда пользователь отменяет задачу или выходит из аккаунта,
а `outcome:` показывает, чем завершается `job.done`. Две части страницы ниже
открываются версией, которую пишут первой: очередью, которая запускает задачи
по порядку, и правилом, записанным в `check()`. Под ней показано, что этот код
делает, а рабочая версия идёт следом под своим заголовком.

## Своя задача

Своя задача создаёт контекст, который получает её тело, и запускает тело с ним.
Две приватные обёртки позволяют остальному движку запустить задачу и дождаться
её:

```dart
import 'package:async_job/engine.dart';

final class MyJob<T> extends JobBase<T> {
  final Future<T> Function(MyContext ctx) _body;

  MyJob(this._body, {super.key, super.observer, super.cancellable});

  @override
  JobContextBase createContext() => MyContext(this);

  @override
  Future<T> execute(covariant MyContext ctx) => _body(ctx);

  // `start` и `whenDone` защищены: остальной движок вызывает их
  // через эти обёртки, приватные для его библиотеки.
  void _launch() => start();

  Future<void> get _whenDone => whenDone;
}

final class MyContext extends JobContextBase {
  MyContext(super.owner);
}
```

Член с `@protected` доступен только наследнику, а движок обращается к задаче
со стороны, из своей очереди. Обёртки приватные, поэтому движок живёт
в Dart-библиотеке `MyJob`, и никто другой, у кого есть задача, не запустит её
в обход движка. `whenDone` ждёт задачу, не наблюдая её исход, поэтому провал,
на который никто не посмотрел, всё равно доходит до зоны. Ожидание `done`
считалось бы наблюдением.

Переопределите `started()` и `finished()`, чтобы следить за жизненным циклом.
`started()` вызывается перед стартом тела, когда задача уже работает.
`finished()` вызывается, когда у задачи появился исход, в том числе у задачи,
снятой до того, как её тело начало работу. Перед таким `finished()` вызова
`started()` не было. Ошибка, брошенная любым из них, уходит в `onError` и затем
к ответу наблюдателя, как всякая ошибка, которой не несёт ни один исход: о них
говорит раздел [«С наблюдателем»](observing.md#с-наблюдателем) страницы
о наблюдении. Задача при этом идёт дальше как шла. Недоделанным остаётся ваш
собственный учёт, поэтому держите оба короткими и безусловными.

Чтобы движок сам отвечал за такие ошибки, повесьте своего наблюдателя на каждую
задачу, подмешайте в него `JobAnswerer` и переопределите его `onUnanswered`,
как это делает `solo`. Ребёнок, принятый без наблюдателя, берёт наблюдателя
родителя, поэтому ответ доходит и до детей. Исключение составляет ребёнок,
который пришёл со своим наблюдателем: он отвечает через своего. Продолжение,
которое создаёт `then`, не задача вашего движка: оно принадлежит тому, кто
вызвал `then`, и у него только тот наблюдатель, которого передали в `then`.
Провал вашей задачи, который оно принимает, этот наблюдатель слышит как провал
самого продолжения. За ошибки в коде продолжения отвечает тот, кто вызвал
`then`, в своей зоне, поэтому своего наблюдателя продолжению не передавайте.

Когда этому `onUnanswered` некому передать ошибку,
`super.onUnanswered(job, error, stackTrace)` отправляет её в зону, где задача
создана, и не пускает туда отмену, от какой бы задачи ошибка ни пришла:
ребёнок, принятый без наблюдателя, может и не быть задачей вашего движка. То же
делает `reportToZone` для движка, чей ответ живёт вне наблюдателя. Этот метод
защищён, поэтому движок добирается до него через обёртку, как до `start`,
и только у своих задач. Метод контекста, который нельзя вызывать из работы,
переданной в `ctx.unattended`, сначала вызывает `throwIfUnattended`; об этой
работе говорит раздел
[«Работа, которую задача не ждёт»](observing.md#работа-которую-задача-не-ждёт)
страницы о наблюдении. Весь защищённый API описан в справке
[JobBase](https://pub.dev/documentation/async_job/latest/engine/JobBase-class.html)
и [JobContextBase](https://pub.dev/documentation/async_job/latest/engine/JobContextBase-class.html).

## Своя очередь

Движок выполняет свои задачи по одной, в том порядке, в каком они пришли.
Задачу могут отменить, пока она ждёт своей очереди, и те, что стоят за ней, всё
равно должны выполниться.

### Первая попытка

Очередь хранит задачи и запускает каждую через `_launch`:

```dart
final class MyQueue {
  final _waiting = <MyJob<Object?>>[];

  void add(MyJob<Object?> job) => _waiting.add(job);

  Future<void> run() async {
    while (_waiting.isNotEmpty) {
      final job = _waiting.removeAt(0).._launch();
      await job._whenDone;
    }
  }
}
```

Пользователь отменяет вторую задачу, пока работает первая:

```dart
final second = MyJob<void>(key: 'second', (ctx) => ctx.wait(upload));
final queue = MyQueue()
  ..add(MyJob<void>(key: 'first', (ctx) => ctx.wait(upload)))
  ..add(second)
  ..add(MyJob<void>(key: 'third', (ctx) async => print('third runs')));
final running = queue.run();
await second.cancel();
print('second: ${await second.done}');
try {
  await running;
  print('the queue is empty');
} on StateError catch (error) {
  print('the queue stopped: $error');
}
```

```text
second: Cancelled(manual)
the queue stopped: Bad state: Job(second) has already finished
```

Задачу, которая ещё не стартовала, отмена заканчивает сразу: останавливать
в ней нечего, тела нет. Очередь всё ещё хранила её, и когда до неё дошёл черёд,
`start` бросил ошибку. На этом очередь остановилась, и третья задача ждёт
вечно.

### Уйти из очереди при отмене

Любая отмена, о которой просят задачу, приходит в `cancelWith`, среди них
`cancel()`, каскад от родителя и отмена, о которой движок просит сам через
`cancelOwnJob` контекста. Переопределение дополняет этот метод, а не заменяет
его, и анализатор требует, чтобы оно вызывало `super`. `MyJob` помнит очередь,
в которой ждёт, и в `cancelWith` уходит из этой очереди:

```dart
  MyQueue? _queue;

  @override
  void cancelWith(Cancelled cancelled, {bool rejectable = true}) {
    _queue?._waiting.remove(this);
    super.cancelWith(cancelled, rejectable: rejectable);
  }
```

Очередь сообщает каждой задаче, чья она:

```dart
  void add(MyJob<Object?> job) => _waiting.add(job.._queue = this);
```

Тот же запуск теперь доходит до третьей задачи:

```text
second: Cancelled(manual)
third runs
the queue is empty
```

Очередь пошла бы дальше и в том случае, если бы задача уходила из неё
в `finished()`: `finished()` вызывается и у задачи, снятой до старта.
В `cancelWith` движок ещё и распоряжается самой отменой. Задачу, которая
не стартовала, ядро заканчивает, что бы ни говорил `cancellable`: задача,
созданная с `cancellable: false`, отклоняет отмену только тогда, когда уже
работает. Если задача вашей очереди может отклонить отмену, пока ждёт,
`cancelWith` первым делом возвращается, раньше, чем задача уйдёт из очереди,
как это делает `solo`:

```dart
    if (status == JobStatus.created && !cancellable && rejectable) return;
```

У отмены, которую не может отклонить ни одна задача, `rejectable` равен
`false`: о такой отмене просит, например, `cancelOwnJob`.

## Своё правило

Задачам движка можно работать, только пока пользователь вошёл в аккаунт,
и вошёл ли он, показывает `account.signedIn`. Задача, которая ещё работает,
когда пользователь выходит, останавливается так же, как отменённая: её колбэки
`onCancel` закрывают то, что она открыла, её дети останавливаются, а сама она
кончается `Cancelled`.

`check()` служит контрольной точкой контекста. Пока тело работает, `wait`,
`join` и `uncancellable` спрашивают её перед действием, `join` ещё раз после
него, `run` когда пришло значение ребёнка, а `runAll` перед тем, как отдать
значения. Правило движка ставится туда. Задача движка скачивает строки через
соединение и сохраняет их:

```dart
final job = MyJob<void>(observer: printer, (ctx) async {
  ctx.onCancel(() => print('close the connection'));
  final rows = await ctx.join(download);
  print('downloaded $rows rows');
  await ctx.join(() => save(rows));
  print('saved');
})
  .._launch();
```

### Первая попытка

`MyContext` переопределяет `check()` правилом:

```dart
  @override
  void check() {
    if (!account.signedIn) throw const SignedOut();
  }
```

Пользователь отменяет задачу, пока идёт скачивание:

```text
cancel
close the connection
downloaded 42 rows
saved
outcome: Cancelled(manual)
```

Пользователь выходит из аккаунта, пока идёт скачивание:

```text
sign out
onError: SignedOut
outcome: Failed(SignedOut)
```

Анализатор указывает на это переопределение, и оба запуска показывают почему.
Оно заменило контрольную точку ядра, а не дополнило её: после `cancel`
`check()` больше не спрашивает об отмене, поэтому `join` отдал строки
отменённой задаче, тело их сохранило, а `ctx.uncancellable` начал бы свой шаг
на отменённой задаче. `wait` и `run` отмену всё равно бросают: они читают её
сами. А правило, которое перестало выполняться, не провал. Задача кончается
`Failed` с ошибкой самого движка, соединение никто не закрывает, а ребёнок
задачи доработал бы до конца.

### Собственная отмена движка

Переопределение сперва спрашивает `super.check()`, а правило бросает
`Cancelled` с причиной самого движка:

```dart
final class SignedOutReason extends CancelReason {
  const SignedOutReason();

  @override
  String get name => 'signed out';
}
```

```dart
  @override
  void check() {
    super.check();
    if (!account.signedIn) {
      throw Cancelled.by(
        reason: const SignedOutReason(),
        started: true,
        stackTrace: StackTrace.current,
      );
    }
  }
```

Пользователь отменяет задачу, пока идёт скачивание:

```text
cancel
close the connection
outcome: Cancelled(manual)
```

Пользователь выходит из аккаунта, пока идёт скачивание:

```text
sign out
close the connection
outcome: Cancelled(signed out)
```

Отмена снова останавливает задачу на `join`, а после выхода из аккаунта задача
кончается `Cancelled`. Тело выпускает `Cancelled` правила наружу и сдаётся
с ним, а задача, тело которой сдалось само, останавливается так же, как
отменённая: её колбэки `onCancel` вызываются, а дети останавливаются. Задача
принимает отмену правила, когда тело выпускает её, не раньше: тело, которое
поймало её и пошло дальше, не отменено. Об этой отмене задачу никто не просил,
поэтому в `cancelWith` она не приходит. Правилу не мешают
ни `cancellable: false`, ни `ctx.uncancellable`: они отклоняют отмену,
о которой просят задачу, или придерживают её, а отмену правила бросает тот
самый шаг, который она останавливает. Правило спрашивают там же, где спрашивают
`check()`, и больше нигде: выход из аккаунта во время скачивания замечают,
когда `join` возвращается, а выход во время `wait` заметит только следующий
вызов, который спрашивает `check()`.

Движок, который не может ждать следующей контрольной точки или должен
остановить задачу, что бы ни поймало её тело, отменяет задачу сам, когда
пользователь выходит из аккаунта, тем же `Cancelled`, который бросает его
правило. Он делает это через свои обёртки, как со `start`: вокруг `cancelWith`
с `rejectable: false` или вокруг `cancelOwnJob` контекста, который передаёт
`false`. Такую отмену задача отклонить не может, и `ctx.uncancellable` её
не придерживает. `finish` заканчивает задачу переданным ему исходом, и для
остановки идущей задачи он не годится: он не ждёт детей и не останавливает их,
не вызывает колбэки `onCancel` и не разматывает стек уборки, поэтому
не выполняются ни `dispose`, ни `discard`, и открытое телом остаётся открытым.
Сколько уборок брошено, говорит только отладочный канал, который включается
строкой `Job.debug = print;`. Задача, которая приняла отмену, кончается
`Cancelled`, что бы ни передали в `finish`: `Done` и `Failed` уступают отмене,
которую задача приняла, переданное значение не достаётся никому, и остаётся
в силе только другой `Cancelled`, переданный в `finish`. Движок, который всё же
заканчивает идущую задачу руками, сначала освобождает то, что она держит.

## Отложенный старт

Обычная `Job` планирует свой запуск на следующую микротаску. Если момент
запуска должен выбрать вызывающий код, используйте `Job.deferred(body)`. Он
возвращает `DeferredJob<T>` с публичным методом `start()`. Его можно вызвать
самостоятельно, поручить запуск очереди или передать задачу родителю через
`ctx.run(child)`, как в разделе [«Дети»](children.md#дети) страницы о детях.

```dart
final job = Job.deferred<void>((ctx) => ctx.wait(work));
// ... позже, или из своей очереди
job.start();
```
