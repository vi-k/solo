# Уборка

`Job` может открыть блокировку, базу данных или временный файл, а её дети могут
пользоваться ими и после возврата из тела. Регистрируйте освобождение
в контексте, в месте получения ресурса, и `Job` выполнит его, когда завершится
целиком:

```dart
final lock = await ctx.join(Lock.acquire, dispose: (lock) => lock.release());
final database = await ctx.join(
  Database.open,
  discard: (database) => database.close(),
);

await ctx.join(() => database.migrate(stop));

return database;
```

| Колбэк | Когда выполняется |
| --- | --- |
| `dispose` | при любом исходе |
| `discard` | когда `Job` заканчивается, не передав своё значение |

`wait`, `join` и `run` принимают оба; `ctx.onDispose` и `ctx.onDiscard`
регистрируют колбэк там, где оборачивать нечего. Передать в один вызов
и `dispose`, и `discard` — это `ArgumentError`.

Три раздела ниже открываются версией, к которой ведёт этот словарь, — колбэк,
чьё имя совпадает с намерением, или регистрация, записанная на строке, где она
лучше читается, — и говорят, что эта версия делает вместо того, что от неё
ждали. Где следующая версия это чинит и приносит собственный изъян, она стоит
второй попыткой. Работающая версия идёт под своим заголовком.

## Выбор колбэка

`Job` берёт блокировку для своей работы и открывает базу, которую возвращает
тому, кто её попросил. Ни то, ни другое не должно пережить `Job`, которой оно
больше не нужно.

### Первая попытка

```dart
final lock = await ctx.join(Lock.acquire, discard: (lock) => lock.release());
final database = await ctx.join(
  Database.open,
  discard: (database) => database.close(),
);

return database;
```

Оба ресурса уходят вместе с одной `Job`, поэтому один и тот же колбэк выглядит
подходящим для обоих. `discard` выполняется, только когда `Job` заканчивается,
не передав своё значение, а `Job`, возвращающая базу, его передаёт. Блокировка
освобождается на всех путях, кроме того, ради которого `Job` и написана:
отменённая или упавшая — освободит, успешная — оставит захваченной на всё время
жизни процесса. Тест, который отменяет `Job`, ничего не заметит: на этом пути
колбэк как раз выполняется.

### `dispose` — для того, что остаётся

```dart
final lock = await ctx.join(Lock.acquire, dispose: (lock) => lock.release());
final database = await ctx.join(
  Database.open,
  discard: (database) => database.close(),
);

return database;
```

`dispose` — для того, что `Job` оставляет себе: блокировки, временного файла,
подписки. `discard` — для того, что тело возвращает или отдаёт наружу. Здесь
успешная `Job` оставляет базу открытой для вызывающего и всё равно освобождает
блокировку, а отменённая или упавшая освобождает и то, и другое.

## Ресурс, который передают дальше

Ресурс может открыть одна `Job`, а получить другая: `connect` открывает базу,
`ready` делает миграцию и передаёт её дальше. У того, кто держит её последним,
должна остаться возможность её закрыть.

### Первая попытка

```dart
final connect = Job.deferred<Database>(
  (ctx) => ctx.wait(Database.open, discard: (db) => db.close()),
);

final ready = Job.deferred<Database>((ctx) async {
  final database = await ctx.run(connect);
  await ctx.join(() => database.migrate());

  return database;
});
```

`connect` зарегистрировал освобождение, поэтому база выглядит прикрытой,
куда бы она ни попала. Условная регистрация зависит только от исхода той `Job`,
которая её сделала, и больше ни от чего. `connect` кончился `Done` — он передал
своё значение, — поэтому его `discard` отбрасывается вместе со значением,
и регистрацию получателю не несёт ничто. Когда миграция затем падает, у `ready`
есть база и нет собственной регистрации, и соединение остаётся открытым,
а закрыть его некому.

### Вторая попытка

```dart
final ready = Job.deferred<Database>((ctx) async {
  final database = await ctx.run(connect);
  ctx.onDiscard(database.close);
  await ctx.join(() => database.migrate());

  return database;
});
```

Получатель регистрирует полученное — на той строке, где он его получает.
Со значением ребёнка на руках `run` проверяет родителя: на его собственную
отмену и на правила его предметной области, — и контрольная точка, бросившая
там, уносит значение с собой. Ребёнок кончился `Done` и по дороге отбросил свою
регистрацию, до строки, которая сделала бы следующую, дело не доходит, и базу
не закрывает никто. Ребёнок, отказавшийся от каскада через
`cancellable: false`, попадает в это окно при любой отмене родителя.

### Регистрация по приходу

```dart
final ready = Job.deferred<Database>((ctx) async {
  final database = await ctx.run(connect, discard: (db) => db.close());
  await ctx.join(() => database.migrate());

  return database;
});
```

Переданная в `run`, регистрация делается в момент прихода значения, до этой
контрольной точки. Теперь `ready` закрывает базу, когда заканчивается чем
угодно, кроме значения, и передаёт её нетронутой, когда успевает, — получателю,
который регистрирует её так же. Это верно для любой передачи, включая группу:
ветвь `ctx.runAll` регистрирует по приходу каждое значение, полученное от своих
детей, как и все.

Закрывает базу получатель — тот, кто зарегистрировал её по приходу. То же
значение остаётся доступным через `Job.value` ребёнка, пока кто-нибудь держит
хэндл, но закрывать его оттуда — значит закрыть дважды;
[Дети, стримы и цепочки](children.md#что-группа-отдаёт-обратно) называет хэндл
для случая, когда значение не доходит ни до какого получателя.

Отладочный канал называет каждую передачу, которая отбросила регистрацию, —
независимо от того, зарегистрировал ли получатель хоть что-то, — так что места,
где действует это правило, читаются прямо из прогона:

```text
Job(opener) handed its value over: 1 conditional cleanup dropped
```

## Регистрация без вызова

Там, где оборачивать нечего, колбэк регистрируют напрямую — `ctx.onDispose`
и `ctx.onDiscard`. Правила исхода у них те же, а колбэк может делать
и остальную завершающую работу, например сбрасывать буфер на завершении `Job`:

```dart
final buffer = StringBuffer();
ctx.onDispose(() => sink.add(buffer.toString()));
```

Оба метода возвращают функцию, снимающую регистрацию. Пользуйтесь ей, когда
ресурс уже освобождён или передан; вызвать её повторно или после выполнения
уборки безопасно. `wait`, `join` и `run` возвращают сам ресурс, а не функцию
снятия, и сделанную ими регистрацию снимает `ctx.disown(value)`. Он ищет
значение по идентичности и возвращает, нашёл ли, — поэтому передавайте ровно
тот объект, который вернул вызов.

### Первая попытка

```dart
final removeDisposer = ctx.onDispose(cursor.close);
await ctx.join(() => cursor.readAll()); // в конце закрывает его
removeDisposer();
```

Регистрация прикрывает курсор до тех пор, пока действие его не закроет,
а строка после действия эту регистрацию убирает. До этой строки тело доходит,
только если вызов его пустит: при отмене во время `readAll` `join` бросает
вместо значения, и регистрация остаётся стоять. Курсор закрыт действием,
и уборка закрывает его во второй раз.

### Снятие внутри действия

```dart
final removeDisposer = ctx.onDispose(cursor.close);
await ctx.join(() async {
  await cursor.readAll(); // в конце закрывает его
  removeDisposer();
});
```

Внутри действия эти два шага не разнести: что бы вызов ни бросил после,
освобождение и снятие регистрации уже случились вместе. То же верно для
значения, зарегистрированного самим вызовом: `ctx.disown(value)` стоит там, где
меняется владение, а не строкой ниже.

## Порядок уборки и поздние результаты

| Шаг | Что делает `Job` |
| --- | --- |
| Дети | ждёт их всех: они могут пользоваться её ресурсами |
| Стек уборки | разматывает его с последней регистрации, ожидая каждый колбэк |
| Вторая волна | выполняет `discard`, который отмена сделала нужным задним числом |
| Конец | исход и освобождение того, что держит движок |

Ожидание каждого колбэка и даёт библиотеке поверх ядра возможность дождаться
освобождения ресурсов при закрытии.

Колбэки уборки выполняются после конца тела, и их не отменяют. `ctx.wait`
и `ctx.join` принадлежат телу и здесь бросают `StateError`, поэтому колбэк ждёт
свой ресурс напрямую. Ждать свою же `Job` он не должен: `done`, `value`
и `cancel()` завершаются после той уборки, которая их и ждала бы. Держите
колбэки короткими и безусловными. Ошибка одного из них уходит в `onError`,
а остальные колбэки всё равно выполняются.

**Отмена после возврата из тела.** `Job` может ещё ждать детей или выполнять
уборку после `return`. Отмена, пришедшая в это время, может сменить её исход
на `Cancelled`, и база, зарегистрированная через `discard`, будет тогда закрыта
вместо того, чтобы вернуться вызывающему. `discard`, уже пропущенный
на успешном пути, выполняется второй волной, и она ставит его после колбэков,
зарегистрированных позже него, а не в строгом обратном порядке регистрации.

Ветвь `ctx.runAll` — единственное исключение, и ради него держится пауза. Ветвь
не выпускают к исходу, пока не решила её группа, и после того, как группа
отдала значения вызывающему, `discard` этой ветви больше не выполняется —
ни второй волной, ни на отмене, пришедшей в саму размотку, ни как-либо ещё.
Значение в руках вызывающего, а `discard` означает, что значение не досталось
никому. Пока группа не решила, всё сказанное выше верно как написано: отмена,
дошедшая до ветви, закрывает то, что ветвь взяла.

Значение, которое вернуло действие, брошенное `wait`, нуждается в уборке при
любом исходе: до тела оно не дошло. Зарегистрированный для него колбэк
выполняется и после конца `Job` — поздно и в одиночку, и этого никто не ждёт.

Регистрация работает и после обычного `await`, и правило выше объясняет, почему
это стоит назвать: обычный `await` не контрольная точка, поэтому между вызовом
и строкой под ним бросить нечему.

```dart
final job = Job<Database>((ctx) async {
  final database = await Database.open();
  ctx.onDiscard(database.close);

  return database;
});
```

Отмена, пришедшая во время `Database.open()`, прервать его не может. Тело
дожидается вызова, регистрирует открытое, и `Job` заканчивается `Cancelled`,
а `onDiscard` закрывает базу, потому что значение не дошло ни до какого
вызывающего. Для получения, которое отмена может оборвать, берите `ctx.join`
с `dispose` или `discard`, как выше.
