# Время

Пауза и срок — два места, где отмена встречается со временем: `ctx.pause` ждёт
и кончается в момент отмены задачи, а `timeout` отменяет задачу, когда выходит
её предел. Ожидание, которое отмена не должна обрывать, берёт предел
у `Future.timeout`, как показывает раздел
[«Вызов, который может не вернуться»](#вызов-который-может-не-вернуться).
Остальное об отмене — на странице [«Отмена»](cancellation.md).

Код работает с базой страницы об отмене: `database.readAll` читает строки за 10
мс, а миграция идёт в три шага по 10 мс. Перед каждым шагом миграция читает
`CancelToken`, сигнал остановки клиента базы, а не тип этого пакета; найдя его
отменённым, она останавливается, бросая `DatabaseStopped`. Приложение один раз,
в `main`, называет эту остановку, как показывает раздел
[«Токен через `onCancel`»](cancellation.md#токен-через-oncancel), и каждая
задача на этой странице идёт с этой строкой. Последний раздел останавливает
устройство той же страницы, остановка которого занимает 10 мс.

Строки под кодом показывают, что он печатает при запуске. База и устройство
говорят, что делают, `cancel` отмечает момент, когда пользователь отменяет,
а `printing`, наблюдатель каждой задачи со строками под кодом, печатает то, что
до него дошло: `log:` для `ctx.log`, `onError:` для ошибки. `outcome:`
показывает, чем завершается `job.done`. Провал, исход которого никто
не наблюдает, уходит дальше к ответу, а у `printing` ответ — это зона, как
показывает раздел
[«Ошибка, которую никто не ждёт»](outcomes.md#ошибка-которую-никто-не-ждёт)
страницы об исходах.

## Дать времени пройти

Задача читает строки раз в секунду.

### Первая попытка

```dart
// Первая попытка: обычный await досиживает задержку.
final job = Job<void>((ctx) async {
  while (true) {
    use(await ctx.abandonable(database.readAll));
    await Future<void>.delayed(const Duration(seconds: 1));
  }
});
```

Пользователь отменяет через 500 мс после старта, на середине задержки, и задача
кончается на 510 мс позже. Обычный `await` контрольной точкой не служит: тело
досиживает задержку и узнаёт об отмене на `ctx.abandonable` следующего оборота.
До тех пор `cancel()` не возвращается, и всё, что ждёт задачу, ждёт вместе
с ней.

### Вторая попытка

```dart
// Вторая попытка: таймер задержки переживает задачу.
await ctx.abandonable(
  () => Future<void>.delayed(const Duration(seconds: 1)),
);
```

Теперь задержка стоит за контрольной точкой, и задача кончается в момент
отмены. Но `abandonable` прекращает ожидание, а не работу, а работой здесь
служит таймер. `Future.delayed` отменить нельзя, и его таймер идёт оставшиеся
510 мс, хотя его никто не ждёт. Программа, которой больше нечего делать,
не выйдет, пока он не сработает, а тест, который ищет незавершённые таймеры,
найдёт один.

### Пауза самой задачи

```dart
await ctx.pause(const Duration(seconds: 1));
```

`ctx.pause` служит контрольной точкой, которая занимает время. Она сразу
бросает `Cancelled`, когда приходит отмена, как `ctx.abandonable`, и её таймер
снимается вместе с ней:

| Как тело ждёт | Задача кончается | Оставшийся таймер |
| --- | --- | --- |
| `await Future.delayed(...)` | через 510 мс после отмены | нет |
| `ctx.abandonable(() => Future.delayed(...))` | сразу | ещё 510 мс |
| `ctx.pause(...)` | сразу | нет |

Без длительности `ctx.pause()` возвращается на следующем обороте цикла событий:
в этом месте долгое вычисление пропускает другую работу и может услышать
отмену. Внутри `ctx.uncancellable` отмена придержана, как любая другая, и пауза
идёт целиком. Отрицательная длительность считается нулевой, как
у `Future.delayed`: в отличие от `timeout`, `ctx.pause` из-за неё не бросает.

## Срок

Миграции дано 15 мс. Когда они вышли, задача должна остановиться так же, как
при отмене пользователем: токен останавливает миграцию, а `discard` закрывает
базу. Вручную здесь никто не отменяет.

### Первая попытка

Задачу останавливает `cancel`, поэтому таймер вызывает его, когда предел вышел:

```dart
// Первая попытка: таймер лимита переживает задачу.
const limit = Duration(milliseconds: 15);

final job = Job<Database>(observer: printing, (ctx) async {
  final database = await ctx.join(
    Database.open,
    discard: (database) => database.close(),
  );
  final stop = CancelToken();
  ctx.onCancel(stop.cancel);

  await ctx.join(() => database.migrate(stop));

  return database;
});
Timer(limit, job.cancel);
```

```text
step 1
step 2
migration stopped
onError: DatabaseStopped
database closed
outcome: Cancelled(manual)
```

Задача останавливается так же, как у пользователя в разделе
[«Токен через `onCancel`»](cancellation.md#токен-через-oncancel) страницы
об отмене, а задачу, которая уже кончилась, вызов не трогает: `cancel()` с ней
ничего не делает. Но сам таймер живёт до предела, кончилась задача или нет.
Миграция, которая падает на плохой схеме, сразу кончает задачу `Failed`,
а таймер идёт оставшиеся 15 мс, хотя отменять ему нечего. Программа, которой
больше нечего делать, не выйдет, пока он не сработает, а тест, который ищет
незавершённые таймеры, найдёт один.

### Вторая попытка

Таймер снимается, когда задача кончается:

```dart
// Вторая попытка: чтение done не пускает сбой в зону.
final timer = Timer(limit, job.cancel);
job.done.whenComplete(timer.cancel);
```

Оставшегося таймера больше нет, но чтение `job.done` наблюдает исход. Провал
на плохой схеме по-прежнему доходит до наблюдателя как `onError`, а до зоны
больше не доходит. Без наблюдателя его никто не слышит, и сообщать о нём
приходится коду, который снимает таймер.

### Срок самой задачи

```dart
final job = Job<Database>(observer: printing, timeout: limit, (ctx) async {
  final database = await ctx.join(
    Database.open,
    discard: (database) => database.close(),
  );
  final stop = CancelToken();
  ctx.onCancel(stop.cancel);

  await ctx.join(() => database.migrate(stop));

  return database;
});
```

```text
step 1
step 2
migration stopped
onError: DatabaseStopped
database closed
outcome: Cancelled(timeout)
```

`timeout` даёт задаче собственный срок. Когда срок выходит, задача отменяется
с причиной `TimeoutCancelReason`, у которой `timeout` равен пределу. Исход
говорит об этом: `Cancelled(timeout)`, тогда как таймер первой попытки оставлял
`Cancelled(manual)`, как у пользователя.

Срок действует как отмена через `cancel()`, а не как `TimeoutException`
из `Future.timeout`:

- Тело останавливается на следующей контрольной точке.
- Секция `uncancellable` придерживает запрос, пока не закроется, и тогда задача
  его принимает, раньше чем тело вернёт значение: тело, которое кончается
  `return ctx.uncancellable(...)`, кончается `Cancelled(timeout)`, значение
  секции не доходит ни до исхода, ни до `value`, и регистрации `onDiscard`
  срабатывают. Кончиться, пока секция ещё придерживает запрос, может только
  тело, которое пошло дальше, не дождавшись секции: тогда запрос уходит вместе
  с таймером, и задача кончается тем, что вернуло тело. См.
  [«Придержать отмену»](cancellation.md#придержать-отмену).
- Уже отменённая задача сохраняет свою причину.
- Дети получают срок в `cause` своей `ParentCancelReason`.

Срок ограничивает тело и детей, которых задача ждёт после него, но не стек
уборки. Как ядро обращается с таймером:

- Ядро ставит таймер, когда стартует тело, поэтому время до старта
  не считается: например, ожидание `start()` у `Job.deferred` или `ctx.run`
  у родителя.
- Ядро снимает таймер до того, как стек уборки начнёт разматываться: отмена,
  пришедшая туда, превратила бы задачу, которая сделала свою работу,
  в отменённую и закрыла бы её значение через `discard`.
- Ядро снимает таймер и при любом другом конце задачи.

Снимая таймер, ядро ничего не наблюдает, поэтому с `timeout` провал задачи
по-прежнему доходит до зоны:

| Как задача получает предел | Оставшийся таймер | Провал задачи |
| --- | --- | --- |
| `Timer(limit, job.cancel)` | ещё 15 мс | доходит до зоны |
| `job.done.whenComplete(timer.cancel)` | нет | до зоны не доходит |
| `timeout: limit` | нет | доходит до зоны |

Задача, которая ещё идёт, когда кончается тест, держит свой таймер, как любой
другой. Тест под `fakeAsync` или `testWidgets` кончает такую задачу, отменив её
или дождавшись, раньше, чем кончится сам.

Нулевой или отрицательный срок бросает `ArgumentError`, и так же бросает срок
вместе с `cancellable: false`: отмену по сроку задача вправе отклонить,
а задача с `cancellable: false` отклоняла бы её всегда.

### Срок для одного шага

Страница уходит без миниатюры, если миниатюра рисуется дольше 15 мс,
а `renderThumbnail` рисует её 20. Отдельный шаг получает срок как собственный
ребёнок, сделанный через `ctx.child`, которого примет движок задачи:

```dart
final thumbnail = ctx.child<String>(
  renderThumbnail,
  key: 'thumbnail',
  timeout: const Duration(milliseconds: 15),
);
try {
  return 'page with ${await ctx.run(thumbnail)}';
} on Cancelled catch (cancelled) {
  ctx.check();
  if (cancelled.reason case TimeoutCancelReason(:final timeout)) {
    return 'page without a thumbnail after ${timeout.inMilliseconds} ms';
  } else {
    rethrow;
  }
}
```

```text
outcome: Done(page without a thumbnail after 15 ms)
```

Ребёнок кончается `Cancelled(timeout)`, и `ctx.run` бросает эту отмену в тело
родителя. Сам родитель не отменён: срок вышел у ребёнка. Ветка `catch` в Dart
отбирает только по типу, без шаблона и без `when`, поэтому она ловит любой
`Cancelled`. Первым в ней стоит `ctx.check()` и бросает отмену самой задачи,
потому что причина срока не говорит, чей это срок: задача, у которой
собственный `timeout` вышел до `ctx.run`, сразу получает от него свой
`Cancelled(timeout)` и без проверки приняла бы его за срок миниатюры и пошла бы
дальше. Шаблон стоит в `if` после неё: он узнаёт причину срока и достаёт его
длительность. `else` бросает дальше миниатюру, которую отменил кто-то другой.
Если ветки нет, срок ребёнка кончает родителя
`Cancelled(body: Job(thumbnail): Cancelled(timeout))`. Ключ нужен ради этой
строки: ребёнок без ключа печатается как `Job()`.

## Вызов, который может не вернуться

Задача останавливает устройство и потом освобождает его, и остановку она ждёт
целиком: устройство, освобождённое посреди остановки, — как раз то, чего
избегает раздел
[«Остановка, которая занимает время»](cancellation.md#остановка-которая-занимает-время)
страницы об отмене. Остановка занимает 10 мс, но время от времени устройство
на неё вовсе не отвечает. Через 15 мс задача должна бросить такую остановку
и всё равно освободить устройство.

### Первая попытка

```dart
// Первая попытка: остановка без ответа устройства держит задачу навсегда.
ctx.onDispose(device.release);
await ctx.join(device.stop);
```

Устройство не отвечает на остановку, а пользователь отменяет через 5 мс:

```text
cancel
```

После этой строки ничего не идёт: задача не кончается никогда, и устройство так
и не освобождается. `join` ждёт своё действие целиком, сквозь отмену тоже,
а это действие не возвращается. `cancel()` возвращается, когда задача
кончилась, поэтому и его future не завершается.

### Вторая попытка

Срок ограничивает ожидание, и раздел
[«Срок для одного шага»](#срок-для-одного-шага) даёт его отдельному шагу в виде
ребёнка:

```dart
// Вторая попытка: отмена задачи бросает остановку.
ctx.onDispose(device.release);
await ctx.run(
  ctx.child(
    (ctx) => ctx.abandonable(device.stop),
    key: 'stop',
    timeout: const Duration(milliseconds: 15),
  ),
);
```

Устройство не отвечает на остановку:

```text
device released
outcome: Cancelled(body: Job(stop): Cancelled(timeout))
```

Граница держится. Ребёнок кончается `Cancelled(timeout)` через 15 мс,
устройство освобождается, а срок ребёнка, выпущенный из тела, кончает задачу.
Ребёнок ждёт остановку через `abandonable`: с `join` внутри срок тоже ждал бы
остановку, и остановка, которая не возвращается, держала бы ребёнка так же, как
первая попытка держит задачу.

Устройство отвечает через 10 мс, а пользователь отменяет через 5 мс:

```text
cancel
device released
outcome: Cancelled(manual)
device stopped
```

Отмена задачи переходит к её детям, и `abandonable` в ребёнке бросает остановку
за 5 мс до её конца: устройство освобождается посреди остановки. Это трасса
первой попытки раздела
[«Остановка, которая занимает время»](cancellation.md#остановка-которая-занимает-время),
а остановка — тот самый вызов, который задача хотела дождаться целиком.

### Таймаут внутри `join`

```dart
ctx.onDispose(device.release);
try {
  await ctx.join(
    () => device.stop().timeout(const Duration(milliseconds: 15)),
  );
} on TimeoutException {
  ctx.log('the device did not answer');
}
```

Устройство не отвечает на остановку:

```text
log: the device did not answer
device released
outcome: Done(null)
```

Устройство отвечает через 10 мс, а пользователь отменяет через 5 мс:

```text
cancel
device stopped
device released
outcome: Cancelled(manual)
```

`join` ждёт остановку целиком, сквозь отмену задачи, а `Future.timeout`
ограничивает это ожидание: через 15 мс future, который ждёт `join`, падает
с `TimeoutException`. Это `TimeoutException` из Dart, ошибка вызова, а не срок
ядра: никакая задача не отменяется, и `TimeoutCancelReason` не создаётся.
Ошибку своего действия `join` бросает как есть, с отменой или без, поэтому тело
само говорит, что значит остановка без ответа: здесь это строка в журнале,
и задача кончается `Done` или `Cancelled`, если пользователь тем временем
отменил. Без `try` задача кончается `Failed` с `TimeoutException`; задача,
которую тем временем отменили, кончается `Cancelled`, а ошибка идёт туда же,
куда любой провал тела отменённой задачи: к наблюдателю, а затем в зону.
Остановка, которая кончилась или упала после границы, не доходит ни до кого:
то, что пришло слишком поздно, отбрасывает сам `Future.timeout`.

`ctx.uncancellable` вокруг ребёнка второй попытки тоже дожидается остановки:
секция придерживает отмену задачи, и ребёнок её не слышит, как показывает
раздел [«Придержать отмену»](cancellation.md#придержать-отмену) страницы
об отмене. От таймаута внутри `join` его отличают две вещи. Отмена, которую
задача не может отклонить, например правило, которое добавляет движок,
не придерживается, и ребёнок бросает остановку, как во второй попытке, тогда
как `join` ждёт сквозь неё. А остановка, которая падает после границы, падает
в вызове, который ребёнок бросил, поэтому её ошибка доходит до наблюдателя
и до зоны, тогда как `Future.timeout` её отбрасывает.
