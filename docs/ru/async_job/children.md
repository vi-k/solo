# Дети, стримы и цепочки

Тело может отдать работу другой задаче тремя способами:

1. Ребёнка тело запускает само и само его дожидается.
2. Стрим обрабатывается по одному событию в ребёнке, которому принадлежит
   подписка.
3. Продолжение, созданное через `then`, стартует, когда задача, за которой оно
   стоит, завершится успешно, и живёт дольше неё.

Слова для этих трёх похожи, и неверное из них компилируется тоже:

```dart
final job = Job<void>((ctx) async {
  // Ребёнок: тело его запускает, дожидается и отменяет вместе с собой.
  final rows = await ctx.run(Job.deferred<int>((c) => c.wait(loadRows)));

  // Стрим: по одному событию, в собственном ребёнке.
  final saving = ctx.each(events, (c, e) => c.join(() => save(e)));

  // Цепочка: стартует сама, когда источник завершится успешно,
  // и усыновить её не может никакой родитель.
  final tail = saving.then<void>((c, _) => report(rows));
});
```

Четыре раздела ниже начинаются с той версии, к которой ведут привычка или имена
API: с обычного `Future.wait`, который и так есть в любой программе на Dart,
с голого `await` или с метода, чьё имя совпадает с требованием. Каждый из них
говорит, что эта версия делает вместо того, что от неё хотели. Работающая
версия идёт следом под своим заголовком.

## Дети

Тело поручает работу другой `Job`, зарегистрировав её как дочернюю:

```dart
final parent = Job<void>((ctx) async {
  final child = Job.deferred<int>((ctx) => ctx.wait(load));
  final rows = await ctx.run(child);
  ctx.log('$rows rows');
});
```

`ctx.run(child)` сразу запускает дочернюю задачу и возвращает future её
результата. Родитель ждёт всех дочерних задач перед завершением. Когда родителя
отменяют, он передаёт отмену дочерним задачам, и так же он поступает, когда его
тело бросает `Cancelled`. Дочерняя задача с `cancellable: false` отклоняет
отмену в обоих случаях: она работает до конца, а родитель дожидается её
и только потом кончается `Cancelled`. При другой ошибке тела родитель позволяет
дочерним задачам доработать и ждёт их завершения.

Создавайте дочерние задачи через `Job.deferred`, чтобы родитель управлял их
запуском. `ctx.run` отклоняет обычную `Job`, потому что такая задача
запускается автоматически: она может стартовать раньше, чем родитель её
зарегистрирует, и тогда будет работать вне отмены и ожидания родителя.

`run` ждёт завершения дочерней задачи, включая её детей и уборку, и проверяет
отмену родителя перед возвратом значения в тело. Если дочерняя задача отклонит
отмену, `run` продолжит ждать её; после её успешного завершения он бросит
отмену родителя, и тело не перейдёт к вызову `log`. Ошибка или отмена дочерней
задачи передаётся через возвращённую future со своим стеком. Для запроса отмены
вызовите `child.cancel()`, для просмотра исхода используйте `child.done`.

Дочерняя задача наследует наблюдателя родителя, если у неё нет своего. Если её
отмена выходит через `await ctx.run(child)` или `child.value`, родитель
завершается с `HandlerCancelReason` и описанием, указывающим на дочернюю
задачу.

### Ребёнок без `await`

```dart
final parent = Job<void>((ctx) async {
  final rows = ctx.run(Job.deferred<int>((c) => c.wait(loadRows)));
  final child = Job.deferred<void>((c) => c.wait(warmCache));
  ctx.run(child).ignore();
  ctx.log('${await rows} rows');
});
```

Оба ребёнка запускаются сразу. В `rows` лежит future, которую вернул `ctx.run`:
её сохранили и дожидаются позже, а такую future нужно дождаться или обработать
её ошибки. `child` прогревает кэш, который здесь никто не читает,
и `ctx.run(child).ignore()` говорит, что результат не нужен. Родитель всё равно
дождётся обоих перед завершением. `child.ignore()` не заменяет
`ctx.run(child).ignore()`. `child.ignore()` гасит отчёт ядра о провале,
на который никто не посмотрел, а здесь на провал смотрит `run`: он ждёт
значения ребёнка. Если `child` упадёт, его ошибка придёт через future, которую
вернул `run`, а это обычная future Dart: необработанной она уходит в зону,
и `Cancelled` ребёнка тоже. `ctx.run(child).ignore()` гасит ошибку этой future,
и больше ничего: наблюдатель ребёнка всё равно слышит эту ошибку через
`onError`.

Если тело ребёнка упало, а после этого до ребёнка дошла отмена, например пока
он ещё ждал своих дочерних задач или шла его уборка, эта ошибка через future
от `run` не приходит. Ребёнок кончается `Cancelled`, `await ctx.run(child)`
бросает `Cancelled`, а ошибка уходит туда, куда уходит ошибка, которую никто
не обработал: к наблюдателю ребёнка и, если он за неё не отвечает, в зону, как
в разделе [«Куда уходят ошибки»](observing.md#куда-уходят-ошибки) страницы
о наблюдении. `child.ignore()` её гасит. `ctx.run(child).ignore()` её не гасит:
он гасит то, что бросает future, а она бросает отмену. Чтобы отвечать за ошибку
иначе, дайте ребёнку наблюдателя, который отвечает: `JobAnswerer`
с переопределённым `onUnanswered`.

### Когда `ctx.run` отклоняет ребёнка

`ctx.run` отклоняет недопустимый запуск синхронно, до того как ребёнок начнёт
работать:

| Ребёнок | Что делает `ctx.run` |
| --- | --- |
| Задача с автоматическим запуском или задача другой реализации | Бросает `ArgumentError` |
| Задача, которая уже запущена или уже закончилась | Бросает `StateError` |
| Любая задача после того, как тело родителя завершилось | Бросает `StateError` |
| Любая задача, когда родитель уже отменён | Отменяет ребёнка до старта и бросает `Cancelled` родителя |

### Глубина дерева

```dart
Job<void> level(int depth) {
  return Job.deferred<void>((ctx) async {
    // Без этого await вся цепочка строится на одном стеке.
    await null;
    if (depth > 0) await ctx.run(level(depth - 1));
  });
}
```

Глубина дерева ограничена стеком, и упирается она в два разных обхода. Запуск
ребёнка выполняет его тело до первого `await`. Без `await null` выше каждый
уровень создаёт своего ребёнка раньше, чем приостанавливается, и вся цепочка
строится на одном стеке: около тысячи уровней в Dart VM на десктопе, и обвал
приходит ещё на постройке дерева. С `await null` постройка идёт по микротаскам,
и предел переходит ко второму обходу, то есть к отмене, которая спускается
по дереву рекурсией и доходит примерно до трёх тысяч. Ни то ни другое число
не обещание: оба следуют из размера кадра тела.

Каскад, у которого кончился стек, останавливается там, где стек кончился,
а задачи ниже этой глубины продолжают работать. Переполнение выходит из самого
`cancel()`, раньше, чем тот вернёт future, поэтому `cancel().ignore()` его
не ловит. Рекурсии, измеряемой тысячами вложенных задач, нужен не стек
поглубже, а плоская структура.

## Ожидание нескольких детей

Экспорту нужны два источника: строки и картинки. Друг друга они не ждут,
поэтому открываться должны сразу оба, и каждая ветка закрывает открытое сама,
если не отдала его наружу. Что бы ни случилось, родитель обязан кончиться
правдой об этом, и ничего не должно остаться открытым.

### Первая попытка

```dart
final parent = Job<void>((ctx) async {
  final rows = Job.deferred<Source>(
    (ctx) => ctx.wait(openRows, discard: (source) => source.close()),
  );
  final images = Job.deferred<Source>(
    (ctx) => ctx.wait(openImages, discard: (source) => source.close()),
  );

  final sources = await Future.wait([ctx.run(rows), ctx.run(images)]);
  await ctx.join(() => writeArchive(sources));
});
```

`Future.wait` оставляет себе первую дошедшую до него ошибку, а остальные
отпускает, и тем самым исход родителя решает гонка. Допустим, `rows` падает,
а `images` кончается `Cancelled`: если до `Future.wait` первым дойдёт провал,
родитель кончится `Failed`; если отмена, он кончится
`Cancelled(HandlerCancelReason)`, и провала `rows` в исходе нет вовсе. Упавший
ребёнок при этом объявляет свой провал наблюдателю сам, и только туда, так что,
если наблюдателя нет ни у родителя, ни у детей, эта ошибка теряется целиком.
В зону её не отдаёт ни ядро, ни Dart: для ядра на исход ребёнка смотрит `run`,
ведь тело ждёт его future, а `Future.wait` молча отпускает все ошибки, кроме
первой.

Если `rows` падает, а `images` удаётся, источник, открытый `images`, пропадает
вместе со значениями. `discard` закрывает значение, только если оно никуда
не дошло, а здесь оно доходит до тела: ветка возвращает открытое и кончается
`Done`, поэтому её собственная уборка его не закрывает. Тело, когда значение
пришло, ничего не зарегистрировало; потом `Future.wait` завершается ошибкой
и выбрасывает значения тех веток, которые удались, так что тело его даже
не держит. Этот источник не закрывает никто.

`eagerError: true` не чинит ни того ни другого:

```dart
final sources = await Future.wait(
  [ctx.run(rows), ctx.run(images)],
  eagerError: true,
);
```

Он меняет ровно одно: когда просыпается тело. Раннего конца он не даёт:
остановиться остальным веткам никто не предлагает, а детей ядро дожидается
в любом случае, поэтому задача по-прежнему кончается вместе с последней из них.
Вся разница в том, что тело успевает сделать в этом промежутке. Исход
по-прежнему решает то, чья беда пришла первой, а источник удавшейся ветки
по-прежнему пропадает вместе со значениями.

### Регистрация по приходу и ожидание в одном конверте

```dart
final parent = Job<void>((ctx) async {
  final rows = Job.deferred<Source>(
    (ctx) => ctx.wait(openRows, discard: (source) => source.close()),
  );
  final images = Job.deferred<Source>(
    (ctx) => ctx.wait(openImages, discard: (source) => source.close()),
  );

  final sources = await [
    ctx.run(rows, dispose: (source) => source.close()),
    ctx.run(images, dispose: (source) => source.close()),
  ].wait;
  await ctx.join(() => writeArchive(sources));
});
```

Изменились две вещи, и каждая чинит одну из двух бед.

`ctx.run(child, dispose: ...)` регистрирует значение на родителе в тот момент,
когда ветка его отдаёт, и с этого момента его закрывает родитель, когда
кончается, чем бы он ни кончился. Если `rows` удалась, а `images` упала или
отменилась, источник `rows` закрывает родитель: `dispose`, переданный вместе
с `ctx.run(rows)`, срабатывает, когда родитель завершается. Так же и после
записи архива, и при отмене, дошедшей до родителя в промежутке. Ветка,
не дошедшая до возврата, закрывает своё через `discard`, с которым открывала
источник. Одно это закрывает то, что первая попытка оставила открытым,
и закрыло бы и под `Future.wait`. Правило то же, что в разделе
[«Регистрация по приходу»](cleanup.md#регистрация-по-приходу) страницы
об уборке; `dispose`, а не `discard`, потому что источники родитель держит для
себя.

`.wait` чинит исход. Он собирает все ошибки в один `ParallelWaitError`,
и значения тех веток, которые удались, ложатся в тот же конверт. Ядро его
читает: конверт с настоящим провалом остаётся провалом, со своими ошибками
и значениями нетронутыми, а конверт из одних отмен и успехов заканчивает
родителя первой по списку отменой, ровно так же, как ожидание одной дочерней
задачи. Порядок, в котором пришла беда, больше ничего не решает. Значения
в конверте уже зарегистрированы, и если закрыть их ещё и там, они закроются
дважды.

`.wait` не останавливает ни одну ветку раньше срока: он возвращает управление,
когда закончены все ветки, поэтому, если одна ветка упала или была отменена
сама по себе, её сосед доигрывает до конца. С отменой родителя иначе: она
каскадом доходит до каждого ребёнка, в том числе до веток `.wait`. Ресурс,
открытый веткой для себя, всё равно освобождается вовремя, если ветка взяла его
через `ctx.wait(() => open(), dispose: (value) => value.close())`: уборка
принадлежит задаче, а не ожиданию.

### Когда один провал делает остальное бессмысленным

```dart
final values = await ctx.runAll([
  Job.deferred<int>((ctx) => ctx.wait(loadRows)),
  Job.deferred<int>((ctx) => ctx.wait(loadExtra)),
]);
```

`ctx.runAll` запускает каждого ребёнка синхронно, по порядку списка,
и возвращает их значения в том же порядке. Как только тело любой ветки
кончается не значением, остальных просят остановиться причиной
`SiblingCancelReason`. Ветку, из которой пришла беда, не просят: иначе её
ошибка превратилась бы в отмену и пропала. Что выйдет наружу, решают итоговые
исходы: настоящий провал, если он есть, иначе первая полученная отмена.
Бросается то самое исключение, которое несёт исход, ровно то, что бросил бы
`await ctx.run(child)`. Провал, который группа получила, но не бросила,
не теряется: он уходит туда, куда уходит ошибка, за которую никто не ответил.

| Форма | Ждёт | Останавливает остальных | Значения удавшихся веток |
| --- | --- | --- | --- |
| `Future.wait` | все ветки | нет | выброшены раньше, чем их увидит тело |
| `Future.wait(eagerError: true)` | первую ошибку, а задача всё равно ждёт | нет | выброшены |
| `[...].wait` | все ветки | нет | в `ParallelWaitError.values` |
| `ctx.runAll` | все ветки | да, причиной `SiblingCancelReason` | возвращены по порядку, если удались все ветки |

Берите `[ctx.run(a), ctx.run(b)].wait`, когда ветки не зависят от чужого
провала или когда одна ждёт другую. Берите `ctx.runAll`, когда результат без
одной из частей всё равно ни к чему. Ни одна из форм не закрывает то, что
вернули ветки: форма только отдаёт значения или выбрасывает их. Значение
закрывает регистрация, которую получатель сделал в момент, когда оно пришло.
У `ctx.run` это `dispose`, переданный с каждым вызовом, как в разделе
[«Регистрация по приходу и ожидание в одном конверте»](#регистрация-по-приходу-и-ожидание-в-одном-конверте)
выше. У `ctx.runAll` такого аргумента нет, а как зарегистрировать список,
который он возвращает, показывает раздел
[«Список, который вернула группа»](#список-который-вернула-группа).

Пяти вещей `runAll` не обещает. Часть из них зависит от того, что группа делает
с веткой, тело которой вернуло значение: группа держит такую ветку, пока
не решит, чем кончится сама, и до тех пор у ветки нет исхода, а её уборка ждёт.

**Остановка кооперативная.** Ветка, ждущая через `ctx.wait`, кончится,
а операция за ней доиграет и запишет свой результат. Чтобы остановилась сама
работа, передайте ей отмену через `ctx.onCancel` и дождитесь её через
`ctx.join`. Ветка, созданная с `cancellable: false`, отвергает остановку вовсе,
и группа её дожидается.

**Потомки упавшей ветки доигрывают.** Провал никогда не расходится каскадом,
поэтому детей, которых эта ветка запустила, никто не отменяет, и группа ждёт их
так же, как ждёт всё остальное.

**Исход ветки не окончателен, пока группа не решила.** Тело, вернувшее
значение, всё ещё может кончиться `Cancelled`: пока группа не решила, `outcome`
ветки равен `null`, а её `isCancelled` равен `false`. Когда другая ветка
кончается не значением, группа отменяет эту ветку причиной
`SiblingCancelReason`, и та кончается `Cancelled`, а `isCancelled` становится
`true`. Ветка, созданная с `cancellable: false`, эту отмену отклоняет
и кончается `Done`.

**Ветка, которая ждёт соседа по той же группе, может не кончиться никогда.**
Ожидание `Job.value` или `Job.done` соседа вешает группу: соседа держат, пока
группа не решила, а группа решает только тогда, когда держат всех или когда
тело одной из веток кончилось не значением. Ядро такое зависание не распознаёт:
ошибки не будет, группа просто ждёт. Отмена снимает это зависание на тех же
условиях, что и зависание на блокировке из следующего пункта: ветка, которая
ждёт соседа через `ctx.wait`, кончается, если только она не создана
с `cancellable: false` и не ждёт внутри `ctx.uncancellable`, а ветка в голом
`await` не кончается. Для веток, зависящих друг от друга, выход даёт
`[...].wait`.

**Может не кончиться и ветка, которая ждёт того, что соседняя отпускает в своей
уборке.** Размотку ветка начинает, только когда все ветки кончили тела
и дождались своих детей или когда тело одной из них кончилось не значением;
до тех пор ждут и её `dispose` с `onDispose`. Пусть ветки делят блокировку или
пул, где свободных слотов меньше, чем веток, которым они нужны, и каждая ветка
берёт блокировку или слот так, как на [странице об уборке](cleanup.md):
`ctx.join(Lock.acquire, dispose: (lock) => lock.release())`. Освобождение
записано в `dispose`, а он ждёт, так что блокировка или слот остаются у ветки,
которая их получила. Ветка, которая их ждёт, не даёт размотаться ни одной
ветке, и группа висит без таймеров и без ошибок, пока тело другой ветки
не кончится чем-то, кроме значения.

Отмена, родителя или ветки, снимает зависание, только если кончает то, чего
ветка ещё ждёт перед размоткой: её тело или её ребёнка. Кончить их она может,
когда они ждут через `ctx.wait` или на операции, которая слышит `ctx.onCancel`.
Застрявших в `ctx.join` на операции, глухой к отмене, в голом `await`, внутри
`ctx.uncancellable` или в задаче с `cancellable: false` отмена не кончает.
Отмена ветки, которая держит блокировку, ничего не даёт: её тело уже кончилось.
Поэтому такую блокировку берите в ребёнке ветки. Он отпустит её, когда
кончится, ещё внутри тела ветки:

```dart
Job.deferred<Source>((ctx) async {
  final locked = Job.deferred<Source>((ctx) async {
    await ctx.join(Lock.acquire, dispose: (lock) => lock.release());
    return ctx.wait(openRows, discard: (source) => source.close());
  });

  return ctx.run(locked, discard: (source) => source.close());
});
```

Ребёнок `locked` держит блокировку и заодно открывает источник, который ветка
вернёт. Сам он этот источник не закрывает: он его отдаёт, а его `discard`
срабатывает, только если значение никуда не дошло. Поэтому ветка регистрирует
своё закрытие в тот момент, когда источник к ней пришёл: это `discard`
у `ctx.run(locked, ...)`, как в разделе
[«Регистрация по приходу»](cleanup.md#регистрация-по-приходу). Если группа
кончится не успехом, ветка закроет источник сама, и блокировку к тому времени
уже никто не держит: ребёнок отпустил её, когда кончился. Или возьмите
`[...].wait`: там каждая ветка разматывается сама.

## Что группа отдаёт обратно

Свой это ресурс или отданный наружу, ветка говорит тем членом контекста, через
который регистрирует его освобождение:

```dart
Job.deferred<Source>((ctx) async {
  final cache = await ctx.wait(openCache, dispose: (cache) => cache.close());
  final rows = await ctx.wait(openRows, discard: (source) => source.close());
  await ctx.join(() => cache.warm(rows));

  return rows;
});
```

Владение здесь то же, что и везде, и именно в группе оно начинает быть важным.
Ресурс, который ветка держит для себя, идёт в `dispose` у `ctx.wait`
и `ctx.join` или в `onDispose` и закрывается концом ветки при любом исходе.
Ресурс, который ветка отдаёт наружу, идёт в их `discard` или в `onDiscard`: он
живёт до полного успеха группы и достаётся вызывающему открытым. Когда группа
кончается чем-то другим, ветка, принявшая остановку, закрывает взятое сама,
и закрывает до возврата из группы, поэтому к моменту, когда родитель поймает
ошибку, этот ресурс уже закрыт.

Ресурс ветка может и получить от своего ребёнка, как ветка с ребёнком `locked`
в разделе выше. Собственный `discard` ребёнка его не закроет: ребёнок отдаёт
ресурс и кончается `Done` внутри ветки, ещё до того, как группа что-то решила,
а `discard` срабатывает, только если значение никуда не дошло. Здесь оно дошло
до ветки, поэтому ветка регистрирует ресурс заново в момент, когда он пришёл,
через `ctx.run(child, discard: ...)`. Это уже её собственная регистрация:
ресурс живёт до полного успеха группы, а если группа кончится чем-то другим,
ветка закроет его сама. Этот вызов показан в разделе
[«Регистрация по приходу»](cleanup.md#регистрация-по-приходу) страницы
об уборке.

Одна вещь остаётся открытой, и она следует из раздела
[«Выбор колбэка»](cleanup.md#выбор-колбэка) страницы об уборке. Ветка,
созданная с `cancellable: false`, остановку отвергает и кончается `Done`, а её
значение считается отданным через её собственный `Job.value`: `discard`,
зарегистрированный веткой, не выполнился бы, и больше ресурс никто
не закрывает. Тело по-прежнему держит `rows`, задачу, которую передало
в `runAll`, и закрывает значение через неё:

```dart
final rows = Job.deferred<Source>(cancellable: false, (ctx) => openRows());
try {
  await ctx.runAll([rows, images]);
} on Object {
  if (rows.outcome case Done(:final value)) value.close();
  rethrow;
}
```

## Список, который вернула группа

`ctx.runAll` отдаёт телу список открытых источников, и тело должно закрыть
каждый из них, что бы ни случилось после возврата группы. Список ничем
не отличается от любого другого значения, и получатель у него тело: в отличие
от `run`, у `runAll` нет своих `dispose` или `discard`, чтобы зарегистрировать
его по приходу, поэтому список регистрирует само тело.

### Первая попытка

```dart
final sources = await ctx.runAll(branches);
await ctx.join(() => writeArchive(sources));
for (final source in sources) {
  source.close();
}
```

Тело закрывает источники там, где они ему больше не нужны, как любой код
на Dart закрывает файл после последней записи. Цикл выполняется, только если
тело до него дойдёт. Если отмена приходит, пока пишется архив, `ctx.join`
дожидается архива и бросает отмену вместо его значения, а упавший
`writeArchive` так же бросает свою ошибку. В обоих случаях до цикла тело
не доходит. Список уже на руках у тела и теперь недостижим, и об утечке
не объявляет ничто: вызывающий видит обычную отмену или ошибку архива.

### `try` следующей строкой

```dart
final sources = await ctx.runAll(branches);
try {
  await ctx.join(() => writeArchive(sources));
} finally {
  for (final source in sources) {
    source.close();
  }
}
```

`try` открывается следующей же строкой после возврата из группы, раньше всего,
что может бросить, а `finally` выполняется, как бы тело его ни покинуло:
на отмене, которую бросает `join`, на ошибке архива или после последней строки.
Список, который тело держит для себя, так закрывается целиком. `ctx.onDispose`
с тем же циклом на той же строке делает то же, что `finally`.

### Список, который тело отдаёт

```dart
final exported = Job.deferred<List<Source>>((ctx) async {
  final sources = await ctx.runAll(branches);
  try {
    await ctx.join(() => writeArchive(sources));
  } on Object {
    for (final source in sources) {
      source.close();
    }
    rethrow;
  }
  return sources;
});
```

Эта ветка пишет архив, а потом возвращает источники открытыми, чтобы вызывающий
работал с ними дальше. `finally` закрыл бы их и при успехе, поэтому закрытие
переезжает в `catch`. Он покрывает каждую ошибку тела и ничего после него:
возвращённый список всё ещё может не дойти ни до кого. Если `exported` стоит
веткой в группе `ctx.runAll` и брат падает уже после того, как тело вернулось,
группа отменяет ветку, как описано в разделе
[«Что группа отдаёт обратно»](#что-группа-отдаёт-обратно), и до вызывающего
список не доходит. Тело к этому времени давно вышло из `try`, и источники
остаются открытыми.

`ctx.onDiscard` выполняется ровно тогда, когда значение ни до кого не дошло,
поэтому закрывает список и в этом случае, а когда список доходит, не мешает:

```dart
final exported = Job.deferred<List<Source>>((ctx) async {
  final sources = await ctx.runAll(branches);
  ctx.onDiscard(() {
    for (final source in sources) {
      source.close();
    }
  });
  await ctx.join(() => writeArchive(sources));
  return sources;
});
```

`ctx.onDiscard` ставится следующей же строкой, раньше всего, что может бросить:
ошибка или отмена выше регистрации оставила бы список открытым, как в первой
попытке.

## Обработка стримов

`ctx.each(stream, onData)` подписывается на стрим и обрабатывает события
по одному. Метод сразу возвращает дочернюю `Job<void>`, которой принадлежит
подписка. Колбэк получает контекст этого ребёнка и событие.

Например, `saveMessages` ниже принимает стрим сообщений и асинхронную функцию
сохранения одного сообщения. `each` ждёт завершения каждого сохранения, прежде
чем передать следующее сообщение в колбэк:

```dart
Future<void> saveMessages(
  Stream<String> messages,
  Future<void> Function(String message) save,
) async {
  final job = Job<void>((ctx) async {
    final processing = ctx.each(messages, (childCtx, message) {
      return childCtx.join(() => save(message));
    });
    await processing.value;
  });

  await job.value;
}
```

`processing.value` завершается, когда стрим закончился и последнее сохранение
выполнено. Ошибка стрима или колбэка прекращает обработку; ожидание `value`
передаёт её в тело родителя и затем вызывающему `saveMessages`. Брошенный
`Cancelled` идёт путём отмены.

Возвращённая `Job` также позволяет родителю отдельно прекратить подписку. Этот
пример печатает событие каждую секунду, прекращает подписку через 2,5 секунды
и продолжает тело родителя:

```dart
Future<void> watchTicks() async {
  final job = Job<void>((ctx) async {
    final ticks = ctx.each(
      Stream<int>.periodic(const Duration(seconds: 1), (index) => index + 1),
      (childCtx, tick) => print('Tick $tick'),
    );

    await ctx.wait(
      () => Future<void>.delayed(const Duration(milliseconds: 2500)),
    );
    await ticks.cancel();
    print('Parent continues');
  });

  await job.value;
}
```

Вывод: `Tick 1`, `Tick 2`, затем `Parent continues`. Стрим ещё не завершён,
когда `ticks.cancel()` снимает подписку. Вызов ждёт завершения ребёнка; отмена
этого ребёнка сама не отменяет родителя.

Используйте `ticks.value`, когда ошибка или отмена ребёнка должна быть брошена
в тело, либо `ticks.done`, чтобы прочитать исход без броска. Неперехваченный
`Cancelled` из `value` ребёнка отменяет родителя по обычным правилам исходов
дочерней `Job`.

Родитель ждёт ребёнка, даже если его тело вернулось, не ожидая ребёнка. Поэтому
открытый стрим держит родителя до конца стрима или отмены ребёнка. Принятая
отмена родителя передаётся ребёнку. Наблюдатель видит этого ребёнка как
отдельную `Job`.

Как и `run`, `each` запускает детей только пока тело родителя активно; вызовы
из `unattended` или уборки отвергаются. Никто не ждёт future, которую
возвращает `cancel()` самой подписки; если она упадёт, ошибка уйдёт в `onError`
наблюдателя ребёнка и, если он за неё не отвечает, в зону. Обычное завершение
стрима по-прежнему зависит от отправки `onDone` источником.

В future от этого `cancel()` идёт уборка самого источника: закрывается
соединение, сбрасывается на диск файл. Ребёнок отпускает стрим и кончается,
не дожидаясь её, поэтому задача может кончиться, пока источник ещё закрывается.
Задача, которой нельзя кончаться раньше источника, кладёт его закрытие на свой
стек уборки:

```dart
final feed = Feed();
ctx.onDispose(feed.close);
await ctx.each(feed.messages, (childCtx, message) => save(message)).value;
```

`feed.close()` здесь возвращает future, которая завершается, когда соединение
закрыто. Уборка задачи её ждёт, поэтому задача кончается после неё,
а `cancel()` и родитель, которые ждут задачу, ждут и источник.

### Первая попытка

Сообщение сохраняется в два шага: сперва само сообщение, потом его вложения.
Колбэк ждёт оба:

```dart
ctx.each(messages, (childCtx, message) async {
  await store.saveBody(message);
  await store.saveAttachments(message);
});
```

Приняв отмену, ребёнок сразу снимает подписку и прекращает доставку событий.
Прервать уже идущий колбэк он не может: обычный `await` контрольной точкой
не служит, поэтому колбэк возвращается с первого шага, начинает второй
и доигрывает до конца, как будто ничего не случилось. Ребёнок его дожидается,
и уборка родителя тоже: отменённая задача, у колбэка которой ещё есть работа,
не освобождает ничего, пока этот колбэк не кончится.

### Контрольные точки самого ребёнка

```dart
ctx.each(messages, (childCtx, message) async {
  await childCtx.join(() => store.saveBody(message));
  await childCtx.join(() => store.saveAttachments(message));
});
```

Контекст ребёнка колбэк получает именно для того, чтобы его шаги могли
остановиться по отмене. `childCtx.join` дожидается того шага, который обёрнут
(сохранение на полпути всё равно сохранение), а затем выпускает отмену вместо
значения, поэтому второй шаг не начинается вовсе, а уборка родителя идёт сразу,
как только кончился первый. `childCtx.wait` остаётся другим выбором, для шага,
результат которого можно бросить. Чего внутрь класть нельзя, так это завершения
самого ребёнка: ожидание `value` задачи, которую вернул `each`, или её
`cancel()` из колбэка не кончится никогда, потому что ребёнок уже ждёт этот
колбэк.

### Что открывает одно событие

Каждое сообщение пишется через черновик, и черновик надо закрыть. Колбэк отдаёт
закрытие в `dispose`, как это делает тело:

```dart
ctx.each(messages, (childCtx, message) async {
  final draft = await childCtx.join(
    () => store.openDraft(message),
    dispose: (draft) => draft.close(),
  );
  await childCtx.join(draft.write);
});
```

`dispose` кладёт закрытие на стек уборки ребёнка, а этот стек разматывается,
когда кончается ребёнок, а не когда возвращается колбэк. После двух сообщений
оба черновика записаны и ни один не закрыт; закроются они вместе, когда
кончится стрим, а на стриме без конца не закроются никогда. `ctx.onDispose`
и `discard` в колбэке регистрируют на том же стеке.

То, что открывает одно событие, принадлежит ребёнку, запущенному для этого
события:

```dart
ctx.each(messages, (childCtx, message) {
  return childCtx.run(Job.deferred<void>((eventCtx) async {
    final draft = await eventCtx.join(
      () => store.openDraft(message),
      dispose: (draft) => draft.close(),
    );
    await eventCtx.join(draft.write);
  }));
});
```

Колбэк возвращает future от `run`, поэтому следующее сообщение ждёт этого
ребёнка, а его стек разматывается раньше: каждый черновик закрыт до того, как
открыт следующий. Отменённый посреди записи, ребёнок всё равно закрывает свой
черновик до конца задачи.

### `await for` в теле

```dart
Job<void>((ctx) async {
  await for (final message in messages) {
    await ctx.join(() => store.saveBody(message));
  }
});
```

Пока идёт сохранение, `join` служит контрольной точкой: отмена, пришедшая в это
время, бросается, когда сохранение кончилось, и цикл отпускает стрим. Между
двумя сообщениями контрольной точки нет. Тело стоит внутри `await for`, который
о задаче ничего не знает, поэтому задача, отменённая при молчащем стриме,
продолжает идти и держать подписку, пока не придёт следующее сообщение.
`job.cancel()` до этого тоже не возвращается. На стриме, который замолчал
насовсем, этого не случится никогда.

`ctx.each` снимает подписку в тот момент, когда задача приняла отмену, идёт
сообщение или нет.

### `listen` в теле

```dart
Job<void>((ctx) async {
  final subscription = messages.listen((message) async {
    await store.saveBody(message);
  });
  ctx.onCancel(subscription.cancel);
  await ctx.wait(subscription.asFuture<void>);
});
```

Последние две строки привязывают подписку к задаче: отмена её снимает, а тело
ждёт конца стрима. Не хватает ещё двух вещей.

`listen` не ждёт асинхронный колбэк. Второе сообщение приходит, пока
сохраняется первое, и его сохранение начинается сразу: оба идут рядом, и какое
кончится первым, не сказано нигде.

И колбэк зовёт стрим, а не тело. Ошибка, брошенная в нём, уходит в зону мимо
задачи: задача продолжает идти и держать подписку, её исход о провале ничего
не знает, и тот, кто ждёт её `value`, тоже.

`ctx.each` доставляет следующее сообщение, когда колбэк предыдущего кончился,
а ошибка колбэка кончает ребёнка исходом `Failed`.

### Задача, которая только следует за стримом

```dart
Future<void> saveAll(
  Stream<String> messages,
  Future<void> Function(String message) save,
) async {
  final saving = Job.each(messages, (ctx, message) {
    return ctx.join(() => save(message));
  });

  await saving.value;
}
```

`saveMessages` выше понадобилось две задачи: родитель, которому больше нечего
делать, и ребёнок, которому принадлежит подписка. `Job.each` создаёт одну
задачу, которая следует за стримом сама. Это корень, а не ребёнок, и колбэк
получает контекст этой задачи. За стримом она следует так же, как `ctx.each`;
`key`, `describe`, `cancellable` и `observer` те же, что у `Job(...)`.

От ребёнка её отличают три вещи:

- **Она стартует внутри вызова.** Задача, созданная `Job(...)`, запускает тело
  следующей микротаской. `Job.each` к возврату уже подписана, поэтому событие,
  которое broadcast-стрим отправил сразу после вызова, не теряется. По той же
  причине `onStart` наблюдателя выполняется раньше, чем вызывающий получил
  хэндл, а источник, отдающий событие прямо из `listen`, доходит до колбэка
  до возврата из вызова. Колбэк, которому нужна своя задача, читает `ctx.job`.
- **Она корень, где бы её ни создали.** Вызванная в теле другой задачи, она
  не становится её ребёнком: тело её не ждёт и не отменяет, а `ctx.run`
  отказывает ей с `ArgumentError`. Внутри тела за стримом следуют через
  `ctx.each`. Провал, который никто не прочёл, уходит в зону, как у любого
  корня.
- **С `cancellable: false` снаружи её не остановить.** Такая задача
  не принимает ни одной отмены, и `cancel()` не возвращается, пока задача
  не кончится сама: стрим кончился или упал либо колбэк бросил, в том числе
  `Cancelled`. На стриме без конца другого выхода нет.

## Цепочки

`then` продолжает работу с результатом предыдущей `Job`. Каждый вызов
возвращает новую `Job` и передаёт колбэку отдельный контекст. Следующий колбэк
запускается после успешного завершения предыдущей `Job`, включая её детей
и уборку:

```dart
final loaded = Job<String>((ctx) => ctx.join(loadText));
final parsed = loaded.then<int>((ctx, text) => int.parse(text));
final saved = parsed.then<void>((ctx, number) => ctx.join(
      () => saveNumber(number),
    ));

await saved.value;
```

Отмена `saved` запрашивает отмену ещё не завершённых `parsed` и `loaded`.
Отмена `parsed` запрашивает отмену незавершённого `loaded` и отменяет `saved`.
Отмена `loaded` передаётся вперёд обоим продолжениям. Переданный запрос
получает `ChainCancelReason`, в поле `cause` которой лежит `Cancelled`
соседнего звена. Завершённые `Job` сохраняют свой исход. Если к одной `Job`
присоединено несколько продолжений, отмена одного может отменить общий источник
и остальные.

`await saved.cancel()` ждёт незавершённых предшественников, их детей и уборку,
а также уже начатую работу и уборку самого `saved`. Источник сохраняет свои
правила отмены: `cancellable: false` отклоняет запрос, а `uncancellable`
придерживает его. Отменённое продолжение всё равно ждёт такой источник, затем
завершается без вызова колбэка. Во время ожидания у него может быть
`isCancelled`, но ещё не `isFinished`; исход содержит `started: false`, если
отмена принята при ожидании источника.

Провал предшественника передаёт ошибку и стек дальше без вызова колбэка.
Наблюдайте продолжение через `value`, `done` или `ignore`, чтобы обработать
этот провал. Если отменённое продолжение не может передать ошибку источника,
оно её и не наблюдает: например, источник, который отказал отмене, а затем
упал, требует отдельной обработки ошибки.

Колбэк возвращает значение или future. Возврат другой `Job` не ожидает её: для
отложенного ребёнка верните `ctx.run(child)`. `then` не запускает отложенный
источник, а само продолжение нельзя усыновить через `ctx.run`. Не ожидайте его
из тела или уборки его источника: оно само ждёт завершения этого источника.

Каждое продолжение относится к корневым `Job` ядра. У него есть необязательный
аргумент `observer`; оно не наследует ни наблюдателя источника, ни того, что
движок предметной области навесил на источник. Зарегистрированная источником
уборка уже выполнена к передаче значения: ресурс, закрытый через `onDispose`
источника, в этот момент уже закрыт.

С `discard` источника всё наоборот: источник кончился `Done`, поэтому `discard`
не выполнялся и не выполнится, а получателем становится само продолжение:
значение приходит к нему аргументом, и освобождение оно регистрирует в своём
теле. Один случай остаётся без получателя вовсе: продолжение, отменённое, пока
оно ждало, заканчивается, ни разу не позвав свой колбэк, так что нет ни тела,
ни момента. Источник, забравший отмену с собой, по пути закрыл то, что взял;
а тот, что её отверг (`cancellable: false` или кончившийся к приходу запроса),
кончается `Done` всё равно, и ресурс тогда закрывает вызывающий, через хэндл
источника, ровно как у ветки, отвергающей остановку группы.

Наблюдатель последнего звена слышит провал из любого места цепочки выше как
провал этого звена: провал идёт по цепочке вниз и заканчивает каждое следующее
звено. Ошибка без исхода, например провал работы `ctx.unattended` или уборщика,
остаётся на звене, где случилась: она уходит к наблюдателю этого звена и, если
он за неё не отвечает, в зону, где звено создано; у продолжения это зона, где
вызвали `then`.

### Первая попытка

Задача загружает строки, продолжение о них докладывает, и тело хочет, чтобы
к его концу было сделано и то и другое, поэтому усыновляет обоих:

```dart
final child = Job.deferred<int>((ctx) => ctx.wait(load));
final tail = child.then<void>((ctx, rows) => report(rows));

final parent = Job<void>((ctx) async {
  ctx.log(await ctx.run(child));
  await ctx.run(tail);
});
```

Второй `ctx.run` бросает `ArgumentError`:
`Invalid argument (child): is a continuation,
which starts itself once its source finishes: "Job(then)"`. `ctx.run` принимает
`Job`, которую никто не стартует сам, а продолжение не из таких. Длина цепочки
ничего не меняет: `child.then(...).then(...)` вешает одно продолжение
на другое, и каждое звено отказывает в усыновлении одинаково.

### Два ребёнка подряд

```dart
final parent = Job<void>((ctx) async {
  final rows = await ctx.run(Job.deferred<int>((ctx) => ctx.wait(load)));
  await ctx.run(Job.deferred<void>((ctx) => ctx.join(() => report(rows))));
});
```

Последовательность, которая принадлежит операции, строится из детей. Второй
`ctx.run` стартует, когда первый вернул значение, родитель ждёт обоих, и его
отмена доходит до того из них, который сейчас работает.

Последовательность, которая сознательно живёт дольше операции, строится
цепочкой, и тогда ребёнком остаётся только источник:

```dart
final parent = Job<void>((ctx) async {
  // Источник остаётся ребёнком: родитель его запускает и дожидается.
  ctx.log(await ctx.run(child));
});

await parent.value; // Done, что бы ни делало продолжение.
await tail.value; // Продолжение наблюдать вам.
```

Родитель ждёт своих детей, а не то, что на них навешано. Как только
`ctx.run(child)` вернулся и тело закончилось, родитель завершается `Done`, пока
медленное продолжение ещё работает. Отмена родителя доходит до продолжения,
только пока оно ещё ждёт источник: отмена родителя отменяет ребёнка, а отмена
ребёнка идёт вперёд по цепочке как `ChainCancelReason`. Когда источник кончился
и продолжение заработало, ничто из того, что делает родитель, до него
не доходит. Остановить его может только собственный хэндл продолжения:
`tail.cancel()` или `ctx.onCancel(() => tail.cancel().ignore())` в теле
родителя, пока оно ещё идёт.

Ошибка продолжения касается только его самого. Наблюдайте его через `value`,
`done` или `ignore`; ошибка, которую никто не наблюдал, уйдёт в зону, где
вызвали `then`, уже после того, как родитель закончился. Исход продолжения
возвращается вам, а не родителю.
