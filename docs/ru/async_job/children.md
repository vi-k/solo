# Дети

Тело может отдать работу другой задаче тремя способами:

1. Ребёнка тело запускает само и само его дожидается. Несколько детей, которых
   ждут вместе, составляют [группу](groups.md).
2. [Стрим](streams.md) обрабатывается по одному событию в ребёнке, которому
   принадлежит подписка.
3. [Продолжение](chains.md), созданное через `then`, стартует, когда задача,
   за которой оно стоит, завершится успешно, и живёт дольше неё.

Слова для этих трёх похожи, и неверное компилируется так же, как верное. Каждое
на своём месте:

```dart
final job = Job<void>((ctx) async {
  // Ребёнок: тело его запускает, дожидается и отменяет вместе с собой.
  final rows =
      await ctx.run(Job.deferred<int>((c) => c.abandonable(loadRows)));

  // Стрим: по одному событию, в собственном ребёнке.
  final saving = ctx.each(events, (c, e) => c.join(() => save(e)));

  // Цепочка: стартует сама, когда источник завершится успешно,
  // и ребёнком её не может взять никакой родитель.
  final tail = saving.then<void>((c, _) => report(rows));
});
```

## Дети

Тело поручает работу другой `Job`, зарегистрировав её как дочернюю:

```dart
final parent = Job<void>((ctx) async {
  final child = Job.deferred<int>((ctx) => ctx.abandonable(load));
  final rows = await ctx.run(child);
  ctx.log('$rows rows');
});
```

`ctx.run(child)` сразу запускает дочернюю задачу и возвращает future её
результата. Родитель ждёт всех дочерних задач перед завершением. Когда родителя
отменяют, он передаёт отмену дочерним задачам, и так же он поступает, когда его
тело бросает `Cancelled`. Дочерняя задача с `cancellable: false` отклоняет
отмену в обоих случаях: она работает до конца, а родитель дожидается её
и только потом кончается `Cancelled`. При другой ошибке тела родитель позволяет
дочерним задачам доработать и ждёт их завершения.

Создавайте дочерние задачи через `Job.deferred`, чтобы родитель управлял их
запуском. `ctx.run` принимает `ChildJob`, а обычная `Job` им не является,
потому что такая задача запускается автоматически: она может стартовать раньше,
чем родитель её зарегистрирует, и тогда будет работать вне отмены и ожидания
родителя.

`run` ждёт завершения дочерней задачи, включая её детей и уборку, и проверяет
отмену родителя перед возвратом значения в тело. Если дочерняя задача отклонит
отмену, `run` продолжит ждать её; после её успешного завершения он бросит
отмену родителя, и тело не перейдёт к вызову `log`. Ошибка или отмена дочерней
задачи передаётся через возвращённую future со своим стеком. Для запроса отмены
вызовите `child.cancel()`, для просмотра исхода используйте `child.done`.

Дочерняя задача наследует наблюдателя родителя, если у неё нет своего. Если её
отмена выходит через `await ctx.run(child)` или `child.value`, родитель
завершается с `HandlerCancelReason` и описанием, указывающим на дочернюю
задачу.

### Ребёнок без `await`

```dart
final parent = Job<void>((ctx) async {
  final rows = ctx.run(Job.deferred<int>((c) => c.abandonable(loadRows)));
  final child = Job.deferred<void>((c) => c.abandonable(warmCache));
  ctx.run(child).ignore();
  ctx.log('${await rows} rows');
});
```

Оба ребёнка запускаются сразу. В `rows` лежит future, которую вернул `ctx.run`:
её сохранили и дожидаются позже, а такую future нужно дождаться или обработать
её ошибки. `child` прогревает кэш, который здесь никто не читает,
и `ctx.run(child).ignore()` говорит, что результат не нужен. Родитель всё равно
дождётся обоих перед завершением. `child.ignoreFailure()` не заменяет
`ctx.run(child).ignore()`. `child.ignoreFailure()` гасит отчёт ядра о провале,
на который никто не посмотрел, а здесь на провал смотрит `run`: он ждёт
значения ребёнка. Если `child` упадёт, его ошибка придёт через future, которую
вернул `run`, а это обычная future Dart: необработанной она уходит в зону,
и `Cancelled` ребёнка тоже. `ctx.run(child).ignore()` гасит ошибку этой future,
и больше ничего: наблюдатель ребёнка всё равно слышит эту ошибку через
`onError`.

Если ребёнок кончился `Cancelled`, а его тело упало, ошибка через future
от `run` не приходит. Так бывает, например, когда отмена остановила операцию,
а тело бросило ошибку этой операции. `await ctx.run(child)` бросает
`Cancelled`, а ошибка уходит туда, куда уходит ошибка, которую никто
не обработал: к наблюдателю ребёнка и, если он не перехватит её
в `onUnanswered`, в зону, как в разделе
[«Куда уходят ошибки»](observing.md#куда-уходят-ошибки) страницы о наблюдении.
Ошибка, которую приложение назвало в `Job.isCancellationError`, дальше
наблюдателя ребёнка не идёт, как в разделе
[«Ошибки отмены»](observing.md#ошибки-отмены). `child.ignoreFailure()` гасит
ошибку, какой бы она ни была. `ctx.run(child).ignore()` её не гасит: он гасит
то, что бросает future, а она бросает отмену. Чтобы отправить ошибку в другое
место, дайте ребёнку наблюдателя, который её перехватит: `JobAnswerer`
с переопределённым `onUnanswered`.

### Когда `ctx.run` отклоняет ребёнка

`ctx.run` принимает `ChildJob`: задачу из `Job.deferred` или задачу движка,
который его объявил. Задача, которая стартует сама, из `Job(body)`, `then` или
`Job.each`, не из таких, и её не пропустит компилятор. Чего по типу не видно,
`ctx.run` отклоняет синхронно, до того как ребёнок начнёт работать:

| Ребёнок | Что делает `ctx.run` |
| --- | --- |
| Задача другой реализации | Бросает `ArgumentError` |
| Задача, которая уже запущена или уже закончилась | Бросает `StateError` |
| Любая задача после того, как тело родителя завершилось | Бросает `StateError` |
| Любая задача, когда родитель уже отменён | Отменяет ребёнка до старта и бросает `Cancelled` родителя |

`ArgumentError` или `StateError` ребёнка не трогают, и он остаётся у кода,
который его создал: `Job.deferred`, которую так отклонил `ctx.run`, остаётся
незапущенной, а её `done` ждёт, пока этот код её не запустит или не отменит.
[`ctx.runAll`](groups.md) до первого старта делает те же проверки для каждой
задачи своего списка, а одну и ту же задачу дважды отклоняет с `ArgumentError`;
такой отказ не трогает ни одной задачи списка.

### Глубина дерева

```dart
ChildJob<void> level(int depth) {
  return Job.deferred<void>((ctx) async {
    // Без этого await вся цепочка строится на одном стеке.
    await null;
    if (depth > 0) await ctx.run(level(depth - 1));
  });
}
```

Глубина дерева ограничена стеком, и упирается она в два разных обхода. Запуск
ребёнка выполняет его тело до первого `await`. Без `await null` выше каждый
уровень создаёт своего ребёнка раньше, чем приостанавливается, и вся цепочка
строится на одном стеке: около тысячи уровней в Dart VM на десктопе, и обвал
приходит ещё на постройке дерева. Дерево, которое там переполнило стек, всё
равно кончается: `ctx.run` бросает `StackOverflowError` в тело, которое его
вызвало, а задачи, чей старт оборвало переполнение, кончаются, когда кончится
это тело. С `await null` постройка идёт по микротаскам, и предел переходит
ко второму обходу, то есть к отмене, которая спускается по дереву рекурсией
и доходит примерно до трёх тысяч. Ни то ни другое число не обещание: оба
следуют из размера кадра тела.

Каскад, у которого кончился стек, останавливается там, где стек кончился,
а задачи ниже этой глубины продолжают работать. Переполнение выходит из самого
`cancel()`, раньше, чем тот вернёт future, поэтому `cancel().ignore()` его
не ловит. Рекурсии, измеряемой тысячами вложенных задач, нужен не стек
поглубже, а плоская структура.

## Обработка стримов

`ctx.each(stream, onData)` подписывается на стрим и обрабатывает события
по одному в дочерней `Job<void>`, которой принадлежит подписка. Родитель ждёт
этого ребёнка, даже если его тело вернулось, не ожидая ребёнка. Остальное
на странице о [стримах](streams.md): что вместо этого делают `await for`
и `listen` в теле, как колбэк останавливается по отмене, чья уборка у одного
события и `Job.each` для задачи, вся работа которой в стриме.
