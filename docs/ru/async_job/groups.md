# Группы

Строки под кодом — то, о чём сообщает код:

- `rows closed`: источник строк закрыт;
- `lock acquired`, `lock waits`, `lock released`: что происходит с блокировкой,
  которую делят ветки;
- `outcome:` то, чем завершается `parent.done`.

## Ожидание нескольких детей

Экспорту нужны два источника: строки и картинки. Друг друга они не ждут,
поэтому открываются сразу оба. Каждая ветка закрывает то, что открыла, если
не отдала это наружу. Что бы ни случилось, родитель обязан кончиться правдой
об этом, и ничего не должно остаться открытым.

### Первая попытка

```dart
// Первая попытка: исход решает гонка, а источник утекает.
final parent = Job<void>((ctx) async {
  final rows = Job.deferred<Source>(
    (ctx) => ctx.abandonable(openRows, discard: (source) => source.close()),
  );
  final images = Job.deferred<Source>(
    (ctx) => ctx.abandonable(openImages, discard: (source) => source.close()),
  );

  final sources = await Future.wait([ctx.run(rows), ctx.run(images)]);
  await ctx.join(() => writeArchive(sources));
});
```

`Future.wait` — то, чем Dart ждёт несколько future, и здесь у него две беды.
Вот что происходит:

1. Исход решает гонка. `Future.wait` оставляет себе первую дошедшую до него
   ошибку, а остальные молча отпускает. Допустим, `rows` падает, а `images`
   кончается `Cancelled`. Если первым дойдёт провал, родитель кончится
   `Failed`. Если первой дойдёт отмена, родитель кончится
   `Cancelled(HandlerCancelReason)`, и провала `rows` в исходе нет вовсе. Тогда
   его слышит только наблюдатель ребёнка. Ядро не отдаёт его в зону: тело ждало
   future от `run`, поэтому ядро считает, что на провал посмотрели. Если
   наблюдателя нет ни у родителя, ни у детей, ошибка теряется.
2. Источник утекает. Допустим, `rows` падает, а `images` удаётся. Ветка
   `images` возвращает свой источник и кончается `Done`, поэтому её `discard`
   не выполняется: значение дошло до `ctx.run`. Но `Future.wait` завершается
   ошибкой и выбрасывает значения, так что тело источника даже не держит. Его
   не закрывает никто.

`eagerError: true` не чинит ни того ни другого:

```dart
// Первая попытка с eagerError: та же гонка и та же утечка.
final sources = await Future.wait(
  [ctx.run(rows), ctx.run(images)],
  eagerError: true,
);
```

Он меняет только то, когда просыпается тело: на первой ошибке, а не после
последней ветки. Остановиться остальным веткам никто не предлагает, а детей
ядро дожидается в любом случае, поэтому задача кончается не раньше. Исход
по-прежнему решает то, чья беда пришла первой, а источник удавшейся ветки
по-прежнему пропадает.

### Регистрация по приходу и ожидание в одном конверте

```dart
final parent = Job<void>((ctx) async {
  final rows = Job.deferred<Source>(
    (ctx) => ctx.abandonable(openRows, discard: (source) => source.close()),
  );
  final images = Job.deferred<Source>(
    (ctx) => ctx.abandonable(openImages, discard: (source) => source.close()),
  );

  final sources = await [
    ctx.run(rows, dispose: (source) => source.close()),
    ctx.run(images, dispose: (source) => source.close()),
  ].wait;
  await ctx.join(() => writeArchive(sources));
});
```

Когда `rows` открылась, а `images` упала, код печатает:

```text
rows closed
outcome: Failed(ParallelWaitError: Bad state: disk)
```

Изменились две вещи, и каждая чинит одну беду.

`ctx.run(child, dispose: ...)` чинит утечку. Он регистрирует значение
на родителе в тот момент, когда ветка его отдаёт. С этого момента значение
закрывает родитель, когда кончается, чем бы он ни кончился: после записи
архива, когда другая ветка упала или отменилась или когда родителя отменили
в промежутке. Ветка, которая не дошла до возврата, закрывает свой источник
через `discard`, с которым его открывала. Под `Future.wait` это тоже
починило бы утечку. Это правило из раздела
[«Регистрация по приходу»](cleanup.md#регистрация-по-приходу) страницы
об уборке. Колбэк — `dispose`, а не `discard`, потому что источники родитель
держит для себя.

`.wait` чинит исход. Он собирает все ошибки в один `ParallelWaitError` вместе
со значениями тех веток, которые удались. Ядро читает этот конверт. Конверт
с настоящим провалом остаётся провалом, со своими ошибками и значениями
нетронутыми. Конверт из одних отмен и значений заканчивает родителя первой
по списку отменой, так же, как [ожидание одной дочерней задачи](children.md).
Порядок, в котором пришла беда, больше ничего не решает. Значения в конверте
уже зарегистрированы, поэтому, если закрыть их ещё и там, они закроются дважды.

`.wait` не останавливает ни одну ветку раньше срока. Он возвращает управление,
когда закончены все ветки, поэтому, если одна ветка упала или была отменена
сама по себе, её соседка доигрывает до конца. Отмена родителя их останавливает:
она доходит до каждого ребёнка, в том числе до веток `.wait`. Ресурс, открытый
веткой для себя, всё равно освобождается, когда ветка кончается, если ветка
зарегистрировала его через `dispose`:
`ctx.abandonable(() => open(), dispose: (value) => value.close())`. Уборка
принадлежит задаче, а не ожиданию.

### Когда один провал делает остальное бессмысленным

Бывает, что результат без одной из частей ни к чему, и ветки, которые ещё
работают, должны остановиться, как только одна упала. Это делает `ctx.runAll`:

```dart
final values = await ctx.runAll([
  Job.deferred<int>((ctx) => ctx.abandonable(loadRows)),
  Job.deferred<int>((ctx) => ctx.abandonable(loadExtra)),
]);
```

`ctx.runAll` запускает каждого ребёнка синхронно, по порядку списка,
и возвращает их значения в том же порядке. Как только тело ветки кончается
не значением, группа отменяет остальные ветки причиной `SiblingCancelReason`.
Ветку, из которой пришла беда, она не отменяет, иначе ошибка этой ветки
превратилась бы в отмену и пропала.

Что бросит `runAll`, решают итоговые исходы: настоящий провал, если он есть,
иначе первая полученная отмена, кроме тех, которые группа запросила сама.
Бросается тот самый объект, который несёт исход, как бросил бы
`await ctx.run(child)`. Провал, который группа получила, но не бросила, идёт
путём ошибки, которую не несёт ни один исход. Если движок руками кончает ветку
значением уже после того, как группа услышала о провале её тела, группа исходит
из этого провала, а не из `Done` ветки; см. раздел
[«Не дожидаясь контрольной точки»](extending.md#не-дожидаясь-контрольной-точки)
страницы о расширении.

Ветки группы ждут друг друга. Ветка, тело которой вернуло значение,
не разматывается, пока все ветки не кончили тела и не дождались своих детей или
пока тело одной из них не кончилось без значения. Её колбэки `dispose` ждут
вместе с ней. Поэтому ветка, которая ждёт соседку, может повесить группу; как
это бывает, показывает раздел
[«Ветки, которые ждут друг друга»](#ветки-которые-ждут-друг-друга).

| Форма | Ждёт | Останавливает остальных | Значения удавшихся веток |
| --- | --- | --- | --- |
| `Future.wait` | все ветки | нет | выброшены раньше, чем их увидит тело |
| `Future.wait(eagerError: true)` | первую ошибку, а задача всё равно ждёт | нет | выброшены |
| `[...].wait` | все ветки | нет | в `ParallelWaitError.values` |
| `ctx.runAll` | при успехе уборку каждой ветки, кроме зарегистрированной веткой уже после своей уборки, при провале каждую ветку до конца | да, причиной `SiblingCancelReason` | возвращены по порядку, если удались все ветки |

Берите `[ctx.run(a), ctx.run(b)].wait`, когда ветки не зависят от чужого
провала или когда одна ждёт другую. Берите `ctx.runAll`, когда результат без
одной из частей всё равно ни к чему.

При успехе `ctx.runAll` отдаёт значения, когда каждая ветка выполнила свою
уборку, и раньше, чем ветки кончились. Ветка, выполнившая уборку, ждёт там
уборки остальных, и уборка, которую она регистрирует в этом ожидании, —
из таймера или своего события, — выполняется уже после того, как значения
пришли, под родителем, который, как всегда, ждёт своих детей. При провале
`ctx.runAll` ждёт конца каждой ветки, так что к приходу ошибки всё, что ветки
взяли, закрыто.

Ни одна из форм не закрывает то, что вернули ветки: форма только отдаёт
значения или выбрасывает их. Значение закрывает регистрация, которую его
получатель сделал, когда оно пришло. У `ctx.run` это `dispose`, переданный
с каждым вызовом. У `ctx.runAll` такого аргумента нет, а как зарегистрировать
этот список, показывает раздел
[«Список, который вернула группа»](#список-который-вернула-группа).

## Ветки, которые ждут друг друга

Две ветки читают строки под одной блокировкой, потому что хранилище пускает
одного читателя за раз. Так же ведёт себя пул, в котором свободных мест меньше,
чем веток, которым они нужны. Каждая ветка берёт блокировку так, как страница
об уборке берёт ресурс:
`ctx.join(Lock.acquire, dispose: (lock) => lock.release())`.

### Первая попытка

```dart
// Первая попытка: блокировка ждёт группу, а группа — её.
ChildJob<int> reading() {
  return Job.deferred<int>((ctx) async {
    await ctx.join(Lock.acquire, dispose: (lock) => lock.release());
    return ctx.abandonable(loadRows);
  });
}

final parent = Job<List<int>>((ctx) => ctx.runAll([reading(), reading()]));
```

```text
lock acquired
lock waits
```

Больше ничего не приходит: группа висит без ошибки и без таймера. Вот что
происходит:

1. Первая ветка берёт блокировку, читает и возвращает значение. Её тело
   кончилось, но ветка ещё не разматывается, и `dispose`, который отпускает
   блокировку, ждёт вместе с ней.
2. Вторая ветка ждёт блокировку, поэтому её тело не кончается.
3. Ветки разматываются, когда каждое тело кончилось вместе со своими детьми или
   когда одно кончилось без значения. Ни того ни другого не происходит, а ядро
   зависание не распознаёт.

Ветка, которая ждёт `Job.value` или `Job.done` соседки, вешает группу так же:
у соседки нет исхода, пока группа не решила.

Отмена здесь не помогает. Она снимает такое зависание, только если кончает то,
чего ветка ещё ждёт: тело или его ребёнка, которые ждут через `ctx.abandonable`
или на операции, которая слышит `ctx.onCancel`. Вторая ветка ждёт в `ctx.join`
на `Lock.acquire`, а тот отмены не слышит, поэтому висит даже отменённый
родитель. Голый `await` отмена тоже не кончает, как и ожидание внутри
`ctx.uncancellable` или в задаче с `cancellable: false`. Отмена ветки, которая
держит блокировку, ничего не даёт: её тело уже кончилось.

### Блокировка в ребёнке ветки

```dart
ChildJob<int> reading() {
  return Job.deferred<int>((ctx) async {
    final locked = Job.deferred<int>((ctx) async {
      await ctx.join(Lock.acquire, dispose: (lock) => lock.release());
      return ctx.abandonable(loadRows);
    });
    return ctx.run(locked);
  });
}
```

```text
lock acquired
lock waits
lock released
lock acquired
lock released
outcome: Done([21, 21])
```

Блокировку держит ребёнок `locked`, а кончается он внутри тела ветки. Тогда же
его уборка отпускает блокировку, ещё до того, как группа что-то решила,
и вторая ветка её берёт. Для веток, которые зависят друг от друга, есть
и другой выход, `[...].wait`: под ним каждая ветка разматывается сама.

## Что группа отдаёт обратно

Свой это ресурс или отданный наружу, ветка говорит тем членом, через который
регистрирует его освобождение:

```dart
Job.deferred<Source>((ctx) async {
  final cache =
      await ctx.abandonable(openCache, dispose: (cache) => cache.close());
  final rows =
      await ctx.abandonable(openRows, discard: (source) => source.close());
  await ctx.join(() => cache.warm(rows));

  return rows;
});
```

Владение здесь то же, что и везде, и именно в группе оно начинает быть важным.
Ресурс, который ветка держит для себя, идёт в `dispose` у `ctx.abandonable`
и `ctx.join` или в `onDispose`. Конец ветки закрывает его при любом исходе.
Ресурс, который ветка отдаёт наружу, идёт в их `discard` или в `onDiscard`.
Тогда он живёт до полного успеха группы и достаётся вызывающему открытым. Когда
группа кончается чем-то другим, ветка, принявшая остановку, закрывает взятое
сама, ещё до возврата из группы. К моменту, когда родитель поймает ошибку, этот
ресурс уже закрыт.

Ресурс ветка может получить и от своего ребёнка:

```dart
Job.deferred<Source>((ctx) async {
  final opening = Job.deferred<Source>(
    (ctx) => ctx.abandonable(openRows, discard: (source) => source.close()),
  );
  return ctx.run(opening, discard: (source) => source.close());
});
```

Собственный `discard` ребёнка источник не закрывает. Ребёнок отдаёт источник
и кончается `Done` внутри ветки, ещё до того, как группа что-то решила,
а `discard` срабатывает, только если его задача кончилась не `Done`. Здесь
источник дошёл до ветки. Поэтому ветка регистрирует источник заново в момент,
когда он пришёл, через `discard`, переданный в `ctx.run`. Это собственная
регистрация ветки: источник живёт до полного успеха группы, а если группа
кончится чем-то другим, ветка закроет его сама. Этот вызов показан в разделе
[«Регистрация по приходу»](cleanup.md#регистрация-по-приходу) страницы
об уборке.

Одна вещь остаётся открытой, и она следует из раздела
[«Выбор колбэка»](cleanup.md#выбор-колбэка) страницы об уборке. Ветка,
созданная с `cancellable: false`, остановку отвергает и кончается `Done`. Её
значение считается отданным через её собственный `Job.value`: `discard`,
зарегистрированный веткой, не выполнился бы, и больше ресурс никто
не закрывает. Тело по-прежнему держит `rows`, задачу, которую передало
в `runAll`, и закрывает значение через неё:

```dart
final rows = Job.deferred<Source>(cancellable: false, (ctx) => openRows());
try {
  await ctx.runAll([rows, images]);
} on Object {
  if (rows.outcome case Done(:final value)) value.close();
  rethrow;
}
```

## Список, который вернула группа

`ctx.runAll` отдаёт телу список открытых источников, и тело должно закрыть
каждый из них, что бы ни случилось после возврата группы. Список ничем
не отличается от любого другого значения, и получатель у него тело. В отличие
от `run`, у `runAll` нет `dispose` или `discard`, чтобы зарегистрировать список
по приходу, поэтому тело регистрирует его само.

### Первая попытка

```dart
// Первая попытка: исключение до цикла оставляет все источники открытыми.
final sources = await ctx.runAll(branches);
await ctx.join(() => writeArchive(sources));
for (final source in sources) {
  source.close();
}
```

Тело закрывает источники там, где они ему больше не нужны, как любой код
на Dart закрывает файл после последней записи. Цикл выполняется, только если
тело до него дойдёт. Если отмена приходит, пока пишется архив, `ctx.join`
дожидается архива и бросает отмену, вместо того чтобы вернуться. Упавший
`writeArchive` так же бросает свою ошибку. В обоих случаях тело до цикла
не доходит. Список пропадает на руках у тела, и об утечке не объявляет ничто:
вызывающий видит обычную отмену или ошибку архива.

### `try` следующей строкой

```dart
final sources = await ctx.runAll(branches);
try {
  await ctx.join(() => writeArchive(sources));
} finally {
  for (final source in sources) {
    source.close();
  }
}
```

`try` открывается следующей же строкой после возврата из группы, раньше всего,
что может бросить. `finally` выполняется, как бы тело ни покинуло `try`:
на отмене, которую бросает `join`, на ошибке архива или после последней строки.
Список, который тело держит для себя, так закрывается целиком, если ни один
`close` не бросает. `close`, который бросил, обрывает цикл, и источники после
него остаются открытыми.

Отдельная регистрация на каждый источник закрывает остальные и в этом случае.
Стек уборки вызывает каждый колбэк, что бы ни сделал предыдущий. Ошибка одного
уходит в `onError` и по умолчанию дальше в зону, как описано в разделе
[«Порядок уборки и поздние результаты»](cleanup.md#порядок-уборки-и-поздние-результаты)
страницы об уборке. Цикл регистраций встаёт на место `try`, следующей же
строкой:

```dart
final sources = await ctx.runAll(branches);
for (final source in sources) {
  ctx.onDispose(source.close);
}
await ctx.join(() => writeArchive(sources));
```

### Список, который тело отдаёт

```dart
final exported = Job.deferred<List<Source>>((ctx) async {
  final sources = await ctx.runAll(branches);
  try {
    await ctx.join(() => writeArchive(sources));
  } on Object {
    for (final source in sources) {
      source.close();
    }
    rethrow;
  }
  return sources;
});
```

Эта ветка пишет архив, а потом возвращает источники открытыми, чтобы вызывающий
работал с ними. `finally` закрыл бы их и при успехе, поэтому закрытие
переезжает в `catch`. Он покрывает каждую ошибку тела и ничего после него,
а возвращённый список всё ещё может не дойти ни до кого. Пусть `exported` стоит
веткой в группе `ctx.runAll`, и соседка падает уже после того, как тело
вернулось. Группа отменяет ветку, как описано в разделе
[«Что группа отдаёт обратно»](#что-группа-отдаёт-обратно), и до вызывающего
список не доходит. Тело вышло из `try` задолго до этого, и источники остаются
открытыми.

`ctx.onDiscard` выполняется ровно тогда, когда ветка кончается не `Done`: она
упала или её остановила группа. Поэтому он закрывает список и в этом случае,
а когда список доходит, не мешает. Каждый источник получает свою регистрацию,
как в разделе выше:

```dart
final exported = Job.deferred<List<Source>>((ctx) async {
  final sources = await ctx.runAll(branches);
  for (final source in sources) {
    ctx.onDiscard(source.close);
  }
  await ctx.join(() => writeArchive(sources));
  return sources;
});
```

Регистрации ставятся следующей же строкой, раньше всего, что может бросить.
Ошибка или отмена выше них оставила бы список открытым, как в первой попытке.

## Чего `runAll` не обещает

Ветка, тело которой вернуло значение, ещё не кончилась: она ждёт остальную
группу, как показывает раздел
[«Ветки, которые ждут друг друга»](#ветки-которые-ждут-друг-друга). Трёх вещей,
которых можно ждать, не происходит:

| Чего можно ждать | Что происходит |
| --- | --- |
| Ветка, которую группа останавливает, прекращает работу | Прекращается только ожидание. Ветка, ждущая через `ctx.abandonable`, кончается, а операция за ней доигрывает. Чтобы остановилась сама работа, передайте ей отмену через `ctx.onCancel` и дождитесь её через `ctx.join`. Ветка, созданная с `cancellable: false`, отвергает остановку, и группа её дожидается |
| Детей упавшей ветки отменяют | Они доигрывают. Провал никогда не переходит к детям, и группа ждёт их, как и всё остальное |
| У ветки, тело которой вернуло значение, есть исход | Пока группа не решила, её `outcome` равен `null`, а `isCancelled` равен `false`. Она ещё может кончиться `Cancelled`: когда другая ветка кончается без значения, группа отменяет её причиной `SiblingCancelReason`, и `isCancelled` становится `true` |

Когда группа отдала список, решение окончательно. Каждая ветка кончается `Done`
с тем значением, которое отдала. Отмену, которая застаёт ветку, пока та ещё
разматывается, ветка отвергает, и каскад от родителя тоже.
