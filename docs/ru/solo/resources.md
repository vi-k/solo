# Ресурсы и освобождение

`Job`, которая что-то взяла — хэндл базы, подписку, блокировку, временный
файл, — обязана это вернуть, а отмена приходит на `await`, а не между
операторами. Освобождение регистрируется в контексте, и выбранный метод решает,
кто освобождает ресурс и когда:

```dart
(ctx) async {
  // Создано здесь, на месте: между двумя строками ничто не приходит.
  final sub = device.events.listen(onEvent);
  ctx.onDispose(sub.cancel);

  // Получено вызовом: освобождение едет на вызове, а не строкой ниже.
  final db = await ctx.join(Database.open, dispose: (db) => db.close());

  // Уходит с результатом, поэтому освобождается, только если никому не дошло.
  final file = await ctx.join(openTemp, discard: (file) => file.delete());

  // Передано состоянию, и дальше владеет им оно.
  ctx
    ..check()
    ..disown(db)
    ..emit(Ready(db));
}
```

| Метод | Что и когда освобождает |
| --- | --- |
| `dispose:` у `wait` или `join` | значение этого вызова, при любом исходе |
| `discard:` у `wait` или `join` | значение этого вызова, и только если оно никому не дошло |
| `ctx.onDispose(callback)` | то, что закрывает колбэк, при любом исходе |
| `ctx.onDiscard(callback)` | то, что закрывает колбэк, если `Job` ничего не передала |
| `ctx.disown(value)` | ничего — снимает регистрацию, сделанную `wait` или `join` |

Четыре раздела ниже открываются версией, к которой ведёт этот словарь, — метод,
чьё имя совпадает с требованием, или регистрация, записанная там, где она лучше
читается, — и говорят, что эта версия делает вместо того, что от неё ждали. Где
следующая версия это чинит и приносит собственный изъян, она стоит второй
попыткой. Работающая версия идёт под своим заголовком. `Database`, `Idle`,
`Loaded(rows)` и `Ready(db)` относятся к модели этого приложения.

## Получение ресурса вызовом

`Job` открывает базу, читает строки и публикует их. Отменённая в любой момент,
она не должна оставить открытую базу.

### Первая попытка

```dart
Job<void> load() => run<Idle, void>(
      key: 'load',
      (ctx) async {
        final db = await ctx.join(Database.open);
        ctx.onDispose(db.close);

        final rows = await ctx.join(db.readAll);
        ctx.emit(Loaded(rows));
      },
    );
```

`onDispose` — метод для ресурса, который `Job` освобождает при любом исходе,
а строка под получением — место, где он лучше всего читается. Эти две строки —
один шаг для читателя, но два для движка, и отмена помещается между ними.

Отмените эту `Job`, пока `Database.open` в полёте. `join` остаётся с вызовом,
как и должен, открытие доходит до конца, и тогда `join` бросает `Cancelled`
вместо значения, а до строки ниже тело не доходит. База открыта, единственная
ссылка на неё ушла вместе с броском, а стек уборки пуст: в этой `Job` никто
не знает, что база вообще есть.

### Освобождение едет на вызове

```dart
Job<void> load() => run<Idle, void>(
      key: 'load',
      (ctx) async {
        final db = await ctx.join(
          Database.open,
          dispose: (db) => db.close(),
        );

        final rows = await ctx.join(db.readAll);
        ctx.emit(Loaded(rows));
      },
    );
```

`wait` и `join` принимают колбэк `dispose` для ресурса, который принадлежит
`Job`, и правило тут одно: значение, не дошедшее до тела, освобождается
на месте; дошедшее ложится на стек уборки и освобождается, когда `Job`
заканчивается. Здесь база принадлежит операции загрузки, а состоянием
контроллера становятся только её строки, поэтому `dispose` закрывает её при
успехе, при ошибке и при отмене — в том числе при той отмене, которая не даёт
значению дойти до тела.

`join` дожидается этого освобождения до того, как бросить, поэтому следующая
`Job` в очереди стартует с уже закрытой базой. Регистрируйте каждое
освобождение один раз: добавление `ctx.onDispose(db.close)` в это тело
закрыло бы одну базу дважды.

У ресурса, который тело создаёт само, такого зазора нет: между созданием
и регистрацией освобождения нет `await` — `ctx.onDispose(sub.cancel)` стоит
прямо под `listen`. Эта регистрация возвращает функцию, которую можно сохранить
как `removeDisposer`, чтобы снять регистрацию, не вызывая колбэк.

Ничто не мешает и такому созданию поехать на вызове:

```dart
final sub = await ctx.join(
  () => device.events.listen(onEvent),
  dispose: (sub) => sub.cancel(),
);
```

`wait` и `join` принимают действие, которое возвращает без ожидания, поэтому
синхронное создание регистрируется на вызове, как и любое другое. По сравнению
с парой `listen` и `onDispose` под ним это даёт контрольную точку, которую
вызов делает перед действием: если отмена уже стоит, подписки не возникает
вовсе, тогда как та пара её создаёт и отменяет во время уборки.

## Возврат ресурса вызывающему

Теперь база — результат, а не средство: `open` ниже открывает её и возвращает,
и с этого момента ею владеет тот, кто взял значение — `await open().value`.

### Первая попытка

```dart
SoloJob<Database> open() => run<Idle, Database>(
      key: _Op.open,
      (ctx) async {
        final db = await ctx.join(
          Database.open,
          dispose: (db) => db.close(),
        );
        await ctx.run(job<Idle, void>((child) => child.join(db.readAll)));
        return db;
      },
    );
```

Базу всё ещё освобождает эта `Job`, если она упадёт, поэтому колбэк, который
срабатывает при любом исходе, выглядит безопасным. Успех — тоже исход. Тело
возвращает хэндл, уборка выполняется до доставки исхода, и `dispose` закрывает
базу прямо там — `await` вызывающего завершается хэндлом, закрытым мгновением
раньше.

Тесты на отмену об этом молчат. На отменённом пути эта `Job` делает ровно то,
что должна; закрытую базу отдаёт успешный путь, и видит это только тест,
который потом пользуется результатом.

### `discard` — для значения, которое уходит

```dart
SoloJob<Database> open() => run<Idle, Database>(
      key: _Op.open,
      (ctx) async {
        final db = await ctx.join(
          Database.open,
          discard: (db) => db.close(),
        );
        await ctx.run(job<Idle, void>((child) => child.join(db.readAll)));
        return db;
      },
    );
```

`discard` срабатывает, только когда `Job` заканчивается, не передав своё
значение: отменённой или упавшей. Соответствующий метод регистрации называется
`ctx.onDiscard`. Ожидающий вызов принимает либо `dispose`, либо `discard`,
и никогда оба. Всё, что `Job` оставляет себе — блокировка, временный файл,
подписка, — остаётся с `dispose`, иначе течёт на том пути, куда не смотрит
ни один тест на отмену.

Ребёнок выше и показывает, чем это различение окупается: тело вернуло базу,
но `Job` ещё не завершилась. Если отмена приходит во время этого ожидания,
вызывающий получает `Cancelled` вместо ресурса, и `discard` его закрывает.

Регистрацию решает исход той `Job`, которая её сделала, и со значением она
не уезжает. Тот, кто взял базу, владеет ею с этого момента и регистрирует
освобождение сам: родитель, который берёт её через
`ctx.run(child, discard: ...)`, регистрирует на вызове, а почему это не может
подождать до строки ниже, сказано в `doc/children.md`.

## Передача ресурса состоянию

Базу держит сам экран: `Ready(db)` становится состоянием, а контроллер
закрывает её, когда закрывается сам.

### Первая попытка

```dart
final db = await ctx.join(
  Database.open,
  dispose: (db) => db.close(),
);
ctx.emit(Ready(db));
```

Запись проходит, экран показывает `Ready`. Потом тело возвращается, `Job`
разматывает стек уборки, и `dispose` закрывает базу, которую держит экран.
Объект состояния при этом не меняется: у экрана остаётся хэндл, выглядящий
ровно как прежде, а отказ всплывает на первом чтении из него.

### Вторая попытка

```dart
ctx
  ..disown(db)
  ..emit(Ready(db));
```

`disown` снимает регистрацию, сделанную вызовом, и `Job` больше не закрывает
то, что собирается отдать. Снимает он её и до того, как хоть что-то проверит,
состоится ли запись вообще.

`emit` — контрольная точка: для `Job`, принявшей отмену, он бросает `Cancelled`
вместо записи. Отмена, приходящая в тело между защищённым шагом и этим
каскадом, — дело обычное: `uncancellable` держит её, и выходит она
на контрольной точке после секции. Здесь такая точка — `emit`, и к моменту
броска регистрации уже нет: состоянию база не досталась, стек уборки о ней
больше не знает, и не закрывает её никто.

### `check`, `disown`, `emit`

```dart
ctx
  ..check()
  ..disown(db)
  ..emit(Ready(db));
```

Эти вызовы синхронны, поэтому между ними ничто не приходит. `check` бросает
первым, если `Job` отменена или её правила больше не держатся, — и база ещё
зарегистрирована: уборка её закроет. Если `emit` записал состояние и затем
бросил, потому что `Job` отменил синхронный слушатель, базой уже владеет
состояние, а стек уборки — уже нет. В обоих случаях владелец остаётся ровно
один.

Для асинхронной передачи она и `disown` идут внутрь одной ожидаемой секции
`uncancellable`:

```dart
await ctx.uncancellable(() async {
  await archive.take(file);
  ctx.disown(file);
});
```

Для самой передачи внутри секции берите обычный `await`. Контрольная точка
между передачей и `disown` — а `ctx.join(() => archive.take(file))` это она —
бросает после того, как владение сменилось, и до того, как снята регистрация,
и уборка удаляет файл, который держит архив.

## Когда случится освобождение

`Job` пишет временный файл и удаляет его при любом исходе. Следующая `Job`
в очереди не должна его застать, и `close()` к своему возврату — тоже.

### Первая попытка

```dart
// Брошен при отмене: файл может появиться уже после конца Job. Он всё
// равно будет удалён, но этого никто не ждёт.
await ctx.wait(openTemp, dispose: (file) => file.delete());
```

Ожидающий метод решает, когда случится освобождение, а не случится ли оно.
`wait` отпускает вызов в момент принятия отмены: `Job` заканчивается, очередь
идёт дальше, и следующая `Job` стартует, пока `openTemp` ещё работает. Файл
появляется после этого, а удаление идёт следом — поздно и в одиночку,
и ни того, ни другого никто не ждёт. Поздняя ошибка вызова или самого колбэка
уходит в обработчик ошибок контроллера.

### Ожидание, которое остаётся с вызовом

```dart
// Удалён до старта следующей Job и до возврата из close().
await ctx.join(openTemp, dispose: (file) => file.delete());
```

`join` дожидается вызова, освобождает переданное ему значение и только потом
бросает. Удаление входит в то, чего ждёт очередь, поэтому следующая `Job`
не стартует против файла, который эта ещё удаляет. Берите `join`, когда
освобождение ресурса должно предшествовать следующей `Job` или закрытию
контроллера.

## Порядок уборки и поздние результаты

| Шаг | Что делает `Job` |
| --- | --- |
| Дети | ждёт завершения каждого ребёнка |
| Стек уборки | разматывает его с последней регистрации, ожидая каждый колбэк |
| Вторая волна | выполняет `discard`, который отмена сделала нужным задним числом |
| Конец | итоговый обработчик состояния, доставка исхода, освобождение очереди |

Обычный `try`/`finally` остаётся полезен для локальной работы;
зарегистрированная уборка вдобавок охватывает время после возврата из тела
и до завершения его детей.

Отмена может прийти после возврата из тела, в том числе во время уборки.
Регистрация `discard`, пропущенная на успешном пути, выполняется тогда второй
волной — после тех колбэков, которые обработали раньше неё, а не в строгом
обратном порядке регистрации.

Ошибки уборки уходят в обработчик ошибок контроллера и наблюдателям, а без
установленного обработчика ошибка доходит до зоны. `Cancelled`, брошенный
уборкой, идёт тем же маршрутом в обработчик и наблюдателям и не доходит до зоны
никогда: отмена — чьё-то решение, а не отказ. Исход `Job` не меняет ни то,
ни другое — упавшая уборка оставляет `Done` там, где был `Done`.

Никогда не ждите из уборки `done`, `value` или `cancel()` своей же `Job`
и не ждите более позднюю `Job` той же очереди: все они зависят от окончания
текущей уборки, и такое ожидание не кончается.
