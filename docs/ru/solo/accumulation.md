# Накопление событий до запуска задачи

Несколько событий могут разделять одну задачу в очереди. `collect` сохраняет
каждое событие в списке, `accumulate` объединяет его с одним накопленным
значением. У обеих три аргумента типа, `<W, E, T>`: рабочий тип `W`, как
у `run`, тип события `E` и тип результата `T`, а возвращают обе накопитель,
`SoloAccumulator<E, T>`. Создайте его один раз в контроллере, затем вызывайте
`add(event)` из публичных методов контроллера.

Накопитель владеет входными данными ожидающей задачи. Добавление события
не запускает обработчик и не меняет состояние контроллера. События, которые
разделяют одну задачу, составляют группу, и группа принимает события, пока
не запечатана: её запечатывает истечение окна debounce, а при throttle или
вовсе без `timing` тот момент, когда очередь берёт задачу на выполнение.
Обработчик получает этот вход и обычный `SoloContext<S, W>`; состояние он
меняет через `ctx.emit`.

## Рецепты

Четыре контроллера, и у каждого событий приходит больше, чем есть работы,
которую стоит делать. Разница в том, что остаётся: последнее значение, слияние
всех или каждое событие в списке.

Каждый рецепт открывается той версией, к которой ведёт словарь самого
контроллера: так пишут, когда берут `run` и на этом останавливаются. Там, где
очевидная починка стоит того, чтобы её увидеть отдельно, за первой попыткой
идёт вторая. Под каждой версией стоит то, к чему приводит сценарий над ней: что
доходит до сервера или устройства и каким остаётся состояние контроллера.

### Поиск, который стреляет на каждый символ

Строка поиска спрашивает сервер, пока пользователь печатает. Каждое нажатие
становится событием, и запроса стоит только последнее.

```dart
import 'package:solo/solo.dart';

class SearchState {
  final List<String> results;

  const SearchState.idle() : results = const [];

  const SearchState.results(this.results);
}

abstract interface class SearchApi {
  Future<List<String>> search(String text);
}
```

#### Первая попытка

Словарь контроллера говорит `run`, значит, на каждое нажатие заводится задача:

```dart
final class QueuedSearch extends Solo<SearchState> {
  final SearchApi api;

  QueuedSearch(this.api) : super(const SearchState.idle());

  Job<void> query(String text) => run<SearchState, void>(
        key: 'query',
        (ctx) async {
          final results = await ctx.abandonable(() => api.search(text));
          ctx.emit(SearchState.results(results));
        },
      );
}
```

Набирается `solo`, по символу каждые 50 мс, сервер отвечает за 100 мс:

```text
the server was asked 4 times: [s, so, sol, solo]
at 100 ms the screen shows [hits for s]
at 200 ms the screen shows [hits for so]
at 300 ms the screen shows [hits for sol]
at 400 ms the screen shows [hits for solo]
```

Очередь делает ровно то, что обещала, и в этом беда. Каждый запрос ждёт
предыдущего, поэтому ответ на `solo` приходит через 400 мс после первого
нажатия: четыре обращения вместо одного. А по дороге экран отвечает на три
слова, которые пользователь уже дописал.

#### Вторая попытка

`Policy.restart` отменяет работающую задачу, когда приходит следующая; политики
самой очереди описаны в разделе
[«Очередь и политики»](jobs.md#очередь-и-политики) страницы о задачах. Меняется
только метод:

```dart
Job<void> query(String text) => run<SearchState, void>(
      key: 'query',
      policy: Policy.restart,
      (ctx) async {
        final results = await ctx.abandonable(() => api.search(text));
        ctx.emit(SearchState.results(results));
      },
    );
```

```text
the server was asked 4 times: [s, so, sol, solo]
at 250 ms the screen shows [hits for solo]
```

Устаревшее до экрана больше не доходит, и ответ приходит раньше: запросы теперь
идут внахлёст, а не в очередь. Сервер при этом спросили те же четыре раза:
отмена задачи не отзывает то, что она уже отправила. `ctx.join` вместо
`ctx.abandonable` их тоже не отзовёт: он держит единственный слот выполнения
контроллера до ответа, и сколько запросов уйдёт, зависит от того, насколько
сервер быстрее набора.

#### Накопитель

```dart
final class Search extends Solo<SearchState> {
  final SearchApi api;
  late final _queries = accumulate<SearchState, String, void>(
    (ctx, text) async {
      final results = await ctx.abandonable(() => api.search(text));
      ctx.emit(SearchState.results(results));
    },
    merge: (accumulated, incoming) => incoming,
    timing: AccumulationTiming.debounce(const Duration(milliseconds: 300)),
    policy: AccumulationPolicy.join,
    key: 'query',
  );

  Search(this.api) : super(const SearchState.idle());

  Job<void> query(String text) => _queries.add(text);
}
```

```text
the server was asked 1 time: [solo]
at 550 ms the screen shows [hits for solo]
```

Один запрос. `merge` берёт пришедший текст и выбрасывает прежний, поэтому
группа несёт последний запрос; debounce держит группу, пока набор не замрёт
на 300 мс. Эта пауза и есть цена: ответ приходит позже, чем у обеих попыток
выше, и он единственный отправленный. `policy` выписывает умолчание, `join`;
что решает политика, сказано в разделе
[«Выбор места присоединения событий»](#выбор-места-присоединения-событий).

Уже начавшаяся группа завершается до старта следующей, а возвращённая `Job`
предоставляет исход и отмену, как и другие `Job`. Завершается при этом задача:
отмена кончает ожидание, а не запрос, который задача уже отправила, поэтому тот
может быть ещё в пути, когда стартует следующая группа.

### Настройки, сохраняемые на каждом щелчке

На экране настроек есть переключатель, выбор темы и выбор языка. Каждое
изменение становится событием, а серверу нужна одна запись, а не три.

`SettingsPatch` описывает, какие настройки изменить. Новое значение поля
заменяет прежнее; поля, которых в новом патче нет, сохраняются. В этом примере
сами настройки не могут быть `null`, поэтому `null` в поле патча означает «это
не трогать». Для nullable-настройки, которую можно очистить, понадобится
отдельно выражать, есть ли в патче значение.

```dart
import 'package:solo/solo.dart';

class Settings {
  final bool notifications;
  final String theme;
  final String language;

  const Settings({
    required this.notifications,
    required this.theme,
    required this.language,
  });
}

class SettingsPatch {
  final bool? notifications;
  final String? theme;
  final String? language;

  const SettingsPatch({
    this.notifications,
    this.theme,
    this.language,
  });

  SettingsPatch merge(SettingsPatch incoming) => SettingsPatch(
        notifications: incoming.notifications ?? notifications,
        theme: incoming.theme ?? theme,
        language: incoming.language ?? language,
      );

  Settings apply(Settings current) => Settings(
        notifications: notifications ?? current.notifications,
        theme: theme ?? current.theme,
        language: language ?? current.language,
      );
}

abstract interface class SettingsApi {
  Future<void> save(Settings settings);

  Future<Settings> load();
}
```

#### Первая попытка

Каждое изменение становится задачей, и задача пишет:

```dart
final class EagerSettingsController extends Solo<Settings> {
  final SettingsApi _api;

  EagerSettingsController(this._api, Settings initial) : super(initial);

  Job<void> update(SettingsPatch patch) => run<Settings, void>(
        key: 'settings',
        (ctx) async {
          final next = patch.apply(ctx.state);
          await ctx.join(() => _api.save(next));
          ctx.emit(next);
        },
      );
}
```

Переключатель, потом тема, потом язык, с промежутком в 20 мс, сервер пишет 100
мс:

```text
the server was written to 3 times:
  notifications: true, theme: light, language: en
  notifications: true, theme: dark, language: en
  notifications: true, theme: dark, language: ru
the screen ends up with notifications: true, theme: dark, language: ru
```

К концу экран прав, а платит за это сеть: три обращения за один заход
в настройки, и первые два публикуют настройки, от которых пользователь уже
ушёл. Другое устройство, прочитавшее между ними, найдёт светлую тему, хотя
хозяин уже выбрал тёмную.

#### Вторая попытка

`Policy.restart` убирает из очереди ожидающие записи с тем же ключом и просит
остановиться ту, что идёт. Меняется только метод:

```dart
Job<void> update(SettingsPatch patch) => run<Settings, void>(
      key: 'settings',
      policy: Policy.restart,
      (ctx) async {
        final next = patch.apply(ctx.state);
        await ctx.join(() => _api.save(next));
        ctx.emit(next);
      },
    );
```

```text
the server was written to 2 times:
  notifications: true, theme: light, language: en
  notifications: false, theme: light, language: ru
the screen ends up with notifications: false, theme: light, language: ru
```

Переключатель вернулся в положение «выключено», а тема снова светлая. Каждая
задача читает состояние, с которым стартовала, и пишет целый `Settings`,
поэтому задача, заменившая другую, не наследует того, что та собиралась
изменить: она переписывает это из состояния, где того изменения не было. Первая
из двух записей и есть та, которую `restart` просил остановиться, и она всё
равно ушла: `ctx.join` ждёт вызов, который сам же сделал, а `_api.save` запроса
на отмену не слышит. Два пользовательских изменения из трёх исчезли,
и с сервера, и с экрана, и при этом ничего не упало.

#### Накопитель

```dart
final class SettingsController extends Solo<Settings> {
  final SettingsApi _api;
  late final _updates = accumulate<Settings, SettingsPatch, void>(
    (ctx, patch) async {
      final next = patch.apply(ctx.state);
      await ctx.join(() => _api.save(next));
      ctx.emit(next);
    },
    merge: (accumulated, incoming) => accumulated.merge(incoming),
    key: 'settings',
    timing: AccumulationTiming.debounce(const Duration(milliseconds: 200)),
  );

  SettingsController(this._api, Settings initial) : super(initial);

  Job<void> update(SettingsPatch patch) => _updates.add(patch);

  Job<void> reload() => run<Settings, void>(
        key: 'reload',
        (ctx) async => ctx.emit(await ctx.abandonable(_api.load)),
      );
}
```

```text
the server was written to 1 time:
  notifications: true, theme: dark, language: ru
the screen ends up with notifications: true, theme: dark, language: ru
```

`merge` объединяет патчи, а не выбирает между ними, поэтому ничего
из сделанного пользователем не пропадает, а группа несёт все три изменения
в одну запись.

Экран ещё и читает настройки с сервера, и `reload` здесь обычная задача,
а не накопленная. Этот накопитель берёт политику по умолчанию, `join`, поэтому
`reload`, вставший в очередь между двумя щелчками, границей не становится:
щелчки остаются одной группой и одной записью, чем бы очередь ни была занята.
Когда вместо неё брать `adjacent`, сказано в разделе
[«Выбор места присоединения событий»](#выбор-места-присоединения-событий).

Первое событие становится накопленным значением без вызова `merge`. Каждое
следующее синхронно вызывает `merge(accumulated, incoming)` из `add`, до старта
обработчика. Сохраняется только результат.

Три вызова возвращают одну задачу, и дождаться её один раз значит дождаться
всех трёх:

```dart
Future<void> changeSettings(SettingsApi api, Settings initial) async {
  final controller = SettingsController(api, initial);
  try {
    final first = controller.update(
      const SettingsPatch(notifications: true),
    );
    final second = controller.update(const SettingsPatch(theme: 'dark'));
    final third = controller.update(const SettingsPatch(language: 'ru'));

    print(identical(first, second) && identical(second, third));
    print(await first.done);
  } finally {
    await controller.close();
  }
}
```

```text
true
Done(null)
```

После 200 мс без новых изменений обработчик сохраняет один снимок со всеми
тремя, а когда запись закончилась, отдаёт его в состояние. До запуска
обработчика состояние остаётся исходным, и за время паузы могут выполниться
другие готовые `Job`. `.done` не бросает: его ожидание возвращает `Outcome`,
будь то `Done`, `Failed` или `Cancelled`.

Если сохранение падает, состояние не меняется, а группа завершается провалом.
Повторять ли неудавшиеся изменения, решает вызывающий; более поздний
независимый патч не включает их автоматически. Пример предполагает одного
писателя и future API, которая завершается при фактическом окончании записи.
`ctx.join` удерживает слот выполнения до её завершения, в том числе после
отмены, и этим держится то, что следующая запись не начнётся поверх этой. Один
клиентский таймаут не доказывает, что сервер перестал записывать: `save`,
завершающая свою future по таймауту, возвращает слот, пока сервер ещё пишет,
следующая группа отправляет свою запись поверх незакончившейся, и какая из двух
уцелеет, решает уже сервер, а не очередь. Экран и сервер могут разойтись
насовсем. Отмена также может помешать финальному `emit` после того, как сервер
уже принял запись.

Срок, заданный аккумулятору через `timeout`, работает как отмена, а не как
клиентский таймаут: `ctx.join` держит слот, пока `save` не завершится, поэтому
следующая запись по-прежнему ждёт конца этой. Срок обходится в финальный
`emit`. Группа, у которой вышел срок, отменяется, пока сервер ещё пишет,
кончается `Cancelled(timeout)`, когда запись сохранена, и до своего `emit`
не доходит: состояние сохраняет старые настройки, и следующая группа
накладывает свой патч на них и записывает старые значения поверх изменения.

### Один запрос на строку журнала

Приложение пишет записи журнала по одной, а сервер принимает их пачками. Дойти
должна каждая, и в том порядке, в каком её написали.

```dart
import 'package:solo/solo.dart';

class LogEntry {
  final String message;

  const LogEntry(this.message);
}

abstract interface class LogApi {
  Future<void> send(List<LogEntry> entries);
}
```

#### Первая попытка

Каждая строка становится задачей, и задача отправляет:

```dart
final class EagerLogController extends Solo<int> {
  final LogApi _api;

  EagerLogController(this._api) : super(0);

  Job<void> logEvent(LogEntry entry) => run<int, void>(
        key: 'logs',
        (ctx) async {
          await ctx.join(() => _api.send([entry]));
          ctx.emit(ctx.state + 1);
        },
      );
}
```

Три строки, написанные подряд кодом, который обрабатывает переход между
экранами, и ещё одна через две секунды; сервер тратит на запрос 100 мс:

```text
the server got 4 requests:
  [opened] at 0 ms
  [loaded] at 100 ms
  [shown] at 200 ms
  [tapped] at 2000 ms
the three lines of the transition cost 3 of them
the counter says 4
```

Четыре строки, четыре запроса. Порядок держит очередь, и она же заставляет их
ждать: каждая отправка начинается, только когда закончилась предыдущая, поэтому
всплеск логирования превращается в цепочку обращений, которая переживёт
породившее её событие.

#### Накопитель

`collect` дописывает события в приватный список и отдаёт обработчику
неизменяемый снимок, снятый в момент запечатывания группы: каждое событие,
в том порядке, в каком его написали. Снимок копирует список, но не сами
события, поэтому событие, изменённое после `add`, уйдёт изменённым. Берите
неизменяемые объекты.

```dart
final class LogController extends Solo<int> {
  final LogApi _api;
  late final _logs = collect<int, LogEntry, void>(
    (ctx, entries) async {
      await ctx.join(() => _api.send(entries));
      ctx.emit(ctx.state + entries.length);
    },
    key: 'logs',
    policy: AccumulationPolicy.join,
    timing: AccumulationTiming.throttle(const Duration(seconds: 1)),
  );

  LogController(this._api) : super(0);

  Job<void> logEvent(LogEntry entry) => _logs.add(entry);
}
```

```text
the server got 2 requests:
  [opened, loaded, shown] at 0 ms
  [tapped] at 2000 ms
the three lines of the transition cost 1 of them
the counter says 4
```

Три строки перехода едут вместе. Четвёртая написана, когда интервал throttle
уже прошёл, поэтому она уходит сразу и одна, а не ждёт компании: интервал
задаёт нижнюю границу частоты, а не добавляет задержку каждой записи.

Буфер, который вы держите сами, тоже собрал бы их в пачку. `collect` добавляет
к этому то, что буфер и есть вход задачи: события запечатываются в группу,
которую берёт очередь, вызывающий получает ту же `Job`, что и все добавлявшие
в эту группу, а `close()` сбрасывает группу вместо того, чтобы оставить после
себя список и таймер.

Состояние этого контроллера считает записи, отправка которых завершилась,
а обработчик дошёл до `emit`. Рабочий тип `int` и есть всё это состояние,
поэтому обработчик стартует при любом счёте и читает его как `ctx.state`.
Раздел
[«Выбор места присоединения событий»](#выбор-места-присоединения-событий)
объясняет, почему умолчанием выбрана политика `join`, которую этот пример
выписывает явно, а раздел
[«Выбор момента готовности группы»](#выбор-момента-готовности-группы) говорит,
от чего отсчитывается интервал throttle и чего немедленный старт стоит
всплеску, который не уместился в один проход.

Сбор записей не гарантирует доставку. Неудачная отправка, отмена группы или
обычный `close()` могут оставить их неотправленными; `close()`
с `SoloCloseMode.drain` отправляет то, что уже стоит в очереди. Надёжное
хранение и повторы требуют протокола приложения сверх этого накопителя.

### Команды, где важна только последняя

Плеер вешает воспроизведение и паузу на одну кнопку, а пользователь жмёт её
быстрее, чем отвечает устройство.

```dart
import 'package:solo/solo.dart';

enum Command { resume, pause }

sealed class Playback {
  const Playback();
}

final class Playing extends Playback {
  const Playing();
}

final class Paused extends Playback {
  const Paused();
}

abstract interface class PlayerDevice {
  Future<void> resume();

  Future<void> pause();
}
```

#### Первая попытка

Каждая команда идёт отдельной задачей:

```dart
final class QueuedPlayer extends Solo<Playback> {
  final PlayerDevice device;

  QueuedPlayer(this.device) : super(const Paused());

  Job<void> resume() => run<Playback, void>(
        key: Command.resume,
        (ctx) async {
          await ctx.join(device.resume);
          ctx.emit(const Playing());
        },
      );

  Job<void> pause() => run<Playback, void>(
        key: Command.pause,
        (ctx) async {
          await ctx.join(device.pause);
          ctx.emit(const Paused());
        },
      );
}
```

Три нажатия подряд, воспроизведение, пауза и снова воспроизведение,
на устройстве, которому нужно 100 мс на исполнение:

```text
the device heard 3 commands:
  resume at 0 ms
  pause at 100 ms
  resume at 200 ms
the button gave back a job for every tap
the player settles Playing at 300 ms
```

Плеер оказывается там, куда просило последнее нажатие, но приходит туда длинной
дорогой: играет, останавливается и играет снова, а эту остановку посередине
пользователь слышит. Три обращения к устройству и 300 мс до того, как всё
уляжется.

#### Накопитель

Очередь, в которой лежат `resume`, а за ним `pause`, вот-вот сделает две
взаимно уничтожающие вещи, а пришедший сейчас `resume` делает бессмысленной всю
пару: её итог тот же, к которому пришёл бы один `resume`. `merge` берёт
пришедшую команду и выбрасывает ту, что была:

```dart
final class Player extends Solo<Playback> {
  final PlayerDevice device;

  late final _transport = accumulate<Playback, Command, void>(
    key: 'transport',
    policy: AccumulationPolicy.adjacent,
    merge: (accumulated, incoming) => incoming,
    (ctx, command) async {
      switch (command) {
        case Command.resume:
          await ctx.join(device.resume);
          ctx.emit(const Playing());
        case Command.pause:
          await ctx.join(device.pause);
          ctx.emit(const Paused());
      }
    },
  );

  Player(this.device) : super(const Paused());

  Job<void> resume() => _transport.add(Command.resume);

  Job<void> pause() => _transport.add(Command.pause);
}
```

```text
the device heard 1 command:
  resume at 0 ms
the button gave back one job
the player settles Playing at 100 ms
```

Три вызова подряд оставляют в очереди одну задачу, и все три возвращают один
и тот же хэндл. Устройству сказано включить воспроизведение один раз. Ничего
не ставилось в очередь и не отменялось по дороге.

Это работает потому, что команды абсолютны: каждая говорит, каким должно стать
итоговое состояние, поэтому ответом служит последняя. Команды, которые
надстраиваются друг над другом («ещё десять секунд вперёд»), сливаются
сложением, а не заменой.

`adjacent` присоединяет к группе только в хвосте очереди, поэтому задача
другого рода, добавленная между двумя командами, становится границей, и слияние
на ней прекращается. Именно это сохраняет порядок с остальной работой, и потому
рецепт называет политику, а не берёт умолчание: `join` присоединяет к группе
там, где она стоит, а здесь это выбросило бы `resume`, который нажал
пользователь, и оставило бы устройству один `pause`.

#### Когда это всё-таки разные задачи

Там, где `resume` и `pause` правда разные операции, а не одна команда
со значением, они обычные задачи со своими ключами, и `Policy.replace`
не поможет: она убирает задачи с тем же ключом, а общего ключа у этих двух нет.
Убирает их собственная очередь контроллера:

```dart
Job<void> resume() {
  queue.removeWhere(
    (job) => job.key == Command.resume || job.key == Command.pause,
  );

  return run<Playback, void>(key: Command.resume, (ctx) async {
    await ctx.join(device.resume);
    ctx.emit(const Playing());
  });
}
```

Удалить и добавить значит повторить форму `AccumulationPolicy.replace`: команда
оказывается в хвосте, за всем, что встало между. Разница в хэндле: этим путём
приходится строить новую задачу, а накопитель переносит ту, что у него уже
есть. Очередь умеет удалить задачу и добавить задачу, но не умеет изменить то,
что сделает уже стоящая, поэтому место, которое сохраняет
`AccumulationPolicy.join`, этим путём не получить: для него команду надо
держать вне задачи, там, откуда задача прочтёт её при старте, и именно это
накопитель делает для своей задачи.

Работающую задачу очередь не трогает никогда: уже начавшийся `pause` доработает
до конца, что бы за ним ни убрали. Чтобы отменить и работающую задачу, нужен
`cancelAll()`, который чистит всю очередь и отменяет текущую задачу, или общий
ключ на обе команды с `Policy.restart`. `removeWhere` пропускает задачи,
созданные с `cancellable: false`, пока не передан `force: true`.

## Справочник

Эти разделы разбирают группировку, порядок выполнения и исходы отдельных
вызовов.

### Выбор момента готовности группы

Обе фабрики принимают необязательный `timing`. Настройка определяет, когда
группе можно стартовать; `collect` сохраняет каждое принятое событие,
а `accumulate` сохраняет результат своей `merge`. Например,
`merge: (accumulated, incoming) => incoming` сохраняет последнее значение.

| | `debounce(duration)` | `throttle(duration)` | `throttle(duration, startAtOnce: false)` |
| --- | --- | --- | --- |
| Первая группа готова | через `duration` без новых событий | сразу | через `duration` |
| Добавление | перезапускает таймер | не продлевает таймер | не продлевает таймер |
| Ожидание отсчитывается от | последнего принятого события | прошлого фактического старта | прошлого старта или появления группы |

`AccumulationTiming.debounce(duration)` ждёт паузы после последнего принятого
события в каждой группе. Каждое добавление перезапускает таймер, даже если
`merge` вернула неизменное значение. При окне 200 мс события на 0, 60 и 120 мс
делают группу готовой на 320 мс. Когда таймер debounce срабатывает, группа
запечатывается, даже если другая `Job` работает. Следующие события создают
новую группу и не меняют запечатанный вход. `collect` делает снимок в этот
момент и больше его не повторяет. Непрерывный вход может удерживать открытую
группу неограниченно долго. Ради этого ожидания debounce и стоит в рецепте
поиска: запрос уходит, когда набор замер. Из-за него же сборщик журнала берёт
throttle, а не debounce: записям, которые должны дойти все, нельзя ждать паузы,
которой может и не быть.

`AccumulationTiming.throttle(duration)` разрешает первый старт сразу, затем
выдерживает не менее `duration` между фактическими стартами групп одного
накопителя. Добавления за этот интервал собираются в открытую группу,
не продлевая таймер. По истечении интервала накопленное готово без нового
события. Группа принимает события, пока очередь не возьмёт её на выполнение.
Интервал, за который событий не было, `Job` не создаёт, и группа следующего
события готова сразу: интервал отсчитывается от прошлого старта и уже истёк.

`startAtOnce: false` отсчитывает интервал и до первой группы. Накопитель,
у которого ничего своего не стоит в очереди и не работает, заводит интервал
в момент появления группы, и группа готова по его истечении, вместе со всем,
что записали тем временем. Этим условием всё и исчерпывается: уже идущий
интервал не перезаводится никогда, а группа, появившаяся рядом с другой группой
того же накопителя, которая ждёт в очереди или работает, интервала не заводит.
Поэтому группу, которая свой интервал отстояла и ждёт только слота выполнения,
позднее событие назад не отодвигает, что бы политика с этим событием
ни сделала. Интервал, прошедший без событий, ничего идущего не оставляет,
и следующая группа отсчитывает целый интервал от собственного появления.

У немедленного старта есть цена, когда ничего не работает. Очередь берёт первую
группу на ближайшей микрозадаче, поэтому всплеск, не уместившийся в один
синхронный проход, разрывается: первое событие уходит одно, а остальные ждут
целый интервал. Три строки рецепта журнала остаются вместе потому, что написаны
за один проход. Вместе остаётся и всплеск, написанный, пока работает какая-то
задача контроллера, сколько бы проходов он ни занял: при throttle группу
запечатывает очередь, когда берёт её на выполнение, а пока эта задача
не кончится, взять её нельзя.

У ожидания есть своя цена. Единственное событие на простаивающем накопителе
задержано на целый интервал, и `close(mode: SoloCloseMode.drain)` ждёт вместе
с ним, а обычный `close()` его выбрасывает. Берите `startAtOnce: false` там,
где частота важнее задержки первого события, и оставляйте умолчание там, где
именно первого события и ждут.

Стартом считается переход к выполнению, до `onStart`. Группа, отклонённая
стартовыми правилами, не расходует интервал throttle; отмена из `onStart`
расходует. При `startAtOnce: false` после отказа у накопителя не остаётся
ничего в очереди, поэтому следующая появившаяся группа отсчитывает свой полный
интервал от собственного появления. Если группа стартовала на 0 мс с интервалом
200 мс, а другая `Job` занимает слот до 500 мс, следующая группа стартует
на 500 мс, а последующая не раньше 700 мс. Если собственный обработчик группы,
дети или уборка длятся дольше интервала, следующая группа может стартовать
сразу после их завершения.

Ожидающие группы видны в `queue.jobs`. Очередь берёт первую готовую `Job`
в порядке списка, пропуская ожидающие группы. Поэтому список может быть
непустым, когда ни одна `Job` не работает. Ожидание времени не занимает слот
выполнения; после старта обработчика очередь ждёт его детей и уборку перед
запуском следующей корневой `Job`.

Без `timing` или при `Duration.zero` группы готовы сразу и таймеров нет, что бы
ни говорил `startAtOnce`. Отрицательная длительность бросает `ArgumentError`.
Общую настройку времени можно передать нескольким накопителям; у каждого свои
группы и интервал throttle. Колбэки таймеров следуют порядку событий Dart:
событие, обработанное до колбэка debounce, может перезапустить таймер; событие
после него относится к новой группе. Занятый цикл событий может задержать
колбэки и старты.

### Выбор места присоединения событий

```dart
// Три вызова подряд: очередь между ними ничего не берёт. Куда ляжет A2,
// решает политика.
final a1 = settings.update(const SettingsPatch(theme: 'dark'));
settings.reload(); // B, обычная отдельная Job
final a2 = settings.update(const SettingsPatch(language: 'ru'));
```

Обе фабрики принимают `AccumulationPolicy`, фиксируемую при создании
накопителя.

| Политика | Очередь после добавлений | Хэндл для A2 |
| --- | --- | --- |
| `adjacent` | `[A1, B, A2]` | Новая задача |
| `replace` | `[B, A(A1 + A2)]` | Существующая задача A1, перенесённая за B |
| `join` (по умолчанию) | `[A(A1 + A2), B]` | Существующая задача A1 |

`adjacent` принимает событие в группу, только если она стоит в хвосте очереди.
`replace` и `join` находят последнюю открытую ожидающую группу того же
накопителя, проходя через другие задачи. Эти задачи остаются в очереди. При
`join` A сохраняет место перед B; `replace` переносит A за B. Выполнение также
зависит от готовности: готовая B может пройти перед A, пока A ждёт своего
времени.

`join` стоит по умолчанию для того, чтобы группа не зависела от того, что ещё
стоит в очереди. Запись, сделанная, пока в очереди ждёт другая задача, всё
равно принадлежит той пачке, которая уже стоит; при `adjacent` она завела бы
вторую группу за этой задачей, а throttle придержал бы её ещё на интервал: два
запроса на записи, сделанные почти одновременно. Одни и те же два события
давали бы то одну группу, то две, смотря чем контроллер был занят в этот
момент, а такого решения не принимал никто. Платит `join` за это границей:
пачка сохраняет своё место впереди задачи, пришедшей между.

Берите `adjacent` там, где эта граница и есть суть: где `merge` выбрасывает то,
что заменяет, и задача, вставшая между двумя событиями, обязана выполниться
между ними, как в рецепте команд, или где такая задача меняет смысл
накопленного.

Политики смотрят на текущую очередь. Если B уже выполнилась, ожидающая A снова
может оказаться хвостом, и следующее событие присоединится к ней при
`adjacent`. Уже раздельные группы задним числом не объединяются. Запечатанная
debounce-группа не подходит ни одной из трёх политик.

`replace` добавляет входящее событие в найденную группу и переносит её задачу
в хвост. Хэндл остаётся тем самым, который получили все добавления в эту
группу, принятые события остаются в ней, а группа, уже стоящая хвостом,
сохраняет своё место. По дороге ничего не отменяется, поэтому ни один колбэк
отмены не выполняется посреди переноса. `Solo.debug`, собственная трасса движка
из раздела [«Логи»](errors.md#логи) страницы об ошибках, печатает
`move <задача> to the tail`; события наблюдателя нет, потому что ни одна задача
не стартовала и не завершилась.

Перенос начинает новое окно debounce и сохраняет интервал throttle накопителя.
Он применим к ожидающей группе, в том числе настроенной с `cancellable: false`:
перенос не удаление, и флагу нечего отклонять. Работающая группа
не переносится: она перестаёт принимать события, когда очередь её забрала.
У обычной политики очереди `Policy.replace` свои правила отмены;
`AccumulationPolicy` объявлен отдельным `enum`.

Возможность объединения определяется идентичностью накопителя. Два накопителя
с одинаковым `key` остаются разными. Ключ по-прежнему помечает их задачи для
обычного поиска и политик очереди. Создание накопителя заново на каждом вызове
не даёт событиям присоединяться к существующему.

### Запуск, отмена и ошибки

```dart
final group = logs.logEvent(const LogEntry('checkout opened'));
final same = logs.logEvent(const LogEntry('cart shown'));

// Все, кто добавлял в эту группу, держат один и тот же хэндл...
print(identical(group, same));

// ...поэтому его отмена отменяет всю группу, и каждый из них читает
// один и тот же исход.
await group.cancel();
switch (await same.done) {
  case Done():
    print('sent');
  case Failed(:final error):
    print('failed: $error');
  case Cancelled(:final reason):
    print('cancelled: $reason');
}
```

```text
true
cancelled: manual
```

Все три политики работают с ожидающими группами. Группа прекращает приём
событий, когда её запечатывает debounce или когда очередь её берёт,
до `canStart` и `onStart`. События из этих колбэков идут в последующую группу.
Обработчик выполняется с заданным рабочим типом и правилами, а задача группы
во всём остальном для очереди обычная `Job`.

До первого события накопитель не создаёт задач. Без `timing`, если каждая
группа завершается до прихода следующего события, каждое событие запускает
отдельную задачу. Поиск при `join` может пройти всю очередь, как и при
`replace`, а `adjacent` проверяет только её хвост.

Добавления в одну группу разделяют один хэндл, результат и отмену при любой
политике, и отмена хэндла затрагивает всю группу. `replace` переносит задачу,
а не строит другую, поэтому хэндл переживает перенос: его отмена отменяет
группу там, где задача теперь стоит, и ждать второй хэндл не нужно.

`merge` должна быть синхронной и чистой. Она не должна менять аргументы или
обращаться к контроллеру. Если она бросает, `add` бросает ту же ошибку,
а существующая группа, её задача и таймер остаются неизменными. Вызов `add`
того же накопителя из его `merge` бросает `StateError`. Движок также проверяет
после колбэка, что группа ещё подходит, прежде чем записать результат.

`canStart`, `keepWhile` и отмена действуют на всю задачу, а сами правила
описаны в разделе [«Состояние и правила»](state.md#состояние-и-правила)
страницы о состоянии. Стартовое правило, отклонившее задачу, отменяет всё, что
группа накопила. Результат и ошибки обработчика следуют обычному контракту
`Job`; принятая отмена сохраняет приоритет над более поздним значением или
ошибкой. Накопитель не откатывает частичные внешние эффекты и не пересылает
неудачный вход сам.

Отмена ожидающей debounce-группы убирает её таймер. Удаление или очистка
throttle-групп сохраняет уже начатый интервал, поэтому новое событие не обходит
ограничение. Таймер истекает один раз; он заводится заново, когда группа
фактически стартует, а при `startAtOnce: false` ещё и когда группа появляется
на накопителе, у которого ничего своего не стоит в очереди и не работает.

`close()` отменяет все таймеры `timing`, снимает ожидающие группы и отменяет
или ждёт работающую задачу по обычным правилам. Последнюю пачку он
не отправляет: группа, которая ещё ждёт своего окна, пропадает, а её задача,
единственный хэндл всех добавлявших, завершается `Cancelled(closed)`. Второй
выбор, `close(mode: SoloCloseMode.drain)`, дожидается окна накопления
и выполняет уже стоящие в очереди группы по правилам из раздела
[«Отмена работы и закрытие контроллера»](cancellation.md#отмена-работы-и-закрытие-контроллера)
страницы об отмене. Ничего нового не принимает ни тот, ни другой: вызов `add`
после `close()` возвращает новую задачу, уже завершённую `Cancelled(closed)`;
`merge` и обработчик не вызываются. После завершения группы её внутреннее
хранилище входа освобождается. Обработчик, результат или ошибка, сохранившие
вход, по-прежнему владеют своими ссылками.
