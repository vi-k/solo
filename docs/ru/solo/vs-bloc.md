# solo и bloc рядом

Перевод
[packages/solo/doc/vs-bloc.md](https://github.com/vi-k/solo/blob/main/packages/solo/doc/vs-bloc.md).
Источник правды — оригинал.

Часть пакета [solo](https://pub.dev/packages/solo).

bloc хорошо ложится на обычный экран: пришло событие, обработчик ответил
состоянием. Десять пунктов ниже — про контроллеры с жизненным циклом:
железо, устройства, плееры, фоновая синхронизация, — где с одним состоянием
происходит сразу несколько вещей и порядок важен.

Каждый пункт называет предметную область, потом показывает, что пишет для
неё опытная команда на bloc и чего этот код стоит, а потом то же самое на
`solo`. Где у bloc есть рабочий ответ, он здесь и работает; где ответа нет,
об этом сказано прямо. Ни одна из ловушек не баг: они следуют из устройства
bloc — трансформер на обработчик, `emit` действителен только внутри своего
обработчика, `add` возвращает `void`, — и там, где вопрос обсуждался в
трекере, стоит ссылка на issue.

Документ опирается на [раздел «Понятия»][concepts] из README: `Job` и
`Outcome`, `Policy`, рабочий тип `W` в `run<W, T>` и стоящий рядом с ним
`keepWhile`, `ctx.wait` и уборку, зарегистрированную вместе со значением,
`ctx.onCancel`, `SoloObserver` и очередь.

[concepts]: https://github.com/vi-k/solo/blob/main/packages/solo/README.ru.md#понятия

Каждый фрагмент кода ниже компилировался и запускался — фрагменты на bloc
против bloc 9.2.1 с bloc_concurrency 0.3.0, фрагменты на `solo` против
`solo` 0.2.0, — и все приведённые трассы взяты из этих запусков.

В том же пакете есть `Cubit`: ни событий, ни трансформеров, только методы,
которые излучают состояние. По пунктам это меняет немногое. Трансформеров у
него нет вовсе, поэтому пункты 1 и 4 — и его беда тоже; пункт 2 достаётся
ему целиком, потому что наблюдатель работает внутри `BlocBase.emit`, а это
один и тот же метод у обоих; `emit` после `close` бросает `Bad state:
Cannot emit new states after calling close`, и это пункт 3; управлять
нечем — очереди нет, и это пункт 6; отмены нет, и это пункт 9; а в пункте
10 у него нет и эмиттера, значит нет и `emit.isDone`, и проверка на
устаревание возвращается в собственное поле.

Пункты 5 и 7 он закрывает наполовину, и это одна и та же половина: метод
кубита принимает типизированные аргументы и возвращает значение, которого
можно дождаться, — на него и указывает felangel в самом
[#1556](https://github.com/felangel/bloc/issues/1556). Не закрыта другая
половина — очередь, которая шла с событиями: состояние движения пишет тот
нативный вызов, который вернулся последним (5), а два вызова по одному
заказу списывают с карты дважды (7). В обоих пунктах кубит выписан.

## 1. Параллельные обработчики пишут в одно состояние

Заметки с синхронизацией. `UploadNote` и `RefreshList` меняют один и тот же
объект состояния, а с bloc 7.2 трансформер по умолчанию — конкурентный:
если трансформер не указан, оба обработчика работают одновременно.
`RefreshList` спрашивает сервер прежде, чем загрузка дойдёт, а отвечает уже
после неё, поэтому список, который старше заметки, записывается поверх
более нового. Чтение свежего `state` после каждого `await`, как это делают
оба обработчика ниже, лечит устаревший снимок, но не чередование: никакого
снимка тут нет, два обработчика просто ходят по очереди по одному объекту.

**На bloc.** Лекарство — воронка: один обработчик на весь тип события с
`sequential()`, чтобы между `await` и `emit` всегда было не больше одного
тела. Из этой формы исходят несколько пунктов ниже, и они о том, чего она
стоит; а пункт 8 — про смену состояния, которую в эту форму не уложить
вовсе.

```dart
class NotesBloc extends Bloc<NotesEvent, NotesState> {
  final Api _api;

  // Один обработчик на весь тип, поэтому все записи в состояние
  // сериализованы: одна очередь, одно тело между await и emit.
  NotesBloc(this._api) : super(const NotesState()) {
    on<NotesEvent>((e, emit) async {
      switch (e) {
        case UploadNote(:final note):
          emit(state.copyWith(uploading: true));
          await _api.upload(note);
          emit(
            state.copyWith(notes: [...state.notes, note], uploading: false),
          );
        case RefreshList():
          final serverNotes = await _api.list();
          emit(state.copyWith(notes: serverNotes));
      }
    }, transformer: sequential());
  }
}
```

Это работает — итоговое состояние `NotesState([n0, n1], uploading: false)`,
заметка на месте, — и стоит формы. Один обработчик на тип означает один
трансформер на все команды внутри него, поэтому политика на команду
закрыта навсегда; а с классом на событие, как здесь, весь контроллер
становится одним `switch`. Пункт 5 показывает другую форму, которую может
принять тот же единственный обработчик.

Глубже лежит другая цена: гарантия здесь — соглашение, а не правило.
Трансформер на обработчик её не даёт: с `sequential()` на каждом из двух
отдельных `on<E>` заметка всё равно теряется —
`NotesState([n0], uploading: false)`, — потому что два обработчика это две
очереди. И в тот день, когда кто-нибудь зарегистрирует третий `on<E>` под
новый тип события, у состояния снова окажется два писателя, молча, и ни
одна сигнатура при этом не изменится.

Две строки, которыми читается список, в большинстве кода пишут одной:
`emit(state.copyWith(notes: await _api.list()))`. Этот вариант хуже, чем
кажется: получатель вычисляется раньше ожидаемого аргумента, поэтому
`state` берётся тот, что был до ожидания. Запись выгрузки происходит внутри
этого ожидания и затирается целиком: заметка теряется, а `uploading`
застревает на `true` — `NotesState([n0], uploading: true)`.

**На solo.** Очередь одна и корневая задача выполняется одна, поэтому
чередоваться не с чем.

```dart
final class NotesController extends Solo<NotesState> {
  final Api _api;

  NotesController(this._api) : super(const NotesState());

  Job<void> upload(Note note) => run<NotesState, void>(
        key: 'upload',
        (ctx) async {
          ctx.emit(ctx.state.copyWith(uploading: true));
          // От записи не уходят: `join` держит задачу, а с ней и очередь,
          // пока сервер не ответит.
          await ctx.join(() => _api.upload(note));
          final merged = [...ctx.state.notes, note];
          ctx.emit(ctx.state.copyWith(notes: merged, uploading: false));
        },
      );

  Job<void> refresh() => run<NotesState, void>(
        key: 'refresh',
        (ctx) async {
          // Выполняется до upload или после него, но никогда поперёк.
          final serverNotes = await ctx.wait(_api.list);
          ctx.emit(ctx.state.copyWith(notes: serverNotes));
        },
      );
}
```

`ctx.state` читается в момент излучения, и пока идёт корневая задача,
никакая другая корневая задача этого контроллера состояние не пишет.
Внутрь ведут два пути: собственные дети, запущенные `ctx.run` в том же
теле, — это пункт 9, — и `externalSetState` снаружи, а это пункт 8; оба
осознанные, оба видны. Это гарантия владения, а не дисциплина, которую два
тела должны соблюдать, и десятый метод её под угрозу не ставит.

Дисциплина здесь всё-таки есть, и назвать её стоит рядом с гарантией, а не
в конце: всякое ожидание внутри тела идёт через контекст. Голый `await`
тоже выполнится — остановить его нечем, — и то, что он выполнит, окажется
вне отмены и вне рабочего типа: контрольной точки не будет, и уже
отменённая задача продолжит его ждать. А вот `close()` его как раз
дождётся — он часть той же future, которую вернуло тело; мимо `close`
уходит другое: работа, отданная `unawaited(...)`, которая переживает
запустившее её тело. Что нет ни того ни другого, не проверяет никто, — то
же самое непроверяемое соглашение, за которое платит bloc-сторона этих
пунктов. Разная только цена забывчивости: здесь вызов выпадает из
гарантий, а там пропущенный `isClosed` пишет состояние, которое уже
устарело.

Запись дожидается через `join`, чтение — через `wait`, и в этой разнице
всё дело: от чтения уйти можно, от записи нельзя. Отменённый `wait`
закончил бы задачу загрузки, пока `_api.upload` ещё идёт по проводу,
очередь запустила бы `refresh`, и сервер прочитали бы поперёк незавершённой
записи — ровно то наложение, о котором этот пункт.

## 2. Ошибка наблюдателя становится ошибкой самой команды

Полевой рекордер. `start` просит нативный рекордер начать, публикует
`Recording` и включает измеритель уровня. Наблюдатель отправляет каждую
смену состояния в телеметрию, и однажды этот вызов бросает: эндпоинт лежит
или смена не сериализуется. Запись на устройстве уже идёт, поэтому
провалившаяся метрика не должна оставить экран в `Idle` с выключенным
измерителем.

**На bloc.** Порядок библиотека называет сама, в дартдоке `onChange`:

> [onChange] is called before the `state` of the `cubit` is updated.

(«`onChange` зовётся до того, как состояние кубита обновится».)

`BlocBase.emit` — тот самый, общий у `Bloc` и `Cubit`, — оборачивает всю
последовательность в один `try`, чей `catch` зовёт `onError` и перебрасывает.
Значит наблюдатель идёт первым, и наблюдатель, который бросил, останавливает
ту самую запись, за которой он только и пришёл посмотреть.

```dart
class RecorderBloc extends Bloc<StartRecording, RecorderState> {
  final Recorder _recorder;
  final Journal _journal;

  RecorderBloc(this._recorder, this._journal) : super(const Idle()) {
    on<StartRecording>((e, emit) async {
      await _recorder.start();
      // Ничего защитного здесь нет, и ничего конкурентного тоже: один
      // обработчик, одна операция, трансформер ни при чём.
      emit(const Recording());
      _recorder.armMeter();
    });
  }

  // Своё переопределение обязано позвать `super.onChange`, а это и есть
  // вызов, на котором приезжает глобальный наблюдатель. Значит глобальный
  // наблюдатель, который бросил, уносит с собой и строку ниже.
  @override
  void onChange(Change<RecorderState> change) {
    super.onChange(change);
    _journal.note('${change.nextState}');
  }
}

class TelemetryObserver extends BlocObserver {
  final Telemetry _telemetry;

  TelemetryObserver(this._telemetry);

  @override
  void onChange(BlocBase<dynamic> bloc, Change<dynamic> change) {
    super.onChange(bloc, change);
    // Эндпоинт лежит, поэтому это бросает.
    _telemetry.send(change.nextState);
  }
}
```

Запись идёт, а экран говорит обратное. Состояние остаётся `Idle`; до
`armMeter` дело не доходит, поэтому трасса устройства — `[native start]` и
больше ничего; журнал — `[]`, потому что пишущая в него строка стоит после
`super.onChange`, который бросил, — один провалившийся вызов телеметрии
выключил заодно и собственный учёт контроллера. Сам обработчик кончается
`telemetry unavailable`: `onError` зовётся, а потом `emit` перебрасывает,
и ошибка уходит дальше обработчика в зону. У `Cubit` это тот же путь по
коду, и тот же прогон через `RecorderCubit.start()` отдаёт ошибку
телеметрии тому, кто позвал метод.

Лечится обёрткой, и это работает:

```dart
class GuardedTelemetryObserver extends BlocObserver {
  final Telemetry _telemetry;
  final Log _fallback;

  GuardedTelemetryObserver(this._telemetry, this._fallback);

  @override
  void onChange(BlocBase<dynamic> bloc, Change<dynamic> change) {
    super.onChange(bloc, change);
    // Это нужно каждому наблюдающему колбэку, который может бросить, в
    // каждом наблюдателе, — и никто не проверяет, что оно на месте.
    try {
      _telemetry.send(change.nextState);
    } on Object catch (error, stackTrace) {
      _fallback.write(error, stackTrace);
    }
  }
}
```

С ней состояние доходит до `Recording`, трасса устройства — `[native start,
arm meter]`, в журнале `[Recording]`, а ошибка телеметрии уходит в резервный
журнал, а не в зону. Цена — соглашение: так надо написать каждый колбэк
каждого наблюдателя, и в тот день, когда один написан иначе, канал
диагностики начинает решать, выполнится ли команда. `onError` для этого тоже
не место — `emit` зовёт его и всё равно перебрасывает.

**На solo.** Хуки зовутся по отдельности, каждый сам за себя, а брошенное
ими уходит в зону.

```dart
final class RecorderController extends Solo<RecorderState> {
  final Recorder _recorder;
  final Journal _journal;

  RecorderController(this._recorder, this._journal) : super(const Idle());

  Job<void> start() => run<RecorderState, void>(
        key: 'start',
        (ctx) async {
          await ctx.join(_recorder.start);
          ctx.emit(const Recording());
          _recorder.armMeter();
        },
      );

  // Зовётся сам за себя, поэтому глобальный наблюдатель, стоящий рядом,
  // выключить его не может.
  @override
  void onChange(RecorderState previous, RecorderState current) =>
      _journal.note('$current');
}

final class TelemetryObserver extends SoloObserver {
  final Telemetry _telemetry;

  TelemetryObserver(this._telemetry);

  @override
  void onChange(SoloBase<Object> solo, Object previous, Object current) =>
      _telemetry.send(current);
}
```

Один наблюдатель обслуживает все контроллеры приложения, поэтому его хуку
достаётся общий для них базовый тип `SoloBase`, а не тот `Solo<S>`, на
котором стоит весь остальной документ; у стоящего рядом хука экземпляра тип
— собственное состояние контроллера.

Наблюдатель бросает в точности как раньше, и тело этого не замечает.
Состояние доходит до `Recording`, трасса устройства — `[native start, arm
meter]`, задача кончается `Done(null)`, а в журнале `[Recording]` — хотя
глобальный наблюдатель рядом только что провалился. Ошибка телеметрии
приходит туда, куда пришла бы необработанная ошибка `Future`, — в зону.

Это изоляция потока управления, и стоит сказать, чем она не является.
Ошибку не проглотили: в зоне, которая её не обрабатывает, необработанная
ошибка так и остаётся необработанной, и оба прогона выше идут под
`runZonedGuarded` именно поэтому. `solo` не делает ненадёжный логгер
надёжным. Он делает другое: не пускает провал логгера в решение о том,
пишет ли рекордер.

## 3. Закрытие, пока работа ещё идёт

Экран чата или ленты. Пользователь отправляет сообщение, уходит назад, и
ответ приходит в контроллер, который уже закрыт. Что будет дальше, зависит
от трансформера. С `sequential()` `close()` дожидается работающего
обработчика, и запоздавший `emit` доходит: состояние меняется после
`close`, и слушатели стрима его получают. С трансформером по умолчанию, с
`concurrent()`, `droppable()` или `restartable()`, `close()` возвращается
сразу, эмиттер отменён, и запоздавший `emit` выбрасывается молча. И в том,
и в другом случае тело продолжает работать.

**На bloc.** Обычный обходной путь — проверка `isClosed` после каждого
`await`.

```dart
class ChatBloc extends Bloc<ChatEvent, ChatState> {
  final Api _api;

  ChatBloc(this._api) : super(const ChatState()) {
    on<SendMessage>((e, emit) async {
      final reply = await _api.send(e.text);
      // Пользователь ушёл назад, пока запрос был в пути. Без этой строки
      // ответ всё равно дойдёт до состояния — `sequential()` заставляет
      // `close()` дождаться этого тела, — а `add` ниже бросит
      // `Bad state: Cannot add new events after calling close`.
      if (isClosed) return;
      emit(state.withReply(reply));
      // Отдельным событием: инлайновый `await` пошёл бы под
      // трансформером этого обработчика и заставил бы `close()` ждать.
      add(const MarkReplyRead());
    }, transformer: sequential());
    on<MarkReplyRead>(
      (e, emit) => _api.markRead(),
      transformer: sequential(),
    );
  }
}
```

Это работает: `close()` возвращается только после того, как вернулось тело,
сколько бы оно ни шло, и состояние остаётся нетронутым. Второй `on<E>` —
это вторая очередь, ровно то, о чём предупреждал пункт 1; безопасно это
здесь только потому, что `MarkReplyRead` в состояние не пишет. Дайте ему,
что писать, — и два обработчика снова два писателя.

Одна пропущенная строка — и под `sequential()` состояние меняется после
`close`, и слушатели это видят; под любым другим трансформером та же
пропущенная строка молчит. `add` после `close` бросает `Bad state: Cannot
add new events after calling close`
([#52](https://github.com/felangel/bloc/issues/52),
[#120](https://github.com/felangel/bloc/issues/120) — оба из эпохи
`mapEventToState`, за несколько мажорных версий до `on<Event>`; отменяемые
операции всё ещё в статусе предложения,
[#3069](https://github.com/felangel/bloc/issues/3069)), поэтому каждому
месту вызова, которое может сработать после закрытия, нужна ещё и
собственная проверка.

Случай тяжелее — футура, пережившая свой обработчик. `emit` из неё роняет
`assert` в debug ([#2961](https://github.com/felangel/bloc/issues/2961)), а
с выключенными ассертами просто пишет состояние: один и тот же запуск
оставляет `ChatState(null)` под `dart run --enable-asserts` и
`ChatState(reply to hi)` без него — обработчик, вернувшийся давным-давно,
всё ещё двигает экран под пользователем.

**На solo.** Закрытие — часть той же дисциплины очереди.

```dart
final class ChatController extends Solo<ChatState> {
  final Api _api;

  ChatController(this._api) : super(const ChatState());

  Job<void> send(String text) => run<ChatState, void>(
        key: 'send',
        (ctx) async {
          final reply = await ctx.wait(() => _api.send(text));
          ctx.emit(ctx.state.withReply(reply));
          // Не ребёнок: `run` всегда идёт через очередь, значит это
          // корневая задача, вставшая позади текущей.
          markReplyRead();
        },
      );

  Job<void> markReplyRead() =>
      run<ChatState, void>((ctx) => ctx.wait(_api.markRead));
}

Future<void> onScreenClosed(ChatController chat) async {
  // Отменяет выполняющийся send и ждёт, пока его тело остановится;
  // задачи из очереди завершаются с Cancelled(closed).
  await chat.close();
  chat.send('bye'); // задача, уже завершённая с Cancelled(closed)
}
```

Разница не в ожидании: `sequential()` у bloc тоже дожидается тела, и тело
solo, которое пользуется голым `await` вместо `ctx.wait`, заставит
`close()` ждать ровно столько же. Разница в том, что устаревшая запись
отклоняется, а не принимается и не проглатывается молча, — и что
отклоняется она в release тоже.

В теле выше отмена приходит на `ctx.wait`, который бросает `Cancelled`
задачи, и до строки с `emit` дело не доходит. Напишите то же тело с обычным
`await` — и до неё дойдёт, с уже отменённой задачей, и `ctx.emit` бросит эту
самую `Cancelled` вместо записи: пропущенной строке `isClosed` здесь нет
соответствия, потому что проверку делает движок. Трудный случай тот же самый
— футура, которую тело запустило и не стало дожидаться, приземляется, когда
задачи уже нет, — и её `ctx.emit` бросает `Bad state: Job(send) has already
finished, cannot emit`, именно `throw`, а не `assert`, поэтому с
выключенными ассертами он никуда не пропадает. Задачи из очереди завершаются
с `Cancelled(closed)` и завершают свой `done` — future на хэндле, несущую
исход и никогда не бросающую, это пункт 7, — а `send` после `close`
возвращает задачу, уже завершённую тем же `Cancelled(closed)`, вместо того
чтобы бросить, — так что месту вызова проверка `isClosed` не нужна.

## 4. Один restartable среди sequential

Медиаплеер. `play`, `pause` и `seek` говорят с одним нативным плеером,
поэтому выполняться должны по одному; но `seek`, выпущенный, пока
пользователь тянет ползунок, не должен вставать в очередь за более ранними
шагами того же движения — важна только последняя позиция, — а два
переключателя обязаны выполняться в том порядке, в каком их нажали.

Трудная половина — seek, уже ушедший в устройство. Футуру в Dart нельзя
прервать снаружи, поэтому просто перестать её ждать значило бы оставить
плеер перематывающим в тот момент, когда следующая команда уже отдана ему,
а плеер, которого просят перемотать дважды разом, — это плеер, который
ломается. Нативный вызов принимает токен отмены: получив команду
остановиться, он останавливается и возвращает управление. Оба решения ниже
им пользуются; различаются они тем, кто держит токен и кто дожидается
возврата.

**На bloc.** Трансформер — аргумент `on<E>` (или, глобально,
`Bloc.transformer`), и упорядочивает он только события этого одного
обработчика. Если дать `seek` собственный `on<Seek>` с `restartable()`,
эмиттер и правда начнёт перезапускаться, но обработчик пойдёт рядом с
`play` и `pause`, а не в одну линию с ними. Поэтому все три сводят в одну
воронку с `sequential()`. Движение прореживают полем с самой свежей
позицией, а seek, уже дошедший до устройства, останавливают через второе
поле — токен выполняющегося seek, отменяемый из `onEvent`, который `add`
зовёт синхронно.

```dart
class PlayerBloc extends Bloc<PlayerCommand, PlayerState> {
  final Player _player;
  Duration? _newestSeek;
  CancelToken? _seeking;

  PlayerBloc(this._player) : super(const PlayerState()) {
    on<PlayerCommand>((command, emit) async {
      switch (command) {
        case Play():
          await _player.play();
        case Pause():
          await _player.pause();
        case Seek(:final position):
          // Все шаги движения, чья позиция не самая свежая, отсекаются
          // здесь — чего это не ловит, сказано ниже.
          if (position != _newestSeek) return;
          final token = CancelToken();
          _seeking = token;
          // Плеер останавливается сам и возвращает управление, поэтому
          // команда, стоящая за этой, доходит до устройства, которое уже
          // не перематывает.
          await _player.seek(position, cancelToken: token);
          _seeking = null;
          if (token.cancelled) return;
          emit(PlayerState(position: position));
      }
    }, transformer: sequential());
  }

  @override
  void onEvent(PlayerCommand event) {
    // `add` зовёт это синхронно, поэтому более свежий шаг движения доходит
    // до seek, который уже в пути, раньше, чем до очереди за ним.
    if (event is Seek) {
      _newestSeek = event.position;
      _seeking?.cancel();
    }
    super.onEvent(event);
  }
}
```

Он делает то, что просили, — для движения, которое всё время идёт дальше.
Добавленное разом, оно доходит до плеера как `[play, seek 3, pause]`: один
нативный seek на всё движение, переключатели по-прежнему в порядке нажатий.
Поле сравнивает позицию, а не то, какое событие свежее, поэтому движение,
вернувшееся в точку, где уже было, пропускает оба: `1, 2, 1` одной пачкой
доходит до устройства как `[play, seek 1, seek 1, pause]`. Лечится
счётчиком поколений на событие, то есть `Expando` из пункта 6, написанным
второй раз.

Сделайте один шаг, дождитесь,
пока он дойдёт до плеера, сделайте ещё один — и устаревший seek будет
остановлен, а не дослушан до конца. Речь тут о том, что два вызова не
перекрываются, поэтому в этой трассе каждый вызов стоит в паре со своим
возвратом: `[seek 1 start, seek 1 stopped, seek 3 start, seek 3 end]` —
первый seek возвращается раньше срока, потому что ему так велели, а второй
стартует только после того, как он вернулся.

Цена — то, что каждая часть этого собрана руками. Токен — поле рядом с
полем самой свежей позиции: выставляется перед вызовом, снимается после
него, отменяется из переопределённого `onEvent` и читается ещё раз после
await, чтобы решить, действителен ли ещё `emit`, — одно правило,
размазанное по четырём местам, и ни одно из них компилятор с остальными не
связывает. Прореживание пишется заново для каждой команды, которой оно
нужно. Политика остаётся политикой воронки: `sequential()` — трансформер и
для `play` с `pause`, и для `seek`, поэтому команде, которой нужна другая,
придётся уйти из воронки, а уйти из воронки значит уйти из очереди — ради
которой `seek` в неё и попал. И тот, кто звал `add`, не узнаёт из этого
ничего: ни что этот шаг движения выброшен как устаревший, ни что этот seek
остановлен на середине. `add` возвращает `void`, а это пункт 7.

**На solo.** Очередь последовательна по построению, политика принадлежит
задаче, а не очереди, а отмена уходит к устройству, которое способно на
неё ответить. `Ready` первым аргументом типа — рабочий тип задачи: движок
сверяет с ним состояние и отменяет задачу, когда оно перестаёт подходить,
и об этом пункт 8. У этого плеера других состояний нет, поэтому здесь
ничего не отсекается, и `Ready` читается как состояние, в котором он
находится.

```dart
enum PlayerKey { play, pause, seek }

final class PlayerController extends Solo<PlayerState> {
  final Player _player;

  PlayerController(this._player) : super(Ready());

  // Переключатель никто не перезапускает, поэтому он просто дожидается
  // устройства.
  Job<void> pause() => run<Ready, void>(
        key: PlayerKey.pause,
        (ctx) async {
          await ctx.join(_player.pause);
          ctx.emit(ctx.state.copyWith(playing: false));
        },
      );

  Job<void> seek(Duration position) => run<Ready, void>(
        key: PlayerKey.seek,
        policy: Policy.restart,
        (ctx) async {
          final token = CancelToken();
          ctx.onCancel(token.cancel);
          // Плеер останавливается сам, а `join` его дожидается, поэтому
          // следующий seek никогда не перекрывается с этим.
          await ctx.join(() => _player.seek(position, cancelToken: token));
          ctx.emit(ctx.state.copyWith(position: position));
        },
      );
}
```

`Policy.restart` выбрасывает стоящие в очереди seek и отменяет
выполняющийся — всё по ключу `seek`; у `play()` и `pause()` политики нет,
поэтому они остаются в той же единственной очереди и выполняются в том
порядке, в каком их нажали. `ctx.onCancel` срабатывает в тот момент, когда
задачу пометили отменённой, раньше тела, поэтому токен доходит до плеера
сразу; тело после этого дожидается возврата вызова, а движок ничего не
запускает, пока задача работает. Эта пара — отменить сейчас, запустить
после возврата — и не пускает второй seek на плеер, который ещё
перематывает.

Устройство видит то же, что и выше: `[play, seek 3, pause]` на движение и
`[seek 1 start, seek 1 stopped, seek 3 start, seek 3 end]` на перезапуск.
Отличается то, где живут все три правила. Политика — именованный аргумент
той единственной задачи, которой она управляет, поэтому `seek`
перезапускается, а `play` и `pause` в той же очереди — нет: уходить из
воронки не надо, и переписывать нечего, когда придёт четвёртая команда с
четвёртым ответом. Порядок и отмена — забота движка: токен здесь локальная
переменная тела, живущая ровно столько, сколько его задача, и ни одно поле
контроллера не смотрит на то, что выполняется. А исход доходит до
вызывающего: хэндл устаревшего seek несёт `Cancelled(manual)` и завершает
свой `done`, так что ползунок, который хочет знать, дошла ли его
перемотка, может спросить.

## 5. Метод, событие и одна очередь

Карта. `moveTo` и `setZoom` — два действия на одном виджете, и движение
пальца выпускает `moveTo` на каждом кадре. С классом на событие — в этой
форме написаны пункты 1 и 6 — каждое действие есть класс, регистрация и
`add`: типы аргументов живут в событии, работа живёт в обработчике где-то
ещё, а место вызова говорит `add`, а не то, чего оно хочет.

**На bloc.** `Cubit` закрывает половину этого прямо: кубит и есть
методы, — что другими словами означает: вся эта обвязка принадлежит
событиям, а не пакету.

```dart
class MapCubit extends Cubit<MapState> {
  final MapApi _map;

  MapCubit(this._map) : super(const MapState());

  Future<void> moveTo(Point<double> point) async {
    await _map.moveTo(point);
    emit(state.copyWith(center: point));
  }

  Future<void> setZoom(double value) async {
    await _map.setZoom(value);
    emit(state.copyWith(zoom: value));
  }
}
```

Обвязки нет, аргументы типизированы. Вместе с ней исчезла очередь: у кубита
её нет. Кадры движения идут все разом к одной нативной карте, и состояние
пишет тот вызов, который вернулся последним, а не тот, на котором палец
остановился. Дайте нативным вызовам разную длительность — и трасса будет
`[moveTo 1 start, moveTo 2 start, moveTo 3 start, moveTo 3 end, moveTo 2
end, moveTo 1 end]`: карта осядет на первом кадре движения, `MapState(1, z1)`.

Чтобы вернуть порядок, футуры сцепляют в поле; чтобы отбросить устаревшие
кадры, рядом заводят поле с самой свежей точкой. Это очередь из пункта 1 и
перезапуск из пункта 4, пересобранные руками, а `close()` у кубита цепочку
к тому же не дожидается.

Только очередь — не то, чего стоит метод, и у `Bloc` ответ короче, чем у
кубита. `Event` — параметр типа без ограничения, поэтому событием может
быть функция; один обработчик её исполняет, а методы вокруг — обычные
типизированные методы.

```dart
typedef MapCommand = Future<void> Function(Emitter<MapState>);

class CommandMapBloc extends Bloc<MapCommand, MapState> {
  final MapApi _map;

  CommandMapBloc(this._map) : super(const MapState()) {
    on<MapCommand>(
      (command, emit) => command(emit),
      transformer: sequential(),
    );
  }

  void moveTo(Point<double> point) => add((emit) async {
        await _map.moveTo(point);
        emit(state.copyWith(center: point));
      });

  void setZoom(double value) => add((emit) async {
        await _map.setZoom(value);
        emit(state.copyWith(zoom: value));
      });
}
```

Это обе половины сразу: типизированные аргументы на месте вызова и
собственная очередь bloc за ними. Движение идёт по порядку — `[moveTo 1
start, moveTo 1 end, moveTo 2 start, moveTo 2 end, moveTo 3 start, moveTo 3
end]`, и кончается на `MapState(3, z4)`, — и никакой цепочки футур руками
писать не надо.

Стоит это того, что сказано в типе. Событие — `Function(Emitter<MapState>)`,
значит эмиттер теперь часть публичного типа события, а все команды блока —
один и тот же тип: трансформер общий, воронкин, и команда, которой нужен
свой, снова упирается в пункт 4. Методы возвращают `void`, потому что `add`
возвращает `void`, — дождаться здесь нечего, и это пункт 7. А тело каждой
команды — замыкание над блоком, то есть обвязка не исчезла, а переехала.

**На solo.** Это два метода, а у движения есть политика.

```dart
enum MapKey { moveTo, setZoom }

final class MapController extends Solo<MapState> {
  final MapApi _map;

  MapController(this._map) : super(const MapState());

  // Движение пальца выпускает это на каждом кадре; важна только самая
  // свежая точка.
  Job<void> moveTo(Point<double> point) => run<MapState, void>(
        key: MapKey.moveTo,
        policy: Policy.restart,
        (ctx) async {
          // Перезапускаемая, поэтому отмена уходит к самой карте, а
          // `join` дожидается её возврата, — форма из пункта 4.
          final token = CancelToken();
          ctx.onCancel(token.cancel);
          await ctx.join(() => _map.moveTo(point, cancelToken: token));
          ctx.emit(ctx.state.copyWith(center: point));
        },
      );

  Job<void> setZoom(double value) => run<MapState, void>(
        key: MapKey.setZoom,
        policy: Policy.restart,
        (ctx) async {
          final token = CancelToken();
          ctx.onCancel(token.cancel);
          await ctx.join(() => _map.setZoom(value, cancelToken: token));
          ctx.emit(ctx.state.copyWith(zoom: value));
        },
      );
}

void onMapDrag(MapController map, Point<double> point) => map.moveTo(point);
```

Сигнатура несёт аргументы и результат, место вызова читается как вызов, а
возвращённый `Job<void>` есть на случай, если вызывающий захочет его
дождаться, — вызов без `await` не поднимает линтов, потому что хэндл не
`Future`. Движение прореживает та же `Policy.restart`, что и seek из пункта
4, и оба метода отдают отмену карте тем же способом. На тех же неравномерных
нативных вызовах трасса будет `[moveTo 1 start, moveTo 1 stopped, moveTo 3
start, moveTo 3 end]`: средний кадр не стартует вовсе, первому велят
остановиться, а третий доходит до карты только после того, как первый
вернулся. Карта останавливается там же, где палец, и `MapState(3, z4)`
вместе с ней.

## 6. Очередью нельзя управлять

Экран BLE-устройства. Пользователь открывает его — подключение, — жмёт
«прочитать заряд» и «прочитать уровень сигнала», переименовывает устройство
и закрывает окно: отключение. Оба чтения делались для экрана, которого
больше нет, и должны быть выброшены; переименование пользователь попросил
сам, и оно обязано уцелеть.

**На bloc.** Чтобы очередь вообще появилась, все команды сводят в один
`on<DeviceEvent>` с `sequential()`; пять отдельных `on<E>` дали бы пять
очередей, работающих бок о бок, а это пункт 1. Очередь настоящая,
но непрозрачная: перечислить ожидающее нечем и убрать оттуда нечем. Значит,
чтения приходится отбрасывать изнутри обработчика, а обработчику надо
как-то сказать, какие из них устарели.

Булев `_leaving`, выставленный при добавлении `Disconnect`, — первый ответ,
и для одного экрана он работает. Ломается он, как только экран открывают
заново до того, как очередь опустела: флаг снимается для нового экрана, и
чтение, принадлежавшее старому, всё-таки выполняется
(`[connect, battery, disconnect, connect]`). Выдерживает это поколение.
Каждое событие штампуется в `onEvent`, который `add` зовёт синхронно, и
чтение выполняется, только если его штамп ещё текущий.

```dart
class DeviceBloc extends Bloc<DeviceEvent, DeviceState> {
  final Ble _ble;
  final _stampOf = Expando<int>();
  int _screen = 0;

  DeviceBloc(this._ble) : super(const DeviceState()) {
    // Один обработчик на весь тип, чтобы `sequential()` делал одну очередь.
    on<DeviceEvent>((e, emit) async {
      switch (e) {
        case Connect():
          await _ble.connect();
          emit(state.copyWith(online: true));
        case ReadBattery():
          // Чтения нужны были только тому экрану, который их и просил.
          if (_stampOf[e] != _screen) return;
          emit(state.copyWith(battery: await _ble.battery()));
        case ReadSignal():
          if (_stampOf[e] != _screen) return;
          emit(state.copyWith(signal: await _ble.signal()));
        case Rename(:final name):
          await _ble.rename(name);
        case Disconnect():
          await _ble.disconnect();
          emit(const DeviceState());
      }
    }, transformer: sequential());
  }

  @override
  void onEvent(DeviceEvent event) {
    // Почему здесь: `add` зовёт это синхронно, поэтому каждое событие
    // штампуется тем экраном, который его просил, раньше, чем очередь
    // дойдёт хоть до одного. Внутри case обработчика сдвиг случился бы
    // тогда, когда до него дойдёт очередь, — перед чтениями, стоящими за
    // ним.
    if (event is Disconnect) _screen++;
    _stampOf[event] = _screen;
    super.onEvent(event);
  }
}
```

Это работает и продолжает работать, когда экран возвращается. Железо видит
`[connect, rename kitchen, disconnect]`; откройте экран заново до того, как
очередь опустеет, — устаревшее чтение отброшено, новое выполнено:
`[connect, disconnect, connect, battery]`.

Цена — вторая очередь. До настоящей не дотянуться, поэтому блок ведёт
собственную запись о том, что в ней лежит: штамп на событие и счётчик, — и
сверяется с этой записью изнутри обработчика. Правило живёт в поле блока, а
не в том месте вызова, которое знает, что экрана больше нет; это условие, а
не удаление, поэтому события всё так же идут по очереди и всё так же
доходят до обработчика; и каждой команде, способной устареть, нужна своя
копия этой строки. Штамповка вдобавок держится только пока каждое событие —
отдельный объект: сделайте события `const`, и два чтения разделят один
штамп, а устаревшее выполнится снова — `[connect, battery, disconnect,
connect, battery]`.

И сказать тому, кто просил заряд, что запрос выброшен, нечем. `add`
возвращает `void`; это пункт 7.

**На solo.** Очередь — объект, которым владеет контроллер, а у задач в ней
есть ключи.

```dart
enum DeviceKey { connect, readBattery, readSignal, rename, disconnect }

// Состояние здесь — два класса, а не один объект с флагами: `Offline`,
// пока радио не ответило, и `Connected` после. Именно поэтому задача может
// назвать `Connected` своим рабочим типом, — а bloc выше вынужден нести
// тот же факт в `bool` и проверять его руками.
final class DeviceController extends Solo<DeviceState> {
  final Ble _ble;

  DeviceController(this._ble) : super(const Offline());

  // connect() излучает `Connected`; readBattery(), readSignal() и rename()
  // — обычные задачи, стоящие на нём.

  Job<void> disconnect() {
    // Чтения нужны были только экрану, который пользователь уже закрыл;
    // переименование он попросил сам, поэтому остаётся в очереди.
    queue.removeWhere(
      (job) =>
          job.key == DeviceKey.readBattery || job.key == DeviceKey.readSignal,
    );
    return run<Connected, void>(
      key: DeviceKey.disconnect,
      (ctx) async {
        // `join` не бросает радио на полпути: он дожидается вызова и
        // сдаётся только после того, как радио вернулось.
        await ctx.join(_ble.disconnect);
        ctx.emit(const Offline());
      },
    );
  }
}
```

Трасса железа та же самая. Разница в том, что правило — выражение в месте
вызова, вычисленное один раз и по самой очереди: второй записи, которую
надо держать в согласии с ней, нет, и дополнять по мере появления новых
команд нечего; и в том, что оба чтения завершаются исходом
`Cancelled(manual)` и завершают свой `done`, так что вызывающие узнают, что
произошло. Переименование остаётся — пользователь его попросил и не
отменял, — а отключение идёт следом, потому что очередь последовательна, а
отключение добавлено последним. `removeWhere` трогает только очередь: уже
начавшийся `connect` сначала доработает.

## 7. Нельзя дождаться своего события

Оформление заказа. Кто-то просит приложение оплатить заказ и должен узнать,
прошёл ли *именно этот* платёж. `add` возвращает `void`, а стрим состояний
говорит лишь то, что состояние изменилось. Так задумано, а не
недосмотрено, — felangel в
[felangel/bloc#1556](https://github.com/felangel/bloc/issues/1556):

> … a single add can result in multiple state changes so you would never
> know when the event was actually "done" being processed.

(«…один add может привести к нескольким изменениям состояния, так что
узнать, когда событие на самом деле «обработано», вы не сможете».)

Первый ответ на это — что спрашивать и не надо. Экран не ждёт: он слушает,
и `BlocListener` переходит дальше, когда приходит `Paid`. Это верно, и для
экрана разговор на этом кончается — спрашивать у блока результат одного
события из виджета, который мог бы просто смотреть на состояние, значит
идти против библиотеки. Большинству экранов этот пункт не нужен вовсе.

Верным это быть перестаёт, когда вызывающий — не экран. Обработчик
платформенного канала, отвечающий системе;
`WidgetsBindingObserver.didRequestAppExit`, отвечающий фреймворку
`AppExitResponse`; асинхронный гард роутера, отвечающий маршрутом, — ни у
кого из них нет ни `BuildContext`, ни того, что можно перестроить, ни
слушателя. Каждый — функция, обязанная вернуть ответ про доставшийся ей
запрос, и на другом конце держат трубку, пока она этого не сделает.

И платёж этот обязан быть контроллерским, а не вызовом репозитория рядом с
ним. Кнопка «Оплатить» в самом приложении запускает ту же операцию; два
вызывающих не должны списать с карты дважды, а тому, кто пришёл вторым,
надо сообщить исход того запуска, который уже идёт. Владеть этой операцией
— и есть работа контроллера: состоянием — пункт 1, очередью — пункт 6.
Поэтому вызывающему надо
дотянуться до контроллера и дождаться его, чего `add` как раз и не делает.

**На bloc.** Ответ — `Completer` внутри события и метод на блоке, отдающий его
футуру вызывающему.

```dart
class Pay extends CheckoutEvent {
  final Order order;
  final Completer<Receipt> result;

  Pay(this.order) : result = Completer<Receipt>();
}

class CheckoutBloc extends Bloc<CheckoutEvent, CheckoutState> {
  final Api _api;
  final _inFlight = <String, Completer<Receipt>>{};

  CheckoutBloc(this._api) : super(Cart()) {
    on<Pay>((e, emit) async {
      try {
        emit(Paying());
        final receipt = await _api.pay(e.order);
        // Сначала результат, потом состояние: бросивший `emit` — а
        // бросающий наблюдатель это пункт 2 — не должен оказаться тем,
        // из-за чего вызывающий ждёт вечно.
        e.result.complete(receipt);
        emit(Paid(receipt));
      } on Object catch (error, stackTrace) {
        if (!e.result.isCompleted) {
          e.result.completeError(error, stackTrace);
        }
        emit(PaymentFailed(error));
      } finally {
        _inFlight.remove(e.order.id);
      }
      // `droppable()` отпадает: он выбросил бы дубль, не заходя в этот
      // обработчик, и его completer не завершился бы никогда.
    }, transformer: sequential());
  }

  /// То, чем место вызова пользуется вместо `add`.
  Future<Receipt> pay(Order order) {
    final running = _inFlight[order.id];
    if (running != null) return running.future;
    final event = Pay(order);
    _inFlight[order.id] = event.result;
    try {
      add(event);
    } on Object {
      // `add` после `close` бросает, и это событие никогда не дойдёт до
      // обработчика, который его завершает. Без этой строки запись
      // остаётся, и следующий `pay` по тому же заказу отдаёт future,
      // которую некому завершить.
      _inFlight.remove(order.id);
      rethrow;
    }
    return event.result.future;
  }
}
```

и вызывающий после этого — `await bloc.pay(order)`, ровно то, чего просил
пункт: два вызова по одному заказу отвечают одним чеком, а второй заказ
получает свой.

Цена — форма. Раз этот метод появился, он и есть то, чем `add` отказался
быть, а класс события — обвязка вокруг него, это пункт 5. Completer надо
завершить на каждом пути выхода, включая ошибку, иначе вызывающий будет
ждать вечно, и оборвать это ожидание нечему; отсев дублей нельзя поручить
`droppable()`, потому что выброшенное событие в обработчик не заходит и его
completer не завершается никогда, — поэтому карта `_inFlight` написана
руками.

Путей выхода при этом больше, чем кажется. Три вещи в показанном коде
стоят там только ради них: `try` вокруг `add` — потому что `add` после `close`
бросает `Bad state: Cannot add new events after calling close`, это
пункт 3, — и без него осталась бы запись дедупликации, которую некому
завершить; проверка `isCompleted` — потому что в `catch` попадают и из
провалившегося `emit`; и завершение результата **до** записи `Paid`, а не
после, — потому что бросающий наблюдатель идёт через `emit`, это пункт 2, а
списанная карта не должна превращаться в вызывающего, ждущего вечно.
Каждая из них — строка, которую надо помнить, и не просит её никто.

**На Cubit.** У второго контроллера того же пакета событий нет: метод
принимает аргументы и возвращает значение, поэтому половину этого пункта,
ту, что про ожидание, закрывает сам язык. `emit(Paying())`,
`await _api.pay(order)`, `emit(Paid(receipt))`, `return receipt` — и у
вызывающего есть его чек.

Вторая половина не закрыта никак. Операцией никто не владеет, поэтому два
вызова по одному заказу выполняют свои тела бок о бок и списывают с карты
дважды, а их `emit`-ы чередуются, и потянуться не за чем — трансформеров
нет, это пункт 1. Дойти до того, чего просил пункт, значит написать обе
половины руками: карту незавершённых из bloc выше и свою цепочку,
пропускающую по одному:

```dart
class CheckoutCubit extends Cubit<CheckoutState> {
  final Api _api;
  final _inFlight = <String, Future<Receipt>>{};
  Future<void> _tail = Future.value();

  CheckoutCubit(this._api) : super(Cart());

  /// По одному платежу за раз, а второй вызов по заказу, который уже в
  /// пути, присоединяется к нему вместо повторного списания.
  Future<Receipt> pay(Order order) {
    final running = _inFlight[order.id];
    if (running != null) {
      return running;
    }
    final turn = Completer<void>();
    final before = _tail;
    _tail = turn.future;
    final result = before.then((_) => _pay(order)).whenComplete(turn.complete);
    _inFlight[order.id] = result;
    return result;
  }

  Future<Receipt> _pay(Order order) async {
    emit(Paying());
    try {
      final receipt = await _api.pay(order);
      emit(Paid(receipt));
      return receipt;
    } finally {
      _inFlight.remove(order.id);
    }
  }
}
```

Так — доходит: три вызова по двум заказам списывают дважды, а второй вызов
по заказу получает чек первого. Остаётся `close`. Кубит, закрывающийся
поверх идущего платежа, не ждёт его и не останавливает: `close()`
возвращается сразу, списание проходит следом, а вызывающий, ждавший чек,
получает вместо него `Bad state: Cannot emit new states after calling
close`. Платёж состоялся, и сказать об этом уже некому.

**На solo.** Метод возвращает хэндл задачи, которую он создал.

```dart
final class CheckoutController extends Solo<CheckoutState> {
  final Api _api;

  CheckoutController(this._api) : super(const Cart());

  Job<Receipt> pay(Order order) => run<CheckoutState, Receipt>(
        // Ключ называет заказ, поэтому второй вызов — дубль, а другой
        // заказ — другая задача.
        key: ('pay', order.id),
        policy: Policy.droppable,
        cancellable: false,
        (ctx) async {
          ctx.emit(const Paying());
          // Списание, ушедшее на сервер, назад не забрать, поэтому отменить
          // задачу нельзя, пока оно не вернётся.
          final receipt = await ctx.uncancellable(() => _api.pay(order));
          ctx.emit(Paid(receipt));
          return receipt;
        },
      );
}
```

и функция, которая должна дать ответ:

```dart
/// Платформа попросила приложение оплатить заказ и держит трубку, пока не
/// узнает, прошёл ли этот платёж.
Future<Map<String, Object?>> handlePayRequest(
  CheckoutController checkout,
  Order order,
) async {
  switch (await checkout.pay(order).done) {
    case Done(:final value):
      return {'paid': true, 'receipt': value.id};
    case Cancelled(:final reason):
      return {'paid': false, 'cancelled': reason.name};
    case Failed(:final error):
      return {'paid': false, 'error': '$error'};
  }
}
```

`done` несёт исход именно этого вызова и никогда не бросает; `value` несёт
значение и, наоборот, бросает. Ни тому, ни другому не нужно гадать, чьё
изменение состояния перед ним. Поскольку ключ называет заказ, а не метод,
`Policy.droppable` считает второй вызов тем дублем, каким он и является, —
оба вызывающих получают один хэндл и один чек, — а другой заказ остаётся
другой задачей. Три вызова по двум заказам доходят до API дважды, ровно как
у карты и цепочки выше, только писать не надо ни того, ни другого.

`cancellable: false` и `ctx.uncancellable` — это всё остальное, и это не
одно и то же. Секция **придерживает** отмену на время вызова, а не
отказывает в ней: `cancel` и `close` не получают отказ, их заставляют
подождать, и в момент, когда списание вернулось, придержанная отмена
приходит. Без `cancellable: false` строка с `Paid` была бы обычной записью
и бросила бы придержанную отмену вместо того, чтобы что-то записать; задача
закончилась бы `Cancelled(closed)` про платёж, который действительно
состоялся. Перенести запись внутрь неотменяемой секции — не помощь: исход
всё равно определит придержанная отмена.

Обещание держится на `cancellable: false` у задачи: такая задача отказывает
всякой отмене, которой может отказать, — `close` в том числе. С ним задача
возвращается с `Done(receipt)`, состояние заканчивается на `Paid`, и
приложение закрывается после этого.

Чему флаг не отказывает — так это правилу. Рабочий тип или `keepWhile`,
переставший подходить, отменяет задачу независимо от флага, и ровно это
секция и закрывает: без неё правило режет тело там, где оно стоит, и
списание не уходит вовсе — замерено `charged=false`, исход
`Cancelled(rules: …)`; с ней списание сначала возвращается, а отмена
приходит после. У этого платежа такого правила нет, и нарочно: `W` здесь
базовый `CheckoutState`, а `keepWhile` не задан, потому что рабочий тип
поуже дал бы смене состояния отменить платёж в промежутке между списанием
и строкой, которая его записывает. Значит на рецепте, как он показан,
секция не меняет ничего — замерено, что `cancel`, `close` и форсированная
чистка дают `Done(receipt)` и с ней, и без неё, — и стоит она для
читателя, который позже даст задаче правило.

Стоит флаг того, что пользователь передумать уже не может. Отказ действует
с того момента, как задачу добавили, включая её место в очереди:
`job.cancel()` на платеже, который ещё не стартовал, получает отказ, и с
карты списывают всё равно — замерено `Done(receipt)` там, где та же задача
без флага заканчивается `Cancelled(manual)` и не списывает ничего. Экрану
оплаты, которому нужна кнопка «Отмена» до ухода списания, нужен свой
второй затвор, перед вызовом.

Две отмены до не стартовавшего платежа всё же доходят, потому что они не
спрашивают. `close()` убирает его из очереди с `Cancelled(closed)`, а
`clear(force: true)` — с `Cancelled(manual)`; ни та ни другая ничего не
списывают. Отсюда и берётся ветка `Cancelled` у обработчика, вместе с
вызовом после `close`, который не стартует вовсе, — и потому же она читает
`reason.name`, а не додумывает, которая из двух это была.

У стартовавшей задачи не забирает ничто: `close()` дожидается списания, и
приложение закрывается после него.

## 8. Состояние меняется извне

Камера или BLE-датчик. Железо сообщает об отказе через листенер, пока
обработчик калибровки на середине пути, и всё, что идёт после этой точки,
говорит со сломанным железом.

**На bloc.** Собственный `emit` у bloc помечен `@visibleForTesting` и
описан как внутренний — «only for internal use and should never be called
directly outside of tests» («только для внутреннего использования, звать
его напрямую вне тестов нельзя»), — поэтому поддерживаемый путь внутрь из
листенера — `add(HardwareFailed(error))`. Этому событию нужен свой
обработчик, вне очереди калибровки, чтобы он мог работать рядом с ней, а не
за ней; а калибровка повторяет своё предусловие после каждого `await`.

```dart
class SensorBloc extends Bloc<SensorEvent, SensorState> {
  final Sensor _hw;

  SensorBloc(this._hw) : super(Ready()) {
    // Поддерживаемый путь внутрь — событие. У него свой обработчик, чтобы
    // он мог работать *рядом* с калибровкой, а не за ней.
    _hw.onError = (error) => add(HardwareFailed(error));
    on<HardwareFailed>((e, emit) => emit(Broken(e.error)));
    on<Calibrate>((e, emit) async {
      if (state is! Ready) return;
      await _hw.zero();
      // Broken мог прийти во время await; этот обработчик никто не отменил,
      // поэтому предусловие повторяется руками после каждого шага.
      if (state is! Ready) return;
      await _hw.sample();
      if (state is! Ready) return;
      emit(Calibrated());
    }, transformer: sequential());
  }
}
```

Это работает: состояние заканчивается на `Broken(cable unplugged)`, а
`Calibrated` не появляется вовсе.

Стоит это строки на каждый `await`, в каждом обработчике, всегда.
Предусловие невидимо в сигнатуре, поэтому новое состояние или новый `await`
означают повторный обход всех тел; пропустите одно — и калибровка запишет
`Calibrated` поверх `Broken`: экран датчика отрапортует об успехе на
отключённом железе.

И само разделение — не выбор. Примените лекарство из пункта 1 и заведите
отказ в ту же воронку — он встанет в очередь за калибровкой: `[Calibrated,
Broken(cable unplugged)]`, причём `Calibrated` по дороге опубликуется
слушателям. Сериализованные записи в состояние или отказ, способный
вклиниться, — трансформеры дают одно или другое, но не оба сразу.

**На solo.** Состояние пишет сам листенер, а правила остаются в
объявлении.

```dart
final class SensorController extends Solo<SensorState> {
  final Sensor _hw;

  SensorController(this._hw) : super(const Ready()) {
    // Листенер сам пишет состояние. Каждая работающая задача, которая
    // перестала подходить состоянию по рабочему типу или keepWhile,
    // отменяется сразу.
    _hw.onError = (error) => externalSetState(Broken(error));
  }

  // Предусловие — это сигнатура: W здесь Ready. В теле проверять нечего и
  // повторять после каждого await нечего.
  Job<void> calibrate() => run<Ready, void>(
        key: 'calibrate',
        (ctx) async {
          // `join` не бросает вызов датчика: он дожидается его и
          // сдаётся после, если за это время состояние перестало
          // подходить.
          await ctx.join(_hw.zero);
          await ctx.join(_hw.sample);
          ctx.emit(const Calibrated());
        },
      );
}
```

`externalSetState` переоценивает по новому состоянию каждую работающую
задачу и отменяет те, чей рабочий тип или `keepWhile` больше не держится:
калибровка завершается исходом `Cancelled(rules: is not Ready)`, и
вызывающий может это прочитать. Предусловие живёт в `run<Ready, void>`, где
движок проверяет его перед стартом, при каждом изменении состояния и при
каждом чтении, — в одном месте, и новый вызов в теле его наследует
настолько, насколько идёт через контекст: `wait`, `join` или
`uncancellable` либо `await`, за которым следует чтение.

От этой переоценки освобождена одна задача, и это как раз та, что пишет.
`ctx.emit` не перепроверяет задачу, из которой его позвали, — потому
последняя строка выше и может записать `Calibrated`, которому её
собственный `Ready` иначе отказал бы: замерено `Done(null)`. Правила
догоняют её на следующем чтении через контекст, поэтому та же запись, за
которой стоит один `ctx.wait`, заканчивается уже `Cancelled(rules: is not
Ready)`. Тело, у которого запись за пределы своего рабочего типа —
последнее действие, обычно; тело, которое после такой записи продолжает
работать, — нет.

Уже начавшийся `sample()` всё равно доработает — и там, и там: прервать
футуру в Dart не может ни одна библиотека, а датчику, который только что
лишился кабеля, сказать уже нечего. Там, где устройство всё-таки принимает
токен отмены, пункт 4 отдаёт ему токен через `ctx.onCancel`. Здесь
останавливается всё, что идёт после `sample()`.

## 9. После отмены обработчик продолжает работать

Обновление прошивки по BLE, кусок за куском. Перезапущенная прошивка должна
перестать писать в устройство; `restartable()` закрывает эмиттер, и это
всё, что он делает: цикл продолжает писать.

Этому устройству нельзя велеть остановиться. Кусок, отданный стеку, дойдёт,
и никакой токен отмены его не заберёт — обычное дело для записи по BLE.
Значит, единственный способ развести два образа по одному проводу —
дождаться записи, идущей прямо сейчас, прежде чем начать следующую.

**На bloc.** Ответ здесь — от самого мейнтейнера, в
[felangel/bloc#3349](https://github.com/felangel/bloc/issues/3349):

> This is because Futures aren't truly cancelable. To get the behavior
> you're describing you can simply check if `emit.isDone` is true before
> performing any expensive computations:

(«Дело в том, что Future по-настоящему неотменяемы. Чтобы получить
описанное вами поведение, можно просто проверять, истинно ли
`emit.isDone`, перед любыми дорогими вычислениями».)

```dart
class FirmwareBloc extends Bloc<FirmwareEvent, FirmwareState> {
  final Ble _ble;

  FirmwareBloc(this._ble) : super(Idle()) {
    on<Flash>((e, emit) async {
      var written = 0;
      for (final chunk in e.chunks) {
        await _ble.write(chunk);
        // Без этой строки перезапущенный обработчик продолжает писать
        // куски в устройство: `restartable()` закрывает эмиттер, а не
        // останавливает тело. Она нужна каждому циклу, трогающему железо.
        if (emit.isDone) return;
        emit(Flashing(++written, e.chunks.length));
      }
    }, transformer: restartable());
  }
}
```

В своих пределах это работает. Со строкой прошивка, перезапущенная на
середине файла, пишет `[0, 1, 100, 101, …]` и на этом останавливается. Без
неё две прошивки чередуются до конца: `[0, 1, 100, 2, 101, 3, 102, 4, 103,
5, 104, 105]` — два образа идут в одно устройство разом.

Строку надо повторять после каждого `await` в каждом цикле, трогающем
железо, и никто не проверит, что она там есть. И приходит она к тому же
слишком поздно, чтобы развести две прошивки. `restartable()` запускает
замену в тот самый момент, когда событие добавили, — старый `_ble.write`
ещё на проводе, — а `emit.isDone` не читается, пока эта запись не
вернётся, поэтому у устройства просят кусок нового образа, пока оно ещё
принимает кусок старого: `[write 0 start, write 0 end, write 1 start,
write 100 start, write 1 end, write 100 end, …]`.

Положить ожидание трансформерам некуда. Они предлагают «начать новый
обработчик сейчас» (`restartable()`) и «начать его после того, как старый
допишет весь файл» (`sequential()`), но не «дать старому вернуться из
куска, который он пишет, и потом начать». Значит, ожидание строят рядом с
ними, руками: провод уходит под замок. В ядре Dart замка нет, а написать
его недолго — цепочка футур, где каждый вызывающий держит очередь
следующего, — та самая, что кубит пункта 7 выписывал инлайном:

```dart
/// По одному за раз. Каждый вызывающий ждёт предыдущего и передаёт
/// очередь дальше, когда его собственная работа кончилась, с ошибкой или
/// без.
class Lock {
  Future<void> _tail = Future.value();

  Future<T> protect<T>(Future<T> Function() action) {
    final turn = Completer<void>();
    final before = _tail;
    _tail = turn.future;
    return before.then((_) => action()).whenComplete(turn.complete);
  }
}

class LockedFirmwareBloc extends Bloc<FirmwareEvent, FirmwareState> {
  final Ble _ble;
  final _wire = Lock();

  LockedFirmwareBloc(this._ble) : super(Idle()) {
    on<Flash>((e, emit) async {
      var written = 0;
      for (final chunk in e.chunks) {
        // Заменяющий обработчик стартует, пока эта запись идёт по проводу,
        // и ждёт здесь, пока она дойдёт. Каждый вызов устройства, в каждом
        // обработчике, обязан идти через этот же замок.
        await _wire.protect(() async {
          // Проверка внутри своей очереди, а не перед ней. Ожидание замка
          // — второе место, где можно устареть, а замок зовёт то, что
          // держит, независимо от того, жив ли ещё тот обработчик.
          if (emit.isDone) return;
          await _ble.write(chunk);
        });
        if (emit.isDone) return;
        emit(Flashing(++written, e.chunks.length));
      }
    }, transformer: restartable());
  }
}
```

Это работает. Доходят те же куски, `[0, 1, 100, 101, …]`, и теперь по
одному за раз: `[write 0 start, write 0 end, write 1 start, write 1 end,
write 100 start, write 100 end, …]`.

Проверка переехала внутрь своей очереди потому, что замок добавил второе
место, где можно устареть, — и первая редакция этого рецепта его
пропускала. Обработчик, дошедший до `protect`, пока проводом владеет чужая
запись, встаёт в цепочку; отмените его там — и цепочка всё равно позовёт
то, что держит, когда очередь дойдёт. Замерено на варианте с проверкой
перед замком: три прошивки, запущенные подряд, кладут в провод
`[0, 100, 200, 201]` — кусок среднего образа уходит в устройство, хотя ту
прошивку заменили раньше, чем она вообще добралась до радио; и запись
может начаться после того, как `close()` уже вернулся.

Стоит это не длины замка. Стоит это второго порядка, стоящего рядом с
порядком трансформера, и друг о друге они ничего не знают. `restartable()`
считает старый обработчик заменённым в тот момент, когда пришло событие;
провод говорит иначе ещё один кусок времени, и знает об этом только замок.
Строка `emit.isDone` всё равно нужна: замок упорядочивает записи, но не
заканчивает цикл. А под тем же замком обязан идти каждый вызов устройства, в
том числе из обработчиков, к прошивке отношения не имеющих; никто не
проверит, что это так, и одного пропущенного хватит, чтобы оба образа снова
оказались на проводе — без единой ошибки где бы то ни было.

А досягаемость `emit.isDone` кончается на эмиттере. Занесите отказ как
состояние, а не как перезапуск — событие `HardwareFailed`, излучающее
`Broken`, поддерживаемый путь из пункта 8, — и `emit.isDone` не станет
истинным никогда: прошивка запишет `[0, 1, 2, 3, 4, 5]` в сломанное железо,
а потом перезапишет `Broken` на `Flashing`. Зеркальный случай — футура,
запущенная внутри обработчика и оставленная без `await`: ничего, что
пережило бы обработчик, тут не устроено, поэтому её ловит только `assert` в
debug ([#2961](https://github.com/felangel/bloc/issues/2961)) — см. пункт 3.

**На solo.** Ожидание — забота очереди, и писать для этого нечего.

```dart
final class FirmwareController extends Solo<FirmwareState> {
  final Ble _ble;

  FirmwareController(this._ble) : super(const Idle());

  Job<void> flash(List<Chunk> chunks) => run<NotBroken, void>(
        key: 'flash',
        policy: Policy.restart,
        (ctx) async {
          var written = 0;
          for (final chunk in chunks) {
            // Цикл заканчивает `join`: запись, которой он ждёт, доходит,
            // и он бросает Cancelled этой задачи. Прошивка, заменяющая
            // эту, не стартует, пока не вернётся всё тело.
            await ctx.join(() => _ble.write(chunk));
            ctx.emit(Flashing(++written, chunks.length));
          }
        },
      );
}
```

Перезапуск пишет те же `[0, 1, 100, 101, …]`, что и bloc под замком выше, и
так же по одному за раз: `[write 0 start, write 0 end, write 1 start,
write 1 end, write 100 start, write 100 end, …]`. В контроллере это не
устроено ничем, и замка тут нет. Задача держит контроллер, пока её тело не
вернётся, а `Policy.restart` помечает эту отменённой и ставит замену за
ней, поэтому вторая прошивка не доберётся до устройства, пока на нём ещё
первая.

Это же тело закрывает и другую отмену — ту, до которой перезапуск не
достаёт: `Broken`, записанный листенером железа, перестаёт подходить
рабочему типу, поэтому задачу помечают, и прошивка останавливается на
`[0, 1, 2]` с `Cancelled(rules: is not NotBroken)`, а не дописывает файл, —
случай, которого `emit.isDone` не видит. Хэндл самого отменённого вызова
несёт `Cancelled(manual)` там, где `add` не нёс ничего. А работа, которая
иначе была бы запущена и брошена, идёт через один из двух членов. Работа
со своим исходом — через `ctx.run(child)`, дочернюю задачу, которую
родитель дожидается; работа без исхода — метрика, остановка «как
получится» — через `ctx.unattended`: её родитель не ждёт, но её провал
слышит.

## 10. Отменённая операция всё равно приносит ресурс

Экран аудиомонтажа рисует форму волны выбранного клипа. Декодер выделяет
нативный PCM-буфер, контроллер берёт из него форму волны и возвращает буфер
обратно. Пользователь выбирает другой клип, пока первый буфер ещё строится.
Первая волна больше не нужна; отдать память — не по желанию. Два
декодирования здесь независимы: буферы разные, и начало второго не портит
первый; декодер, который такого наложения не терпит, — это пункт 9, а не
этот.

**На bloc.** `restartable()` отменяет эмиттер старого обработчика, а
`await _decoder.open(...)` живёт себе дальше. Строка из пункта 9 делает своё
дело — и этим же теряет буфер.

```dart
class PreviewBloc extends Bloc<OpenPreview, PreviewState> {
  final Decoder _decoder;

  PreviewBloc(this._decoder) : super(const NoPreview()) {
    on<OpenPreview>((e, emit) async {
      final buffer = await _decoder.open(e.clip);
      // Права насчёт экрана, неправа насчёт буфера: декодер ответил
      // обработчику, которого больше никто не слушает, а выделенную им
      // нативную память никто не вернёт.
      if (emit.isDone) return;
      emit(Preview(buffer.waveform()));
      await buffer.release();
    }, transformer: restartable());
  }
}
```

Публичного места под освобождение у эмиттера нет: его disposables
обслуживают подписки `onEach` и `forEach`, а не ваш ресурс. Но ответ короток
и он работает — получить, затем взять использование в скобки, а проверку на
устаревание перенести внутрь скобок:

```dart
class GuardedPreviewBloc extends Bloc<OpenPreview, PreviewState> {
  final Decoder _decoder;

  GuardedPreviewBloc(this._decoder) : super(const NoPreview()) {
    on<OpenPreview>((e, emit) async {
      final buffer = await _decoder.open(e.clip);
      try {
        if (emit.isDone) return;
        emit(Preview(buffer.waveform()));
      } finally {
        await buffer.release();
      }
    }, transformer: restartable());
  }
}
```

Оба буфера возвращаются — `stale releases 1, current releases 1`, тогда как
вариант выше оставляет `stale releases 0`. Стоит это того, где живёт
обязательство: в теле, которое продолжает ждать после отмены своего
эмиттера и которое единственное знает, что буфер вообще есть. Перенесите
проверку на строку выше, перед `try`, — и утечка вернулась; возьмите второй
ресурс — и скобки вложатся; отдайте буфер наружу в состояние — и вопрос
владения начнётся заново. Ничто из этого не цена классов событий и не цена
стиля: обработчик просто и есть единственный держатель обязательства.

И проверить работу по состоянию нельзя. Оба прогона выше кончаются
`Preview(2)`: верное состояние с утечкой и верное состояние без неё — одно
и то же состояние.

**На solo.** Обязательство прикреплено к получению значения, а не к телу.

```dart
final class PreviewController extends Solo<PreviewState> {
  final Decoder _decoder;

  PreviewController(this._decoder) : super(const NoPreview());

  Job<void> open(Clip clip) => run<PreviewState, void>(
        key: 'preview',
        policy: Policy.restart,
        (ctx) async {
          // Одна регистрация на два окна: буфер, пришедший после конца
          // этой задачи, уходит прямо уборщику, а пришедший вовремя
          // освобождается после тела.
          final buffer = await ctx.wait(
            () => _decoder.open(clip),
            dispose: (buffer) => buffer.release(),
          );
          ctx.emit(Preview(buffer.waveform()));
        },
      );
}
```

`ctx.wait` может закончить отменённую задачу, не дожидаясь декодера, —
перезапущенный предпросмотр не стоит за декодированием, которое никому не
нужно, — а пришедшее следом значение всё равно уходит зарегистрированному
для него колбэку. Тот же колбэк закрывает и обычный путь: буфер, пришедший
вовремя, освобождается, когда тело с ним закончило. Ни `isDone`, о котором
надо помнить, ни отдельной ветки под позднее значение писать не нужно.

Здесь именно `dispose`, а не `discard`, и разница есть: `discard` работает
только тогда, когда задача не отдала своё значение наружу, а успешная
задача здесь не отдаёт ничего, кроме состояния. Буфер в любом случае
остаётся временным ресурсом тела, поэтому освободить его надо и на успешном
пути, — а это и значит `dispose`.

Декодер видит одно и то же в обоих случаях — `[open 1, open 2, ready 2,
sample 2, release 2, ready 1, release 1]`, устаревший буфер отдан
последним, — и состояние кончается на `Preview(2)`.

Границу стоит назвать так же прямо, как и гарантию. `close()` не ждёт
ресурс, который появится только после конца задачи. В замеренном прогоне
контроллер закрывается первым — `closed true`, а устаревшая задача давно
`Cancelled(manual)`, — и буфер приходит уже после этого и тогда же
освобождается: поздно, но освобождается. Регистрация обещает, что
освобождение случится, а не что оно случится до возврата из `close()`.
Операция, которую вообще нельзя оставлять в полёте, — это `ctx.join`, и это
пункт 9.
