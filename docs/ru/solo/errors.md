# Ошибки и наблюдение

Обработчики состояния и хуки диагностики решают разные задачи.
`run(onError: ...)` вычисляет состояние после ошибки `Job`. Метод контроллера
`onError` и `SoloObserver.onError` получают ошибки для логирования или
отправки, включая ошибки уборки и брошенных операций, а `onUnanswered` отвечает
за те, которых не несёт ни один исход.

Пять разделов ниже открываются той версией, к которой ведёт словарь этого API —
член, названный по вопросу, который вы задаёте, вызов, который говорит то, что
вы имеете в виду, — и говорят, что эта версия делает вместо задуманного.
Работающая версия идёт следом под своим заголовком.

## Отправка ошибки

Контроллер может переопределить `onStart`, `onFinish`, `onError`, `onLog`,
`onChange` и `onClose`, а также `onListenerError` — для слушателя, который
бросил при оповещении. Контроллеру профиля нужно, чтобы его сбои попадали
в систему отчётов.

```dart
final class ProfileController extends Solo<ProfileState> {
  final ProfileApi api;

  ProfileController(this.api) : super(const Initial());

  // ...задачи из быстрого старта...

  @override
  void onError(Job<Object?> job, Object error, StackTrace stackTrace) =>
      reportCrash(error, stackTrace);
}
```

Хуку рассказывают о каждой ошибке задач этого контроллера — о провале тела,
об ошибке уборки или операции, брошенной `wait`, о правиле, которое бросило
вместо ответа, — и рассказывают один раз. Он отправляет отчёт и возвращается,
и это всё, для чего он есть: хук ни за что не отвечает, и его переопределение
не двигает ни одну ошибку никуда.

### Ответ за ошибку

```dart
final class ProfileController extends Solo<ProfileState> {
  // ...задачи и хук отчёта выше...

  @override
  void onUnanswered(Job<Object?> job, Object error, StackTrace stackTrace) =>
      _apiFailures.add(error);
}
```

Почти каждую ошибку несёт исход задачи. Провал тела становится `Failed`,
по нему `run(onError: ...)` вычисляет состояние, а исход, которого никто
не наблюдал, сам доходит до зоны создания `Job`. Исход не несёт остального:
операции, брошенной `wait` и упавшей позже, уборщика, колбэка `onCancel`,
работы, отданной `ctx.unattended`. За них кто-то должен ответить, и спрашивают
всегда одного: `onUnanswered` того контроллера, чья это была задача.

Переопределение выше отвечает за них здесь, и дальше они не идут никуда: этот
контроллер владеет тем, на чём упали его задачи, и сказал об этом.
У контроллера без такого переопределения остаётся тело по умолчанию, и оно
передаёт их дальше:

```dart
Solo.errorHandler = (solo, job, error, stackTrace) =>
    Sentry.captureException(error, stackTrace: stackTrace);
```

Обработчик один на весь процесс, ставится один раз при старте; `solo` он
получает потому, что служит всем контроллерам. Если обработчика нет, такие
ошибки уходят в зону создания `Job`. Ошибка приходит в хук, а хук зовёт
обработчика, поэтому каждый контроллер решает за свои задачи, услышит ли их
общий обработчик процесса вообще. Переопределение сохраняет и этот маршрут,
если позвать `super.onUnanswered(job, error, stackTrace)`.

Отвечать за ошибку — это ответственность, которую берут на себя, а не побочный
эффект включения лога. Поставить `SoloObserver` — тоже не ответ: наблюдение
ни за что не отвечает.

## Наблюдение за всеми контроллерами

`SoloObserver` получает те же события от всех контроллеров, а также `onCreate`.
Установите его при запуске приложения:

```dart
final class LoggingObserver extends SoloObserver {
  @override
  void onStart(Solo<Object> solo, Job<Object?> job) =>
      print('$job started');

  @override
  void onFinish(Solo<Object> solo, Job<Object?> job) =>
      print('$job finished ${job.outcome}');

  @override
  void onChange(Solo<Object> solo, SoloTransition<Object> transition) =>
      print('${transition.job ?? 'external'}: ${transition.current}');
}

void main() {
  Solo.observer = LoggingObserver();
}
```

Хук изменения получает `SoloTransition`: состояние до и после, `job`, чей
`emit` его сделал — `null` для `externalSetState`, а у дочерней задачи это она
сама, а не корневая, которой она принадлежит, — и `revision`, растущий
на единицу за изменение, так что два перехода упорядочены даже когда хук
поменял состояние ещё раз изнутри первого. Он отвечает на вопрос, кто изменил
состояние, а снаружи движка это не выводится.

Наблюдатель вызывается перед соответствующим хуком контроллера. Каждый вызов
независим; отсутствие `super` в хуке контроллера не отключает наблюдателя.
Ошибка любого из них передаётся в текущую зону Dart, не меняя исход `Job`,
не останавливая очередь и не препятствуя вызову второго хука.

Наблюдатель только наблюдает. Его наличие никак не влияет на то, куда дальше
пойдёт ошибка.

## Что удерживает контроллер

`close()` ждёт работающую `Job`, а `Job` может не торопиться. Контроллер
говорит, чего именно он ждёт:

```dart
unawaited(controller.close().timeout(
  const Duration(seconds: 5),
  onTimeout: () => log('closing is held by ${controller.pending}'),
));
```

`SoloPending` — снимок той `Job`, которую ждёт контроллер:

| Поле | Что говорит |
| --- | --- |
| `job` | `Job`, которую ждут |
| `phase` | чем она занята: `body`, `children`, `cleanup` |
| `cancellation` | отмена, которой она помечена, иначе `null` |
| `heldCancellation` | отмена, которую держит открытая секция `ctx.uncancellable` |
| `children` | сколько детей она ещё ждёт |
| `inUncancellableSection` | открыта ли такая секция |
| `refusesCancellation` | создана ли она с `cancellable: false` |
| `closing` | позвали ли у контроллера `close()` |

Рядом с полями снимок считает и один свой ответ: `pending.cancellationPending`
истинно, когда есть любая из двух отмен выше — помеченная или придержанная.
`Job` с `refusesCancellation` отклоняет те отмены, которые может отклонить,
и тогда ждать нечего, сколько бы раз её ни просили остановиться.

`null` говорит, что ни одна `Job` не работает, а не что закрытие ничто
не держит. Дренаж — `close(mode: SoloCloseMode.drain)` — ждёт ещё и очередь,
а группа `collect` или `accumulate` стоит в ней, пока её не отпустит тайминг, —
`isDraining` в это время ещё истинно. У `SoloStream` стрим закрывается после
движка и ждёт, пока каждая подписка получит событие завершения: подписка,
оставленная на паузе, держит `close()`, хотя `isFinished` уже истинно.

Он сообщает, а не ставит диагноз. Долгое ожидание не доказывает забытый
`ctx.wait`: тело внутри внешнего вызова выглядит так же, и неторопливое
освобождение ресурса тоже. Фаза говорит, где `Job`, а не почему: пока работает
тело, фаза — `body`, чего бы оно ни ждало, и движок не гадает.

## Почему отмена была долгой

`SoloPending` отвечает, пока ожидание идёт, и для этого надо, чтобы кто-то
стоял рядом и спрашивал. Вторая половина вопроса приходит потом и там, где
никто не смотрит: какие задачи работали дальше, несмотря на отмену, которая
должна была их остановить, и сколько.

### Первая попытка

```dart
final class SlowJobs extends SoloObserver {
  final _startedAt = Expando<DateTime>('start');

  @override
  void onStart(Solo<Object> solo, Job<Object?> job) =>
      _startedAt[job] = clock.now();

  @override
  void onFinish(Solo<Object> solo, Job<Object?> job) {
    final startedAt = _startedAt[job];
    if (startedAt == null) return;
    final ran = clock.now().difference(startedAt);
    if (ran > const Duration(milliseconds: 50)) {
      log('${job.key} ran ${ran.inMilliseconds} ms');
    }
  }
}
```

`onStart` и `onFinish` — два конца задачи, а разница между ними — её время
жизни. Задача, которая шла 300 мс, потому что работа занимает 300 мс, даёт
ту же строку, что и задача, отменённая на десятой миллисекунде и всё равно
доработавшая до конца. Искать стоит вторую, а эти два хука их не различают.

### Отметка отмены

```dart
final class SlowCancellations extends SoloObserver {
  // Expando держит ключ слабо: запись уходит вместе с задачей,
  // и чистить нечего.
  final _markedAt = Expando<DateTime>('cancellation');

  @override
  void onStart(Solo<Object> solo, Job<Object?> job) {
    // whenCancelled срабатывает, когда отмена стала действующей, а не
    // когда позвали cancel(): шаг под ctx.uncancellable отработает раньше.
    job.whenCancelled((_) => _markedAt[job] = clock.now());
  }

  @override
  void onFinish(Solo<Object> solo, Job<Object?> job) {
    final markedAt = _markedAt[job];
    if (markedAt == null) return;
    final delay = clock.now().difference(markedAt);
    if (delay > const Duration(milliseconds: 50)) {
      log('${job.key} ran ${delay.inMilliseconds} ms past its cancellation');
    }
  }
}
```

Задачу, которую никто не отменял, не отмечают и не сообщают о ней, сколько бы
она ни шла. Число — то самое ожидание, которое высидел вызвавший `cancel` или
`close`: от момента, когда отмена стала действующей, до исхода, вместе с детьми
и уборкой.

Смотреть на него стоит ради одной конкретной ошибки. Тело, ждущее что-то долгое
голым `await`, держит отмену всё это ожидание целиком, а тот же вызов через
`ctx.wait` отдаёт её сразу. Ожидание на 300 мс, отменённое на десятой:

| как тело ждёт | сообщённая задержка |
| --- | --- |
| `await Future.delayed(...)` | 290 мс |
| `ctx.wait(() => Future.delayed(...))` | 0 мс |

Задача, отменённая до старта, не сообщает ничего: `onStart` для неё не зовут
вовсе, значит регистрации и отметки не было. Замечать отмену было некому,
и в контроллере под это попадает всё, что выброшено из очереди.

`clock.now()`, а не `DateTime.now()`: под `fake_async` первый идёт вместе
с фальшивым временем, а второй стоит на месте, так что того же наблюдателя
можно проверить тестом. Наблюдатель работает в приложении, поэтому
`package:clock` идёт в его зависимости, а не в зависимости разработки; пакет
этот без своих зависимостей, и `fake_async` и так от него зависит везде, где
идут тесты.

### `Job`, которая не кончается

```dart
final class Hangs extends SoloObserver {
  // An Expando holds its key weakly, so a job takes its timer with it.
  final _timers = Expando<Timer>('hang');

  @override
  void onStart(Solo<Object> solo, Job<Object?> job) => _timers[job] = Timer(
        const Duration(seconds: 5),
        () => log('${job.key} is still running: ${solo.pending}'),
      );

  @override
  void onFinish(Solo<Object> solo, Job<Object?> job) => _timers[job]?.cancel();
}
```

Отметку выше читают, когда `Job` кончается, а зависшая не доходит туда никогда:
`onFinish` не приходит, задержку никто не считает, и самая долгая отмена
из всех — та, о которой не сказано ничего. Этот таймер заводится с другого
конца — на `onStart` — и срабатывает, вернулась `Job` или нет.

`Job`, которая успела кончиться, снимает свой таймер сама и молчит. Та, что
не успела, — всё ещё та самая, на которой стоит контроллер, поэтому
`solo.pending` — снимок именно её:

```text
stuck is still running: SoloPending([stuck] in its body)
held is still running: SoloPending([held] in its body, holding Cancelled(manual) back)
```

Пять секунд — утверждение о предметной области, а не о движке: `Job`, которая
открывает камеру, вполне может идти дольше, и число здесь то, с которого это
приложение считает ожидание долгим.

## Обработанные и необработанные ошибки

Экран запускает задачу и идёт строить дальше: `profile.load()`, и результата
никто не ждёт. Отвечать за ошибку всё равно кому-то придётся.

### Первая попытка

```dart
final class Failures extends SoloObserver {
  @override
  void onFinish(Solo<Object> solo, Job<Object?> job) {
    final outcome = job.outcome;
    if (outcome is Failed) {
      reportCrash(outcome.error, outcome.stackTrace);
    }
  }
}
```

Теперь каждый провал доходит до системы отчётов, и код читается так, будто
за ошибки ответили. Не ответили. Чтение `job.outcome` говорит, что случилось,
не беря за это ответственности, а наблюдатель только наблюдает: само его
наличие не помечает исходы наблюдёнными. Исход `Failed`, который никто
не наблюдает, вдобавок передаётся в зону создания `Job` через
`Zone.handleUncaughtError`, а там необработанная ошибка может завершить
приложение — через мгновение после того, как отчёт о сбое отправили руками.

### Наблюдение исхода

```dart
profile.load().ignore(); // аналог Future.ignore
```

Обращение к `job.done` или `job.value`, а также вызов `job.ignore()` помечают
исход наблюдённым. `ignore()` — для вызывающего кода, которому не нужен
результат и который оставляет диагностику хукам; а тот, кому результат нужен,
берёт его через `await job.value` и отвечает за ошибку, перехватывая её.

Ошибки уборки, колбэков отмены и операций, брошенных через `wait`, передаются
хукам диагностики, а ответить за них контроллеру предлагают через
`onUnanswered`. Без его переопределения и без установленного
`Solo.errorHandler` они попадают в зону создания `Job`. Такая ошибка может
прийти уже после завершения `Job`. Она не заменяет существующий исход отмены.
`Cancelled`, пришедший этим путём — брошенная операция, закончившаяся им, — для
хуков такая же поздняя ошибка, как любая другая, и они её видят. В зону движок
`Cancelled` не отдаёт никогда — ни этим путём, ни любым другим из своих.

Неперехваченная ошибка `job.value` или `ctx.run(child)` остаётся необработанной
ошибкой future по правилам Dart, даже если это `Cancelled`, — это путь самого
Dart в зону и единственный, которым `Cancelled` до неё доходит. Обрабатывайте
эти future через `await`, `catchError` или `ignore()` в зависимости
от ситуации.

## Перехват ошибок внутри тела

Тело управляет камерой. Ему нужно собственное состояние ошибки и устройство,
оставшееся полуоткрытым, возвращённое в исходное положение.

### Первая попытка

```dart
try {
  await ctx.join(hw.open);
  await ctx.join(() => hw.setZoom(zoom));
} on Object catch (error) {
  await hw.reset();
  ctx.emit(Broken(error));
  rethrow;
}
```

`Cancelled` реализует `Exception`, поэтому широкий `catch` забирает и его
вместе с ошибками устройства. Отмените эту задачу, пока `hw.open` в полёте:
`join` бросит `Cancelled`, `catch` прочитает его как ошибку камеры и сбросит
камеру, которую эта задача ни разу не открывала. `ctx.emit` на отменённой
задаче бросает `Cancelled` в свою очередь, так что `Broken` не публикуется
никогда, а `rethrow` под ним не выполняется. Исход — тот самый `Cancelled`,
каким он и был бы, и ни в хуках, ни в зоне про сброс камеры нет ни слова.

### Пропустить отмену дальше

```dart
try {
  await ctx.join(hw.open);
  await ctx.join(() => hw.setZoom(zoom));
} on Cancelled {
  rethrow;
} on Object catch (error) {
  await hw.reset();
  ctx.emit(Broken(error));
  rethrow;
}
```

Отмена уходит первой, а дальше обрабатываются только ошибки устройства. После
принятой отмены исход `Job` остаётся `Cancelled`, даже если тело её
перехватило. Для итогового состояния ошибки предпочтителен параметр `onError`
у `run`, а не коррекция внутри широкого `catch`.

## Ошибки правил состояния

Задача, которой нужен свободный слот, просит его в стартовом правиле.

### Первая попытка

```dart
canStart: (state) {
  if (state.free == 0) throw StateError('no free slot');

  return true;
},
```

Бросок читается как отказ, а является провалом. Ошибка уходит хукам
диагностики — отчёт о сбое ради обычного «не сейчас», — а `Job` заканчивается
`Failed`, и этот исход доходит ещё и до зоны создания, если его никто
не наблюдает. Обработчик `onError` того же `run` за него тоже не отвечает:
обработчик состояния правит состояние после задачи, которая работала, а эта
не стартовала. Очередь переходит к следующей задаче.

### Правило отвечает

```dart
// Правило отвечает; чтобы отказать, оно не бросает исключение.
canStart: (state) => state.free > 0,
```

Правило, ответившее `false`, — не ошибка: оно отменяет `Job`, и `Cancelled`
несёт трассу того изменения, которое правило отвергло, — `emit` или
`externalSetState`, чьё состояние правило нарушило. Взятие этой трассы стоит
почти столько же, сколько само изменение, поэтому её берут там, где включены
проверки, и не берут в релизной сборке. `Solo.traceStateChanges = true`
оставляет её везде, `false` — убирает везде; без неё отмена всё равно несёт
трассу того места, которое заметило.

Где правило всё-таки бросило, решает, кто об этом узнает:

| Где бросило | Что происходит |
| --- | --- |
| Стартовое правило | `Job` проваливается, очередь продолжает работать. |
| Правило в контрольной точке контекста | Ошибку получает тело. |
| Переоценка после обновления состояния | Передаётся для диагностики; работающее тело сама по себе не отменяет. |
| Проверка, управляющая итоговым обработчиком состояния | Обработчик запрещается. |

Когда за ошибки переоценки не отвечает ни переопределённый `onUnanswered`,
ни `Solo.errorHandler`, они попадают в зону создания `Job`. В корневой зоне
Dart необработанная ошибка может завершить приложение. Настройте сообщения
об ошибках и наблюдение исходов в соответствии с требованиями приложения.

## Фоновая работа и логи

Тело отправляет событие аналитики. Задаче нечего тут ждать и нечего отменять:
событие либо уйдёт, либо нет.

### Первая попытка

```dart
unawaited(analytics.send('zoom'));
```

`unawaited` говорит ровно то, что имелось в виду — этот вызывающий код
не ждёт, — и этим всё сказанное исчерпывается. Ошибка этого future в задаче
не принадлежит никому: хуки её не увидят, `Solo.errorHandler` не спросят,
а всплывёт она необработанной ошибкой в той зоне, где случилось работать телу,
и назвать задачу, из которой она пришла, там нечему.

### Работа со своей жизнью

```dart
// Работа со своей жизнью: Job её не ждёт и не отменяет, а ошибки всё
// равно доходят до хуков этой Job.
ctx.unattended(() => analytics.send('zoom'));
```

`ctx.unattended(action)` запускает работу, которую `Job` не ждёт и не отменяет.
Её ошибки передаются хукам ошибок `Job` даже после завершения `Job`; без
обработчика действует тот же переход в зону. Используйте его для работы
с независимым временем жизни. Запуск детей из этой работы запрещён. Захваченный
контекст всё ещё принадлежит исходной `Job`: `emit` может работать, пока `Job`
активна, но отклоняется после отмены или завершения. Фоновая операция
не продлевает время жизни контекста.

### Логи

```dart
// Данные приложения для хуков логирования и наблюдателей.
ctx.log(('zoom', zoom));

// И собственная трасса движка, когда нужно посмотреть на очередь.
Solo.debug = print;
```

`ctx.log(data)` передаёт данные приложения хукам логирования и наблюдателям как
есть, поэтому строку делает тот слушатель, которому она нужна. `Solo.debug`
дополнительно трассирует внутренние операции очереди и жизненного цикла
контроллера.
