# Ошибки и наблюдение

Обработчики состояния и хуки отчёта решают разные задачи. `run(ifFailed: ...)`
вычисляет состояние после ошибки `Job`. Метод контроллера `onError`
и `SoloObserver.onError` получают ошибки для логирования или отправки, включая
ошибки уборки и брошенных операций, а `onUnanswered` отвечает за те, которых
не несёт ни один исход.

Пять разделов ниже открываются той версией, к которой ведёт привычка или
словарь этого API: широким `catch`, `throw` вместо отказа или членом, названным
по вопросу, который вы задаёте. Под ней сказано, что эта версия делает вместо
задуманного. Работающая версия идёт следом под своим заголовком.

## Отправка ошибки

Контроллер может переопределить `onStart`, `onFinish`, `onError`,
`onUnanswered`, `onLog`, `onChange` и `onClose`, а также `onListenerError` для
слушателя, который бросил при оповещении. Контроллеру профиля нужно, чтобы его
сбои попадали в систему отчётов.

```dart
final class ProfileController extends Solo<ProfileState> {
  final ProfileApi api;

  ProfileController(this.api) : super(const Initial());

  // ...задачи из быстрого старта...

  @override
  void onError(Job<Object?> job, Object error, StackTrace stackTrace) =>
      reportCrash(error, stackTrace);
}
```

Хуку рассказывают о каждой ошибке задач этого контроллера: о провале тела,
об ошибке уборки или операции, брошенной `abandonable`, о правиле, которое
бросило вместо ответа. Рассказывают по одному разу на каждую `Job`. Ошибка,
которую бросила дочерняя `Job` и пропустила родительская, становится провалом
обеих: хук слышит её дважды, а различить два вызова даёт переданная ему `job`.
Он отправляет отчёт и возвращается, и это всё, для чего он есть: хук ни за что
не отвечает, и его переопределение не двигает ни одну ошибку никуда.

### Ответ за ошибку

```dart
final class ProfileController extends Solo<ProfileState> {
  // ...задачи и хук отчёта выше...

  @override
  void onUnanswered(Job<Object?> job, Object error, StackTrace stackTrace) =>
      _apiFailures.add(error);
}
```

Почти каждую ошибку несёт исход задачи. Провал тела становится `Failed`,
по нему `run(ifFailed: ...)` вычисляет состояние, а исход, которого никто
не наблюдал, сам доходит до зоны создания `Job`. Исход не несёт остального:

- операции, брошенной `abandonable` и упавшей позже;
- того, что `Job` зовёт вне своего тела: уборщика, колбэка `ctx.onCancel`,
  слушателя `whenCancelled`, обработчика состояния у `run`;
- `keepWhile`, который бросил, когда его перепроверяло изменение состояния;
- работы, отданной `ctx.unattended`;
- провала ветки `ctx.runAll`, который группа не бросила;
- провала тела, если после него до задачи дошла отмена, до того как ошибка
  вышла из тела или пока задача ещё ждала своих дочерних или шла её уборка:
  кто бы ни читал такой исход, он получает отмену.

За них кто-то должен ответить, и спрашивают всегда одного: `onUnanswered` того
контроллера, чья это была задача.

Переопределение выше отвечает за них здесь, и дальше они не идут никуда: этот
контроллер владеет тем, на чём упали его задачи, и сказал об этом.
У контроллера без такого переопределения остаётся тело по умолчанию, и оно
передаёт их в `Solo.unansweredHandler`. Этот обработчик задаёт приложение:

```dart
Solo.unansweredHandler = (solo, job, error, stackTrace) =>
    Sentry.captureException(error, stackTrace: stackTrace);
```

Обработчик один на всё приложение, ставится один раз при старте. Если
обработчика нет, такие ошибки уходят в зону создания `Job`. Ошибка приходит
в `onUnanswered`, а `onUnanswered` зовёт `Solo.unansweredHandler`, поэтому
каждый контроллер решает за свои задачи, услышит ли их общий обработчик
приложения вообще. Переопределение сохраняет и этот маршрут, если позвать
`super.onUnanswered(job, error, stackTrace)`.

`onUnanswered` и `Solo.unansweredHandler` получают по одному провалу за раз.
Когда ошибкой оказывается `ParallelWaitError`, который `[a, b].wait` бросает
с несколькими ошибками внутри, каждый провал приходит отдельным вызовом
и со своим стеком. Неперехваченный `Cancelled`, отдельный или вложенный в него,
не приходит вовсе. Хук отчёта `onError` слышит их так же, по одной, и каждый
`Cancelled` тоже.

Одной ошибки, которую не несёт исход, в этом списке нет, и ответа за неё
не спрашивают ни у кого. Это провал тела, случившийся после того, как `Job`
приняла отмену: например, падает вызов, которого ещё дожидается `ctx.join`.
`Job` кончается `Cancelled`, об ошибке рассказывают хуку `onError`, и дальше
она не идёт. Чаще всего так кончается сама операция, которую отмена остановила:
останавливаясь, она бросает. Отличить от этого настоящий сбой операции движок
не может. Тело, которое ловит такую ошибку само, спрашивает у `Job`,
а не у ошибки: такой `catch` показан в разделе
[Пропустить отмену дальше](#пропустить-отмену-дальше).

Ответственность за ошибку кто-то берёт на себя сам, она не появляется побочным
эффектом включённого лога. Поставленный `SoloObserver` тоже ни за что
не отвечает: наблюдать не значит отвечать.

## Наблюдение за всеми контроллерами

`SoloObserver` рассказывают то же, что контроллерам: `onStart`, `onFinish`,
`onError`, `onLog`, `onChange` и `onClose` от каждого контроллера процесса,
а ещё `onCreate`. `onUnanswered` и `onListenerError` остаются только
у контроллера. Установите наблюдателя при запуске приложения:

```dart
final class LoggingObserver extends SoloObserver {
  @override
  void onStart(Solo<Object> solo, Job<Object?> job) => print('$job started');

  @override
  void onFinish(Solo<Object> solo, Job<Object?> job) =>
      print('$job finished ${job.outcome}');

  @override
  void onChange(Solo<Object> solo, SoloTransition<Object> transition) =>
      print('${transition.job ?? 'external'}: ${transition.current}');
}

void main() {
  Solo.observer = LoggingObserver();
}
```

Хук `onChange` получает `SoloTransition`: состояние до и после, `job`, которой
принадлежит изменение, и `revision`, растущий на единицу за изменение, так что
два перехода упорядочены даже когда хук поменял состояние ещё раз изнутри
первого. В `job` лежит та `Job`, чей `emit` сделал изменение или чей обработчик
состояния его вернул: для `externalSetState` там `null`, а у дочерней задачи
это она сама, а не корневая, которой она принадлежит. Это поле отвечает
на вопрос, кто изменил состояние, а снаружи движка это не выводится.

Наблюдатель вызывается перед одноимённым хуком контроллера. Каждый вызов
независим; отсутствие `super` в хуке контроллера не отключает наблюдателя.
Ошибка любого из них передаётся в текущую зону Dart, не меняя исход `Job`,
не останавливая очередь и не препятствуя вызову второго хука.

Наблюдатель только наблюдает. Его наличие никак не влияет на то, куда дальше
пойдёт ошибка.

## Что удерживает контроллер

`close()` ждёт работающую `Job`, а `Job` может не торопиться. Контроллер
говорит, чего именно он ждёт:

```dart
unawaited(controller.close().timeout(
  const Duration(seconds: 5),
  onTimeout: () => log('closing is held by ${controller.pending}'),
));
```

Пока контроллер ждёт `Job`, `pending` возвращает `SoloPendingJob`, снимок этой
`Job`:

| Поле | Что говорит |
| --- | --- |
| `job` | `Job`, которую ждут |
| `phase` | чем она занята: `body`, `children`, `cleanup` |
| `cancellation` | отмена, которую она приняла, иначе `null` |
| `heldCancellation` | отмена, которую держит открытая секция `ctx.uncancellable` |
| `children` | сколько детей она ещё ждёт |
| `inUncancellableSection` | открыта ли такая секция |
| `cancellable` | принимает ли она отмену, которую может отклонить |
| `closing` | позвали ли у контроллера `close()` |
| `draining` | дренаж ли этот `close()`: тогда `Job` доработает до конца |

Рядом с полями снимок считает и один свой ответ:
`SoloPendingJob.cancellationPending` истинно, когда есть любая из двух отмен
выше, принятая или придержанная. `Job`, у которой `cancellable` равно `false`,
отклоняет те отмены, которые может отклонить, и тогда ждать нечего, сколько бы
раз её ни просили остановиться.

Кроме `Job`, закрытие ждёт ещё двух вещей. Их `pending` тоже называет. Дренаж,
то есть `close(mode: SoloCloseMode.drain)`, ждёт ещё и очередь, а группа
`collect` или `accumulate` стоит в ней, пока её не отпустит тайминг. Если `Job`
в это время не работает, `pending` возвращает `SoloPendingQueue`, и в его
`jobs` лежит то, что дренажу ещё предстоит запустить. У `SoloStream` стрим
закрывается после движка и ждёт, пока каждая подписка получит событие
завершения. Подписка, оставленная на паузе, держит `close()`, хотя `isFinished`
уже истинно, и тогда `pending` возвращает `SoloPendingStream`. Печатаются все
три одинаково, так что строке выше `switch` не нужен:

```text
closing is held by SoloPending([stuck] in its body, closing, cancelled by Cancelled(closed))
closing is held by SoloPending(draining, 1 queued: [group])
closing is held by SoloPending(stream: a subscription has not taken its done event)
```

`null` говорит, что закрытие не держит ничто, о чём знает контроллер. Таймер
читает `pending` между шагами закрытия, а синхронный хук посреди шага:
`onFinish` последней `Job` и `onClose` видят `null`, хотя `close()` ещё
не вернулся.

Снимок отвечает тому, кто спросил, а пример выше спрашивает на `close()`.
О `Job`, которая зависла раньше, пока экран ещё открыт и никто ничего
не закрывает, не спрашивает никто. Спросить, когда никто не просит, может
наблюдатель: он заводит таймер, когда `Job` начинается, и снимает его, когда
она кончилась:

```dart
final class Hangs extends SoloObserver {
  // Expando держит ключ слабо: таймер уходит вместе с задачей.
  final _timers = Expando<Timer>('hang');

  @override
  void onStart(Solo<Object> solo, Job<Object?> job) => _timers[job] = Timer(
        const Duration(seconds: 5),
        () => log('${job.key} is still running: ${solo.pending}'),
      );

  @override
  void onFinish(Solo<Object> solo, Job<Object?> job) => _timers[job]?.cancel();
}
```

`Job`, которая успела кончиться, снимает свой таймер сама и молчит. Ту, что
не успела, строка называет в начале. Снимок рядом с именем снят с корневой
`Job`, на которой стоит контроллер, и это та же самая `Job`, если только
зависла не дочерняя:

```text
stuck is still running: SoloPending([stuck] in its body)
held is still running: SoloPending([held] in its body, holding Cancelled(manual) back)
```

Таймер заводится на старте, потому что другого конца у зависания нет:
`onFinish` для `Job`, которая не кончается, не придёт никогда. Рецепт раздела
[Почему отмена была долгой](#почему-отмена-была-долгой) считает задержку как
раз на `onFinish` и потому о зависании не скажет ничего.

Пять секунд говорят о предметной области, а не о движке: `Job`, которая
открывает камеру, вполне может идти дольше, и число здесь то, с которого это
приложение считает ожидание долгим.

`Hangs` только сообщает: `Job`, которую он назвал, продолжает идти. `Job`,
которая должна остановиться на своём пределе, получает этот предел сама,
`run(timeout: ...)`, и кончается `Cancelled(timeout)`, когда он выходит; так
сделано в разделе [«Срок задачи»](cancellation.md#срок-задачи) на странице
об отмене.

Снимок сообщает, а не ставит диагноз. Долгое ожидание не доказывает забытый
`ctx.abandonable`. Тело внутри внешнего вызова, которого оно обязано дождаться,
даёт тот же снимок, с фазой `body`. Ресурс, который освобождается долго, держит
`Job` столько же, и тогда фаза `cleanup`. Фаза говорит, где `Job`, а не почему:
пока работает тело, фаза `body`, чего бы оно ни ждало, и движок не гадает.

## Почему отмена была долгой

`SoloPendingJob` отвечает, пока `Job` ещё работает. Вторая половина вопроса
приходит потом и там, где никто не смотрит: какие задачи работали дальше,
несмотря на отмену, которая должна была их остановить, и сколько.

### Первая попытка

```dart
final class SlowJobs extends SoloObserver {
  final _startedAt = Expando<DateTime>('start');

  @override
  void onStart(Solo<Object> solo, Job<Object?> job) =>
      _startedAt[job] = clock.now();

  @override
  void onFinish(Solo<Object> solo, Job<Object?> job) {
    final startedAt = _startedAt[job];
    if (startedAt == null) return;
    final ran = clock.now().difference(startedAt);
    if (ran > const Duration(milliseconds: 50)) {
      log('${job.key} ran ${ran.inMilliseconds} ms');
    }
  }
}
```

`onStart` и `onFinish` приходят на двух концах задачи, и разница между ними
равна времени её жизни. Задача, которая шла 300 мс, потому что работа занимает
300 мс, даёт ту же строку, что и задача, отменённая на десятой миллисекунде
и всё равно доработавшая до конца. Искать стоит вторую, а эти два хука их
не различают.

### Отметка отмены

```dart
final class SlowCancellations extends SoloObserver {
  // Expando держит ключ слабо: запись уходит вместе с задачей,
  // и чистить нечего.
  final _markedAt = Expando<DateTime>('cancellation');

  @override
  void onStart(Solo<Object> solo, Job<Object?> job) {
    // whenCancelled срабатывает, когда Job приняла отмену, а не когда
    // позвали cancel(): сперва кончится секция ctx.uncancellable.
    job.whenCancelled((_) => _markedAt[job] = clock.now());
  }

  @override
  void onFinish(Solo<Object> solo, Job<Object?> job) {
    final markedAt = _markedAt[job];
    if (markedAt == null) return;
    final delay = clock.now().difference(markedAt);
    if (delay > const Duration(milliseconds: 50)) {
      log('${job.key} ran ${delay.inMilliseconds} ms past its cancellation');
    }
  }
}
```

Задачу, которую никто не отменял, не отмечают и не сообщают о ней, сколько бы
она ни шла. Число считается от момента, когда `Job` приняла отмену,
а не от `cancel()`, и до исхода, вместе с детьми и уборкой. Отмену, пришедшую,
пока открыта секция `ctx.uncancellable`, `Job` принимает, когда секция
кончается: секция на 100 мс, отменённая на десятой, даёт 0 мс, а вызвавший
`cancel` или `close` ждал 90 мс.

Смотреть на число стоит ради одной конкретной ошибки. Тело, ждущее что-то
долгое голым `await`, замечает отмену, только когда ожидание кончится, а тот же
вызов через `ctx.abandonable` перестаёт ждать сразу, как и задержка, записанная
через `ctx.pause`. Ожидание на 300 мс, отменённое на десятой:

| как тело ждёт | число |
| --- | --- |
| `await Future.delayed(...)` | 290 мс |
| `ctx.abandonable(() => Future.delayed(...))` | 0 мс |
| `ctx.pause(...)` | 0 мс |

Строкой в логе станет только первая: две другие не дотягивают до 50 мс,
с которых наблюдатель начинает сообщать.

Задача, отменённая до старта, не сообщает ничего: `onStart` для неё не зовут
вовсе, значит регистрации и отметки не было. Замечать отмену было некому,
и в контроллере под это попадает всё, что выброшено из очереди.

`clock.now()`, а не `DateTime.now()`: под `fake_async` первый идёт вместе
с фальшивым временем, а второй стоит на месте, так что того же наблюдателя
можно проверить тестом. Наблюдатель работает в приложении, поэтому
`package:clock` идёт в его зависимости, а не в зависимости разработки; пакет
этот без своих зависимостей, и `fake_async` и так от него зависит везде, где
идут тесты.

### Отмена, которая не доходит

```dart
final class StuckCancellations extends SoloObserver {
  final _timers = Expando<Timer>('cancellation');

  @override
  void onStart(Solo<Object> solo, Job<Object?> job) => job.whenCancelled(
        (_) => _timers[job] = Timer(
          const Duration(seconds: 5),
          () => log('${job.key} has not stopped: ${solo.pending}'),
        ),
      );

  @override
  void onFinish(Solo<Object> solo, Job<Object?> job) => _timers[job]?.cancel();
}
```

Отметку выше читают, когда `Job` кончается, и потому о самой долгой отмене
из всех, о той, что не кончается, она как раз молчит. Здесь отметка становится
таймером: `whenCancelled` его заводит, конец `Job` снимает, и остаётся ровно та
`Job`, которую попросили остановиться, а она не остановилась:

```text
ignores has not stopped: SoloPending([ignores] in its body, cancelled by Cancelled(manual))
```

`Job`, которую никто не отменял, здесь не заводит таймера, сколько бы
ни работала: этот наблюдатель о неисполненной отмене, а не о долгой работе.
Пока открыта секция `ctx.uncancellable`, не видит он и `Job`, которую за это
время отменили: секция эту отмену придерживает, и `whenCancelled` сработает,
когда секция закроется. Пять секунд идут с этого момента. Дочерняя `Job`,
до которой отмена дошла от родительской, получает свою строку, и снимок в этой
строке снова снят с корневой.

`Solo.observer` держит одного наблюдателя, а ставить с этой страницы пора уже
четверых. `SoloObserver.all` складывает их в одного:

```dart
Solo.observer = SoloObserver.all([
  LoggingObserver(),
  Hangs(),
  SlowCancellations(),
  StuckCancellations(),
]);
```

Каждый хук идёт каждому из них в порядке списка, и каждый вызов сам по себе:
тот, кто бросил исключение, отдаёт его в зону, а следующий всё равно
вызывается. Если один и тот же наблюдатель в списке дважды, `SoloObserver.all`
бросает `ArgumentError`.

## Обработанные и необработанные ошибки

Экран запускает задачу и идёт строить дальше: `profile.load()`, и результата
никто не ждёт. Отвечать за ошибку всё равно кому-то придётся.

### Первая попытка

```dart
final class Failures extends SoloObserver {
  @override
  void onFinish(Solo<Object> solo, Job<Object?> job) {
    final outcome = job.outcome;
    if (outcome is Failed) {
      reportCrash(outcome.error, outcome.stackTrace);
    }
  }
}
```

Теперь каждый провал доходит до системы отчётов, и код читается так, будто
за ошибки ответили. Не ответили. Чтение `job.outcome` говорит, что случилось,
не беря за это ответственности, а наблюдатель только наблюдает: само его
наличие не помечает исходы наблюдёнными. Исход `Failed`, который никто
не наблюдает, вдобавок передаётся в зону создания `Job` через
`Zone.handleUncaughtError`, а там необработанная ошибка может завершить
приложение через мгновение после того, как отправили отчёт о сбое.

### Наблюдение исхода

```dart
profile.load().ignoreFailure();
```

Обращение к `job.done` или `job.value`, а также вызов `job.ignoreFailure()`
помечают исход наблюдённым. `ignoreFailure()` пишет вызывающий код, которому
результат не нужен и который оставляет отчёты хукам; а тот, кому результат
нужен, берёт его через `await job.value` и отвечает за ошибку, перехватывая её.
Одну ошибку он не перехватит: если загрузка падает, а после этого до задачи
доходит отмена, до того как ошибка вышла из тела или пока задача ещё ждёт своих
дочерних или идёт её уборка, `await job.value` бросает `Cancelled`, а провал
уходит в `onUnanswered`, как ошибки ниже. `ignoreFailure()` гасит и его.

Ошибки уборки, колбэков отмены и операций, брошенных через `abandonable`,
передаются хукам отчёта, а ответить за них контроллеру предлагают через
`onUnanswered`. Их берёт на себя либо его переопределение, либо установленный
`Solo.unansweredHandler`; когда нет ни того, ни другого, они попадают в зону
создания `Job`. Такая ошибка может прийти уже после завершения `Job`. Она
не заменяет существующий исход отмены. О `Cancelled`, пришедшем этим путём,
например когда брошенная операция закончилась отменой другой `Job`, узнают хуки
отчёта, а ответа за него не спрашивают ни у кого: он не доходит
ни до `onUnanswered`, ни до `Solo.unansweredHandler`, ни до зоны. Собственная
отмена этой `Job`, которую такая операция бросила обратно, ни для кого
не новость, и о ней не сообщают вовсе.

Неперехваченная ошибка `job.value` или `ctx.run(child)` остаётся необработанной
ошибкой future по правилам Dart, даже если это `Cancelled`: этот путь в зону
принадлежит самому Dart, а не движку. Обрабатывайте эти future как любые
другие: ждите их через `await` там, где ошибку перехватят, или дайте им
`onError` либо `Future.ignore()`. `job.ignoreFailure()` этого за них
не сделает: вызов говорит `Job`, что её провал никому не нужен, а future,
которую уже взяли у `job.value`, остаётся обычной future, и её ошибку всё равно
надо обработать.

## Перехват ошибок внутри тела

Тело управляет камерой. Ему нужно собственное состояние ошибки и устройство,
оставшееся полуоткрытым, возвращённое в исходное положение.

### Первая попытка

```dart
try {
  await ctx.join(hw.open);
  await ctx.join(() => hw.setZoom(zoom));
} on Object catch (error) {
  await hw.reset();
  ctx.emit(Broken(error));
  rethrow;
}
```

`Cancelled` реализует `Exception`, поэтому широкий `catch` забирает и его
вместе с ошибками устройства. Отмените эту задачу, пока `hw.setZoom` в полёте:
`join` дождётся вызова и бросит `Cancelled` вместо его результата, а `catch`
прочитает это как ошибку камеры. Он сбросит камеру, которая открылась и приняла
зум, а тот, кто отменил задачу, будет вынужден ждать ещё и сброса.

Две строки под сбросом не меняют ничего. `ctx.emit` на отменённой задаче
бросает `Cancelled` в свою очередь, так что `Broken` не доходит до экрана,
а `rethrow` под ним не выполняется, и исход тот же `Cancelled`, который дал бы
`rethrow`. Потому сброс и трудно заметить: задача кончается ровно так, как
положено отменённой, ни в хуках, ни в зоне о ней ни слова, а единственный след
остался на устройстве.

### Пропустить отмену дальше

```dart
try {
  await ctx.join(hw.open);
  await ctx.join(() => hw.setZoom(zoom));
} on Object catch (error) {
  ctx.check();
  await hw.reset();
  ctx.emit(Broken(error));
  rethrow;
}
```

`ctx.check()` спрашивает у `Job`, а не у ошибки. Что бы ни поймал `catch`, этот
вызов бросает `Cancelled` самой `Job`, если она приняла отмену, и строки ниже
обрабатывают сбои только той `Job`, которую никто не отменял.

Секция, которая спрашивает у ошибки, умеет меньше. `on Cancelled { rethrow; }`
перед широкой секцией или `if (error is Cancelled) rethrow;` первой её строкой
работает, пока каждый вызов в `try` идёт до конца, как эти два. Вызов
с токеном, которому `ctx.onCancel` велит остановиться, как в разделе
[«Токен»](cancellation.md#токен) страницы об отмене, и который останавливается
броском, присылает в `catch` вместо `Cancelled` собственную ошибку: `join`
бросает ошибку своего вызова как есть. Такая секция её пропускает, и камеру
снова сбрасывают по отмене. Эту секцию разбирает раздел
[«Перехват ошибок операции»](../async_job/cancellation.md#перехват-ошибок-операции)
страницы об отмене пакета `async_job`.

У вопроса к `Job` есть оборотная сторона: камеру, которая сама упала после
того, как `Job` приняла отмену, этот `catch` тоже не сбрасывает, и о таком сбое
не слышит ни один хук. На отменённой `Job` этот `catch` только выпускает
отмену.

После принятой отмены исход `Job` остаётся `Cancelled`, даже если тело её
перехватило. Для итогового состояния ошибки предпочтителен параметр `ifFailed`
у `run`, а не коррекция внутри широкого `catch`.

## Ошибки правил состояния

Задача, которой нужен свободный слот, просит его в стартовом правиле.

### Первая попытка

```dart
canStart: (state) {
  if (state.free == 0) throw StateError('no free slot');

  return true;
},
```

Бросок читается как отказ, а оказывается провалом. Ошибка уходит хукам отчёта,
и получается отчёт о сбое ради обычного «не сейчас», а `Job` заканчивается
`Failed`, и этот исход доходит ещё и до зоны создания, если его никто
не наблюдает. Обработчик состояния, переданный тому же `run` как `ifFailed`,
для неё не вызывается: обработчик состояния вычисляет состояние после задачи,
которая работала, а эта не стартовала. Очередь переходит к следующей задаче.

### Правило отвечает

```dart
// Правило отвечает; чтобы отказать, оно не бросает исключение.
canStart: (state) => state.free > 0,
```

Ответ `false` от правила ошибкой не считается: он отменяет `Job`, и трассу
такого `Cancelled` берут там, где правило ответило «нет». `keepWhile`,
перепроверенный на изменении, отвечает «нет» изнутри него, и потому трасса
ведёт к самому изменению: к `emit` или `externalSetState`, чьё состояние
нарушило правило.

Там, где правило отвечает «нет» вдали от изменения, трасса называет место,
которое заметило. `canStart` спрашивают один раз, когда `Job` уходит
из очереди, и трасса называет очередь. А `Job`, нарушившую собственное правило,
на её же `emit` не перепроверяют: она узнаёт об этом на ближайшей контрольной
точке, будь то `ctx.state`, `ctx.check()` или ожидающий метод, и трасса
называет эту контрольную точку.

От того, где правило всё-таки бросило, зависит, что станет с ошибкой:

| Где бросило | Что происходит |
| --- | --- |
| Стартовое правило | `Job` проваливается, очередь продолжает работать. |
| Правило в контрольной точке контекста | Ошибку получает тело. |
| Переоценка после обновления состояния | О ней сообщают; работающее тело она сама не отменяет. |
| Та же переоценка у `Job` с обработчиком состояния | О ней сообщают, а обработчик запрещается. |

`Job` с обработчиком состояния перепроверяют и после конца её тела, об этом
раздел
[«Допуск обработчиков и их ошибки»](state.md#допуск-обработчиков-и-их-ошибки)
страницы о состоянии. Когда за ошибки переоценки не отвечает
ни переопределённый `onUnanswered`, ни `Solo.unansweredHandler`, они попадают
в зону создания `Job`. В корневой зоне Dart необработанная ошибка может
завершить приложение. Настройте сообщения об ошибках и наблюдение исходов так,
как нужно приложению.

## Фоновая работа и логи

Тело отправляет событие аналитики. Задаче нечего тут ждать и нечего отменять:
событие либо уйдёт, либо нет.

### Первая попытка

```dart
unawaited(analytics.send('zoom'));
```

`unawaited` говорит ровно то, что имелось в виду: этот вызывающий код не ждёт.
Больше он не говорит ничего. Ошибка этой future в задаче не принадлежит никому:
хуки её не увидят, `Solo.unansweredHandler` не спросят, а всплывёт она
необработанной ошибкой в той зоне, где случилось работать телу, и назвать
задачу, из которой она пришла, там нечему.

### Работа со своей жизнью

```dart
// Работа со своей жизнью: Job её не ждёт и не отменяет, а ошибки всё
// равно доходят до хуков этой Job.
ctx.unattended(() => analytics.send('zoom'));
```

`ctx.unattended(action)` запускает работу, которую `Job` не ждёт и не отменяет.
Её ошибки остаются за `Job` даже после завершения `Job`: о них рассказывают
хукам отчёта, ответа спрашивают у `onUnanswered`, а когда ответить некому, они
кончаются в зоне создания `Job`. Используйте его для работы с независимым
временем жизни.

Эта работа не сама `Job`, и контекст отказывает в ней всему, что действует
на `Job`: `ctx.run`, `ctx.runAll`, `ctx.each` и `ctx.uncancellable` бросают
`StateError` с именем вызова, для `ctx.run` это
`cannot run a child inside unattended work`. Этот бросок считается ошибкой той
самой работы, поэтому он идёт дорогой, названной выше, к хукам, а сама `Job`
всё равно кончается `Done`.

Захваченный контекст всё ещё принадлежит исходной `Job`: `emit` может работать,
пока `Job` активна, но отклоняется после отмены или завершения. Фоновая
операция не продлевает время жизни контекста.

### Логи

```dart
// Данные приложения для хуков логирования и наблюдателей.
ctx.log(('zoom', zoom));

// И собственная трасса движка, когда нужно посмотреть на очередь.
Solo.debug = print;

// И трасса ядра по каждой задаче: запуск, ошибки, отмена, исход.
Job.debug = print;
```

`ctx.log(data)` передаёт данные приложения хукам логирования и наблюдателям как
есть, поэтому строку делает тот слушатель, которому она нужна. `Solo.debug`
дополнительно трассирует внутренние операции очереди и жизненного цикла
контроллера. Запуск каждой задачи, её ошибки, дошедшую до неё отмену и исход
трассирует `Job.debug`, канал ядра; обе стороны видны, когда включены оба
канала.

По дороге `ctx.log` тоже ничего не зовёт. Там, где строку дорого собирать,
логируйте колбэк, который её соберёт, а звать его или нет, пусть решает
уровень:

```dart
// Строка, которую дорого собирать: логируем колбэк, а не строку.
ctx.log(() => 'zoom to $zoom on ${device.describe()}');

@override
void onLog(Job<Object?> job, Object? message) {
  if (!logger.isLoggable(Level.FINE)) return;
  logger.fine(message is Object? Function() ? message() : message);
}
```

Тело при этом логирует безусловно, а `describe()` выполняется только там, где
этот уровень кто-то слушает. Во всех остальных сборках сообщение так и остаётся
замыканием, которое никто не позвал.
