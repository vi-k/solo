# Ошибки и наблюдение

Задача, которая упала, кончается `Failed`. С её ошибкой имеют дело три части
кода:

- `run(ifFailed: ...)` превращает провал в состояние, которое показывает экран;
- `onError`, хук контроллера, слышит ошибку, чтобы о ней сообщить;
- тот, кто наблюдает исход, отвечает за ошибку.

Когда исход никто не наблюдает, ошибка уходит в зону создания, то есть в зону,
где задачу создали. Там она неперехваченная ошибка, а в корневой зоне
неперехваченная ошибка может завершить приложение. У некоторых ошибок нет
исхода, который бы их нёс, и за них отвечает `onUnanswered`. Раздел
[«Куда уходит каждая ошибка»](#куда-уходит-каждая-ошибка) перечисляет все виды.



Строки под некоторыми блоками — то, что печатает код. `report:` — ошибка,
переданная сервису отчётов о сбоях, а `zone:` — ошибка, которая дошла до зоны
создания неперехваченной.

## Отправка ошибки

Контроллер профиля отправляет провалы своих задач в сервис отчётов о сбоях:

```dart
final class ProfileController extends Solo<ProfileState> {
  final ProfileApi api;

  ProfileController(this.api) : super(const Initial());

  // ...задачи из быстрого старта...

  @override
  void onError(Job<Object?> job, Object error, StackTrace stackTrace) =>
      reportCrash(error, stackTrace);
}
```

У контроллера есть хук на каждое событие с ним самим и с его задачами:
`onStart`, `onFinish`, `onError`, `onUnanswered`, `onLog`, `onChange`
и `onClose`, а ещё `onListenerError` для слушателя, который бросил при
оповещении. `onError` слышит ошибки, на которые наткнулись задачи контроллера:

- провал тела;
- ошибку уборки или операции, которую `abandonable` перестал ждать;
- правило, которое бросило вместо ответа.

Он слышит каждую ошибку по одному разу на каждую задачу. Ошибка, которую
бросила дочерняя задача и пропустила родительская, становится провалом обеих:
хук слышит её дважды, а различить два вызова даёт переданная ему `job`. Сервис
отчётов о сбоях, которого кормят отсюда, может получить одну ошибку трижды:
от дочерней задачи, от родительской и, если исход родительской никто
не наблюдает, из зоны создания.

Хук отправляет отчёт и возвращается. Он ни за что не отвечает, и его
переопределение не двигает ни одну ошибку никуда.

## Обработанные и необработанные ошибки

Экран запускает задачу профиля из быстрого старта, у которого нет своего хука
отчёта: `profile.load()`, и результата никто не ждёт. Сети нет, и `fetchName`
бросает. Приложению нужно, чтобы провал попал в сервис отчётов о сбоях,
и больше ничего.

### Первая попытка

`SoloObserver` слышит хуки всех контроллеров, как показывает раздел
[«Наблюдение за всеми контроллерами»](#наблюдение-за-всеми-контроллерами).
Поэтому приложение отправляет отчёт из наблюдателя:

```dart
// Первая попытка: сбои всё равно уходят в зону.
final class Failures extends SoloObserver {
  @override
  void onError(
    Solo<Object> solo,
    Job<Object?> job,
    Object error,
    StackTrace stackTrace,
  ) =>
      reportCrash(error, stackTrace);
}
```

```text
report: Bad state: no network
zone: Bad state: no network
```

Отчёт уходит, а следом та же ошибка доходит до зоны. Вот что происходит:

1. Загрузка падает, и задача кончается `Failed`. `onError` наблюдателя слышит
   ошибку и отправляет отчёт.
2. Хук, которому рассказали о провале, исход не наблюдает, какой бы это ни был
   хук. Исход загрузки никто не прочитал.
3. `Failed`, который никто не наблюдал, уходит в зону создания через
   `Zone.handleUncaughtError`. В корневой зоне это может завершить приложение
   через мгновение после того, как отправили отчёт.

### Наблюдение исхода

Наблюдатель остаётся, а экран наблюдает исход:

```dart
profile.load().ignoreFailure();
```

```text
report: Bad state: no network
```

Обращение к `job.done` или `job.value`, а также вызов `job.ignoreFailure()`
помечают исход наблюдённым. Чтение `job.outcome` исход наблюдённым не делает.
`ignoreFailure()` пишет вызывающий код, которому результат не нужен и который
оставляет отчёты хукам. Тот, кому результат нужен, берёт его через
`await job.value` и отвечает за ошибку, перехватывая её.

Одну ошибку такой код не перехватит. Если задача кончилась `Cancelled` после
того, как загрузка упала, `await job.value` бросает `Cancelled`, а провал
уходит в `onUnanswered`, как показывает следующий раздел. `ignoreFailure()`
гасит и его.

## Ответ за ошибку

Большую часть ошибок несёт исход: провал тела становится `Failed`, и за него
отвечает тот, кто его наблюдает. У некоторых ошибок нет исхода, который бы их
нёс, и за них отвечает в `onUnanswered` контроллер, чья это была задача. Здесь
профиль складывает их в список:

```dart
final class ProfileController extends Solo<ProfileState> {
  // ...задачи и хук отчёта выше...

  @override
  void onUnanswered(Job<Object?> job, Object error, StackTrace stackTrace) =>
      _apiFailures.add(error);
}
```

Вот ошибки, которых не несёт ни один исход:

- операция, которую `abandonable` перестал ждать, если она упала позже;
- то, что задача зовёт вне своего тела: уборщик, колбэк `ctx.onCancel`,
  слушатель `whenCancelled` или `whenFinished`, обработчик состояния у `run`;
- `keepWhile`, который бросил, когда его перепроверяло изменение состояния;
- работа, отданная `ctx.unattended`;
- провал ветки `ctx.runAll`, который группа не бросила;
- провал тела задачи, которая кончается `Cancelled`: кто бы ни читал такой
  исход, он получает отмену.

Переопределение выше отвечает за них, и дальше они не идут никуда. Этот
контроллер владеет тем, на чём упали его задачи, и сказал об этом.

У контроллера без такого переопределения остаётся тело по умолчанию. Оно
передаёт ошибку в `Solo.unansweredHandler`, один обработчик на всё приложение,
который ставится один раз при старте:

```dart
Solo.unansweredHandler = (solo, job, error, stackTrace) =>
    Sentry.captureException(error, stackTrace: stackTrace);
```

Если обработчика нет, ошибка уходит в зону создания. Переопределение сохраняет
и этот маршрут, если позовёт `super.onUnanswered(job, error, stackTrace)`. Так
каждый контроллер решает, услышит ли его ошибки обработчик приложения вообще.

Обработчик или переопределение может бросить, например когда сервис отчётов
недоступен. Ошибка, о которой его спросили, не пропадёт: сначала она уходит
в зону создания, а следом в текущую зону уходит то, что бросил хук. Брошенный
хуком `Cancelled` в зону не попадает, как и сама ошибка, брошенная обратно, так
что эта ошибка доходит до зоны один раз. Хук, который успел сообщить об ошибке
и только потом бросил, сообщит о ней дважды.

`onUnanswered` и `Solo.unansweredHandler` получают по одному провалу за раз.
`ParallelWaitError`, который `[a, b].wait` бросает с несколькими ошибками
внутри, приходит несколькими вызовами, каждый провал со своим стеком.
Неперехваченный `Cancelled`, отдельный или вложенный в него, не приходит вовсе.
`onError` тоже слышит их по одному, и каждый `Cancelled` тоже.

Последний пункт списка чаще всего приходит от самой отмены. Вызов, которого ещё
дожидается `ctx.join`, останавливается на токене, который отменил
`ctx.onCancel`, и, останавливаясь, бросает. Отличить такую ошибку от сбоя
вызова движок не может. Поэтому приложение один раз, при старте, называет такие
ошибки в поле `Job.isCancellationError` ядра. Провал отменённой задачи, который
оно называет, доходит до `onError` и дальше не идёт: его не слышат
ни `onUnanswered`, ни `Solo.unansweredHandler`. Раздел
[«Токен»](cancellation.md#токен) страницы об отмене называет так остановку
плеера, а раздел [«Ошибки отмены»](../async_job/observing.md#ошибки-отмены)
страницы о наблюдении пакета `async_job` разбирает поле. Тело, которое ловит
такую ошибку, спрашивает у задачи, а не у ошибки: такой `catch` показан
в разделе [«Пропустить отмену дальше»](#пропустить-отмену-дальше).

Ответить за ошибку — обязанность, которую кто-то берёт на себя сам. Включённый
лог её не берёт, и поставленный `SoloObserver` тоже: наблюдать не значит
отвечать.

## Куда уходит каждая ошибка

У каждой ошибки задачи две дороги: к хукам, которые её слышат, и к тому, кто
за неё отвечает. В таблице `onError` — это и хук контроллера, и `onError`
у `SoloObserver`: они слышат одни и те же ошибки. `onUnanswered` — это
переопределение у контроллера или тело по умолчанию, то есть
`Solo.unansweredHandler`, а когда обработчика нет, зона создания. Текущая
зона — та, в которой позвали хук. Для того, что происходит в задаче, это зона,
где задачу создали; для изменения через `externalSetState` — зона того, кто его
позвал.

| Ошибка | Кто её слышит | Кто за неё отвечает |
| --- | --- | --- |
| Ошибка тела, и задача кончается `Failed` с ней | `onError` | Тот, кто наблюдает исход; если никто, зона создания |
| Ошибка стартового правила: `canStart` бросил вместо ответа | `onError` | Так же: задача кончается `Failed` с ней |
| Ошибка тела, а задача кончается `Cancelled` | `onError` | `onUnanswered`, если у задачи не звали `ignoreFailure()` |
| Поздняя ошибка операции, которую `abandonable` перестал ждать | `onError` | `onUnanswered` |
| Ошибка уборщика, колбэка `ctx.onCancel`, слушателя `whenCancelled` или `whenFinished` или обработчика состояния у `run` | `onError` | `onUnanswered` |
| `keepWhile`, который бросил, когда его перепроверяло изменение состояния | `onError` | `onUnanswered` |
| Ошибка работы, отданной `ctx.unattended` | `onError` | `onUnanswered` |
| Ошибка ветки `ctx.runAll`, которую группа не бросила | `onError` | `onUnanswered`, если у ветки не звали `ignoreFailure()` |
| Ошибка, которую называет `Job.isCancellationError`, у отменённой задачи | `onError` | Никто |
| `Cancelled` снаружи тела, например от брошенной операции, которая кончилась отменой другой задачи | `onError` | Никто |
| `Cancelled`, который тело выпустило наружу, например отменённой дочерней задачи | Никто | Никто: задача кончается `Cancelled` с ним |
| Собственная отмена задачи, которую брошенная операция бросила обратно | Никто | Никто |
| Ошибка future, которую тело не ждало | Никто | Зона, где работает тело |
| Ошибка, которую бросил хук | Никто | Текущая зона |
| Ошибка, которую бросил слушатель при оповещении | `onListenerError` | `onListenerError`; по умолчанию текущая зона |

Ошибка может дойти и до `onError`, и до зоны, и приложение, которое сообщает
об ошибках в обоих местах, услышит её дважды. Две из дорог к зоне создания
закрывает само приложение: исход никто не наблюдал или за ошибку никто
не отвечает. Первую закрывает наблюдение исхода. Вторую закрывает
переопределённый `onUnanswered` или установленный `Solo.unansweredHandler`.

Ошибка, которую принимает `onUnanswered`, может прийти уже после завершения
задачи. Исход, который у задачи уже есть, она не заменяет.

У Dart есть своя дорога в зону, и движок на ней не стоит. Неперехваченная
ошибка `job.value` или `ctx.run(child)` остаётся необработанной ошибкой future
по правилам Dart, даже если это `Cancelled`. Обрабатывайте эти future как любые
другие: ждите их через `await` там, где ошибку перехватят, или дайте им
`onError` либо `Future.ignore()`. `job.ignoreFailure()` этого за них
не сделает. Вызов говорит задаче, что её провал никому не нужен, а future,
которую уже взяли у `job.value`, остаётся обычной future, и её ошибку всё равно
надо обработать.

## Перехват ошибок внутри тела

Тело управляет камерой. При сбое устройства ему нужно собственное состояние,
`Broken`, и камера, оставшаяся полуоткрытой, возвращённая в исходное положение.

### Первая попытка

Устройство может упасть где угодно, поэтому тело ловит всё:

```dart
// Первая попытка: отмена сбрасывает исправную камеру.
try {
  await ctx.join(hw.open);
  await ctx.join(() => hw.setZoom(zoom));
} on Object catch (error) {
  await hw.reset();
  ctx.emit(Broken(error));
  rethrow;
}
```

Пользователь отменяет эту задачу, пока `hw.setZoom` в полёте. Ничего не упало,
а камеру сбросили. Вот что происходит:

1. `join` дожидается вызова и бросает `Cancelled` вместо его результата.
2. `Cancelled` реализует `Exception`, поэтому широкий `catch` забирает его
   и читает как сбой камеры. Он сбрасывает камеру, которая открылась и приняла
   зум, а тот, кто отменил задачу, ждёт ещё и сброса.
3. `ctx.emit` на отменённой задаче бросает `Cancelled` в свою очередь. `Broken`
   не доходит до экрана, а `rethrow` под ним не выполняется.
4. Исход тот же `Cancelled`, который дал бы `rethrow`.

Задача кончается ровно так, как положено отменённой. Ни в хуках, ни в зоне
о ней ни слова, а единственный след остаётся на устройстве.

### Пропустить отмену дальше

```dart
try {
  await ctx.join(hw.open);
  await ctx.join(() => hw.setZoom(zoom));
} on Object catch (error) {
  ctx.check();
  await hw.reset();
  ctx.emit(Broken(error));
  rethrow;
}
```

`ctx.check()` спрашивает у задачи, а не у ошибки. Он бросает `Cancelled` самой
задачи, если она приняла отмену, что бы ни поймал `catch`. Строки после него
обрабатывают сбои той задачи, которую никто не отменял.

Секция, которая спрашивает у ошибки, умеет меньше. Возьмём
`on Cancelled { rethrow; }` перед широкой секцией или
`if (error is Cancelled) rethrow;` первой её строкой. Такая секция работает,
пока каждый вызов в `try` идёт до конца, как эти два. Вызов, которому велит
остановиться токен, отменённый в `ctx.onCancel`, как в разделе
[«Токен»](cancellation.md#токен) страницы об отмене, может остановиться
броском. Тогда `catch` получает вместо `Cancelled` ошибку вызова, потому что
`join` бросает ошибку своего вызова как есть. Секция её пропускает, и камеру
снова сбрасывают по отмене. Раздел
[«Перехват ошибок операции»](../async_job/cancellation.md#перехват-ошибок-операции)
страницы об отмене пакета `async_job` разбирает эту секцию.

У вопроса к задаче есть оборотная сторона. Камеру, которая сама упала после
того, как задача приняла отмену, этот `catch` тоже не сбрасывает, и о таком
сбое не слышит ни один хук. На отменённой задаче этот `catch` только выпускает
отмену.

После принятой отмены исход задачи остаётся `Cancelled`, даже если тело её
перехватило. Для итогового состояния ошибки берите параметр `ifFailed` у `run`,
а не широкий `catch`.

## Повтор упавшего вызова

Сеть время от времени теряет запрос. Профиль делает три попытки, прежде чем
сдаться, и после каждой ошибки ждёт чуть дольше.

### Первая попытка

Цикл ловит ошибку и ждёт перед следующей попыткой:

```dart
// Первая попытка: отмена дожидается конца задержек.
ctx.emit(const Loading());
for (var attempt = 1;; attempt++) {
  final String name;
  try {
    name = await ctx.abandonable(api.fetchName);
  } on Object {
    if (attempt == 3) rethrow;
    await Future<void>.delayed(Duration(seconds: attempt));
    continue;
  }
  ctx.emit(Loaded(name));
  return name;
}
```

`catch` стоит здесь ради сети, а забирает и отмену. Пользователь отменяет
задачу, пока первый вызов в полёте, и задача кончается через три секунды. Вот
что происходит:

1. `abandonable` бросает `Cancelled`. `catch` засчитывает это как неудачную
   попытку и ждёт секунду.
2. Обычный `Future.delayed` не служит контрольной точкой, поэтому задача
   отсиживает эту секунду целиком.
3. Следующий `abandonable` бросает сразу, не вызывая `fetchName`, и `catch`
   ждёт ещё две секунды.
4. Наружу выходит только третий бросок. Задача кончается `Cancelled` через три
   секунды после отмены.

Всё это время задача держит очередь. Следующая задача ждёт тело, которому уже
нечего делать, и `close()` ждёт его так же.

### Пауза между попытками

```dart
ctx.emit(const Loading());
for (var attempt = 1;; attempt++) {
  final String name;
  try {
    name = await ctx.abandonable(api.fetchName);
  } on Object {
    if (attempt == 3) rethrow;
    await ctx.pause(Duration(seconds: attempt));
    continue;
  }
  ctx.emit(Loaded(name));
  return name;
}
```

`ctx.pause` даёт задержку, которая служит контрольной точкой. Если `catch`
забрал отмену, пауза бросает её снова, ещё не начав ждать. Отмена, пришедшая
во время паузы, обрывает её на месте вместе с таймером. В обоих случаях задача
сразу кончается `Cancelled`. Как и `ctx.check()` в разделе
[«Пропустить отмену дальше»](#пропустить-отмену-дальше), пауза спрашивает
у задачи, а не у ошибки, поэтому `catch` не нужна отдельная секция для отмены.

После третьей ошибки сети `rethrow` выпускает её наружу, и задача кончается
`Failed` с этой ошибкой. `on Object` повторяет любую ошибку вызова, в том числе
баг в разборе ответа. Секция только для ошибок, которые стоит повторять,
например `on SocketException`, кончает задачу на первом же баге. Для отмены ей
тоже ничего не нужно.

### Повтор у вызывающего кода

Пауза в теле при этом всё равно принадлежит задаче. Корневые задачи идут
по одной, поэтому следующая задача профиля ждёт все попытки и все паузы между
ними. Если между попытками должны идти другие задачи, повторяет вызывающий код,
а не тело. Задача здесь `load()` из быстрого старта, которая пробует один раз,
на профиле из раздела [«Отправка ошибки»](#отправка-ошибки).

```dart
Future<Outcome<String>> loadWithRetries(ProfileController profile) async {
  for (var attempt = 1;; attempt++) {
    final outcome = await profile.load().done;
    if (outcome is! Failed || attempt == 3) return outcome;
    await Future<void>.delayed(Duration(seconds: attempt));
  }
}
```

Здесь `Future.delayed` на своём месте: он не принадлежит никакой задаче
и поэтому ничего не держит. Задачи, отправленные за это время, выполняются
в этом промежутке, и `close()` его не ждёт. Как кончается цикл:

- `Cancelled` кончает цикл так же, как `Done`.
- `cancelAll()` во время попытки отменяет её, и цикл возвращает этот
  `Cancelled`.
- `cancelAll()` в промежутке не находит задачи для отмены, и следующая попытка
  после него всё равно начнётся.
- Если закрыть профиль, следующую попытку он отклонит, и цикл вернёт её
  `Cancelled(closed)` в конце промежутка.

Остановить сам промежуток может только вызывающий код. Пока он этого не сделал,
таймер переживает закрытый профиль: виджет-тест, который закрывает профиль
в промежутке, на нём падает, а с циклом в теле проходит. О загрузке,
отправленной в промежутке, цикл тоже не знает: если она удалась, следующая
попытка всё равно загрузит снова.

Каждая попытка здесь отдельная задача, и профиль показывает, чем кончилась
каждая. Между попытками состояние равно `Failure` из `ifFailed`, и экран
показывает ошибку, пока следующая попытка не выпустит `Loading`; при цикле
в теле состояние всё время остаётся `Loading`. Каждая упавшая попытка доходит
и до `onError`, так что сервис отчётов о сбоях получает каждую, а от цикла
в теле он получал только ту ошибку, которой кончилась задача. `done` помечает
каждый исход наблюдённым, поэтому ни одна ошибка попытки не уходит дальше
в зону.

## Ошибки правил состояния

Задача, которой нужен свободный слот, просит его в стартовом правиле.

### Первая попытка

Правило, которое не может продолжать, бросает, как это делает функция:

```dart
// Первая попытка: исключение в canStart означает сбой.
canStart: (state) {
  if (state.free == 0) throw StateError('no free slot');

  return true;
},
```

Бросок читается как отказ, а оказывается провалом. Вот что происходит:

1. Ошибка уходит в `onError`: отчёт о сбое ради обычного «не сейчас».
2. Задача кончается `Failed`, и этот исход доходит до зоны создания, если его
   никто не наблюдает.
3. Обработчик состояния, переданный тому же `run` как `ifFailed`,
   не вызывается. Обработчик состояния вычисляет состояние после задачи,
   которая работала, а эта не стартовала.
4. Очередь переходит к следующей задаче.

### Правило отвечает

```dart
// Правило отвечает; чтобы отказать, оно не бросает исключение.
canStart: (state) => state.free > 0,
```

Ответ `false` от правила ошибкой не считается: он отменяет задачу, и трассу
такого `Cancelled` берут там, где правило ответило «нет». `keepWhile`,
перепроверенный на изменении, отвечает «нет» изнутри него, и потому трасса
ведёт к самому изменению: к `emit` или `externalSetState`, чьё состояние
нарушило правило.

Там, где правило отвечает «нет» вдали от изменения, трасса называет место,
которое заметило. `canStart` спрашивают один раз, когда задача уходит
из очереди, и трасса называет очередь. А задачу, нарушившую собственное
правило, на её же `emit` не перепроверяют: она узнаёт об этом на ближайшей
контрольной точке, будь то `ctx.state`, `ctx.check()`, ожидающий метод или
`ctx.each`, и трасса называет эту контрольную точку.

От того, где правило всё-таки бросило, зависит, что станет с ошибкой:

| Где бросило | Что происходит |
| --- | --- |
| Стартовое правило | `Job` проваливается, очередь продолжает работать. |
| Правило в контрольной точке контекста | Ошибку получает тело. |
| Переоценка после обновления состояния | О ней сообщают; работающее тело она сама не отменяет. |
| Та же переоценка у `Job` с обработчиком состояния | О ней сообщают, а обработчик запрещается. |

Задачу с обработчиком состояния перепроверяют и после конца её тела, об этом
раздел
[«Допуск обработчиков и их ошибки»](state.md#допуск-обработчиков-и-их-ошибки)
страницы о состоянии. Ошибка переоценки идёт той дорогой, которую таблица
раздела [«Куда уходит каждая ошибка»](#куда-уходит-каждая-ошибка) даёт
`keepWhile`: в `onError`, потом в `onUnanswered`, а когда никто не отвечает,
в зону создания.

## Фоновая работа и логи

Тело отправляет событие аналитики. Задаче нечего тут ждать и нечего отменять:
событие либо уйдёт, либо нет.

### Первая попытка

`unawaited` говорит, что вызывающий код не ждёт:

```dart
// Первая попытка: ошибка не принадлежит никому в задаче.
unawaited(analytics.send('zoom'));
```

Больше он не говорит ничего. Ошибка этой future в задаче не принадлежит никому.
Хуки её не увидят, а `Solo.unansweredHandler` не спросят. Она всплывёт
необработанной ошибкой в зоне, где работает тело, а у задачи из очереди это
зона, где задачу создали. Назвать задачу, из которой она пришла, там нечему.

### Работа со своей жизнью

```dart
// Работа со своей жизнью: Job её не ждёт и не отменяет, а ошибки всё
// равно доходят до хуков этой Job.
ctx.unattended(() => analytics.send('zoom'));
```

`ctx.unattended(action)` запускает работу, которую задача не ждёт
и не отменяет. Её ошибки остаются за задачей даже после её завершения: их
слышит `onError`, ответа спрашивают у `onUnanswered`, а когда ответить некому,
они кончаются в зоне создания. Используйте его для работы с независимым
временем жизни.

Запускайте эту работу внутри колбэка. Future, созданная до вызова и только
ожидаемая внутри, падает мимо хуков, в ту зону, где её создали. Раздел
[«Работа, переданная задаче»](../async_job/observing.md#работа-переданная-задаче)
страницы о наблюдении пакета `async_job` проводит эту границу в обе стороны.

Эта работа не сама задача, и контекст отказывает в ней всему, что действует
на задачу: `ctx.run`, `ctx.runAll`, `ctx.each` и `ctx.uncancellable` бросают
`StateError` с именем вызова, для `ctx.run` это
`cannot run a child inside unattended work`. Этот бросок считается ошибкой той
самой работы, поэтому он идёт дорогой, названной выше, к хукам, а сама задача
всё равно кончается `Done`.

Захваченный контекст всё ещё принадлежит исходной задаче: `emit` работает, пока
задача активна, и отклоняется после отмены или завершения. Фоновая работа
не продлевает время жизни контекста.

### Логи

```dart
// Данные приложения для хуков логирования и наблюдателей.
ctx.log(('zoom', zoom));

// И собственная трасса движка, когда нужно посмотреть на очередь.
Solo.debug = print;

// И трасса ядра по каждой задаче: запуск, ошибки, отмена, исход.
Job.debug = print;
```

`ctx.log(data)` передаёт данные приложения хукам логирования и наблюдателям как
есть, поэтому строку делает тот слушатель, которому она нужна. `Solo.debug`
дополнительно трассирует очередь контроллера и его жизненный цикл. Запуск
каждой задачи, её ошибки, дошедшую до неё отмену и исход трассирует
`Job.debug`, канал ядра; обе стороны видны, когда включены оба канала.

По дороге `ctx.log` тоже ничего не зовёт. Там, где строку дорого собирать,
логируйте колбэк, который её соберёт, а звать его или нет, пусть решает
уровень:

```dart
// Строка, которую дорого собирать: логируем колбэк, а не строку.
ctx.log(() => 'zoom to $zoom on ${device.describe()}');

@override
void onLog(Job<Object?> job, Object? message) {
  if (!logger.isLoggable(Level.FINE)) return;
  logger.fine(message is Object? Function() ? message() : message);
}
```

Тело при этом логирует безусловно, а строку вместе с вызовом `describe()`
собирают только там, где этот уровень кто-то слушает. В остальных местах
сообщение так и остаётся замыканием, которое никто не позвал.

## Наблюдение за всеми контроллерами

Приложению нужен лог всех контроллеров процесса, а не одного. Оно ставит
наблюдателя при запуске:

```dart
final class LoggingObserver extends SoloObserver {
  @override
  void onStart(Solo<Object> solo, Job<Object?> job) => print('$job started');

  @override
  void onFinish(Solo<Object> solo, Job<Object?> job) =>
      print('$job finished ${job.outcome}');

  @override
  void onChange(Solo<Object> solo, SoloTransition<Object> transition) =>
      print('${transition.job ?? 'external'}: ${transition.current}');
}

void main() {
  Solo.observer = LoggingObserver();
}
```

`SoloObserver` рассказывают то же, что контроллерам: `onStart`, `onFinish`,
`onError`, `onLog`, `onChange` и `onClose` от каждого контроллера процесса,
а ещё `onCreate`. `onUnanswered` и `onListenerError` остаются только
у контроллера.

Хук `onChange` получает `SoloTransition`: состояние до и после, `job`, которой
принадлежит изменение, и `revision`, растущий на единицу за изменение, так что
два перехода упорядочены даже когда хук поменял состояние ещё раз изнутри
первого. В `job` лежит та задача, чей `emit` сделал изменение или чей
обработчик состояния его вернул: для `externalSetState` там `null`, а когда
изменение сделала дочерняя задача, это она сама, а не корневая, которой она
принадлежит. Это поле отвечает на вопрос, кто изменил состояние, а снаружи
движка это не выводится.

Наблюдатель вызывается перед одноимённым хуком контроллера. Каждый вызов
независим; отсутствие `super` в хуке контроллера не отключает наблюдателя.
Ошибка любого из них передаётся в текущую зону, не меняя исход задачи,
не останавливая очередь и не препятствуя вызову второго хука. Исключение
`Cancelled`, брошенное хуком, в зону не попадает и задачу не отменяет.

Наблюдатель только наблюдает. Его наличие никак не влияет на то, куда дальше
пойдёт ошибка.

## Что удерживает контроллер

`close()` ждёт работающую `Job`, а `Job` может не торопиться. Контроллер
говорит, чего именно он ждёт:

```dart
unawaited(controller.close().timeout(
  const Duration(seconds: 5),
  onTimeout: () => log('closing is held by ${controller.pending}'),
));
```

Пока контроллер ждёт `Job`, `pending` возвращает `SoloPendingJob`, снимок этой
`Job`:

| Поле | Что говорит |
| --- | --- |
| `job` | `Job`, которую ждут |
| `phase` | чем она занята: `body`, `children`, `cleanup` |
| `cancellation` | отмена, которую она приняла, иначе `null` |
| `heldCancellation` | отмена, которую держит открытая секция `ctx.uncancellable` |
| `children` | сколько детей она ещё ждёт |
| `inUncancellableSection` | открыта ли такая секция |
| `cancellable` | принимает ли она отмену, которую может отклонить |
| `closing` | позвали ли у контроллера `close()` |
| `draining` | дренаж ли этот `close()`: тогда `Job` доработает до конца |
| `queued` | `Job`, стоящие за ней в очереди: они стартуют только после неё |

Рядом с полями снимок считает и один свой ответ:
`SoloPendingJob.cancellationPending` истинно, когда есть любая из двух отмен
выше, принятая или придержанная. `Job`, у которой `cancellable` равно `false`,
отклоняет те отмены, которые может отклонить, и тогда ждать нечего, сколько бы
раз её ни просили остановиться.

Кроме `Job`, закрытие ждёт ещё двух вещей, и их `pending` тоже называет:

- Дренаж ждёт ещё и очередь. Группа `collect` или `accumulate` стоит в ней,
  пока её не отпустит тайминг. Если `Job` в это время не работает, `pending`
  возвращает `SoloPendingQueue`, и в его `jobs` лежит то, что дренажу ещё
  предстоит запустить.
- У `SoloStream` стрим закрывается после движка и ждёт, пока каждая подписка
  получит событие завершения. Подписка, оставленная на паузе, держит `close()`,
  хотя `isFinished` уже истинно, и тогда `pending` возвращает
  `SoloPendingStream`.

Печатаются все три одинаково, так что строке выше `switch` не нужен:

```text
closing is held by SoloPending([stuck] in its body, closing, cancelled by Cancelled(closed))
closing is held by SoloPending(draining, 1 queued: [group])
closing is held by SoloPending(stream: a subscription has not taken its done event)
```

`null` говорит, что закрытие не держит ничто, о чём знает контроллер. Таймер
читает `pending` между шагами закрытия, а синхронный хук посреди шага:
`onFinish` последней `Job` и `onClose` видят `null`, хотя `close()` ещё
не вернулся.

Снимок отвечает тому, кто спросил, а пример выше спрашивает на `close()`.
О `Job`, которая зависла раньше, пока экран ещё открыт и никто ничего
не закрывает, не спрашивает никто. Спросить, когда никто не просит, может
наблюдатель: он заводит таймер, когда `Job` начинается, и снимает его, когда
она кончилась:

```dart
final class Hangs extends SoloObserver {
  // Expando держит ключ слабо: таймер уходит вместе с задачей.
  final _timers = Expando<Timer>('hang');

  @override
  void onStart(Solo<Object> solo, Job<Object?> job) => _timers[job] = Timer(
        const Duration(seconds: 5),
        () => log('${job.key} is still running: ${solo.pending}'),
      );

  @override
  void onFinish(Solo<Object> solo, Job<Object?> job) => _timers[job]?.cancel();
}
```

`Job`, которая успела кончиться, снимает свой таймер сама и молчит. Ту, что
не успела, строка называет в начале. Снимок рядом с именем снят с корневой
`Job`, на которой стоит контроллер, и это та же самая `Job`, если только
зависла не дочерняя:

```text
stuck is still running: SoloPending([stuck] in its body)
held is still running: SoloPending([held] in its body, holding Cancelled(manual) back)
```

Таймер заводится на старте, потому что другого конца у зависания нет:
`onFinish` для `Job`, которая не кончается, не придёт никогда. Рецепт раздела
[Почему отмена была долгой](#почему-отмена-была-долгой) считает задержку как
раз на `onFinish` и потому о зависании не скажет ничего.

Пять секунд говорят о предметной области, а не о движке: `Job`, которая
открывает камеру, вполне может идти дольше, и число здесь то, с которого это
приложение считает ожидание долгим.

`Hangs` только сообщает: `Job`, которую он назвал, продолжает идти. `Job`,
которая должна остановиться на своём пределе, получает этот предел сама,
`run(timeout: ...)`, и кончается `Cancelled(timeout)`, когда он выходит; так
сделано в разделе [«Срок задачи»](cancellation.md#срок-задачи) на странице
об отмене.

Снимок сообщает, а не ставит диагноз. Долгое ожидание не доказывает забытый
`ctx.abandonable`. Тело внутри внешнего вызова, которого оно обязано дождаться,
даёт тот же снимок, с фазой `body`. Ресурс, который освобождается долго, держит
`Job` столько же, и тогда фаза `cleanup`. Фаза говорит, где `Job`, а не почему:
пока работает тело, фаза `body`, чего бы оно ни ждало, и движок не гадает.

## Почему отмена была долгой

`SoloPendingJob` отвечает, пока `Job` ещё работает. Вторая половина вопроса
приходит потом и там, где никто не смотрит: какие задачи работали дальше,
несмотря на отмену, которая должна была их остановить, и сколько.

### Первая попытка

Наблюдатель видит оба конца задачи, поэтому меряет время между ними:

```dart
// Первая попытка: время жизни прячет отмену, после которой задача доработала.
final class SlowJobs extends SoloObserver {
  final _startedAt = Expando<DateTime>('start');

  @override
  void onStart(Solo<Object> solo, Job<Object?> job) =>
      _startedAt[job] = clock.now();

  @override
  void onFinish(Solo<Object> solo, Job<Object?> job) {
    final startedAt = _startedAt[job];
    if (startedAt == null) return;
    final ran = clock.now().difference(startedAt);
    if (ran > const Duration(milliseconds: 50)) {
      log('${job.key} ran ${ran.inMilliseconds} ms');
    }
  }
}
```

Время между `onStart` и `onFinish` равно времени жизни задачи. Задача, которая
шла 300 мс, потому что работа занимает 300 мс, даёт ту же строку, что и задача,
отменённая на десятой миллисекунде и всё равно доработавшая до конца. Искать
стоит вторую, а эти два хука их не различают.

### Отметка отмены

```dart
final class SlowCancellations extends SoloObserver {
  // Expando держит ключ слабо: запись уходит вместе с задачей,
  // и чистить нечего.
  final _markedAt = Expando<DateTime>('cancellation');

  @override
  void onStart(Solo<Object> solo, Job<Object?> job) {
    // whenCancelled срабатывает, когда Job приняла отмену, а не когда
    // позвали cancel(): сперва кончится секция ctx.uncancellable.
    job.whenCancelled((_) => _markedAt[job] = clock.now());
  }

  @override
  void onFinish(Solo<Object> solo, Job<Object?> job) {
    final markedAt = _markedAt[job];
    if (markedAt == null) return;
    final delay = clock.now().difference(markedAt);
    if (delay > const Duration(milliseconds: 50)) {
      log('${job.key} ran ${delay.inMilliseconds} ms past its cancellation');
    }
  }
}
```

Задачу, которую никто не отменял, не отмечают и не сообщают о ней, сколько бы
она ни шла. Число считается от момента, когда `Job` приняла отмену,
а не от `cancel()`, и до исхода, вместе с детьми и уборкой. Отмену, пришедшую,
пока открыта секция `ctx.uncancellable`, `Job` принимает, когда секция
кончается: секция на 100 мс, отменённая на десятой, даёт 0 мс, а вызвавший
`cancel` или `close` ждал 90 мс.

Смотреть на число стоит ради одной конкретной ошибки. Тело, ждущее что-то
долгое голым `await`, замечает отмену, только когда ожидание кончится, а тот же
вызов через `ctx.abandonable` перестаёт ждать сразу, как и задержка, записанная
через `ctx.pause`. Ожидание на 300 мс, отменённое на десятой:

| как тело ждёт | число |
| --- | --- |
| `await Future.delayed(...)` | 290 мс |
| `ctx.abandonable(() => Future.delayed(...))` | 0 мс |
| `ctx.pause(...)` | 0 мс |

Строкой в логе станет только первая: две другие не дотягивают до 50 мс,
с которых наблюдатель начинает сообщать.

Задача, отменённая до старта, не сообщает ничего: `onStart` для неё не зовут
вовсе, значит регистрации и отметки не было. Замечать отмену было некому,
и в контроллере под это попадает всё, что выброшено из очереди.

Наблюдатель читает `clock.now()`, а не `DateTime.now()`. Под `fake_async`
первый идёт вместе с фальшивым временем, а второй стоит на месте, так что
того же наблюдателя можно проверить тестом. Наблюдатель работает в приложении,
поэтому `package:clock` идёт в его зависимости, а не в зависимости разработки;
пакет этот без своих зависимостей, и `fake_async` и так от него зависит везде,
где идут тесты.

### Отмена, которая не доходит

```dart
final class StuckCancellations extends SoloObserver {
  final _timers = Expando<Timer>('cancellation');

  @override
  void onStart(Solo<Object> solo, Job<Object?> job) => job.whenCancelled(
        (_) => _timers[job] = Timer(
          const Duration(seconds: 5),
          () => log('${job.key} has not stopped: ${solo.pending}'),
        ),
      );

  @override
  void onFinish(Solo<Object> solo, Job<Object?> job) => _timers[job]?.cancel();
}
```

Отметку выше читают, когда `Job` кончается, и потому о самой долгой отмене
из всех, о той, что не кончается, она как раз молчит. Здесь отметка становится
таймером: `whenCancelled` его заводит, конец `Job` снимает, и остаётся ровно та
`Job`, которую попросили остановиться, а она не остановилась:

```text
ignores has not stopped: SoloPending([ignores] in its body, cancelled by Cancelled(manual))
```

`Job`, которую никто не отменял, здесь не заводит таймера, сколько бы
ни работала: этот наблюдатель о неисполненной отмене, а не о долгой работе.
Секция `ctx.uncancellable` придерживает отмену, которая пришла, пока она
открыта, и `whenCancelled` сработает, когда секция закроется. Пять секунд идут
с этого момента. Дочерняя `Job`, до которой отмена дошла от родительской,
получает свою строку, и снимок в этой строке снова снят с корневой.

`Solo.observer` держит одного наблюдателя, а ставить с этой страницы пора уже
четверых. `SoloObserver.all` складывает их в одного:

```dart
Solo.observer = SoloObserver.all([
  LoggingObserver(),
  Hangs(),
  SlowCancellations(),
  StuckCancellations(),
]);
```

Каждый хук идёт каждому из них в порядке списка, и каждый вызов сам по себе:
тот, кто бросил исключение, отдаёт его в зону, а следующий всё равно
вызывается. Если один и тот же наблюдатель в списке дважды, `SoloObserver.all`
бросает `ArgumentError`.
