# Задачи и очередь

Метод контроллера ставит задачу в очередь и возвращает её хэндл. Страница
рассказывает о хэндле, об очереди и о политиках, которые решают, что повторный
вызов сделает с первым. Два раздела ниже открываются версией, к которой ведёт
словарь самого API: ключом, какой стоит у остальных методов, и вызовом, каким
метод обычно ставит задачу. Раздел говорит, что она делает вместо задуманного.
Там, где следующая версия это чинит и приносит свой изъян, она стоит второй
попыткой. Работающая версия идёт следом, под своим заголовком.

## Задачи и результаты

`Job<T>` представляет одну операцию и её будущий исход. Метод контроллера
ставит работу в очередь и отдаёт хэндл; `profile.load()` ниже взят из раздела
[«Быстрый старт»](https://github.com/vi-k/solo/blob/main/packages/solo/README.ru.md#быстрый-старт)
README пакета. `await` у `done` или `value` хэндла читает, чем операция
кончилась, а не запускает её. Хэндл при этом не `Future`: `Job` можно отменить,
а её ошибка доходит до контроллера независимо от того, ждёт ли её кто-нибудь.

```dart
switch (await profile.load().done) {
  case Done(:final value):
    print('loaded $value');
  case Failed(:final error):
    print('not loaded: $error');
  case Cancelled(:final reason):
    print('gave up: $reason');
}
```

У `Outcome<T>` эти три варианта: `Done` содержит значение, `Failed` хранит
ошибку и стек вызовов, `Cancelled` называет причину отмены.

| Член API | Назначение |
| --- | --- |
| `job.value` | Дождаться `T`; бросает исключение при ошибке или отмене. |
| `job.done` | Дождаться `Outcome<T>` без исключения. |
| `job.outcome` | Прочитать исход синхронно; `null`, пока `Job` не закончилась. |
| `job.cancel()` | Запросить отмену и дождаться завершения. |
| `job.ignoreFailure()` | Не сообщать об ошибке как о необработанной, когда исхода `Job` никто не ждёт. |
| `job.whenCancelled(callback)` | Узнать об отмене в тот момент, когда `Job` её приняла, работает она или ещё стоит в очереди. |

Ошибка `Job` не останавливает очередь. Ошибка передаётся обработчикам, после
чего может выполняться следующая `Job`. Отмена считается отдельным исходом:
закрытие контроллера, удаление `Job` из очереди и состояние, которое
не устраивает её правила, заканчивают работу исходом `Cancelled`, и ни одно
из них не говорит, что что-то сломалось.

Каждая ошибка передаётся хуку `onError` контроллера и хуку `onError`
у `Solo.observer`. Если к исходу провалившейся `Job` никто не обратился через
`done`, `value` или `ignoreFailure()` к моменту её завершения, ошибка также
передаётся как необработанная в зону Dart, где `Job` была создана. `Job` решает
это один раз, в момент завершения: `done`, прочитанный позже, вернёт `Failed`,
но ошибка уже в зоне. Используйте `ignoreFailure()`, когда достаточно обработки
ошибок в другом месте: отсутствие `await` само по себе не помечает ошибку
обработанной, и чтение `outcome` тоже. Подробности есть в разделе
[«Обработанные и необработанные ошибки»](errors.md#обработанные-и-необработанные-ошибки)
страницы об ошибках.

### Создание и запуск задач

```dart
enum _Op { load, save, zoom, seek, stop, pause }

// Сначала собрать, поставить потом: два шага, если Job нужна в руках.
final saving = job<Ready, void>(
  key: _Op.save,
  (ctx) => ctx.join(store.save),
);
add(saving);

// Либо всё сразу: так обычно и делает метод контроллера.
Job<void> setZoom(double zoom) => run<Ready, void>(
      key: _Op.zoom,
      // Лениво и только для диагностики: строится, когда спросит лог.
      describe: () => 'zoom: $zoom',
      (ctx) => ctx.join(() => camera.zoom(zoom)),
    );
```

`job`, `add` и `run` возвращают `SoloJob<T>`, который реализует `Job<T>`
и добавляет `isQueued`. Все три защищённые, как и `collect` с `accumulate`:
контроллер предоставляет предметные методы вроде `load()` или `setZoom()`,
и вызывающий код видит их, а не члены, из которых они собраны. Предметный метод
объявляет `Job<T>`, как `setZoom` выше: вызывающему коду этого хватает, чтобы
дождаться результата или отменить `Job`. `SoloJob<T>` он объявляет только для
вызывающего кода, который читает `isQueued`.

Код этого раздела и следующих принадлежит одному контроллеру камеры,
`Solo<CameraState>`. Два аргумента типа у `job` и `run` задают рабочий тип
и тип результата. Рабочий тип называет состояния, в которых работает тело,
и здесь это `Ready`, одно из состояний камеры. О рабочем типе говорит раздел
[«Состояние и правила»](state.md#состояние-и-правила) страницы о состоянии.

По `key` политики очереди ищут родственную работу, а `describe` задаёт подпись
для логов, наблюдателей и `toString()`: `Job(key: label)`. Без описания
используется представление `Job(key)`.

## Очередь и политики

`Job`, поставленную в очередь контроллера, называют корневой, и в каждый момент
работает только одна корневая `Job`. Когда метод вызывают снова, пока `Job`
прежнего вызова ещё стоит в очереди или работает, политика решает, какая
из двух останется:

```dart
// sequential, по умолчанию: одна за другой, в порядке обращения.
Job<void> save() =>
    run<Ready, void>(key: _Op.save, (ctx) => ctx.join(store.save));

// droppable: повторная загрузка того же профиля вернёт первую Job.
Job<Profile> load(String id) => run<Ready, Profile>(
      key: (_Op.load, id),
      policy: Policy.droppable,
      (ctx) => ctx.abandonable(() => api.load(id)),
    );

// replace: ожидающий зум уходит, работающий остаётся нетронутым.
Job<void> setZoom(double zoom) => run<Ready, void>(
      key: _Op.zoom,
      policy: Policy.replace,
      (ctx) => ctx.join(() => camera.zoom(zoom)),
    );

// restart: то же самое, и работающую просят остановиться.
Job<void> seek(Duration position) => run<Ready, void>(
      key: _Op.seek,
      policy: Policy.restart,
      (ctx) async {
        final token = CancelToken();
        ctx.onCancel(token.cancel);
        // Дождаться остановки устройства до следующей перемотки.
        await ctx.join(() => camera.seek(position, cancelToken: token));
      },
    );
```

| Политика | Когда `Job` с таким ключом уже существует |
| --- | --- |
| `Policy.sequential` | Добавить новую `Job` в очередь. |
| `Policy.droppable` | Вернуть существующую `Job`, из очереди или работающую корневую; новую отбросить. |
| `Policy.replace` | Удалить отменяемые `Job` с этим ключом из очереди, затем добавить новую. |
| `Policy.restart` | Сделать то же, что `replace`, и запросить отмену работающей корневой `Job` с этим ключом. |

Корневая `Job` удерживает очередь, пока не закончатся её тело, её дети,
освобождение ресурсов и обработчик состояния, то есть `onError` или `onCancel`
у `run`. До тех пор другая корневая `Job` не начинается. Дети, которых она
ждёт, её собственные: они работают внутри неё и в очередь не встают; они
разобраны на странице [«Дочерние задачи и стримы»](children.md). Политика
не касается дочерних `Job`.

`Job`, которую убирают `replace` и `restart`, кончается `Cancelled(replaced)`
с причиной `ReplacedCancelReason`: и зум из очереди, который удаляет `replace`,
и работающая перемотка, которую отменяет `restart`. `droppable` отбрасывает
новую `Job`, и она кончается `Cancelled(duplicate)`, как показано ниже. Для
`droppable` работающая `Job` считается существующей всё время, пока её
не отменили. Та, что уже приняла отмену, сворачивается и работу не сделает,
поэтому вызов, который её застал, ставит в очередь свою `Job`.

`restart` запрашивает отмену при добавлении новой `Job`. Новая `Job` встаёт
в хвост очереди, как любая другая, за тем, что поставили раньше, и всё равно
ждёт завершения текущей: их тела не пересекаются. Поэтому `Job`, которая
отклоняет отмену, то есть созданная с `cancellable: false`, может задержать
свою замену. Так же её задержит та, которой отмену некому передать: `join`
вокруг вызова, до которого запрос не доходит, дождётся его до конца, а исход
всё равно будет `Cancelled`. Токен выше и передаёт отмену операции. Второй
способ даёт `ctx.abandonable`: он годится для операции, которую можно оставить
доигрывать самой. Оба разобраны в разделе
[«Остановка самой операции»](cancellation.md#остановка-самой-операции) страницы
об отмене.

### Ключ на каждый запрос

`load` принимает идентификатор профиля. Два вызова, которые просят один
и тот же профиль, пока он загружается, должны разделить один запрос, а вызов,
который просит другой профиль, должен получить именно его.

#### Первая попытка

```dart
Job<Profile> load(String id) => run<Ready, Profile>(
      key: _Op.load,
      policy: Policy.droppable,
      (ctx) => ctx.abandonable(() => api.load(id)),
    );
```

Один член `_Op` на метод, как у `save`, `setZoom` и `seek`, и `droppable`,
чтобы отбросить повторный запрос. Второй `load('ada')`, пока первый в пути,
получает первую `Job`, как и задумано. Но ту же `Job` получает
и `load('grace')`: ключ говорит `load` и ничего о том, чей профиль, поэтому для
политики этот вызов тоже дубликат. Вызывающий код ждёт выданную ему `Job`
и получает профиль Ады, а запрос за профилем Грейс не уходит.

#### Ключ-запись

```dart
Job<Profile> load(String id) => run<Ready, Profile>(
      key: (_Op.load, id),
      policy: Policy.droppable,
      (ctx) => ctx.abandonable(() => api.load(id)),
    );
```

Ключом может быть любой объект со сравнением через `==`, поэтому запись
`(_Op.load, id)` даёт политике идентичность одного запроса, а не операции
вообще: `droppable` отбрасывает вторую загрузку того же профиля и пропускает
загрузку другого.

`Job`, которую принёс второй вызов, не стартует: она сразу кончается
с `Cancelled(duplicate)`. Причина у неё `DuplicateCancelReason`,
а не `ManualCancelReason`, как после `cancel()`: останавливать эту `Job` никто
не просил. `run` возвращает один хэндл и не говорит, чья это `Job`, поэтому
метод, которому нужно это знать, сначала собирает `Job`, а потом сравнивает её
с тем, что вернул `add`:

```dart
int duplicates = 0;

Job<Profile> load(String id) {
  final mine = job<Ready, Profile>(
    key: (_Op.load, id),
    (ctx) => ctx.abandonable(() => api.load(id)),
  );
  final taken = add(mine, policy: Policy.droppable);
  if (!identical(taken, mine)) {
    // `mine` отброшена и уже кончилась с `Cancelled(duplicate)`;
    // `taken` это загрузка, которая стояла до этого вызова.
    duplicates++;
  }
  return taken;
}
```

Используйте разные ключи для разных операций и типов результата. `Job<int>`,
отданная `droppable` под ключом, который уже занят `Job<String>`, бросает
`ArgumentError`, и бросает до того, как возьмёт задачу: в очередь ничего
не встало, ничего не отменилось, и тот же хэндл можно добавить снова, под
`Policy.sequential` или позже, когда ключ освободится. Сам ключ задаётся при
создании `Job`, поэтому само столкновение разводится там, где обе `Job`
собираются; удобный способ его не иметь даёт `enum`, где на каждый метод свой
член, сам по себе или внутри записи. Политика, отличная от последовательной,
с ключом `null` тоже бросает `ArgumentError`, и обе проверки работают
в release-сборках.

### Работа с очередью напрямую

Сама очередь принадлежит контроллеру, и метод может работать с ней напрямую:

```dart
Job<void> stop() {
  // Что ждёт прямо сейчас.
  print(queue.length);
  // Убрать то, что эта команда обесценила...
  queue.removeWhere((job) => job.key == _Op.zoom);
  // ...и пропустить саму остановку без очереди.
  return add(
    job<Ready, void>(key: _Op.stop, (ctx) => ctx.join(camera.stop)),
    first: true,
  );
}
```

`first` пропускает только то, что ждёт, и ничего больше. Уже работающий зум
не заберёт ни `removeWhere`, ни `first`: остановка стартует, когда этот зум
закончится. Начавшую работу `Job` останавливает только отмена, и о ней страница
[«Отмена»](cancellation.md).

`queue` предоставляет `jobs`, `length`, `isEmpty`, `isNotEmpty`, `remove`,
`removeWhere` и `clear`. `lastJobWhere` контроллера находит последнюю `Job`
в очереди, которая проходит его проверку, а если такой нет, то работающую.
Методы удаления касаются только `Job` в очереди, работающая им не принадлежит,
и сохраняют `Job` с `cancellable: false`, если не вызваны с `force: true`.
Удалённая `Job` заканчивается `Cancelled(manual)` или с причиной, переданной
в `reason:`. Причину принимает и `cancelAll`, который очищает очередь и заодно
отменяет работающую `Job`.

Порядок в `jobs` не совпадает с порядком запуска: `Job`, ждущую окна
накопителя, может обойти готовая, стоящая за ней, так что голова очереди
не всегда стартует следующей. См. раздел
[«Выбор момента готовности группы»](accumulation.md#выбор-момента-готовности-группы)
страницы о накоплении событий.

### Пауза очереди

Очереди нужно на время встать: ничего не стартует, пока контроллеру не скажут
продолжать, а то, что попросили за это время, идёт потом, в том порядке,
в каком просили. Своей паузы у очереди нет, но задача, которая ждёт
`Completer`, держит очередь не хуже любой работы. Эта задача, ворота, работает
в `CameraState`, то есть во всём типе состояния контроллера, тогда как
остальные задачи страницы работают в `Ready`. Задача кончается `Cancelled`,
когда состояние уходит из её рабочего типа, а пауза не должна зависеть
от одного состояния.

#### Первая попытка

```dart
Completer<void>? _gate;

bool get isPaused => _gate != null;

void pause() {
  if (_gate != null) return;
  final gate = _gate = Completer<void>();
  run<CameraState, void>(
    key: _Op.pause,
    (ctx) => ctx.abandonable(() => gate.future),
  );
}

void resume() {
  _gate?.complete();
  _gate = null;
}
```

`run` и есть тот вызов, которым метод обычно ставит задачу, и ворота он ставит
туда же, куда всё остальное: в хвост. Три задачи, которые уже стояли в очереди,
идут до начала паузы, а за воротами ждёт только то, что добавили после
`pause()`.

Уйти ворота могут и без `resume`: их отменяет `cancelAll`, и `close` тоже. Поле
сбрасывает один `resume`, поэтому после `cancelAll` `isPaused` продолжает
отвечать `true`, пока очередь идёт, а следующий `pause()` выходит на первой
строке.

#### Вторая попытка

```dart
void pause() {
  if (_gate != null) return;
  final gate = _gate = Completer<void>();
  add(
    job<CameraState, void>(key: _Op.pause, (ctx) async {
      // Отмена ещё не resume, а отменённые ворота уже не пауза.
      ctx.onCancel(() => _gate = null);
      await ctx.abandonable(() => gate.future);
    }),
    first: true,
  );
}
```

Поле, `isPaused` и `resume()` остаются прежними. `first` ставит ворота впереди
всего, кроме работающей задачи, поэтому ждёт и то, что уже стояло в очереди,
и то, что добавят позже. А `ctx.onCancel` сбрасывает поле, когда ворота
отменяют, если к этому времени они уже работают. Этот колбэк регистрирует тело,
а тело ещё не запускалось, пока ворота ждут своей очереди за работающей
задачей. `queue.clear()`, `cancelAll()` или `close()` в этом окне снимают
ворота с очереди до старта: колбэка нет, поле осталось, и `isPaused` снова
отвечает `true` над очередью, которая идёт.

#### Хэндл ворот

```dart
void pause() {
  if (_gate != null) return;
  final gate = _gate = Completer<void>();
  add(
    job<CameraState, void>(
      key: _Op.pause,
      (ctx) => ctx.abandonable(() => gate.future),
    ),
    first: true,
  ).whenCancelled((_) {
    // Отмена ещё не resume, а отменённые ворота уже не пауза.
    // В поле к этому времени могут стоять новые ворота, и они остаются.
    if (identical(_gate, gate)) _gate = null;
  });
}
```

`whenCancelled` регистрируется на хэндле, который вернул `add`, а не в теле,
поэтому слышит отмену и тех ворот, что не стартовали, и тех, что работают.
На `Job`, которая уже отменена, а именно такую `add` возвращает у закрытого
контроллера, колбэк вызывается сразу. Колбэк сбрасывает поле, только пока
в поле стоят эти самые ворота: после `resume()` и нового `pause()` там уже
следующие, и конец старых ворот не должен их сбросить. Случаи:

| Что делаешь | Что происходит |
| --- | --- |
| `pause()`, потом три задачи | Все три стоят, ни одного исхода. |
| `pause()`, когда три уже стоят в очереди | Они тоже ждут: ворота встают впереди всего, кроме работающей задачи. |
| `resume()` | Идут в том порядке, в каком добавлены. |
| `queue.clear()`, пока ворота работают | Очередь пустеет, пауза остаётся: ворота сейчас текущая задача, а не стоящая в очереди. |
| `queue.clear()`, пока ворота ещё ждут за работающей задачей | Ворота уходят вместе с остальной очередью, и поле сброшено: `isPaused` отвечает `false`, и `pause()` снова работает. |
| `close()` под паузой | Возвращается без `resume`: ворота отменяемы, и их `ctx.abandonable` кончается в момент отмены. |
| `close(mode: SoloCloseMode.drain)` под паузой | Ждёт `resume`: дренаж не отменяет то, что стоит в очереди, а выполняет, и ворота тоже. |
| `cancelAll()` | Ворота уезжают вместе со всем остальным, и очередь идёт дальше, хотя их никто не открывал. Поле сброшено, и `pause()` снова работает. |
| Состояние уходит из `Ready` под паузой | Пауза остаётся: ворота работают в любом состоянии камеры. |

`pause()` не зря ничего не возвращает. Хэндл, который отдаёт `add`, принадлежит
воротам и завершается тогда, когда пауза кончается, а не когда начинается:
`Done` на `resume`, `Cancelled(closed)` на `close`. Вернуть его значит позвать
привычку, которой учат остальные методы страницы, и тогда `await pause()` ждёт
того самого `resume`, который вызывающий и собирался сделать.

Чего движок не знает, так это того, что эта задача служит паузой. Наблюдатель
видит старт обычной задачи, а `pending` отвечает воротами, а не работой, так
что экран, показывающий текущее, покажет ворота. Признак «на паузе» держишь
у себя, и у этого контроллера его держит `isPaused`.

`canStart` паузы не делает. Задача, чьё правило не подошло к состоянию,
не придерживается: она отменяется, когда приходит её очередь,
с `Cancelled(rules: canStart)`, и очередь не наполняется, а пустеет. Пауза,
построенная на нём, теряет работу молча.
