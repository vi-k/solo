# Состояние

## Состояние и правила

`Solo<S>` хранит одно неизменяемое состояние типа `S`. Используйте
отдельные классы, когда состояния разрешают разные операции, и общие
базовые типы, когда операция может проходить через несколько состояний.

Первый аргумент типа у `run<W, T>` задаёт рабочий тип состояния Job,
`W extends S`. Тело читает `ctx.state` как `W`. Например, операция камеры
с `run<Ready, void>` может начаться только в `Ready`.

Доступ к состоянию определяется тремя правилами:

| Правило | Когда проверяется |
| --- | --- |
| Рабочий тип `W` | Перед стартом, при чужих обновлениях состояния во время тела и в контрольных точках состояния. |
| `canStart` | Один раз, непосредственно перед стартом Job. |
| `keepWhile` | Перед стартом, при чужих обновлениях состояния во время тела и в контрольных точках состояния. |

Если стартовая проверка не проходит, Job заканчивается с `Cancelled`
и `started: false`. Нарушение `W` или `keepWhile` при выполнении отменяет
Job с `RulesCancelReason`. Эти правила отклоняют неподходящую работу;
они не оставляют её в очереди до наступления подходящего состояния.

Например, запись может требовать свободное хранилище при старте
и отсутствие паузы камеры на всём протяжении работы. В этом фрагменте
`Ready`, `camera` и `store` принадлежат приложению. `ctx.each` обрабатывает
стрим; его жизненный цикл разобран в разделе
[Дочерние задачи и стримы](children.md).

```dart
Job<void> record() => run<Ready, void>(
      key: 'record',
      canStart: (state) => state.free > 0,
      keepWhile: (state) => !state.paused,
      (ctx) => ctx.each(
        camera.frames,
        (child, frame) => child.join(() => store(frame)),
      ).value,
    );
```

Когда чужое обновление состояния устанавливает `paused` в true,
`keepWhile` отменяет запись. Колбэку не нужно повторять это условие.

### Чтение и изменение состояния

`ctx.state`, `ctx.stateAs<T>()` и `ctx.check()` проверяют отмену и правила
состояния. `stateAs<T>()` дополнительно требует тип `T`; несовпадение
отменяет Job. Методы ожидания также используют контрольные точки
состояния.

`ctx.emit(next)` синхронно обновляет состояние. Job может опубликовать
состояние за пределами своего рабочего типа: например, инициализация
может закончиться публикацией `Ready`. Следующая контрольная точка
отклонит такое состояние, если оно не соответствует `W`, поэтому такой
переход должен быть последним шагом тела, которому нужен доступ
к состоянию. `canStart` после emit не повторяется.

После обновления проверяются другие работающие тела. Собственный emit
Job исключён из этой проверки правил, но всё равно проверяет отмену
до и после записи. Поэтому синхронный хук или слушатель, вызвавший ещё
одно изменение состояния, может отменить излучающую Job до возврата
из `emit`.

Правила перестают отменять Job после завершения её тела. Ручная
отмена, закрытие контроллера и отмена родителя по-прежнему могут достичь
её при ожидании детей или освобождении ресурсов. Job с обработчиками
состояния также продолжают проверять, разрешено ли этим обработчикам
менять состояние; см.
[Состояние после ошибки или отмены](#состояние-после-ошибки-или-отмены).

### Наблюдение за состоянием

Любой код с доступом к контроллеру может читать `state`. `Solo.stream`
доставляет каждое обновление всем подписчикам, по порядку, асинхронно
через микротаску. Начальное состояние не повторяется для нового
подписчика. К моменту доставки события `state` может содержать более
новое значение. Равенство не проверяется: публикация равного состояния
тоже создаёт событие.

Типы контроллеров различаются способом доставки обновлений:

| Тип | Что предоставляет |
| --- | --- |
| `SoloBase<S>` | Состояние, Job, очередь и правила. |
| `Solo<S>` | Всё из `SoloBase` и broadcast-стрим `stream`. |
| `SoloListenable<S>` | Всё из `Solo` и интерфейс Flutter `ValueListenable<S>`. |

Слушатели `SoloListenable` вызываются синхронно, в порядке подписки.
Его стрим остаётся асинхронным.

## Внешнее состояние

Большинство обновлений являются результатом собственных Job
контроллера. Независимый источник, например устройство или сокет, может
измениться, не дожидаясь контроллера. `externalSetState(next)` отражает
изменение, которое уже произошло в таком источнике. Метод помечен
`@protected` и вызывается внутри наследника контроллера, обычно
из зарегистрированного там слушателя.

Рассмотрим устройство, которое отключилось, пока Job ждёт его ответа.
Если слушатель поставит отдельную Job для публикации `Disconnected`,
обновление будет ждать в очереди за текущей Job. До этого контроллер
продолжит сообщать о подключении, а правила текущей Job не смогут
отреагировать на отключение. Сама текущая Job при этом может ждать
ответ, который уже никогда не придёт.

Вызов `externalSetState(const Disconnected())` в слушателе сразу обновляет
состояние и переоценивает работающие Job. Job, правила которой
требуют подключения, отменяется. Её метод ожидания определяет, когда тело
продолжит выполнение и нужно ли дождаться самой операции. Очередь
по-прежнему ждёт завершения тела и освобождения ресурсов до запуска
следующей корневой Job.

Разница в том, что означает уведомление. Если независимая сущность уже
изменилась, этот факт нужно сразу отразить. Если уведомление просит
контроллер выполнить работу, например обновить данные или сохранить
полученное значение, поставьте обычную Job в очередь. Доставка события
через стрим сама по себе не является основанием обходить очередь.

Для собственного успеха, ошибки и отмены контроллера используйте тела
Job и их обработчики состояния. `externalSetState` является исключением
для внешних фактов, а не универсальным сеттером для этих операций.
Остановите внешний слушатель перед закрытием контроллера: метод
продолжает менять `state` и вызывать хуки изменений после `close()`,
но закрытый стрим `Solo` уже не доставляет обновления.

## Состояние после ошибки или отмены

Параметры `onError` и `onCancel` у `run` и `job` позволяют контроллеру
выйти из временного состояния вроде `Loading`, когда операция
провалилась или отменена. Они получают текущее состояние типа `S`
и ошибку со стеком вызовов либо исход `Cancelled`, а затем синхронно
возвращают следующее состояние.

Соответствующий обработчик вызывается после тела, детей и освобождения
ресурсов, до следующей Job из очереди и до хука `onFinish`. Исход
уже зафиксирован: смена состояния не превращает `Failed` или `Cancelled`
в `Done` и не помечает исход обработанным для сообщений об ошибках.

### Сохранение несовместимого внешнего состояния

Итоговый обработчик не должен перезаписывать состояние, которое делает
его Job недопустимой. Например, добавьте к состояниям профиля
из быстрого старта класс `Disconnected` в той же библиотеке и замените
метод `load` контроллера этой версией:

```dart
final class Disconnected extends ProfileState {
  const Disconnected();
}

Job<String> load() => run<ProfileState, String>(
      key: 'load',
      policy: Policy.droppable,
      keepWhile: (state) => state is! Disconnected,
      onError: (state, error, stackTrace) => Failure(error),
      onCancel: (state, cancelled) => const Initial(),
      (ctx) async {
        ctx.emit(const Loading());
        final name = await ctx.wait(api.fetchName);
        ctx.emit(Loaded(name));
        return name;
      },
    );
```

Слушатель устройства вызывает `externalSetState(const Disconnected())`
внутри контроллера. `keepWhile` отклоняет это состояние, отменяет загрузку
и запрещает оба итоговых обработчика. Поэтому `Disconnected` остаётся
видимым и не заменяется на `Initial` или `Failure`.

Если загрузка отменяется вручную при совместимом состоянии, `onCancel`
может вернуть `Initial`. Дополнительные проверки `state is Loading`
не нужны: правила Job выражают, в каких состояниях допустимы
операция и её итоговая коррекция.

### Допуск обработчиков и их ошибки

Несовместимое внешнее обновление навсегда запрещает оба обработчика,
даже если приходит после ручной отмены, при ожидании детей или во время
уборки. Последующее совместимое обновление не разрешает их снова.
Потеря разрешения у родителя также запрещает обработчики его детей.

Дополнительные проверки относятся к Job с собственными обработчиками
состояния. Родитель без обработчиков перестаёт проверять правила после
конца тела; дети остаются ограничены собственными правилами и уже
утраченным разрешением родителя. `canStart` проверяется только при входе.
Собственный `emit` Job не запрещает её обработчики.

Обработчики не вызываются при успехе, для отброшенного дубликата и для
любой Job, тело которой не начиналось. Ошибка обработчика передаётся
для диагностики, не заменяя исход и не блокируя очередь. Если правило
бросает ошибку при проверке допуска обработчика, обработчики запрещаются,
а ошибка передаётся для диагностики. Освобождение ресурсов продолжается.

Ограничьте эти функции вычислением состояния. Для освобождения ресурсов
предназначен API следующего раздела.
