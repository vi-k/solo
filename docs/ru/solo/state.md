# Состояние

`Solo<S>` хранит одно неизменяемое состояние типа `S`, а `Job` объявляет,
в каких состояниях ей позволено начаться и в каких продолжаться. Четыре раздела
ниже открываются версией, к которой ведёт привычка или словарь самого API:
проверка в начале тела и `catch`, который возвращает состояние, задача,
поставленная в очередь первой, и обработчик, у которого ответ один на все
случаи. Раздел говорит, что она делает вместо задуманного. Работающая версия
идёт следом, под своим заголовком.

## Состояние и правила

Записи нужно свободное место, чтобы начаться, и она должна остановиться, когда
устройство сообщит о паузе.

### Первая попытка

```dart
Job<void> record() => run<CameraState, void>(
      key: 'record',
      (ctx) async {
        final state = ctx.state;
        if (state is! Ready || state.free == 0 || state.paused) return;
        await for (final frame in device.frames) {
          await store(frame);
        }
      },
    );
```

Проверка выполняется один раз, в начале тела. О паузе сообщают позже, когда
тело уже внутри цикла, а цикл в состояние больше не смотрит. Кадр, пришедший
до паузы, и два кадра, пришедших после неё, сохраняются одинаково.

Задача при этом и не кончается. `await for` контрольной точкой не является,
поэтому отмена, которую посылает `close`, до тела не доходит, и закрытие
контроллера ждёт, пока не кончится сам стрим.

### Правила

```dart
Job<void> record() => run<Ready, void>(
      key: 'record',
      canStart: (state) => state.free > 0,
      keepWhile: (state) => !state.paused,
      (ctx) => ctx.each(device.frames, (child, frame) async {
        await child.join(() => store(frame));
      }).value,
    );
```

Правила задаются параметрами, и движок проверяет их за задачу. Рабочий тип
сужается с `CameraState` до `Ready`, поэтому правила читают `state.free`
и `state.paused` без проверки типа, а условия, которые первая попытка проверяла
руками, стали `canStart` и `keepWhile`.

Первый аргумент типа у `run<W, T>` задаёт рабочий тип состояния `Job`,
`W extends S`. Его проверяет движок, поэтому `run<Ready, void>` начинается
только в `Ready`; по той же причине тело читает `ctx.state` как `W`. Здесь
`Ready`, `device` и `store` принадлежат приложению, а `ctx.each` обрабатывает
стрим: его жизненный цикл разобран в разделе
[«Обработка стрима»](streams.md#обработка-стрима) страницы о стримах.

Когда обновление состояния устанавливает `paused` в `true`, `keepWhile`
отменяет запись; повторять это условие телу не нужно. От другой задачи
из очереди такое обновление не придёт: корневые задачи выполняются по одной,
и `pause()`, написанная задачей, ждала бы конца записи, прежде чем поставить
`paused`. Пока запись идёт, обновление, о котором спрашивают её правила,
приходит из двух мест: из [`externalSetState`](#externalsetstate), которым
контроллер отражает сообщения устройства, или от дочерней задачи самой записи.

Используйте отдельные классы, когда состояния разрешают разные операции,
и общие базовые типы, когда операция может проходить через несколько состояний.

| Правило | Когда проверяется |
| --- | --- |
| Рабочий тип `W` | Перед стартом, при чужих обновлениях состояния во время тела и в контрольных точках состояния. |
| `canStart` | Один раз, непосредственно перед стартом `Job`. |
| `keepWhile` | Перед стартом, при чужих обновлениях состояния во время тела и в контрольных точках состояния. |

Любое из этих правил отменяет `Job` с `RulesCancelReason`; различается
`started`. Отказ на старте заканчивает `Job` с `started: false`, а нарушение
`W` или `keepWhile` во время тела заканчивает её с `started: true`. Эти правила
отклоняют неподходящую работу; они не оставляют её в очереди до наступления
подходящего состояния.

### Чтение и изменение состояния

```dart
Job<void> zoomIn() => run<Ready, void>(
      (ctx) async {
        // Чтение служит контрольной точкой: проверяются отмена и правила.
        final state = ctx.state;

        // Другого способа записи у тела нет, и эта запись синхронная.
        ctx.emit(state.copyWith(zoom: state.zoom + 1));
      },
    );
```

`ctx.state`, `ctx.stateAs<T>()` и `ctx.check()` проверяют отмену и правила
состояния. Тело выше объявлено как `run<Ready, void>`, поэтому `ctx.state`
в нём уже `Ready`; `stateAs<T>()` нужен телу, у которого `W` шире, чем
состояние, требуемое в этот момент: он требует тип `T`, а несовпадение отменяет
`Job`, вместо того чтобы вернуть `null`. Методы ожидания также используют
контрольные точки состояния.

`check()` делает ту же проверку, только без значения для чтения. Чтения
и методы ожидания делают её сами; `check()` закрывает промежутки между ними.
Голый `await` и возврат из `ctx.uncancellable` не проверяют ничего: задача,
которую правила уже отменили, идёт дальше, пока кто-нибудь внутри не спросит:
а можем ли продолжать? Эти промежутки разобраны в разделе
[«Обычный await и время жизни контекста»](cancellation.md#обычный-await-и-время-жизни-контекста)
страницы об отмене, а таблица в начале той же страницы ставит `check()` рядом
с методами ожидания, которым он сопутствует.

`ctx.emit(next)` позволяет `Job` опубликовать состояние за пределами своего
рабочего типа: например, инициализация может закончиться публикацией `Ready`.
Следующая контрольная точка состояния отклонит такое состояние, если оно
не соответствует `W`, а метод ожидания служит такой точкой наравне с чтением:
`ctx.abandonable` или `ctx.join` после этого `emit` заканчивает `Job` отменой
раньше, чем начнётся действие. Поэтому такой переход ставят в теле последним,
и после него нет ни чтений, ни ожиданий через контекст. `canStart` проверяется
один раз, при запуске, и больше не используется, в том числе после этого
`emit`.

После обновления состояния проверяются другие работающие тела: дочерние задачи
выполняются рядом с родительской, и каждое тело отвечает своим правилам.
Собственный `emit` `Job` исключён из этой проверки правил, но всё равно
проверяет отмену до и после записи. И `onChange` (см. раздел
[«Наблюдение за всеми контроллерами»](errors.md#наблюдение-за-всеми-контроллерами)
страницы об ошибках), и слушатель выполняются синхронно внутри самой записи,
и у обоих нет `ctx`: записать состояние они могут только через
[`externalSetState`](#externalsetstate). Хук, который так поправляет состояние
и превращает `Preparing` одной задачи прямо в `Working`, может тем самым
отменить излучающую `Job` до возврата из её собственного `emit`.

Правила перестают отменять `Job` после завершения её тела. Ручная отмена,
закрытие контроллера и отмена родителя по-прежнему могут достичь её при
ожидании детей или освобождении ресурсов. `Job` с обработчиками состояния также
продолжают проверять, разрешено ли этим обработчикам менять состояние; см.
[Состояние после ошибки или отмены](#состояние-после-ошибки-или-отмены).

### Наблюдение за состоянием

```dart
// Чтение в любой момент.
print(camera.currentState);

// Каждое изменение, синхронно, внутри самого изменения. Новое состояние
// слушатель читает сам, поэтому устареть прочитанному негде.
camera.addListener(() => print(camera.currentState));

// Каждое обновление, по порядку, через микротаску. Начальное состояние
// не повторяется, а публикация равного состояния тоже даёт событие.
// Нужен `with SoloStream` у контроллера, см. таблицу ниже.
final subscription = camera.stream.listen(print);
```

Любой код с доступом к контроллеру может читать `currentState`. К моменту
доставки события стрима `currentState` может содержать более новое значение. Он
намеренно назван не `state`: тело задачи видит все члены своего контроллера без
префикса, и чтение без контрольной точки выглядело бы там в точности как
проверяющий `ctx.state`.

| Тип | Что предоставляет |
| --- | --- |
| `Solo<S>` | Состояние, `Job`, очередь, правила и слушателей. |
| `Solo<S> with SoloStream` | Всё из `Solo` и broadcast-стрим `stream`. |
| `Solo<S> with SoloListenable` | Всё из `Solo` и интерфейс Flutter `ValueListenable<S>`. Миксин лежит в пакете [`flutter_solo`](https://pub.dev/packages/flutter_solo). |

`addListener` принадлежит самому движку и стоит на самом `Solo`, поэтому
сказанное ниже верно для любого контроллера: и со своей доставкой, и без
всякой. Слушателей зовут синхронно, в порядке регистрации, внутри самого
изменения: после записи состояния, но раньше, чем движок переоценит правила
работающих задач, и раньше следующей строки того кода, который изменил
состояние.

Изменению, сделанному изнутри слушателя, этот порядок не достаётся. Оно встаёт
в конец очереди публикации, а не влезает вперёд:

```text
externalSetState(B)
    listeners of B
        externalSetState(C)        // слушатель пишет ещё раз
            rules, against C       // запись C спрашивает их сразу
        next line of the listener
    listeners of C                 // очередь дошла до C только здесь
    rules, against C               // запись B спрашивает их последней, о C
next line of the writer
```

То есть за вложенное изменение правила отвечают раньше, чем его писатель пойдёт
дальше, а слушатели узнают о нём последними. До переоценки как таковое внешнее
изменение не доходит вовсе: когда она запускается, спрашивают уже о вложенном.
Задачу со своими обработчиками состояния о B всё же спрашивают: в самой записи,
раньше любого слушателя, и не чтобы отменить, а чтобы решить, смогут ли её
обработчики ещё поправить состояние. B, которое её правила отвергли, отключает
их насовсем, как любое несовместимое внешнее обновление в разделе
[Допуск обработчиков и их ошибки](#допуск-обработчиков-и-их-ошибки).

Второй вопрос о C единственный задаётся после слушателей C. Правило, которое
читает только состояние, отвечает на него так же, как на первый, а задачу,
отменённую первым ответом, второй раз не спрашивают. `keepWhile`, который
читает ещё и поле контроллера, увидит записанное туда слушателями только
во втором.

Как и у `ChangeNotifier`, `removeListener` сравнивает через `==`,
а не по идентичности: виджет подписывается в `initState` и отписывается
в `dispose` своим же методом. Бросивший слушатель не останавливает
ни слушателей после себя, ни переоценку правил следом: его ошибка уходит
в `onListenerError`, а тот отдаёт её зоне, если наследник не решит иначе.

Движок сбрасывает слушателей насовсем, когда закрытие закончилось, а не когда
вызван `close()`. В тот же момент `isFinished` становится истиной. После этого
`addListener` ничего не делает: слушатель не регистрируется и не хранится,
ошибки тоже нет. На той же черте останавливается и состояние:
`externalSetState` за ней бросает `StateError`.

`SoloListenable` добавляет к этому интерфейс Flutter `ValueListenable`
и сообщает об ошибке слушателя через `FlutterError` вместо зоны. Это миксин
на `Solo`, как и `SoloStream`: виджет перестраивается по `value`, а контроллер,
которому нужны обе доставки, подмешивает оба.

### Своя доставка

Слушатели выше принадлежат движку, и обычный случай они закрывают. `publish`
остаётся швом для доставки другого рода: стрима, сигнала, строки в логе.

```dart
/// Контроллер, записывающий каждое изменение в лог.
class Logged<S extends Object> extends Solo<S> {
  final void Function(String line) write;

  Logged(super.initialState, this.write);

  @protected
  @override
  void publish(S previous, S current) {
    super.publish(previous, current);
    try {
      write('$previous -> $current');
    } on Object catch (error, stackTrace) {
      // Сразу после этого вызова движок переоценивает правила работающих
      // задач. Ошибка, выпущенная отсюда, стоила бы задаче отмены,
      // которую ей должно новое состояние.
      Zone.current.handleUncaughtError(error, stackTrace);
    }
  }
}
```

Что должно такое переопределение и что движок должен ему:

| Обязательство | Почему |
| --- | --- |
| `super.publish` идёт первым | Это он зовёт слушателей, поэтому своя доставка идёт после движковой, а не вместо неё. Так сказано аннотацией `@mustCallSuper`, и анализатор за этим следит. |
| `@protected` повторяется | Dart не переносит аннотацию на переопределение. Без неё `publish` становится публичным членом контроллера, и код, у которого контроллер в руках, может опубликовать состояние, которого никто не записывал: слушателей позовут, доставка отработает, а `currentState` останется прежним. Аннотация лежит в `package:meta`. |
| Ошибка не должна выходить из `publish` | Сразу после вызова переоцениваются правила работающих задач, и выпущенная отсюда ошибка стоила бы задаче отмены, которую ей должно новое состояние. Уходит она туда же, откуда пришла запись: в тело, позвавшее `ctx.emit`; из `externalSetState` тому, кто его позвал, а когда позвал хук движка, то в `Zone.current.handleUncaughtError` из `dart:async`, куда ошибка упавшего хука уходит и так; в `onError` и `onUnanswered` контроллера, когда записью был результат обработчика состояния. |
| Изменения за ней публикуются всё равно | Упавшее изменение потеряно: оно ушло из очереди публикации до вызова, а дважды не публикуется ничто. Но стоящие за ним и есть состояние, которое контроллер уже держит, и они уходят до того, как ошибка выйдет наружу. Из нескольких ошибок бросается только первая, остальные уходят в зону. |

`SoloStream` устроен как такое переопределение с broadcast-контроллером стрима
за ним, а `SoloListenable` оставляет движковых слушателей и добавляет интерфейс
Flutter `ValueListenable`, из-за которого контроллер понимают билдеры
и `Listenable.merge`.

`SoloStream` закрывает стрим после движка, а стрим ждёт, пока каждая подписка
получит событие завершения: подписка, оставленная на паузе, держит `close()`
уже после того, как движок закончил, и `pending` тогда возвращает
`SoloPendingStream`.

## Внешнее состояние

Независимый источник, например устройство или сокет, меняется, не дожидаясь
контроллера, а контроллеру надо показать то, что там уже произошло.

### Первая попытка

```dart
Camera(this.device) : super(const Ready()) {
  _link = device.connection.listen((connected) {
    if (!connected) {
      // Факт отправляется как обычная работа, впереди всех ожидающих.
      add(
        job<Ready, void>(
          key: 'disconnect',
          (ctx) async => ctx.emit(const Disconnected()),
        ),
        first: true,
      );
    }
  });
}
```

`first: true` ставит обновление впереди всего, что ждёт, но не впереди
работающей задачи: очередь выполняет задачи по одной. Пока обновление
не началось, контроллер сообщает о подключённом состоянии, а правила работающей
задачи об отключении не слышат: их спрашивают, когда состояние меняется, а оно
не менялось. Хуже того, сама она может ждать ответа, которого устройство уже
не даст, и обновление, которое её освободило бы, стоит в очереди за ней же.

### externalSetState

```dart
final class Camera extends Solo<CameraState> with SoloStream {
  final Device device;
  late final StreamSubscription<bool> _link;

  Camera(this.device) : super(const Ready()) {
    _link = device.connection.listen((connected) {
      // Устройство уже отключилось: отражаем факт немедленно, а не
      // ставим Job, которая ждала бы за текущей.
      if (!connected) {
        externalSetState(const Disconnected());
      }
    });
  }

  // Вызывается один раз, когда последняя Job закончилась: в очереди
  // больше некому слышать устройство.
  @override
  void onClose() => unawaited(_link.cancel());
}
```

Метод помечен `@protected` и вызывается внутри наследника контроллера, обычно
из подписки, которую тот держит: из той самой подписки на устройство,
а не из слушателя контроллера.

`externalSetState` обновляет состояние немедленно и переоценивает работающие
`Job`, поэтому `Job`, правилам которой нужно подключение, отменяется самим
отключением. Её метод ожидания определяет, когда возобновится тело и должна ли
завершиться сама операция; очередь по-прежнему ждёт тела и уборки `Job` перед
запуском следующей корневой.

Что делать с уведомлением, отразить через `externalSetState` или поставить
на него `Job`, решает его смысл. Если оно говорит, что независимая сущность уже
изменилась, отражайте этот факт немедленно. Если оно просит контроллер
выполнить работу, например обновить данные или сохранить пришедшее значение,
ставьте обычную `Job`. Доставка события стримом сама по себе не оправдывает
обход очереди.

Подписка гасится в `onClose`: движок вызывает его один раз, когда все задачи
закончились, а состояние ещё не окончательное, каким бы режимом контроллер
ни закрывали. Погасить источник в момент вызова `close` выглядит опрятнее,
и это ничего не стоит только пока от этого факта не зависит ни одна работающая
задача. При `SoloCloseMode.drain` это стоит самого дренажа: очередь работает
и после вызова, а её задачам знать об отключении устройства нужнее всех.
`SoloCloseMode.cancel` от этого тоже не спасает: задачу `cancellable: false`,
которая ждёт ответа, а устройство его уже не даст, освобождает именно
отключение, и `close` ждёт эту задачу.

После `onClose` колбэк подписки выше не вызывается вовсе, поэтому его запись
не придёт после конца. Другое дело колбэк, которому перед записью нужно
чего-нибудь дождаться: он начинается, пока подписка жива, а движок может
закончить, пока он ждёт. Такой колбэк проверяет `isFinished` после последнего
`await`, прямо перед `externalSetState`: проверка, сделанная раньше, может
устареть, и запись тогда бросит `StateError`. `isFinished` ложен всё время,
пока движок работает, включая дренаж, и истинен, когда состояние стало
окончательным.

Для собственных успеха, ошибки и отмены контроллера используйте тела `Job` и их
обработчики состояния. `externalSetState` служит исключением для внешних
фактов, а не универсальным сеттером для этих операций. Он работает ровно
столько, сколько работает движок, включая дренаж, и бросает `StateError`, когда
закрытие закончилось: состояние, на котором контроллер остановился, он
и хранит.

## Состояние после ошибки или отмены

Контроллер профиля из раздела
[«Быстрый старт»](https://github.com/vi-k/solo/blob/main/packages/solo/README.ru.md#быстрый-старт)
README пакета публикует `Loading` до того, как его загрузка начнёт ждать.
Что-то должно вывести контроллер из этого состояния, когда загрузка не пришла.

### Первая попытка

```dart
run<ProfileState, String>(
  (ctx) async {
    ctx.emit(const Loading());
    try {
      final name = await ctx.abandonable(api.fetchName);
      ctx.emit(Loaded(name));
      return name;
    } on Object {
      ctx.emit(const Initial());
      rethrow;
    }
  },
);
```

При ошибке это работает: `catch` записывает `Initial` и передаёт ошибку дальше.
При отмене `catch` тоже срабатывает, но `emit` внутри него проверяет отмену
перед записью и на уже отменённой задаче бросает вместо того, чтобы записать.
Отмените загрузку, и контроллер останется в `Loading` навсегда: экран крутит
спиннер над работой, которой уже нет.

### Обработчики

```dart
run<ProfileState, String>(
  // Оба только вычисляют состояние. Они выполняются после тела, детей
  // и уборки, и исход к этому моменту уже определён.
  onError: (state, error, stackTrace) => Failure(error),
  onCancel: (state, cancelled) => const Initial(),
  (ctx) async {
    ctx.emit(const Loading());
    final name = await ctx.abandonable(api.fetchName);
    ctx.emit(Loaded(name));
    return name;
  },
);
```

Параметры `onError` и `onCancel` у `run` и `job` позволяют контроллеру покинуть
временное состояние вроде `Loading`, когда операция завершилась ошибкой или
была отменена. Они получают текущее состояние типа `S`, плюс ошибку со стеком
вызовов или исход `Cancelled`, и синхронно возвращают следующее состояние.

Подходящий обработчик выполняется перед следующей `Job` из очереди и перед
хуком `onFinish`. Изменение состояния не превращает `Failed` или `Cancelled`
в `Done` и не помечает исход обработанным для сообщений об ошибках.

### Сохранение несовместимого внешнего состояния

Обработчик выше возвращает `Initial` при любой отмене загрузки. Расширим
состояния профиля из быстрого старта классом `Disconnected` в той же
библиотеке, и связь теперь может пропасть, пока загрузка идёт.

#### Первая попытка

```dart
final class Disconnected extends ProfileState {
  const Disconnected();
}

Job<String> load() => run<ProfileState, String>(
      key: 'load',
      policy: Policy.droppable,
      onError: (state, error, stackTrace) => Failure(error),
      onCancel: (state, cancelled) => const Initial(),
      (ctx) async {
        ctx.emit(const Loading());
        final name = await ctx.abandonable(api.fetchName);
        ctx.emit(Loaded(name));
        return name;
      },
    );
```

Здесь ничто не говорит, что у загрузки есть мнение о `Disconnected`, поэтому
она продолжает идти сквозь него. А когда её отменят (пользователь, закрытый
экран, что угодно), `onCancel` сделает то, ради чего написан, и вернёт
`Initial` поверх факта, о котором сообщило устройство. Контроллер показывает
просто пустой профиль, хотя случилось другое: связи нет.

Проверка `state is Disconnected` внутри обработчика залатала бы этот случай.
Задача всё равно продолжала бы работу, которую отключение сделало
бессмысленной.

#### Правила

```dart
Job<String> load() => run<ProfileState, String>(
      key: 'load',
      policy: Policy.droppable,
      keepWhile: (state) => state is! Disconnected,
      onError: (state, error, stackTrace) => Failure(error),
      onCancel: (state, cancelled) => const Initial(),
      (ctx) async {
        ctx.emit(const Loading());
        final name = await ctx.abandonable(api.fetchName);
        ctx.emit(Loaded(name));
        return name;
      },
    );
```

Под работающей загрузкой пропадает связь, и контроллер публикует `Disconnected`
через `externalSetState`. `keepWhile` отвергает это состояние, отменяя загрузку
и отключая оба обработчика. Поэтому `Disconnected` остаётся видимым,
а не заменяется на `Initial` или `Failure`.

Если загрузку отменили вручную, пока состояние ещё совместимо, `onCancel`
по-прежнему возвращает `Initial`. Своя проверка `state is Disconnected`
обработчикам не нужна: правила `Job` уже говорят, какие состояния допускают
операцию и поправку после неё.

### Допуск обработчиков и их ошибки

| Что происходит | Что становится с обработчиками |
| --- | --- |
| Несовместимое обновление, которого `Job` не делала сама: `externalSetState` или `emit` её родителя, ребёнка или соседа, когда бы оно ни пришло | Отключены навсегда; последующее совместимое обновление их не возвращает. |
| Родитель потерял допуск | Обработчики его детей тоже заблокированы. |
| Успех, отброшенный дубликат, тело, которое не запускалось | Не выполняются вовсе. |
| Собственный `emit` `Job` | Сам по себе ничего; свои обработчики он не отключает. |
| Правила отменяют `Job` на её собственной контрольной точке: после её `emit` состояния, которое они отвергают, или при несовпадении в `stateAs` | Не выполняются: `Job`, отменённая своими правилами, оставляет состояние как есть. |
| Обработчик бросил ошибку | Ошибка сообщается; исход и очередь не затронуты. |
| Правило бросило ошибку при проверке допуска | Обработчики отключены, ошибка сообщена. Освобождение ресурсов всё равно выполняется. |

Эти дополнительные проверки относятся к `Job` с собственными обработчиками
состояния. Родитель без обработчиков перестаёт проверять свои правила после
завершения тела; дети остаются под своими правилами и под уже потерянным
допуском родителя.

Держите эти функции в границах вычисления состояния: они пишут тем значением,
которое возвращают. Запись изнутри обработчика, через `externalSetState` или
источник, который зовёт его синхронно, с этим значением не складывается: если
правила задачи её принимают, результат обработчика ложится поверх, посчитанный
из состояния до неё, и факт теряется; если отвергают, результат обработчика
отбрасывается. Освобождением ресурсов занимается API уборки, о нём страница
[«Ресурсы и освобождение»](resources.md).
