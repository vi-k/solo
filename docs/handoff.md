## Решения владельца, грабли и чужое

**Решения владельца, которые действуют.**

- `Cancelled`, брошенный хуком `solo`, в зону не идёт, как в ядре, 2026-10-12:
  `callHook` и сторож `onListenerError` отдают в зону только ошибку, в которой
  есть провал. Вопрос и итог — раздел «Вопросы владельцу»
  в `2026-10-04-solo-errors-reread-report.md`.

- Раздел README `flutter_solo` о подписках на свою страницу не выносится,
  2026-10-12, хотя карта `2026-09-11[16]-docs-structure-design.md` числила
  страницу в 325 строк, а в ней 565. Вопрос — раздел «Вопросы владельцу»
  в `2026-10-04-flutter-solo-readme-reread-report.md`. Раздел «Testing» тогда
  тоже оставался, но 2026-10-20 по M6 ревью `solo` ушёл на свою страницу
  `doc/testing.md`.

- Обход ошибок, 2026-10-01: распаковка `ParallelWaitError`, а не предикат «это
  отмена?»; шаблон visitor, статический метод
  `Job.visitErrors(error, stackTrace, onFailure:, onCancelled:)` с колбэками,
  а не функция верхнего уровня; списка `failuresOf` рядом не надо; прерывания
  обхода нет.

- Несколько наблюдателей — для обоих пакетов: `JobObserver.all`,
  `SoloObserver.all`; наблюдение и ответ — разные интерфейсы, `JobObserver`
  и `JobAnswerer`, один список без отдельного `answer:`, отвечающих больше
  одного — `ArgumentError`, 2026-10-01.

- Тело, которое сдаётся само, отменяет задачу тем же путём, что и отмена
  снаружи: каскад на детей, колбэки `onCancel`, `whenCancelled` — в момент
  броска, 2026-10-01.

- `externalSetState` после конца закрытия бросает, и второго метода рядом с ним
  не будет, 2026-10-01.

- `finish` у идущей задачи ядро не меняет: стек уборки не разматывается, и это
  контракт, названный в dartdoc `finish` и на странице `extending.md`. Решение
  владельца 2026-09-30 по FINMARK, находке 7 ревьюера А шестого круга ревью
  дизайна H1; сторож —
  `a branch finished by hand at the second barrier says so too`
  в `debug_test.dart`.

- H1 ревью `async_job` закрыт документами, ядро не меняется: решение владельца
  2026-09-27 после ревью шестой редакции дизайна; дизайн
  `2026-09-26-run-all-one-barrier-design.md` брошен, прежние решения о его
  вариантах не действуют. Отчёт — `2026-09-27-run-all-shared-lock-report.md`.
  Решения владельца по остальным находкам — раздел «Решения владельца» в конце
  `2026-09-26-async-job-project-review.md`.

- «leaks» в английской `packages/solo/doc/resources.md` остаётся как есть,
  2026-09-19: замену, сделанную в русском переводе вместо метафоры «течёт»,
  на оригинал не переносить.
- Правка личных скиллов идёт порциями, 2026-09-19: одна проверенная правка —
  один коммит, а рецепт из команд встаёт в текст только после прогона
  на тяжёлом случае. Правило записано в `README.md` репозитория скиллов
  коммитом `866c1ea`; повод — `2026-09-19-end-handoff-skills-review-3.md`.
- Перенос владения отменён окончательно 2026-09-15:
  `2026-09-14[17]-discard-follows-the-value-design.md` не делать. Освобождение
  регистрирует получатель — `ctx.run(opener, discard: …)`; разбор —
  `2026-09-15[8]-cleanup-registers-on-arrival-report.md`.
- Кортежная форма `ctx.runAll` отложена: добавляется потом без слома.
- Накопление через `externalSetState` отклонено:
  `2026-09-10[6]-state-accumulation-design.md` не реализовывать. Досылка при
  закрытии, надёжный буфер и автоматические повторы — отдельная работа,
  не начата.
- Имя дренажа по-русски, 2026-09-22: `SoloCloseMode.drain` в русской прозе
  зовётся «дренаж», и это единственное существительное для него — по нему
  читатель догадывается сам, а «слив» такого не даёт. «Досылка» и «слив»
  из документов убраны; где проза обходится без существительного, она называет
  сам вызов `close(mode: SoloCloseMode.drain)`, а состояние — `isDraining`.
- Бэктики в русской прозе, 2026-09-15: в них берут inline-код, имена классов
  и имена переменных; future в прозе — обычное слово, строчными и без бэктиков
  (`86edb87`).
- README объясняет API новому читателю, без ссылок на прежнее поведение
  и контекст диалога. `removeDisposer` и пример ленивого лога из `479e934`
  сохранять: с `5922364` они живут не в README `async_job`, а на страницах
  `doc/cleanup-rules.md` и `doc/observing.md`.
- «The second attempt» в `accumulation.md` остаётся без входа отмены: попытка
  должна провалиться, иначе накопитель ниже не нужен (2026-09-15).
- Старые записи `docs/records/` не переименовывать, 2026-09-19: имена
  `YYYY-MM-DD[N]-…` остаются как есть, предложение отклонено.
- scopo не трогать, 2026-09-19. Находка о его `CHANGELOG.md` — раздел `0.14.0`
  говорит об удалении `ScopeInitState`, `ScopeProgress` и `ScopeReady`,

## Требования к README, которые нужно сохранить

- При описании API на русском называть `Job` прямо. Слово «задача» уместно для
  самой работы, но не должно подменять имя класса в объяснении его
  возможностей.
- `ctx.join(Database.open)` объясняется самостоятельно до сравнения
  с `abandonable`: вызывает операцию, ждёт её завершения и проверяет отмену.
  `abandonable` предлагается, когда нужно прекратить ожидание сразу при отмене.
- `discard` после `return` объясняется на примере ожидания дочерней задачи:
  тело вернулось, но весь `Job` ещё не завершился.
- В примере миграции `onCancel` передаёт сигнал токену, `join` ждёт фактической
  остановки, а `uncancellable` защищает шаг от самого сигнала.
- Внешние асинхронные операции в теле следует ожидать через контекст. Прямой
  `await` допустим, но сам не проверяет отмену. Внутри действия, переданного
  контексту, и при уборке обычный `await` уместен с учётом описанных в README
  границ.
- Упоминание `solo` следует из границ ядра: в `async_job` нет управления
  состоянием, очереди и правил планирования; `solo` добавляет их.
- Отменена ли джоба, спрашивают у джобы, а не у ошибки: `ctx.check()` первой
  строкой `catch`, и для `on Exception`, и для `on Object`. Отдельная ветка
  `on Cancelled { rethrow; }` — первая попытка страницы об отмене: из `join`
  после остановки токеном приходит ошибка самой операции, а не `Cancelled`,
  и ветка её пропускает. Проверка типа на `Cancelled` стоит только после
  `ctx.check()` и отличает чужой `Cancelled`, например отменённого
  необязательного ребёнка. Решение владельца 2026-09-29, L29 ревью 2026-09-26.
- Принятая отмена самого `Job` сохраняется после перехвата исключения. Код
  после `catch` может выполниться, следующая контрольная точка снова бросает
  отмену, а при завершении исход остаётся `Cancelled`. Перехваченный
  `Cancelled` от операции или дочерней задачи сам по себе родителя не отменяет:
  возможен `Done`.

Число блоков кода в README больше не годится как ориентир: материал разъехался
по страницам `doc/`. Форму держат `check_translations.py` (двадцать пять пар)
и `check_doc_shape.py`. Примеры `then`, его контракт и переводы обновлены
вместе с реализацией.

## Ограничения и общение

- Не приписывать владельцу ответы на формы или выбор вариантов, которые он
  не давал. Собственную интерпретацию запроса называть своей.
- Владелец просит минимум служебного вывода: ему нужны сообщения по делу,
  а не журналы запусков. Заголовки инструментов формирует интерфейс; не обещать
  скрыть их, сокращать число вызовов и объём вывода.
- Текст рабочих документов переносить на 79 символах. Правило и порядок
  проверок сохранены в `AGENTS.md`.
- Английский README и русский перевод править вместе. Связность и смысл важнее
  косметического сокращения; подтверждённые условия не выкидывать.
- Не менять заодно согласованную семантику отмены.
- `ctx.run` принимает `ChildJob<T>`, а не только `DeferredJob<T>`: библиотечные
  классы на основе `JobBase` объявляют `ChildJob` и тоже могут быть дочерними,
  не получая публичного `start()`. Задача, которая запускается сама, —
  не `ChildJob`.
- Не расширять защищённые `owner` и `parent` без подтверждённой нужды
  потребителя. `isDisposing` не выносить в публичный `Job` без нового решения.
- Буфер ранних событий в `each` сохранять; прежние альтернативы теряли события
  при подписке. При ошибке тела дочерние задачи дорабатывают; при самоотмене
  тела отмена передаётся детям.
- Соседний `scopo` ведётся отдельно. Его прежний переход на опубликованное ядро
  0.1.0 выполнен; обновление на новый API не входит в эту работу. Архивирование
  `stream_future` тоже отдельная внешняя задача.
- `/Users/user/development/yandex/yx_camera` не трогать: это чужой проект.
- Не запускать push, публикацию, теги или релизные коммиты без отдельного
  поручения. Правила связки публикации полностью заданы в `AGENTS.md`.
