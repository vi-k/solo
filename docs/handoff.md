## Требования к README, которые нужно сохранить

- При описании API на русском называть `Job` прямо. Слово «задача»
  уместно для самой работы, но не должно подменять имя класса в объяснении
  его возможностей.
- `ctx.join(Database.open)` объясняется самостоятельно до сравнения
  с `wait`: вызывает операцию, ждёт её завершения и проверяет отмену.
  `wait` предлагается, когда нужно прекратить ожидание сразу при отмене.
- `discard` после `return` объясняется на примере ожидания дочерней
  задачи: тело вернулось, но весь `Job` ещё не завершился.
- В примере миграции `onCancel` передаёт сигнал токену, `join` ждёт
  фактической остановки, а `uncancellable` защищает шаг от самого сигнала.
- Внешние асинхронные операции в теле следует ожидать через контекст.
  Прямой `await` допустим, но сам не проверяет отмену. Внутри действия,
  переданного контексту, и при уборке обычный `await` уместен с учётом
  описанных в README границ.
- Упоминание `solo` следует из границ ядра: в `async_job` нет управления
  состоянием, очереди и правил планирования; `solo` добавляет их.
- Два примера проброса `Cancelled` показывают отдельную ветку `catch`
  и проверку типа внутри общего обработчика. Оба способа подходят
  и для `Exception`, и для `Object`; выбор типа не различает эти способы.
- Принятая отмена самого `Job` сохраняется после перехвата исключения.
  Код после `catch` может выполниться, следующая контрольная точка снова
  бросает отмену, а при завершении исход остаётся `Cancelled`.
  Перехваченный `Cancelled` от операции или дочерней задачи сам по себе
  родителя не отменяет: возможен `Done`.

Оба README ядра имеют по 17 блоков кода, оба README `solo` — по 27.
Примеры нового `each` и переводы обновлены в `0b3e19e`.

## Состояние API и версий

Готовится несовместимый выпуск `async_job` 0.2.0. По состоянию последней
публикации ядро на pub.dev имеет версию 0.1.0; текущий 0.2.0 не опубликован.
`solo` и `flutter_solo` в дереве тоже на 0.2.0 и не опубликованы.

В текущем API `job.whenCancelled(callback)` регистрирует синхронный
обработчик, передаёт ему весь `Cancelled` и возвращает функцию снятия.
Поздняя регистрация вызывает обработчик сразу. Это больше не future.
Реализация и ревью: `2026-09-09[11]-when-cancelled-report.md`.

`CancelReason` — открытый абстрактный класс. Встроенные причины ядра:
`ManualCancelReason`, `ParentCancelReason`, `HandlerCancelReason`.
У `solo`: `RulesCancelReason`, `ClosedCancelReason`, основа
`SoloCancelReason`. Свои классы могут хранить ошибку, стектрейс и другие
данные. `name` служит меткой журнала; проверка по типу, равенства по имени
нет. Переданная в `cancel(reason: ...)` причина сохраняет идентичность.
Связи `ParentCancelReason.cause` и `HandlerCancelReason.cause` сохраняют
исходный `Cancelled` при каскаде и распространении отмены ребёнка.
Реализация и ревью: `2026-09-09[13]-cancel-reason-report.md`.

`solo` зависит от `async_job: ^0.2.0`, `flutter_solo` от `solo: ^0.2.0`.
Локальные оверрайды ядра восстановлены у `solo`, его примера,
`flutter_solo` и его примера. У Flutter-пакета также оверрайд `solo`,
у его примера — обоих пакетов и `flutter_solo`. Пока ядро 0.2.0 не
опубликовано, эти оверрайды нужны.

Прежние dry-run для hosted-ядра 0.1.0 не подтверждают готовность текущего
дерева к публикации. Когда владелец отдельно поручит выпуск, порядок:
ядро, затем `solo`, затем `flutter_solo`. После публикации зависимости
снимать соответствующие оверрайды и повторять разрешение зависимостей,
проверки и dry-run. Саму связку выпуска выполнять только по `AGENTS.md`.

## Дальше, когда владелец выберет новую работу

Два рецепта документации остаются ненаписанными:

- Аккумуляция правок состоянием: записывать правку при вызове, а задача
  с `replace` отправляет текущее состояние. Запись через `emit` внутри
  тела теряется, если задачу заменили ещё в очереди.
- Пауза очереди задачей, ждущей `Completer`. `canStart` не создаёт паузу:
  неподходящие задачи отменяются, и очередь опустошается.

Материал и замеры: `2026-09-09[9]-todo-review.md`. Готовый стенд может
лежать в `.artifacts/2026-09-09-wave2-review/a/stand`; восстановление —
`python3 tool/doc_snippets.py <каталог>`. При проверке внешней операции
дожидаться самой операции: снимок состояния сразу после отмены `Job`
не показывает её окончательный результат.

Пожелания владельца находятся в `docs/backlog.md`. После окончания текущей

Их брать только после выбора владельца.

## Ограничения и общение

- Владелец просит минимум служебного вывода: ему нужны сообщения по делу,
  а не журналы запусков. Заголовки инструментов формирует интерфейс;
  не обещать скрыть их, сокращать число вызовов и объём вывода.
- Текст рабочих документов переносить на 79 символах. Правило и порядок
  проверок сохранены в `AGENTS.md`.
- Английский README и русский перевод править вместе. Связность и смысл
  важнее косметического сокращения; подтверждённые условия не выкидывать.
- Не менять заодно согласованную семантику отмены. Вопрос об ожидании
  секции без `await` `uncancellable` остаётся в бэклоге.
- `ctx.run` принимает `Job<T>`, а не только `DeferredJob<T>`: библиотечные
  классы на основе `JobBase` тоже могут быть дочерними. Автоматически
  запускающийся обычный `Job` отвергается.
- Не расширять защищённые `owner` и `parent` без подтверждённой нужды
  потребителя. `isDisposing` не выносить в публичный `Job` без нового решения.
- Буфер ранних событий в `each` сохранять; прежние альтернативы теряли
  события при подписке. При ошибке тела дочерние задачи дорабатывают;
  при самоотмене тела отмена передаётся детям.
- Соседний `scopo` ведётся отдельно. Его прежний переход на опубликованное
  ядро 0.1.0 выполнен; обновление на новый API не входит в эту работу.
  Архивирование `stream_future` тоже отдельная внешняя задача.
