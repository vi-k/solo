## Документация: цепочка — не ребёнок

Вопрос владельца: запускается ли цепочка задач через `ctx.run`. Ответ —
нет, и записан он в `packages/async_job/doc/children.md`, раздел
`### A chain is not a child`; на стороне `solo` дополнен раздел
«Chaining completed work». Отчёт —
`2026-09-12[7]-chain-vs-child-report.md`.

Коротко: усыновляется только голова цепочки; родитель ждёт детей, а не
то, что на них навешано, и медленный хвост переживает родителя; очередь
контроллера хвоста тоже не ждёт; отмена до хвоста доходит через
источник; необслуженная ошибка хвоста уходит в зону, создавшую цепочку.

## Завершённый timing

Владелец поручил: «продолжи debounce и throttle». Реализация завершена
по `2026-09-10[12]-accumulation-timing-design.md` и
`2026-09-10[16]-accumulation-timing-plan.md`, база — `9493c31`.

- Обычный debounce без maxWait закрывает группу после паузы событий.
- Throttle отсчитывает интервал от фактического старта предыдущей группы
  того же накопителя. Первый старт готов сразу, следующие — по интервалу.
- Collect хранит все события; accumulate сохраняет результат merge.
- Ожидающие группы остаются в queue и пропускают готовые посторонние Job.
  Выполнение обработчиков, детей и уборки остаётся последовательным.
- Timing необязателен; Duration.zero сохраняет поведение без таймеров.
- Close отменяет таймеры и очередь без досылки.

Алгоритм и все тесты готовы. Основные timing-тесты: 10; отдельные
lifecycle-тесты: 46. Полный solo: 433 зелёных, анализ чистый.
Пример solo: 9 тестов; flutter_solo: 8; анализ обоих и Flutter-примера
чистый. Извлечённые рецепты и README Search проверены с FakeAsync.
Dartdoc solo без предупреждений и ошибок; формат и переводы проверены.

## Накопители и границы работы

Базовые collect/accumulate реализованы в `ff5ed8d`; повторно их
не создавать. Состояние меняет обработчик через ctx.emit, а collect
собирает вход в список и accumulate сразу применяет чистую merge.
Совместимость групп определяется идентичностью накопителя, не key.

Adjacent использует текущий хвост; join сохраняет позицию последней
открытой группы; replace переносит данные в новый Job в хвосте,
обязательно отменяя прежний даже при cancellable:false. Новая группа
видна до хуков отмены старой. Закрытые и работающие группы не дополняются.

Базовые записи: `2026-09-10[7]-event-accumulation-design.md`,
`2026-09-10[8]-event-accumulation-plan.md`,
`2026-09-10[9]-event-accumulation-report.md`.
Рецепт: `packages/solo/doc/accumulation.md`, перевод
`docs/ru/solo/accumulation.md`.

Досылка при закрытии, надёжный буфер и автоматические повторы остаются
отдельной работой. Аккумуляция через externalSetState отклонена:
`2026-09-10[6]-state-accumulation-design.md` не реализовывать.

## Требования к README, которые нужно сохранить

- При описании API на русском называть `Job` прямо. Слово «задача»
  уместно для самой работы, но не должно подменять имя класса в объяснении
  его возможностей.
- `ctx.join(Database.open)` объясняется самостоятельно до сравнения
  с `wait`: вызывает операцию, ждёт её завершения и проверяет отмену.
  `wait` предлагается, когда нужно прекратить ожидание сразу при отмене.
- `discard` после `return` объясняется на примере ожидания дочерней
  задачи: тело вернулось, но весь `Job` ещё не завершился.
- В примере миграции `onCancel` передаёт сигнал токену, `join` ждёт
  фактической остановки, а `uncancellable` защищает шаг от самого сигнала.
- Внешние асинхронные операции в теле следует ожидать через контекст.
  Прямой `await` допустим, но сам не проверяет отмену. Внутри действия,
  переданного контексту, и при уборке обычный `await` уместен с учётом
  описанных в README границ.
- Упоминание `solo` следует из границ ядра: в `async_job` нет управления
  состоянием, очереди и правил планирования; `solo` добавляет их.
- Два примера проброса `Cancelled` показывают отдельную ветку `catch`
  и проверку типа внутри общего обработчика. Оба способа подходят
  и для `Exception`, и для `Object`; выбор типа не различает эти способы.
- Принятая отмена самого `Job` сохраняется после перехвата исключения.
  Код после `catch` может выполниться, следующая контрольная точка снова
  бросает отмену, а при завершении исход остаётся `Cancelled`.
  Перехваченный `Cancelled` от операции или дочерней задачи сам по себе
  родителя не отменяет: возможен `Done`.

Число блоков кода в README больше не годится как ориентир: материал
разъехался по страницам `doc/`. Форму держат `check_translations.py`
(двадцать пар) и `check_doc_shape.py`.
Примеры `then`, его контракт и переводы обновлены вместе с реализацией.

## Состояние API и версий

`async_job` 0.2.0, `solo` 0.2.0 и `flutter_solo` 0.2.0 опубликованы на
pub.dev. Релизные коммиты — 547819a, a71641a и bd26a35; теги —
async_job-v0.2.0, solo-v0.2.0 и flutter_solo-v0.2.0.

В текущем API `job.whenCancelled(callback)` регистрирует синхронный
обработчик, передаёт ему весь `Cancelled` и возвращает функцию снятия.
Поздняя регистрация вызывает обработчик сразу. Это больше не future.
Реализация и ревью: `2026-09-09[11]-when-cancelled-report.md`.

`CancelReason` — открытый абстрактный класс. Встроенные причины ядра:
`ManualCancelReason`, `ParentCancelReason`, `HandlerCancelReason`,
`ChainCancelReason`.
У `solo`: `RulesCancelReason`, `ClosedCancelReason`, основа
`SoloCancelReason`. Свои классы могут хранить ошибку, стектрейс и другие
данные. `name` служит меткой журнала; проверка по типу, равенства по имени
нет. Переданная в `cancel(reason: ...)` причина сохраняет идентичность.
Связи `ParentCancelReason.cause` и `HandlerCancelReason.cause` сохраняют
исходный `Cancelled` при каскаде и распространении отмены ребёнка.
`ChainCancelReason.cause` сохраняет отмену соседнего звена `then`.
Реализация и ревью: `2026-09-09[13]-cancel-reason-report.md`.
