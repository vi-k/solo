## В работе прямо сейчас

Ничего. План выполнен целиком; поверх прошли волны правок: по итогам
финального ревью всей ветки и по итогам независимого ревью README
(`docs/records/2026-09-03[2]-readme-review.md`, вердикт по каждой находке
там же), затем разбор замечаний владельца по документу `vs-bloc.md`,
затем закрытие мелочей, оставленных финальным ревью владельцу
(`docs/records/2026-09-04[1]-review-leftovers-report.md`; dartdoc, тесты и
фикстуры, поведение движка не менялось), затем изоляция хуков
(`docs/records/2026-09-04[2]-hook-isolation-report.md`). Финальное ревью
закрыто целиком: вердикт стоит у каждой находки.

Движок за это время изменился трижды. Необслуженный отказ задачи уходит в
зону, у `Job` появился `ignore()` (раздел 5.10 спецификации). Появился
`JobContext.onCancel`: отмена передаётся тому, кто умеет остановиться,
например токену отмены устройства (раздел 5.4a). `guard` прекращает
ожидание, но не работу, и это записано и в dartdoc, и в README, и в
`vs-bloc.md`. И хуки стали каналом, а не звеном цепи: ошибка любого из них
уходит в текущую зону и больше ни на что не влияет. Раньше бросивший
`onFinish` останавливал очередь и обрывал дренаж в `close()`, бросивший
`onStart` при `ctx.run` проваливал родителя, а бросивший `onChange` уносил
с собой публикацию и переоценку правил. `publish` в это правило не входит:
это канал доставки наследника, не сквозной хук.

История работ — в `git log` и в записях.

  `**/doc/api/` в `.gitignore` ловит их во всех пакетах, в дерево они не

- Файлы `.DS_Store` и `build/` игнорируются через `.gitignore`.
- Пункты `packages/solo/TODO.txt`, не вошедшие в спецификацию (сам файл

  отложенному); метод взятия не первой задачи из очереди; аккумуляция
  однотипных задач (включая частный случай — метрики/логи); запуск
  последнего события при диспоузе очереди (чтобы новые не добавлялись); идея
  отмены рутовых `Future` через вложенные `runZoned`; API-удобство вида
  `state.scope`/`state.map().run` для матчинга состояния без повторов
  `state.isA`; тест на `debugInfo`; тест на «неудаляемые» события (в новом
  дизайне такого понятия нет, есть только «неотменяемые» — уже покрыто
  спецификацией); нюанс `restartable`: должен ли он удалять более ранние
  задачи в момент постановки в очередь или только при старте — в новом
  движке очередь устроена иначе, решение не перенесено.
