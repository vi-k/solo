# AGENTS.md

Точка входа для любого агента в этом репозитории: Claude Code, Codex и
других. Прочитай этот файл целиком, затем документы из раздела «Старт
сессии», и только потом берись за работу. Сессия может оборваться в любой
момент, поэтому всё, что нужно для продолжения, живёт в файлах, а не в
памяти диалога.

## Старт сессии

Читай в этом порядке:

1. `docs/handoff.md` — текущее состояние проекта. Единственный источник
   правды о том, что делается сейчас, что дальше и что не трогать.
2. `docs/architecture.md` — устройство пакета. Меняется редко.
3. `docs/conventions.md` — код, тесты, документация, git.
4. `docs/backlog.md` — пожелания владельца. Если там есть записи, предложи
   владельцу взять их в работу.
5. Записи в `docs/records/`, на которые ссылается handoff.

Не переспрашивай то, что записано в этих файлах. Если документ противоречит
коду, верь коду и исправь документ в том же коммите, что и работу.

## docs/handoff.md

Держи его актуальным всегда. Обновляй после каждого законченного шага и
перед тем, как закончить ход, даже если работа не завершена: следующая
сессия может начаться с чистого контекста.

Что в нём есть: фаза проекта, что делается прямо сейчас, следующие шаги,
открытые вопросы, что не трогать, состояние дерева и проверок.

Чего в нём нет: пересказа истории коммитов (это `git log`), разбора
законченных эпизодов (это `docs/records/`), пожеланий владельца (это
`docs/backlog.md`). Только текущее состояние.

## docs/backlog.md

Это записи владельца. Читай его на старте сессии и при выборе следующей
задачи. Предлагай взять записи в работу. Если взял и выполнил, удали
выполненное из бэклога в том же коммите. Сам туда не пиши, если владелец
прямо не попросил.

## docs/records/

История правок: дизайны, планы, отчёты, ревью. Один файл на одну работу или
один эпизод.

Имя файла: `YYYY-MM-DD[N]-name-kind.md`. Квадратные скобки — литералы. `N` —
порядковый номер записи за день, начиная с 1. `name` — тема в kebab-case.
`kind` — жанр записи, одно слово:

- `design` — устройство и API;
- `plan` — план работ;
- `report` — отчёт о сделанном: о волне правок, о разборе дефекта, о
  предмержевом ревью одной работы;
- `review` — полное ревью проекта, состояние всей кодовой базы глазами
  ревьюера, а не итог одной работы: `project-review`, `architecture-review`,
  `flutter-review`, `bug-hunter`, `performance-review`.

Если нужного слова нет в списке, возьми своё по тому же принципу: одно слово
о жанре записи, а не о теме.

Каждый файл в `docs/records/` начинается с шапки о текущем состоянии:

```markdown
> **Состояние на YYYY-MM-DD:** что с этой работой сейчас — сделано и
> смержено (коммит), брошено, частично сделано, пересмотрено позже.
> **Что это:** одна фраза о содержимом.
> **Связанные записи:** имена других файлов в `docs/records/`.
```

Шапку обновляй, когда состояние работы меняется: смержили, бросили,
пересмотрели.

### Ревью

При работе с ревью в конец каждой находки записывай вердикт по этой находке
отдельным абзацем. Прозу находки не трогай. Вердиктов не больше одного на
находку.

## Язык

Документы для владельца и агентов — по-русски: `AGENTS.md`, `docs/*.md`,
`docs/records/`. С владельцем общайся по-русски.

Публичные артефакты — по-английски: `README.md`, `CHANGELOG.md`,
dartdoc-комментарии в `lib/`, сообщения коммитов, тексты ошибок.

У публичных документов есть русские переводы. Перевод README лежит рядом с
оригиналом, в самом пакете: `packages/solo/README.ru.md`,
`packages/flutter_solo/README.ru.md`. Остальные переводы — в
`docs/ru/<пакет>/`: `docs/ru/solo/vs-bloc.md` — перевод
`packages/solo/doc/vs-bloc.md`.

Источник правды — английский оригинал. Любая его правка, включая
комментарии во фрагментах кода, сопровождается правкой перевода в том же
коммите; сверка — `python3 tool/check_translations.py` из корня.

В публикацию русский текст не попадает вообще: `README.ru.md` каждого
пакета исключён его `.pubignore`, остальные переводы лежат вне пакетов, а
английские документы не ссылаются на переводы.

## Git

- Работай в `main`. Мержи прямо в `main`, без PR.
- Коммиты именуй по Conventional Commits: `feat:`, `fix:`, `docs:`, `test:`,
  `refactor:`, `chore:`, `build:`. Сообщения по-английски.
- Не коммить чужие правки вместе со своими. Перед коммитом смотри
  `git status`; всё, что не твоё, оставляй в дереве.
- Документы (`docs/handoff.md`, записи в `docs/records/`) коммить вместе с
  работой, к которой они относятся.

## Проверки

Репозиторий — монорепозиторий: пакеты лежат в `packages/`. Перед коммитом
кода в каждом затронутом пакете из его папки: `dart analyze` без
предупреждений и `dart test` зелёный (`flutter test` для
`packages/flutter_solo`). Пример `packages/solo/example/` со своим
`pubspec.yaml` проверяется отдельно из его папки. Подробности в
`docs/conventions.md`.

## Публикация на pub.dev

Публикация на pub.dev — это вся связка целиком: коммит `Release X.Y.Z`, тег
`vX.Y.Z`, push и `dart pub publish`, одним заходом и подряд. Ни одну часть
по отдельности. Подготовку к публикации делай свободно — это обычные правки
в дереве, их можно откатить.

Разрешение на публикацию — только явное и только на эту связку. Оно не
переносится на следующий релиз, не наследуется от прошлого раза и не
выводится из готовности релиза. «Всё готово к публикации» — не разрешение.
Пройденный чеклист — не разрешение. Связка — отдельная задача. Если в
сообщении владельца есть хоть что-то ещё, кроме публикации, — не запускать
ничего из связки, даже если слово «публикуй» стоит в нём прямым текстом. Не
спрашивай — откажи. В таком случае не задавай вопроса «публиковать?», не
предлагай вариантов и не выноси решение на подтверждение. Сделай остальную
работу и откажи в публикации, назвав условие: разрешение должно прийти
отдельным запросом владельца, состоящим только из просьбы опубликовать.
Сомневаешься — не публикуй. Отказ стоит одного сообщения, ошибка стоит
номера версии.
