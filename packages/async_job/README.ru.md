# async_job

`async_job` добавляет к асинхронному коду на Dart отмену, дочерние задачи
и освобождение ресурсов. Пакет работает на чистом Dart, из зависимостей только
`meta`.

`Job<T>` выполняет функцию, которая называется телом задачи, и запоминает, чем
она завершилась. Через `await job.done` можно получить исход задачи, а через
`await job.value` значение, возвращённое телом. Сама `Job` не реализует
`Future`: задачу можно запустить без `await`, это обычное дело, а не забытое
ожидание, и линты о неожидаемых future её не трогают.

## Зачем

У обычной `Future` нет отмены. Флаг может попросить работу остановиться,
но спрашивать флаг работе приходится после каждого `await` и каждый раз
закрывать то, что она открыла:

```dart
var cancelled = false;

Future<void> load() async {
  final db = await Database.open();
  if (cancelled) {
    await db.close();
    return;
  }
  final rows = await db.readAll();
  if (cancelled) {
    await db.close();
    return;
  }
  use(rows);
  await db.close();
}
```

Каждому новому `await` нужна своя проверка, а каждый новый ресурс добавляет
свою уборку в каждую проверку. Когда уборка разрастается, проверки начинают
пропускать, а пропущенная проверка пускает работу дальше после отмены, и ничто
не укажет на это место.

`Job` проверяет отмену в каждом `ctx.join`, а закрытие базы регистрирует один
раз:

```dart
final job = Job<void>((ctx) async {
  // Проверка перед вызовом и ещё раз перед возвратом значения,
  // а база закрывается, чем бы Job ни кончилась.
  final db = await ctx.join(Database.open, dispose: (db) => db.close());
  use(await ctx.join(db.readAll));
});

// Кто-то ушёл с экрана, пока шло чтение.
await Future<void>.delayed(const Duration(milliseconds: 50));

// Ждёт тело, его детей и его уборку.
await job.cancel();
print(job.outcome); // Cancelled(manual)
```

`Job` завершается одним из трёх исходов: `Done`, `Failed` или `Cancelled`
с причиной. Перед завершением она ждёт дочерние задачи и выполняет
зарегистрированную уборку. Если исход `Failed` никто не наблюдал, ошибка
передаётся в зону создания задачи, как необработанная ошибка `Future` в Dart.
Наблюдает провал тот, кто обращается к `done` или `value` задачи или вызывает
`ignore()`. Ожидание `cancel()` и чтение `outcome`, как в блоке выше,
наблюдением не считаются, и наблюдатель задачи (`JobObserver`) исход тоже
не наблюдает.

Ошибка, которая не стала исходом, например ошибка уборки, тоже уходит в зону,
если за неё не отвечает наблюдатель задачи (`JobAnswerer`). Но ошибка тела,
случившаяся уже после отмены задачи, например при открытии базы в быстром
старте ниже, доходит только до наблюдателя задачи, а без него ни до кого.
Раздел
[«Куда уходят ошибки»](../../docs/ru/async_job/observing.md#куда-уходят-ошибки)
страницы о наблюдении перечисляет каждую, с наблюдателем и без.

Отмена кооперативная: `cancel()` запрашивает её, а тело останавливается
на контрольной точке. Работающая задача принимает запрос прямо внутри
`cancel()`, если его не придерживает секция `uncancellable` и задача не создана
с `cancellable: false`. С этого момента задача отменена: вызываются её колбэки
`onCancel`, а каждая контрольная точка бросает `Cancelled`. `Job` предоставляет
эти точки через контекст `ctx`, переданный телу. `ctx.join(action)` проверяет
отмену перед запуском операции, дожидается её завершения и проверяет отмену ещё
раз, прежде чем вернуть значение телу.

Прямой `await action()` допустим, но отмену `Job` не проверяет. Он продолжает
ждать, а код после него может выполниться, даже если задача уже отменена.
Поэтому отменяемое тело ждёт через контекст. Внутри действия, переданного
контексту, например шага `ctx.uncancellable` в быстром старте ниже, и при
уборке прямой `await` уместен: контекст не добавляет контрольных точек между
`await` этого действия.

Остановить ожидание Dart умеет и сам. `Future.timeout` останавливает его, когда
выходит время, а `CancelableOperation` из `package:async` перестаёт отдавать
значение по вызову `cancel()` и вызывает при этом свой `onCancel`, который
может попросить работу остановиться. Ни то ни другое не держит того, что работа
открывает: значение, которое пришло после конца ожидания, никому не достаётся,
и поздно открытая база остаётся открытой. `CancelableOperation` может поймать
такую базу, но только в `onCancel`, написанном ради неё и держащем future
открытия:

```dart
final open = Database.open();
final operation = CancelableOperation.fromFuture(
  open,
  // cancel() прекращает ожидание, а здесь база закроется, когда откроется.
  onCancel: () async => (await open).close(),
);
```

`ctx.join` передаёт своему `dispose` и базу, открытую уже после отмены задачи,
и для отмены ничего писать не нужно. Задача при этом завершается, когда база
закрыта. `ctx.abandonable` прекращает ожидание так же, как они, и всё равно
передаёт такую базу своему `dispose`, когда она откроется, даже если задача уже
завершилась.

В `async_job` нет управления состоянием, очереди и правил планирования: их
добавляет [solo](#solo).

Повторы и пул задач не входят ни в один из пакетов; их можно добавить
в приложении. Своего таймаута у `Job` тоже нет: `Timer(limit, job.cancel)`
отменяет её, когда время вышло, и ничего не делает с задачей, которая уже
завершилась. Сам таймер живёт до конца лимита: программа, которой больше нечего
делать, не закончит работу, пока он не сработает. Снять его, когда задача
завершилась, через `job.done.whenComplete(timer.cancel)` значит наблюдать
исход: провал задачи тогда до зоны не доходит, и сообщить о нём должен код,
который снимает таймер.

## Установка

```sh
dart pub add async_job
```

## Быстрый старт

Допустим, нужно открыть базу, выполнить миграцию, пометить базу готовой
и вернуть открытую базу вызывающему коду. При ошибке или отмене базу нужно
закрыть. Контекст позволяет описать оба варианта в теле:

```dart
import 'package:async_job/async_job.dart';

final job = Job<Database>((ctx) async {
  final database = await ctx.join(
    Database.open,
    discard: (database) => database.close(),
  );

  final stop = CancelToken();
  ctx.onCancel(stop.cancel);

  await ctx.join(() => database.migrate(stop));
  await ctx.uncancellable(() async {
    await database.writeVersion();
    await ctx.run(database.readyFlag());
  });

  return database;
});

// Кто-то передумал, пока база открывалась.
await Future<void>.delayed(const Duration(milliseconds: 10));
await job.cancel();

final outcome = await job.done; // Cancelled(manual)
```

- **Тело запускается на следующей микротаске.** Вызывающий код сначала получает
  задачу и может зарегистрировать слушателей до её запуска. Если отменить
  задачу сразу после создания, тело не выполнится, а исходом станет
  `Cancelled(manual)` с `started: false`. Задержка в примере даёт телу
  запуститься.
- **`ctx.join(Database.open)`** вызывает `Database.open` и возвращает открытую
  базу. Если во время открытия придёт отмена, метод дождётся завершения вызова
  и бросит `Cancelled`, если открытие прошло успешно. Если открытие завершится
  ошибкой, он бросит её как есть, даже после отмены. Задача всё равно
  закончится `Cancelled`, поэтому ошибка не станет ничьим исходом: она дойдёт
  до наблюдателя задачи и на нём остановится, а без наблюдателя её не услышит
  никто. См. раздел
  [«Куда уходят ошибки»](../../docs/ru/async_job/observing.md#куда-уходят-ошибки)
  страницы о наблюдении.
- **`discard: (database) => database.close()`** закрывает базу, если задача
  завершается отменой или ошибкой. При `Done(database)` база остаётся открытой
  для вызывающего кода. Уборка учитывает и отмену после `return database`:
  например, если тело запустило дочернюю задачу, которая ещё работает, перед
  завершением задача будет её ждать. Отмена во время этого ожидания приведёт
  к исходу `Cancelled` и закрытию базы. См. раздел
  [«Порядок уборки и поздние результаты»](../../docs/ru/async_job/cleanup.md#порядок-уборки-и-поздние-результаты)
  страницы об уборке.
- **`ctx.onCancel(stop.cancel)`** связывает отмену задачи с токеном отмены
  базы. `CancelToken` принадлежит клиенту базы, а не этому пакету. Колбэк
  вызывается сразу после принятия отмены, до следующей контрольной точки
  в теле.
- **`ctx.join(() => database.migrate(stop))`** ждёт завершения миграции. При
  отмене токен просит миграцию остановиться, а `join` ждёт её остановки, прежде
  чем задача закроет базу. Если нужно прекратить ожидание сразу при отмене,
  используйте `ctx.abandonable`. Он прекращает ожидание, но не останавливает
  саму операцию.
- **`ctx.uncancellable(() async { ... })`** не даёт разорвать последний шаг.
  Шаг пишет версию схемы, а затем запускает ребёнка, `database.readyFlag()`.
  Как только задача приняла отмену, `ctx.run` бросает эту отмену вместо того,
  чтобы запустить ребёнка, поэтому `join` вокруг шага оставил бы версию без
  флага. Внутри секции задача отмену не принимает: ребёнок запускается,
  а `onCancel` не срабатывает. Задача принимает отмену, когда секция
  закрывается, и тело доходит до `return database`, но задача всё равно
  завершается `Cancelled`, а `discard` закрывает базу: секция бережёт шаг,
  а не результат. Шагу из обычного кода, который не берёт токен, отменяемый
  `onCancel`, и не вызывает контекст, секция не нужна: хватает одного `join`
  вокруг него. См. раздел
  [«Придержать отмену»](../../docs/ru/async_job/cancellation.md#придержать-отмену)
  страницы об отмене.
- **`ctx.run(database.readyFlag())`** запускает ребёнка: задачу, которая пишет
  флаг готовности. `readyFlag()` создаёт её через `Job.deferred`, и запуск
  остаётся за `ctx.run`: задача, созданная через `Job(...)`, запускается сама,
  и `ctx.run` отвергает её с `ArgumentError`.
- **`await job.cancel()`** запрашивает отмену и ждёт завершения задачи. Это
  ожидание включает уборку, поэтому исход на следующей строке уже готов. Если
  достаточно только запросить отмену, `await` можно опустить.

Полный запускаемый пример с имитацией `Database` и `CancelToken` находится
в `example/example.dart`. Он запускает задачу четыре раза: один раз до конца
и трижды с отменой, пока база открывается, пока идёт миграция и пока пишется
версия.

## solo

[solo](https://pub.dev/packages/solo) добавляет состояние, очередь
и декларативные правила. Он выполняет одну корневую задачу за раз и даёт ей
исключительный доступ к состоянию. Используйте его, если нужен контроллер
с такими гарантиями. Он реэкспортирует `async_job`, поэтому достаточно
зависимости от `solo`.

Задачи работают везде, где работает Dart. Чтобы связать `solo` с виджетами,
используйте [flutter_solo](https://pub.dev/packages/flutter_solo).
