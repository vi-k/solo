# jobs

Отменяемая `Future`: задача с исходом, детьми, кооперативной отменой и
семьёй ожидания. Чистый Dart, из зависимостей только `meta`.

`Job` — не `Future`, и напрямую её никто не ждёт: `await job.done` — за
исходом, `await job.value` — за значением.

## Зачем

`Future` нельзя отменить. Обычные ответы — флаг, который смотрит тело,
`CancelableOperation`, токен, переданный руками, — оставляют открытыми три
вопроса: чем задача кончилась, кто её ждёт и кто узнает об ошибке, на
которую никто не посмотрел.

Задача отвечает на все три. Она кончается исходом `Outcome`: `Done`,
`Failed` или `Cancelled` с причиной. Она умеет запускать детей и не
считается законченной, пока не закончены они. А `Failed`, который никто не
наблюдал, уходит в зону создания задачи — ровно так Dart поступает с
необработанной ошибкой `Future`.

`CancelableOperation` прекращает ожидание точно так же. Чего у неё нет —
это исхода, которым всё кончается, детей, которых надо дождаться,
контрольных точек внутри тела и наблюдателя, который слышит ошибки,
которым больше некуда идти.

Отмена кооперативная: `cancel()` помечает задачу, а останавливается тело
само. Поэтому каждое ожидание в теле идёт через контекст — `await
ctx.wait(action)`, а не `await action()`. Future, который ждут напрямую,
прервать нечем: пометка пришла, а тело продолжает ждать вызов, который о
ней не знает. Какой член контекста выбран, то отмена с этим вызовом и
сделает.

Здесь нет ни состояния, ни очереди, ни правил, ни повторов, ни таймаутов,
ни пула. Нужно что-то из этого — берите `solo`: он построен на этом пакете
и реэкспортирует его целиком, так что тот, кто зависит от `solo`, от `jobs`
отдельно не зависит.

## Установка

```sh
dart pub add jobs
```

## Быстрый старт

```dart
import 'package:jobs/jobs.dart';

final job = Job<Database>((ctx) async {
  final database = await ctx.join(
    Database.open,
    discard: (database) => database.close(),
  );

  final stop = CancelToken();
  ctx.onCancel(stop.cancel);

  await ctx.join(() => database.migrate(stop));
  await ctx.uncancellable(() => database.markReady(stop));

  return database;
});

// Кто-то передумал, пока база открывалась.
await Future<void>.delayed(const Duration(milliseconds: 10));
await job.cancel();

final outcome = await job.done; // Cancelled(manual)
```

По строкам — потому что каждая из них решение:

- **Тело стартует на следующей микротаске**, а не внутри конструктора:
  вызывающий сначала получает хэндл и может на него подписаться — или
  отменить задачу до того, как тело вообще начнётся. Ради этого выше и
  стоит задержка: задача, отменённая на той же полосе, кончается
  `Cancelled(manual)` с `started: false`, и из тела не выполняется ничего.
- **`ctx.join(Database.open)`**, а не `ctx.wait`: начавшееся открытие не
  бросают на полпути, иначе база откроется, а держать её будет некому.
- **`discard: (database) => database.close()`** закрывает всю жизнь этой
  базы одной строкой и один раз. Не только значение, которое вернулось,
  когда задача уже сдалась, — всё, что после него, тоже: отмену между
  шагами, ошибку внутри шага, отмену, пришедшую после `return`. Базу
  закроют, если она не досталась вызывающему. Ни `try`, ни `finally`,
  перед `return` помнить нечего, и регистрировать второй раз тоже нечего —
  одно значение, одна регистрация. См. [Уборку](#уборка).
- **`ctx.onCancel(stop.cancel)`** — так `cancel()` доходит до самой базы.
  Колбэк срабатывает в момент пометки, раньше, чем о ней узнаёт тело, и
  всё, что база делает, получает команду остановиться сразу.
- **`ctx.join(() => database.migrate(stop))`** по той же причине, что и
  открытие: миграции велят остановиться через этот токен, а `join` ждёт,
  пока она действительно остановится. `ctx.wait` прекратил бы ожидание и
  оставил её писать в базу, которую это же тело сейчас закроет.
- **`ctx.uncancellable(() => database.markReady(stop))`** — для шага,
  которому нельзя даже велеть остановиться. `join` здесь не подходит, и в
  этом вся разница между ними: `join` придерживает ожидание, а не отмену.
  Под ним колбэк выше уже сработал, `stop` уже отменён, и `markReady`
  сдастся на середине — вызова дождутся, но это вызов, который
  останавливается. `uncancellable` придерживает саму отмену. Проще
  говоря: пока тело внутри секции, `onCancel` не вызывается вовсе — он
  вызывается сразу, как секция кончилась, а тело узнаёт об отмене уже после
  этого, на ближайшем своём обращении к контексту, — см.
  [Отмену](#отмена).
- **`await job.cancel()`** возвращается, когда задача действительно
  закончилась, поэтому исход ниже уже готов. Сам `await` — выбор: отмена
  пройдёт в любом случае, а без него просто не ждут конца.

`example/example.dart` — это тот же фрагмент с фальшивой `Database`
вокруг.

## Исходы

`Outcome<T>` — sealed, поэтому `switch` по трём его случаям исчерпывающий:

```dart
final message = switch (await job.done) {
  Done(:final value) => 'done $value',
  Failed(:final error) => 'failed $error',
  Cancelled(:final reason) => 'cancelled $reason',
};
```

`Cancelled` несёт `reason`, флаг `started`, необязательное `description` и
стектрейс самой отмены. Причина — это `CancelReason`, здесь их три:
`manual`, `parent` и `handler`. Это не enum и не sealed: движок,
построенный поверх этого, объявляет свои причины через
`const CancelReason('closed')`, а равны они по имени.

`job.done` завершается исходом и никогда не бросает; `job.value`
завершается значением или бросает; `job.whenCancelled` завершается на
любом исходе `Cancelled` — у работающей задачи в момент, когда её
отметили, ещё до конца тела, а у тела, отменившего себя само, — когда
это тело кончилось и дети закончены, прямо перед уборкой. У задачи, кончившейся `Done` или `Failed`, он не
завершается вовсе, поэтому работу на него вешают через `.then(...)` или
гонят наперегонки с `job.done`: голый `await job.whenCancelled` на удачно
закончившейся задаче встаёт намертво. `job.cancel()` отменяет и ждёт, пока
задача действительно завершится; `job.ignore()` говорит, что на исход
никто смотреть не будет.

## Отмена

`cancel()` помечает задачу; остановиться — дело тела. До тела пометка
доходит броском: после пометки `Cancelled` бросают те члены, которые ждут
или что-то начинают, — `check`, `wait`, `join`, `uncancellable`, `onCancel`,
`run` и `each`. Те, которые только регистрируют, работают по-прежнему, так
что только что отменённое тело всё ещё может положить на стек уборки то, что
держит: `onDispose`, `onDiscard`, `disown` и `unattended`. А `Cancelled` —
это `Exception`. Достаточно широкий `catch` проглотит отмену, и тело пойдёт
дальше:

```dart
try {
  await ctx.join(database.migrate);
} on Cancelled {
  rethrow; // эту — никогда не глотать
} on Exception catch (error) {
  ctx.log('migration failed: $error');
}
```

Не всякий `Cancelled`, который видит тело, — его собственный: тот, что
пришёл из `await child.value`, говорит, что сдался ребёнок, и такой ловить
законно — необязательный шаг не вышел. Внутри такого `catch` их различает
`ctx.check()`: он бросит, только если отменена и сама задача.

Исходом всё равно будет `Cancelled` — этим проглоченная отмена и дорога:
снаружи задача кончилась правильно, а тело продолжало работать. Ловите
тот тип, за которым пришли, и пропускайте отмену дальше.

Тело не должно делать `await` само по себе, и выбранный член говорит, что
отмена сделает с этим вызовом:

- `ctx.wait(action)` прекращает ожидание, но не работу. Действие
  доработает, его результат выбрасывается — или уходит в заданный ему
  уборщик, а тот идёт по стеку уборки, пока задача его раскручивает, — и
  закрытие движка его дождётся; в одиночку он работает, только когда
  задача уже кончилась.
- `ctx.join(action)` дожидается всего действия и сдаётся после него:
  команду устройству, уже ушедшую в провод, не бросают на полпути. Его
  уборщика дожидаются до броска `Cancelled` — значит, тот, кто ждёт
  задачу, дождётся и освобождения.
- `ctx.each(stream, onData)` следует за стримом столько, сколько живёт
  задача. Подписка снимается в момент пометки, до того как тело узнает об
  отмене, и ещё раз — когда задача заканчивается с любым исходом, так что
  слушать не остаётся никто даже за телом, ушедшим от этого вызова.
  `onData`, вернувший футуру, дожидается, и доставка на это время
  придержана: события сохраняют порядок.
- `ctx.uncancellable(action)` придерживает отмену на время вызова: пока
  он идёт, задачу не помечают вовсе, поэтому в шаг не дотянется ни колбэк
  `onCancel`, ни каскад на детей. Отмена срабатывает в момент закрытия
  секции, и ближайший вызов контекста её бросает. Шаг, чей хвост тоже
  обязан выполниться, кладут в ту же секцию; задача, которая должна
  пережить отмену целиком, создаётся с `cancellable: false`.
- `ctx.onCancel(callback)` срабатывает в момент пометки, до того как тело
  узнает об отмене: так отмена доходит до того, кто умеет остановиться
  по-настоящему, — токена, обрыва запроса, подписки.
- `ctx.unattended(action)` не ждёт вовсе. Работа отдана движку, и тело
  идёт дальше; отмена её не трогает, а всё, что она бросит — сейчас или
  много позже конца задачи, — приходит в `onError`, а не в процесс.
  Начинай работу внутри и не выноси наружу ничего, что внутри родилось:
  граница её error-зоны двусторонняя.
- `ctx.check()` сдаётся там, где обёртывать нечего.

```dart
final job = Job<void>((ctx) async {
  final token = CancelToken();
  ctx.onCancel(token.cancel);
  await ctx.join(() => device.seek(position, cancelToken: token));
  ctx.unattended(() => analytics.report('seek', position));
});

final feed = Job<void>((ctx) => ctx.each(socket.messages, handle));
```

Задача, созданная как `Job(body, cancellable: false)`, отказывает всякой
отмене, которой может отказать, — с того момента, как стартовала: до
запуска тела защищать нечего, и такую задачу сбрасывает любая отмена.
Собственные правила — те, что добавит движок сверху, — действуют всё
равно.

## Дети

`ctx.run(child)` запускает ребёнка прямо сейчас, в обход любой очереди,
которую заведёт движок сверху. Родитель не закончен, пока не закончены
дети; отменённый родитель роняет их каскадом, а неотменяемый ребёнок
каскаду отказывает. Тело, сдавшееся само через `throw Cancelled(...)`,
роняет детей тоже; тело, которое *упало*, оставляет их доработать и
дожидается.

```dart
final parent = Job<void>((ctx) async {
  final child = ctx.run(Job.deferred<int>((ctx) => ctx.wait(load)));
  final rows = await child.value;
  ctx.log('$rows rows');
});
```

`Job.deferred`, а не `Job`, потому что старт ребёнка принадлежит
родителю: автозадача, до которой `run` не дошёл на той же синхронной
полосе, стартует сама — корневой, никем не усыновлённой, вне каскада
отмены и без ожидания, — и `run` потом откажет ей как уже запущенной.

Ребёнок наследует наблюдателя родителя, если ему не дали своего, а отмена
ребёнка, всплывшая через `child.value`, помечает исход родителя как
`handler` и называет ребёнка.

`run` умеет не только запускать, но и отказывать: чужой для этого ядра
хэндл — `ArgumentError`, уже запущенная задача — `StateError`, кончившееся
тело — тоже `StateError`, потому что начатого тогда ребёнка никто не будет
ждать, а уже отменённый родитель бросает собственный `Cancelled`, и
ребёнок при этом выбрасывается — на это рано или поздно наткнётся тело,
запускающее детей после долгого ожидания.

## Уборка

Что тело открыло, оно тут же и регистрирует — там же, одной строкой:

```dart
final lock = await ctx.join(Lock.acquire, dispose: (lock) => lock.release());
final database = await ctx.join(
  Database.open,
  discard: (database) => database.close(),
);

await ctx.join(database.migrate);

return database;
```

Два слова, и разница между ними несёт весь механизм:

- **`dispose`** работает при любом исходе. Лок, временный файл, счётчик:
  освобождают и на успешном пути, иначе он останется занят навсегда.
- **`discard`** работает, только когда значение никому не досталось —
  отмена или ошибка. База выше на успехе уходит вызывающему, и закрыть её
  тогда было бы дефектом; когда её не получает никто, её закрывает движок.

Правило выбора — одна строка, и это единственная ошибка, которую движок
поймать не может: **`discard` — только для того, что тело возвращает или
передаёт наружу; всё остальное берёт `dispose`.** `discard` на временном
файле, который тело не возвращает, на успехе не сработает — утечка на
счастливом пути, которую не покажет ни один тест на отмену.

Для значения, которое пришло не из вызова, то же самое говорят два члена:

```dart
final buffer = StringBuffer();
ctx.onDispose(() => sink.add(buffer.toString()));
```

Обе формы возвращают функцию снятия; для значения из `wait` или `join`
есть `ctx.disown(value)` — на случай, когда тело передало значение само и
уборка перестала быть его делом.

**Как это работает.** Движок раскручивает стек одним проходом, с
последней регистрации, после детей и до исхода — дети раньше потому, что
они ещё могут пользоваться тем, что открыл родитель, — и дожидается
каждого уборщика, поэтому `close()` движка поверх дождётся и
освобождения. Уборщик работает вне тела: контекст тела там закрыт, ничто
его не отменяет, и ждать собственную задачу он не должен. Короткий и
безусловный; ошибка одного уходит наблюдателю, а остальные всё равно
отработают.

**Поздние значения.** Между `return` тела и исходом задача ещё жива — она
ждёт детей, — и пришедшая туда отмена побеждает. Значение к этому моменту
уже зарегистрировано, поэтому его освободят, как и всякое другое; а
значение, вышедшее из вызова, который тело бросило, освободят при любом
исходе — до тела оно не доехало:

```dart
final job = Job<Database>((ctx) async {
  final database = await Database.open();
  ctx.onDiscard(database.close);

  return database;
});
```

Прерывать в этом теле нечего: оно отдаёт ядру future, ядро его и ждёт, а
отмену, пришедшую тем временем, тело не увидит, пока значение не
вернётся. Регистрация сразу за ним и закрывает этот зазор.

## Наблюдатель

`JobObserver` — сквозной канал одной задачи: `onStart`, `onFinish`,
`onError`, `onLog`. У всех четырёх тела пустые, так что слушатель
переопределяет только нужное; `implements` тоже годится — для слушателя,
который уже что-то наследует. Передаётся при создании; ребёнок без своего
наследует родительского. Хук, который бросил, отдаёт ошибку текущей зоне и
больше ничего не меняет.

```dart
final class Log extends JobObserver {
  @override
  void onFinish(Job<Object?> job) => print('$job: ${job.outcome}');
}

final job = Job<int>(
  key: 'load',
  observer: Log(),
  (ctx) => ctx.wait(load),
); // Job(load): Done(3)
```

Задача печатает себя как `Job($key)` — значит, ключ и есть то, чем она
называется в журнале, и то, по чему её сравнивает движок сверху, как это
делает `solo` в политиках очереди. `describe` добавляет строку тому, кто
этот журнал читает.

У ошибок два пути, и это не одно и то же. Ошибка тела идёт наблюдателю и
становится исходом `Failed`; в зону она попадает, только если исход никто
не наблюдал. Четыре ошибки, которым больше некуда идти, — поздний отказ
действия, брошенного `wait`, ошибка диспозера, ошибка колбэка `onCancel` и
провал работы, отданной `ctx.unattended`, — идут наблюдателю, а без него
сразу в зону. Тишина — выбор того, кто слушает. Второй дорогой не идёт
`Cancelled`: отмена — не провал, а чьё-то решение, и слышит её только
наблюдатель.

## Отложенный старт

`Job.deferred(body)` возвращает `DeferredJob<T>` — с добавкой в виде
публичного `start()`. Запускает задачу тот, кто ею распоряжается: вручную,
очередь или родитель через `ctx.run(child)`.

```dart
final job = Job.deferred<void>((ctx) => ctx.wait(work));
// ... позже, или из своей очереди
job.start();
```

## Тестирование

Задача стартует одной микротаской, а заканчивается другой, поэтому тест
задачи — это тест про цикл событий. `package:fake_async` прогоняет его без
часов; сьюта этого пакета устроена так же:

```dart
test('a cancelled open still closes what it opened', () {
  fakeAsync((async) {
    final job = Job<Database>(
      (ctx) => ctx.join(Database.open, discard: (db) => db.close()),
    );

    async.elapse(const Duration(milliseconds: 10));
    job.cancel().ignore(); // внутри `fakeAsync` никто ничего не ждёт
    async.flushTimers();

    expect(job.outcome, isA<Cancelled>());
  });
});
```

Чтобы задача стартовала, хватает `flushMicrotasks()`; а всё, что стоит на
`Future(...)` или `Future.delayed(...)`, — это таймер, а не микротаска, и
ему нужны `flushTimers()` или `elapse(...)`.

## Своё поверх ядра

`JobBase<T>` и `JobContextBase` — два класса, которые наследует движок
предметной области. Наследник добавляет то, чего у ядра нет, — состояние,
очередь, правила, — и всё, что нужно движку, объявлено защищённым: статус,
отмеченная отмена, дети, старт, завершение, отмена с флагом отклоняемости и
два хука, которые задача предметной области заполняет сама, — `started()` и
`finished()`. Ещё два — про маршруты ошибок: `reportToZone` для движка, у
которого свой путь для ошибки, которой некуда идти, кончается ничем, и
`throwIfUnattended` для члена его контекста, который нельзя звать из работы
без присмотра.

```dart
final class MyJob<T> extends JobBase<T> {
  final Future<T> Function(MyContext ctx) _body;

  MyJob(this._body, {super.key, super.observer});

  @override
  JobContextBase createContext() => MyContext(this);

  @override
  Future<T> execute(covariant MyContext ctx) => _body(ctx);

  // `start` защищён: движок открывает к нему свою дверь.
  void launch() => start();
}

final class MyContext extends JobContextBase {
  MyContext(super.owner);
}

final job = MyJob<int>((ctx) => ctx.wait(load))..launch();
```

Две вещи стоит знать заранее. `check()` — контрольная точка, через которую
проходит каждый член семьи ожидания: `wait`, `join` и `uncancellable`
начинают с неё, — поэтому область, которая проверяет больше отмены,
переопределяет её и получает всю семью бесплатно. И `@protected` действует
только внутри наследника: движку, который трогает задачу со стороны, нужны
приватные обёртки на своём наследнике, а не прямые вызовы, — `launch`
выше как раз такая.

`solo` устроен именно так. Защищённая поверхность — это половина пакета, и
расписана она в справке
[JobBase](https://pub.dev/documentation/jobs/latest/jobs/JobBase-class.html).

## solo

[solo](https://pub.dev/packages/solo) добавляет поверх этих задач
состояние, очередь и правила: не больше одной корневой задачи в момент,
монопольное владение состоянием, декларативные правила. Если нужен
контроллер, а не задача, начинайте оттуда — и зависьте только от него: он
реэкспортирует этот пакет целиком.

Ничего специфичного для Flutter здесь нет: задачи работают везде, где
работает Dart. Виджетный слой `solo` — это
[flutter_solo](https://pub.dev/packages/flutter_solo).
